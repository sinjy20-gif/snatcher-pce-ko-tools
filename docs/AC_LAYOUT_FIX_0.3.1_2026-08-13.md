# AC 레이아웃 결함 규명과 0.3.1 수정 — 2026-08-13

대량 UI(989행)에서 글자가 깨지던 원인을 기전 수준까지 확정하고 고쳤다.
`DYNAMIC_HANGUL_FONT_RESEARCH_HANDOFF_2026-08-13.md` 가 "강한 추정"으로 남겨둔
항목이 여기서 확증으로 바뀌었고, 그 문서의 결론 일부는 폐기해야 한다.

---

## 1. 원인 — atlas가 resident 팩을 침범

### 두 계산이 서로를 몰랐다

```python
# 초기 CD→AC 적재량: atlas 크기로만 결정
init_total = align(DIRECTORY_BYTES + STATE_SPAN + TEMPLATE_BYTES + len(atlas), CHUNK_BYTES)

# resident 팩 목적지: atlas를 전혀 참조하지 않는 하드코딩 상수
cursor = align(dynamic.COMMON_DATA_BASE, USER_BYTES)   # $16000
```

두 값을 비교하는 코드가 없었다. 유일한 검사(`build_ac_dynamic_0_1_14.py:179`)는
16비트 창 검사지 배치 검사가 아니다. 그래서 `byte_exact_verified` 가 전량 통과해도
런타임 배치는 깨질 수 있었다.

### 적재 순서가 파괴 방향을 정한다

`build_ac_dynamic_0_1_14.py:343-363` 에서 확정:

```
부팅 첫 조회 → MAGIC($10000 = AC 15 51) 없음 → init_store
    DEST=$000000, LEFT=init_chunks 로 연속 전송 (0xFF 패딩 포함)
    MAGIC 기록 → 이후 재실행 없음
그 다음 조회 → load_package → metadata의 destination으로 팩 전송   ← 나중
```

초기 적재가 먼저, 팩이 나중. 따라서 **팩이 atlas 꼬리를 덮는다.** 그리고 init은
MAGIC 가드라 세션 중 재실행되지 않으므로 **파워사이클 전까지 복구되지 않는다.**

### 임계점은 절벽이다

`init_total` 이 8 KiB 청크로 올림되므로 실제 덮는 범위는 atlas 끝이 아니라
`align(atlas_end, $2000)` 이다.

```
glyphs  atlas_end  init_total  speaker $16000
   741     $16000      $16000  OK          ← 마지막 안전
   742     $16020      $18000  8,192 B 파괴 ← 32B가 아니라 청크 통째로
  1089     $18B80      $1A000  16,384 B 파괴
```

### 파괴 대상을 이름으로 특정

실패본 `direct_records.tsv` 로 atlas 순서를 재현했더니 **정확히 1,089개**로
manifest와 일치했다(atlas는 레코드 TSV 행 순서로 순회하고, 레코드 내부 글리프
슬롯은 음절 정렬순이다).

```
index 740  루   ← 마지막 생존
index 741  썩   ← 여기부터 348개 파괴
           "썩 좋은 취향은 아니군."  (111800:2636:1)
출처: dialogue 190 / ui 150 / speaker 8
```

UI만의 문제가 아니었다. 본문 대사와 화자명도 같이 죽고 있었다.

## 2. 수정 (0.3.1)

`build_ac_dynamic_0_1_14.py`

```python
common_base = max(dynamic.COMMON_DATA_BASE, init_total)
dynamic.COMMON_DATA_BASE = common_base   # manifest가 실효값을 보고하도록
```

`max()` 인 이유: atlas가 `$16000` 아래면 기존 베이스를 유지하므로 **ac_0.1.14 가
그대로 재현된다.** 커지면 resident가 따라 밀린다.

추가로 fatal extent 감사를 넣었다. 초기 적재·resident 팩·scene 바닥을 정렬해
인접 구간이 겹치면 빌드를 죽이고, 몇 번 인덱스부터 깨지는지 메시지에 찍는다.
scene 팩은 설계상 `scene_base` 를 공유하므로 감사에서 제외한다.

진입점은 `build_snatcher_ko_0_3_1.py` 로 개명했다(파일명과 버전이 어긋나면
프로젝트가 계속 싸워온 "번호 함정"이 재발한다).

## 4. 연구 문서에서 폐기해야 할 결론

`DYNAMIC_HANGUL_FONT_RESEARCH_HANDOFF_2026-08-13.md` §10.2 는 현대 한글 전체
초기 적재를 "약 8.3초, 권장 불가" 로 판정했다. 근거가 `44 호출 x 188ms` 인데,
동결 파이프라인 문서 §8이 그 모델을 **명시적으로 "틀림"으로 표시**한다.

```
틀림   시간 = 호출수 x 188ms + 바이트/150KB/s
맞음   시간 = 바이트 / 34 KB/s        (호출 수는 거의 무관)
```

측정 모델로 다시 계산한 값:

```
시나리오                bitmap      init      1x      8x
현재 출하 (검토 O)         692    90,112 B   2.59s   0.32s
마스터 전량 + UI 전량     1,405   114,688 B   3.29s   0.41s
대사 2.0배 + UI 전량     1,560   122,880 B   3.53s   0.44s
대사 2.5배 + UI 전량     1,638   122,880 B   3.53s   0.44s
현대 한글 전체(양 shift) 22,344   698 KB      —       2.82s
```

`init` 의 65,536 B는 디렉터리라 글리프와 무관하게 항상 읽는다. 최종 상태에서도
글리프 순증가분은 52 KB, 8배속 0.19초다. **용량도 로딩도 제약이 아니다.**

따라서 동적 폰트 공급 구조 · scene별 glyph 팩 · 174+α 조합기는 전부 "정적 atlas가
불가능하다"는 전제 위에 있었고, 그 전제가 성립하지 않는다.

⚠ 남은 가정 하나: 34 KB/s 는 레코드 적재 경로 실측값이고 초기 벌크 전송에
그대로 적용된다는 별도 측정은 없다. 연속 전송이라 유리할 가능성이 높지만
0.3.1 부팅 시간 실측으로 닫아야 한다(예측 8배속 0.38초).

## 5. 코퍼스 실측

### 고유 음절과 포화

```
BODY 번역 6,479행 → 942자     UI 989행 → 462자     화자명 → 96자
합집합 967자 = 현대 한글의 8.7%
```

포화가 확실하다.

```
   647행 → 548자   (1000행당 +543)
 1,619행 → 727자   (+194)
 3,239행 → 834자   (+55)
 6,479행 → 942자   (+24)
 마지막 1000행 신규 발견율 0.02 자/행
```

대사가 2.5배로 늘어도 1,638 bitmap을 넘기 어렵다. UI는 990행 중 989행이 번역돼
있어 462는 사실상 확정값이다.

### y_shift 는 배수가 아니라 두 집합이다

`hangul_y_shift` 를 kind가 100% 결정한다. 예외 없음.

```
dialogue  0     speaker  0     ui  -1
```

즉 같은 음절이라도 BODY용과 UI용 비트맵이 별개다. 715 음절 → 1,089 bitmap
(1.52배)의 정체가 이것이고, 배수가 아니라 **shift0 집합 + shift-1 집합의 합**으로
정확히 계산된다.

```
마스터 전량 + UI 전량 = shift0 943 + shift-1 462 = 1,405
```

이건 `build_ac_dynamic_0_1_14.py` 모듈 docstring이 이미 적어둔 사실이다
("UI glyphs are shifted up one pixel: the same syllable has a BODY bitmap and a
UI bitmap"). 연구 문서가 미지수로 남긴 항목이 실은 기록돼 있었다.

## 6. 알려진 남은 항목

### A. 화자명과 병합된 UI 라벨 22건이 1px 낮게 그려진다

UI 라벨의 일본어 원문이 화자명과 같으면 화자명 레코드로 병합되고, 화자명은
`y_shift=0` 이라 그 항목만 1픽셀 내려간다.

```
국장   kind=speaker  ref=speaker:3,ui:UI0109   y_shift=0    ← 1px 아래
모니터  kind=ui       ref=ui:UI0073             y_shift=-1
```

접수처의 **안내원**(`speaker:1,ui:UI0116`)도 같은 경우다. 총 22건 — 길리언·해리·
미카·리사·이사벨라 등 화자명과 겹치는 UI 라벨 전부.

한국어가 양쪽 일치하면 에러 없이 조용히 병합된다. 불일치하면 아래 B로 간다.
순수 미관 문제라 이번에는 넘어가기로 했다.

### B. speaker/UI 원문 충돌 5건

같은 일본어에 다른 한국어가 붙어 런타임 trie가 구분할 수 없는 경우.
빌더가 `speaker/UI source conflict` 로 큰 소리로 죽인다.

```
UI0241 呼び込み          호객   vs 호객꾼
UI0350 <원문 5자>        오카네상 vs 오카네씨
UI0351 <원문 6자>      가면라이더 vs 가면 라이더
UI0370 イワン            어반   vs 이반
UI0419 <원문 8자>  코우네리상 vs 코우네리 아저씨
```

인계서 §7의 기존 결정대로 UI 쪽 검토를 해제했다. 다섯 건 모두 **같은 인물**을
다르게 옮긴 것이라, 한국어를 화자명 쪽으로 통일하면 전부 출하 가능하다.

### C. 레코드당 15자 제한에 4행이 걸려 있다

704B 레코드의 글리프 슬롯은 19개 = 상수 3 + 가용 15 + fractional-space 헬퍼 1.
한 줄에 서로 다른 한글이 16자를 넘으면 담을 곳이 없다.

```
19자  '데이터를 천성의 목소리 뱅크에 복사하는 것을'
16자  '…해리의 젊은 시절이라고는 생각 안 되는군.'  (2행)
16자  '을 모토로 서비스를 제공하고 있습니다.'
```

atlas 상한과 무관한 별개의 구조 제약이다. 다만 빌드가 예외로 죽으므로 조용히
깨진 디스크를 뱉지 않는다. 해결은 번역 쪽(문장 분할 또는 어휘 교체)이다.

### D. ★ 항목 8건은 출하 제외

`UI0162 ★フレ★<원문 5자>` 는 개발자 디버깅 메뉴다. 나머지 7건(`★`, `★★`,
`０★` 등)은 category=candidate 파편이다. 전부 검토 해제했다.

### E. 세이브 후 타이틀 복귀 시 화면 깨짐 — 원인 규명 완료

인계서 §8-B. **우리 버그가 맞고, 원인은 뱅크 `$69` 헬퍼 케이브다.**

#### 대조 실험

원본 무패치 디스크에서 같은 조작(세이브 → 타이틀 → 로드)은 **정상**이다.
BRAM 세이브는 큐 파일명으로 저장되므로, `[KO 0.3.1].sav` 를
`Snatcher CD-ROMantic (Japan).sav` 로 복사하면 재플레이 없이 원본에서 바로
같은 지점을 로드할 수 있다.

#### 기각된 가설 (기록용 — 같은 길을 다시 가지 않기 위해)

```
AC 오염          magic AC 15 51 / flags / atlas 전부 소프트 복귀 후에도 불변
CD 베이스 미복원  우리 로더는 파손 세션 내내 읽기 0회 ($E006 0회).
                 게임의 $E009 섹터 시퀀스는 원본 실행과 바이트 단위로 동일
                 (18/3600, 03/7E00, 17/BE03, 0C/6E00 …)
훅/캐시 손상     훅은 항상 20 50 7F / 20 40 5E / 20 20 5E, 캐시는 항상 유효 SDR4
트램폴린 MPR5    505프레임짜리 헬퍼 호출에도 프레임 경계 MPR5=$69 가 0건.
                 BIOS가 전송 중 매핑을 자기 것으로 바꾼다. SEI 부재는 무관
```

#### 확정된 기전

`PROBE_SAVELOAD_STATE_v4.lua` 가 케이브 `$BCD2-$BFFF` 에 읽기 콜백을 걸어 잡았다.

```
f5771   342 reads  $BCD2-$BE27   inHelper=false
f5772   472 reads  $BE28-$BFFF   inHelper=false
        342 + 472 = 814 = 케이브 크기 정확히
```

게임이 케이브 **전체를 순차로 긁어간다.** 두 프레임에 나뉘므로 TIA/TII 블록전송이
아니라 루프다(정적 검색에서 `src=$BCD2` 또는 `len=814` 인 블록전송 명령 0건).

원본 `track02.iso` 의 그 자리(ISO `$07F4D2-$07F7FF`)는 **814바이트 전부 `FF`** 다.
즉 원본은 `FF` 를 퍼가고, 우리는 그 자리에 헬퍼 코드를 넣었으므로 **우리 코드가
타일 데이터로 화면에 그려진다.** 텍스트가 멀쩡한 것도 이 구조와 맞는다 —
글리프 공급 경로는 무사하고 그래픽만 오염된다.

#### 교훈

케이브 검증은 "게임이 실행하지 않는다"를 증명했다. 사실이었다. 증명되지 않은 것은
**"읽지도 않는다"** 였다. `FF` 로 채워진 것은 미사용의 증거가 아니라 **의도적으로
`FF` 로 채워둔 소스**였다.

이 프로젝트는 이미 같은 원칙을 다른 구간에 대해 적어뒀다 — "not allocated is not
proven free", "no execution/reference census ... therefore not a free-space
finding". 뱅크 `$69` 케이브에는 적용되지 않았다. 오늘 atlas 중첩과 정확히 같은
부류다: 검사하지 않은 축에서 조용히 깨졌다.

### F. 헬퍼를 옮길 자리 (조사 중)

상주 프로그램 뱅크의 `FF` 구간은 전부 이미 우리 것이다.

```
bank 68  $1BB3-$1FFF  1,101 B   레코드 캐시 + 프리로더
bank 69  $1CD2-$1FFF    814 B   실패한 케이브
bank 6A  $1F50-$1FFF    176 B   폰트 래퍼 + 섹터 로더 + 상태
```

뱅크 `$70` 이상에는 `FF` 가 많지만 쓸 수 없다. `$0940-$1018` 1,753바이트가
뱅크 70·78·79·7A·7B·7C·7D 에 **동일 오프셋으로 반복**된다 — 장면 슬롯의 구조적
패딩이고 CD 재적재가 덮는다. 헬퍼는 상주해야 하므로 불가.

남은 후보는 **전부 0인 뱅크** `$60`, `$61`, `$6C` 다. `$6C` 는 코드 뱅크
`$6B`/`$6D` 사이에 있으면서 8,192바이트가 단일 값 `00` 이다.

기준을 바꿨다. "누가 읽는가"가 아니라 **"이 뱅크가 매핑된 적이 있는가"** 다.
CPU는 매핑하지 않은 뱅크를 건드릴 수 없으므로, 한 번도 매핑되지 않는 뱅크는
구조적으로 안전하다. 트램폴린은 이미 뱅크를 직접 매핑하므로(`LDA #$69`) 대상만
바꾸면 된다.

⚠ 전부 0인 것은 양날이다. 적재되지 않은 뱅크일 수도 있고, 초기값 없는 작업
영역(BSS)일 수도 있다. 후자면 최악의 자리다. 디스크 이미지로는 구분되지 않으므로
`lua/CENSUS_BANK_USAGE_0.1.1.lua` 로 측정한다. **매핑되면 사용 확정, 안 되면 후보일
뿐 증명이 아니다** — 프레임당 1회 샘플링이라 짧은 매핑을 놓친다(v3에서 헬퍼 호출
72회 중 7프레임만 잡힌 실측 근거가 있다).

## 7. 빌드 산출물 관리

빌드당 실비용은 **200 MB**(패치된 Track 02 + Track 24)다. 나머지 22트랙은
`rom(japan)` 과 같은 inode라 0이다. 누적 1.67 GB까지 불어나 있던 것을 정리했다.

```
python build_snatcher_ko_0_3_1.py            빌드 후 자동 프루닝
python build_snatcher_ko_0_3_1.py --no-prune 이전 빌드 이미지 유지
python build_snatcher_ko_0_3_1.py --prune    정리만
python build_snatcher_ko_0_3_1.py --prune --deep   중간물까지 (--stage3 포기)
```

보호 목록은 현재 버전 · `ac_0.1.11-source` · `ac_0.1.14` 다. manifest·TSV·검증
로그는 전 빌드 합쳐 5 MB 미만이라 **어느 경우에도 지우지 않는다** — 옛 빌드를
감사 가능하게 만드는 것이 그 기록물이다.

⚠ `ac_0.1.14` 는 현재 **재현 불가**다. 오늘 전체 빌드가 `ac_0.1.11-source`
중간물을 현재 마스터 기준으로 재생성했기 때문이다. 그 200 MB가 출하 검증본의
유일한 사본이므로 보호 목록에서 빼지 말 것.
