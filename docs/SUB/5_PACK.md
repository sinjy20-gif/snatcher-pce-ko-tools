# 자막 팩 — 데이터를 코드에서 떼어냈다 (2026-08-23 저녁)

`SNATCHER_SUBTITLE_PIPELINE_2026-08-23.md` 다음이다. 그 문서 §9.1 이 남긴
질문 — "코드를 어디 둘 것인가" — 은 **아직 안 풀렸다**. 대신 그 답과 무관하게
확정인 것부터 만들었다.

---

## 1. 왜 데이터만 따로 굽나

`build_subtitle_disc_payload.py` 는 폐기됐다. `$5C40-$5E1F` 를 상주 코드 자리로
가정했는데 거기가 스크립트 VM 데이터 스택이었다.

그 폐기가 무효로 한 것은 **배치**지 **데이터**가 아니다.

```
폐기      $5C40 상주 가정 · 1 차 페이로드의 코드 배치
살아남음  글꼴 · 트리거(ADPCM 지문 · CD-DA LBA) · 세그먼트 표 · 글자 배치 계산
```

감시자를 헬퍼 여유 151 B 에 두든 다른 데 두든, **자막 데이터는 한 글자도 안 바뀐다.**
그래서 지금 만들 수 있었다. `tools/build_subtitle_pack.py`.

---

## 2. 팩 형식 (버전 2)

AC `$1C0000` 에 통째로 올라간다. 예약은 256 KB.

### 머리 64 B

```
+00  magic        "SNSB"
+04  version      u16 = 2
+06  flags        u16 = 0
+08  glyph_count  u16
+0A  glyph_off    u32
+0E  adpcm_count  u16      ★ 조각 수다 (이벤트 수가 아니다)
+10  adpcm_off    u32
+14  cdda_count   u16
+16  cdda_off     u32
+1A  record_off   u32
+1E  pack_bytes   u32
+22  glyph_bytes  u8  = 64
+23  cell_bytes   u8  = 4
+24  limit_px     u16 = 192
+26  char_off     u32
+2A  adpcm_stride u8  = 12
+2B  cdda_stride  u8  = 10
+2C  rec_header   u8  = 6
```

모두 리틀엔디안. 오프셋은 **팩 머리 기준**이라 AC 어디에 올리든 그대로 쓴다.
항목 크기를 머리에 적어 둔 것은 런타임이 판마다 상수를 새로 박지 않게 하려는 것이다.

### 색인 둘 — 트리거 성격이 다르기 때문이다

```
ADPCM  12 B  읽기주소 u16 · 길이 u16 · 재생률 u8 · 플래그 u8
             시작프레임 u16 · 기록오프셋 u32
             사건 기반.  재생 시작 순간의 레지스터 세 값이 그대로 열쇠다

CD-DA  10 B  lba_from u24 · lba_to u24 · 기록오프셋 u24 · 플래그 u8
             시계 기반.  lba_from 으로 정렬 -> 런타임은 이분 탐색
             613 항목이어도 비교 10 번이면 끝난다
```

**둘 다 조각 단위다.** ADPCM 은 `(지문, 시작프레임)` 으로 정렬해 두어 한 이벤트의
조각들이 **붙어 있다**. 런타임은 첫 항목을 찾은 뒤 지문이 같은 동안 앞으로
걸어가기만 하면 된다 — 사슬을 따로 만들 필요가 없다.

> **버전 1 은 여기서 틀렸다.** 지문 하나에 기록 하나만 달아서, 조각이 여럿인
> 이벤트는 조각 2·3 이 소리 없이 사라졌다. 그것이 "지문 충돌 3 건" 으로
> 보고됐는데 충돌이 아니라 같은 이벤트의 조각이었다.

CD-DA 의 절대 LBA 는 `구간 시작 + 조각의 상대 시각 × 75` 로 여기서 미리 낸다.
런타임은 곱셈을 안 한다 — 6280 에 곱셈기가 없다.

### 기록 — 런타임이 계산을 하나도 안 하게

```
+00  cell_count u8
+01  width_px   u8
+02  flags      u8      bit0 = 대사
+03  (pad)
+04  frames     u16     이 조각이 떠 있는 길이
+06  칸 × 4 B  글리프번호 u16 · x u8 · y u8
```

**펜 위치를 미리 다 박아 둔다.** 자막 글꼴은 비례폭이라(한글 10 px, 영문 2/3)
런타임이 누적 덧셈을 해야 하는데, 그걸 빌드 때 끝내 버렸다. 런타임은 SATB 에
그대로 밀어 넣기만 한다.

### 글리프 · 글자표

```
글리프  64 B/자   플레인 0 본체 · 플레인 1 검은 외곽선
                  VRAM 에 올릴 때 플레인 2·3 을 0 으로 채워 128 B 로 편다
글자표  2 B/자    코드포인트.  런타임은 안 쓴다
```

글자표는 **팩을 글로 되돌리기 위한 것**이다. 이게 없으면 팩을 열어도 무슨 글자가
들어갔는지 알 수 없고, 검증기와 Lua 로그가 "지금 뭘 그리는지" 못 찍는다.

**쓰이는 글자만 싣는다.** 글꼴 전체 3320 자는 208 KB 라 예약을 혼자 다 먹는다.

## 3. 지금 구운 결과

```
자막 팩 8,820 B  (256 KB 예약의 3%)
  머리        64 B
  ADPCM 색인  72 B     6 조각 (3 이벤트)
  CD-DA 색인  80 B     8 개    겹침 없음
  기록       948 B    14 개    (같은 글은 한 번만)
  글리프   7,424 B   116 자    (전체 3320 자 중)
```

**적어 보이는 것은 빌더 탓이 아니다.** `cdda_subtitles.tsv` 는 613 행이지만
한국어가 들어간 행이 8 개다. 나머지는 자동 분할이 만든 빈 껍데기고, 번역이
채워지는 만큼 그대로 늘어난다.

613 행이 다 차면 대략:

```
기록    613 × 약 82 B  ≈  50 KB
글리프  약 800 자 × 64 B ≈  51 KB
합계                     약 110 KB  ->  예약 256 KB 안에 넉넉히 든다
```

## 4. 검증기 — 만든 쪽 말을 안 믿는다

`tools/verify_subtitle_pack.py`

빌더는 "8,820 B 를 썼다" 고 말하지만, 그 말이 맞는지는 그 코드가 판단할 수 없다.
같은 가정으로 쓰고 같은 가정으로 세기 때문이다. 그래서 검증기는 **`.json` 을 안
본다.** `.bin` 의 머리 64 B 만 읽고 오프셋을 따라가 글자를 복원한다 — 런타임이
할 일과 똑같다. 여기서 글이 돌아오면 런타임도 돌아온다.

```
구조    구간이 붙어 있는가 · 파일 밖으로 나가지 않는가 · 항목 크기가 머리와 맞는가
왕복    기록을 글로 되돌려 원본 TSV 와 같은가
누락    ★ 원본에 있는 자막이 전부 팩에 들어갔는가
색인    CD-DA 가 정렬돼 있는가 · 구간이 겹치는가
        ADPCM 의 같은 지문 조각들이 **붙어 있는가**
배치    펜 위치가 늘어나는가 · 줄 폭이 한계를 넘는가
글리프  비트맵이 통째로 0 인 글자가 있는가 (공백 말고 0 이면 글꼴 오프셋 오류)
```

> **누락 검사가 핵심이다.** 첫 판 검증기는 "팩에 있는 글이 원본에 있나" 만 봐서,
> 조각 2·3 을 통째로 잃고도 통과했다. 방향을 뒤집어 **원본이 다 들어갔는지**를
> 세게 바꾸고서야 버그가 드러났다.

지금 상태: `CD-DA 8/8 · ADPCM 6/6 조각` 전부 통과.

## 5. 오늘 스튜디오에서 고친 것

```
삭제 버튼      SelectedRows 가 비면 조용히 return 하던 것.  콤보 셀 편집 중에는
               선택이 비고 CurrentRow 만 남아서 눌러도 반응이 없었다
               -> 커서 행으로 되돌아가고, 여러 행을 고르면 전부 지운다
CD-DA 편집칸   대사 탭과 같은 모양.  오른쪽 위 일본어 · 아래 한국어 · 폭 초과 시 빨강
일본어 나누기  ★ 새로 넣음.  아래 참고
```

> **조용한 return 은 버그를 숨긴다.** 같은 뿌리로 구분 버튼(대사/효과음/기타)도
> 안 먹고 있었다. 선택 계열은 전부 `SelectedVoiceRows()` 로 통일했다 —
> 선택이 비면 `CurrentRow` 로 되돌아간다.

### 일본어 나누기

한국어는 조각으로 나뉘는데 일본어는 통짜라 **어느 원문이 어느 조각인지 안 보였다.**
`cdda_subtitles.tsv` 에 `jp_text` 열을 넣고, 구간의 일본어를 조각들에 나눠 담는다.

전사에는 **낱말 시각이 없다** — 한 구간에 문장이 통째로 있을 뿐이다. 다시 전사하지
않기로 한 이상 남은 것은 어림이고, 두 단계로 자른다:

```
1 순위  구두점 (。、！？ 공백)
2 순위  히라가나 -> 한자·가타카나  = 대개 낱말 머리
3 순위  시간 비례 그 자리
```

방향이 중요하다. 반대쪽(한자 → 히라가나)은 어간과 오쿠리가나 사이라 더 나쁘게
잘린다 — `黙 / <원문 6자>` 를 실제로 봤다.

실측: 전체 195 곳 중 낱말 가운데로 의심되는 컷 **7 곳 (3%)**.

```
[c04_005]  구두점이 있는 경우 — 전부 문장 경계
   1. <원문 5자>、<원문 13자>。
   2. そのため、
   3. 年々<원문 12자>。

[c01_007]  구두점이 없는 경우 — 문자종 전환으로
   3. <원문 14자>
   4. <원문 19자>
```

이미 손으로 넣은 일본어는 **덮지 않는다.** 표에서 고칠 수 있고, 오른쪽 창은
지금 고른 조각에 `▶` 를 붙여 보여준다.

`jp_text` 는 **참고용이다.** 팩에는 안 들어간다 — 화면에 나가는 것은 한국어뿐이다.

## 6. 남은 것

§9 의 목록은 그대로다. 팩이 생기면서 순서만 또렷해졌다.

```
1  감시자 자리       음성 시작/끝을 보고 심고 거두는 작은 코드.  헬퍼 여유 151 B 가 후보
                    ★ 이것이 유일한 미해결 구조 문제다
2  엔진             팩을 읽어 SATB 에 미는 코드.  스텁 54 B 는 이미 검증됐다
3  적재 타이밍       접수처 들어가기 전에 AC 에 올라가 있어야 한다
4  오프닝 예외       48~63 칸 쓰는 한 순간만 그림으로 처리
5  번역             사람 시간.  613 조각 중 8 개 됐다
```

**1 번이 풀리기 전에는 디스크에 훅을 영구히 박으면 안 된다.** 음성이 아닐 때
`JSR` 이 스택 데이터를 실행한다.

## 7. 다시 굽는 법

```bash
python tools/build_subtitle_pack.py && python tools/verify_subtitle_pack.py
```

스튜디오에서 번역을 저장했으면 다시 돌리면 된다.
`.json` 에 오프셋이 다 적혀 있어서 Lua 나 엔진이 상수를 박을 필요가 없다.

짐을 쌀 때는 `python tools/pack_subtitle_bundle.py` — 스튜디오·번역표·음원을
`_bundle/` 에 하나로 묶는다 (`make_handoff_bundle.py` 는 빌드 이어하기용으로
따로 있다. 그쪽은 BIOS·펌웨어가 들어가고 음원이 없다).
