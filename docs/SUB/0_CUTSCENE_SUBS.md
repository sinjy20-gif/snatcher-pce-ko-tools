## 0. 한 줄 요약

**앵커 3 개가 다 닫혔고 예산 4 개가 다 잠겼다.**  엔진은 아직 없지만 어디에 무엇을
놓을지가 전부 정해졌고, 빌더가 그것을 감사한다.

```
프레임 훅     $2202 -> $40A4      IRQ1(VDC).  MPR2=$68 상주        §7.1
음성 호출     CD_PLAY <- $60E4    시계 CD_SUBQ <- $6119 실제로 돎   §7.1
스프라이트    오프닝은 아예 안 쓴다.  SAT 64 개 전부 비어 있음      §7.4
AC 데이터     $1C0000  256 KB     예약됨 · 침범하면 빌드 실패      §5.1
케이브 로더   64 B                예약됨                          §5.2
엔진 RAM      $5C40-$5E1F 480 B   BIOS 전환으로 우리가 비운 자리    §7.4
버퍼 RAM      $2311 807 B · $3468 664 B                           §7.4
VRAM          $7B00 부터 20 슬롯   컷신별로 다르다                  §7.4
```

**BIOS 폰트 전환이 자막 자리를 만들어 줬다.**  케이브 여유 5 -> 151 B 도, 엔진이
들어갈 480 B 도 전부 아틀라스와 글리프 루프를 걷어낸 덕이다 (SNATCHER_BIOS_FONT §5).
자리를 찾은 것이 아니라 만든 것이다.

## 2. yunatools 에서 실제로 건진 것

`_side/yunatools` (46 MB, GPLv3).  PCE CD 게임에 자막을 실제로 심은 선례다.
읽고 설계를 배웠다.  **코드는 가져오지 않는다** (§7).

### 2.1 자막 엔진 구조 (`yuna/asm/overlay/scene.s`, 2,716 행)

| | 방식 |
|---|---|
| 훅 | sync(VSync) 벡터 `$5284` 를 가로채 `newSyncLogic` 실행 |
| 타이밍 | VSync 프레임 카운터 + ADPCM 재생(`$6BA9`)마다 증가하는 이벤트 카운터 |
| 스크립트 | 오버레이에 박힌 바이트코드.  `$00~$11` 옵코드, `$12` 이상은 글자 리터럴 |
| 그리기 | 스프라이트.  SAT `$7F00` 앞쪽을 선점, 매 VSync TIA 후 `ST0 #$13` 로 SATB DMA |
| 공존 | 게임의 스프라이트 클리어(`$755D`)·오브젝트 생성 루틴을 패치해 자막을 건너뜀 |
| 스로틀 | VSync 당 스크립트 op 2 · SAT 속성 4 · 패턴 전송 2 |

### 2.2 실측한 숫자

`sceneOp_prepAndSendGrp_handler` 가 인자를 타일번호로 받아 `.rept 6 asl` = ×64
**워드** 로 VRAM 주소를 만든다.  스프라이트 1개 = 128 B 슬롯.

```
1버퍼   2줄 × 16패턴 × 128 B = 4,096 B
더블    2버퍼                = 8,192 B
```

`SCENE_autoPlaceSeparation $0020` = 타일 32개 = 2줄 × 16패턴.  베이스 `$01BC`,
교대 `$01DC`.  `$01BC × 64` = 워드 `$6F00`, SAT 가 `$7F00` — **VRAM 최상단,
SAT 바로 아래**를 쓴다.

**SAT 엔트리는 32개가 아니라 16개다.**

```asm
; round dstptr up to the next even pattern number
; (so we can make use of double-width sprites)
```

패턴 번호를 짝수로 맞춰 32×16 더블폭 스프라이트를 쓴다.  패턴 2개당 엔트리 1개.

```
패턴       2줄 × 16 = 32
SAT 엔트리 2줄 ×  8 = 16     64개 중 1/4
```

플레인 2·3 은 지울 필요가 없다.  팔레트를 비트1 기준으로 글자/그림자 둘로만
채워서(`paletteOverrideColors`) 상위 플레인 잔여물이 결과에 영향을 안 준다.
**스프라이트당 128 B 예약, 실제 전송 64 B.**

### 2.3 가져올 발상

1. **`SYNC_adpcmTime`** — 오디오 이벤트가 어셈블러의 시간 원점(`SYNC_time`)을
   재정의해, 이후 `분:초` 표기가 자동으로 상대값으로 컴파일된다.  오디오가
   밀려도 다음 이벤트에서 다시 붙는다.  이 프로젝트에서 제일 영리한 부분.
2. 옵코드와 텍스트가 한 스트림 — 파서가 하나뿐이다.
3. VSync 당 작업량 상한.
4. 더블버퍼 + `queueSubsOff`(지정 프레임 자동 하강).
5. BIOS `$E09F`(SAT→SATB DMA) / `$E0A2`(스프라이트 클리어) — Syscard 엔트리라
   **스내처에서도 같은 주소다.**  유일하게 주소째 재사용되는 부분.

### 2.4 안 가져오는 것

- `$5284` · `$755D` · `$6BA9` · `$4D74` · `$3800` 전부 Yuna 전용 (§6).
- **폰트 모델 전체.**  Yuna 는 0x50자·10px·가변폭이라 런타임 비트시프트 합성기
  (`leftShiftRightTwoLoop` 등)가 엔진에서 제일 무겁다.  한글은 16×16 **고정폭**
  이라 음절 1개 = 스프라이트 1개, 시프트가 아예 필요 없다.  그 코드가 통째로
  사라진다.

## 3. 우리 쪽 소요 — 실측

`snatcher_ko_master.tsv` 2,279 행 전수 집계:

```
전체 한글 글자수    20,116
전체 고유 음절         761      2,350 이 아니다
행당 평균 한글         8.8
```

컷신 1개 크기 창의 고유 음절:

```
30행 창   중앙값 127   최대 152
50행 창   중앙값 173   최대 193
80행 창   중앙값 225   최대 255
```

**193 < 238.**  리터럴 코드가 `$12~$FF` 238개이므로 컷신 1개의 고유 음절이 그
안에 들어온다.  씬별 글리프 팩을 인덱스 순으로 구우면 **음절 1개 = 1바이트**,
매핑 테이블조차 필요 없다.

전 게임 소요 (컷신 20개 가정, 전역 팩 공유):

```
전역 글리프 팩   761 × 64 B (외곽선까지 구움) =  48 KB
씬별 스크립트    20 × 1.7 KB                  =  34 KB
씬별 인덱스표    20 × 512 B                   =  10 KB
엔진 코드 이미지                              =   2 KB
------------------------------------------------------
                                             약 94 KB
```

외곽선을 오프라인에서 굽는 쪽을 택한다.  디스크를 24 KB 더 쓰지만 런타임
외곽선 코드와 사이클이 사라진다.  **우리 제약은 디스크가 아니라 코드 공간이다.**

## 4. AC 는 저장은 되고 실행은 안 된다

우리 "AC" 는 아케이드 카드다.  빌더가 쓰는 접근:

```python
registers = [(0x1A02, ...), (0x1A03, ...), (0x1A04, ...),
             (0x1A07, 1), (0x1A08, 0), (0x1A09, 0x11)]
```

`$1A02~$1A04` 에 24비트 베이스를 쓰고 포트로 자동증가 읽기.  **스트리밍 포트지
주소공간이 아니다.**  MPR 에 매핑해 그 위로 `JMP` 할 수 없다.

```
저장  가능    2 MB 중 344 KB 사용.  자막 94 KB 는 반올림 오차
실행  불가    포트 너머로는 못 뛴다
```

따라서 **엔진은 AC 에 두고 컷신 진입 때 RAM 으로 복사해 거기서 돈다.**  새 발명이
아니라 지금 글리프에 쓰는 경로와 같다(캐시 미스마다 32 B → 한 번에 1.5 KB).
Yuna 도 `bootloader2` 를 `$3800` 에 올려 씬 내내 상주시킨다.

질문이 이렇게 바뀐다:

```
전   "오버레이 안에 죽은 디스크 공간 1.5 KB 가 어디 있나"
후   "컷신 동안 죽어 있는 RAM 1.5 KB 가 어디 있나"
```

후자가 유리하다.  컷신은 대화 시스템·메뉴·세이브/로드가 전부 안 도는, 시스템
압박이 제일 낮은 상태다.

## 5. 이번에 예약한 것

### 5.1 AC 주소공간 256 KB

`build_ac_dynamic_0_1_14.py`

```python
SUBTITLE_AC_BYTES = 0x40000
SUBTITLE_AC_BASE  = dynamic.AC_BYTES - SUBTITLE_AC_BYTES   # $1C0000
```

씬 팩의 천장을 `AC_BYTES` 에서 `SUBTITLE_AC_BASE` 로 낮추고, 기존 extent 감사에
구역을 한 줄 추가했다.  침범이 "언젠가 이상해진다" 가 아니라 **빌드 실패**가 된다.

```
$00000 - $16000    초기 적재 (디렉터리 64K + 상태 + 템플릿)
$16000 - $53000    상주 팩 (speaker · ui · runtime)
$60000 - $1C0000   씬 구역        1,441,792 B  (현재 사용 0)
$1C0000 - $200000  자막 예약      262,144 B    ← 신규
```

꼭대기에 둔 이유: 초기 적재·상주 팩·씬 팩이 전부 아래에서 위로 자란다.
꼭대기는 커서 하나(`scene_cursor`)만 닿는 자리라 감사가 한 줄로 끝난다.

크기 근거는 §3 의 94 KB 를 2.7 배로 잡은 것.  **과예약 비용은 0 이다** — 떼고도
씬 구역에 1.37 MB 가 남고 현재 씬 팩 사용량은 0 이다.  상수 한 줄로 조정된다.

### 5.2 헬퍼 케이브 64 B

케이브(`$BCD2-$BFE0`, 코드 한도 782 B)는 이 사업에서 제일 귀한 자원이다.
엔진 본체는 여기 못 들어온다.  남는 것은 AC→RAM 복사를 시작하는 로더뿐이다:
`$1A02-$1A04` 에 베이스 3바이트 + 포트에서 블록을 긁는 루프.  `copy_record` 가
이미 하는 일과 같은 모양이라 64 B 면 여유 있다.

예약 방식은 "비워두기" 가 아니라 **한도를 낮추기** 다.

```
코드 631 B  →  여유 151 B  →  예약 64 B  →  잔여 87 B
```

다음에 누가 헬퍼를 88 B 이상 늘리면 그 자리에서 빌드가 멈춘다.

`SNATCHER_KO_BIOS=1 python build_snatcher_ko_0_3_12_bios.py --stage3`

## 6.5 앵커 조사 착수 — 오프닝 (2026-08-19, 정적 분석)

### 오프닝 오디오는 CD-DA 트랙 17 통재생

`SNATCHER_OPENING_CD_AUDIO_HANDOFF.md` 의 실측 LBA 를 트랙 경계와 맞춰봤다.

```
트랙 17 시작 = LBA 184016,  9,954 섹터 = 132.72 초
오프닝 START  184018 = 트랙17 + 2섹터
오프닝 END    193971 = 트랙18 초입   -> 트랙 17 을 끝까지 재생
실측 132.533 초  vs  트랙 길이 132.72 초        일치
CDDA_0002 도 트랙 21 (300섹터 = 4.0 초) 과 일치
```

프로그램 영역에 오프닝 MSF 상수(`40 55 43` 등)는 **없다.**  트랙 번호로 건다.

### CD 오디오 드라이버 위치 확정

트랙02 전역에서 BIOS 점프테이블 호출을 스캔하니 CD_PLAY·SEARCH·PAUSE·FADE·
STAT·SUBQ 가 **섹터 255 한 곳에 뭉쳐** 있었다.  깊은 섹터의 산발적 적중은
그래픽·ADPCM 우연 일치다.

CPU 주소는 우리가 이미 아는 값으로 검산됐다.

```
가설  뱅크69 ISO 0x07D800 = CPU $A000
검산  케이브 $BCD2-$C000 -> ISO 0x07F4D2-0x07F800
      원본 track02.iso 의 그 814 B 가 전부 $FF          <- 일치
      직전 16 B = 8d 11 37 9c 12 37 68 60  (진짜 코드)
확정  ISO 0x07F800 = CPU $C000 (뱅크 6A)
```

### 드라이버 실측

```
$C0D7  ad f9 26   LDA $26F9        <- 트랙 번호가 여기 있다
$C0DA  29 7f      AND #$7F
$C0DC  1a         INC A            (PLAY 는 1-based, SEARCH 는 0-based)
$C0DD  20 b4 e0   JSR $E0B4        BIOS 변환
$C0E2  85 fc      STA $FC
$C0E4  20 12 e0   JSR CD_PLAY
```

### 시계 — Yuna 보다 유리하다

`$C0F6` 에 "CD 오디오가 재생 중인가" 를 묻는 루틴이 있고, 그 부산물로 현재
위치가 들어온다.

```
$C0F6  ad f5 26   LDA $26F5
$C0F9  d0 12      BNE $C10D
$C0FB  a9 00      LDA #$00
$C0FD  20 1b e0   JSR CD_STAT
$C104  ad 7b 22   LDA $227B
$C111  a9 a0      LDA #$A0
$C113  85 fa      STA $FA          포인터 $20A0
$C115  a9 20      LDA #$20
$C117  85 fb      STA $FB
$C119  20 1e e0   JSR CD_SUBQ      -> 결과 10 B
$C120  a5 a0      LDA $A0          <- 제로페이지.  PCE 의 zp 는 $2000-$20FF
$C122  c9 02      CMP #$02         2 = 재생 중
$C126  62 60      CLA; RTS
```

**PCE 제로페이지가 $2000-$20FF 이므로 포인터 `$20A0` 은 곧 zp `$A0` 이다.**
(절대주소 `AD A0 20` 로 훑으면 한 건도 안 잡힌다 — 그래서 "안 쓴다" 고 닫으면
안 되는 자리였다.)

따라서 `JSR $C0F6` 하나로 상태와 **절대 디스크 시각(M:S:F, BCD)** 을 동시에
얻는다.

```
Yuna   VSync 프레임 카운터  +  ADPCM 이벤트로 재동기
우리   VSync 프레임 카운터  +  CD_SUBQ 의 M:S:F 로 재동기   드리프트 0
```

CD-DA 는 75 섹터/초의 하드웨어 시계다.  Yuna 가 ADPCM 이벤트 카운터라는 우회로를
만든 이유(오디오에 시계가 없다)가 우리에겐 없다.

### 단, 아직 아닌 것

- zp `$A0-$A9` 는 게임 전체가 범용으로 재사용한다 (`LDY $A1` 만 16회).
  **상시 유지되는 시계가 아니다.**  `$C0F6` 을 부른 직후에만 유효하다.
- `$C0F6` 호출 비용은 BIOS CD_STAT + CD_SUBQ 두 번이다.  매 프레임은 무리로
  보이고, N 프레임마다 재동기 + 사이는 VSync 카운터로 메우는 형태가 맞다.
  N 은 실측해서 정한다.
- 오프닝 중 이 루틴이 실제로 돌고 있는지는 정적으로 알 수 없다.  확인 필요.

## 7.1 앵커 1·2 — 찾았다 (2026-08-19, PROBE_OPENING_HOOK_0.1.1)

### 먼저, 주소가 틀려 있었다

`NOTES.md` 와 §6.5 가 CD 오디오 드라이버를 `$C000` 이라고 적었는데 **틀렸다.**
오프닝을 돌리며 BIOS 진입점에 걸어 보니 CD_PLAY 의 호출자가 `$60E4`(MPR3=$6A)이고,
정적으로 읽은 오프셋이 전부 그대로 옮겨 간다:

```
$C021 -> $6021    서비스 루틴
$C0E4 -> $60E4    JSR CD_PLAY
$C0F6 -> $60F6    재생 중인가
$C119 -> $6119    JSR CD_SUBQ
```

섹터 255 를 `$6000` 베이스로 디스어셈블하면 바이트가 정확히 재현된다.
`disasm_huc6280.py` 가 처음부터 그렇게 말하고 있었다 ("뱅크 B, 섹터 255-258, $6000").
`$C000` 은 케이브 검산($BCD2-$C000 이 전부 $FF)을 베이스 앵커로 오해한 데서 나왔다.

**`$C021` 에 훅을 걸면 아무것도 안 잡힌다** -- `PROBE_OPENING_HOOK_0.1.0` 이 정확히
그렇게 했고 11,902 프레임 동안 0 건이었다.  §2 의 disasm 주석이 경고한 "같은 바이트,
틀린 페이지" 함정이다.

### 앵커 1 — 프레임 훅

BIOS RAM 벡터표 `$2200` 은 **2 바이트 엔트리**다 (3 바이트로 읽으면 어긋난다).
그렇게 읽으면 게임이 프레임 30~300 사이에 자기 핸들러를 설치하고 그 뒤로 안 바꾼다:

```
프레임 30     $2202 -> $E8E2     BIOS 기본.  아직 미설치
프레임 300~   $2202 -> $40A4     IRQ1 (VDC / VSync)   <- 프레임 훅
              $2204 -> $493D     TIMER
              나머지는 $E8E2 / $0000 그대로
```

`$40A4` 는 MPR2 창($4000-$5FFF)이고 **모든 표본에서 MPR2 = $68** 이다 -- 오프닝
중에도 그렇다.  상주이고 페이징으로 사라지지 않는다.  **Yuna 의 `$5284` 에 해당한다.**

벡터를 건드리기 곤란하면 두 번째 선택지가 있다:

```
CD_STAT <- $6230 : 11,250 프레임 동안 10,244 회   ≈ 프레임당 1 회
```

`$6230` 이 알아서 매 프레임 CD 상태를 폴링한다.

### 앵커 2 — 음성 재생 호출 지점

CD_PLAY <- $60E4   프레임 1077 에 발화.  오프닝 t0 다 (통틀어 3 회 -- 타이틀 데모가 돈다)
CD_SUBQ <- $6119   §6.5 의 시계.  실제로 돈다
CD_STAT <- $60FD   339 회

§6.5 가 "오프닝 중 이 루틴이 실제로 돌고 있는지는 정적으로 알 수 없다" 고 남겨 둔

## 7.2 케이브에는 프레임 훅을 못 넣는다 (2026-08-19)

0.1.1 이 뜬 MPR 을 전부 겹치면 이렇게 갈린다:

```
MPR0  FF  항상        I/O
MPR1  F8  항상        $2000-$3FFF  베이스 RAM
MPR2  68  항상        $4000-$5FFF  ($40A4 가 여기 산다)
MPR3  69/6A           바뀜
MPR4~6                심하게 바뀜   6B 00 6D 85 74 86 71 82 ...
MPR7  00  항상        BIOS
```

**IRQ 는 아무 문맥에서나 걸린다.**  그러므로 프레임 훅은 항상 매핑된 창 --
MPR1 이나 MPR2 -- 에만 둘 수 있다.  **헬퍼 케이브 `$BCD2` 는 MPR5 창이라 못 쓴다.**
크기로는 들어간다(POC 훅 64 B < 잔여 87 B).  자리가 틀렸을 뿐이다.

§5.2 의 케이브 64 B 예약은 **여전히 유효하다.**  AC→RAM 로더는 컷신 진입 시점에
알려진 문맥에서 불리므로 창이 보장된다.  옮겨야 하는 것은 엔진 본체와 훅이다.

그래서 §4 의 "컷신 중 죽은 RAM 1.5 KB" 의 **범위가 확정됐다**: `$2200-$3FFF`
(제로페이지·스택을 뺀 베이스 RAM 7.5 KB) 또는 `$4000-$5FFF`.
`lua/PROBE_DEAD_RAM_0.1.0.lua` 가 오프닝 내내 안 쓰이는 구간을 찾는다.

### 바이트 예산 — 실측 (빌더 어셈블러로 실제 방출)

```
POC 프레임 훅              64 B    INC 카운터 · 임계 비교 · MAWR 세팅 ·
                                   TIA 패턴 288 워드 · TIA SAT 16 엔트리 ·
                                   ST0 #$13 SATB DMA · JMP $40A4 체인
엔진 전체 (추정)        1,140 B
  패턴 준비 버퍼           576 B
  스크립트 인터프리터       300 B
  SAT 준비 버퍼            128 B
  AC->RAM 로더             64 B   <- 이것만 케이브
  상태 변수                 8 B
```

§4 가 어림한 1.5 KB 와 맞는다.  조각이 흩어져 있어도 된다 -- 버퍼와 코드를
나눠 두면 그만이다.

## 7.3 앵커 3 — 스프라이트 경쟁자가 없다 (PROBE_OPENING_SPRITE_0.1.0)

```
vdc.spritesEnabled     = false      오프닝은 스프라이트를 아예 안 켠다
vdc.nextSpritesEnabled = false
vdc.satbBlockSrc       = 4096       SATB 는 VRAM 워드 $1000
```

그리고 VRAM 빈 구간 목록에 `$1000 부터 296 워드 비어 있음` 이 있다 -- SAT 영역이
통째로 0 이다.  증거 두 개가 같은 말을 한다: **SAT 64 엔트리 전부 쓸 수 있다.**

**Yuna 의 "공존" 작업(§2.1)이 통째로 필요 없다.**  저쪽은 게임의 스프라이트
클리어 루틴 `$755D` 와 오브젝트 생성 루틴을 패치해 자막을 건너뛰게 만들어야 했는데,
우리는 경쟁자가 없다.

> 주의: 이 프로브의 `satsum` 행은 못 믿는다.  SATB 자동탐지가
> `satbTransferNextWordCounter = 2` 를 집어 `$0002` 를 읽었다.  결론은
> `spritesEnabled=false` 와 `$1000` 이 0 이라는 두 증거로 선다.

### VRAM — 컷신마다 다르다

```
프레임  300 (타이틀)   $3DF8   520 워드 = 1,040 B
프레임 1100            $1000   296 워드 =   592 B   (SAT 영역.  쓰지 말 것)
프레임 1500~ (오프닝)  $7AF0  1296 워드 = 2,592 B
```

스프라이트 패턴 주소는 64 워드 단위이므로 정렬하면 **`$7B00` 부터 1,280 워드
= 2,560 B = 슬롯 20 개** (슬롯당 64 워드 = 128 B 예약, 실전송 64 B).

```
POC 9 음절        슬롯  9 / 20   들어감
한 줄 16 음절     슬롯 16 / 20   들어감
2 줄 32 음절      슬롯 32 / 20   ★ 안 들어감
Yuna 식 더블버퍼  슬롯 64 / 20   ★ 안 들어감
```

**설계가 여기서 정해진다: 한 줄씩, 단일 버퍼.**  화면 256 px 에 글리프 16x16 이라
어차피 한 줄 최대 16 음절이니 자연스러운 상한이기도 하다.  Yuna 의 2 줄 더블버퍼는
포기한다.

**패턴 주소를 상수로 박으면 안 된다.**  컷신마다 재서 배정해야 한다.

## 7.4 실행 RAM — 확보 (PROBE_DEAD_RAM_0.1.1)

0.1.0 은 타이틀까지 세는 바람에 `$2200-$3FFF` 에서 101 B 밖에 못 찾았다.
**CD_PLAY 를 게이트로 걸어 컷신 구간만 세니** 그림이 완전히 달라진다:

```
$5C40-$5E1F     480 B   1 조각   MPR2.  BIOS 전환으로 우리가 비운 글리프 슬롯 3-17
$5B80-$5E3F     704 B   1 조각   레코드 캐시 전체.  컷신 중에는 게임도 안 건드린다
$2311-$2637     807 B            MPR1
$3468-$36FF     664 B            MPR1
$3701-$3900     512 B            MPR1
$3CF4-$3DFF     268 B            MPR1
$3A2A-$3AFF     214 B            MPR1
...                              MPR1 합계 5,082 B / 150 조각 · 64 B+ 조각 11 개
```

엔진에 필요한 1,140 B 대비 **3 배 여유**다.

### ★ 함정 — `$4000-$5FFF` 8,192 B 는 빈 자리가 아니다

프로브는 이 창 전체가 "쓰기 없음" 이라고 보고한다.  **거기는 코드다.**
프레임 끝 PC 의 4.5% 가 그 창이고 `$43B2` · `$43BC` 가 그 예다.

```
프레임 끝 PC 분포 (PROBE_OPENING_HOOK_0.1.1 상위 20 종)
  $2000-$3FFF (MPR1)      0 회   0.0%    <- 베이스 RAM 은 코드가 안 돈다
  $4000-$5FFF (MPR2)    278 회   4.5%    <- 여기는 코드다
  $6000-$7FFF (MPR3)  5,200 회  83.3%
  $8000+      (MPR4~6)  763 회  12.2%
```

**쓰기가 없다는 것은 빈 자리라는 뜻이 아니다.**  `SNATCHER_SAVELOAD_HANDOFF` 가
`$5B80` · `$BFCF` · `$7FF1` 에서 세 번 틀렸다고 적어 둔 것과 같은 함정이고, 이번이
네 번째가 될 뻔했다.  거꾸로 **`$2000-$3FFF` 는 PC 가 한 번도 안 도므로** 거기서는
"쓰기 없음 = 빈 자리" 가 성립한다.

### 왜 `$5C40` 이 1 순위인가

우리 자리이기 때문이다.  BIOS 모드에서 빌더가 그 범위에 방출하는 코드가 **0 곳**
임을 확인했다 -- 관련 코드가 전부 `if not BIOS_FONT:` 가드 안에 있다.
게임 쪽도 컷신 중에는 안 건드린다 (위 실측).  MPR2 창이라 항상 매핑된다.

### 빌더 감사

```python
SUBTITLE_RAM_CODE    = (0x5C40, 0x5E1F)                    # 480 B
SUBTITLE_RAM_BUFFERS = ((0x2311, 0x2637), (0x3468, 0x36FF))
```

매니페스트에 나온다:

```json
"subtitle_ram_code": "5C40-5E1F",
"subtitle_ram_code_bytes": 480,
"subtitle_ram_buffers": ["2311-2637", "3468-36FF"]
```

그리고 BIOS 모드에서 글리프 루프가 되살아나면 **빌드가 멈춘다.**  루프를 방출하면
반드시 생기는 라벨(`glyph_loop` 등)을 검사한다:

> `SNATCHER_KO_BIOS 인데 글리프 루프가 방출됐다.  그 코드는 $5C40-$5E1F 를 쓰는데
> 그 480 B 는 컷신 자막 엔진에 예약돼 있다`

## 7.6 POC 사양 — 엔진 완성 (2026-08-19)

`tools/build_subtitle_poc.py` 가 굽는다.  산출물은 `build/cutscene_subs/`:

```
poc_engine.bin       245 B   $5C40 에 상주하는 IRQ1 훅
poc_patterns.bin     576 B   9 x 64 B 스프라이트 패턴
poc_sat.bin           72 B   9 x 8 B SAT 엔트리
poc_manifest.json          주소·크기·예산
```

### 배치

```
엔진      $5C40-$5D34   245 B / 예약 480 B   여유 235 B
패턴 RAM  $2311         576 B / 조각 807 B      -> VRAM 워드 $7B00
SAT  RAM  $3468          72 B / 조각 664 B      -> VRAM 워드 $1000
AC 적재   893 B         셋을 합쳐 $1C0000 예약 구역에서 온다
VRAM      슬롯 9 / 20
```

### 훅 흐름

```
PHA
INC frame_lo / (넘치면) INC frame_hi
shown 이 서 있으면            -> PLA, JMP $40A4
frame < 120 이면              -> PLA, JMP $40A4
shown = 1
스프라이트 팔레트 0 을 세운다   색1 = 흰색($01FF), 색2 = 검정(그림자)
패턴 9 개를 VRAM 으로          슬롯마다 MAWR 을 다시 세우고 TIA 64 B
SAT 을 VRAM $1000 으로         TIA 72 B
SATB DMA (ST0 #$13) · CR = $C8
PLA, JMP $40A4                원래 핸들러가 그대로 돈다
```

### 설계 판단 넷 (전부 실측 근거)

```
패턴을 128 B 로 안 편다   플레인 2·3 을 안 보낸다 (§2.2).  VRAM $7B00 이 이미 전부
                          0 이라는 실측이 뒷받침한다.  1,152 -> 576 B.  대신 전송이
                          9 번으로 나뉘는데 코드 여유가 235 B 나 있다
패턴을 엔진 뒤에 안 둔다   480 B 예약을 넘어 $5E20(반칸 도우미)과 $6000(다른 뱅크)을
                          침범한다.  MPR1 버퍼 조각으로 보낸다
출구를 앞에 둔다          전송을 9 번으로 풀면 show 블록이 200 B 를 넘어 상대분기
                          (±127)가 안 닿는다.  조건을 뒤집어 짧은 분기만 쓴다
CR = $C8 이지 $CC 가 아니다  $CC 는 bit2(래스터 IRQ)를 켠다.  실측이
                          enableScanlineIrq=false 였다 -- 없던 인터럽트를 만들면 안 된다
```

`PHA`/`PLA` 로 A 를 보존한다.  IRQ 는 실행 중인 코드를 아무 데서나 끊고, BIOS
디스패치가 A 를 저장해 주는지 확인하지 않았다.  3 바이트짜리 보험이다.

### 남은 것

```
1. 로더        AC -> $5C40(엔진) · $2311(패턴) · $3468(SAT).  케이브 64 B
               copy_record 가 이미 하는 일과 같은 모양이다
2. 벡터 설치    $2202 = $5C40.  로더 안에서 한 번
3. 트리거      title_cache_wipe 스텁($BCEF / MPR3=$69 일 때 $7CEF).  [실측 확인됨, §7.7]

## 7.8 음성 수집은 계속한다 — 그것이 자막 대본이다

세션 중 "지금 모으는 음성이 의미 없어지는 것 아니냐" 는 물음이 있었다.  **아니다.**

```
음성 수집   무엇을 언제 말하는가   = 자막 대본 그 자체.  사람 시간 몇 주.  대체 불가
프레임 훅   코드를 어디에 끼우나   = 배달 수단.        리버싱 며칠
```

Yuna 의 자막 대본은 통째로 타임스탬프 목록이다 (`cut_waitForFrameMinSec 0 8.512`).
우리가 모으는 것이 정확히 그것이다.  저쪽은 오디오 편집기로 손으로 맞췄고,
우리는 에뮬레이터가 자동으로 적는다.

### 수집기는 이미 올바른 앵커를 적고 있다

`snatcher_tool/mesen/runtime_text_audit.lua` 의 음성 헤더:

```
event_type  event_id  sequence  frame  audio_type
read_address  write_address  audio_length  playback_rate  sector
```

| 필드 | 쓰임 |
|---|---|
| `sequence` | ADPCM 이벤트 순번.  **Yuna 의 `cut_waitForAdpcm index` 와 1:1** |
| `sector` | 디스크 좌표 (`cdrom.scsi.sector` / `audioPlayer.currentSector`).  세션 불변 |
| `audio_length`·`playback_rate` | 재생 없이 길이 산출 |
| `frame` | **세션 종속.** 타이틀 통과 속도에 따라 달라진다.  교차검증용으로만 |

**결론: 수집 방식은 바꿀 것이 없다.**  다만 어떤 지점을 나중에 다시 지목할 때는
`frame` 이 아니라 `sector` / `sequence` 로 적어야 재현된다.

두 타이밍 모델이 이미 다 덮인다.

```
ADPCM 대사   sequence 순번   -> Yuna 모델 그대로
CD-DA 컷신   sector          -> 절대 시각.  더 정확
```

기존 수집물: `dump/opening_cd_audio_events.tsv` (14 행, 오프닝 CD-DA 전 구간).

## 9. Lua 로 자막을 화면에 띄웠다 (2026-08-20)

**처음으로 우리 자막이 화면에 나왔다.**  엔진과는 별개의 확인 경로다.

### 왜 0.1.2/0.1.3 이 실패했나 -- 원인이 셋 겹쳐 있었다

`SUBTITLE_OVERLAY 0.1.2` 로그는 완전히 정상이었다.  `SUB >` 가 찍히므로 표 적재·
키 매칭·타이밍이 다 통과했고 `drawString` 도 불렀다.  그런데 화면에 아무것도 없었다.

```
1  emu.drawString 이 **세로로** 그린다.  한 글자마다 아래로 내려간다
2  Mesen 폰트에 **한글 글리프가 없다**.  ASCII 만 찍히고 한글은 자리만 먹는다
3  0.1.3 의 진단용 TEST 막대마저 한글이라 **판정 자체가 성립하지 않았다**
```

3 이 특히 고약하다.  0.1.3 은 *"TEST 막대도 안 보이면 Mesen 설정"* 이라는 판정표를
달아 두었는데, 그 막대가 자막과 **같은 이유로** 사라지므로 "설정 문제" 라는 틀린
결론으로 간다.  §1 이 *"Mesen 그리기가 안 나오는 환경 문제"* 라며 Lua 를 접은 것도
여기서 나왔을 것이다.

**ASCII 만 그리는 프로브 하나가 이것을 갈랐다** (`lua/PROBE_DRAW_0.1.0.lua`).
진단 도구는 진단 대상과 같은 실패 모드를 공유하면 안 된다.

### 갈라낸 순서

```
PROBE_DRAW_0.1.0   ASCII·한글·도형을 따로 그린다
                   -> 사각형 보임(표면 정상) · TOP-RIGHT 만 보임 · 한글 안 보임
PROBE_DRAW_0.1.1   20 px 격자로 좌표계 실측
                   -> x=0~260 전부 보임.  **좌표계는 정상이었다**
PROBE_DRAW_0.1.2   글자 수·공백·한글을 가른다
                   -> 모든 문자열이 세로로 흐름.  ASCII 만 찍힘
```

### 채택 -- 갈무리 글리프를 픽셀로 직접 찍는다

`lua/SUBTITLE_DRAW_0.2.0.lua`.  Mesen 폰트를 안 쓴다.

```
글리프   build/bios_font/galmuri_ks_2350.bin   16x16 · 32 B/자 · KS 순서 (가=0)
그리기   emu.drawPixel.  외곽선(8 이웃 검정) 먼저, 본체 나중

부수 효과가 더 크다: **실제 엔진에서 나올 픽셀과 같다.**  같은 16x16 글리프,
같은 1 px 외곽선.  그래서 여기서 정한 값이 그대로 엔진 사양이 된다.

### 실측 -- 글리프 폭

2,350 자 **전부** x=1..11 이다.  16 칸 중 왼쪽 1 · 오른쪽 4 가 비어 있다.

```
자간 16 -> "가 나 다 라" 처럼 4 px 이 벌어져 보인다
자간 12 (폭 11 + 1)  ->  한 줄 21 자 (256 / 12)
왼쪽 여백 1 px 을 빼고 찍어야 x=0 근처에서 안 잘린다
```

### ★ 자막 기본 사양 -- 확정 (2026-08-20, 화면에서 눈으로 정함)

```
격자      16x16 갈무리 · 검은 1 px 외곽선      스프라이트 2 플레인과 동일
자간      12 px  (실측 폭 11 + 1)             ->  한 줄 21 자
위치      **그림 상자 안쪽 맨 아래**            SUB_BOTTOM = 140
줄 수     **한 줄**
```

위치를 그림 상자 안으로 잡은 이유:

```
상자 안      초상화를 안 가린다 (소유자 지정).  선택지 메뉴와도 안 겹친다
상자 밑 띠   인물 얼굴·입 애니메이션 자리.  게임이 스프라이트를 쓸 수 있다
```

### 이것은 **기본값**이고 화면 종류마다 다르다

소유자 지정 (2026-08-20):

```
일반 진행    SUB_BOTTOM = 140   그림 상자 안쪽 아래.  **기본값**
오프닝·컷신  화면마다 따로       그림 상자가 없고 전체 화면 영상이라 기준이 다르다
```

그러므로 엔진은 자막 Y 를 **씬마다 지정할 수 있어야 한다.**  스크립트에 좌표를
싣는 것으로 충분하다 -- 어차피 씬별 스크립트가 있고, 인계서 §7.3 이 밝힌 대로
**VRAM 빈 자리도 컷신마다 다르므로** 씬별 배정이 이미 필요하다.  같은 자리에
Y 하나를 더 얹으면 된다.

**한 줄 확정이 제일 큰 소득이다.**  §7.3 의 VRAM 계산이 여기서 닫힌다:

```
한 줄 16 음절   슬롯 16 / 20   들어간다      <- 채택
두 줄 32 음절   슬롯 32 / 20   부족했다
```

두 줄이 필요했으면 VRAM 을 더 찾거나 설계를 바꿔야 했다.  단일 버퍼로 확정된다.

### 외곽선은 이미 공짜다

"글자 모양대로 검은색을 뒤에 깔고 그 위에 흰색" 이 바로 지금 쓰는 외곽선이다.
한 스프라이트 안에서 끝나므로 슬롯이 안 늘어난다.  PCE 스프라이트 2 플레인이면
색 4 개를 쓸 수 있다:

```
색 0  투명    색 1  흰색(본체)    색 2  검정(외곽선)    색 3  여분(그림자)
```

비싼 것은 글자 모양이 아니라 **사각형 막대**다 -- 글자 없는 자리까지 칠해야 해서
256x16 막대 하나가 스프라이트 16 개를 먹는다 (슬롯 2 배).  가지 않는다.

### 남은 것

                         길이가 다를 수 있다.  대본이 쌓이면 확인

글리프 팩  자막 대본이 확정된 뒤 **실제로 쓰이는 음절만** 구우면 된다 (§3 기준 761 자).
