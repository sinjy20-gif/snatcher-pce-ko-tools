## 4. ★ 정정 — 앞 문서의 틀린 서술 둘

### 4-1. "옛 12-hex 키가 대사 6 개를 뭉갠다" — **틀렸다**

네이티브 키가 6 개니 대사도 6 개일 거라고 넘겨짚은 것이었다.  오디오를 직접 대조하니

```
00F00EAB8DA9  6 행  드리프트 [-14, -6, -85, -39, -86]   ★ 전부 같은 오디오
00500E8051BB  5 행  드리프트 [2, -23, -16, -6]          ★ 전부 같은 오디오
14 그룹 전수  -- 전부 같은 오디오 14 · 다른 것 섞임 0
대조군(서로 다른 대사) 003367 vs 0032C4 -> 정렬 안 됨
```

**뭉침이 아니라 중복 제거다.**  36 행은 실제로 **14 개 오디오**이고 각각 2~6 번 재생된다.
소유자 확인: 전부 **효과음**이고 `jp_text` 는 Whisper 환각(`<원문 14자>`).

왜 네이티브 키가 갈라지나 -- `sector` 는 재생 시작 순간의 **CD 헤드 위치**이지 오디오의
정체가 아니다.  같은 소리를 나중에 다시 틀면 헤드가 딴 데 있어 다른 키가 된다.

```
12-hex 키    내용 기준       같은 오디오를 하나로 묶는다   ✓
네이티브 키   sector 포함     같은 오디오를 6 개로 쪼갠다   ✗
```

### 4-2. 그래서 **B 안(팩·엔진을 네이티브 키로)은 취소**

자막 14 줄이 36 줄로 늘고 "한 오디오 = 한 자막" 이 깨진다.

대신 **A 안은 근거가 단단해졌다.**  두 키는 서로 다른 일을 한다:

```
자막 신원        내용 기준(12-hex)이 맞다     한 오디오 = 한 자막
안전 VRAM 자리    재생 회차별 측정이 맞다      같은 소리라도 장면마다 빈 자리가 다르다
```

지도가 네이티브 키로 회차를 갈라 재는 것은 **정확한 동작**이고, 게이트가 그것을
12-hex 로 모아 **교집합**하면 된다 (fail-closed).

### 4-3. 곁가지 -- 중복 오디오 전수

끝 8 KB 지문으로 990 개를 훑으면 **15 그룹 37 파일**이 중복이다 (고유 968).
12-hex 충돌로 걸린 14 그룹 + 1 그룹.  들으면서 분류할 때 22 개는 이미 들은 소리다.

## 5. ★ 정정 — 내 검증 하나가 무효였다

`build_voice_console_keys.py` 의 `read_addr` 역산을 고치고 "표 재생성 후 바뀐 행 0 ·
팩 바이트 동일" 이라고 보고했는데 **무효한 검증이었다.**

```python
if failures:
    raise SystemExit("키 생성 실패: ...")   # ← 엔딩 클립 65 개 때문에 여기서 죽는다
write_tsv(OUT, FIELDS, rows)                 # ← 여기까지 못 온다
```

```
voice_console_keys.tsv                     08-31 12:59:27
그 백업(오늘 만든 것)                       08-31 12:59:27   ← 초까지 같음 = 새로 안 써짐
```

파일을 **자기 복사본과 비교**한 것이었다.  팩이 바이트 동일하게 나온 것도 입력이 안
바뀌었으니 당연한 결과다.

```
유효     read_addr 계산 자체 -- 기존 979 행의 runtime_key 를 재현, 불일치 0
         (파일에서 직접 계산해 대조한 것이라 진짜다)
무효     "표 재생성 0 변경" · "팩 바이트 동일"
미검증   그 수정이 실제 표에 반영됐을 때의 결과
```

### 무엇을 고쳤나 (수정 자체는 유효)

런타임 키의 표본 3 개는 **절대 주소**(end/4 · end/2 · 5end/8)에서 읽힌다.  그걸 클립
오프셋으로 바꾸려면 그 파일이 ADPCM RAM 어디서 시작했는지를 알아야 한다.
옛 코드는 `read_addr = (end - clip_length) & 0xFFFF` 로 역산했는데, 스트리밍 대사는
클립이 64 KB 를 넘어 `clip_length` 가 더 이상 머리 길이가 아니다.

수집기가 END 마다 남기는 `read_address` + `bytes_captured` 를 쓴다 -- **역산이 아니라
실측**이다.  파일 크기와 `bytes_captured` 가 같은 행이 그 파일을 만든 포착이다.

⚠ **이 수정은 엔딩 클립 65 개가 채워져야 비로소 검증된다.**  그전에는 빌더가 못 쓴다.
지금은 옛 표가 살아 있어 팩이 잘 구워지므로 **그대로 두는 것이 안전하다.**
