## 2. ★ CD-DA 구간표가 꼬리 자막을 버리고 있었다

### 증상

`build_cdda_mini_index_all.py` 가 `트랙 12 start_frame u16 초과: -170` 으로 멈춤.

### 원인

```
트랙 11 오디오      283.7 초 (디스크 파일 크기)
구간표(세그먼트)     275.5 초에서 끝  (c11_049 가 마지막 클립)
자막 part 88·89·90   276.4 · 277.9 · 280.9 초   ← 어느 구간에도 안 든다
```

구간표의 `lba_from/lba_to` 는 "소리 나는 구간" 이 아니라 런타임이
`lba_from <= currentSector <= lba_to` 로 **자막을 찾는 범위**다. 꼬리가
안 덮이면 그 자막은 **다음 트랙**으로 밀려 붙고, 그 트랙 시작보다 앞이라
음수 프레임이 된다.

### 왜 지금까지 몰랐나

```
그동안   mini index 를 09-08 것 그대로 재사용 -> 검사가 안 돌았다
         그 판은 그 3 줄을 처음부터 안 실은 채로 만들어져 있었다
오늘     번역이 바뀌어 팩을 다시 구움 -> rec_off 가 낡아 재생성 필요
         -> 그 과정에서 검사가 **처음** 돌았다
```

**새 문제가 아니라 원래 있던 구멍이 드러난 것**이다. 데이터는 오늘 안 바뀌었다
(오늘 백업 4 개 전부 그 3 줄이 동일).

### ⚠⚠ 실패한 시도 — 트랙 끝까지 늘리면 안 된다

처음엔 18 개 트랙 전부를 **트랙 끝까지** 늘렸다. 결과:

```
mini index  690 -> 610 구간 · 16 -> 13 트랙
트랙 9 · 11 · 13 이 통째로 빠짐 ("관찰 없음")   ← 93 구간 손실
```

안전자리는 *그 구간 내내* 안 쓰인 VRAM 을 찾는데, 창을 5~17 초 넓히면 그 꼬리가
**관찰된 적 없는 구간**이라 판정을 못 하고 트랙을 버린다.
**자막 4 줄 얻자고 93 구간을 잃는 거래였다.**

### 고침 둘

```
build_cdda_segments.py         마지막 구간을 **자막 끝 + 0.5 초** 까지만 늘린다
                               자막이 꼬리에 없는 트랙은 안 건드린다
build_cdda_mini_index_all.py   '관찰 안 함(None)' 과 '자리 없음(∅)' 을 갈랐다
                               전에는 미관찰 창 하나가 트랙 전체를 죽였다
```

결과: **738 구간 · 16 트랙** (옛 판 690/16 보다 +48). 빠지는 자막 0 줄.

### ★ UNVERIFIED — 다니면서 이걸 봐야 한다

```
트랙  9  창  8 중  2 개 미관찰
트랙 11  창 87 중  3 개 미관찰
트랙 13  창 28 중  1 개 미관찰
```

base 는 **관찰된 창에서만** 검증됐다. **이 트랙들의 자막이 쓰레기 타일로 보이면
그 미관찰 구간부터 의심할 것.** CD-DA VRAM 수집기로 그 구간을 한 번 지나면 닫힌다.
빌드 로그에 `★★ UNVERIFIED` 로 찍힌다.

## 5. ★ GFX native — r1~r4 실패 원인 확정

### 문서에 적힌 원인은 틀렸다

`SNATCHER_GFX_NATIVE_REASSESS_2026-09-09.md` 는 "타이틀에서 16 B 타일 지문이
오탐" 이라고 적었다. **아니다.**

```
0.4.2 주행 3 회 · 덩어리 22 개(코나미·타이틀·오프닝 그림 전부 포함)
   지문 적중은 헌사 덩어리 **하나에서만** 16 회.  나머지 21 개 전부 0
```

### 진짜 원인 — MPR7 뱅크

```
lua/GFX/0.4.3-mpr-at-uploader.lua (정상 0.6.2)
   $725C 진입 26,576 회 · MPR7 = $00   예외 0

BIOS 변경 360 B = 파일 $02FB2-$03FCE = **뱅크 $01** = CPU $EFB2-$FFCE
```

훅은 Track 02 `$7256` 을 `JSR $FF74` 로 바꾼다. `$FF74` 는 MPR7 이고, **업로더가
돌 때 거기엔 항상 원본 뱅크 `$00` 이 매핑돼 있다.** 우리 코드는 뱅크 `$01`.
그러니 그 JSR 은 원본 시스템카드로 뛴다 — 지문·무장과 무관하게 처음부터 폭주.

증명: `SNATCHER_GFX_SIG_NEVER=1` 로 지문을 절대 안 맞게 해 **주입 0 회**인
`0.6.3-diag-gfx-nosig` 를 구웠는데 **여전히 배경이 깨졌다** (Track02 는 r4 와
바이트 동일, BIOS 만 16 B 차이).

★ 일반화: **Track 02 → BIOS 로 건너뛰는 훅만 위험하다.** BIOS 가 부르는
`$FC07` tick 이나 `$ECF9` CD-DA 스케줄러는 같은 주소대라도 안전하다 —
호출 문맥이 다르기 때문이다.

### 오프닝 순서 (문서 정정)

```
✗ 문서    부팅 → 타이틀 → 헌정
✓ 실제    코나미 → 타이틀 → 파란화면(픽션 고지) → RSS → 헌사 → 모스크바 …
```

### 무장 신호 — 완전히 결정론적

```
무장   CD_READ($E009) · 제로페이지 위치 $20FD:$20FE = $03:$5A · 호출자 $54E4
       ⚠ HuC6280 zero page 는 $2000-$20FF 다 ($0000 아님)
       7,000 프레임 주행에 딱 1 회

               무장    +544     +1194    +1588
1 회차 f4698   파란화면  RSS      헌사
2 회차 f4534   파란화면  RSS      헌사
               ────────────────────────────
               모든 간격이 프레임 단위로 동일
```

덩어리 구조도 호출 수까지 같다 (2,400 / 15,072 / 3,696 / 3,392 / 2,016).
입력 없이 자동으로 흐르는 시퀀스라 그렇다.

### 22 덩어리 표 (접수처 방향 주행)

```
burst 무장후  frame    calls   caller    화면
  1          3460      2,400   $70AA    코나미
  2          4328     15,072   $7175    타이틀
  3     1    6577      3,696   $7081    파란 화면
  4     2    7227      3,392   $70EC    RSS
  5     3    7621      2,016   $70EC    ★헌사 (지문 16)
  6~22  4~20                            오프닝 그림들
```

★ 호출자 6 종(`$70EC` 13 회 · `$7081` 2 · `$70DE` 2 · `$70AA`·`$7175`·`$70BC`·`$7141`·`$74FF`).
**호출자 단독으로는 화면을 못 가른다** (RSS·헌사가 둘 다 `$70EC`).
다만 한 번만 쓰인 것(`$7141`·`$74FF`·`$70BC`)은 그 자체가 신호가 된다.
호출 수도 화면 내용량에 비례해 식별에 쓸 수 있다.

⚠ `burst 20`(448 회)·`burst 22`(22 회)는 화면 한 장 올리기엔 너무 작다 —
**22 덩어리 ≠ 22 화면**이다.

### r5 설계 — Track 02 를 아예 안 건드린다

```
무장   CD_READ($E009) 위치 $03:$5A     ← BIOS 호출.  MPR7 이 우리 것
대기   tick 이 프레임을 센다 (+1588)    ← 주행 2 회 오차 0
확인   $3B00 타일 지문                  ← RAM 이라 BIOS 에서 읽힌다
주입   기존 injector 369 B 그대로       ← 새 코드 자리를 안 찾아도 된다
```

자리 문제도 이걸로 사라진다. 실측한 여유:

```
BIOS 뱅크1  injector 12 B · helpers 41 B · tick 10 B      합계 약 63 B
Bank 69     $BCD2-$BFFF 814 B — 자막 헬퍼가 전부 사용
Track02     bank A/B 에 FF 굴 **0 B**                      ← 옮길 자리가 없다
```

데이터(타일·BAT)는 AC 로 가므로 여유롭다 (헌사 4,718 B, 30 장이면 약 150 KB).

### ⚠ 그 설계의 '확인' 칸은 못 쓴다 (0.5.0 실측)

```
lua/GFX/0.5.0-tick-can-see.lua   무장 f4906 -> 헌사 f6494
   프레임 경계 지문 일치  f7200 까지 0 회
```

지금까지 지문은 *업로더 호출마다* 봤다 (한 덩어리에 수천 번). tick 은 *프레임에
한 번*만 본다. 헌사 덩어리는 호출 2,016 회가 몇 프레임 안에 끝나므로, 그 한 번이
하필 그 16 B 타일에 걸릴 확률이 낮다. **r2 가 "나중에 보니 버퍼가 이미 덮여
있었다" 로 죽은 것과 같은 벽이다.**

=> `$3B00` 지문은 **호출 단위 신호**지 프레임 단위 신호가 아니다.

남는 길 둘:

```
A  타이밍만으로 간다      무장 -> N 프레임 뒤 주입.  주행 2 회 프레임 오차 0
B  프레임에 오래 남는 다른 신호를 찾는다
```

둘 다 **덩어리가 몇 번째 프레임에 몇 프레임 동안 걸쳐 있는지**를 먼저 알아야 한다.
지금 아는 `+1588` 은 *업로더 호출 순서*로 잰 값이고 프레임과의 관계가 아니다.
`lua/GFX/0.5.1-burst-frame-map.lua` 가 그것만 잰다 —
덩어리 길이가 1~3 프레임이면 A 안 확정, 길면 B 안이 살아난다.
덩어리마다 `무장후` 값이 유일하면 **타이밍 자체가 신원**이라 지문이 필요 없어진다.

```

내 추론 오류: `SNATCHER_GFX_SIG_NEVER=1` 실험은 **"방아쇠가 아니다"까지만**
증명했다.  그러면 용의자로 **패치 자리 둘(Track02 · BIOS)** 이 남는데,
나는 거기서 MPR7 실측을 근거로 Track02 하나로 단정했다.
BIOS 쪽을 안 지운 채였다.

```
