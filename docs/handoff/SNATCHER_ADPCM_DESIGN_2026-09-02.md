# SNATCHER ADPCM 네이티브 설계서

작성일: 2026-09-02  
상태: 최신 Office 마스터 반영 후 기준, 환경 A `dump/` 반영 전의 설계 기준

## 1. 목표

ADPCM 음성이 시작되면 음성의 시작 LBA를 이용해 정확한 자막 레코드를 찾고, 기존에 검증된 공용 자막 렌더러가 조각을 순서대로 표시한다.

```text
ADPCM 시작 감지
  → 시작 LBA 추출
  → LBA 색인 조회
  → mini index / 첫 selector 설치
  → 공용 renderer 기동
  → 조각별 자막 출력
  → 음성 종료 후 정리 및 게임 복귀
```

ADPCM 전용 렌더러를 새로 만들지 않는다. CD-DA도 최종적으로 같은 렌더러를 사용하고, 매체별 차이는 감지기·시간표·종료 정책에서만 처리한다.

## 2. 기준으로 삼는 성공 경로

### 네이티브 데이터 경로

검증된 D000 경로는 다음과 같다.

```text
AD_TRANS 시작 LBA
  → native route 조회
  → AC mini index에 해당 음성의 조각 목록 복사
  → AC active engine에 첫 selector 설치
  → state active
  → 공용 renderer가 CPU 실행 영역으로 연결
```

LBA는 ADPCM RAM의 샘플값을 추측해 만드는 방식이 아니라, ADPCM 전송 명령의 시작 LBA를 기준으로 한다. 이 방식은 음성 RAM을 읽거나 재생 중인 버퍼를 건드리지 않아 재생 교란 위험이 낮다.

### 조각 스케줄

검증된 3조각 기준은 다음이다.

```text
part 1/3  시작
part 2/3  +90 frame
part 3/3  +180 frame
종료      마지막 조각 종료 후 정리
```

음성마다 조각 수가 다르므로 1조각부터 최대 11조각까지를 데이터로 보존한다. 3조각을 모든 음성에 강제로 적용하지 않는다.

## 3. 현재 데이터 상태

최신 Office 묶음과 현재 분석 결과 기준이다. 환경 A에서 가져온 `dump/`를 반영하면 다시 갱신한다.

```text
ADPCM 전체 확장 대상       약 937 음성 / 2,014 조각
기존 자막 팩               188,044 B / 192 KiB 한도 중 약 95%
ADPCM 안전자리             190 / 933
안전자리 원본 개선 전      50 / 933
콘솔 키 미확보             148개
runtime key 충돌           5건
19칸 초과                  4건
```

효과음은 자동 판별하지 않는다. 사용자가 Studio에서 효과음으로 표시한 항목만 효과음으로 취급하며, `기타`, 자막 없음, 키 없음만으로 효과음으로 바꾸지 않는다.

## 4. 안전자리 표와 키 형식

안전자리 숫자가 움직이지 않았던 원인은 두 가지였다.

1. 게이트가 읽는 `vram_key_bases_pairs.tsv`가 옛 12-hex 키 형식 50개만 가지고 있었다.
2. 새 `ADPCM_...` 키를 쓸 때 표 정렬이 기본 `0x20`이라 native 재무장 엔진이 요구하는 `$0100` 정렬을 통과하지 못했다.

현재 원칙은 다음과 같다.

```text
Studio/런타임 키       voice_console_keys.tsv의 runtime_key_hex
안전자리 쌍 표         새 키와 옛 12-hex를 연결한 pairs 표
정렬                   --pairs --align 0x100
게이트                 6바이트 runtime key 입력
```

환경 A `dump/`의 최신 원자료에는 새 키와 옛 키가 함께 있을 가능성이 있으므로, 반영 시 기존 pairs를 덮어쓰기 전에 백업하고 3세대 원자료와 다시 생성한다.

## 5. 메모리·팩 설계

### 팩 구성

ADPCM 네이티브 경로는 다음 데이터를 분리한다.

```text
자막 텍스트/글리프       공용 렌더링 데이터
ADPCM route index        시작 LBA → mini payload 위치
mini payload             한 음성의 조각 목록
engine template           공용 653 B renderer
runtime state             현재 음성·조각·경과 프레임
```

전체 음성을 감지하는 색인과 실제 자막을 표시할 수 있는 레코드는 분리한다.

```text
전체 음성 감지           key/LBA 존재 여부 확인
자막 표시                유효한 text record와 glyph 존재 시에만 실행
키 미스                  fail-closed
효과음                   자막 renderer 무개입
```

### AC 용량

현재 팩은 192 KiB 한도에 거의 도달했다. 따라서 전체화를 진행할 때는 먼저 다음을 실측한다.

- 새 route/index 추가 후 실제 팩 끝 주소
- 번역 데이터 영역과의 경계
- 글리프 중복 및 압축 가능 영역
- 누락 148개를 넣었을 때의 증가량
- 충돌 5건을 해결했을 때의 증가량

`AC_PACK_MAX`를 바로 늘리지 않는다. `$1C0000` 아래 번역 데이터 영역과 겹치는지 확인한 뒤 저장 위치를 결정한다.

## 6. 런타임 상태 설계

공용 엔진이 관리할 최소 상태는 다음이다.

```text
media          ADPCM
voice_id       현재 음성
part_index     현재 조각
part_count     전체 조각 수
start_frame    현재 조각 시작 프레임
duration       조각 지속시간
active         renderer 실행 여부
restore_mode   정상 종료 / 스킵 / 무개입
```

ADPCM은 CD-DA와 state 의미를 공유하되, 종료 판정은 ADPCM 재생 상태에 맞춰 별도로 둔다. CD-DA 종료 비트를 ADPCM 종료 조건에 재사용하거나, 반대로 ADPCM playing bit를 CD-DA에 요구하지 않는다.

## 7. 제작 단계

### 1단계 — 최신 원자료 회수

- 환경 A `dump/`를 현재 작업 폴더에 복사한다.
- 기존 `vram_key_bases.tsv`, `vram_key_bases_pairs.tsv`, runtime key 표를 백업한다.
- 최신 spans와 console key를 키별로 대조한다.
- 안전자리 190과 실제 새 키 coverage를 재검증한다.

### 2단계 — 데이터 정리

- 콘솔 키 없는 148개를 원자료에서 재탐색한다.
- 충돌 5건은 같은 6바이트 키가 왜 발생하는지 원본 end address/rate/sample을 비교한다.
- 19칸 초과 4개는 자막 문장 자체를 임의로 줄이지 말고, 해당 음성의 표시 정책을 결정한다.
- 팩을 늘리기 전에 번역·글리프·route 중 무엇이 필요한지 분리한다.

### 3단계 — 단독 ADPCM 네이티브 확정

다음 순서로 대표군을 검증한다.

```text
1조각 음성
3조각 음성
최대 조각 수 음성
연속 음성 전환
키 미스
사용자 지정 효과음
19칸 초과 음성
```

판정 항목은 자막 출력만이 아니다.

```text
음성 시작 감지
첫 selector 설치
조각 전환
음성 종료
자막 정리
UI 복귀
게임 진행
화면 잔상/깨짐 없음
```

### 4단계 — 전체 ADPCM 확장

대표군이 모두 통과한 뒤 전체 route를 연결한다. 전체 937음성을 한 번에 상태 변경 대상으로 넣지 않고, 감지 로그와 렌더 대상 로그를 분리해 단계적으로 확대한다.

### 5단계 — CD-DA 연결

ADPCM 단독판을 기준으로 CD-DA 감지기와 타임라인 어댑터만 추가한다. CD-DA 엔진을 두 번째 렌더러로 탑재하지 않는다.

## 8. 금지 사항

- `기타`를 자동으로 효과음 처리하지 않는다.
- 안전자리 숫자만 보고 실제 표시 가능하다고 판정하지 않는다.
- 6바이트 키 충돌을 임의의 빈자리 선점으로 해결하지 않는다.
- AC 용량이 부족한 상태에서 전체 route를 강제로 굽지 않는다.
- ADPCM과 CD-DA의 종료 비트를 공용 조건으로 합치지 않는다.
- 자막 표시 성공만 보고 UI 복귀와 게임 진행을 통과 처리하지 않는다.
- 원본 `dump/`를 반영하기 전에 기존 색인 표를 덮어쓰지 않는다.

## 9. 다음 작업

현재 다음 작업은 환경 A `dump/` 반영 후 아래 순서다.

1. `vram_key_spans3`와 `voice_console_keys` 재생성/대조
2. ADPCM safe coverage와 키 누락·충돌 재계산
3. 팩 사용량 재계산
4. 대표 ADPCM 네이티브 테스트판 작성
5. 1/3/최대 조각 및 종료/UI 복귀 검증
6. ADPCM 전체 route 확장
7. 그 후 CD-DA 감지·타이밍 어댑터 연결

## 10. 핵심 요약

ADPCM은 이미 `LBA → mini index → 첫 selector → 공용 renderer → 조각 scheduler`라는 성공 방정식이 있다. 현재 남은 일은 새로운 엔진을 만드는 것이 아니라, 환경 A의 최신 dump로 키와 안전자리 표를 갱신하고, 팩 용량·키 충돌·누락을 정리한 뒤 검증된 3조각 경로를 전체 음성으로 확장하는 것이다.
