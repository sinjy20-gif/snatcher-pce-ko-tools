# 자막 팩 — 데이터를 코드에서 떼어냈다 (2026-08-23 저녁)

`SNATCHER_SUBTITLE_PIPELINE_2026-08-23.md` 다음이다. 그 문서 §9.1 이 남긴
질문 — "코드를 어디 둘 것인가" — 은 **아직 안 풀렸다**. 대신 그 답과 무관하게
확정인 것부터 만들었다.

---

## 1. 왜 데이터만 따로 굽나

`build_subtitle_disc_payload.py` 는 폐기됐다. `$5C40-$5E1F` 를 상주 코드 자리로
가정했는데 거기가 스크립트 VM 데이터 스택이었다.

그 폐기가 무효로 한 것은 **배치**지 **데이터**가 아니다.

```
폐기      $5C40 상주 가정 · 1 차 페이로드의 코드 배치
살아남음  글꼴 · 트리거(ADPCM 지문 · CD-DA LBA) · 세그먼트 표 · 글자 배치 계산
```

감시자를 헬퍼 여유 151 B 에 두든 다른 데 두든, **자막 데이터는 한 글자도 안 바뀐다.**
그래서 지금 만들 수 있었다. `tools/build_subtitle_pack.py`.

## 2. 팩 형식 (버전 2)

AC `$1C0000` 에 통째로 올라간다. 예약은 256 KB.

### 머리 64 B

```
+00  magic        "SNSB"
+04  version      u16 = 2
+06  flags        u16 = 0
+08  glyph_count  u16
+0A  glyph_off    u32
+0E  adpcm_count  u16      ★ 조각 수다 (이벤트 수가 아니다)
+10  adpcm_off    u32
+14  cdda_count   u16
+16  cdda_off     u32
+1A  record_off   u32
+1E  pack_bytes   u32
+22  glyph_bytes  u8  = 64
+23  cell_bytes   u8  = 4
+24  limit_px     u16 = 192
+26  char_off     u32
+2A  adpcm_stride u8  = 12
+2B  cdda_stride  u8  = 10
+2C  rec_header   u8  = 6
```

모두 리틀엔디안. 오프셋은 **팩 머리 기준**이라 AC 어디에 올리든 그대로 쓴다.
항목 크기를 머리에 적어 둔 것은 런타임이 판마다 상수를 새로 박지 않게 하려는 것이다.

### 색인 둘 — 트리거 성격이 다르기 때문이다

```
ADPCM  12 B  읽기주소 u16 · 길이 u16 · 재생률 u8 · 플래그 u8
             시작프레임 u16 · 기록오프셋 u32
             사건 기반.  재생 시작 순간의 레지스터 세 값이 그대로 열쇠다

CD-DA  10 B  lba_from u24 · lba_to u24 · 기록오프셋 u24 · 플래그 u8
             시계 기반.  lba_from 으로 정렬 -> 런타임은 이분 탐색
             613 항목이어도 비교 10 번이면 끝난다
```

**둘 다 조각 단위다.** ADPCM 은 `(지문, 시작프레임)` 으로 정렬해 두어 한 이벤트의
조각들이 **붙어 있다**. 런타임은 첫 항목을 찾은 뒤 지문이 같은 동안 앞으로
걸어가기만 하면 된다 — 사슬을 따로 만들 필요가 없다.

> **버전 1 은 여기서 틀렸다.** 지문 하나에 기록 하나만 달아서, 조각이 여럿인
> 이벤트는 조각 2·3 이 소리 없이 사라졌다. 그것이 "지문 충돌 3 건" 으로
> 보고됐는데 충돌이 아니라 같은 이벤트의 조각이었다.

CD-DA 의 절대 LBA 는 `구간 시작 + 조각의 상대 시각 × 75` 로 여기서 미리 낸다.
런타임은 곱셈을 안 한다 — 6280 에 곱셈기가 없다.

### 기록 — 런타임이 계산을 하나도 안 하게

```
+00  cell_count u8
+01  width_px   u8
+02  flags      u8      bit0 = 대사
+03  (pad)
+04  frames     u16     이 조각이 떠 있는 길이
+06  칸 × 4 B  글리프번호 u16 · x u8 · y u8
```

**펜 위치를 미리 다 박아 둔다.** 자막 글꼴은 비례폭이라(한글 10 px, 영문 2/3)
런타임이 누적 덧셈을 해야 하는데, 그걸 빌드 때 끝내 버렸다. 런타임은 SATB 에
그대로 밀어 넣기만 한다.

### 글리프 · 글자표

```
글리프  64 B/자   플레인 0 본체 · 플레인 1 검은 외곽선
                  VRAM 에 올릴 때 플레인 2·3 을 0 으로 채워 128 B 로 편다
글자표  2 B/자    코드포인트.  런타임은 안 쓴다
```

글자표는 **팩을 글로 되돌리기 위한 것**이다. 이게 없으면 팩을 열어도 무슨 글자가
들어갔는지 알 수 없고, 검증기와 Lua 로그가 "지금 뭘 그리는지" 못 찍는다.

**쓰이는 글자만 싣는다.** 글꼴 전체 3320 자는 208 KB 라 예약을 혼자 다 먹는다.

## 4. 검증기 — 만든 쪽 말을 안 믿는다

`tools/verify_subtitle_pack.py`

빌더는 "8,820 B 를 썼다" 고 말하지만, 그 말이 맞는지는 그 코드가 판단할 수 없다.
같은 가정으로 쓰고 같은 가정으로 세기 때문이다. 그래서 검증기는 **`.json` 을 안
본다.** `.bin` 의 머리 64 B 만 읽고 오프셋을 따라가 글자를 복원한다 — 런타임이
할 일과 똑같다. 여기서 글이 돌아오면 런타임도 돌아온다.

```
구조    구간이 붙어 있는가 · 파일 밖으로 나가지 않는가 · 항목 크기가 머리와 맞는가
왕복    기록을 글로 되돌려 원본 TSV 와 같은가
누락    ★ 원본에 있는 자막이 전부 팩에 들어갔는가
색인    CD-DA 가 정렬돼 있는가 · 구간이 겹치는가
        ADPCM 의 같은 지문 조각들이 **붙어 있는가**
배치    펜 위치가 늘어나는가 · 줄 폭이 한계를 넘는가
글리프  비트맵이 통째로 0 인 글자가 있는가 (공백 말고 0 이면 글꼴 오프셋 오류)
```

> **누락 검사가 핵심이다.** 첫 판 검증기는 "팩에 있는 글이 원본에 있나" 만 봐서,
> 조각 2·3 을 통째로 잃고도 통과했다. 방향을 뒤집어 **원본이 다 들어갔는지**를
> 세게 바꾸고서야 버그가 드러났다.

지금 상태: `CD-DA 8/8 · ADPCM 6/6 조각` 전부 통과.

## 5. 오늘 스튜디오에서 고친 것

```
삭제 버튼      SelectedRows 가 비면 조용히 return 하던 것.  콤보 셀 편집 중에는
               선택이 비고 CurrentRow 만 남아서 눌러도 반응이 없었다
               -> 커서 행으로 되돌아가고, 여러 행을 고르면 전부 지운다
CD-DA 편집칸   대사 탭과 같은 모양.  오른쪽 위 일본어 · 아래 한국어 · 폭 초과 시 빨강
일본어 나누기  ★ 새로 넣음.  아래 참고
```

> **조용한 return 은 버그를 숨긴다.** 같은 뿌리로 구분 버튼(대사/효과음/기타)도
> 안 먹고 있었다. 선택 계열은 전부 `SelectedVoiceRows()` 로 통일했다 —
> 선택이 비면 `CurrentRow` 로 되돌아간다.

### 일본어 나누기

한국어는 조각으로 나뉘는데 일본어는 통짜라 **어느 원문이 어느 조각인지 안 보였다.**
`cdda_subtitles.tsv` 에 `jp_text` 열을 넣고, 구간의 일본어를 조각들에 나눠 담는다.

전사에는 **낱말 시각이 없다** — 한 구간에 문장이 통째로 있을 뿐이다. 다시 전사하지
않기로 한 이상 남은 것은 어림이고, 두 단계로 자른다:

```
1 순위  구두점 (。、！？ 공백)
2 순위  히라가나 -> 한자·가타카나  = 대개 낱말 머리
3 순위  시간 비례 그 자리
```

방향이 중요하다. 반대쪽(한자 → 히라가나)은 어간과 오쿠리가나 사이라 더 나쁘게
잘린다 — `黙 / <원문 6자>` 를 실제로 봤다.

실측: 전체 195 곳 중 낱말 가운데로 의심되는 컷 **7 곳 (3%)**.

```
[c04_005]  구두점이 있는 경우 — 전부 문장 경계
   1. <원문 5자>、<원문 13자>。
   2. そのため、
   3. 年々<원문 12자>。

[c01_007]  구두점이 없는 경우 — 문자종 전환으로
   3. <원문 14자>
   4. <원문 19자>
```

이미 손으로 넣은 일본어는 **덮지 않는다.** 표에서 고칠 수 있고, 오른쪽 창은
지금 고른 조각에 `▶` 를 붙여 보여준다.

`jp_text` 는 **참고용이다.** 팩에는 안 들어간다 — 화면에 나가는 것은 한국어뿐이다.

## 6. 감시자 자리 — 후보를 좁혔다

### 헬퍼 여유 151 B 는 안 된다

가장 유력했던 후보인데 **상주가 아니다.** 기존 연구가 이미 답을 갖고 있었다:

```
helper_base = $BCD2 · helper_limit = $C000        helper_symbols.json
$7F88 트램펄린이 MPR5 를 뱅크 $69 로 갈아끼우는 동안에만 헬퍼를 부른다
505 프레임짜리 호출에도 **프레임 경계 MPR5=$69 가 0 건**   (08-13 · 08-14 인계서)
```

IRQ1 이 뜨는 순간 `$BCD2` 에는 헬퍼가 없다. 프레임 훅을 걸 수 없다.

### 오버레이 구멍 여섯 중 다섯도 안 된다

`PROBE_OVERLAY_HOLE 0.1.0` 이 73200 프레임 무접촉 구간 여섯을 줬다. 측정은 옳게
만들어졌다 (읽기·쓰기·실행 셋 다). 그런데 **디스크를 안 봤다.**

`tools/check_overlay_holes.py` 로 확인한 결과:

```
$6A94-$6B93  256 B   멀쩡한 루틴 (JSR $663A · $3370,X 카운터).  9 군데가 가리킨다
$78E5-$7998  180 B   루틴.   2 군데
$79C6-$7A5E  153 B   루틴.   4 군데
$7A8D-$7B00  116 B   루틴.  13 군데
$7C6F-$7CB3   69 B   루틴.   2 군데
$7FA0-$7FEB   76 B   전부 FF · 가리키는 곳 0 군데      ← 유일한 생존자
```

다섯은 **휴면 코드**였다 — 73200 프레임에서 안 돌았을 뿐 특정 장면의 경로다.
덮었으면 그 장면에서 죽었을 것이다. 규칙이 한 겹 늘었다:

> `Write 를 못 봤다 != 안전` 에 이어
> **`안 돌더라도 코드가 있으면 산 자리다`**

검사기가 제대로 도는지는 `$7CD2-$7FFF` 가 증명한다 — 디스크에서 전부 FF 인데
가리키는 곳이 24 군데 나온다. 헬퍼 케이브가 맞다.

### 다음: `$7FA0-$7FEB` 76 B 를 험한 장면까지

`lua/PROBE_OVERLAY_HOLE_0_2_0.lua`. 0.1.0 의 목록은 "한 장면에 오래 머문" 탓에
부풀었을 수 있다. **세이브/로드 · 사격 씬 · 장면 전환**을 반드시 지날 것.

76 B 면 감시자 전체는 안 들어간다. 대신 이런 몫이면 된다:

```
오버레이 A 안 (76 B)   음성 중인가 보고, 맞으면 $5B80 엔진으로 넘긴다
$5B80-$5E3F (704 B)    엔진 본체.  음성 중에만 빈다 (134/134 실측)
```

훅과 감시자가 **같은 오버레이에 같이 실린다** — 닭-달걀도 잔류도 없다.

### 상주부는 32 B 다 — 실제로 짜서 셌다

`tools/build_resident_stub.py --at 7FA0`. 상주부는 **일을 안 한다.** 판단 하나만
하고 넘긴다.

```
7FA0  08              PHP
7FA1  78              SEI
7FA2  A9 3F           LDA #$3F      ┐ 밀려난 원래 명령
7FA4  85 17           STA $17       ┘ 조건과 무관하게 항상
7FA6  AD 80 5B        LDA $5B80     ┐
7FA9  C9 53           CMP #'S'      │
7FAB  D0 11           BNE done      │
7FAD  AD 81 5B        LDA $5B81     │ 엔진 매직 3 B
7FB0  C9 55           CMP #'U'      │
7FB2  D0 0A           BNE done      │
7FB4  AD 82 5B        LDA $5B82     │
7FB7  C9 42           CMP #'B'      │
7FB9  D0 03           BNE done      ┘
7FBB  20 83 5B        JSR $5B83     엔진 진입점
7FBE  28        done: PLP
7FBF  60              RTS
                                    32 B · 구멍 76 B 기준 여유 44 B
```

매직을 3 바이트 보는 이유: `$5B80` 은 VM 스택 바닥이라 음성이 아닐 때는 게임 값이
들어 있다. 그냥 `JSR` 하면 쓰레기를 실행한다 — `SUBTITEL 0.2.5` 가 정확히 그렇게
부팅에서 멈췄다. 2 바이트(1/65536)면 60 fps 로 18 분마다 한 번 우연히 맞는다.
3 바이트면 3 일이다.

빌더에 금지 구역 가드를 넣었다 — §6 에서 탈락한 다섯 범위와 VM 스택을 주면 멈춘다.
훅은 `$601E` 를 `20 A0 7F EA` 로 덮는다.

### 곁가지로 나온 지도

```
오버레이 A (섹터 251)   스프라이트 엔진.  우리 $601E 훅이 여기다
오버레이 B (섹터 255)   ★ 오디오 드라이버.  AD_RESET/TRANS/READ/CPLAY/STOP/STAT ·
                        CD_PLAY/PAUSE/STAT 가 전부 여기 있다 ($604F-$6493)
```

둘은 같은 `$6000-$7FFF` 창을 쓰므로 **동시에 올라오지 않는다.** 같은 `$601E` 가
A 에서는 `LDA #$3F / STA $17`, B 에서는 `JSR $E01E` 다 — 지문 검사가 왜 필요했는지
여기서 다시 확인된다.

포트를 직접 쓰는 곳은 A·B 통틀어 **0 건**이다. 그래서 "재생 루틴을 후킹해 사건으로
받는다" 는 길은 오버레이가 아니라 BIOS 쪽을 봐야 한다 — 지금은 접어 둔다.

### 오늘 저녁에 뒤집힌 것 셋

**1. 지문은 끝 주소로 정규화해야 한다**

팩 버전 2 는 `(읽기주소, 길이, 재생률)` 세 값을 정확히 맞추려 했다.  **하나도 안
맞았다.**  실측:

```
팩 0063+CF9D = D000     런타임 0068+CF98 = D000
팩 0066+579A = 5800     런타임 0064+579C = 5800
팩 006B+6795 = 6800     런타임 0070+6790 = 6800
```

재생 시작 지점이 매번 달라 읽기주소와 길이가 서로 상쇄되고, **합만 안 변한다.**
기존 연구가 "끝 주소로 정규화" 라고 한 것이 이 뜻이었는데, 팩을 만들 때
"정확한 세 값이 더 정밀하다" 며 일부러 뺐다.  정밀한 것이 아니라 **안 맞는 값**이었다.

> 대가는 알고 간다: 449 이벤트 -> 71 열쇠로 뭉갠다.  빌더가 충돌을 세어 보고한다.

**2. 팔레트 0 은 메뉴가 쓴다**

레코드 5 번째 바이트의 **하위 니블이 팔레트 번호**다 (`$6463` 이 `AND #$8F` 로
속성을 뽑는다).  0 으로 두고 팔레트 0 의 색 1·2 를 흰/검으로 덮었더니 **메뉴 선택
하이라이트가 깨졌다.**  팔레트 15 로 옮겼다 (VCE `$1F1`).

**3. VRAM 은 빌리되 되돌려야 한다**

```
항상 빈 VRAM 은 없다        32768 워드 중 31620 이 쓰인다 (PROBE_VRAM_FREE 0.2.0)
음성 중에는 거의 안 쓴다     $2078-$7FFF 24456 워드 무변화 (PROBE_VRAM_VOICE 0.1.0)
```

`$5B80` 과 같은 모양이다.  다만 **RAM 과 달리 게임이 안 지운다** -- 하이라이트가
음성이 끝난 뒤에도 계속 깨져 있었다.  그래서 음성 시작에 576 워드를 떠 두고
끝나면 되돌린다.  지금은 Lua 가 하고, 엔진으로 옮길 때는 AC 에 뜬다 (704 B 에
1152 B 버퍼가 안 들어간다).

> `$1080-$1FFF` 도 "음성 중 무변화" 로 잡히지만 **쓰면 안 된다.**
> 워드 `$1000-$10FF` 가 SATB 이고 그 뒷절반이 안 쓰는 슬롯이라 안 바뀐 것뿐이다.

### 4. 한 줄 상한과 자리

9 자 상한은 **VRAM 자리가 없어서** 뒀던 것이다.  되돌리게 된 뒤로는 음성 중에
비어 있기만 하면 얼마든 빌릴 수 있다.

```
19 자 = $4C0 워드 -> $7900-$7DBF        음성 중 빈 창 $2078-$7FFF 안
19 자는 실측 한 줄 한계다 (192 px · 초상화 위 폭)
```

자리는 세 칸이다.  기록 머리의 남는 바이트를 y 로 쓴다 (팩 버전 4 · 크기 안 늘었다).

```
위 32 · 중간 122 · 아래 192        기본  ADPCM 중간 · CD-DA 아래
```

**중간 122 가 눈으로 맞춘 값**이라 게임 중 대사는 그대로고, 컷신은 화면을 다 쓰므로
아래로 간다.  자막 **한 줄 단위**라 특정 줄만 올릴 수도 있다.

따로 있다. 그쪽은 BIOS·펌웨어가 들어가고 음원이 없다).
