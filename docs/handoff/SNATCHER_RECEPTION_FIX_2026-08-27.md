## 2. 폐기된 주장 — 읽고 반복하지 말 것

`SNATCHER_PRELOAD_RECEPTION_2026-08-27.md`는 `0.4.6.7`을 해결책으로 기록했지만
그 빌드는 접수처에서 크래시했고, `0.4.6.8`은 크래시는 없었으나 복구 루틴이
**한 번도 실행되지 않았다.** 확인된 사실은 다음과 같다.

### 2-1. `$5E40`은 단순 문자 fetch가 아니다 — 포인터를 갈아치운다

`$66E5`의 원본은 `JSR $5E40`이고, `0.4.6.7`/`0.4.6.8`은 **그 호출 뒤에**
`$3471/$3472`를 읽어 접수처를 판정했다. 그런데 `$5E40`(디스크 bank 68)은
게임 자신의 접수처 판정을 내장하고 있고, 그 분기를 빠져나오며 포인터를
덮어쓴다.

```text
5E54  AD 71 34   LDA $3471          ; 포인터를 $03/$04로
5E5E  C9 34      CMP #$34
5E6E  A5 03      LDA $03
5E70  C9 99      CMP #$99           ; 접수처 판정이 여기 이미 있다
5E74  C9 9A      CMP #$9A
...
5F8A  A9 90 8D 71 34   LDA #$90 / STA $3471
5F8F  A9 5B 8D 72 34   LDA #$5B / STA $3472   ; 포인터 -> $5B90
```

런타임 실측(`SUB 0.3.31`):

```text
GUARD WINDOW ptr_before=$3499  ->  after JSR $5E40: ptr=$5B90 A=$90
```

**따라서 `$5E40` 뒤에서는 `$3499/$349A`를 절대 볼 수 없다.** 검증된 POC
`SUB 0.3.24`가 `$66E5` 실행 시점(호출 **전**)에 읽었던 이유가 이것이다.
`0.4.6.9`는 가드를 `JSR $5E40` 앞으로 옮겼다.

### 2-2. `0.4.6.7` 크래시의 진짜 원인은 IRQ 벡터 상실이었다

`TAM #$80`으로 MPR7을 bank 1로 바꾸면 `$FFF6-$FFFF`의 인터럽트 벡터가 전부
`$FF`가 된다.

```text
bank0 vectors FFF6-FFFF: 36 E7 70 E8 B3 E6 A9 E6 F3 E0
bank1 vectors FFF6-FFFF: FF FF FF FF FF FF FF FF FF FF
```

`0.4.6.7`에는 `SEI`가 없어 bank 1 매핑 구간에서 IRQ가 뜨면 `$FFFF`로 점프했다.
`0.4.6.8`이 `PHP/SEI`를 넣은 뒤로 크래시가 사라졌고, 이는 부수적으로
**`$5E40`이 `$E000-$FFFF`를 건드리지 않는다는 것도 실증**한다 — bank 1이
매핑된 채로 게임 전체에 걸쳐 수십만 번 호출되고도 멀쩡했다.

### 2-3. 접수처 문자열은 여러 번 다시 그려진다

`SUB 0.3.31` 실측:

```text
GUARD WINDOW frame=28484 / 28486 / 28487 / 28489 / 28491
```

메뉴가 떠 있는 동안 `$3499` 문자열이 반복 렌더된다. `0.4.6.9`는 복구 후 훅을
원복하므로 매 패스마다 arm→복구를 반복하고, 마지막 패스의 복구가 남는다.
"첫 `$66F8`에서 복구하면 너무 이르지 않나"는 우려는 이 때문에 성립하지 않는다.

### 2-4. 렌더러 코드 영역은 장면 종료 후 덮어써진다

```text
frame=28500 이후  66E5=D4 29 7F  66F8=DE 80 33
```

`$66xx`는 렌더 패스가 끝나면 다른 데이터로 교체된다. 이 주소들의 바이트를
장면 밖에서 읽어 판단하면 안 된다. 디스크의 패치는 다음 로드 때 다시 올라온다.

## 3. `0.4.6.9`의 구조

디스크 변경은 한 곳뿐이다. `$66F8`은 디스크상 원본이며 armed 상태에서만
런타임에 바뀐다.

```text
Track02 $66E5   20 D4 FF        JSR $FFD4   (원본 20 40 5E)
Track02 $66F8   4C 3F 68        원본 유지
```

BIOS:

```text
bank0 $FFD4  08 78 A9 01 53 80   PHP / SEI / LDA #$01 / TAM #$80   (6 B / 8 B 케이브)
bank1 $FFDA  4C 54 F0            TAM 직후 착지 -> dispatch
bank1 $F054  150 B               dispatch $F054 / repair $F08A
bank1 $F04E  53 80               TAM #$80 -> bank 0
bank0 $F050  68 28 60            PLA / PLP / RTS   (기존 BIOS 바이트 재활용)
```

dispatch 흐름:

```text
$66F9 == $D4 ?  -> repair
아니면 가드:  $3472==$34 && $3471 in {$99,$9A}
   -> arm: $66F8 = JMP $FFD4,  $66E5 = 원본 JSR $5E40 (훅 해제)
   -> fetch: JSR $5E40 / PHA / 복귀

repair: PHX/PHY -> 두 훅 원복 -> VDC $1600에 512 B -> PLY/PLX/PHA -> 복귀
```

설계상 중요한 점 세 가지:

- **가드가 `JSR $5E40`보다 먼저** 실행된다 (2-1).
- **arm이 `$66E5` 훅을 해제**한다. `$66E5`는 문자마다 불리므로, 해제하지 않으면
  같은 문자열의 다음 글자가 repair 분기로 들어가 스택 계약이 어긋난다.
  `$66F8`은 `JMP`(복귀주소 없음), `$66E5`는 `JSR`(복귀주소 있음)이라 둘의
  스택이 다르다.
- **`PHP/SEI` … `PLP`**로 bank 1 구간 전체를 감싸고, 종료를 bank 0의 기존
  `PLA/PLP/RTS`로 보내 A와 호출자의 I 플래그를 모두 복원한다.

## 4. 정적 검증 — 6280 시뮬레이터

에뮬레이터 없이 두 경로를 실제로 실행해 확인했다. 이 검증이 `0.4.6.7`의
스택 결함과 `0.4.6.8`의 무동작을 모두 재현한다. `$5E40`은 2-1의 실제 동작
(접수처 분기에서 포인터를 `$5B90`으로 덮어씀)까지 모델링해야 한다.

```text
경로1  $66E5 (ptr=$3499)  -> $66E8 복귀, A=99 보존, X/Y/I 보존, SP 균형
                             $66E5 -> 20 40 5E,  $66F8 -> 4C D4 FF
경로3  $66F8 (문자열 끝)   -> 호출자 복귀(JMP $683F/RTS와 동일), SP 균형
                             VRAM 512 B 기준 이미지 대비 불일치 0
                             두 훅 원복,  MPR7 전환 2회 모두 I=True
대조   0.4.6.8 동일 입력   -> $66F8 = 4C 3F 68 (arm 실패) = 실측 로그와 일치
```

스크립트는 세션 임시 폴더에 있었고 산출물이 아니라 일회성이다. 다시 필요하면
위 조건대로 재작성하면 된다. `$683F`는 `60`(단독 RTS)이라 `JMP $683F`는
사실상 RTS이며, 그래서 repair가 `PLA/PLP/RTS`로 끝나는 것이 등가다.

## 6. 남은 미해결 사항

- **VDC 레지스터 선택 상태를 복원하지 않는다.** 복구가 MAWR/VWR을 남긴 채
  빠져나온다. HuC6270은 선택된 레지스터를 읽어올 수 없어 저장이 불가능하다.
  현재 화면에서는 문제가 관측되지 않았지만, 접수처 이후 다른 장면에서 VDC
  관련 이상이 생기면 여기부터 볼 것.
- **`0.3.32`의 확인 범위는 접수처 액션 메뉴 한 장면**이다. 다른 장면에서
  `$66E5` 훅이 상시 동작하므로(문자마다 bank 1 진입 + SEI), 장시간 플레이에서
  타이밍 민감한 연출이 있으면 그때 확인이 필요하다.
