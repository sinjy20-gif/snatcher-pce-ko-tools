## 1. 0.1.x 가 무엇을 틀렸나 — 실측

`runtime_text_audit.lua:235` 의 `resolveAfterControl` 은 3단으로 판정한다.

```
디코더가 0D:32/33 을 썼다   -> BR    관측
디코더가 0D:36/37 을 썼다   -> PAGE  관측
18칸을 다 채웠다            -> CONT  추측
그 외 전부                  -> END   추측 (기본값)
```

보관 로그 4개 4,957행:

```
END  · SHORT_BUFFER (추측)    3,491
CONT · FULL_18_CELLS (추측)     736
END  · UI_BUFFER                702
BR   · DECODER_WRITE (관측)      23
PAGE · DECODER_WRITE (관측)       5
```

**관측 28건, 나머지 99.3% 가 칸 수로 찍은 값이다.**  코드 주석도 `END is the right
guess` 라고 인정하고 있다.

### 두 방향으로 틀린다

**못 끊는다** — 문단의 마지막 줄이 마침 18칸을 채우면 CONT 로 판정되어, 다음에 오는
캡처(= 다음 대사의 화자명)를 같은 블록으로 삼킨다.

```
ギリアン | <원문 17자>。      <- 18칸으로 끝남
ミカ     | <원문 11자>。<원문 5자>。      <- 18칸으로 끝남
```

보관 로그에서 129 블록(고유 69종).  PROBE 0.6.7 표본에서는 11/130 (8.5%).

**헛끊는다** — 엔진이 18칸을 안 채우고 절에서 끊으면 둘 다 END 가 되어 한 문단이
남남이 된다.  이쪽이 더 많고, 18칸 검사로는 **보이지도 않는다.**

```
rec 1   ＪＵＮＫＥＲ本部です。      11칸 END
        <원문 9자>？        11칸 END      <- 같은 접수처의 한 문단
```

측정 (PROBE 0.6.7, 90 레코드):

```
0.1.x 가 만들었을 블록   215
실제 레코드               90      2.4 배로 부수고 있었다
쪼개졌을 문단        26 / 90      28.9%
```

보관 로그에 화자명 규칙을 적용해도 같은 배율이 나온다 (3,495 블록 -> 1,540 레코드,
2.3배).  서로 다른 두 방법이 같은 답을 냈다.

**인계서 §1 의 진단(`？` 한 글자에 번역이 6종인 것 등)이 맞았고, 원인이 하나 더
있었다.**  조각이 순서를 잃은 것만이 아니라 **애초에 한 문단이 여러 조각으로
등록돼 있었다.**

## 5. 레이아웃 제약 — 소유자 확인 사실

```
18칸        엔진이 정한 규칙.  표시 줄마다 걸린다
고유 15자   AC 레코드마다 걸린다.  줄이 몇 개든 합쳐서 15
3줄까지     한 레코드 안에서 엔터(FD)로 표시 줄을 만들 수 있다
{EMPTY}     뒤 문장을 없애고 첫 줄을 연장
```

15의 출처:

```
AC 레코드 704 B = 텍스트 96 B + 글리프 슬롯 19개 × 32 B
  슬롯 0~2   상수 (마침표 · 공백 · 말줄임표)
  슬롯 3~17  우리 몫 = 15
  슬롯 18    헬퍼 글리프
704 는 원본 게임의 레코드 크기라 못 늘린다
```

**줄을 늘려도 예산은 안 늘어난다.**  그래서 3줄은 이론상 존재할 뿐이고, 2줄도
간당간당하다.  실사용 실측:

```
ko_text 에 줄바꿈이 든 행   15 / 7,204   (0.2%)
```

즉 **슬롯 개수는 사실상 일본어 원문이 정한다.**  엔터는 비상구다.  2줄을 전제로
설계하면 0.2% 를 위해 99.8% 를 비트는 꼴이 된다.

### 예산 현황

```
행 단위 고유 한글   평균 8.2 · 13자 이상 454행(6.3%) · 15자 도달 11 · 초과 3
```

대부분 여유가 있고 6% 가 벽에 붙어 산다.  고통은 전부 그 6% 에서 나온다.

### "슬롯 몇 개 더 짜내기" 는 답이 아니다

```
헬퍼 슬롯 1개 회수   +1   1칸
텍스트 96B 여유      +?   실사용 44/80B 로 절반이 논다.  다만 헬퍼가 글리프를
                          고정 오프셋으로 읽어서 레이아웃을 바꾸면 헬퍼 재작성
```

판을 바꾸는 것은 **자모 조합**뿐이다.  이미 건드려 본 길이다:

## 6. 새 마스터 설계

`tools\build_runtime_master.py`.  기존 마스터는 읽기만 한다.

### 행은 AC 레코드다, 문단이 아니다

문단을 한 행으로 합치면 아틀라스 예산을 넘는다:

```
행 단위 고유 한글    최대 19 · 평균 8.2 · 16자 이상 3행
문단으로 합치면      최대 48 · 평균 12.5 · 16자 이상 1,368문단 (30.4%)
```

**30.4% 가 빌더에서 터진다.**  그래서 행은 그대로 두고 `record_id` 로 묶기만 한다.

이 결정의 부수 효과: **스튜디오의 검사 로직은 아무것도 안 바뀐다.**  15자 검사는
행마다, 18칸 검사는 행 안의 표시 줄마다 — 지금과 동일.  바뀌는 것은 그리드에 묶음과
문맥이 보이는 것뿐이다.  (줄바꿈 안전 검사는 없애면 안 된다.  사람이 칸을 셀 수
없어서 붙여둔 경고다.)

### 번역 이관

```
1. 줄 단위 일치      옛 마스터에 같은 원문 행 -> 그 번역 그대로
2. 문단 단위 일치    한 줄짜리 레코드에서만.  ko_para 열에 담아 사람이 나눠 담는다
3. 못 찾음           빈칸
```

문단 단위 일치가 정확하다는 근거 — 검토 O 2,445행:

```
2회 이상 나오는 원문 375종 -> 번역이 갈리는 것 4종   98.9% 일치
```

`{EMPTY}` 만 다른 것은 충돌로 세지 않는다 (행 분할의 흔적).  갈리는 것 중 하나는
겹말 오타였다 (`지켜온 지켜온`) — 검사기가 못 잡는 종류.
목록: `dump\review_O_conflicts_2026-08-15.tsv`

### 검토 O 승계 규칙 (§7-3 답)

기존 마스터의 검토 열은 **13번, 헤더에 이름이 없다.**  `DictReader` 로 읽으면 키가
`''` 이다.  값은 `O` 2,445 + `예외처리` 19 = 2,464 (인계서 숫자와 일치).
**검사기가 못 보는 열에 승인 표시가 들어 있는 상태다.**  새 파일에서는 `reviewed`.

```
줄 단위로 그 행이 O 였다                -> 승계
한 문단 안에 있었고 문단 전체가 O 였다   -> 승계
여러 조각에 걸친 것을 합쳤다             -> 번역만 얹고 O 는 뗀다
```

마스터에 `け？` 같은 꼬리 조각에 찍힌 O 가 실제로 있다.  조각 검토가 합친 문장의
보증이 될 수 없다.  문단 안 O 분포 실측: 전부 아님 64.5% · 전부 O 33.7% · 섞임 1.8%.

## 7. 팩 — 장소 팩 + UI 합류

소유자 실증(본부 → 폐공장 → 깁슨집)이 데이터에 그대로 있다.  **판별 기준은
재사용률이 아니라 구간 수와 섹터 수다** (재사용률은 전부 48~64% 로 안 갈린다).

```
pack   고유행   구간   섹터   압축     성격
6D      310     45     27   38.8K   공용
74      321     34     23   40.1K   공용
75      369      9      7   46.1K   중간
76      247      3      5   30.9K   장소
72      181      5      4   22.6K   장소
77      107      3      4   13.4K   장소
6E/71/70  40    16      6    4.9K   장소
합    1,575                196.9K
```

MPR6 기준 9팩은 0.3.6 docstring 의 예측(9~11)과 일치한다.  **28팩 천장 문제가 사라져
`coalesce 3→6` 임시방편을 버릴 수 있다.**

### UI 는 장소 귀속이다 — 74%

```
1개 팩에만  125/169  74.0%
2개 팩       34
3개 팩        8
4개 팩        2      見る · 持物 뿐
```

`ＪＵＮＫＥＲの事`/`ミカの事` 같은 화제 항목이 장소마다 다르다.

현재 팩 예산:

```
ui              954레코드  120.0 KB  15청크   <- 부팅 부담의 34%
shared          332         42.0 KB   5청크
나머지 25팩                152.0 KB
합                         350.0 KB
```

배분 규칙: **1개 팩에만 나오면 그 장소 팩, 2개 이상이면 공용.**  복제하지 않는다.

예상: 부팅 120 KB -> 30 KB 대, 장소당 ~11 KB 수요적재(어차피 그 장소 대사와 같이

## 8-J. ROUTE_FAIL 이 같은 문단 안에서 중복을 만들었다

`대사 편입` 이 중복 60 건을 만들어 놓고 있었다.  실례:

```
R00069 L2   ている。  ->  속속 들어오고 있군.
R00069 L3   ている。  ->  속속 들어오고 있군.     <- 같은 문단에 같은 것이 또
```

원인은 의도된 예외였다:

```csharp
if (item.Classification != "ROUTE_FAIL" && FindStaticExactRows(...).Count > 0)
    continue;                      // ROUTE_FAIL 은 중복 검사를 건너뛴다
```

*"ROUTE_FAIL 은 행이 있지만 다른 state 에 속하므로 복제해야 한다"* -- trie state 시절의
논리다.  state 는 지금도 살아 있다 (0.3.9 실측 354 종, 비루트 355 레코드).  문제는
마스터가 레코드 기준으로 바뀐 뒤 **같은 문단 안에서** 복제가 일어난다는 것.

고친 방식: 복제의 목적은 다른 루트가 **다른 번역**을 갖는 것이다.  번역까지 같으면
복제는 아무 것도 구분해 주지 않으므로 ROUTE_FAIL 도 건너뛴다.

병합 후: 중복 60 -> 1, `RUNTIME_` 잔재 16행 -> 0.

```
디스크       track24 덧붙이기            여유 있다
헬퍼 코드    814 B 중 809 B              여유 5 B    <- 벽
```

### 뱅크 탐색 — 여러 번 했고, 결론은 "아직 없음" 이다 (소진 아님)

소유자 표현: *"지겹도록 찾아봤는데 결론은 없음"*.  다만 **어디까지 봤는지는 소유자도
기억하지 못한다.**  남아 있는 자료는 이것뿐이다:

```
dump\bank_usage_215946.tsv    frame  600  (10초)
dump\bank_usage_220001.tsv    frame 7200  (2분)
cold_wram_*                   없음 -- CENSUS_COLD_REGIONS 는 실행 안 됐거나 안 남았다
```

`bank_usage_220001` 이 남긴 것 (2분 · 한 장면):

```
never-seen 11개   $60 $61 $62 $63 $64 $65 $66 $67 · $78 $79 $7A
표본이 3~10회     $74(3) $7B(3) $77(7) $76(8) $75(10)
```

**이것을 "빈 공간" 으로 읽지 말 것.**

```
2분·한 장면에서 안 보였다 ≠ 죽었다
$60-$67 은 매핑이 안 된 게 아니라 하드웨어가 없는 주소일 수 있다
```

소유자 규칙이 그대로 걸린다 -- *$FF 는 빈 공간이 아니다.  런타임에 죽어 있는지
확인하고 넣어라.*

**다시 할 가치는 있다.**  당시 관측은 2분이었고 지금은 전체 플레이 수집 워크플로가
있다.  `CENSUS_BANK_USAGE_0.1.1.lua` 를 수집과 같이 돌리면 훨씬 넓은 창으로 다시
잴 수 있다.  그 다음이 "쓰기가 되는가 · 실행이 되는가" 확인이다.

### 남은 방향 — 코드 페이징 가설 (미검증)

빈 공간을 찾는 대신 **같은 공간을 돌려 쓰는** 쪽으로 문제를 바꾼다.  근거는 문서
뷰어와 대사 렌더러가 **동시에 돌지 않는다**는 것이다.  헬퍼는 이미 `TAM` 으로 MPR6 에
Card RAM 을 갈아끼우고 있으므로 코드 페이지도 같은 수법이 가능할 수 있다.

```
선결 확인   실행 중 자기 페이지 교체가 되는가
            여유 MPR 슬롯이 있는가
            전환 코드 자체가 몇 바이트인가 (5 B 로는 당연히 안 된다)
위험        전환이 렌더링 중간에 걸리면 0.3.4~0.3.5 의 깜빡임 문제가 재발
```

되돌려 회수하는 길(0.3.5 의 52 B, 0.3.9 의 12 B)도 있지만 이미 산 성능을 파는 것이라
마지막 수단이다.

## 8-O. 반각 라틴 — 미관 과제 (예산 아님)

소유자 정정: 반각을 원하는 이유는 글자 수가 아니라 **보기에 이상해서**다.  한국어
문장 안의 `ＪＵＮＫＥＲ` 는 자간이 벌어져 거슬린다.

어제의 "반각은 없다"(NOTES)는 **대사 렌더러가 18칸으로 계산한다**는 증거였지, 이
하드웨어에 반각 폰트가 없다는 뜻이 아니었다.  문서 뷰어가 반각을 쓰는 것이 그 구분을
드러냈다.

```
단서 1   분수공백 헬퍼가 반칸 전진을 이미 해낸다.  공백에만 구현돼 있을 뿐 (NOTES)
단서 2   문서 뷰어 = 이 하드웨어에서 반각을 실제로 그리는 코드
유리한 점 라틴·숫자는 원본 폰트라 **우리 아틀라스를 안 쓴다**.  15자 예산과 무관
약한 근거 "16x16 한 글자에 $E060 두 번" 은 절반씩이 아니다 -- 추적된 두 호출의
          문자 코드가 $7097 / $81A1 로 서로 다른 글자다
```

참고 실측 (칸이 글리프보다 훨씬 빡빡하다 -- 8-K 의 인상과 반대):

```
칸 17~18칸    378행 (24.3%)   평균 13.3 / 18
고유 14~15자   50행 ( 3.2%)   평균  8.7 / 15
라틴·숫자 든 행 189 (12.2%) · 그 행의 라틴 평균 5.6자
```

**번역 뒤에 할 것.**  렌더러가 바뀌면 같은 텍스트가 그냥 예쁘게 나오므로 기존 번역
재작업이 없다.

## 8-P. ⚠ 배포 대상은 안드로이드다 — Lua 는 대안이 아니다 (2026-08-18)

소유자 확인: **안드로이드 에뮬레이터에서 돌릴 것이다.**  Mesen Lua 오버레이는 데스크톱
전용이므로 **대안이 되지 못한다.  전부 디스크 안에서 끝나야 한다.**

이 제약이 이전 판단 여러 개를 무효로 만든다:

```
취소   "음성 자막은 Lua 로 이미 되니 위험 0"      -> 게임 안에 그려야 한다
취소   "최악에도 Mesen 으로는 보인다"             -> 최악은 정말 최악이다
취소   "만들어둔 데이터가 버려지는 경우는 없다"    -> 버려질 수 있다
```

현재 안전한 것과 막힌 것:

```
안전   대사 번역          디스크 안에서 이미 작동
안전   암호 팔레트 교체    데이터만 바꾼다 (§8-Q)
막힘   컴퓨터 화면 · 사전   게임 안 렌더링 필요
막힘   음성 자막           게임 안 렌더링 + 렌더러를 없는 데서 새로
막힘   반각 라틴           게임 안 렌더링
```

**음성 자막 데이터를 미리 만들지 말 것.**  넣을 방법이 확정되기 전에는 위험하다.
NOTES 초기의 "voice-only 대사는 자막 시스템을 처음부터 만들어야 해서 범위 밖" 이 지금도
유효하다.

## 8-Q. 암호 입력 화면 — 거의 데이터 교체다

가나 팔레트 격자(`<원문 5자>` … `<원문 5자>`, 5자 × 9줄 = 45칸)로 답을 입력하는 화면.
소유자 제안: **조합형(초·중·종성 조립) 대신 완성형** -- 필요한 한글 음절을 팔레트에
깔고 저장된 정답도 같은 코드로 바꾼다.  비교 로직은 코드열 비교이므로 안 건드린다.

**팔레트는 이미 마스터에 행으로 있다** (`ui_text.tsv`, 전부 검토 O):

```
<원문 5자> [O] 아이우에오      <원문 5자> [O] 카키쿠케코   ...
<원문 5자> [O] 라리루레로
```

지금은 음역만 되어 있어 **입력용으로는 쓸모가 없다** -- 그 격자로는 원문 정답 코드를
만들 수 없다.  `ko_text` 를 필요한 음절로 바꾸면 그대로 격자에 나온다.

남은 것:

```
저장된 정답의 위치     미발견.  대사의 힌트 문장과는 별개일 것
45칸 안에 들어가나     게임 전체 암호 정답의 **필요 음절 합집합**이 기준
```

주변 대사는 이미 번역되어 있다 (`革命は？` -> `혁명은?` 등).

## 8-R. 문서 뷰어 — **같은 렌더러다.  풀렸다** (2026-08-18 확정)

★ 분기점이었다.  **싼 쪽으로 갈렸다.**

`$6000-$7FFF` 전수 역어셈블 결과 `$3471`(렌더러 포인터)에 새 값을 넣는 곳은 `$63AC`
하나뿐이었고, 수집기는 `$3619`/`$349A` 만 보고 있었다.  그래서 *"문서 뷰어가 같은
경로에 다른 버퍼를 쓰면 우리 손으로 버린 것"* 이라는 가설을 세웠다.

`PROBE 0.6.8` 로 주소 필터 없이 `$3471` 을 전수 기록한 결과:

```
$3471 이 가진 값        53 종
렌더 사이클             $3610 -> $3612 -> ... -> $3619 -> $5B90 -> INSTALL($63AC)
$3610 + 9 = $3619       앞 9 바이트는 제어 프리픽스.  본문은 +9 부터
$5B90                   번역문이 놓이는 출력 버퍼.  SRT4 가 여기로 포인터를 돌린다
```

즉 판정 기준의 **"다른 값이 나온다"** 쪽이다 -> 같은 렌더러 -> **새 코드 0 바이트.**

### 중간에 틀렸던 것 — 기록해 둔다

프로브 로그에서 `$3619` 가 187 회 중 184 회 비어 있는 것을 보고 *"수집기가
184/187 을 놓치고 있다"* 로 읽어 수집기를 `$3610` 에서도 잡도록 고쳤다 (0.2.1).
**그 해석이 틀렸다.**  프로브는 렌더 도중 포인터가 지나가는 모든 순간을 기록하고,
그중 버퍼가 잠깐 비는 순간이 184 회였다.  수집기는 `#source == 0` 이면 그냥 넘어가므로
애초에 잡을 것이 없던 호출이다.

같은 구간을 0.2.1 로 다시 돌려 대조한 결과:

```
0.2.0 이 잡았을 고유 원문  35
0.2.1 이 추가로 본 자리    35
베이스에서만 잡힌 것        0
옛 자리에서만 잡힌 것       0
```

**수집기는 고장나 있지 않았다.**  0.2.1 은 캡처 이득이 없다 (§8-V 참조 -- 그래도
남긴 이유가 있다).

## 8-T. 글자깨짐 A/B 판 준비됨

소유자 정정: **장소 문제가 아니다.**  폐공장이 유독 심할 뿐 본부에서도 난다.  그리고
완전히 없어지지도 않는다.

`SNATCHER_BLANK_SLOTS=0` 이 0.3.4 동작(매 레코드 608 B 템플릿 통째 복사)을 정확히
재현한다는 것을 확인했다 -- 헬퍼 크기가 713 B · 여유 69 B 로 0.3.4 와 일치한다.

```
build\patch\EXPERIMENT\0.3.9-noblank-unpatched\
  Snatcher CD-ROMantic (Japan) [KO 0.3.9-noblank].cue
```

폐공장을 돌아 판정한다:

```
깨짐이 사라진다   -> 0.3.5 의 조건부 지우기가 원인.  확정
그대로 깨진다     -> 가설 기각
```

**배포용이 아니다.**  깜빡임이 0.3.4 수준으로 돌아간다 (그것이 0.3.5 가 산 것이다).

가설: 상수 슬롯에는 센티널이 있어 다음 레코드에서 복구되지만 **글리프 슬롯 15칸에는
검사가 없어** 오염이 그 칸을 쓰는 레코드가 올 때까지 남는다.  "완전히 없어지지 않는다"
와 맞물린다.  부하 높은 곳에서 심한 것도 "헬퍼가 CPU 를 오래 잡는다"는 공통 원인
가설과 어긋나지 않는다 -- **다만 픽셀 밀림과 글자깨짐이 한 원인이라는 것은 미검증.**

## 8-U. 가우디 사전 — POC 통과.  치환은 그냥 된다 (2026-08-18)

```

문단 줄 수     고정          3 줄 문단은 3 줄, 4 줄 문단은 4 줄.  늘릴 수 없다
줄 나누기      자유          일본어가 `<원문 5자>`/`ザード` 로 자른 자리에 맞출 필요 없다

```

**즉 사전에서는 15 자 예산(§5) 이 절대 걸리지 않는다.**  대사(18 칸)만 걸릴 수 있다.

### 문단 경계는 바이트로 찍혀 나온다

9 바이트 제어 프리픽스의 마지막 바이트가 화면 행 번호이고, 문단이 바뀌면 `00` 으로
리셋된다.  한 항목(`▽` 로 시작)이 통째로 한 레코드다 (`record_seq` 하나).

```
FC 01 F9 01 FE 06 FB 03 00   ▽１９９１年６月６<원문 5자>
FC 01 F9 01 FE 06 FB 03 01   <원문 14자>
FC 01 F9 01 FE 06 FB 03 02   <원문 8자>。
FC 01 F9 01 FE 06 FB 03 00   当時、<원문 11자>     <- 리셋 = 새 문단
```

그리고 **사전과 대사가 프리픽스로 갈린다**:

```
사전   FE 06 · FB 03
대사   FE 01 · FB 01
```

§8-E 가 "메뉴와 본문이 안 갈린다" 고 했던 문제가 이것으로 풀린다.

## 8-Y. 인명 검색 -- 목록이 아니라 **글자 입력**이다 (2026-08-18)

가우디의 `<원문 6자>` 는 목록에서 고르는 것이 아니라 **가나 자판으로 이름을 친다.**
게임 안내문 그대로:

```
<원문 18자>…
　<원문 11자>
　<원문 11자>『<원문 6자>』
　<원문 6자>『スズキ』
　<원문 13자>
　　<원문 11자>。
```

**접두 매칭이다.**  한 글자씩 칠 때마다 가장 가까운 항목이 갱신되는 것이 로그에 그대로
찍혔다:

```
キ -> ギ -> ギフ -> ギプ -> ギプス -> ギプスン
ギフ -> ギブ -> ギブス -> ギブスン   ->   <원문 13자>
```

`ギブ` 두 글자로 `ギブス` 를 찾아낸다.  **그러므로 글자 수가 달라도 된다** -- 한국어
`깁슨`(2자)이 `ギブスン`(4자) 자리를 대신해도 매칭 자체는 문제가 없다.

### 이것은 장식이 아니라 필수 기능이다

퀴즈가 이 검색에 의존한다 (소유자 증언): 깁슨의 나이, 카트린느의 3 사이즈, `テンカ` 등.
사전 본문만 번역하고 검색을 두면 **게임 진행이 막히는 자리가 생긴다.**

### 이름 표 -- 찾았다.  트랙 02

```
위치      약 0x111380 ~ 0x111900   (rom(japan)/... (Track 02).bin)
형식      FF 종단 · 가변 길이 · <원문 5자> 순 정렬
```

**고정폭이 아니다.**  짧은 한국어 이름이 긴 가나 이름 자리에 들어가도 남는 칸을 채울
필요가 없다.

등록된 이름 (실측):

```
<원문 7자>      <원문 7자>       <원문 7자>      <원문 7자>
<원문 9자>   <원문 11자>  <원문 9자>    <원문 7자>
<원문 7자>      <원문 9자>    <원문 9자>    <원문 10자>
<원문 5자>         <원문 8자>      <원문 7자>      <원문 7자>
<원문 6자>       <원문 5자>          <원문 8자>
```

개발자 이름도 20 여 명 들어 있다 (`<원문 6자>` `<원문 7자>` `<원문 7자>`
`<원문 7자>` 등).  이스터에그다.

**별칭이 있다**: `<원문 11자>` 과 `<원문 11자>` 이 **둘 다** 등록돼
있다 (ス/ソ 혼동 대비).  한국어에서도 같은 방식으로 오타 별칭을 넣을 수 있다.

### 자판 -- 화면 실측 48 칸.  그리고 **배경 타일이지 렌더러 텍스트가 아니다**

처음에 인명 표 안의 14 줄(`<원문 5자>` `<원문 5자>` `<원문 5자>` …)을 자판으로 읽고
`14 x 5 = 70 칸` 으로 계산했다.  **틀렸다.**  그것들은 정렬 인덱스의 행 머리글이다
(이름이 탁점까지 포함해 정렬되므로 `<원문 5자>` 줄도 있는 것).

화면 실측 (소유자 캡처, 2026-08-18):

```
1 행   <원문 5자>  <원문 5자>  <원문 5자>  <원문 5자>      20
2 행   <원문 5자>  <원문 5자>  <원문 5자>  <원문 5자>      20
3 행   <원문 5자>   ー  ﾞ  ﾟ   決定                    5 + 3
                                              ─────
                                              45 가나 + 기호 3 = 48 칸
```

탁점 줄은 자판에 없다.  `ﾞ`/`ﾟ` 키로 앞 글자를 변형한다 -- 즉 **두 입력을 한 글자로
합치는 기계장치가 이미 있다.**  한글 조합에 그대로 쓰기는 어렵지만(초x중x종이 수천),
"조합 코드가 존재한다" 는 것은 확인됐다.  나중에 볼 것.

**자판은 텍스트 렌더러를 타지 않는다.**  배경 타일로 직접 찍는다.  `0x99FD0` 부근에
타일맵으로 보이는 RLE 데이터가 있고 타일 번호가 `0x93`~`0xC8` 로 연속한다.

이것이 §8-N 의 *"반각 가타카나도 0 건 -- 전체 로그 통틀어 한 글자도 없다"* 를 설명한다.
**렌더러를 안 지나가니 수집기가 잡을 수가 없었다.**  글자가 없어서가 아니다.

### 타이핑이 필요한 것은 정답 3 개뿐이다 (데이터 검증 완료)

처음에는 선택지 표 55 개를 전부 타이핑 대상으로 잡아 97/70 초과가 나왔다.  **아니었다.**
실제로 답을 쳐 넣는 자리는 셋뿐이다:

```
<원문 5자>   보나파르트    나폴레옹 2 차 · 본명.  인명 표에 있다 (0x113D59)
クイーン     퀸          퀸 병원 비밀번호.  별도 표 (0x1C9FE2)
```

온라인 공략 문서는 퀸 병원 답을 "`クイン` 혹은 `クイニ` 계열의 변칙 입력" 이라고
애매하게 썼는데, **데이터에는 `クイン` 이 없다.**  `クイーン` 이 정답이고 대신 근접
오답이 따로 등록돼 있다: `オウリン` `オリン` `オリイン` `オリーナ` `オリーヌ` `オリーノ`
`クレーン` `<원문 6자>`.  **문서보다 디스크를 믿을 것.**

`テンカ`(天下) / `デンカ`(殿下) 는 한 글자 차이 말장난이다.  `ui_text.tsv` 가 한쪽은
음차(`텐카`) 한쪽은 의역(`전하`)이라 짝이 깨져 있던 것을 **`천하` / `전하` 로 통일했다**
(소유자 지정).  힌트가 `백일천하` 이므로 답도 의역이 맞다.

나머지 선택지 어휘(`カクメイ` `センソウ` `シラン` `ハズレ` 등)는 **화면에서 고르는 것**이라
자판 예산과 무관하다.  이미 `ui_text.tsv` 에 번역돼 있다.

## 8-AA. ⚠ 병합이 하루치 검토를 덮어썼다 (2026-08-18)

### 원인 -- 번역을 **원문 문자열 하나당 하나**로 들고 있었다

```
R00512:2  す。   내것 "타이머 같은 소리가…"    -> 덮임 "주입해 두었습니다."

번역 32 행 · 검토 O 23 행
```

## 8-AB. 부팅 음악 끊김 — 원본엔 없던 자리다 (2026-08-24)

§8-H 를 이어서 정정한다.  §4(`SNATCHER_HANDOFF_2026-08-22.md`)의 "CD 로딩 중 음악
끊김 | 원래 동작... 버그 아님" 이라는 문구를 소유자에게 그대로 옮겼다가 정정받았다.

**틀렸던 부분**: "하드웨어 특성" 과 "그 특성이 이 지점에서 발현된 것" 을 하나로
묶었다.  "CD 를 읽으면 CD-DA 가 선다" 는 맞는 하드웨어 제약이지만, **원본이 접수처
대사 직전에 CD 를 읽는다는 뜻은 아니다.**

같은 문서의 실측이 오히려 소유자 기억을 뒷받침한다:

```
원본   20회 읽고 58.3초에 끝.  그 뒤로 더 안 읽는다   (§4, PROBE_BOOT_LOAD)
```

20회가 오프닝 중에 끝난다는 뜻이므로, **원본은 접수처 대사가 뜨는 순간엔 이미
읽기가 다 끝나 있어 조용히 넘어간다.**  우리 쪽은 훅이 `$66E5`(대사창이 처음
살아나는 순간, §8-P·00_PIPELINE_0.3.0.md L191)에서 걸리는데, 그 시점에 상주 팩
3 개(현재 약 1.0 MB)를 그제서야 처음 읽기 시작한다.  원본이 필요 없던 읽기를
하필 그 순간에 새로 만든 것 — 끊김의 자리는 패치가 만들었다.

```
"CD 읽으면 음악이 선다"     하드웨어 특성.  맞음 · 버그 아님
"접수처 직전에 끊긴다"      패치가 만든 자리.  원본엔 없었음
```

원인(하드웨어 제약)과 자리(우리 훅 위치)를 같은 문장에서 섞지 말 것 — 다음에
또 이 실수를 반복하기 쉽다.

### 곁가지: 그림 밀림 — 오버클럭 ~10x 로 사라진다 (소유자 관측, 미확인)

같은 대화에서 나온 별개 증상이다.  소유자가 MesenCE 오버클럭을 약 10 배 주니
사라진다고 보고했다.

**증상 (소유자 설명, 2026-08-24)**: 스프라이트가 떠야 할 시점에 못 뜬다.  그래서
그림이 한 번에 안 맞춰지고 약간 늦게, 순차적으로 구성되는 것처럼 보인다 — SATB
갱신이 그 프레임의 VBlank 창을 못 맞추고 한두 프레임 밀리는 모양과 일치한다.

**탐침으로 확인한 것은 아니고 소유자 관측만 있다.**  다만 정황은 세 갈래로 겹친다:

```
CPU 예산이 빠듯함        오늘 다른 발견들과 같은 결 (헬퍼 여유 151 B · 엔진 704 B)
레코드 재구성 비용        §8-AB 위 항목 (2026-08-14 분석).  "재구성 비용 x 화면 항목 수"
                        가 프레임 예산을 먹는다는 게 이미 실측돼 있다 -- 그 비용이
                        스프라이트 푸시와 같은 프레임에서 경합하면 정확히 이 증상이 난다
오버클럭에 반응함         CD 배속(패스트포워드)이 아니라 CPU 클럭에 반응한다는 것은
                        CD 전송이 아니라 **CPU 사이클 문제**라는 뜻과 맞는다
                        (§8-AB 위쪽의 부팅 음악 끊김은 반대로 배속에 반응했다 -- 서로
                        다른 다이얼이라는 게 이 대조로 한 번 더 확인된다)
```

가설: 대사창·메뉴의 레코드 재구성이 그 프레임의 스프라이트 푸시(자막 엔진의
`$6463` 푸시 루프도 여기 얹힌다 -- `SNATCHER_SUBTITLE_LIVE_2026-08-23.md`) 와
사이클을 다투다가 밀려나는 것으로 보인다.  **아직 확인 안 됐다.**  어느 프레임
어느 루틴이 못 끝내는지는 안 잡았고, 다음에 확인할 방법:

```
1  오버클럭만 켜고 패스트포워드는 끈 채로 재현되는지 (CPU 쪽인지 가른다)
2  PROBE_FRAME_COST_0.1.0.lua 로 그림 밀림이 나는 프레임의 스캔라인 소비를 잰다
3  그 프레임에 레코드 재구성이 같이 도는지 대조한다
```

자막 엔진이 게임 SATB 에 얹혀 도는 구조라 (스텁이 게임 푸시 루프를 빌려 쓴다),
자막을 붙이는 작업에서 다시 걸릴 가능성이 있다.  여기 남겨 둔다.

## 8-AC. 부팅 로딩 재조사 (2026-08-24) — 실측 · pack 분할 재검토 · 우선순위 결정

§8-AB 를 이어서 같은 대화에서 계속됐다.  이론 계산(바이트/34KB/s)을 실측으로
검증하고, "pack 으로 나눠보자"를 재검토하다가 **오늘은 안 하기로** 결정했다.

### 실측 — PROBE_BOOT_LOAD_0.1.0 (2026-08-24)

```
첫 대사까지 2171 프레임 (36.2초) · CD 읽기 11회 253섹터 (506 KB)
```

이론 계산(§8-AB, 바이트/34KB/s 로 약 30초)보다 실제가 더 길다 — 프로브 자신의
설명대로 디렉터리 64 KB + 시크 비용이 계산에서 빠져 있었다.  **8배속 체감 4초는
버그가 아니라 36.2초를 8로 나눈 것과 정확히 일치한다** (36.2/8=4.5).  패스트포워드는
프레임 수를 안 바꾼다 (PCE 내부 60fps 클럭은 그대로다) — 그래서 프로브는 배속과
무관하게 같은 프레임 수를 낸다.

**진짜 플레이어는 패스트포워드를 안 쓴다.**  36초 검은 화면 + 무음은 실제 문제다.
다만 원본과 같은 정지-후-끝 패턴이라 §8-AB 의 판정("버그 아님, 대가")은 그대로다.

첫 대사 이후에도 CD 읽기가 계속 늘어나는 것이 로그에 잡혔다 (11 → 27 → 65 → 103 →
142회).  `$F123` 훅이 우리 팩 로딩과 게임 자신의 CD-DA 재생 읽기를 구분 못 해서
같이 잡혔을 가능성이 있다 — **확인 안 됨.**  다음에 이 수치를 다시 볼 때는 CD-DA
재생 여부와 겹쳐서 봐야 한다.

### pack 분할 재검토 — "교체" 대신 "누적"이면 스왑 버그가 안 생긴다

§8-H/8 의 결론(전부 상주)은 **"교체(swap)" 방식을 시도했다가 실패한 결과**였다.
소유자가 다른 설계를 제안했다: 장소를 **처음** 방문할 때만 그 pack 을 추가하고,
**한 번 올리면 절대 안 내린다.**  이러면:

```
스왑 방식(예전 시도)   장소 바뀔 때마다 교체.  타이밍 잘못되면 깨진다 -> 실패해서 되돌림
누적 방식(오늘 제안)   처음 볼 때만 추가.  안 내리니 스왑 자체가 없다
```

한 가지 확인된 한계: **총 이동량은 안 줄어든다.**  다 방문하면 결국 지금과 같은
1.03 MB 를 전부 싣게 된다.  다만 "한 번의 큰 고통(36초)" 이 "여러 번의 작은
고통(장소 전환마다 몇 초)" 으로 흩어진다 — 첫 방문 pack(짐작 · 미확인)만 실으면
되므로 **첫 화면은 훨씬 짧아진다.**
