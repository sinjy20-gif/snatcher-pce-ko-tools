## 1. ★ 다중 조각 정지 — 원인 확정

### 1-1. §8-A 측정이 기존 가설을 반증했다

`0.4.40-callflow.lua` 로 미카 3조각 음성(`ADPCM_00309D_D000_0E`)을 재며
`$601E · $7FA0 · engine+3/+17/+118 · $FEC4 · $E742 · $E74A` 실행 횟수를
프레임마다 셌다.  덤프: `dump/callflow_0_4_40_20260828_223204.tsv`

```
             쓰기 프레임        다음 프레임
성공  90f    ready=00 start=90   REBUILD=1 COUNTOK=1  ready→01
성공 120f    ready=00 start=120  REBUILD=1 COUNTOK=1  ready→01
정지 180f    ready=00 start=180  REBUILD=0 COUNTOK=0  E742=859 pc=$E746
```

**정지 프레임(vf 602)에도 HOOK=1 · ENTRY=1 이 정확히 왔다.**  즉 호출 기회는
사라지지 않았다.  엔진에 들어갔는데 rebuild 분기(+17)를 안 탔고, 그 프레임의
12% 지점에서 CPU 가 BIOS 루프로 떨어져 459프레임 동안 안 돌아왔다.

결정적 단서: 정지 후 endFrame PC 표본이 주기적으로 `engine+535..545` 에 찍혔다.
`stage` 는 offset 503 이다 — **CPU 가 엔진의 데이터 버퍼를 실행하고 있었다.**

### 1-2. 원인 — `entry` 가 `stage` 를 코드로 부른다

`engine_ac_lua_frame_mini.bin` 실측 바이트:

```
+3   AD D7 5C   LDA $5CD7      ; ready
+6   D0 06      BNE +6         ; ready != 0 -> +14 (JMP push)
+8   20 77 5D   JSR $5D77      ; ready == 0 -> stage 를 코드로 호출
+11  4C 91 5B   JMP $5B91      ; rebuild
```

`$5D77` = stage 에는 31 B 팔레트 초기화 루틴이 `$5D95` 의 RTS 로 끝나게 깔려 있다.
그런데 **같은 stage 가 글리프 전송 버퍼다** (`build_subtitle_engine_ac_record_poc.py`):

```python
a.emit(0xF3); a.word(AC_PORT); a.word("stage"); a.word(GLYPH_BYTES)   # AC -> stage
a.emit(0xE3); a.word("stage"); a.word(VDC_VWR); ...                   # stage -> VDC
```

첫 rebuild 가 그 루틴을 글리프 비트맵으로 덮는다.  빌더 주석이 전제를 밝혀 놨다:

> 자체 전환은 entry 가 아니라 rebuild 로 직접 가므로 두 번 부르지 않는다.

**그런데 Lua 프레임 타이머는 조각 전환마다 `ready=0` 을 쓴다**
(`0.4.31.lua` 의 endFrame).  그래서 매 전환이 entry 를 거치고 매번 글리프 픽셀을
코드로 JSR 한다.

```
조각 1   stage = 진짜 팔레트 루틴        -> RTS 복귀 · rebuild ✓
조각 2   stage = 조각1 의 글리프 비트맵  -> 우연히 복귀 · rebuild ✓
조각 3   stage = 조각2 의 글리프 비트맵  -> 복귀 실패 · 폭주 ✗
```

정지 후 PC 가 찍힌 `$5D97~$5DA1` 은 사라진 RTS 바로 다음이다.

**부수 발견:** "잘 되던" 1→2 전환도 매번 글리프 픽셀을 JSR 하고 **운으로 복귀**하던
것이었다.  3번째에서 터진 게 아니라 3번째에서 운이 다한 것이다.

### 1-3. 고침과 검증

`entry` 에 exec 콜백을 걸어 `ready==0` 이면 **JSR 이 일어나기 전에** stage 31 B 를
원본 이미지에서 되살린다.  매직 `SUB` 와 JSR 피연산자 `20 77 5D` 를 둘 다 확인한
뒤에만 쓴다 (음성 사이에는 게임 코드가 `$5B80` 에 있다).

검증 (미카 3조각):

```
조각1        base $1600   SATB $1600 $1640 … $1A40   (18개)
 90f 재무장#2 base $1A80   SATB $1A80 $1AC0 … $1E00   (15개)
180f 재무장#3 base $2BC0   SATB $2BC0 $2C00 … $3000   (18개)
             restore $2BC0 (voice end)
INTRUDER 0건 · 정지 없음 · KEY#1(2조각) KEY#2(1조각) 도 정상
```

**엔진 재빌드도 디스크 빌드도 없었다.**  제대로 된 고침은 `entry` 가 `stage` 를
아예 안 부르게 하는 것(빌더에 별도 init 플래그)이고, 그건 엔진 재빌드가 필요하다.

## 2. ★ 팩과 엔진의 세대 불일치 — 오늘 세 번 물렸다

`build_subtitle_engine_ac_lua_frame_mini.py` 는 팩 헤더의 오프셋을 **엔진
바이너리에 상수로 박아** 빌드한다:

```python
glyph_off,  = struct.unpack_from("<I", blob, 10)
record_off, = struct.unpack_from("<I", blob, 26)
args = dict(glyph_base=AC_PACK + glyph_off, record_base=AC_PACK + record_off, ...)
```

팩만 다시 빌드하고 엔진을 안 뽑으면 엔진이 엉뚱한 자리를 읽는다.  **레코드 첫
바이트가 글리프 개수(count)** 라서, 그게 쓰레기가 되면 push 루프가 19개가 아니라
최대 255개 스프라이트를 SATB 에 밀어 **화면 전체가 무너진다.**

실측 (팩 180,818 → 183,255 B 로 바뀌었을 때):

```
off  72 ($5BC8)  87 → 8C     record_base 하위   $1C7A87 → $1C7C8C   (517 B 어긋남)
off  80 ($5BD0)  7A → 7C     record_base 중위
off 202 ($5C4A)  DA → 4F     glyph_base  하위
off 209 ($5C51)  EC → F4     glyph_base  중위
     region: index_compare 2 · glyph_loop 2
```

증상은 SATB 가 `$FCA0 $F480 $F800 $FF40 …` 처럼 완전히 흩어지고 INTRUDER 가
쏟아지는 것이다.  **자막 로직 문제로 오해하기 딱 좋다.**

### 2-1. 검사가 왜 못 잡았나

`0.4.31.lua` 의 `ensureInstalled()` 는 이렇게만 본다:

```lua
packV6   = AC[PACK+4]==6 and AC[PACK+5]==0        -- 버전 바이트뿐.  옛 팩도 통과
engineOk = 오프셋 {0,1,2,50,630} 비교              -- 바뀌는 자리 {72,80,202,209} 를
                                                  --   하나도 안 덮는다
```

그래서 **파일은 새것인데 AC RAM 엔 옛것**인 상태가 조용히 만들어진다.  엔진을
새로 뽑아도 반영이 안 되니, 수정이 실패한 것처럼 보인다.

### 2-2. 넣은 가드 (`0.4.45.lua`)

```
가드 1   팩 파일 ↔ 엔진 파일   오프셋 72/80/202/209 대조.  불일치면 error 로 즉시 중단
가드 2   AC RAM 의 팩          헤더 8필드 대조.  다르면 팩 전체를 다시 올린다
가드 3   AC RAM 의 엔진        조건 없이 다시 올린다
덤       SUB_VOICE_ENGINE_BYTES 를 631 로 박지 않고 파일에서 잰다
```

⚠ 오프셋 `72/80/202/209` 는 팩만 바꿔 두 엔진을 diff 해서 **실측으로** 잡은
값이다.  엔진 코드 구조를 바꾸면 이 자리가 밀리므로 같이 갱신해야 한다.
(실패는 죽는 쪽이라 조용히 틀리지는 않는다.)

## 3. allocator — 이미 "쓰지 말라"고 적혀 있었다

`SNATCHER_ALLOCATOR_CDDA_2026-08-28.md` §8 제목이 이것이다:

> **★ 0.3.42-wide 실측 — 위험하다. 그대로 쓰지 말 것**
> §8-1 유력한 원인 — 복원(restore)이 장면 전환을 덮는다
> §8-4 `0.3.42-wide` 는 시험용으로만 두고, B·C 를 넣기 전에는 쓰지 않는다

§8-3 의 처방과 현재 상태:

```
A  정주행하며 참조된 word 지도       "비싸고 느리다" 로 비권장 -> ★ 결국 이걸 했다 (§4)
```

§8-2 의 경고도 유효하다 — 프레임별 SATB 덤프 + flush + 64슬롯 침범 감시가
FPS 를 떨어뜨린다.  실측으로 FPS 15 를 봤다.  **진단 로그부터 줄일 것.**

넣은 것들이다.

## 4. ★★ 방향 전환 — allocator 를 버리고 키별 고정 base 로

### 4-1. 왜 allocator 로는 안 되는가

`SNATCHER_ALLOCATOR_CDDA_2026-08-28.md` §3-2 에 이미 결론이 있다:

```
INTRUDER 슬롯 16·18~21  $6000~$647F  팔레트 C   ← 초상화 스프라이트 5개
```

> allocator 가 고를 때는 비어 있었고, 그 뒤에 게임이 가져갔다.
> **allocator 는 미래를 모른다.**

`blank()`(전부 0인 블록 고르기)가 폐기된 것도 같은 이유다.  "전부 0" 이든
"지금 미참조" 든 **둘 다 현재 시점의 성질**이라 미래를 보장하지 못한다.

### 4-2. `VRAM-key-map.lua` 측정 (진행 중)

읽기 전용 probe 로 **음성별로** 그 음성이 나는 동안 게임이 건드린 VRAM 을 누적해
자유 구간을 뽑는다.  자막 Lua 를 전부 빼고 돌려야 한다 (우리 글리프가 "사용 중"
으로 찍히면 오염된다).

```
dump/vram_key_map_20260829_130855.tsv     키별 자유 base 목록
dump/vram_key_spans_20260829_130855.tsv   키별 점유/자유 구간 원자료
```

⚠ `map` 파일의 `bases` 열은 키당 24개로 잘려 있다.  교집합 계산은 반드시
**spans 파일**로 할 것.  (잘린 열로 계산하면 "공통 base 0개" 라는 허수가 나온다.)

### 4-3. 31키 시점 결과 — 잠정

```
자유 base 0개인 키       0개          ★ 모든 키가 자리를 갖는다
키별 1216 이상 구간      4~5개씩
```

**키별 고정 배치는 성립한다.**  반면 전역 단일 고정은 키가 늘수록 죽는다:

```
24키 시점   $1600..$1FFF   2560 word   ★
31키 시점   $1600..$17FF    512 word      ← 1216 미달로 탈락
            $1F80..$1FFF    128 word
            $4AD0..$4FFF   1328 word   ★  ← 유일한 생존자, 여유 112 word
            $1110..$13FF 752 · $53C0 64 · $5F80 128 · $6F00 256
            교집합 합계 3168 word
```

`$1600` 이 7키 더 재는 사이에 탈락했다.  남은 `$4AE0` 도 여유가 112 word 뿐이라
장면이 더 쌓이면 같이 죽을 가능성이 크다.

**판단: 전역 하나로 박는 것은 포기. 키별로 박는다.**

### 4-4. 이 전환이 없애는 것

```
choose()                미래를 모르는 추측이 사라진다
snapshot / restore      되돌릴 일이 없으니 §8-1 위험이 통째로 사라진다
침범 경쟁 (B 안)         고를 때 이미 "이 음성 동안 안 쓰인다"가 보장된다
defer / GRACE / 지문     복원이 없으니 전부 불필요
프레임별 64슬롯 스캔     FPS 문제도 같이 사라진다
```

어젯밤 싸운 버그 대부분이 **메커니즘 자체가 없어져서** 사라진다.

### 4-5. 남은 위험

측정은 **한 번의 진행 경로**에서 그 음성이 날 때 벌어진 일만 기록한다.  다른
순서·다른 선택으로 들어가면 게임 상태가 다를 수 있다.  최소한 이 둘이 필요하다:

```
여유 정책      고른 base 주변에 마진을 두거나, 후보 2순위를 같이 박는다
검증 통과      박은 뒤 전수 진행하며 침범 감시로 0 건인지 확인
```

## 4-6. ★★ 진짜 벽 — 표시 중인 VRAM 에 쓰고 있다 (미해결)

키별 고정 base 를 실제로 박아 돌린 결과, **자리 배치는 답이 아니었다.**

### 4-6-1. 측정으로 하나씩 지운 것

```
0.4.65-verify   배치 13번 전부 · 업로드 후 90프레임 동안 블록 1 word 도 안 변함
                침범 0 · 미업로드 0
                -> 게임이 우리 VRAM 을 가져가지 않는다.  자리 다툼이 아니다

0.4.66-slots    빈 슬롯 31~34 개 (19 필요) · 슬롯 부족 아님
                스캔라인 16 초과는 **정상 사례에도** 뜬다 -> 무관

0.4.67-blank    블록 1216 word 를 비워도 그대로.  오히려 쓰기만 늘었다

0.4.68-satb     자막 줄 스프라이트 전부 정상:
                  팔레트 전부 F · 크기 1x1 · 주소 $3B80 $3BC0 … 0x40 간격 완벽
                  조각 전환에 13개 -> 10개로 여분도 깨끗이 사라짐
                  블록 밖을 가리키는 스프라이트 0개
```

프레임 경계에서 잰 것은 **전부 정상**인데 화면은 깨진다.

### 4-6-2. 소유자 관측이 답을 줬다

> "글자가 새로 써지는 시점에 저게 살짝 나왔다가 바로 사라짐"

찢어짐(tearing)이다.  VDC 는 스캔라인마다 스프라이트 패턴을 읽어가며 화면을
그리는데, 그 도중에 같은 자리를 덮으면 그 프레임만 옛 데이터와 새 데이터가
섞여 보이고 다음 프레임엔 멀쩡해진다.

모든 관측이 이것으로 맞아떨어진다:

```
VRAM·SATB·팔레트 전부 정상    프레임 끝에는 쓰기가 이미 끝나 있으니까
속도를 늦춰야 보인다           프레임 안에서 스치는 현상이니까
블록 비우기가 무효             살아있는 블록에 2,432 B 를 더 쓴 것일 뿐
슬롯·스캔라인 무관             처음부터 상관없는 지표였다
```

### 4-6-3. allocator 로 돌아가도 안 된다 — 오히려 나빴다

`0.4.45`(allocator + defer)로 되돌리자 **더 심해졌다.**  앞서 멀쩡하던 대사까지
깨졌고, 잔상이 게임의 **UI 선택 상자** 모양이었다.

```
고정 base    화면에 떠 있는 블록에 새 글리프를 쓴다          -> 쓰는 동안 찢어짐
allocator    거기에 옛 스냅샷 복원 쓰기까지 더한다            -> 쓰기 2배, 더 심함
             고른 자리에 원래 UI 상자 패턴이 있었고
             복원이 그걸 되살려 자막 줄에 그렸다 (뷰어로 확인)
```

즉 **자리를 어디로 옮기든, 복원을 하든 말든** 쓰는 시점이 화면 그리는 중이면
찢어진다.  allocator 가 조각마다 자리를 바꾸던 것이 이 문제를 *부분적으로*
가려주고 있었을 뿐이다.

### 4-6-3b. ★★★ 국장실 -- 화면 떨림 + 천장의 국장.  **출하불가급.  여기부터 볼 것**

자막이 좀 깨지는 것과 급이 다르다.  **게임 화면 자체가 망가진다.**

```
증상   화면이 덜덜 떨린다
       타일맵 위쪽이 소환된다 (원래 아래만 보여야 하는데 천장의 인물이 나온다)
       자막을 쓰는 순간에만
```

⚠ 이 증상은 **아직 안 잡혔다.**  프로브 0.2 수정 뒤 사라졌다고 적었던 것은
스크린샷 하나를 보고 단정한 오판이다.  0.4.6.14 + 0.4.64 에서도 재현된다.

**유력한 원인 -- 엔진이 인터럽트를 막지 않고 VDC 를 건드린다.**

실측: `engine_ac_lua_frame_mini.bin` 631 B 전체에 **SEI 0 개 · CLI 0 개.**
빌더(`build_subtitle_engine_ac_record_poc.py` · `build_subtitle_engine.py`)에도
PHP/SEI/CLI/PLP 가 하나도 없다.

PC엔진 VDC 는 레지스터 선택 래치가 **하나**다.  접근이 두 단계다:

```
1  포트에 "몇 번 레지스터" 를 쓴다      <- 여기서 IRQ 가 끼면
2  데이터를 쓴다                        <- 데이터가 엉뚱한 레지스터로 들어간다
```

스내처는 그림 창을 만들려고 **래스터 분할 IRQ** 를 쓴다 -- 화면을 그리는 도중
인터럽트가 걸려 스크롤 레지스터를 바꾼다.  우리 엔진이 1과 2 사이에서 그 IRQ 를
맞으면 우리 데이터가 **세로 스크롤 레지스터로 들어간다.**

모든 관측이 맞아떨어진다:

```
떨림                 스크롤 값이 매 프레임 튄다
타일맵 위쪽 소환      표시 창이 위로 밀린다
자막 쓸 때만          우리가 VDC 를 건드리는 순간에만
프레임 끝 측정 정상    게임이 다음 프레임에 스크롤을 되돌려 놓으니까
0.4.45 가 더 나빴다   복원 쓰기까지 더해져 VDC 접근이 2배
```

블록 전송(TIA/TAI)은 HuC6280 에서 중간에 안 끊기므로 안전하다.  위험한 것은
**그 앞의 주소 설정**이다 -- allocator 가 고치던 `off 144/146` 자리가 거기다.

**★ 이 가설은 실측으로 반증됐다 (`lua/SUB/0.4.69-vdc.lua`).**

## 5. CD-DA 현황

### 5-1. "CDDA 키 0개" 는 절반만 맞다

```
ADPCM 색인   1,950항목   rate 전부 $0E        ← 이 부분은 맞음
CD-DA 색인     698항목   stride 10 B          ← 팩에 엄연히 있다
             LBA 0 .. 211,539
```

ADPCM **키 테이블 안에** CD-DA 가 없다는 뜻이지, CD-DA 자막이 없다는 뜻이 아니다.
CD-DA 는 키가 아니라 **LBA 구간**으로 찾는 별도 색인이다.

"CD-DA 는 자리를 안 찾아도 된다" 는 결론 자체는 지금은 맞다.  다만 이유가 다르다 —
**런타임에 CD-DA 를 그리는 코드가 아직 없다** (`0.4.31.lua` 에 `cdda` 언급 0건).
`lua/SUB/CDDA_DRIFT_0_1_0.lua` 도 `emu.write` 가 0개인 순수 측정 스크립트다.

### 5-2. 조각난 이유

```
cdda_segments.tsv (408 클립)   c01_001  track01  LBA   0.. 396  (5.29초)
팩 CD-DA 색인                            LBA   0.. 132
                                         LBA 132.. 264
                                         LBA 264.. 396   ← 클립 하나를 셋으로 균등분할
```

실제 발화 타이밍이 아니라 **클립 길이를 자막 줄 수로 나눈 것**이라 싱크가 안 맞는다.
구간 길이 중앙값 174섹터(2.3초).

### 5-3. 재생 단위 추출 — 가능하다

진짜 재생 단위는 **게임이 CD 에 거는 재생 명령의 start/end LBA** 다.  런타임에
가로채면 나온다.  디스크는 24트랙(02번만 MODE1 데이터, 나머지 AUDIO)이고,
Mesen 이 `cdrom.audioPlayer.currentSector` 를 노출한다 (CDDA_DRIFT 가 이미 쓴다).

⚠ 첫 본부 대사는 **ADPCM** 이다 (미카 = `ADPCM_00309D_D000_0E`).  CD-DA 는
오프닝·컷신 쪽이다 (`c01_001` 의 whisper 가 기리안/메탈 차 안 대화).  CD-DA 재생
명령을 잡으려면 컷신 구간에서 재야 한다.

## 6. MINI_COUNT 초과 — 미해결

`0.4.31.lua:160` 의 `assert(#parts <= MINI_COUNT)` 는 하드 assert 다.
MINI_COUNT=5 인데 넘는 키가 3개 있다:

```
FFFF0E188A0E   11조각
FFFF0E088D80    7조각
FFFF0EBD5188    7조각
```

`FFFF` 는 플레이스홀더가 아니라 **ADPCM RAM 을 거의 다 쓰는 긴 음성의 실제 end
주소**다 (`read_addr $003D + length $FFC2 = $FFFF`).  긴 음성일수록 조각이 많고
긴 음성일수록 end 가 FFFF 가 되므로, 저 셋은 실제로 터진다.

후보:

```
(a) Lua 가 현재 조각 주변 5개 창을 밀어준다      엔진 변경 0.  가장 싸 보인다
(b) MINI_COUNT 를 11 로                         엔진 재빌드.  여유 631/672 B = 41 B
(c) 자막을 5조각 이하로 합침                     18셀 제한 때문에 아마 불가능
```

(다른 세션이 `SUB_RUNTIME_MINI_COUNT=11` 로 실험 중 — `0.4.50` · `0.4.52`)

## ★ 미해결이다.  아래 조사는 "어디가 아닌지"만 밝혔다.

기준 빌드의 베이스 갱신 누락(§8 파일 절)을 고쳐 `0.4.6.14-reviewed` 를 만들었고
Track 02 해시도 바뀌었다.  **그런데 증상은 그대로다** -- 소유자 확인:
가우디에서 0.4.6.14 로 찍은 화면에 여전히 원문이 섞여 나온다.

그러므로 아래의 "적용 단계에서 빠졌다" 는 **틀린 결론이다.**  뒤에 이어지는
검증(§ 이 절 끝)에서 33행이 전부 빌드에 들어간 것이 확인됐다.

확인한 것 — **수집·번역·검토 문제가 아니다.**

⚠ 열 이름 함정 먼저.  마스터의 **14번째 열은 이름이 없다.**  그것이 스튜디오의
검토 열이다 (`build_runtime_master.py:658` 의 `"": reviewed or ""`).
`byte_check` 는 검토 여부가 아니라 `apply_translations` 가 쓰는 길이 계산 결과다.
둘을 혼동하면 "미검증 42%" 같은 허수가 나온다 (실제로 한 번 그렇게 잘못 쟀다).

```
검토 열 = 'O'    15,604 / 15,786 = 98.8%      ← 검토는 거의 끝나 있다
```

해당 문서 화면 13행 (`R10435` · `R10436`) 의 현재 상태:

```
검토        O            ← 사람이 확인 끝냄
status      draft
byte_check  비어 있음     ← apply_translations 를 통과한 적 없음
ko_text     전부 채워져 있음
pack        76
```

`tools/apply_translations.py:163` 이 번역을 적용할 때 레이아웃 열을 **함께** 쓴다:

```python
("ko_bytes", byte_len), ("byte_check", "OK")
```

즉 `byte_check` 가 비어 있다 = 그 행은 적용된 적이 없다 = 게임 데이터에 안 들어갔다.
그래서 화면에 원문이 남는다.

**유력한 원인 — 검토 열과 `status` 가 따로 논다:**

```
검토 O      15,604 행
status=review  278 행        ← 검토가 끝나도 status 는 draft/ai_draft/todo 로 남는다
```

빌더나 apply 가 `status` 를 기준으로 거른다면, **검토가 끝난 행도 status 가
안 올라가서 통째로 누락된다.**  이 13행이 정확히 그 경우다.

다음 확인:

```
1  apply_translations / 디스크 빌더가 status 로 거르는지 확인
   거른다면 -- 검토 O 를 status 에 반영하는 단계가 빠진 것이다
2  검토 O 인데 byte_check 가 빈 행이 몇 개인지 세기 (누락 규모)
3  적용 커버리지를 빌드 산출물에 숫자로 남길 것 -- 지금은 조용히 빠진다
```
