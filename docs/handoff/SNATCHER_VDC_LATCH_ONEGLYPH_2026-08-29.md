## 1. ★ 두 증상이 갈렸다

`0.4.87`(한 글자 엔진)로 국장실을 지나며 사용자가 육안 판정했다.

| 증상 | 한 글자에서 | 뜻 |
|---|---|---|
| 화면 떨림 | **확실히 줄었다** | 전송량 / 래스터 IRQ 지연 |
| 타일맵 위쪽(천장의 인물)이 중간중간 짧게 보임 | **그대로** | 전송량이 원인이 아니다 |

이 분리가 오늘의 핵심이다.  어제까지는 두 증상을 한 덩어리로 보고 있었다.

### 1-1. 왜 떨림만 줄었나

글리프 루프는 조각마다 19번 돈다.  매 회 `TAI` 64 B + `TIA` 128 B 다.
HuC6280 의 블록 전송은 **중단 불가**라 그동안 래스터 IRQ 가 통째로 밀린다.
`0.4.70` 실측으로 한 조각 업로드가 34~67 스캔라인을 점유했고, 대부분
`start_line 19~25 → end_line 47~81` 즉 **활성 표시 구간 한복판**이었다.

한 글자면 이 연쇄가 1/19 이 된다.  떨림이 준 것이 그 증거다.

### 1-2. 왜 위 그림은 안 줄었나 -- 한 글자가 줄이지 못하는 유일한 구간

엔진 631 B 를 정적으로 뜯으면 구조가 이렇다.

```
+$08B  A2 00        LDX #$00
+$08D  03 00        ST0 #$00      ; 레지스터 선택 = MAWR
+$08F  13 00        ST1 #$00
+$091  23 16        ST2 #$16      ; MAWR = $1600
+$093  03 02        ST0 #$02      ; 선택 = VWR      ← 루프 "밖", 딱 한 번
+$095  glyph_loop:
       ...  주소 계산 80 B  ...                     ← 조각마다 그대로 남는 구간
+$0DC  F3  TAI $1A00 -> $5D77  len $0040
+$0E3  E3  TIA $5D77 -> $0002  len $0080
       ...
+$11E  4C 15 5C     JMP glyph_loop                  ; 재선택 없음
```

소스에서도 같다 --
[build_subtitle_engine_ac_record_poc.py](../../tools/build_subtitle_engine_ac_record_poc.py)
의 `set_vram_write()` 호출이 `a.label("glyph_loop")` **바로 위**에 있다.

- 엔진 전체에 **SEI 0개 · CLI 0개** (바이트 `$78`/`$58` 각 0개, 실측).
- PC엔진 VDC 의 레지스터 선택 래치는 **하나**이고 되읽을 수 없다.
- 즉 `ST0 #$02` 부터 첫 `TIA` 까지 **80 바이트** 동안 래치가 `$02` 로
  유지된다고 가정하고 있다.  그 사이 래스터 분할 IRQ 가 VDC 를 한 번만
  건드리면, 남은 글리프 데이터가 그 레지스터로 들어간다.  BYR($08)이면
  세로 스크롤이 튀고 -- **타일맵 위쪽이 화면으로 끌려나온다.**

**한 글자 패치(`record.cells` → 1)는 루프 반복만 1회로 줄인다.
셋업 구간은 조각마다 한 번씩 똑같이 실행되므로 전혀 줄지 않는다.**
증상도 전혀 줄지 않았다.  일치한다.

"중간중간 짧게" 라는 것도 맞다.  이 창은 0.5 스캔라인 남짓이라 상시가 아니라
**가끔 걸리는 경합**이다.

> 이 가설 자체는 새것이 아니다.  [0.4.69-vdc.lua](../../lua/SUB/0.4.69-vdc.lua)
> 머리말이 증상까지 똑같이 적어 두었다.  다만 그 프로브는 **한 줄도 못 찍었다**
> (§5-1).  오늘 갈린 것은 가설이 아니라 판정이다.

## 2. ★ `0.4.87` 이 두 번 실패한 진짜 이유

### 2-1. 표본 검사가 하필 판정 바이트를 안 봤다

[0.4.31.lua](../../lua/SUB/0.4.31.lua) 의 `ensureInstalled()` 는 AC 의 엔진이
최신인지 표본 몇 바이트로 봤다.

```lua
for _, offset in ipairs({0, 1, 2, 50, #engine - 1}) do   -- 0,1,2,50,630
```

한 글자 엔진과 원본의 **유일한 차이는 +$6D(109)** 다 (`AD 38 5D` → `A9 01 EA`).
표본 다섯 개 어디에도 109 가 없다.  그래서:

1. 스크립트 로드 때 `FORCE` 로 한 번 올린다 → `AC install #1` → 그 자리에서
   `FORCE = false`
2. 이후 음성 gate 마다 `ensureInstalled()` 가 돌지만 표본이 전부 일치 →
   `engineOk = true` → **조용히 return**
3. `install #2` 가 영영 안 찍히고 디스크 원본이 계속 `$5B80` 으로 복사된다

19:03 인계서가 "AC 에 남은 원본을 재사용했다"까지는 맞게 봤지만, 처방(FORCE
1회)이 2·3 단계를 못 막았다.  **그래서 두 번 다 실패했다.**

### 2-2. ★ `$1F1F00` 은 디스크 상주 렌더러 슬롯이다

무엇이 원본을 되돌려 놓는지는 `0.4.88` 지문이 찍었다.

```
frame    1   AC $1F1F6D = A9 01 EA   (우리 이미지)
frame 2560   AC $1F1F6D = FF FF FF  →  1C 8D 04     ★ 여기서 날아감
frame 5990   AC $1F1F6D = 1C 8D 04   (그대로)
첫 음성      AC install #2  →  AC = A9 01 EA · CPU $5BED = A9 01 EA
```

`$1F1F00` 은 디스크 빌드의 **상주 렌더러 자리**다.

```
build_subtitle_native_poll_bios_0_8_4.py:29
    PACK_AT, HELPER_AT, RENDERER_AT = 0x1C0000, 0x1F1C00, 0x1F1F00

0.4.6.15-reviewed / bios_preload.json
    subtitle_helper    -> 2038784 = $1F1C00
    subtitle_renderer  -> 2039552 = $1F1F00
```

헬퍼가 이 슬롯에서 `$5B80` 으로 복사하므로 `0.4.31` 이 여기를 덮는 것은
**의도된 설계**다.  문제는 장면 전환 때 디스크 선적재가 자기 렌더러로
되돌린다는 것이다.  따라서 **음성마다 다시 덮어야 한다.**

### 2-3. 고친 것

[0.4.31.lua](../../lua/SUB/0.4.31.lua) 두 군데.

```
engineOk      표본 5개  ->  631 B 전량 비교 (첫 불일치에서 중단)
업로드        팩+엔진 통째  ->  실제로 어긋난 쪽만
              (엔진만 어긋나도 팩 184 KB 를 다시 올리면 음성당 18만 번의
               emu.write 가 되어 실행이 눈에 띄게 느려진다.
               로그의 바이트 수가 이번에 쓴 양이다.  0 = 건너뜀)
```

### 2-4. 성립한 실행

```
AC install #2 … #16          음성마다 재적재.  되돌림을 매번 잡는다
CPU $5BED = A9 01 EA         KEY 마다 한 글자 엔진이 실제로 돈다
WIPE 33건 전부 1칸           직전 실행은 14/18/16칸
```

19:03 인계서의 성립 조건 ①②③ 을 모두 만족한다.

> 부수 관측: 음성 사이에 `CPU $5BED` 가 `1A A9 1F` / `00 00 00` 으로 변한다.
> `$5B80` 은 스크립트 VM 데이터 스택이라 음성 중에만 빌리는 자리이므로 정상이다.

## 4. 다음 -- `0.4.89` 별도 체인

### 4-1. 넣을 것

`TIA` 직전으로 재무장을 옮기고 그 짧은 구간만 감싼다.

```
PHP / SEI
ST0 #$00 · MAWR = 이번 글리프 주소 (lo,hi 를 $0002/$0003 에)
ST0 #$02 · VWR
TIA stage -> $0002, $0080        ; 어차피 중단 불가
PLP
```

- `TIA` 는 이미 원자적이라 **추가되는 IRQ 지연은 앞의 ST/LDA/STA 몇 개뿐**이다.
  즉 §1-1 의 떨림을 악화시키지 않고 §1-2 의 경합만 없앤다.
- `SEI`/`CLI` 가 아니라 `PHP`/`PLP` 로 감싼다.  엔진이 IRQ 문맥에서 불릴
  가능성을 배제하지 못했으므로 인터럽트 플래그를 보존해야 한다.
- 루프 밖 `set_vram_write`(8 B)는 뺀다.  재무장이 매 회 하므로 불필요하다.
- 글리프 주소는 **새 ZP 를 쓰지 않고** 기존 글리프 인덱스 `$16` 에서 만든다.
  `PAT_VRAM` 이 256워드 정렬($1600)이라 성립한다.

```
lo = ($16 & 3) << 6
hi = (PAT_VRAM >> 8) + ($16 >> 2)
```

### 4-2. 크기와 오프셋 (빌드로 확인 완료)

```
in-loop 추가 30 B · set_vram_write 제거 -8 B  ->  순증 +22 B
631 B -> 653 B      한도 672 B (SAFE_BYTES = $5E20 - $5B80)
```

무엇이 밀리는지가 중요하다.

| 라벨 | 631 B | 653 B | 비고 |
|---|---:|---:|---|
| entry | 3 | 3 | 안 밀림 |
| count_ok | 118 | 118 | **안 밀림** → 0.4.82 marker 그대로 쓸 수 있다 |
| glyph_loop | 149 | 141 | set_vram_write 제거분 |
| ready | 343 | 365 | 밀림 |
| selector / list | 345 | 367 | 밀림 |
| index / record | 440 | 462 | 밀림 |
| stage | 503 | 525 | 밀림 → CPU `$5D77` → `$5D8D` |

빌드 결과가 이 표와 일치했다.  `653 B / 한도 672 B · 순증 +22 B · stage 루틴 31 B`.
검증한 것:

- 재무장 블록 16개 명령이 설계와 바이트 단위로 일치.  `ST0 #$02`(+$0F6) 바로
  다음이 `TIA`(+$0F8) -- **노출 창 80 B → 0 B**
- `+525` 의 stage 루틴 31 B 가 원본 `+503` 의 것과 **바이트 동일**
- 엔진 머리의 `JSR` 가 `20 8D 5D`($5D8D)로 따라 옮겨졌다
- 공유 빌더를 고쳤지만 `vdc_rearm=False` 는 무해하다 --
  `engine_ac_lua_frame_mini.bin` 을 다시 구워 sha256 이 그대로였다
  (`11b1d330…4ee1c9`)

### 4-3. 그래서 왜 "별도 체인" 인가

지금 도는 체인이 오프셋을 하드코딩한다.

```
0.4.57   SUB_VOICE_ENGINE_BYTES = 631 · SELECTOR = 345 · READY_OFFSET = 343
0.4.58   STAGE = 0x5D77 · engine:find('\x60', 504)
```

여기를 고치면 **지금 유일하게 잘 도는 경로를 잃는다.**  그래서 `0.4.57/0.4.58`
은 손대지 않고, 빌더가 오프셋을 같이 내보내고 새 체인이 그것을 읽는다.
(JSON 파서가 없으므로 `build_vram_key_bases.py` 처럼 `.lua` 파일도 같이 쓴다.)

```

  -> build/cutscene_subs/engine_ac_lua_frame_rearm.lua   (오프셋 표)
```

전부 만들었다.  실행은 Power Cycle 뒤 `0.4.89-vdc-rearm.lua` 하나만 로드한다.
로그에서 `engine 653 B` 와 `STAGE $5D8D` 를 먼저 확인할 것.

### 4-5. ⚠ `0.4.48` 의 지뢰 하나

`forceRenderer` 가 엔진을 **고정 오프셋으로 직접 패치**한다.

```

```

`SUB_FRAGMENT_FORCE_KEY` 와 `SUB_FRAGMENT_FORCE_BASE` 가 **둘 다** 있을 때만
돌기 때문에 0.4.82 · 0.4.89 어느 쪽도 지금은 안 탄다.  다만 재무장 엔진에서
켜면 코드를 조용히 부순다.  `0.4.89-vdc-rearm` 진입점에 assert 로 막아 두었다.
나중에 FORCE 경로가 필요해지면 그 네 오프셋도 표에서 읽게 바꿔야 한다.

그 위에 `cdda_segments.tsv`(408클립 절대 LBA), `cdda_subtitles(_timed).tsv`,
팩 v6 의 `cdda_index` 698항목, 드리프트 상수 1.25364 섹터/프레임까지 다 있고,
[PROBE_SUB_CDDA_0_1_0.lua](../../lua/PROBE_SUB_CDDA_0_1_0.lua) 로 **실제 화면
표시까지 성공**했다.

남은 것은 08-28 인계서 §4-3 의 하나뿐이다 -- **실기에서 시작 LBA 를 어디서
얻나.**  Lua 는 `currentSector` 를 직접 읽어 해결돼 있고, 네이티브 케이브에는
그것이 없다.  재료(`CD_PLAY $E012` · 호출자 `$60E4` · CD_READ ZP 인자블록
`$20F8-$20FF`)는 이미 문서화돼 있고, 없는 것은 **CD_PLAY 호출 순간의 인자를
찍은 로그**다.  `$60E4` 주변 디스어셈으로 정적으로 끝낼 수 있다.
