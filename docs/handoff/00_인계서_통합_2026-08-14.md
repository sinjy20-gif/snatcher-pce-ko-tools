## 2. 0.3.1 — atlas 가 resident 팩을 덮어쓰던 문제

### 원인

`COMMON_DATA_BASE = $16000` 이 atlas 크기를 참조하지 않는 하드코딩 상수였다.
초기 CD→AC 적재는 AC `$00000` 부터 한 덩어리로 흐르고 8 KiB 청크로 올림 패딩되는데,
그 끝과 resident 팩 시작을 비교하는 코드가 없었다.

```python
init_total = align(DIRECTORY_BYTES + STATE_SPAN + TEMPLATE_BYTES + len(atlas), CHUNK_BYTES)
cursor     = align(dynamic.COMMON_DATA_BASE, USER_BYTES)   # $16000, atlas 무관
```

팩은 초기 적재 **다음에** 전송되므로 팩이 atlas 꼬리를 덮는다. init 은 MAGIC 가드라
세션 중 재실행되지 않아 파워사이클 전까지 복구되지 않는다.

절벽은 청크 정렬 때문에 칼같다.

```
glyphs  atlas_end  init_total  speaker $16000
   741     $16000      $16000  OK          ← 마지막 안전
   742     $16020      $18000  8,192 B 파괴 ← 32B가 아니라 청크 통째로
  1089     $18B80      $1A000  16,384 B 파괴
```

실패본의 파괴 대상은 이름까지 특정했다. `index 741 = 썩` 부터 348개, 출처는
dialogue 190 / ui 150 / speaker 8 — UI만의 문제가 아니었다.

### 수정

```python
common_base = max(dynamic.COMMON_DATA_BASE, init_total)
dynamic.COMMON_DATA_BASE = common_base
```

`max()` 인 이유: atlas 가 `$16000` 아래면 기존 베이스를 유지하므로 ac_0.1.14 가
바이트 동일 재현된다. 더해서 초기 적재·resident·scene 바닥의 extent 를 정렬해
겹치면 빌드를 죽이는 감사를 넣었고, 에러에 몇 번 인덱스부터 깨지는지 찍는다.

## 3. 0.3.2 — 메뉴를 다시 열 때마다 CD를 읽던 문제

### 실측

```
scene_111800  $50000  ×7      scene_10F800  $50000  ×5
scene_121800  $50000  ×2      scene_111000  $50000  ×1
서로 다른 팩 4개인데 로드 15회
```

resident 팩은 각각 한 번씩만, 목적지도 manifest 와 일치했다. `shared` 는 무죄다.

### 원인

```python
destination = cursor if resident else scene_base    # scene 팩 전부 $50000
```

scene 팩을 한 슬롯 오버레이로 설계했고 런타임도 "현재 장면팩 ID" 한 칸만 뒀다.
전제는 "한 번에 한 장면"인데 실제로는 **같은 장소에서 메뉴와 대사가 다른 팩에 있어**
핑퐁했다. 그런데 scene 팩 전체가 102 KB, scene 영역이 1.7 MB 라 오버레이가 아무것도
벌어주지 못했다.

### 수정과 결과

scene 팩도 순차 할당하고, 런타임은 팩 종류 구분 없이 모두 `3 + pack_id` 플래그를
쓴다. 초기화도 팩 수만큼 루프로 돈다.

```
scene 팩 21개   목적지 고유 21개   겹침 0건
AC 사용 309,248 B = 2 MB의 14.7%
헬퍼 709 → 664 B   (scene_flag 5 B · mark_scene 11 B · 분기 제거)
```

**검증 완료** — `PROBE_PACK_RELOAD_0.1.2` 로 전 팩 ×1, `loaded again` 0줄,
읽기 49회에서 정지 후 90초간 CD 접근 0.

### 팩 상한

번역이 늘어 팩이 15 → 25개가 되며 빌드가 죽었다.

```
메타데이터 $10080-$100FF 128 B, 팩당 8 B  →  16개가 상한
METADATA_AC_OFFSET  $80 → $20             →  28개  (현재 25, 여유 3)
```

헬퍼가 `CLC; ADC #offset` 으로 한 바이트 오프셋을 쓰므로 표가 256 B 상태페이지
안에 있어야 한다. **28을 넘으면 상수로는 안 되고** 16비트 주소 지정이나 별도
메타데이터 구역이 필요하다. 에러 메시지에 적어뒀다.

## 4. §8-B 저장 후 재로드 화면 깨짐 — 원인 규명 완료

### 재현 조건

```
게임 중 저장 → 타이틀 복귀 → 같은 세션에서 그 슬롯 재로드 → 그래픽/문자 타일 깨짐
재실행 후 로드하면 정상. 세이브 파일 손상은 없다
```

0.3.2 · ac_0.1.14 · 0.2.26 **전부**에서 같은 계열로 발생한다.

### 확정된 기전

원본이 `FF` 로 두었던 자리에 우리가 코드를 넣으면, 재로드 경로에서 **그 바이트가
그래픽 소스로 읽혀 VRAM 에 올라간다.** 코드가 파괴되는 게 아니라 멀쩡한 코드가
타일로 그려진다.

두 사례가 각각 직접 관측됐다.

```
뱅크 $69 케이브   f5771 342 reads $BCD2-$BE27  /  f5772 472 reads $BE28-$BFFF
                  342+472 = 814 = 케이브 크기 정확히.  같은 프레임 VDC write 1,170/1,298
                  원본 track02.iso 의 그 자리는 814 B 전부 FF

$5E20-$5FF1       외부 caller $70BF  read 8,673  VDC write 39,869
프리로더           외부 caller $7064  read   311  VDC write  1,464
                  실제 루프: B1 12 (LDA ($12),Y) / JSR $71B0 / INY / CPY $01 / BNE
```

### 2차 인계서의 오류 (정정)

2차는 "원인은 뱅크 $69 케이브"라고 단정했다. **케이브는 한 사례일 뿐이다.** AC 헬퍼를
그 케이브에 두지 않는 0.2.26 에서도 같은 깨짐이 난다.

따라서 2차 §4·§5 의 "헬퍼를 옮길 자리를 찾자"는 방향도 무의미하다. **옮겨도 안
고쳐진다** — `$5E40-$5FF1` 프리로더는 `$66E5` 훅 대상이라 이동 자체가 불가능한데
그것도 똑같이 읽힌다.

### 기각된 가설 (다시 파지 말 것)

```
AC 오염          magic/flags/atlas 전부 소프트 복귀 후에도 불변
CD 베이스 미복원  우리 로더는 파손 세션 내내 읽기 0회.
                 게임의 $E009 섹터 시퀀스는 원본 실행과 바이트 단위 동일
훅/캐시 손상     훅 항상 20 50 7F / 20 40 5E / 20 20 5E, 캐시 항상 유효 SDR4
                 SAVE 0.1.2 로 6개 고정 영역 byte-exact 확인, CHANGE 0건
트램폴린 MPR5    505프레임 호출에도 프레임 경계 MPR5=$69 가 0건.
                 BIOS 가 전송 중 매핑을 바꾼다. SEI 부재는 무관
```

### 남은 선택지

```
그래픽만 정상 재적재     타이틀→재로드 시 해당 타일을 원본 데이터로 다시 올림
소스에서 패치 구간 마스킹  전송이 읽을 때만 FF 로 보이게. 가장 외과적
코드를 cold region 이동   ← §5 가 닫음. 그런 자리가 없다
특수 경로에서 전체 재초기화 가장 둔하지만 확실
현행 유지                게임 내 세이브 경로에서만 발생. 진행 불가는 아님
```

## 5. 공간 조사 — 결론은 "없다"

목적은 무의미해졌지만(§4) **패치가 쓸 수 있는 공간이 없다는 사실 자체는 유효**하고,
앞으로 코드를 어디에 놓을지의 기준이다.

```
상주 뱅크 FF 구간   bank 68 $1BB3-$1FFF 1,101 B  → 캐시 + 프리로더가 점유
                   bank 69 $1CD2-$1FFF   814 B  → 실패한 케이브
                   bank 6A $1F50-$1FFF   176 B  → 래퍼 + 트램폴린 + 상태
                   셋뿐이고 전부 우리 것

캐시 아래쪽        $5A00-$5B7F 384 B 전수 → cold 0 바이트
뱅크 단위          $68-$87 전부 매핑됨.  $60-$67 은 Super CD RAM 범위 밖
WRAM $2000-$3FFF   폐기됨 (2026-08-10). 미접촉은 스택 페이지뿐
뱅크 $6C           폐기됨 (2026-08-10). BIOS PC $EA9E 가 32페이지 전부에 기록
```

게임이 우리 캐시 안쪽 `$5BB3-$5CB9` 를 상시 덮어쓴다. BODY 는 줄마다 재적재하므로
데이터로는 버티지만 **코드를 놓으면 즉사**한다.

수지 계산상 재배치만으로는 627 B 적자다. 글리프 온디맨드로 회수해도 §4.3 때문에
코드로 쓸 수 있는 건 `$5CBA` 위쪽 358 B 뿐이라 여전히 적자다.

## 6. 번역 데이터 — 상태 라우팅

### 구조

조회 키는 원문 바이트만이 아니라 **`state` 를 포함**한다. 프리로더는 실패 시 루트로
한 번 재시도하고, 그것도 실패하면 `ROUTE_FAIL` 이다.

```asm
scan_record        못 찾음 → PASS_NO 가 0이면 retry_root_state
retry_root_state   부모 상태가 있으면 have_parent_state
have_parent_state  MATCH_LO/HI = 0 (루트) · PASS_NO = 1 · restart_scan
```

**상태별 다중 레코드는 이미 동작한다** — 현재 빌드에 57종이 그렇게 실려 있다.

```
src=82 AB 82 DC 82 B7 81 42
   state=00B6  111800:38DE:2  '가우디를 이용할 수 있어요.'
   state=00FC  119800:2C0E:2  '{EMPTY}'
```

### 남은 문제

마스터는 **일본어 1행 = 한국어 1개**이고 여러 참조가 한 행을 공유한다. 같은 원문이
장면마다 다른 상태로 오면 하나만 담을 수 없다.

```
だぞ。   161800:3D8B:3 · 112000:51C7:3 · 162000:758E:3  세 참조가 한 행
        ko='부족해지면... 바로 신청하게.'  ← 161800 문맥. 국장실엔 못 씀
        그래서 검토 O 를 못 받고 출하에서 빠짐 → 게임에 일본어로 나옴
```

**해법은 참조별로 행을 쪼개는 것**이다. 엔진은 이미 지원하므로 데이터 작업이다.

`master_conflict_exclusions.tsv` 가 이 충돌을 "검토 해제"로 처리해온 기록이고,
짧은 꼬리(4자 이하) 580행 중 225행(39%)만 출하되는 이유다. **그 판단이 과했을
가능성이 크다** — 상태가 다르면 공존 가능하다. 3~4행으로 먼저 시험할 것.

### 카탈로그는 낡으면 못 쓴다

`runtime_text_catalog_20260814_001611.tsv` 의 `MISS/NEAR` 113건을 마스터에 넣으려
했으나 **전부 이미 등록돼 있었다.** 그 카탈로그는 00:16 것이고, 이후 번역·검토가
진행돼 0.3.2 에 이미 실렸다.

```
카탈로그 MISS/NEAR 113건 → 현재 전부 검토 O, 0.3.2 산출물에 있음
```

**작업 전에 반드시 재수집할 것.** `MASTER_ONLY 240` 도 같은 이유로 크게 줄어든다.

⚠ 카탈로그는 **UTF-16** 이다. UTF-8 로 읽으면 조용히 건너뛴다(그래서 한 번
"런타임이 못 잡았다"고 오진했다).

## 7. 반각 띄어쓰기 — 두 안 모두 기각

엔진에 이미 들어 있다. 없는 건 데이터뿐이었다.

```asm
$5E20  분수공백 헬퍼 32 B  ($674A 훅)  F041이면 $3470 토글, 커서는 두 번에 한 번 전진
$64B3  분수 글리프 시프트 49 B          플래그 서면 시프트 +2. 커서는 안 건드림
```

| 안 | 결과 |
|---|---|
| `F041` | **기각.** 공백이 폭을 전혀 못 얻어 글자가 겹침 |
| `$20` | **기각.** 렌더는 정상인데 간격이 전각과 동일 |

코덱 주석의 "not reliable in the live game"이 무엇이었는지 이번에 증상으로 기록됐다.

**다음 후보 (미착수)**: `NOTES.md` 의 "half-width katakana (single-byte SJIS
`$A1-$DF`)". 게임이 단일바이트를 실제로 반각으로 그린다는 뜻이므로, 그 범위에서
게임 텍스트에 안 쓰이는 코드를 찾아 글리프를 비우면 **커서를 건드리지 않는 진짜
반각 공백**이 된다. 두 안이 모두 커서 조작으로 실패했으므로 이쪽이 유력하다.

## 8. 대사 3줄 — 규칙 도출

게임은 3줄 이상을 원래 지원한다(3줄 407 · 4줄 34 · 5줄 26 · 6줄 8). 레코드는 늘릴
수 없지만 한국어 안에 `{BR}`(= `FD`)로 표시상 쪼갤 수 있다.

```
FD 는 동작한다
FD 는 커서를 x=0 으로 되돌린다      게임의 BR 은 대사창 여백까지 맞춘다
FD 뒤에 레코드가 오면 겹친다        게임의 줄 카운터가 FD 를 모른다
→ 인라인 줄바꿈은 마지막 레코드(after_control=END)에서만 안전하다
```

여백 보정본(`무슨{BR} 용무이신가요?`)이 `build\patch\0.3.1-3line3\` 에 있다. **미검증.**

실익은 크다 — `END` 레코드가 4,229개라 모든 대사 뭉치의 마지막 줄을 두 줄로 쪼갤 수
있고, 18칸 제한 때문에 줄여 쓴 문장을 되돌릴 수 있다.

```

python build_snatcher_ko_0_3_2.py --prune --deep  중간물까지
python build_snatcher_ko_0_3_2.py --space F041|20 띄어쓰기 실험
python build_snatcher_ko_0_3_2.py --tag NAME      데이터 실험
```

`--space`/`--tag` 는 산출 폴더와 1·2단계 중간물을 **함께** 분기한다. 중간물을
분기하지 않으면 이후 평범한 `--stage3` 이 실험 바이트를 정식 이름으로 뱉는다.

빌드당 실비용 200 MB(Track 02 + Track 24). 나머지 22트랙은 `rom(japan)` 과 같은
inode. **자동 프루닝은 제거됐다** — 삭제는 `--prune` 을 직접 줄 때만.
`PROTECTED` = 현재 버전 · `ac_0.1.11-source` · `ac_0.1.14` · `0.2.26`.

마스터를 고쳤으면 전체 빌드. 3단계 로직만 고쳤으면 `--stage3`.

## 12. 함정

1. **`FF`·`00` 은 빈 공간의 증거가 아니다.** 실행·읽기·쓰기 셋 다 조용해야 하고,
   실제로 지나간 경로에 한해서만 유효하다. 뱅크 $69 케이브가 이걸로 무너졌다.
2. **디스크 이미지의 뱅크 오프셋 환산은 적재 영역 밖에서 무효다.**
   `bank $68 == user $07B800` 은 부트 로더의 우연이다.
3. **계측 Lua 는 버전을 올린다. 출력 경로도 같이.** 로그는 그것을 만든 코드 없이는
   판독할 수 없다.
4. **TSV 를 줄 단위로 다루지 말 것.** 인용 필드는 개행을 포함한다. `csv` 로 읽고
   쓰고, 손대기 전에 **무변경 왕복이 바이트 동일한지** 확인할 것.
   (08-14 에 이걸 어겨 `ui_text.tsv` 의 note 80,957줄을 날리고 검토 O 를
   976 → 756 으로 떨어뜨렸다. 백업에서 원복함.)
5. **자기 검증을 자기와 같은 방식으로 하지 말 것.** 잘못된 파서로 읽고 같은 파서로
   대조하면 "차이 0건"이 나온다.
6. **카탈로그·마스터의 인코딩을 확인할 것.** 카탈로그는 UTF-16, 마스터는 UTF-8 BOM.
7. **빌드 전 Studio 를 닫을 것.**
8. **작업 전 카탈로그를 재수집할 것.** 낡은 카탈로그는 이미 끝난 일을 남은 일처럼
   보이게 한다.
