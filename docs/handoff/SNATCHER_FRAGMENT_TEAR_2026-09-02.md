## 1-0. ★ 2026-09-02 정정 — 방아쇠는 "조각 전환" 이 아니라 "새 자막 적재"

> "새 조각이 나올때야 즉 자막 렌더러가 **새 자막을 가져올 때**임.  원래 조각 변경이
> 아니라" (소유자, 2026-09-02)

아래 §1 은 원인을 **이전 조각 스프라이트가 살아 있는 것** 으로 적었다.  소유자
관측은 그것과 다르다.  방아쇠가 조각 사이의 교체가 아니라 **렌더러가 자막 데이터를
가져오는 순간** 이다.  같은 음성의 첫 조각에서도 난다는 뜻이 된다.

그러면 후보 기구가 둘로 갈린다.

```
(가) 스프라이트 생존   이전 조각 스프라이트가 같은 base 를 가리키는데 덮어쓴다
                       -> 조각 2->3 에서만 난다.  첫 조각에는 안 난다
(나) 전송 가시화       업로드가 화면 그리는 중에 일어나 반쯤 쓰인 블록이 보인다
                       -> **적재할 때마다** 난다.  첫 조각에도 난다
```

소유자 관측은 (나) 를 가리킨다.  그리고 (나) 를 지지하는 실측이 이미 있다:

```
0.4.70   업로드가 34~69 스캔라인에 걸친다.  화면의 4분의 1이다.
         TIA 는 인터럽트를 못 받는다
```

★ 이것이 맞다면 **핑퐁이 실패한 이유도 설명된다.**  핑퐁은 (가) 를 푸는 수단이다.
  기구가 (나) 였다면 자리를 둘로 나눠도 증상은 그대로고, 검증 안 된 둘째 자리 탓에
  게임만 깨진다 — 소유자가 본 그대로다.

같은 이유로 §3 의 SATB wipe 도 (가) 를 푸는 수단이다.  (나) 가 맞으면 그것도 안 듣는다.

**다음에 앉으면 이 둘부터 가른다.**  첫 조각에서도 나는지만 보면 된다 —
첫 조각에서 나면 (나), 조각 2 부터만 나면 (가).  측정 없이 눈으로 갈린다.

### 1-0-1. 더 좁힌 관측 (같은 날, 추가)

> "이전에는 자리바꿈에서 깨졌다면 지금은 새로운 자막 즉 **화자가 바뀌어서 새 ADPCM 이
> 재생되기 전에** 깨진다" (소유자, 2026-09-02)

방아쇠가 조각 전환도 아니고 재생 중도 아니다.  **음성 무장(arming) 구간** 이다.
그 구간에서 우리가 하는 일은 정확히 둘뿐이다.

```
STATE=1  ->  helper 가 base 의 VRAM 을 백업 (2,432 B 읽기)
         ->  resident 가 렌더러를 CPU $5B80 에 싣는다
         ->  렌더러가 글리프를 VRAM 에 올린다   TIA · 34~69 스캔라인 (0.4.70)
         ->  자막 표시
```

읽기(백업)는 화면에 안 보인다.  남는 것은 **글리프 업로드** 하나다.  그것이
화면 그리는 중에 걸치면 반쯤 쓰인 블록이 한 순간 보인다.

이 관측으로 기구 (가) 는 사실상 배제된다 — 화자가 바뀌는 **첫 자막** 이면 덮을
이전 조각이 없다.  (나) 만 남는다.

방향이 정해지면 고칠 곳도 달라진다.  자리를 옮기거나(핑퐁) 스프라이트를 지우는(wipe)
것이 아니라, **업로드가 활성 표시 구간에 걸치지 않게** 만드는 문제가 된다.
전송을 vblank 안으로 넣거나, 한 번에 올리는 양을 줄여 화면에 안 걸치게 쪼개는 쪽이다.

⚠ 아직 측정으로 확정한 것은 아니다.  업로드가 실제로 활성 구간에 걸치는지, 그리고
  그 프레임에 화면이 깨지는지를 같은 프로브에서 같이 봐야 확정된다.

```

   스프라이트 16 · BG타일 0

조각 전환마다 15~18 개 스프라이트가 우리 블록을 가리키고 있었다.
**BG 타일은 항상 0** — 게임 것이 아니라 **이전 조각의 우리 자막**이다.

새 글리프를 덮고, VDC 가 그 자리를 읽는 중이라 그 프레임만 찢어져 보인다.  다음
프레임엔 멀쩡해진다.  소유자 관측과 일치한다:

> "글자가 새로 써지는 시점에 저게 살짝 나왔다가 바로 사라짐"

함께 확인된 것 (0.4.65 · 0.4.70):

게임이 그 자리를 다시 그림  전부 (512~4,736 word)
```

### 2-1. 실패 양상 — 자막이 아니라 **게임이 깨졌다**

> "이상하게 핑퐁은 자꾸 게임이 깨지더라고" (소유자, 2026-09-02)

이 구분이 중요하다.  글자가 틀리거나 안 뜨는 것이 아니라 **게임 화면이 깨졌다.**
그러면 원인은 그리는 방식이 아니라 **자리**다.

핑퐁은 자리를 **하나 더** 요구한다.  첫 자리는 측정으로 골랐지만 둘째 자리도
같은 근거를 갖췄다는 기록이 없다.  둘째가 게임이 쓰는 자리였다면 그 위에 글리프를
올리는 순간 게임 화면이 깨진다 — 관측과 정확히 맞는다.

이것이 맞다면 핑퐁 자체가 틀린 설계는 아니고, **둘째 자리를 안 재고 쓴 것**이
문제였다는 뜻이 된다.  다시 하려면 두 자리 **모두** 를 런타임 측정으로 세워야 한다.

★ 그런데 자유 구간은 장면마다 다르다.  `0.5.82` 가 CD-DA 임대 구간(LBA
  186792~187428)에서 잰 결과는 1,216 word 이상 연속으로 비는 구간이 **단 하나**
  (`$2640-$7FFF`) 였다.  한 장면에서 둘이 들어가더라도 **모든 장면에서** 성립하는
  고정 둘째 자리는 기대하기 어렵다.  핑퐁을 되살리려면 자리를 키별로 잡아야 한다.

⚠ 실패의 기계적 사유는 문서에 안 남아 있다.  `dump/sub_0_4_81_visible_compare_*.tsv`
와 `dump/sub_0_4_79_fixedbase_baseline.tsv` 가 남아 있으면 거기서 복원할 수 있다.
다시 시도하기 전에 그 두 덤프를 먼저 읽을 것.

## 5. 다음에 앉으면

핑퐁이 실패였으므로 남은 길은 B 의 네이티브 이식이다.  다만 착수 전에:

1. `dump/sub_0_4_81_visible_compare_*.tsv` 를 읽어 **핑퐁이 왜 실패했는지** 확정한다.
   그 사유가 wipe 에도 걸리는 것이면 B 도 같은 벽에 부딪힌다.
2. 렌더러 671 B 슬롯에는 **빈 자리가 없다** (0.4.6.52 문서).  `$5D9A-$5DD9` 의 64 B 는
   빈 자리가 아니라 `TIA $5D5A,$0002,128` 이 올리는 글리프의 빈 오른쪽 절반이다 —
   거기에 코드를 넣으면 화면에 그려진다.  헬퍼가 `128 B x 19 -> 64 B x 38` 재분할로
   자리를 냈던 것과 같은 수를 렌더러에도 써야 할 수 있다.
3. wipe 대상 슬롯 번호를 렌더러가 알아야 한다.  헬퍼의 wipe 가 무엇을 근거로
   슬롯을 고르는지 먼저 읽을 것.

## 5-1. 국장실 떨림 — 성능 이슈로 확인.  뒷문제로 넘김

> "국장실 떨림 문제는 역시나 성능 이슈인가봄.  **오버클럭 주니까 깔끔하네.**
> 이건 뒷문제로 넘긴다" (소유자, 2026-09-02)

`0.4.71` 이 적어둔 기구와 일치한다.

> 국장실 **화면 떨림** 은 그대로다.  그건 다른 원인이다: 업로드가 34~69 스캔라인에
> 걸친다.  **TIA 는 인터럽트를 못 받으므로 래스터 분할 IRQ 가 밀린다.**
> -> 스크롤이 엉뚱한 줄에서 바뀌고, 밀린 정도가 매 프레임 달라 떨린다.

오버클럭으로 사라진다는 것은 이 설명의 **확증** 이다.  사이클을 더 주면 IRQ 지연이
사라진다.  자리·스프라이트·래치 문제가 아니라 **시간 예산** 문제다.

### ★ 뿌리가 §1-0 과 같다

업로드가 화면 4분의 1을 먹는다는 사실 하나에서 증상이 둘로 갈라진다.

```
사이클을 뺏겨 래스터 IRQ 가 밀린다     ->  국장실 떨림      (오버클럭으로 사라짐)
그리는 중에 걸쳐 반쯤 쓴 블록이 보인다 ->  새 자막 적재 노이즈
```

**업로드가 활성 표시 구간에 걸치는 폭을 줄이면 둘 다 줄어들 여지가 있다.**
따로 고칠 것이 아니라 한 지점일 수 있으므로, §1-0 측정을 할 때 스캔라인 폭을
같이 기록해 둘 것.

## 6. 섞지 말 것 — 오늘 열려 있는 다른 건

```
A  자막 사이 한 프레임 노이즈    이 문서.  조각 전환 wipe 부재
B  MAWR 미복원                  0.4.6.52 가 헬퍼 8 B 로 고침.  그런데 .61/.63/.64 에
                                안 실렸다 (서명 검색: .52 의 Track24 에만 HIT)
                                렌더러 경로($5CB6)는 .52 도 안 고쳤다
C  ACT1 배경 파손               임대 구간에 게임이 $7900 에 320 회 쓴다 (0.5.80).
                                단 깨끗한 판에서는 0 회 (0.5.82) -> 우리가 유발한다
D  음성 자막 178건 미표시        키의 end_addr 가 FFFF 센티넬.  64KB 경계.
                                bytes_captured 를 0x800 올림으로 복원 가능 (충돌 0)
```

B 와 C 는 같은 뿌리(우리가 VDC/VRAM 상태를 남긴다)일 가능성이 있다.  A 와 D 는 별개다.
