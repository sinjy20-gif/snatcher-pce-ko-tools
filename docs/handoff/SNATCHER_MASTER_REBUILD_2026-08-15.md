# 마스터 구조 전면 개편 — 조사와 이관 설계 (2026-08-15)

소유자 판단으로 시작된 건이다.  기존 마스터는 **정적 추출본을 기준으로 삼고 런타임
수집을 뒤에 덧붙이는** 구조인데, 그 전제가 무너졌다.

```
정적 추출본이 데이터 전체가 아니다        크게 잡아도 30~40% 수준
조각난 문장을 담지 못한다
런타임으로 부족분을 채우지만 기존 정적 행 뒤로 붙는다
-> 조각이 순서대로 배치되지 않는다
```

방향: **정적 추출본은 참조용(커버리지 대장)으로 내리고, 런타임 수집을 마스터로.**

---

## 0. 결론 — 개편에 찬성한다.  기존 번역은 얹을 수 있다

목표는 **런타임이 수집한 문장 위에 기존 번역을 얹는 것**이다.  지금 마스터의 행
분할은 정적 추출의 산물이므로 지키지 않는다.

```
원문 기준으로 얹을 때 자동으로 붙는 비율
  행 단위    96.2%   (어긋나는 행 271, 3.8%)
  문단 단위  98.9%   (어긋나는 문단 47, 1.1% · 검토 포함 28, 1.8%)
```

**문단 기준으로 얹으면 98.9% 가 자동이고, 소유자가 직접 볼 목록은 28 건이다.**
중복과 조각 의심은 소유자가 직접 판정한다.

---

## 1. 왜 행 단위로는 안 되는가 — 실측

`ko_text` 는 `jp_text` 의 **행별 번역이 아니다.**  한국어 길이에 맞춰 문단을 다시
흘려썼기 때문에 분할점이 어긋나 있다.

```
412  jp 'ジェミー、<원문 9자>。'   ko '제이미, 화상전화'
413  jp '<원문 7자>'                ko '끊을게. 그럼...'
```

일본어는 412 에서 문장이 끝나는데 한국어는 413 으로 넘어가 끝난다.  같은 문단이
다른 곳에서는 제대로 나뉘어 있다.

```
6266  ko '제이미, 전화 끊을게.'
6267  ko '그럼…'
```

`？` 한 글자에 번역이 6 종인 것도 같은 이유다 -- 일본어는 물음표만 남은 꼬리인데
한국어는 그 앞 행에서 질문을 끝냈다.

**즉 "번역 충돌" 로 보이던 것 대부분이 조각 어긋남의 흔적이다.**  소유자 진단이
정확했고, 이것이 개편을 지금 해야 하는 이유이기도 하다 -- 나중에 고치면 이미 번역된
것까지 다시 손봐야 한다.

## 3. 이관 가능성 — 숫자

### 3.1 행 단위

```
중복 원문                635종 (2,087행, 29.0%)
  번역이 모두 같다        552종 (86.9%)  -> 어느 것을 골라도 무해
  번역이 다르다            83종
원문+화자+제어로도 갈림    76조합 (271행, 3.8%)
검토 O 중 중복 원문       1,339 / 2,464 (54.3%)
```

### 3.2 문단 단위 — 이쪽을 쓸 것

```
번역이 갈리는 문단        20종 (47문단, 1.1%)
검토 O 포함 문단 중 갈림   28 / 1,586 (1.8%)
```

**행에서 문단으로 올리는 것만으로 모호함이 1/3 로 준다.**  남은 28 건은 실제 판단이
필요한 것들이다 (예: `『天皇賞』、<원문 6자>？` 가 "천황상, 곧이잖아?" 와
"『천황상』,이제 곧이지?" 로 갈림).

## 4. 이관 설계

**틀을 분명히 해 둔다 (소유자 지정).**  지금 마스터의 문장 구조를 지키자는 것이
아니다.  런타임이 수집한 문장이 골격이고, 거기에 **기존 번역을 얹는다.**

```
런타임 수집 결과   행 구조의 진실.  순서도 조각도 여기서 온다
기존 ko_text       그 위에 얹을 재료.  현재의 행 분할은 버린다
겹치지 않는 것      목록으로 뽑아 소유자가 직접 본다
```

절차:

```
1. 런타임 수집으로 새 행 골격을 만든다
2. 기존 번역을 원문 기준으로 얹는다 (문단 단위가 정확도가 높다 -- §3.2)
3. 안 얹힌 것 · 갈리는 것 · 조각 의심을 목록으로 출력
4. 소유자가 그 목록만 직접 판정
```

문단 단위를 쓰는 이유는 보존이 목적이 아니라 **매칭 정확도** 때문이다.  행으로
맞추면 3.8% 가 어긋나고 문단으로 맞추면 1.1% 다 (§3).  얹고 난 뒤의 분할은 런타임이
정한다.

### 반드시 정해야 할 것

```
검토 O 의 의미     행 단위로 검토했는데 문단 단위로 옮기면 무엇이 "검토됨" 인가.
                  문단 안에 O 가 하나라도 있으면 문단을 O 로 볼 것인가 (1,586 문단)
문단 경계          END 가 잘못 찍힌 문단은 이관도 틀린다.  경계 신뢰도를 먼저 볼 것
중복 원문 처리     같은 jp 문단이 여러 곳에 나올 때 어느 것을 정본으로 둘 것인가
```

### 안전장치 (기존 스튜디오 규율과 동일하게)

```
새 마스터를 별도 파일로 먼저 만든다.  기존은 그대로 두고 나란히 검증
드라이런 -> 백업 -> 왕복 byte-exact 검증
이관 전후로 검토 O 개수와 번역 내용이 보존되는지 대조
```

번역 작업을 멈추지 않고 갈아탈 수 있다는 점에서도 별도 파일 방식이 맞다.

## 5. 정적 추출본을 왜 남겨야 하는가

소유자 제안대로 참조용으로 남기는 것이 맞고, 이유를 분명히 해 둔다.

**런타임 수집에는 분모가 없다.**  안 가본 분기, 안 본 아이템 설명, 안 죽어본 엔딩은
영원히 안 잡히고 **무엇이 빠졌는지도 모른다.**  정적본은 부정확해도 "이만큼은
존재한다" 는 목록이므로 커버리지를 잴 수 있다.

```
정적본   무엇이 존재하는가          분모.  30~40% 라도 목록으로서 유효
런타임   무엇이 어떤 순서로 나오는가  분자.  본문·조각·순서의 진실
```

따라서 정적본은 마스터에서 빼되 **커버리지 대장으로 유지**하고,
"정적에는 있는데 런타임에서 아직 못 본 것" 보고서를 뽑을 수 있어야 한다.

## 7. 다음 세션에서 시작할 것

```
1. 원시 런타임 로그의 현재 형태 확인      <- 여기서부터.  개편의 성패가 여기 달렸다
   조각과 순서를 얼마나 복원할 수 있는가
2. 문단 경계(END) 신뢰도 점검
3. 검토 O 의 문단 단위 정의 결정
4. 이관 스크립트 작성 (별도 파일로 출력)
5. 갈리는 28 건 수동 판정 목록 출력
```

**새로 원인 조사부터 다시 하지 말 것.**  §1~§3 의 숫자는 실측이고, 문단 단위 이관이
가능하다는 것도 실측으로 확인됐다.
