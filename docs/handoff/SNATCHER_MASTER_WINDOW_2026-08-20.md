# 인계서 — 마스터를 "창 단위"로 다시 만들다 (2026-08-20 환경 A)

환경 B분 인계서(`SNATCHER_VOICE_RAM_2026-08-20.md`)에 이어지는 그날 저녁 기록이다.
수집을 돌리다가 **마스터의 레코드 경계가 게임 화면과 어긋나 있다**는 것이 드러나
마스터를 다시 만들었다.  이 문서 하나로 이어서 일할 수 있게 쓴다.

---

## 0. 한 줄 요약

**레코드 하나 = 게임 텍스트 창 하나** 라는 규칙이 깨져 있었다.  한 창이 두 레코드로
쪼개져 있었고, 그래서 가운데 조각이 사라지고 빈 줄이 남고 남의 문맥 번역이 붙었다.
런타임 수집기는 처음부터 제대로 묶고 있었다 -- 어긋난 것은 마스터 쪽이다.
로그 묶음을 정답으로 삼아 마스터를 다시 만들고, 번역 4,305 행 중 **4,300 행을 글자
그대로 옮겼다**.

---

## 1. 무엇이 잘못돼 있었나

소유자가 화면에서 발견했다 -- 대사 한 창 가운데에 빈 줄이 있다.

```
게임 창 하나
  1 줄   なんだ。またか？<원문 10자>     <- R03028
  2 줄   (빈 줄)                              <- 「う。」 는 마스터 어디에도 없다
  3 줄   <원문 5자>。                          <- R03029
```

**ID 가 다르면 다른 창이어야 한다.**  그런데 한 창에 둘이 들어가 있었다.

### 1.1 런타임 로그는 처음부터 맞았다

```
seq 8137  rec_seq=2455 line 1  END   ギリアン
seq 8138  rec_seq=2455 line 2  CONT  なんだ。またか？<원문 10자>   state 0000->04D4
seq 8139  rec_seq=2455 line 3  END   う。                              state 04D4->0000
seq 8140  rec_seq=2455 line 4  END   <원문 5자>。                       state 0000->0000
```

수집기가 화자명까지 한 덩어리(`record_seq` 2455)로 묶어 놓았다.  잘라먹은 것이
없다.  잃어버린 곳은 그 다음 단계다.

### 1.2 왜 「う。」 가 마스터에 없었나 -- 뿌리 지뢰

`う。` 는 화면에서 지워지고 있었다 (`changed=yes`).  치환한 것은 이 레코드다:

```
R01389:1   state=0000   ko={EMPTY}
```

**state 0000 은 와일드카드처럼 동작한다.**  실측 (오늘 밤 치환 성공 7,322 건 분해):

```
state 가 정확히 일치해서 치환   7,267 건
state 0000 짜리가 대신 먹음        55 건     <- 「ギリアン」 이 state 0011 에서, 「局長」 이 006F 에서
설명 안 되는 것                     0 건
```

화자 이름처럼 아무 문맥에나 나오는 것에는 필요한 동작이다.  문제는 **꼬리 조각이
뿌리에 앉을 때**다.  두 글자짜리 `う。` 가 뿌리에 있으면 게임 안의 모든 `う。` 를
먹는다.

그리고 먹혔으니 감사는 `HIT` 으로 분류하고, 스튜디오의 `대사 포함` 은
`MISS·NEAR·ROUTE_FAIL` 만 담으므로 **영영 마스터에 안 들어온다.**  소유자가
"이거 왜 없냐" 고 물은 것이 이 고리다.

### 1.3 뿌리 지뢰 목록 (state 0000 + `{EMPTY}`) -- 14 개

```
R01389:1 「う。」      R01283:1 「が。」      R01316:1 「る。」      R01936:1 「物。」
R01799:1 「タ』」      R01287:1 「です。」    R01345:1 「れた。」    R01932:1 「なった。」
R01929:1 「が生じた。」 R02101:4 「　です。」  R01958:1 「ド・・・」
R01865:1 「<원문 8자>」   R1955:1 「<원문 7자>。」   R01807:1 「査。（アメリカ）」
```

오늘 밤에만 **16 회 · 12 가지 다른 state** 에서 먹었다.  그 자리들은 전부 지금
이 대사와 같은 상태다 -- 화면엔 빈 줄, 마스터엔 없음.

부모는 로그로 전부 특정된다 (`next_state == state_before` 로 잇는다).  12 개 조합
전부 부모가 하나로 나왔다:

```
「う。」 state 04D4 -> R03028:1   「る。」 state 03B4 -> R02227:1 (신賴 깨진 그 대사)
「う。」 state 030D -> R01117:1   「です。」 state 0452 -> R02688:2
「う。」 state 0429 -> R02598:1   「です。」 state 0483 -> R02827:1
```

### 1.4 근본 원인은 임포터의 배치 규칙

스튜디오의 `대사 포함` 은 런타임 MISS 를 **무조건 `line_no="1"` 로** 넣는다
(`MainForm.cs:2096`).  관측된 state 를 `note` 에 적어 두면서 정작 배치는 뿌리로
한다.  그래서 꼬리가 앞 문장에서 떨어져 나와 전체를 대표하게 된다.

옛 "같은 원문 = 같은 번역" 시절의 잔재다.  지금은 state 로 문맥을 가르는
시스템이므로 **꼬리는 앞 문장에 종속**이어야 한다.

## 2. 다시 만든 방법

`tools/rebuild_master_by_window.py` (새로 만듦).

```
로그 묶음(record_seq) = 창 하나 = 레코드 하나        <- 정답의 기준
화자명 줄은 body 에서 빼고 speaker 열로
after_control 은 마지막 줄만 END, 나머지 CONT
같은 내용의 창이 여러 번 관측되면 하나로
```

### 번역 옮기기 -- 한 글자도 안 바꾼다

```
A  ID 를 물려받은 레코드의 같은 줄 · 같은 원문   -> 그 번역 그대로      3,641 행
B  원문이 현역 마스터 전체에서 번역이 딱 하나    -> 그것 그대로        1,344 행
C  그 외 (번역이 여러 개거나 없음)              -> 비운다              816 행
```

C 는 소유자 지시다: **겹치거나 말이 안 되면 꼬리는 그냥 비운다.**  짧은 꼬리는
원문만으로 절대 못 맞힌다.

### 전수 검증 (표본 아님)

현역 마스터의 번역 있는 행 **전부**를 새 마스터에서 `(원문, 번역)` 바이트 단위로
확인했다.

```
현역 번역          4,305 행
그대로 옮겨진 것    4,300 행  (99.9%)
못 옮긴 것              5 행  <- 전부 "같은 원문에 번역이 2~7 가지" 라 비운 것
```

못 옮긴 5 행은 원문·번역·사유까지 보고서에 남겼다.

## 4. 아직 안 한 것 -- 다음 세션의 할 일

### 4.1 ★ 스튜디오 임포터 (제일 중요)

지금 고치지 않으면 **다음 수집 때 같은 지뢰가 다시 생긴다.**

```
MainForm.cs:2096   master.Set(row, "line_no", "1")     <- 관측된 state 를 무시하고 뿌리로
```

관측된 state 의 부모(`next_state == state_before`) 밑 `:N` 으로 붙여야 한다.
로그에 필요한 정보가 다 있다 (§1.3 에서 12/12 특정됨).

### 4.2 뿌리 지뢰 14 개 정리

새 마스터에서 다시 세어볼 것.  창 단위로 다시 만들었으므로 상당수가 제자리를
찾았을 수 있다.  남은 것은 state 0000 에서 내린다.

### 4.3 BIOS 폰트 -- 빠진 글자 58 자

```
슬롯맵 882 자 (08-20 08:22 에 구움) · 디스크가 쓰는 음절 939 자
빠진 58 자 -> 85 개 레코드에서 글자 하나씩 깨진다 (화면 실측: 「신賴가」 = 뢰 없음)
```

원인은 시간 순서다 -- 슬롯맵 08:22, 마스터 16:21.  **BIOS 만 다시 굽는 걸로는
안 된다.**  슬롯맵이 커지면 인덱스가 흔들리므로 디스크도 같이 구워야 한다.

```
1  build_bios_hangul_map.py    마스터에서 슬롯맵 다시
2  build_bios_font_patch.py    그 맵으로 BIOS
3  디스크 재빌드                같은 맵으로
4  Syscard3_galmuri.pce -> Mesen Firmware 로 복사
```

번역이 더 늘면 58 자도 늘어난다.  **한 바퀴 다 돈 뒤에 한 번에** 굽는 게 맞다.

### 4.4 `{EMPTY}` 가 빈 줄로 남는 문제

빌더가 막아 놨다 (`compile_overlay_assets.py:142,146`):

```
END must occur only on the final row
canonical ko_text cannot contain inline layout controls   ({BR}·{PAGE} 금지)
```

즉 `ko_text` 안에 `{BR}` 을 넣어 한 행을 두 줄로 만들 수 없다.  줄 나눔은 **행을
나눠서만** 표현한다.  그러므로 빈 줄을 없애려면 그 자리에 글자를 넣어야 한다
(창 단위로 다시 만들었으니 이제 그 자리에 행이 있다).

## 5. 자막 -- 오늘 밤 알아낸 것

### 5.1 엔진이 살 자리를 "빌리는" 설계

자리를 찾는 시도가 세 번 다 무효가 됐다 (`$5C40-$5E1F` · `$2311` · `$3468`).
그래서 **빌려 쓰고 되돌려 놓는** 쪽으로 간다.

```
음성 START   프리로더 $5E40-$5FFF (448 B) 를 AC 로 대피 · 엔진 적재 · IRQ1 벡터 교체
음성 END     벡터 원복 -> AC 에서 448 B 되돌리기
```

프리로더를 고른 이유:
1. 하는 일이 텍스트 치환뿐이다.  **이 게임은 음성 재생 중 대사가 출력되지 않는다
   (대사 창 자체가 없다 -- 소유자 확인).**  그러면 프리로더는 할 일이 없다
2. 스택이 `$5E40` 을 넘으면 게임은 지금도 죽는다.  그 선 위는 이미 "침범하면 끝"
   인 구역이라 빌려도 위험이 새로 생기지 않는다

### 5.2 실측 -- `PROBE_ARENA_0.1.5` (새로 만듦)

게이트를 `cdrom.adpcm.playing` 으로 걸고 그 창 안에서 프리로더 진입점
(`$5E7B·$5F20·$5F72·$5FB4`) 실행을 셌다.

```
음성 창 71 건
  1~52 · 65~67   preloader 0 회   stack $5B80 (깊이 0)      <- 빌려도 된다
  53~64          preloader 3~38   stack $5B80~$5C19         <- 빌리면 죽는다
```

**음성 중에는 스택이 바닥까지 풀려 있다.**  그러면 빌릴 수 있는 자리가 프리로더
448 B 에 스택 구역 704 B 까지 더해 **1,152 B** 다.  엔진 전체 견적이 1,140 B 이므로
통째로 들어간다.

### 5.3 예외 12 건의 정체

로그 정렬(지속시간 수열 70/70 일치, 프레임 차 1,894)로 수집기 쪽과 맞춰 보니
**프리로더가 돈 13 창 전부가 같은 클립** `vDA76A9EB.bin` 이었다.

```
vDA76A9EB   46 회 재생 중 프리로더 돈 것 13 회   (33 회는 조용함)
그 외 클립   25 창 중 프리로더 돈 것  0 회
```

92 프레임 12 KB 짜리가 46 번 반복 -- 대사가 아니라 **반복 효과음**이다.  그 소리가
깔린 화면에서 게임이 가끔 텍스트를 그린다.

**해결은 간단하다: 자막이 있는 대사에만 빌린다.**  효과음은 자막표에 없으므로
엔진이 애초에 켜지지 않는다.  지금 표본으로는 그 규칙이 깨끗하다 (효과음 아닌
대사 25 창 전부 프리로더 0).  100 건쯤 모이면 설계를 확정해도 된다.

### 5.4 대조군을 반드시 볼 것

`0.1.5` 는 음성 **밖** 진입도 따로 센다.  음성 밖이 0 이면 주소가 틀렸거나 훅이 안
걸린 것이지 "음성 중에 안 돈다" 가 아니다.  이번엔 VOICE[53] 에서 실제로 터져서
계기가 살아있음이 스스로 증명됐다.
