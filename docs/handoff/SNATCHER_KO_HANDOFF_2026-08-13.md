## 2. master 오염과 복구

`snatcher_ko_master.tsv` 가 과거에 CP949 로 저장되면서 그 코드페이지에 없는 일본어가
전부 `?` 로 뭉개져 있었다.

```
ジェミー。      →  ジェミ?。        (장음 ー 소실)
<원문 6자>    →  軍隊を?けた      (한자 抜 소실)
危険だ          →  危?だ
```

**6,846 행 중 3,743 행(54.7%) 손상, 그중 1,064 행이 출하 중**이었다.

치명적인 이유: 런타임 치환은 **일본어 원문 바이트로 조회**한다. 원문이 깨진 행은
검토 O 를 찍어도 게임에서 영원히 매칭되지 않는다. 즉 1,064 행이 헛돌고 있었다.

**복구 완료.** 같은 날 10:03 백업(UTF-8, 손상 0)에서 일본어만 되살리고 한국어·검토는
현재 것을 유지했다. 백업 56 개를 전수 대조해 **한국어 손실 0 건**을 확인했다.

### 재발 방지

원인은 스튜디오였다. `TsvDocument.Load` 가 BOM 없는 파일을 무조건 UTF-8 로 단정했고,
CP949 파일을 그렇게 읽으면 모든 글자가 U+FFFD 가 된 뒤 저장 시 파일에 그대로 쓰였다
(실측 411,633 개).

```
수정 후: BOM 없음 → 엄격한 UTF-8 검사 → 실패하면 CP949 로 읽기
         저장 시 UTF-8 + BOM 으로 승격
```

**파이썬으로 TSV 를 쓸 때 `encoding=` 을 반드시 명시할 것.** 한국어 윈도우의
`open()` 기본값이 CP949 라 이 사고가 났다.

## 4. MPR6 = 장면(팩) 키

빌드 stage 3 은 AC 팩을 장면 단위로 분할한다(로딩 때문). 런타임 행은 장면이 없어
캡처 순번이 가까운 항목의 장면을 **추정**했고, 실패하면 빌드가 죽었다.

**캡처 시점($5E40)의 MPR6 뱅크가 곧 장면이다.** 하드웨어가 그 순간 들고 있는 값이라
추정이 아니라 관측이다.

| 위치 | MPR6 | 근거 |
|---|---|---|
| 접수처 | `74` | 장면 111800 과 9/9 일치, **파워사이클 2 회 재현** |
| 본부·국장실 | `75` | 200 줄 넘게 안정 |
| 컴퓨터실·기계실 | `76` | |
| 깁슨 사무실·사격장 | `72` | 3 회 재진입 모두 동일 |
| **공용 이동 프롬프트** | `71` | `<원문 12자>？` 등 10 줄뿐 |

`71` 이 결정적이다. 구역 전환마다 끼어 있고 고유 대사가 10 줄(1,280 B)뿐인데, 이는
빌드가 이미 가진 상주 팩 `shared` 와 성격·크기가 정확히 일치한다.

MPR6 는 RAM 스테이징 뱅크라 `scene_111800` 같은 CD 오프셋으로 환산되지 않는다.
**환산할 필요가 없다** — `classify` 는 팩 이름 **문자열**을 돌려주는 플러그인 지점이고,
CD 오프셋이어야 할 이유가 코드 어디에도 없다.

### 붙일 때 고칠 곳

`build_ac_dynamic_0_1_11.py` 의 `classify_runtime_scene` 은 런타임 행이 여러 씬에
걸치면 **예외를 던진다.** 반면 정적 행은 `classify_split_common` 이 같은 상황을
`shared` 로 보낸다. 같은 논리로 통일하면 된다.

```python
packs = {PACK_OF[ref] for ref in runtime_refs}
return f"area_{next(iter(packs))}" if len(packs) == 1 else "shared"
```

즉 **관측된 pack 이 하나면 그 구역 팩, 여러 개면 shared.** `RuntimeError` 도 사라진다.

## 5. Lua 수집기 수정 — 점검 통과

### ① 진짜 버그: `after_control` 이 항상 비어 있었다

```lua
-- 전 (Lua 테이블 생성자 안에서는 다중대입이 성립하지 않는다)
pending = { ..., afterControl, controlOrigin, controlHex = resolveAfterControl(...) }
--          ↑ 전역변수 nil 이 배열 원소로 들어가고 controlHex 만 첫 반환값을 받음
```

`pending.afterControl` 이 항상 `nil` 이었다. **BR/PAGE 를 감지하고도 기록이 안 됐다.**

### ② 제어코드 귀속 1:1

기존 "2 프레임 이내" 는 느린 줄에서 BR 을 놓쳤다. **소비-1회 + 60 프레임 상한**으로
바꿨다.

### ③ 컬럼 추가: `pack`(MPR6) · `sector`(`cdrom.scsi.sector`)

`$E006` 의 제로페이지 `$F8-$FB` 는 LBA 가 아니라 **바이트 수와 목적지 포인터**다.
그리고 제로페이지는 CPU `$00F8` 이 아니라 **`$20F8`** 에 있다(MPR0=`$FF` 는 I/O,
MPR1=`$F8` 이 RAM 을 `$2000` 에 매핑).

## 6. master `pack` 자동 기록

스튜디오가 캡처를 기존 master 행에 매칭하면 MPR6 를 찍는다. 실측:

```
기존 정적 행   pack 받음 260 / 미기록 6,138
RUNTIME_ 행    pack 받음  37 / 미기록   417
```

**297 건 중 260 건이 예전부터 있던 정적 행**이다. 매칭이 일본어 원문 바이트 기준이라,
오늘 원문을 복구한 덕에 기존 행들이 걸린 것이다. 복구 전이었다면 절반이 영영 매칭되지
않았다.

### 값이 흩어져 보이는 것은 정상이다

`pack 74` 가 111800 이 아닌 페이지에도 찍힌다. 확인해 보니:

```
87 건 중  원문이 111800 행과 동일 32   ← 같은 원문 = 트라이에서 한 레코드, 정상
          원문이 111800 에 없음   55   ← 55 건 중 52 건이 2~3 자 (`す。` `です。`)
```

**같은 원문이면 같은 pack 에 들어간다**(사용자 지적이 맞았다). 흩어져 보인 건 정적
추출이 남긴 문장 꼬리 조각들이 값을 같이 받은 것뿐이고, 그 조각들은 이미 폐기 대상이다.
그리고 그런 조각은 애초에 여러 곳에 쓰이므로 **`shared` 로 가는 것이 맞다** — 4 장의
규칙과 일치한다.

## 10. 남은 일

### A. 세이브 후 타이틀 복귀 시 화면 깨짐 (미조사)

정상 세이브 → 타이틀로 나갔다가 복귀하면 화면이 깨진다. **파워사이클 후 로드는 정상.**
부팅 시 한 번만 세팅되는 상태(AC 팩 포인터 · `$5B80-$5E3F` 캐시 · VRAM 폰트 타일)가
소프트 복귀에서 재초기화되지 않는 쪽이 의심된다. 9 장과 같은 뿌리일 수 있다.

### B. 디버그 씬 점프 메뉴 — 노동량을 크게 줄일 수 있음

Track02 `0xBDD05~0xBDF4F` 에 개발자용 씬 점프 테이블 45 개가 있다.

```
ａｃｔ１前半 · ａｃｔ２開始 · ＪＤへ直行 · <원문 8자> · <원문 8자>
<원문 6자> · <원문 8자> · <원문 6자> · <원문 7자> …
```

가나 순 → 한자 순으로 정렬돼 있어 개발자용이 확실하다. **띄울 수만 있으면 act 단위로
건너뛰며 수집**할 수 있어, 런타임 수집의 유일한 약점인 "전 구간 직접 플레이"가 사라진다.
테이블 주소 참조 코드에 브레이크포인트를 걸면 호출부가 나온다.

### C. CDDA(오프닝) 수집 미구현

오프닝은 ADPCM 이 아니라 `cdrom.audioPlayer` 경로라 현재 수집기가 못 잡는다.
`auditVoiceAtFrame` 에 `cdrom.audioPlayer.currentSector` 증가 감시(12 프레임 유예)를
추가하면 된다. 기록기의 `audio_type` 이 `"ADPCM"` 으로 하드코딩돼 있으니 인자로 뺄 것.
ADPCM 경로는 건드리지 않는다.

### D. 타이틀 메뉴 그래픽 — `SNATCHER_TITLE_MENU_GFX_HANDOFF.md`

스프라이트 고정 그래픽. `$3B00` 작업 버퍼 → `$725C` 전송 → VRAM.
**`$725C` 직전에 `$3B00` 을 한국어 스프라이트로 덮어쓰는 우회**가 가장 현실적.

### E. 오프닝 자막 — `SNATCHER_OPENING_CD_AUDIO_HANDOFF.md`

본편이 `frame 2331~10283 / sector 184018~193971 / 132.533 초` 짜리 연속 한 구간이라,
시작점 하나만 후킹하고 타임코드 테이블로 뿌리면 된다. 이 구조가 오늘 개편한 음성 자막
탭의 데이터 모델(`event_id · part · start_sec · duration_sec · gap_after_sec`)과 그대로
맞는다. 다만 `AddVoiceSubtitle()` 이 `kind == "대사"` 만 허용하므로 CDDA 이벤트용
수동 등록 경로가 필요하다.

## 12. 함정

1. **스튜디오를 켜둔 채 파일을 외부에서 고치지 말 것.** 저장하면 외부 수정이 덮어써진다.
   부득이하면 **강제 종료**로 닫을 것(일반 종료는 저장 여부를 묻는다).
2. **파이썬으로 TSV 를 쓸 때 `encoding=` 명시.**
3. **`jp_text` 를 임의로 고치지 말 것.** 런타임 조회 키다. 표시가 이상해도 ROM 과
   바이트가 같아야 한다(예: `★フレ★<원문 5자>`).
4. **압축 해제 위치는 `C:\snatcher` 고정.**
5. 빌드 전 스튜디오를 닫을 것.
