## 1. 트리거 — 시계가 아니라 사건이다 (ADPCM)

게임이 재생을 걸 때 쓴 레지스터 값을 지문으로 쓴다.  "지금 몇 초냐" 를 몰라도 된다.

```
ADPCM   ADPCM_<readAddr>_<length>_<rate>
        재생 중에는 readAddr 가 움직이므로 **끝 주소**로 정규화한다
            finish = (readAddr + length) & 0xFFFF   ->   E<finish>_<rate>
        끝 주소는 write_address 와 같다 -- 시작만 밀리고 끝은 고정이다
```

`emu.getState()` 는 **평평한 점표기 키**를 준다.  `s["cdrom.adpcm.playing"]` 처럼.
중첩 테이블이 아니다 (여기서 두 번 헛짚었다.  `st.vdc.hvReg` 는 안 된다).

### 충돌 — 정규화가 과하게 뭉갠다

```
449 이벤트  ->  정규화 열쇠 71 개     같은 클립을 반복 수집한 것이 대부분
그런데 실제 ADPCM 클립은 248 개다     ★ 71 << 248 -- 다른 소리까지 뭉갠다
겹치는 열쇠 29 개 중 6 개는 지속시간 산포가 크다 (다른 클립이 섞였다)
```

`E6800_0E` 하나에 17 개가 붙어 있고 그중 하나만 자막이 달려 있었다.  표가 마지막
행으로 덮어써서 자막을 못 찾았다.  **열쇠가 겹치면 자막 있는 것 > 대사 > 화자 있는 것
순으로 고르게** 고쳤다.

> 믿을 수 있는 신원은 `clip_file`(내용 해시) 하나뿐이다.  주소로 잇지 마라.

## 2. CD-DA 는 시계 기반이다 — 그리고 여기가 본체다

CD-DA 이벤트를 실측하니 **전부 트랙 시작(0.00 초)에 잡힌다.**

```
20260814_124935_0004  sector 02CED0 -> 트랙 17  0.00 초
20260814_125627_0006  sector 02F5B2 -> 트랙 18  0.00 초
```

트랙 10 안에만 대사가 80 개다.  이벤트 하나로는 못 가른다.
**자막 단위는 이벤트가 아니라 전사 세그먼트 407 개다.**

그리고 대사의 본체가 여기다:

```
CD-DA  407 세그먼트 · 32.5 분     분류기 기준 대사 222 · 실제로 말이 있는 것 345
ADPCM  248 클립 · 14.7 분         분류 없음 · Whisper 환각 섞임
```

### 자동 분류가 대사의 40% 를 놓친다

```
분류기       대사 222
글자 기준    345      ★ 음악으로 숨어 있던 것 152 개
```

배경음 위에 얹힌 내레이션을 음악으로 본다.  **트랙 17 의 오프닝 내레이션 15 개가
통째로 그렇게 숨어 있었다** (`1991年6月6<원문 5자>...` 부터 `<원문 11자>` 까지).
그래서 화면 필터는 분류가 아니라 글자로 판단한다 (6 자 이상 · 환각 문구 아님).

### 그리고 내레이션은 트랙 시작이 아니다

트랙 17 의 내레이션은 **36.46 초부터** 시작한다.  앞 36 초는 음악이다.
이벤트에 자막을 달면 36 초 일찍 뜬다.  시간 기반이어야 하는 이유다.

### 런타임을 단순하게 — 절대 LBA 를 미리 박았다

`.cue` 는 트랙마다 파일이 따로라 INDEX 가 파일 기준이다.  앞 파일들의 섹터 수를
누적해야 절대값이 나온다.  그 계산을 빌드 때 다 해서 각 세그먼트에 박아 둔다.

```
build/cutscene_subs/cdda_segments.tsv
  clip · track · lba_from · lba_to · start_sec · end_sec · seconds · kind · jp_whisper

런타임이 할 일:  lba_from <= cdrom.audioPlayer.currentSector <= lba_to
```

407 세그먼트, 구간 겹침 0.


### ★ TSV 를 읽을 때 인용을 꺼야 한다

`subfont_Galmuri9.tsv` 에 큰따옴표(`"`, U+0022) 한 글자가 있는데, Python 의
`csv.DictReader` 가 기본으로 그것을 인용부호로 보고 **3320 행을 3 행으로 잘랐다.**
증상은 "13 글자를 넣었는데 2 글자만 나온다" 였다.

```python
csv.DictReader(fh, delimiter="	", quoting=csv.QUOTE_NONE)
```

TSV 는 탭으로만 나누므로 인용이 필요 없다.  `cdda_segments.tsv` 도 일본어에
`"` 가 들어가면 같은 식으로 깨진다.  Lua 와 스튜디오는 탭으로 직접 자르므로 무사하다.

`audioop` 은 Python 3.13 에서 표준 라이브러리에서 빠졌다.  표본율을 줄일 때만
필요하므로 그때만 불러온다.

## 9. 기술 과제 — 남은 것 전부

번역(사람 시간)을 뺀 기술 항목만 모았다.  이 넷이 끝나면 기술장벽은 사실상 끝이다.

### 9.1 디스크 적용 — 자리를 두 번 틀렸다.  결론은 "음성 중에만 빌린다"

#### 먼저: 문서를 날짜순으로 볼 것

오늘 같은 실수를 두 번 했다.

```
아침   CUTSCENE_SUBS 를 SUB/ 로 복사해 놓고 안 읽음  -> 반나절 오버레이 구멍 찾기
저녁   CUTSCENE_SUBS(08-19)는 읽고, 그것을 뒤집은 ARENA(08-20)는 안 읽음
       -> $5C40 에 페이로드를 다 만들어 놓고 폐기
```

**08-19 의 결론을 08-20 이 뒤집었다.**  앞것만 보고 움직이면 안 된다.

#### 무효 — `$5C40-$5E1F` 는 스크립트 VM 데이터 스택이다

```
$5B80-$5E3F   704 B   스크립트 VM 데이터 스택.  $4880 이 바닥을 깔고 위로 자란다
자막 예약     $5C40-$5E1F 480 B  ->  그 안에 100% 들어간다

probe_arena_0_1_3.tsv:  최고 깊이 $5DEF · 623 B · 프리로더($5E40)까지 여유 81 B
```

`PROBE_DEAD_RAM_0.1.1` 이 "오프닝 중 한 번도 안 쓰인다" 고 한 것은 **오프닝에서만
스크립트 중첩이 얕았기 때문**이다.  `$5B80` · `$BFCF` · `$7FF1` · `$2311` 에 이어
같은 함정을 다섯 번째로 밟을 뻔했다.

> 규칙 (ARENA §7): **Write 를 못 봤다 != 안전.**

빌더 두 개에 정지 가드를 걸어 두었다 -- `$5B80-$5E3F` 를 주면 멈춘다.

#### 그런데 음성 중에는 그 704 B 가 통째로 빈다

```
probe_arena_0_1_5_voice.tsv — 음성 134 건 · 32167 프레임
  top_at_start / top_min / top_max   전부 $5B80    ← 깊이 0
  gap_min                            전부 704 B
```

**예외가 없다.**  자막은 음성이 나올 때만 뜨므로, 우리가 필요한 바로 그 구간에
자리가 비어 있다.  같은 파일의 `빌리면 그 대사에서 죽는다` 판정은 **프리로더
자리($5E40 위)** 에 대한 것이지 스택 구간이 아니다.

#### 그래서 설계는 "음성 중에만 빌린다"

`POC_SUBTITLE_ACTIVE_0.1.0.lua` 가 원래 이 설계였다.  그것이 맞았다.

```
음성 시작   $5B80-$5E3F 를 AC 에 백업 -> 엔진·스텁·글리프를 올린다 -> $601E 패치
음성 중     자막을 민다.  스택은 어차피 안 자란다
음성 끝     $601E 원복 -> RAM 을 바이트 단위로 되돌린다
```

**훅을 디스크에 영구히 박으면 안 된다.**  음성이 아닐 때 `JSR` 이 스택 데이터를
실행한다.  훅도 음성에 맞춰 심고 거둔다 -- Lua 가 매 프레임 하던 것을
**음성 단위(134 회)로** 하는 셈이라 부담은 오히려 적다.

남은 것: 음성 상태를 지켜보고 심고 거두는 **작은 감시자**를 어디 둘 것인가.
작으므로 헬퍼 여유 151 B 가 후보다.

#### 오늘 만든 것 중 살아남는 것

#### 참고 -- 오버레이 A 안에서 안 쓰는 구간 (73200 프레임)

오버레이에 상주해야 하는 코드가 생기면 쓸 수 있다.  다만 한 장면에 오래 머문
구간이 많아 사격 씬·세이브·엔딩을 지나면 더 깎인다.

### 9.3 오프닝의 한 순간만 예외로 둔다

**일반 대사는 스프라이트 그대로 간다 -- 이것이 결정이다.**
실측이 그것을 지지한다 (`PROBE_SPRITE_DURING_VOICE_0_1_0`):

```
ADPCM 재생 중      게임이 SATB 최대  4 칸    -> 60 칸이 논다.  어떤 길이든 된다
CD-DA 재생 중      평균 16.7 · 최대 63 칸
                   0-7:3464  8-15:707  16-23:265  24-31:2388
                   32-39:590 40-47:374 48-55:325  56-63:83
19 자가 들어가는 CD-DA 프레임   93.0%
```

빡빡한 5%(48~63 칸)는 **오프닝의 한 순간**에 몰려 있다.  정지 그림 하나가 떠 있고
그 뒤로 그림이 계속 움직이는 구간이다.  거기서 우리가 19 칸을 먼저 가져가면
게임은 45 만 받는다.

**일반화하지 않는다.**  정해진 시퀀스의 한 순간이므로 그 구간만 예외로 처리한다.
배경(BAT) 경로를 미리 만들 이유는 없다.

먼저 볼 것: 트랙 17 시험 자막이 이미 들어 있으므로 `PROBE_SUB_LIVE_0_1_1` 로
오프닝을 그냥 지나가면 된다.  **뒤 움직임이 눈에 띄게 상하는지 아닌지가 바로 나온다.**
숫자로는 "게임이 45 칸만 받는다" 까지만 알 수 있고 보기 싫은지는 봐야 안다.

```
안 티나면    조치 불필요.  이 절을 닫는다
티나면       그 한 순간만 글자 수를 줄이거나 배경으로 옮긴다
```

참고: `SUBTITLE_BREAKTHROUGH §5` 는 "오프닝은 스프라이트를 아예 안 켠다" 고
적었는데 실측과 어긋난다 -- 서로 다른 구간(타이틀 vs 내레이션)을 본 것으로 보인다.
