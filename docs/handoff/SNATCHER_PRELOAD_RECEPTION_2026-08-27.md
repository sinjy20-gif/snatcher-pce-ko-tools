1. **번역 전체와 자막 3종을 BIOS 부팅 구간에서 AC에 한 번만 선적재**

   - Lua `SUB 0.3.24`가 접수처에서 정확한 정상 패턴 `512 B`를 복구해 화면이 완전히 돌아오는 것을 확인했다.
   - 동일한 복구를 접수처 포인터에만 작동하는 네이티브 루틴으로 옮겨 `0.4.6.7`에 반영했다.

## 2. BIOS AC 선적재의 현재 확정 상태

기반 빌더:

```text
C:\snatcher\tools\build_snatcher_0_4_6_0.py
```

현재 동작:

```text
BIOS 첫 유효 게임 CD_READ
  -> Bank69 load_blob 확인
  -> translation_all 적재
  -> subtitle_pack 적재
  -> subtitle_helper 적재
  -> subtitle_renderer 적재
  -> 번역 팩 상태 00 01 02 게시
  -> 이후 장면 수요 적재 금지
```

AC 배치:

| 항목 | 목적지 | 크기 |
|---|---:|---:|
| translation_all | `$000000` | 1,124,416 B |
| subtitle_pack | `$1C0000` | 89,598 B |
| subtitle_helper | `$1F1C00` | 320 B |
| subtitle_renderer | `$1F1F00` | 671 B |

검증된 사항:

- 네 페이로드가 Track 24에서 AC로 byte exact 적재됨.
- 네 AC 범위는 서로 겹치지 않음.
- 코나미 빌딩 한글 표시 확인.
- 코나미 빌딩의 패치 페이로드 재적재 없음.
- 접수처까지 패치 페이로드 재적재 없음.
- 일반 게임 장면 데이터 CD 읽기는 정상적으로 계속 발생한다. 이것은 제거 대상이 아니다.

주의:

- 부팅 선적재는 약 1.2 MiB라 시작할 때 한 번 긴 적재가 있다.
- 이후 장면에서 사라진 것은 **패치 페이로드의 중복 적재**다.

## 3. 접수처 UI 깨짐의 확정 해결책

### 3-1. 증상

`0.4.6.6` 노스킵 경로에서 접수처 액션 메뉴의 선택 상자/글자 패턴이 깨졌다.

```text
노스킵 -> 깨짐
스킵   -> 정상
```

최종 문제 VRAM 범위:

```text
Mesen byte VRAM $2C00-$2DFF = 512 B
VDC word VRAM   $1600-$16FF = 256 words
```

### 3-2. 이미 성공한 Lua POC

```text
C:\snatcher\lua\SUB\0.3.24.lua
```

접수처 렌더러 포인터가 다음 값일 때만 무장한다.

```text
$3471/$3472 == $3499 또는 $349A
```

그 프레임이 끝난 뒤 스킵 경로에서 캡처한 정상 `512 B`를 복원한다.

사용자 런타임 확인 결과:

```text
원인 확정
제대로 돌아옴
```

따라서 추가 원인 추적은 중단하고 이 복구를 정식 해결책으로 채택했다.

### 3-3. `0.4.6.7` 네이티브 반영 구조

Track 02 Bank-6A:

```text
$66E5  JSR $FFD4
$66F8  JMP $683F        평상시 원본 종료
```

BIOS bank 0 트램펄린:

```text
$FFD4  JSR $5E40        기존 프리로더 동작 보존
       PHA              반환 A 보존
       MPR7 = bank $01
```

BIOS bank 1:

```text
$F054  접수처 가드/분기
$F07C  정상 512 B VDC 복구
```

접수처 포인터에서만 `$66F8`의 종료 목적지를 한 번 복구 루틴으로 바꾼다. 복구 루틴은 진입 즉시 `$66F8 -> $683F`를 되돌리므로 다른 대사나 장면에 지속되지 않는다.

BIOS bank 1을 사용한 이유:

- bank 0의 기존 부팅 로더는 `271/280 B`로 여유가 거의 없다.
- bank 1의 사용 지점은 빌드 시 전부 `$FF`인지 검사한 뒤에만 쓴다.
- `$5E40`은 bank 0이 매핑된 상태에서 먼저 호출한다.
- bank 전환 중인 코드는 IRQ 문맥에서 실행되며, 반환 전에 MPR7을 bank 0으로 복원한다.

```text

Track02 $66F8   4C 3F 68          JMP $683F
BIOS bank0      20 40 5E 48 A9 01 53 80
BIOS bank1 입구 4C 54 F0
BIOS bank1 복귀 53 80
BIOS bank0 계속 68 60             PLA / RTS
```

추가 통과:

- Track 02 수정 섹터 Mode-1 EDC/ECC 재생성.
- BIOS SHA-256 manifest 일치.
- Track 02 SHA-256 manifest 일치.
- 안정된 CUE/Track 파일명 유지.
- `0.4.6.7` BIOS 파일명에 버전 포함.

## 5. 다음 시작 시 딱 한 번 할 런타임 확인

아직 `0.4.6.7`의 네이티브 VDC 복구는 사용자 화면에서 최종 확인 전이다. 정적 검증은 끝났지만 런타임 성공을 미리 확정해서는 안 된다.

확인 순서:

1. `Syscard3_galmuri_0.4.6.7.pce` 선택.
2. `Snatcher CD-ROMantic (Japan) [KO].cue` Power Cycle.
3. `lua/SUB/0.3.29.lua` 실행.
4. **노스킵**으로 접수처까지 진행.
5. 액션 메뉴를 연다.

합격 로그:

```text
SUB 0.3.29 reception guard PASS ptr=$3499
SUB 0.3.29 ★ 0.4.6.7 REPAIR PASS: $2C00-$2DFF byte exact
```

화면 합격 조건:

- 접수처 액션 메뉴 위·아래 항목이 모두 정상.
- 선택 상자/글자 패턴 깨짐 없음.
- 첫 한국어 대사 정상.
- UI 진입과 복귀 정상.

실패하면 먼저 볼 곳:

1. `0.3.29`의 `mismatch=N/512 B`.
2. `$66F8`이 복구 후 `4C 3F 68`로 돌아왔는지.
3. VDC 쓰기 뒤 게임의 후속 업로드가 다시 `$2C00-$2DFF`를 덮는지.

성공하면 `0.4.6.7`을 오늘 작업의 기준판으로 확정하고 이 문제는 다시 추적하지 않는다.
