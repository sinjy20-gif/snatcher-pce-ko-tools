## 2. 원인 A — 원자적 블록전송 (수정 완료)

`build_ac_dynamic_0_1_14.py` 의 `copy_record` 가 704 B 레코드를 재구성할 때 608 B
템플릿을 **`TAI` 단일 명령**으로 옮기고 있었다. HuC6280 블록전송(`TAI`/`TII`/`TIA`/
`TIN`/`TDD`)은 원자적이라 **실행 중 인터럽트를 받지 않는다.**

```
608 B TAI = 17 + 6x608 = 3,665 사이클 = 8.05 스캔라인 인터럽트 차단
                                        (7.16 MHz, 스캔라인 455 사이클)
```

76 B x 8 로 분할해 차단을 **473 사이클(1.04 스캔라인)** 로 낮췄다.
`TEMPLATE_CHUNK` / 환경변수 `SNATCHER_TAI_CHUNK` (608 이면 원래 코드 그대로).

**분할은 바이트 무해하다.** AC 포트 `$1A00`/`$1A01` 은 같은 데이터 레지스터의 두
미러라 어느 경계에서 잘라도 읽히는 순서가 같다. 레코드 byte-exact 2329/2329 유지.

### 실측

```
0.3.3-base       재현 (기존과 동일)      TAI 608 x 1
0.3.3-irqsplit   빈도·강도 크게 감소      TAI 76 x 8
                 발생 지점이 위로 이동, 한글 자형 정상
```

두 디스크는 **Track 24 가 바이트 동일**하고 Track 02 헬퍼 코드만 다르다(664→713 B).

## 3. CD 경합은 원인이 아니다 (기각 근거)

한때 가장 유력했고, 코드 근거도 있었다. 기각 과정을 남긴다 — **다시 파지 말 것.**

### 3.1 발견됐던 기전 (사실이긴 하다)

`resident` 는 "미리 적재"가 아니다. 초기화는 디렉터리+상태+템플릿+아틀라스(13청크)
만 올리고 **모든 팩 플래그를 `$FF`(미적재)로 지운다** — `ui` 포함. `resident` 는
목적지 주소만 정한다. 그리고 `lookup` 은 슬롯의 `pack_id` 를 보고 미적재면
`load_package` → `load_blob` → **CD 읽기**를 한 뒤에야 `copy_record` 로 간다.
즉 빗나간 프로브가 남의 팩을 통째로 끌어올 수 있다.

### 3.2 실제로 게임이 CD 를 계속 읽고 있었다

`dump\ui_load_v11_180102.tsv` — 폐공장에서 **게임 자신이 13~14 프레임 주기로**
CD 를 읽는다(우리 코드가 안 도는 프레임들). 그리고 스트리밍 구간에 떨어진 우리
팩 적재 **5건이 5건 모두** 게임의 다음 읽기를 13 → 22~30 프레임으로 밀어냈다.

여기까지는 상관관계가 완벽했다. **그래서 틀렸다.**

### 3.3 선적재판으로 기각됐다

`SNATCHER_PRELOAD_PACKS=1` 로 팩 25개를 초기화 때 전부 올린 `0.3.3-preload` 를
만들었다(초기 적재 13 → 52 청크 + 3 섹터, 104 KB → 422 KB).

`dump\ui_load_v12_182900.tsv`:

```
packloads = 0    전 구간.  load_blob 한 번도 안 돎 = 선적재가 실제로 먹었다
cdreads   = 0    전 구간
그런데 버벅임    9회 그대로
```

**독립 방증**: 사용자가 에뮬레이터에서 CD 배속을 올려도 동일하게 끊겼다. CD 대역폭이
원인이면 반드시 완화됐어야 한다.

선적재판은 릴리스로 쓰지 않는다. 부팅 로딩만 4배로 늘고 증상은 그대로다.

## 4. 원인 B — 레코드 재구성 비용 (미수정, 다음 작업)

### 4.1 메뉴 한 화면이 레코드를 13건 재구성한다

같은 메뉴를 세 번 열었더니 패턴이 완전히 동일했다.

```
f977~f986    10프레임   레코드 13건   프레임별 [1, 3, 1, 1, 1, 3, 3]
f1585~f1595  11프레임   레코드 13건   [1, 3, 1, 1, 1, 3, 3]
f2166~f2175  10프레임   레코드 13건   [1, 3, 1, 1, 1, 3, 3]
```

프레임당 비용:

```
레코드 1건 -> 10~17 스캔라인
      2건 -> 19~33
      3건 -> 29~50      <- 한 화면에 이런 프레임이 3개
```

원인 A 의 `TAI` 하나가 **8 스캔라인**으로 눈에 띄었다. 지금은 **연속 10프레임 동안
매 프레임 10~50 스캔라인**을 먹는다. "UI 항목이 많을수록 심하다"는 사용자 관측이
정확히 이것이다 — 항목 수 = 레코드 수 = 방해받는 프레임 수.

### 4.2 비용의 86% 가 낭비다

레코드 1건 최소 4,377 사이클 중:

```
608 B 템플릿 재복사   3,784 사이클  86%   <- 매 레코드 똑같은 상수 데이터
96 B 텍스트             593 사이클  14%
글리프 (쓴 만큼)     0~3,135 사이클
```

템플릿의 상수 슬롯(마침표·공백·말줄임표 + 헬퍼 슬롯 = 128 B)은 영원히 안 변하고,
나머지 480 B 는 사실상 "안 쓸 슬롯 비우기"다. 그런데 매번 608 B 전체를 AC 에서
다시 긁는다.

### 4.3 이 비용은 장면과 무관하다 — 폐공장은 "드러나는" 곳일 뿐

사용자 가설이고, 근거가 있다. 헬퍼는 장면을 모른다. 같은 메뉴면 본부에서도 레코드
13건을 똑같이 재구성한다. **다른 것은 게임 쪽 여유다.**

게다가 PCE 에서는 스프라이트가 많을수록 VDC 가 VRAM 을 더 오래 점유해 **CPU 가 실제로
느려진다.** 위 사이클 추정치는 VDC 경합이 없다는 가정이므로, 번개 연출과 스프라이트가
몰린 폐공장에서는 같은 작업이 **더 많은 스캔라인**을 차지한다. 즉 폐공장은 원인이
아니라 증폭기다.

이 가설은 "본부는 정상"을 **본부에 다른 코드 경로가 있다고 가정하지 않고** 설명한다.
기존 인계서가 "폐공장 고유 리소스/전송 경로와의 충돌"을 우선 검토하라고 했던 방향은
이 지점에서 불필요해진다.

확인 방법은 싸다. **본부에서 같은 메뉴를 열고 `PROBE_UI_LOAD` 를 돌려 `copies` 패턴을
비교한다.** 13건 / `[1,3,1,1,1,3,3]` 이 똑같이 나오는데 눈에는 안 보인다면 확정이다.

수정 목표도 여기서 정해진다 — 비용을 0 으로 만들 필요는 없고, **폐공장의 여유 아래로**
내리면 된다.

### 4.4 수정 방향

```
상수 슬롯 4개    초기화 때 한 번만            레코드당 -768 사이클
빈칸 처리        직전에 쓴 슬롯만 지움          레코드당 -2,000~2,800 사이클
                 (2바이트 비트맵, 글리프 루프에 합침)
```

예상 4,377 → **1,000~1,600 사이클**. 3건 프레임이 29~50 → **7~11 스캔라인**.

**제약: 헬퍼 여유 68 B** (713/814 사용). 안 들어가면 8분할 `TAI` 를 루프로 바꿔
자리를 만든다(약 -35 B).

### 4.5 적용 결과 — `0.3.3-glyphopt` (2026-08-14)

**한 번의 전송이 상수 복원과 빈칸 처리를 겸하게 했다.** 템플릿은 상수 슬롯 0-2 →
빈 슬롯 3-17 → 헬퍼 슬롯 18 순으로 연속이므로, 시작점에서
`96 + (직전 레코드의 글리프 수) x 32` 바이트만 옮기면 상수는 복원되고 직전에 쓴
슬롯만 지워진다. 최장 런은 96 + 15x32 = 576 으로 슬롯 18 바로 앞에서 멈춘다 —
헬퍼 글리프는 이미지의 초기 길이 608 이 한 번 써 주고 이후 건드리지 않는다.

```
템플릿 전송   608 B 고정  ->  96 + 직전글리프수 x 32
레코드 비용   6글자 5,631 -> 3,829 사이클 (-32%)
              3글자 5,201 -> 2,626 (-50%)
3건 프레임    29~50 -> 20~33 스캔라인
helper        713 -> 712 B (여유 70).  코드가 오히려 줄었다
Track 24      irqsplit 과 바이트 동일 -- 순수 코드 변경
```

상태는 스크래치 3바이트(`TPL_LO`/`TPL_HI`/`FILLED`)뿐이다. 글리프 루프가 슬롯 17
에서 내려오므로 **첫 번째로 채운 슬롯이 가장 높은 슬롯**이고, 런이 조밀하다는 것이
빌드에서 보장되므로(구멍 있으면 빌드 실패) 그 한 번만 기록하면 범위가 정확하다.

**실측**: 사용자 확인 "확실히 좋아졌다".

**남은 검증**: 긴 대사 직후 짧은 UI — 지우는 범위가 틀리면 여기서만 잔상이 난다.

### 4.6 다음 후보 — 전역 글리프 슬롯

슬롯 번호는 **레코드 로컬 인덱스**이고 레코드 텍스트에 빌드 시점에 박힌다
(`SLOT_COUNT_PER_RECORD = 19`, 로컬 15개, 초과 시 빌드 실패). 따라서 "이미 올린
글리프를 계속 유지하는" 지속 캐시는 런타임 슬롯 재배치가 필요한 **다른 설계**이지
최적화가 아니다.

다만 상수 슬롯 3개는 이미 지속 캐시다. 이걸 넓히는 것은 가능하다.

```
지금   상수 3 + 로컬 15 + 헬퍼 1
가능   상수 3 + 전역 N + 로컬 (15-N) + 헬퍼 1
       전역 N = 전체 대본에서 가장 흔한 글자 N개를 빌드 때 고정 배정
```

전역 슬롯은 레코드마다 복사도 빈칸 처리도 필요 없다. 대가는 **레코드 하나에 쓸 수
있는 서로 다른 글자 수**가 15 → 15-N 으로 줄어드는 것이다.

#### 실측 결과 — 이 방향은 닫혔다 (2026-08-14)

출하 레코드(검토 O) 3,137건 = BODY 2,161 + UI 976 을 세었다.

```
레코드당 고유 한글 분포
  0자 237 · 3자 284 · 6자 208 · 9자 303 · 12자 156 · 13자 153 · 14자 61 · 15자 5
```

**이미 한계(15)까지 차 있다.** 여유가 0 이므로 슬롯을 떼면 즉시 터진다.

```
N   전역 슬롯       로컬 여유   초과 레코드   최악 필요
0   -                  15           0          15
1   이                 14           3          15
3   니다이              12          91          15
6   가는니다이지          9         492          14
```

**전역 슬롯 하나에 3건, 셋에 91건, 여섯에 492건이 한계를 넘는다.**

원인은 한국어의 음절 다양성이다. 3,137 레코드에 고유 한글이 735자이고, 가장 흔한
"이" 조차 744건(24%)에만 등장한다("다" 17%, "니" 15%). **어느 글자도 레코드의
과반에 없다.** 전역 슬롯의 비용("그 자리를 못 쓴다")은 모든 레코드가 치르는데
이득은 그 글자를 쓰는 소수만 받는다 — 빈도가 높다는 직관은 *글자 단위*로는 맞고
*레코드 커버리지* 로는 틀렸다.

레코드별로 "전역 모드 / 전량 로컬 모드" 를 섞는 것도 성립하지 않는다. 전량 로컬
레코드가 전역 슬롯을 덮어쓰므로 다음 전역 모드 레코드가 다시 채워야 하고, 이득이
사라진다.

**따라서 남은 지렛대는 글리프 슬롯 쪽이 아니다.** 인접한 것들도 작다 — 텍스트 96 B
(593 사이클)와 인덱스 30 B(197)는 이미 최소이고, 글리프 전송은 6 사이클/바이트로
블록전송의 하한이다. 실질적으로 남은 것은 "언제 하느냐"(화면 분할이 바뀌는 프레임을
피해 작업을 배치) 하나뿐이고, 그것은 런타임 상태가 늘어나는 구조 변경이다.

**참고**: `$5B80-$5E3F` 캐시를 실패한 조회도 덮어쓴다는 주석은
`build_direct_overlay_patch_ui.py` 의 것으로, CD 섹터를 직접 읽던 옛 설계 이야기다.
AC 빌드에서 이 영역의 유일한 기록자는 헬퍼의 `copy_record` 다.

## 4.7 최종 상태 (2026-08-14 마감)

**남길 빌드는 `0.3.3-safe` 다.** = TAI 분할 + 팩 선적재 + 경계 지우기.

```
레코드당      5,631 -> 3,829 사이클
인터럽트 차단  8.05 -> 1.04 스캔라인
재생 중 CD    팩마다 1회 + 탐색 2회 -> 0
```

### 폐기한 실험과 그 이유 — 다시 시도하지 말 것

`noblank` / `both` / `lean` / `lean2` 는 **빈칸 처리를 없앤 계열이고 잔상이 난다.**
실측으로 확인됐다(폐공장, "폐공장? 내부로 들어왔습니다" 의 첫 글자가 이전 줄의
글자로 남음).

기전은 빌더에 있다.

```python
while used and used[-1] == blank: used.pop()   # 끝쪽 빈 글리프를 버린다
```

원본 레코드가 **끝쪽 슬롯을 빈 글리프로 참조**하는 경우가 있다. 그 슬롯은 압축
레코드에 `FFFF` 로 남아 글리프 루프가 건너뛴다. 템플릿 복사가 있을 때는 그 자리가
0 이라 빈칸으로 정확히 그려졌지만, 지우지 않으면 **직전 레코드의 글자가 남는다.**

경계 지우기(`0.3.3-safe`)는 직전 레코드가 쓴 만큼을 지우므로 이 경우를 정확히
덮는다. `lean2` 의 상수 센티널 자가 복구는 **상수 슬롯만** 보므로 이 잔상을 못 잡는다.

빈도가 낮아서 짧은 시험에서는 안 보인다 — `both` 에서 "잔상 없음" 으로 넘어갔던 것이
그 예다. **짧은 관측으로 무해하다고 결론내지 말 것.**

### 남은 증상

산발적으로 남아 있고, **음성 재생이 방아쇠**다.

```
음성 전   10회 중 약 3
음성 후   10회 중 약 9    그리고 되돌아오지 않는다
```

게임이 음성 재생 이후 프레임 예산을 잃는 것으로 보인다(ADPCM 서비스/폴링 지속).
우리가 게임 동작을 바꿀 수는 없으므로 지렛대는 우리 비용을 더 줄이는 것뿐인데,
안전하게 줄일 여지는 이번에 대부분 썼다.

**이것은 버그가 아니라 예산 문제다.** 깨짐·오염·진행 불가 없음. 폐공장처럼 번개와
스프라이트가 많아 게임 쪽 여유가 적은 장면에서만 드러난다.

다음에 다시 판다면 순서는 이렇다.

```
1. lua\PROBE_ADPCM_STATUS_0.1.1.lua 로 음성 전후 폴링량 비교
   -> 예산이 정말 줄어드는지, 얼마나 줄어드는지 숫자로 확인
2. 4.6 의 전역 글리프 슬롯 (대본 통계부터, 빌드 불필요)
3. 그래도 남으면 "언제 하느냐" -- 화면 분할이 바뀌는 프레임을 피해 작업 배치.
   구조가 커지므로 최후 수단
```

## 5. 도구

```
lua\PROBE_UI_LOAD_0.1.1.lua   0.3.3-irqsplit 전용.  팩 id 까지 찍는다
lua\PROBE_UI_LOAD_0.1.2.lua   0.3.3-preload 전용.  스캔라인 눈금 + E 키 마커
build\patch\<ver>\helper_symbols.json   빌더가 남기는 헬퍼 심볼.  프로브 주소의 출처
```

**디스크를 다시 빌드하면 헬퍼 심볼이 움직인다.** 프로브의 주소 블록을
`helper_symbols.json` 과 대조해 갱신할 것. 0.1.1 과 0.1.2 의 주소가 1씩 다른 것이
그 예다(헬퍼 713 → 714 B).

### 프로브 작성 시 함정 두 개

```
F5 를 마커로 쓰지 말 것    Mesen 의 세이브 스테이트 저장 키와 겹친다
나눗셈 결과에 %d 금지      Lua 5.4 는 정수 표현이 없는 실수를 거부한다.  %.0f 를 쓸 것
```

## 6. 빌드

```
0.3.3-base        기준 (TAI 608 x 1)          재현됨
0.3.3-irqsplit    원인 A 수정 (TAI 76 x 8)     현재 기준
0.3.3-preload     CD 기각용 실험               릴리스 아님
```

**빌드 정리 규칙**: `--prune` 은 허용목록 방식으로 바뀌었다. 지울 빌드를 이름으로
직접 대야 하고, 아무것도 기본으로 지워지지 않는다. `PROTECTED` 는 이름을 대도
거부한다. 소유자가 실험용이라고 명시한 빌드 외에는 어떤 빌드도 지우지 않는다.
