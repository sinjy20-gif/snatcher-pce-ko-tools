## 0. 한 줄 요약

"한글이 한 자도 안 나온다" 의 원인은 폰트도 배정표도 아니었다.
**아틀라스가 0 이 되면서 AC 블롭 기준점이 `$4000` 어긋났다.**
`0.4.5.2` 가 정식이고 한글이 정상 출력된다.

## 1. 진짜 원인 — `init_total` 이 바닥값 아래로 떨어졌다

`build_ac_dynamic_0_1_14.py:127` 이 스스로 적어둔 불변식이 있다.

```
Disc image is directory + init_extra + blob and the blob's offset equals
init_total, while common_data_base resolves to init_total as well
-- disc offset and AC address coincide.
```

그런데 627 행이:

```python
common_base = max(dynamic.COMMON_DATA_BASE, init_total)   # 바닥값 $16000
```

`max()` 는 **아틀라스가 너무 클 때**만 막아준다.  BIOS 폰트 경로가 아틀라스를
retire 하면서(0 글리프 · 0 B) `init_total` 이 사상 처음으로 바닥값 아래로
떨어졌고, 그때부터 이미지의 blob 위치와 디렉터리가 가리키는 AC 주소가 갈렸다.

```
이미지 blob 실제 위치   $12000   (SDR4 2,509 개가 96 B 간격으로)
디렉터리가 가리키는 곳   $16000   -> AC 에 00 00 00 00
차이                    $4000
```

### 증상이 이렇게 이어진다

```
copy_record 는 정상으로 돈다 (AC -> 캐시)
그런데 읽어온 자리가 비어 있어 캐시가 전부 0
프리로더 $5F3B 의 매직 검사('SDR4')에서 즉사
$03/$04 가 원문을 계속 가리킨다 -> **일본어가 그대로 나간다**
```

### 왜 0.3.11-bios 는 나왔나

그때는 아틀라스가 1,115 자(35,680 B)라 `init_total` 이 `$1A000` 이었다 --
바닥값 위다.  **회귀는 BIOS 폰트 작업이 아니라 "아틀라스 0" 최적화(`-opt`)가
들여왔다.**  0.3.9 까지의 모든 정식 빌드는 자기정합이다 (blob `$1A000`).

### 고친 방법

바닥값이 이기면 init 적재를 거기까지 늘린다.  0.3.9/ac_0.1.14 는 이미
`init_total` 이 max 를 이기므로 **byte-exact 재현이 깨지지 않는다.**

```python
if init_total < common_base:
    init_total = align(common_base, CHUNK_BYTES)
    init_extra_bytes = init_total - DIRECTORY_BYTES
    build_packs_compact.init_chunks = init_total // CHUNK_BYTES
    build_packs_compact.init_extra_bytes = init_extra_bytes
    common_base = init_total
    dynamic.COMMON_DATA_BASE = common_base
assert init_total == common_base
```

```
initial CD load  38 chunks -> 41 chunks + 2 sectors
디렉터리 어긋난 엔트리  2,509 -> 0
```

## 2. 어떻게 찾았나 -- 네 겹 프로브

육안·추측 없이 층을 하나씩 벗겼다.  다시 팔 때 이 순서를 그대로 쓰면 된다.

```
PROBE_FONT_ADDR_0.1.6      EX_GETFNT 202 회 · **한글코드 0 회** · 82/83(가나) 111 회
                           -> 폰트가 아니다.  렌더러가 일본어를 그리고 있다
PROBE_RECORD_PATH_0.1.0    init_ok · lookup -> valid -> copy_record 전부 정상
                           -> 레코드는 캐시에 실린다.  치환 자체는 돈다
PROBE_PRELOADER_0.1.0      slot_loaded 33 · **캐시 매직 00 00 00 00** · sig 0
                           -> 매직에서 즉사.  캐시에 0 이 들어온다
정적 대조                   이미지 SDR4 $12000 vs 디렉터리 $16000
                           -> $4000.  여기서 끝
```

`copy_record` 가 도는 것과 렌더러가 그것을 **받아들이는 것**은 다른 단계다.
프로브를 헬퍼에만 걸면 "정상" 으로 보인다.  프리로더의 서명 검사까지 봐야 한다.

## 3. 배정표 생성기 재작성 (`tools\build_bios_hangul_map.py`)

### 3.1 출하되는 한글을 다 세지 않고 있었다

`needed_hangul()` 이 `snatcher_ko_master.tsv` 하나만 읽었다.  UI 라벨·화자
이름·구형 정적 문자열의 **한글 69 자(등장 118 회)** 가 배정 없이 남아 산술
폴백으로 떨어졌고, 그대로 한자로 출력됐다.

```
몽타주 -> 功타주 · 얼굴 윤곽 -> 얼굴 星곽 · 암시장 -> 章시장
마츠다히로시 -> 마苧다히로시 · 뉴욕 -> 뉴水
```

이제 네 파일을 다 읽되 **출하되는 행만** 센다.  검수 규칙은 빌더와 같은 모듈을
그대로 부른다 (`layout.reviewed_row_ids` / `ui_review_column` / `is_ui_reviewed`).
규칙이 갈라지면 배정표와 디스크가 어긋나고, 그게 오늘 하루를 태운 종류의 버그다.

```
전부 세면 995 자 -> 빈 칸 966 을 넘어선다
출하분만  769 자 -> 들어간다
```

### 3.2 "게임이 안 쓰는 칸" 을 정적으로는 다 못 안다

`鎧`(8A5A, idx 761)가 배정돼 있었는데 프로브가 게임이 그리는 것을 관측했다.
그런데 그 글자는 **우리 추출 코퍼스 어디에도 없다** (jp_text·jp_name·source_hex
전부 0 건).  원본 Track 02 의 FF-종결 문자열 스캔으로도 안 잡힌다.
MODE1 데이터 트랙은 Track 02 하나뿐이라 더 훑을 데도 없다.

그래서 근거를 세 겹으로 쌓는다.

```
TSV 코퍼스 4 개            1,588 글리프
원본 Track 02 FF-종결 스캔   +275     (노이즈 제거: FF 로 끝나는 런만, FD/FE 허용)
런타임 관측                 +1       build\bios_font\observed_used.tsv
                          = 1,864
```

`observed_used.tsv` 가 유일하게 확실한 출처다.  플레이 중 엉뚱한 한자가 보이면
PROBE_FONT_ADDR 로 코드를 잡아 한 줄 더하고 배정표 -> BIOS -> 디스크를 다시 만든다.

### 3.3 충돌한 기존 배정은 옮긴다

"이미 배정된 글자는 안 옮긴다" 규칙에 예외를 뒀다.  그 자리가 "게임이 쓴다" 로
새로 밝혀지면 옮긴다 (126 자 재배정).  BIOS 도 디스크도 이 표에서 매번 다시
나오므로 둘을 같이 만들면 정합이 유지된다.

## 4. ★ BIOS 와 디스크는 이제 한 쌍이다

**섞으면 안 된다.**  오늘 실제로 당했다 -- 배정표를 바꿔 BIOS 를 다시 굽고
Firmware 를 덮어쓴 뒤, 소유자가 **옛 디스크(0.4.2)** 를 돌렸다.

```
안으로 들어阿虻요.  悟제든 블鎌스터를 쓸 존비를 해두勲요!
```

재배정된 126 자만 어긋나서, 멀쩡해 보이는데 군데군데 한자가 박힌다.
"거의 맞는데 몇 자만 틀림" 은 **배정표 불일치의 지문**이다.  폰트 버그로 오해하기 쉽다.

```
배정표를 바꾸면   배정표 -> BIOS -> **전체 빌드** -> 2 단계   넷을 다 다시
--stage3 로는 안 된다   텍스트 인코딩은 스테이지 1/2 에서 나온다
```

## 5. 15자 제한과 새 상한

**레코드당 15자 제한은 없어졌다.**  아틀라스 글리프 슬롯 19 칸을 채우던 구조의
제약이었고, BIOS 폰트 경로는 슬롯을 안 쓴다 (`atlas 0 glyphs, 0 B`).

대신 성격이 다른 상한이 생겼다 -- 게임 전체에서 쓸 수 있는 **서로 다른** 한글 자수.

```
한자 행(0x30~0x47) 총 글리프   2,256
게임이 쓰는 것으로 확인된 자리   1,864
현재 배정                       779
남은 빈 칸                      187
```

자막이 들어오면 여기가 다음 벽이다.  그때는 행 0x21/0x22/0x24/0x25(기호·가나)의
빈 칸을 열면 400 칸 가까이 더 나오지만, 그 행들은 게임이 훨씬 자주 쓰므로
관측 근거를 더 쌓은 뒤에 손대는 것이 맞다.

## 6. BIOS 폰트 경로 -- ROM 코드로 확정한 것

추측이 아니라 `$F151`~`$F190` 을 읽어서 역산했다.

```
$F17D  bit0($FF)=0 -> idx<<5  (x32)      $F188  $EE += ($FF<<1)|1
$F15E  bit0($FF)=1 -> idx*9<<1 (x18)     => base = ((($FF<<1)|1) << 16)

    16x16 -> $010000        12x12 -> $030000
```

```
게임이 타는 경로   12x12 ($FF=$01).  PROBE_FONT_ADDR_0.1.5 실측:
                  $F2CD 3,132 회 · $F1BA 0 회 · base12 $030000 수렴
행 0x28~0x2F      **BIOS 가 거부한다** ($F22F/$F231 `CMP #$30 / BCC`)
                  -> 이전 판의 SAFE_ROWS 는 성립하지 않는 선택지였다
행 0x48~0x4F      행표 압축 때문에 0x40~0x47 의 별칭.  새 공간이 아니다
12x12 테이블      일본 원본 BIOS 에도 $030000 에 그대로 있다 (해태 전용이 아니다)
```

## 8. 밀림 실험 -- 중단 지점

### 8.1 만들어 둔 것

헬퍼에 **런타임 조절 가능한 지연 손잡이**를 넣었다.  값을 바꿀 때마다 굽지 않는다.

```
BE57  A0 nn     LDY #n      <- nn 이 $BE58.  Lua 가 이 한 바이트만 덮어쓴다
BE59  F0 08     BEQ $BE63   n=0 이면 통째로 건너뛴다 = 정식 빌드와 동일
BE5B  A2 00     LDX #0      <- 바깥 루프 (render_delay_outer).  여기를 세면 실행 확인
BE63  48        PHA         <- 지연 끝 (render_delay_done)

단위   1 회 = 256 x (DEX 2 + BNE 4) ~= 1,536 cycle ~= 3.4 스캔라인
빌드   SNATCHER_RENDER_DELAY_SLOT=1  (기본 꺼짐 -- 정식 빌드 바이트는 그대로)
디스크 build\patch\0.4.7-delayslot\...(0818-2130).cue
```

### 8.2 계측기는 정상이다 (검증 완료)

`DELAY_VERIFY_0.1.0` 실측, 32 구간 전부 일치:

```
want   calls  iters/call  byte_seen   occ_avg    occ_max
0        12      0.0          0        4.3 라인   4.9
72       23     72.0         72      284.6 라인  289.1
```

지연은 설계대로 완벽하게 돈다.  "루프가 안 돈다" 는 내 추측이었고 **틀렸다.**
`DELAY_SWEEP_0.2.1` 의 표는 고장난 계측이 아니라 **진짜 결과다.**

### 8.3 그래서 나온 것 두 개

**(1) BIOS 모드의 우리 점유는 4.2 라인이다.  12.3 이 아니다.**

```
SNATCHER_FLICKER_ELIMINATION §0 (아틀라스 시절)   12.3 라인   608 B 템플릿 + 글리프 슬롯
DELAY_VERIFY_0.1.0 실측 (BIOS 모드)               4.2 라인   96 B 압축 레코드 · 글리프 0
```

**1/3 로 줄었다.**  밀림이 눈에 안 띄게 된 것이 이 숫자로 설명된다.
§0 의 12.3 은 이제 옛 수치다 -- 그 문서를 인용할 때 같이 고칠 것.

**(2) 286 라인을 태워도 스크롤 갱신은 꿈쩍도 안 한다.**

```
지연 72 = 호출당 286 라인 -- **한 프레임(262 라인)보다 길다**
8 초에 73 회 호출 -> 480 프레임 중 80 프레임어치를 CPU 가 멈춰 있었다
그런데 samples 는 전 구간 정확히 5269 · >40 은 정확히 1436
```

CPU 가 멈췄는데 갱신 횟수가 자리 하나 안 변한다면, 그 갱신은 **CPU 메인 루프가
아니라 인터럽트에서 나온다.**  우리 지연 루프는 IRQ 를 막지 않으므로 래스터 IRQ 는
그 와중에도 계속 들어온다.  `overlap` 12~21 (헬퍼가 도는 중에 들어온 갱신)이
정확히 그 그림이다.

그러면 §0 의 *"우리 점유가 게임의 래스터 갱신을 밀어낸다"* 가 **이 계측으로는
재현되지 않는다.**  §0 은 "게임이 폴링으로 갱신한다" 고 적었는데, 폴링이면 CPU 를
뺏겼을 때 밀려야 한다.

### 8.4 다음에 할 것 -- 갱신이 IRQ 인지 폴링인지 (소유자 지정)

**스크롤/VDC 갱신을 실행하는 PC 가 IRQ 진입 후에 호출되는지 확인한다.**
스택 포인터로 정확히 갈린다.

```
1. 벡터를 읽는다 (HuC6280.  $E000-$FFFF 는 MPR7 -- 그때 매핑된 뱅크를 본다)
       $FFF6 IRQ2   $FFF8 IRQ1(VDC)   $FFFA TIMER   $FFFC NMI   $FFFE RESET
   ★ 이 배치는 6502 와 다르다.  읽어서 로그에 찍고 시작할 것 -- 외워서 쓰지 말 것
2. 각 핸들러 진입 주소에 exec 훅.  진입 순간의 cpu.sp 를 irqSP 로 기억
3. 스크롤 쓰기 6 개($43F7 $43FD $4408 $440E $E428 $E42B)에 exec 훅
4. 쓰기 시점의 cpu.sp <= irqSP 이면 **핸들러 안**, 아니면 메인 루프
   보강: 마지막 IRQ 진입 이후 경과 사이클도 같이 본다 (한 프레임 이내인지).
   두 신호를 따로 찍어서 서로 맞는지 본다 -- 한 지표만 믿지 않는다
5. 스택도 몇 건 덤프한다.  PCE 스택은 $2100-$21FF (MPR1=$F8 이 $2000 에)
```

```
IRQ 안이면    §0 모형을 고쳐야 한다.  점유로는 갱신을 못 민다는 뜻이고,
              0.4.6 에서 본 "심해짐" 은 하늘 경계 밀림이 아니라 전반적 버벅임일 수 있다
폴링이면      계측이 왜 안 움직였는지를 다시 봐야 한다 (훅 주소·집계 방식)
```

**착수 조건: 이것부터.**  §8.7(아래 "함정") 의 구조 변경은 이 답이 나오기 전에는 시작하지 않는다.

### 8.5 계측 실패 -- 반복하지 말 것

```
emu.isKeyPressed("0")    Mesen 키 이름이 아니다.  프레임마다 "Invalid key name"
                         -> 후보를 pcall 로 찔러 **불리언을 돌려준 것만** 채택
`scanline` 키 자동탐색    `vce.scanlineCount` 가 잡혔다 -- 현재 위치가 아니라 **총 줄 수(상수)**
                         상수끼리 빼서 간격이 늘 0.  "밀림 0" 은 결과가 아니라 고장이었다
                         -> 위치는 `cpu.cycleCount` (1 라인 = 455 cycle).  키를 박아 쓴다
"가만히 켜두면 된다"       헬퍼는 글자를 그릴 때만 돈다.  가만히 있으면 점유 0 · 지연값도 안 써짐
                         -> **메뉴를 계속 열었다 닫았다** 해야 한다.  화면에 `헬퍼 N 회` 를 띄워 둠
```

임계값을 미리 정하고 세지 않는다.  0.2.0 은 "14 줄 넘으면 밀림" 이라고 정해놓고
셌는데 실제 간격 분포를 본 적이 없었다.  0.2.1 은 분포를 통째로 낸다.

### 8.6 ★ 안드로이드 Beetle PCE 에서는 밀림이 안 난다 (소유자 실측)

소유자가 안드로이드의 **Beetle PCE(mednafen)** 로 돌려보니 폐공장 밀림이
**발생하지 않았다**.

이것이 §8.3 의 계측과 앞뒤가 맞는다.  우리가 286 라인을 태워도 스크롤 갱신
간격이 자리 하나 안 움직였고(갱신이 IRQ 로 들어오기 때문), 그렇다면 "우리 점유가
갱신을 민다" 로는 밀림을 설명할 수 없다.  다른 에뮬에서 안 난다는 것은
**밀림이 Mesen 쪽 타이밍 재현 차이일 가능성**을 크게 올린다.

다만 단정하면 안 되는 이유도 있다.

```
(가) Mesen 고유 현상        -> 실기·다른 에뮬에서 안 난다면 고칠 것이 없다
(나) Beetle 이 못 잡는 것    -> 정밀도가 낮아 1 줄 밀림을 안 재현할 수도 있다
(다) 조건이 달랐다           -> 안드로이드에서 돌린 디스크·BIOS 가 같은 판이었나
                              화면 크기·스케일링 때문에 1 줄이 안 보였을 수도 있다
```

**다음에 확인할 것 (싸다)**

```
1. 안드로이드에서 돌린 것이 어느 빌드·어느 BIOS 였는지 확인
2. 같은 디스크·같은 BIOS 를 Mesen 과 Beetle 에 각각 물려 같은 장면 비교
3. 그래도 갈리면 -> Mesen 쪽 문제로 보고 이 건을 닫는다
```

이 결과가 (가)로 굳으면 §8.4(IRQ/폴링 판별)와 §8.7(구조 변경)은 **둘 다 필요
없어진다.**  그래서 §8.4 보다 이 확인이 먼저다.

### 8.7 함정 -- "VBlank 까지 기다렸다가 작업" 은 안 된다

```
기다리는 것도 CPU 점유다.  라인 40 에서 VBlank(라인 240)까지 스핀하면
그 200 라인 동안 게임의 스크롤 갱신을 통째로 막는다.  지금보다 나쁘다.
```

안전 구간 배치는 스핀이 아니라 **VBlank 핸들러에서 작업하는 구조 변경**이라야
하고, 그건 런타임 상태 증설이 따라온다 (헬퍼 여유 139 B).  §8.3 이 끝나기 전에는
착수하지 않는다.

## 13. 조이 디비전 "쇼핑하기" 진행 불가 — 해결됨, 원인은 §15 (2026-08-19 기록)

> **★ 2026-08-20: 해결.** 이 절의 가설 열두 개는 전부 증상을 본 것이었다.
> 진짜 원인과 수정은 **§15** 에 있다.  아래 내용은 기록으로만 남긴다.

**증상**: 조이 디비전 상점에서 `쇼핑하기` 를 누르면 즉시 정지.  화면은 전환 도중

### 13.1 사망 형태

`PROBE_CRASH_WATCH_0.1.4` 자동 감지 (I/O 페이지 실행 순간):

```
PC $0041 (I/O 페이지) · SP $D4 · MPR FF F8 68 6A 6B 6C 6D 00
ZP $03/$04 = $A001          렌더러 원문 포인터.  정상은 $34xx/$36xx
```

BRK 가 IRQ2 벡터를 쓰므로 IRQ2 진입이 236,274 회까지 올라간다 -- 그 숫자와
$2200 오염은 전부 **폭주의 결과**이지 원인이 아니다.

늦게 뜬 덤프의 스택은 이미 0 으로 덮여 쓸모가 없다.  **자동 감지분만 증거가 된다.**

## 15. ★ 조이 디비전 「쇼핑하기」 크래시 -- 원인 확정 (2026-08-20)

§13 은 미해결로 닫혀 있었다.  **정적 분석만으로 끝까지 잡혔다.**  런타임 추측이
아니라 디스크에서 읽은 코드다.

### 15.1 한 줄

게임에는 `$5C00` 에서 **위로 자라는 범프 할당기**가 있다.  우리 프리로더는
`$5E40-$5FFF` 다.  쇼핑 화면은 그 할당기를 `$5E43` 까지 밀어올린다.
프리로더 첫 바이트가 지워지고, 다음 `JSR $5E40` 이 `BRK` 를 밟는다.

### 15.2 할당기 -- 상주 엔진 bank $68 안에 있다

    $4880  A9 00      LDA #$00
    $4882  85 25      STA $25
    $4884  A9 5C      LDA #$5C     <- 아레나 바닥 = $5C00
    $4886  85 26      STA $26

`$25/$26` 을 올리는 것은 `$8AEC` (ADC), 내리는 것은 `$8AF8` (SBC).
소유자가 `$2025/$2026` 감시에서 **접수처부터 계속 적중**한 이유가 이것이다.
조이 디비전 전용 변수가 아니라 **엔진 전역 할당 포인터**다.

### 15.3 실제로 덮어쓴 코드 -- 씬 뱅크, Track 02 섹터 339, CPU $8000

`$825A` 를 정적으로 찾아냈다.  `92 7E` (STA ($7E)) 가 섹터 선두 +$25A 에 오는
곳은 전 트랙에서 **한 군데뿐**이다.  객체 필드 초기화 루틴이고, 같은 틀이
`N = 1,2,3,4,5...` 로 반복된다.

    LDA #$03 / STA $80
    LDA $25  / STA $7E
    LDA $26  / STA $7F
    LDA $7E  / SEC / SBC $80 / STA $7E      ; ptr = base - 3
    LDA $7F  / SBC #$00      / STA $7F
    LDA #$00
    $825A  92 7E   STA ($7E)                ; <- 여기서 죽었다

`base - 3 = $5E40` 이므로 그 순간 `$25/$26 = $5E43`.

### 15.4 Mesen 이 보여준 `[$5E40] = $DA` 의 정체

**$DA 는 쓰인 값이 아니다.  우리 프리로더의 첫 명령 `PHX` 다.**

    $5E40  DA        PHX      <- 여기가 지워진다
    $5E41  5A        PHY
    $5E42  A2 05     LDX #$05

Write breakpoint 가 **쓰기 직전**에 멈춰 그 자리의 현재 값을 보여준 것이다.
그래서 우리 프리로더가 그 시점까지 멀쩡했다는 것도 같이 증명된다.

### 15.5 왜 쇼핑에서만 -- 3 바이트 차이

    아레나가 쓸 수 있던 공간   $5C00-$5E3F   576 B
    쇼핑 화면이 요구한 크기    $5C00-$5E42   579 B
    ------------------------------------------------
    모자란 양                                  3 B

다른 UI 는 579 B 를 안 쓴다.  그래서 안 죽었다.  원판은 `$5C00-$5FFF` 1,024 B
를 통째로 쓰므로 여유가 445 B 남는다.  **원판이 멀쩡한 이유가 이것이다.**

### 15.6 왜 열두 개 가설이 전부 빗나갔나

전부 **증상**을 보고 있었다.  BRK 무한루프 · IRQ2 · $F5 CD lock 은 잘못된 코드를
실행한 **뒤**의 잔해다.  훅을 빼도 죽은 것은, 훅이 원인이 아니라 훅이 **피해자를
호출하는 쪽**이기 때문이다.

### 15.7 공간 실사 -- 원판 Track 02, FF 32 B 이상 구간

    bank $68  $5BB3-$5FFF   1,101 B     <- 아레나가 $5C00 부터 여기를 쓴다
    bank $69  $BCD2-$BFFF     814 B     <- AC 헬퍼가 약 648 B 사용, 여유 166 B
    bank $6A  $7F50-$7FFF     176 B     <- 폰트래퍼 54 + 트램펄린/상태 120 = 꽉 참

**상주 오버레이 24 KB 안에 448 B 짜리 빈칸은 없다.**  프리로더를 그냥 옮길 자리가
없다는 뜻이다.

덧붙여, `$5C00-$5FFF` 를 **절대주소로 참조하는 코드는 전 뱅크에 하나도 없다.**
오직 `$25/$26` 포인터로만 닿는다.  그래서 아레나 바닥은 패치 가능하다.

### 15.8 실험 빌드 -- 2 바이트

`build\patch\EXPERIMENT\0.4.5.2-arena5B80`

    $4880  A9 00 85 25 A9 5C 85 26   ->   A9 80 85 25 A9 5B 85 26
    아레나 바닥  $5C00 -> $5B80
    아레나 용량   576 B -> 704 B      (관측치 579 B 대비 여유 125 B)

`$5B80-$5BB2` 에 디스크 데이터가 있지만 그 자리는 게임 자신의 704 B 레코드
버퍼라 어차피 첫 렌더에서 덮인다.  섹터 248 을 고쳤고 EDC/ECC 를 재계산했다.

**이것은 검증판이지 최종 수정이 아니다.**  아레나의 진짜 최댓값을 모른다.
쇼핑이 살아나면 15.1-15.5 가 100 % 확정되고, 그때 15.9 로 간다.

### 15.9 최종 수정 -- 아직 결정 안 됨

프리로더 448 B 를 `$5C00-$5FFF` 밖으로 완전히 빼야 한다.  15.7 대로 상주
오버레이에는 자리가 없으므로 셋 중 하나다.

    (a) 새 CD-RAM 뱅크를 하나 확보해 본체를 넣고, 훅은 트램펄린만 부른다
        -- 문제: 훅과 같은 창(bank $6A)에 둘 스텁 자리가 2 B 뿐이다
    (b) 프리로더를 크게 줄여 bank $69 여유 166 B 안에 넣는다
    (c) 아레나를 다른 영역으로 통째로 이사시킨다 (15.7 덕분에 가능은 하다)

### 15.10 이번에 다시 확인한 규칙

`$5E40-$5FFF` 는 원판 디스크에서 **전부 $FF** 였다.  그래서 빈 칸으로 봤다.
`_claude_memory` 의 [[ff_on_disc_is_not_free_space]] 가 정확히 이 사고다.
이번에는 한 걸음 더 나간다:

    런타임 Write 를 못 봤다  != 안전
    Write 를 한 번 봤다      -> 그 자리를 쓰는 **루틴을 찾아 범위를 계산**한다

$5E40 하나를 관측한 것으로 끝냈다면 "$5E40 만 피하자" 가 됐을 것이다.
할당기를 찾았기에 **$5C00-$5FFF 전체가 금지 구역**이라는 것을 알았다.

### 15.11 ★ 검증 결과 -- 살았다 (2026-08-20)

`EXPERIMENT\0.4.5.2-arena5B80` 으로 조이 디비전 「쇼핑하기」 **통과**.

이것으로 15.1-15.5 가 전부 확정이다.  2 바이트가 원인이고 2 바이트가 고쳤다.

    아레나 바닥 $5C00 -> $5B80    아레나 576 B -> 704 B
    쇼핑 요구치 579 B             여유 3 B 부족 -> 125 B 여유

§13 은 이것으로 닫는다.

### 15.12 남은 질문 하나 -- 아레나 최댓값

지금 아는 것은 **쇼핑 화면이 579 B 를 쓴다**는 것뿐이다.  게임 전체의 최댓값은
모른다.  원판은 1,024 B 를 주고, 우리는 704 B 를 준다.

    최대 <  704 B   ->  이 2 바이트가 그대로 최종 수정이다
    최대 >= 704 B   ->  프리로더 448 B 를 bank $68 밖으로 빼야 한다 (§15.9)

`lua\PROBE_ARENA_0.1.0.lua` 가 이 값을 잰다.  `$2026` 쓰기 콜백 +
프레임 폴링으로 최고 수위만 기록하고, 디버거를 멈추지 않는다.  **평소대로
플레이하면 된다.**  넓게 돌수록 값이 정확해진다.

### 15.13 프리로더 해부 -- 줄일 여지가 없다

$5E40-$5FFF 448 B 전부 실코드다.  테이블도 패딩도 없다.

    $5E40-$5E53  레지스터 + ZP $05-$08, $F8-$FF 18 회 push
    $5E54-$5E78  $3471/$3472 게이트 ($3499/$349A/$3619) -- 아니면 즉시 탈출
    $5E7B-$5EF9  ($03) 64 B 해시 -> 슬롯 번호 ($7FF1/$7FF2)
    $5F00-$5FB1  탐색 루프 6 회.  JSR $7F88 (트램펄린 -> bank $69 헬퍼)
                 'S' 매직 + 키 5 B 대조, 맞으면 $3471/$3472 -> $5B90
    $5FB4-$5FE3  체인/오버플로, 2 차 트램펄린 호출
    $5FE6-$5FFF  복원 + LDA $3471 (밀려난 원래 명령) + RTS

원판 수준(1,024 B)을 되찾으려면 bank $68 잔류분을 128 B 이하로 줄여야 하는데
위 구조로는 불가능하다.  그래서 §15.9 (a)/(c) 가 실제 후보이고, 15.12 측정이
그 작업이 필요한지 아닌지를 먼저 가른다.

### 15.14 0.4.5.3 으로 승격 · 빌더에 반영 (2026-08-20)

실험 폴더에 두면 스튜디오 빌더가 안 먹으므로 정식 버전으로 올렸다.

    build\patch\0.4.5.3\      <- EXPERIMENT\0.4.5.2-arena5B80 을 이동
    manifest.version = 0.4.5.3, arena_base_patch 항목 추가
    TEST_IN_MESEN.txt 에 쇼핑 화면 회귀 항목 추가

★ **2 바이트를 빌더에 넣었다.**  안 넣으면 다음 빌드에서 그냥 사라진다.

`build_direct_overlay_patch_ui.py` (stage 1) 에 정식 Patch 항목으로 추가:

    ARENA_FLOOR_INIT = 0x4880
    ARENA_FLOOR_OLD  = 0x5C00
    ARENA_FLOOR_NEW  = CACHE_BASE      (= $5B80)
    ARENA_MIN_BYTES  = 704

    common.Patch("arena_floor", bank68_iso($4880),
                 A9 00 85 25 A9 5C 85 26,
                 A9 80 85 25 A9 5B 85 26)

기존 preflight 가 원본 바이트를 대조하므로 원판이 다르면 빌드가 멈춘다.
추가로 조립 전 불변식을 하나 넣었다 -- 프리로더 시작을 옮기거나 바닥을
올리면 아레나가 704 B 미만이 되는 순간 빌드가 실패한다.

    arena_bytes = RUNTIME_START - ARENA_FLOOR_NEW
    if arena_bytes < ARENA_MIN_BYTES: raise

주의: `0.4.5.3` 의 Track 02 는 빌더가 아니라 사후 바이너리 패치로 만든 것이다
(바이트는 동일).  다음 정식 빌드부터는 빌더가 같은 결과를 낸다.

### 15.16 ★ 정정 -- 그것은 할당기가 아니라 스크립트 VM 데이터 스택이다

§15.2 이하에서 `$25/$26` 을 "범프 할당기" 라고 불렀다.  **틀렸다.**
씬 뱅크를 더 읽어보니 push/pop 쌍이 나온다.

    $8D7A  push     PHA / ptr+1 / PLA / STA ($25)
    $8D8B  push X   PHA / ptr+1 / PLA / TXA / STA ($25)
    $8D9E  pop X    LDA ($25) / PHA / ptr-1 / PLA / TAX
    $8DB0  pop      LDA ($25) / PHA / ptr-1 / PLA

`$4880` 이 까는 것은 아레나 바닥이 아니라 **스택 바닥**이고, 값은 올라갔다
내려갔다 한다.  §15.3 의 `LDA $25 / SBC #$N / STA ($7E)` 도 객체 필드 초기화가
아니라 **스택 프레임의 지역변수 접근**이었다.

수정 내용과 위험 조건은 그대로다 -- 포인터가 `$5E40` 을 넘으면 프리로더 첫
바이트가 죽는다.  다만 재는 대상의 이름이 "최대 할당량" 이 아니라
**최대 스택 깊이**이고, 그것을 좌우하는 것은 목록 길이가 아니라
**스크립트 중첩 깊이**다.

### 15.17 ★ 0.1.2 로 잰 값은 폐기 -- 찢어진 읽기

`PROBE_ARENA_0.1.2` 가 `$2025` 와 `$2026` 을 **따로** 읽었다.  포인터 갱신은

    LDA $25 / CLC / ADC #$01 / STA $25      <- 하위 먼저
    LDA $26 / ADC #$00       / STA $26      <- 상위 나중

두 명령이라, 그 사이를 읽으면 (새 하위 + 옛 상위) 라는 있지도 않은 주소가 나온다.
로그에 남은 증거 두 개:

    BASE lowered to $5B01 / $5B00     스택 바닥 $5B80 아래 -- 불가능
    $5D09 -> $5DFF 한 걸음에 246 B    스택이 그렇게 뛸 리 없다

그러므로 **"최고 $5DFF · 여유 65 B" 는 무효다.**  실제 여유는 더 클 수도, 더
작을 수도 있다.  이 값을 근거로 §15.9 판단을 하지 말 것.

`PROBE_ARENA_0.1.3` 이 고친 판이다.  쓰기 콜백이 넘겨주는 **값 자체**를 상위
바이트로 쓴다 -- 상위가 쓰이는 순간 하위는 이미 갱신돼 있으므로 이 조합만
항상 정합하다.  프레임 폴링은 찢어짐의 출처라 판정에서 뺐고, 새 최고 깊이마다
호출자 PC 와 MPR4/5/6 을 같이 남긴다 (어느 화면이 깊이 파는지 알기 위해).

측정은 아직 안 끝났다.  **다음 세션의 첫 할 일이다.**
