## 1. 원인 — 섹터 패딩

선적재는 CD 를 **섹터(2048 B) 단위**로 읽는다.  실데이터가 짧아도 뒤의 패딩까지
통째로 AC 에 실린다.  그 패딩이 `FF` 다.

```text
subtitle_helper    $1F1C00 + 1섹터 -> $1F1C00-$1F23FF   (실데이터   448 B)
subtitle_renderer  $1F1F00 + 1섹터 -> $1F1F00-$1F26FF   (실데이터   671 B)

옛 색인 자리 $1F2400   ★ renderer 섹터의 패딩 한복판
옛 슬롯 자리 $1F2200   ★ 같은 섹터 안
```

자리를 처음 고를 때 **"renderer 는 `$1F21A0` 에서 끝나니 안 겹친다"** 고 봤다.
데이터 끝만 보고 **섹터 끝을 안 본 것**이 이 밤의 전부다.

> ★ 규칙 -- AC 자리를 고를 때는 **데이터 끝이 아니라 섹터 끝**을 본다.
> 빌더 주석(`tools/build_snatcher_0_4_7_0_lba_probe.py`)에 박아 두었다.

### 어떻게 갈랐나 (헛다리 둘을 먼저 죽였다)

```text
0.5.38  디스패처 진입 때 MPR0 = FF   -> "문맥 문제" 로 보였으나 **진입 시점만 쟀다.**
        접근 순간을 안 쟀으므로 판정 불가.  그 결론은 철회했다
0.5.41  $1A00-$1A0F 에 읽기/쓰기 콜백 -> **포트는 멀쩡했다**

          성공 base $1F33D2 · 제어 $11 -> 읽기 $24
        같은 관용구 · 같은 MPR · 주소만 다른데 한쪽은 읽힌다
        => (a) 문맥 · (b) base 미설정 둘 다 기각.  남은 설명은 "그 자리에 표가 없다"
0.5.42  60 프레임마다 표를 대조   -> **3120 프레임에 64/64 B 가 FF 로 깨짐**
        게임 데이터가 아니라 FF 로 통째 -> 디스크 패딩이다.  원인 확정
```

★ `0.5.41` 은 **표를 올리지 않는 판**이었다.  그런데도 그 자리에서 값이 나왔다.
그것이 "이 구역이 한가하지 않다" 는 첫 신호였다.

★ `0.5.40` 의 "AC 되읽기 OK" 는 안심의 근거가 못 된다.  Lua 는
`pceArcadeCardRam` 으로 **포트를 안 거치고** 읽고, 그 확인은 **로드 시점**이다.

## 2. ✔ 남은 문제 셋 -- 전부 해소됨

> **2026-08-30 23:40 갱신.**  아래 세 가지는 **BIOS 결함이 아니었다.**

### 2-1 · 2-2 (도장 $00 · 117 단계) -- 슬롯 배치가 한 칸 어긋난 것

두 경로가 키 자리에 쓰는 바이트 수가 달랐다.

```text
found   status +0 · LBA +1~3 · 키 6B +4~9 ·        단계 +10 · BUILD +11
miss    status +0 · LBA +1~3 · 동적3 +4~6 · 고정4 +7~10 · 단계 +11 · BUILD +12
```

Lua 는 `slot[11]=단계 · slot[12]=BUILD` (miss 배치) 로 읽었다.  그래서 found 일 때

```text
slot[11] = BUILD_ID $75 = 117 (십진)  ->  "117단계"      ★ 117 의 정체
slot[12] = 안 쓴 자리 = $00           ->  "BUILD $00"
```

**BIOS 는 처음부터 옳았고 판독이 틀렸다.**  found 경로에 채움 1 B 를 넣어
**고정 ABI** 로 통일했다 (0.4.6.27).

```text
+0      status
+1~3    LBA
+4~10   found: 키 6B + 채움 1B   ·   miss: 동적3 + 고정4
+11     단계 수
+12     BUILD 도장
```

### 2-3 (한 칸 밀림) -- 진단 문구가 낡은 것

`#2` 의 `$003057` 은 표의 **최소값 `$00306B` 보다 작다.**  표에 없는 것이 맞고
miss 가 정답이다.  이분검색이 경계에서 가장 가까운 항목에 내려앉는 것은 정상이다.

"마지막으로 읽은 항목이 표에 있으면 이상하다" 는 진단 어림짐작이 틀렸다.
-> 그 문구들(`mid*9 주소 계산이 틀렸다` · `비교/분기 논리 문제`)은 **폐기한다.**

### ⚠ 남은 사소한 것 하나 (양성)

`#1` 의 목표 `$0A0000` 은 표 최대값보다 크다.  그때 동적 읽기가 `$00F7F7` --
표 항목이 아니다.  **탐색이 표 끝을 한 칸 넘어 읽는다.**  결과는 miss 로 옳고
해는 없지만, 언젠가 상한을 물려 두는 편이 낫다.

## 2-old. (아래는 해소 전 기록)

성공한 세 건과 실패한 두 건의 **숫자가 다르다.**  경로가 둘로 갈려 있다.

```text
성공(#3~#5)   BUILD $00 (기대와 다름)   117 단계   st $A1   OK
실패(#1~#2)   BUILD $75 (정상)          9~11 단계  st $A0
```

1. **성공 경로가 버전 도장을 안 찍는다.**
   빌더에 도장이 두 군데 있다.  한쪽 경로만 찍는다.  어느 경로가 도는지 못 가린다.

2. **117 단계.**  902 항목 이분 검색이면 ~10 단계여야 한다.
   실패한 쪽의 9~11 이 오히려 정상 깊이다.  117 은 다른 루프다.

3. **한 칸 밀림 1 건.**  `#2` 의 진짜 LBA 는 `003057` 인데 디스패처는 `00306B`
   를 찾았다 -- 그것은 `#3` 의 LBA 다.  한 음성 앞서 읽는 것인지 논리 오류인지 미확인.

> ★ `OK x3` 은 큰 진전이지만 **"우연히 맞았다" 를 아직 배제하지 못한다.**
> 성공한 셋이 전부 도장 없는 경로였기 때문이다.  다음 작업은 경로 구분이다.

## 5. 이어서 할 일

조회는 **검증이 끝났다.**  다음은 그것을 실제로 쓰는 단계다.

```text
1  ★ 감지기와 결합     조회 결과로 selector/record 를 세우고 state 를 연다
                        (BASELINE §12.7)
2  탐색 상한 물리기     목표가 표 범위를 벗어나면 표 끝을 한 칸 넘어 읽는다 (양성)
3  진단 문구 정리       `mid*9 ...` · `비교/분기 ...` 는 틀린 어림짐작이다.  뺀다
4  Lua 판독 고정        slot ABI 가 고정됐으니 프로브가 경로별로 갈릴 이유가 없다
```

★ 1 로 넘어가기 전 확인된 것 -- **조회 경로는 위험 0 이다.**  이 POC 는 자막을
켜지 않고 state 도 안 건드리고 결과를 슬롯에 적기만 한다.  그 상태로 5/5 정답이
나왔으므로, 다음 단계의 실패는 **결합부** 로 범위가 좁혀진다.
