# UI 갱신 시 배경 밀림 — 사실·자료·가설 취합

작성: 2026-09-15. 범위: 자료 검토와 가설 정리. 새 실행 시험이나 런타임 수정은 하지 않았다.

## 1. 출발점: 사용자가 확인한 사실

1. 오버클럭 설정을 10으로 주면 그림의 밀림이 없다.
2. 특정 UI, 특히 ‘보다’에서 다른 글자/항목보다 AC 접근량이 매우 많다.
3. UI 선택·미선택 갱신 때마다 배경화면이 밀린다.
4. 대사 이후 UI가 다시 나올 때도 배경화면이 밀린다.
5. 최초 관측 때보다 현재 증상이 심해졌다.
6. AC 접근량을 줄였을 때 밀림도 줄었다. (취합 중 사용자 추가 확인)

사용자 추론: AC 접근은 원초적 단독 원인보다 증폭 요인이고, 여러 문제의 복합 증상일 것이다.
이 해석을 우선 작업 모델로 채택한다. 다만 AC 접근 감소에 동반된 다른 처리 감소까지
분리 측정한 것은 아니므로, ‘AC 포트 읽기 자체’와 ‘AC를 사용하는 경로의 비용’은 구분한다.

설정값 10의 정확한 배율이나 구현은 이번에 확인하지 않았다. ‘10배 최적화가 필요하다’로 해석하지 않는다.
현재 실행판·BIOS 해시·에뮬레이터 설정과 항목별 측정치는 아직 이 여섯 사실에 연결되지 않았다.

## 2. 가장 유력한 작업 가설

UI를 갱신할 때 번역 조회·레코드 전개·문자 생성·화면 전송이 발생하고,
그 작업이 배경의 시간 민감한 갱신을 늦추거나 표시 제어 상태와 충돌한다.
AC 접근은 작업량이 커졌다는 신호일 수 있으며, 그 자체가 유일한 원인이라고 볼 수는 없다.

가능한 사슬:

    선택 변경 / 대사 종료 후 메뉴 복귀
      → UI 갱신
      → 조회·전개·글자 생성·전송 중 하나 이상이 증가
      → 배경 제어의 실행 시각 / 레지스터 적용 순서가 달라짐
      → 배경이 밀려 보임

‘보다’의 작업량 차이, 현재판의 악화는 사슬 앞부분을 설명하는 가설이고,
스크롤 갱신 지연·인터럽트 지연·상태 충돌은 뒷부분을 설명하는 가설이다.
이들은 서로 배타적이지 않다.

### 복합 증상 모델 세 가지

1. **공통 취약점 + 여러 증폭 요인**: 배경 제어가 타이밍에 민감하고, AC 조회·문자 전송·자막 복원 비용이 함께 갱신을 늦춘다. 현재 우선 모델이다. AC를 줄이면 덜하지만 다른 비용 때문에 남고, 오버클럭은 여러 비용을 함께 줄인다.
2. **독립된 오류의 중첩**: AC/UI 처리 지연으로 생기는 밀림과, 다른 훅의 VDC 상태 보존 실패 등이 따로 존재한다. AC를 줄이면 전자만 개선된다. 서로 다른 밀림의 모양·지속 시간·발생 조건이 나뉘는지가 표적이다.
3. **조건부 상호작용**: 평소에는 괜찮지만 자막 복원과 UI 재출력 등이 같은 구간에 겹칠 때만 실패한다. AC 비용은 그 겹침을 길게 만들어 증상을 증폭한다. 기능 A/B 각각과 A+B를 비교하되, 실행 시각 변화도 함께 계측해야 한다.

이 세 모델은 일부가 동시에 성립할 수 있다. ‘복합 증상’이 곧 독립 버그 여러 개가
입증됐다는 뜻은 아니다. 또한 AC 감소에 따른 개선이 선형이라는 근거는 없으며,
경계를 넘는 순간 급격히 나빠지는 양상도 가능하다.

## 3. 기존 자료에서 확인한 것

### 3.1 우선 읽어야 할 정정

[09-08 재진단](SNATCHER_SHAKE_REDIAG_2026-09-08.md):

- `noexpand`: 한글 동적 레코드 전개와 그 뒤 출력을 함께 끈 시험. 사용자는 밀림이 줄었지만 남았다고 보고했다.
- 처음에는 BIOS의 idle AC 읽기 1회가 남았다.
- `zeroac`: 이 읽기도 막고 관측 장면에서 AC read/write 0회를 확인했으나, 밀림은 남았다고 기록했다.
- 따라서 앞선 문서의 ‘AC/UI 전개가 뿌리 원인으로 확정’은 철회됐다.
- `nodraw`: AC 전개는 유지하고 뒤 출력을 끄는 분리 시험이 제안됐다. 관련 도구는 있지만 이번 검색 범위에서 결과 기록은 찾지 못했다.

해석 한계:

- `noexpand`는 AC 전개와 출력 둘을 함께 제거한다. 개선량을 AC 단독의 효과로 분리할 수 없다.
- `zeroac`는 원본 일본판이 아니다. 패치 BIOS와 다른 변경이 남는다.
- zeroac의 ‘AC 0회’는 확인한 장면/상태의 결과이지 전체 게임 모든 경로의 보장이 아니다.
- 과거 시험 결과는 중요한 반증이지만 현재판에서 그대로 재현했음을 뜻하지 않는다.

- ATLAS 접근이 없다는 관측은 이 세션의 많은 AC 접근을 ‘한글 획/글리프를 AC에서 읽는 비용’으로 바로 해석할 수 없다는 근거다.
- 항목 표식이 0이므로 이 프레임을 ‘보다’의 프레임으로 특정하지 않는다.

### 3.3 VDC 원자료

[프레임 로그](../../dump/vdc_0_5_191_20260908_151202_frames.tsv),
[요약](../../dump/vdc_0_5_191_20260908_151202_summary.txt).

- 프레임 3: VWR 512 B, MAWR 2회, 첫~마지막 전송 폭 34줄.
- 프레임 14: VWR 1408 B, MAWR 12회, 폭 196줄.
- 프레임 16: VWR 1068 B, MAWR 14회, 폭 204줄.
- VWR는 VRAM으로 보내는 데이터, MAWR는 쓰기 시작 주소 지정이다.
- 이는 전송량과 주소 지정 횟수가 늘어난 프레임이 있음을 보여준다.
- 프레임 전체 합계다. 1408 B 전부를 패치가 추가한 한글 글리프라고 단정하지 않는다.
- 첫 접근~마지막 접근 사이에는 다른 실행이 있을 수 있다. 196줄은 연속 CPU 점유 시간이 아니다.
- AC 로그와 VDC 로그는 다른 세션이다. 프레임 번호로 서로 대응시키면 안 된다.
- 요약 파일의 ‘폭이 10~12줄을 넘으면 범인’이라는 자동 판정 문구는 측정 결과가 아니라 진단 가정이다.

### 3.4 과거 최적화·실패 시험

[09-08 뿌리 추적 기록](SNATCHER_SHAKE_ROOT_2026-09-08.md):

- `scan_0B`: 탐색 상한 92→11, 화면상 변화 없음. 실측 깊이가 이미 11 이하였다면 실제 작업을 줄이지 못한 시험이다.

- AC의 일부 비용을 줄였어도 다른 비용이나 실행 시각 문제가 남았을 수 있다.

[08-15 진단](SNATCHER_FLICKER_ELIMINATION_2026-08-15.md):

글자 자체 가설을 살리려면 가변 처리 경로나 캐시 차이를 관측해야 한다.

### C. 대사 이후 재등장과 최근 악화를 설명하는 가설

## 5. 지금 하면 안 되는 단정

- ‘오버클럭에서 사라진다 → CPU 총성능 부족 확정’: 실행 시각, 경쟁 조건, 상태 적용 순서도 가능하다.
- ‘AC 접근이 많다 → AC 하드웨어가 배경을 직접 민다’: AC 없는 관측 장면에서도 잔여 증상이 있다.
- ‘zeroac에서 남는다 → 원본 게임 문제’: 수정 BIOS와 다른 패치 코드가 남아 있다.
- ‘notpl 무변화 → AC 무죄’: 일부 비용 제거 시험이다.
- ‘작업이 10~12줄보다 짧으면 안전’: 갱신 직전에 시작하면 짧아도 경계를 걸칠 수 있다.
- ‘VWR 폭 196줄 → CPU 196줄 연속 점유’: 접근 사이 간격을 포함한다.
- ‘1408 B가 VBlank 이론 용량에 들어감 → 옮기면 해결’: 원래 게임의 VBlank 작업·전송 대기·설정 비용·버퍼·완료 계약을 빼고 남은 예산을 재야 한다.
- ‘ATLAS 0 → 폰트 비용 0’: BIOS에서 글자를 만들고 VDC로 보내는 비용은 별개다.
- ‘같은 PC가 수백 번 → 함수 수백 회’: 블록 전송의 바이트별 접근이 같은 PC로 기록될 수 있다.
- ‘둘을 각각 조금 줄여도 실패 → 반드시 둘 다 동시에 수정해야 함’: 실험 범위 밖의 결론이다.

## 6. 가장 적은 시험으로 가설을 줄이는 순서

### 1단계: 동일한 기준에서 증상과 이벤트를 연결

- 현재 실제 BIOS·Track 02·관련 트랙 해시, 에뮬레이터/코어 버전, 오버클럭 설정을 기록한다.
- 순정 일본판+순정 BIOS와 현재판을 동일 장면/입력으로 비교한다.
- 상태 저장 파일이 코드를 포함할 수 있으므로 다른 빌드의 상태를 그대로 재사용해 코드 비교가 오염되지 않게 한다.
- 무입력 / ‘보다’ 진입 / ‘보다’ 이탈 / 다른 항목 왕복 / 대사 후 UI 복귀를 따로 표시한다.
- 밀림 시작·끝·화면 Y 경계와 AC/VDC/배경 제어 쓰기를 같은 세션에서 수집한다.
- 오버클럭 10과 기본값에서 같은 호출 수·주소·전송량인지도 비교한다. 같고 시각만 달라지면 타이밍 가설이 강해진다.

### 2단계: ‘보다’가 비싼 이유 분해

    UI 이벤트당 총비용
      = 조회 호출 수 × 호출당 후보 수 × 후보당 전개 비용
        + 실제 출력 횟수 × 문자 생성·전송 비용
        + 복원/정리/그 밖의 부대 작업

요청 키, 후보 ID, hit/miss, 출력 ID, 전개 진입/반환 사이클, VWR/MAWR를 기록한다.
문구가 원인인지 위치/메뉴 의미가 원인인지는 동일 길이 문구 교환으로 분리한다.

### 3단계: 전개와 화면 출력 분리

현재판에 맞춰 검증한 진단으로 전체 패치 / nodraw / noexpand를 비교한다.
기존 도구는 0.6.2의 주소와 기대 바이트를 전제로 하므로 현재판에 무검증 적용하지 않는다.

- nodraw가 noexpand와 비슷하게 개선: 뒤 출력 경로의 기여를 우선.
- nodraw가 전체 패치와 비슷: 전개/헬퍼 실행의 기여를 우선.
- 중간: 양쪽 또는 실행 위상의 상호작용을 조사.

경로를 제거하면 실행 위상도 바뀐다. 이 비교는 조사 방향을 정하는 근거이며
단일 인과 확정이 아니다. 필요하면 제거한 비용에 상응하는 대조 지연을 둔 시험으로 분리한다.

### 4단계: 처음 어긋나는 배경 제어 쓰기 포착

- 값은 정상이고 쓰는 시각만 늦음: A1/A2/A3/A6 우선.
- 잘못된 레지스터·주소·값에 씀: A5/A8 우선.
- 한 번 어긋난 뒤 수 프레임 지속: C7 또는 상태 복구 시점 조사.
- 원본은 정상, zeroac만 이상: C4/C5/C9의 패치 잔여 경로를 분리.

### 5단계: 악화 시점 비교

구판과 현판의 같은 이벤트에서 실제 작업량 증가와 시작 시각 변경을 분리한다.
이후 변경 구간을 좁히면 번역량 증가, 최적화 누락, 새 상주 훅 중 어디서 악화됐는지 판단할 수 있다.

## 결론

가장 먼저 조사할 대상은 **AC가 증폭하는 공통 취약점이 무엇이며, UI 갱신으로 늘어난 작업이 배경 제어를 언제, 얼마나 늦추는가**다.
‘보다’의 과다 AC 접근은 원인을 좁힐 좋은 비교 표적이다.
다만 과거 zeroac 결과 때문에 **AC 최적화만 하면 완전히 해결된다고 예고할 근거는 없다.**
UI의 작업량을 만드는 원인과 배경을 실제로 미는 기전을 같은 이벤트에서 연결해야 한다.
