## 1. 음성 — 무엇이 잘렸고 왜였나

수집기 `0.1.2` 는 재생이 **시작되는 순간** ADPCM RAM 을 한 번만 떴다.  ADPCM RAM 은
64 KB 링버퍼이고 게임은 재생하면서 계속 채워 넣는다(스트리밍).  그래서 한 판
분량인 8.19 초까지만 담겼다.

```
rate 0x0E -> 32000/(16-14)/2 = 8000 B/s -> 64 KB = 8.192 초   (실측과 정확히 일치)

ADPCM_003367_FFFF_0E   8.18 초 담김 / 23.73 초 재생 = 34 %
ADPCM_0032C4_FFFF_0E   8.18 / 16.85 = 49 %
```

소리만이 아니라 **그 소리로 뜬 `jp_text` 도 앞 8 초치뿐**이다.  162 개 전부 대사다.

## 2. 세 번 헛돈 기록 — 다음에 또 밟지 말 것

### 2-1. `0.1.3` — 이어붙였는데 파일에 못 썼다

```lua
if #data > #old and endsWith(data, old)     -- 옛 파일이 새 데이터의 꼬리인가?
```

꼬리로 자라면 옛 파일은 **머리(prefix)** 다.  판정이 다 빗나가 `k..._vXXXXXXXX.bin`
변종으로 새 나가고 마스터의 `clip_file` 은 잘린 옛 파일을 그대로 가리킨다.

### 2-2. ★ `0.1.4` — 링을 한 바퀴 헛돌았다 (파일 19 개 오염)

커서에서 포인터까지의 **모듈로 전방 거리**를 새로 채워진 양으로 봤다.

```
머리를 뜬 직후 커서 = read+length = $D000 · read 는 아직 앞쪽 $0064
    (0x0064 - 0xD000) mod 0x10000 = 0x3064 = 12,388 B    <- 작아 보인다
실제로는 read 가 커서보다 0xCF9C **뒤에** 있다
```

전방 거리로는 **앞섰는지 뒤졌는지 구분할 수 없다.**  12 KB 를 헛붙이고 커서를 당긴 뒤
다시 끝까지 따라가 결과가 **정확히 링 한 바퀴(+65,536 B)** 불었다.  오염 19 개가 전부
그 값이었다.

```
k00306B_A000_0E   40,848 -> 106,384  (+65,536)   13.30초 담김 / 5.10초 재생 = 261 %
```

**커버리지가 100 % 를 넘은 것이 유일한 경보였다.**  재생된 것보다 많이 담을 수 없다.

`tools/restore_voice_clips.py` 로 전량 복구했다 -- 앞/뒤로 잘라 **sha256 이 맞는 쪽만**
되돌린다.  추측하지 않는다.  결과 `기준과 다른 파일 0 개`.

### 2-3. 검사기가 안 닫힌 문자열을 못 잡았다

Python 패치가 Lua 문자열 리터럴 안에 실제 개행을 넣어 로드가 죽었다.  블록 균형만
보는 검사기는 `end` 개수가 멀쩡해서 통과시킨다.  문자열 종료 검사를 먼저 하도록
고쳤고, 일부러 깨뜨린 파일로 잡히는 것까지 확인했다.

⚠ 자리표시자에 따옴표를 쓰면 안 된다 (`""` 로 치환하면 모든 줄이 오탐).

## 3. `0.1.5` 의 설계

```
머리   readAddress 에서 adpcmLength 바이트   <- 0.1.2 와 **바이트가 같다**
       (그래야 옛 파일이 prefix 가 되어 성장 판정이 선다.
        그 결과 정상 클립은 파일이 아예 안 바뀐다 -- existing_key)
이후   **펼친 누적 전진량(accAdv)** 이 머리를 넘어선 만큼만 이어붙인다
       담을 조건은 accAdv > accBytes 하나뿐 · 읽어 올 자리는 accStart + accBytes
도약   한 프레임 4,096 B 초과 = 포인터 리셋.  붙이지 않고 재동기 + 로그
```

### ★ write 가 아니라 read 를 따라간다

```
v012 로그 3,471 START:  write == read+adpcmLength  2,247 회
                        나머지는 write 가 최대 18 KB 앞섬
```

**write 는 이 클립의 끝이 아니다** -- CD 가 다음 것까지 미리 채워 둔 자리다.  write 만
따라가면 다음 클립이 꼬리에 섞여 전사가 오염된다.

**`readAddress` 는 살아 있는 값이 맞다** (실측 · 전 클립 `[read]` 모드 · 폴백 0 회).

### 머리 어긋남 -- 양쪽 다 인정한다

`readAddress` 는 주행마다 몇 바이트 흔들린다 (실측 `$0011`~`$0079`).

```
새가 일찍 시작  ->  expanded_shifted   (옛 것이 새 데이터 안에 있다)
새가 늦게 시작  ->  expanded_prepend   (옛 것의 앞 k 바이트를 붙인다)
```

`0.1.5` 이전에 갈라진 변종은 `tools/merge_voice_clip_variants.py` 로 오프라인 병합했다
(003318 2 B · 0033D7 9 B · 003423 2 B).  **다음 주행에서 `key_collision` 없이
`existing_key_tail` 로 지나가 병합이 옳았음이 증명됐다.**

⚠ 중간 저장(`flushPartial`)은 변종을 만들면 안 된다 -- 003318 하나에 300 프레임마다
변종이 하나씩 생겨 3 개가 됐다.  `partial` 플래그로 막았다.

## 4. ★★ 안전자리 벽 -- 별도 작업으로 넘긴다

지도는 잘 모였는데 **게이트 숫자가 안 움직인다.**

```python
# tools/verify_subtitle_safe_positions.py:24
ADPCM_POS = BUILD / "vram_key_bases_pairs.tsv"     # build_vram_key_bases.py --pairs 출력
# :102
if len(key) != 12: problems.append("runtime key must be 6 bytes")
```

팩·게이트·런타임 엔진은 **옛 12-hex 키**(end 2 B + rate 1 B + ADPCM RAM 표본 3 B)만 안다.
지도 0.4 와 마스터와 수집기는 **네이티브 키**(`ADPCM_<sector>_<end>_<rate>`)를 쓴다.

지금 `--pairs` 로 돌리면 전 행이 거부되어 **50 -> 0** 이 된다.  (그래서 안 돌렸다.)

### 다리를 놓으면 얼마나 버나 (실측)

```
지도가 자리를 낸 네이티브 키          125
  12-hex 로 번역되는 것                82     (43 실패 = 마스터에 없는 새 음성)
  그중 팩 902 에 있는 것               67
  이미 pairs 표에 있는 것              50
  ★ 새로 추가될 것                     17     ->  ADPCM 50/902 -> 67/902
이 125 개 안의 뭉침 충돌                0
```

### 옛 키의 구조적 한계

```
마스터 1,055 행에서
  네이티브 키 중복                     0
  옛 12-hex 로 뭉개지는 키            36 개가 14 개로
    00F00EAB8DA9 <- 001108 · 0011E5 · 001242 · 002381 · 0039D8 · 004BDE   (대사 6 개!)
```

게다가 스트리밍 클립은 t0 에 표본 자리가 아직 안 채워져 있다 (실측 `FFFF0E000009`).
**옛 키는 긴 대사에 원래 못 쓴다.**
