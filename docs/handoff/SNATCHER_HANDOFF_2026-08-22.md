## 1. 빌드가 뚫렸다 — 무엇이 막고 있었나

두 가지였고 둘 다 풀렸다.

### 1-A. 글리프 자리 (빈 칸 4개, 31자 부족)

배정표는 "게임이 쓰는 글리프"를 세 겹으로 쌓는다. **TSV 코퍼스 1,701 + 디스크
스캔 254 + 런타임 관측 1 = 1,956.** 앞의 둘은 추정이고, 추정에는 디스크 어딘가에
글자가 있을 뿐 **화면에 한 번도 안 나오는** 한자가 섞여 있다. 그게 자리를 잡아먹었다.

엔딩까지 한 판을 완주하며 `EX_GETFNT($F124)` 에 실제로 들어간 코드를 전부 기록했다
(runtime_text_audit 0.2.2). **고유 2,141 코드 · 37만 호출.**

한글판으로 돌았기 때문에 "게임 한자"와 "우리가 그 자리에 넣은 한글"이 EX_GETFNT
에서 구분되지 않는다. 원문 코퍼스와 대조해서 갈랐다:

```
관측 2,141
  슬롯 배정된 코드   773  ->  원문에 그 한자가 아예 없는 것 724 = 우리 한글
                             원문에 나오는 것 49 = 애매, 보호 유지
  배정 안 된 코드  1,368  ->  게임이 그린 것 확실 (한자 1,137)

★ 게임이 실제로 그린 한자 = 1,137 ~ 최대 1,186   (추정치는 1,906 이었다)
```

`build_bios_hangul_map.py --trust-observation <glyph_used.tsv>` 로 **코퍼스 추정분
중 관측에 없는 것만** 놓아준다. 디스크 스캔분과 기존 관측분은 그대로 보호한다 --
셋 중 코퍼스가 제일 약한 근거다.

```
놓아준 코퍼스 추정   892 자
남은 빈 칸           4  ->  595
새로 배정            35
★ 재배정             0        <- 기존 배정이 하나도 안 움직였다
배정 후 남은 칸      560
```

**재배정 0 이 핵심이다.** 전에는 배정표를 다시 돌리면 기존 10자(곽님릴뽑줬첩청총항혼)가
옮겨가 이미 나간 판과 어긋나는 게 걸림돌이었는데, 관측을 물리니 충돌 자체가 사라졌다.

BIOS 는 975자로 새로 구웠다 (이전 940).

```
build/bios_font/hangul_slot_map.tsv     975행
build/bios_font/Syscard3_galmuri.pce    sha1 a1d8feb84511   (Firmware 에 적용 완료)
```

**아직 검증 안 된 위험이 하나 있다.** 새로 배정한 35자리가 전부 원문에 나오는 한자
위에 앉았다 (`哀 逢 圧 扱 案 位 偉 囲 威 為 異` -> `꺽 껏 꼭 냅 늑 늙 댁 덴 랄 략 렌`).
완주 중 한 번도 안 그려진 것들이지만 **한 판으로는 선택지·조사 분기를 다 못 밟는다**
(관측된 것 중 195자가 딱 1회만 그려졌다). 미번역 일본어 문장 한가운데 한글 한 글자가
보이면 그 코드를 `build/bios_font/observed_used.tsv` 에 추가하고 다시 배정하면 된다.

회수 후보 전체 목록: `build/bios_font/unused_kanji_candidates.tsv` (2,298개, 그중
원문에도 없는 것 1,962개가 제일 안전).

### 1-B. 트라이 충돌 — 같은 디스크 주소에 레코드가 둘

```
RuntimeError: same runtime trie state/source has conflicting Korean text
```

원인은 **편입이 이미 있는 디스크 주소에 레코드를 하나 더 만드는 것**이다. 마스터가
오늘 밤 6,075행 -> 15,082행으로 늘었는데 그 증가분의 상당수가 이미 있던 주소의 사본이다.
지운 레코드 2,332개 중 1,892개(81%)가 R04001 이상, 즉 오늘 밤 편입분이었다.

`tools/dedupe_disc_records.py` 로 정리했고 **검증까지 했다**:

```
지운 3,967행의 일본어가 살아남은 쪽에 있는가   3,967/3,967   사라진 것 0
번역이 있었는데 지우고 나서 빈칸이 된 행                      0
```

꼬리가 다른 것(`すわ。` vs `します。` 류)은 포함 관계가 깨져서 애초에 안 지운다.

**다만 소유자 지시로 마스터는 정리 전(15,082행)으로 되돌려 놓았다.** 중복은 직접
처리하겠다고 했다. 정리본은 `snatcher_tool/backups/20260822_*_deduped_11115_*.tsv` 에,
지운 행 전량은 `_archive_pre_dedupe_20260822/removed_rows.tsv` 에 있다.

빌드는 충돌나는 것만 그때그때 풀면서 진행하면 된다. 실제로 오늘 그렇게 두 건을 풀었다:

```
R01184 / R05033   같은 주소 4BC2, 번역이 갈림 -> 중복 정리로 해소
speaker:6 / UI0144   <원문 5자> 가 '카트리느'(화자표) vs '카트린느'(UI) -> 통일
```

**소유자 통찰:** 중복이 남아 있어도 **번역만 같으면 빌드가 안 막힌다.** 지우는 게
아니라 맞추는 걸로 푸는 쪽이 싸다.

## 2. 번역 데이터가 CP949 로 깎이고 있었다

`ui_text.tsv` 와 `speaker_name_standard.tsv` 가 어떤 인코딩으로도 안 읽혔다.
CP949 에 없는 문자가 전부 `?` 로 박혀 있었다.

```
受付嬢  ->  '����?'      <- ? 로 날아간 글자.  복구 불가
```

**화자표가 깨져서 화자명이 안 붙고 있었다.** 대사 첫 줄의 `受付嬢` 이 화면에 일본어로
남던 증상이 이것이다 -- 골격 문제가 아니었다.

둘 다 복구했다 (백업이 멀쩡했고, 마지막 정상 저장 이후 바뀐 게 4행뿐이라 손실 없음).

```
tools/repair_ui_text_encoding.py    ui_text.tsv    -> UTF-8 BOM 491 KB
translation/speaker_name_standard.tsv (UTF-16 사본) -> UTF-8 BOM 55행 복원
```

**근본 방어를 스튜디오에 넣었다.** `TsvDocument.Save` 가 쓰기 전에 왕복 검사를 한다 --
쓰려는 인코딩으로 인코딩했다 다시 디코딩해서 원문과 다르면 UTF-8 BOM 으로 강제한다.
`Encoding` 이 어떤 경로로 손실 인코딩이 되든 이제 파일은 안 깎인다.

## 3. 검토열이 믿을 수 없는 상태였다

편입(`ApplyLegacyTranslation`)이 옛 마스터에서 번역을 얹으면서 **검토 O 까지 베꼈다.**
사람이 한 번도 안 본 문장이 검토 완료로 들어앉는다.

증거: 중복 정리에서 같은 주소에 번역이 서로 다른 두 행이 **둘 다 O** 인 자리가 50개
나왔다. 둘 중 하나는 반드시 틀렸는데 양쪽 다 "검토됨"이었다.

특히 나쁜 것이 **꼬리 조각**이다. `ます。` `ん。` `る。` 같은 짧은 꼬리는 옛 마스터
어딘가에 반드시 있어서 전부 매칭되고, 서로 다른 문단의 꼬리에 같은 번역이 복사된다.
실측: 짧은 꼬리 원문 379종 중 341종이 번역이 한 가지뿐이다 (785행).

```
MainForm.cs   ApplyLegacyTranslation 에서 검토열 승계 차단.  status=review 로 들어온다
tools/unreview_new_since.py   기준 시점 이후 새 행의 O 를 뗀다 (오늘 334행 적용)
```

## 4. 로딩 — 팩 구조를 건드렸다가 되돌렸다  ★ 읽을 것

소유자가 "부팅 로딩이 길고 음악이 끊긴다"고 했고, 원인을 찾아 팩을 쪼갰다가
**체감이 나빠져서 전부 되돌렸다.** 그 과정에서 나온 사실이 다음 작업의 기반이다.

### 측정으로 확인한 것

`PROBE_BOOT_LOAD` 로 세 판을 같은 조건에서 재보니 **부팅 CD 읽기가 섹터 단위까지
동일**했다:

```
원본        58.3초  20회 371섹터   <- 여기서 끝.  더 안 읽는다
0.4.5.5     66.7초  88회 643섹터   (첫 대사 뒤 +68회)
0.4.5.6     99회 684섹터           (+79회)
```

**부팅은 원본과 같고, 재생 중에 우리만 CD 를 계속 읽는다.** 읽을 때마다 시크하고,
시크하면 CD-DA 가 끊긴다. 음악 끊김의 정체가 이것이다.

`PROBE_PACK_MISS` 로 어디서 읽는지 잡았다:

```
75초  lookup 2 · load_package 1 · bios_cd_read 91   <- 15초 만에 23 -> 91
```

`load_package` **한 번**이 CD 68회를 냈다. 원인은 **대사 4,704개가 팩 하나(452 KB)**
였다는 것. `classify_split_common` 이 `reference` 에서 `([0-9A-F]{6}):` 를 찾는데
마스터가 런타임 골격으로 바뀐 뒤 reference 가 `R00392:1` 형식이라 전부 빗나가
`"runtime"` 한 이름으로 떨어졌다.

### 쪼갰더니 나빠졌다

`pack` 열(6D~79)로 13개 씬 팩 + UI 3분할 = 16팩으로 갈랐다.

```
총 CD 읽기   91 -> 59회        줄었다
체감         나빠졌다          로딩이 4번으로 나뉘어 플레이 중에 흩어졌다
```

**중요한 것은 읽는 횟수가 아니라 언제 읽느냐였다.** 원래 구조는 부팅에 다 읽고 그
뒤로 조용하다. 쪼개니 그게 구역마다 흩어졌다. 소유자 판단이 맞았고 전부 되돌렸다.

정식 0.4.5.6 은 **원래 구조 그대로**다 (`all`, 3팩, 78 chunks, helper 631 B/151 B free).
분할 코드는 환경변수 뒤에 남아 있고 기본값이 꺼짐이라 동작에 영향 없다.

```
SNATCHER_SCENE_PACKS=1   대사를 pack 열로 씬 팩 분할
SNATCHER_UI_PACKS=1      UI 만 ui_core/ui_main/ui_rest 로 분할
```

### 확인된 좋은 것

```
120초  lookup  23 · bios_cd_read 60
135초  lookup 100 · bios_cd_read 60   <- 조회 77번 늘었는데 CD 읽기 0
```

**팩이 한 번 올라오면 그 뒤 대사는 전부 AC 에서 나온다.** 적재 구조 자체는 제대로 돈다.

### UI 분할이 실패한 이유 (같은 실수 반복 금지)

`ui_rest` 를 "게임에 안 나오는 것"으로 갈랐는데, 근거로 쓴 UI 캡처 로그가
**98세션 다 합쳐도 고유 문자열 623개**뿐이다 (ui_text 는 991개). 캡처 훅이 UI 전부를
못 잡는다. "관측 안 됨"이 "안 나옴"이 아니었고, 실제로 쓰는 UI 가 `ui_rest` 에 들어가
뜰 때마다 팩을 불렀다.

**관측을 근거로 무언가를 빼기 전에, 그 프로브가 그것을 볼 수 있었는지부터 확인할 것.**

### 다음에 할 것 — 챕터 + 팩

소유자 제안이고, 지금은 이것만 말이 된다.

```
부팅          core + shared + 챕터1        약 35~40 chunks  (지금 78)
챕터 전환     다음 챕터 팩 한 번에          화면 전환 구간이라 멈춰도 티가 안 난다
플레이 중     아무 것도 안 읽는다
```

로딩이 게임 전체에 딱 2번 생기고, 그 2번이 원래 멈춰도 되는 자리다.

**필요한 것 두 가지:**

1. **진짜 챕터 경계.** 시간 3등분 말고 스토리 경계. `dump/record_seen_*.tsv` 에
   레코드마다 first_frame 이 있어 순서는 재구성된다.
2. **전환 훅.** 그 지점에서 팩 적재를 부르는 코드. 지금 런타임은 **레코드를 못 찾을
   때만** 팩을 부르므로, 훅이 없으면 챕터 2 팩도 "챕터 2 첫 대사"에서 로딩이 걸린다 --
   오늘 되돌린 그 상태로 수렴한다. 헬퍼 여유 151 B.

**주의:** 팩은 챕터 로컬이 아니다. 실측상 13개 팩 전부가 시작 2~3분에 처음 나와
엔딩(629분)까지 계속 쓰인다. 그래서 "챕터별 슬라이스"는 **1회 등장 레코드**에만
성립하고, 2회 이상 등장한 33%(1,899레코드 50 KB)는 `shared` 로 빼야 한다.
미관측 레코드도 `shared` 로 -- AC 씬 구역이 1.4 MB 비어 있어 공짜다.

그림자 버퍼 포인터 후보다. 5분이면 잡힌다.
