## 1. 무엇이 문제였나

런타임 키는 6 B 다.

```
end_addr u16 LE + rate u8 + ADPCM RAM 표본 3 B   (표본 위치 end/4, end/2, 5*end/8)
```

**sector 가 없다.**  그래서 서로 다른 음성이 같은 키를 받는다.  1,211 음성에 `end_addr`
이 34 종뿐이라 뼈대가 얇고, 식별이 사실상 표본 3 B 에 걸려 있다.

그리고 표 빌더가 그 6 B 로 조각을 묶었다.

```python
groups[entry[:6]].append(entry)
rows = sorted((lba, key, entries) for key, entries in groups.items()
              for lba in lbas_by_key[key])
```

```
음성 A  키 123456  LBA 100      ->  LBA 100 에 A+B 자막
음성 B  키 123456  LBA 200      ->  LBA 200 에 A+B 자막
```

`--skip-collisions` 는 **양쪽을 다 뺀다** (`dropped_keys = 모든 owners`).  이긴 쪽을
고르는 옵션이 아니다.  쓰면 6 개 음성 자막이 통째로 빠진다.

## 2. 고친 방법 — 런타임은 이미 LBA 로 갈린다

디스패처는 **재생 시점**에 호출되지만, 로드 시점의 LBA 를 이미 들고 있다.

```
build_snatcher_0_4_7_0_lba_probe.py
  296 label("found")     이분 검색이 LBA 로 표를 찾은 지점
  306 CDB_LBA 3 B 를 관측 슬롯(AC $1F2700)+1 에 적는다     ★ SCSI CDB 의 LBA
  308 런타임 키 6 B 를 슬롯 +4 에 적는다

build_snatcher_0_4_6_29_native_arm.py
  146 arm_idle      슬롯 상태가 ST_FOUND 인지 본다
  150 arm_new_hit   맞으면 여기 (아니면 cdda_check 로)
  169 슬롯+1 의 3 B 를 WANT 로 복사        ★ 로드 때 잡아둔 LBA
  207 AC_DIR 에서 9 B 읽어 WANT 와 비교     ADPCM 자막 디렉터리 (start_lba u24 BE)
```

즉 **런타임은 원래 갈릴 수 있었다.**  섞인 것은 빌드 시점의 귀속뿐이었다.

### 2-1. 두 파일만 고쳤다

```
build_subtitle_pack.py
    항목에 주인(event_id)을 실어 두고, 팩에 쓸 때만 빼서 13 B 그대로 기록
    adpcm_index_owner.tsv 를 같이 낸다  (index_pos · event_id · runtime_key)
    ★ 팩 바이너리는 한 바이트도 안 바뀐다 -- 형식·스트라이드 불변

    충돌 관문을 2 층으로
        runtime_key_collisions      발견한 6 B 키 충돌.  ★기록만 한다
        unresolved_lba_collisions   LBA 로도 못 가른 것.  이것만 빌드를 세운다
    voice_start_lba() 헬퍼: adpcm_lba_master_index.tsv 의 key -> start_lba

build_adpcm_native_subtitle_table.py
    groups 를 6 B 키가 아니라 event_id 로 묶는다 (주인표를 읽어서)
    LBA 도 event_id 기준으로 마스터 색인 TSV 에서 가져온다
    key6_of[] 로 안전자리 조회는 그대로 6 B 키를 쓴다
    주인표가 없으면 옛 동작으로 물러난다
```

★ 충돌 수를 0 으로 지우지 않는다.  6 B 키 충돌은 여전히 3 쌍이고, 그것을 0 으로
  만들면 해결이 아니라 증거를 숨기는 것이다.  정확한 결과는 **발견 3 / 미해결 0** 이다.

### 2-2. 순서 무결성 확인

주인표는 `adpcm_index` 를 **정렬한 뒤** 훑어 쓴다.  정렬(459 행) 이후 그 리스트는
497·508·517·544 에서 **읽히기만 하고 한 번도 걸러지지 않는다.**  그래서 팩에 쓰는
517 행과 주인표를 쓰는 544 행의 순서가 같다.

## 3. ★ 그때 드러난 것 — 시작 LBA 충돌 4 쌍

주인별로 묶으니, 자막은 있는데 LBA 색인에 없는 음성 8 개가 드러났다.  전에는 다른
음성의 6 B 키에 얹혀 조용히 통과하던 것들이다.

```
003F91  1.5초   12,193 B  ->  003F8B
003FBB 12.3초   98,247 B  ->  003F8B      같은 자리

007378  0.8초    6,064 B  ->  007375
007398  8.9초   71,651 B  ->  007375      같은 자리

0085AC  2.3초   18,309 B  ->  0085A3
0085CC 10.5초   83,881 B  ->  0085A3      같은 자리

0077B8 · 0090B1  각각 하나씩
```

★ **길이가 부정확해서가 아니다.**  v014 실측 바이트가 양쪽 다 있는데도 겹친다.

원인은 `start_lba = 끝섹터 − ceil(길이/2048)` 라는 **역산**이다.  짧은 음성과 긴
음성이 디스크에서 붙어 있으면, 긴 쪽을 되짚었을 때 짧은 쪽 시작점까지 내려온다.
두 음성이 같은 데이터 덩어리를 공유하는 것으로 보이며, 그렇다면 시작 LBA 가 같은
것이 **사실**일 수 있다.

즉 시작 LBA 만으로는 이 쌍들을 구분할 수 없다.  해결하려면 끝 섹터나 길이를 같이
보는 판별자가 필요하고, 그것은 색인 형식과 디스패처 비교 코드를 함께 고치는 일이다.
오늘 즉흥으로 할 것이 아니라 따로 착수한다.
