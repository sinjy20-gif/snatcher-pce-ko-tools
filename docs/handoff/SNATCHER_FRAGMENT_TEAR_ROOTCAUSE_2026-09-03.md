## 7. 남은 가설과 다음 한 판

목록은 프레임 N 에 **이미 만들어져 있다** (0.5.130/131: 다음 프레임에 정확히 새 칸수와
새 x 로 바뀐다 -> 계산은 N 에 끝나 있었다).  못 간 것은 **운반**이다.

```
운반 수단   게임이 매 프레임 SATB 256 word 를 VRAM $1000 에 올린다
그 프레임   그 256 word 가 우리 자리로 떨어진다              0.5.132
왜          우리가 MAWR 을 가져가고 안 돌려준다
```

즉 "삭제 타이밍" 과 "MAWR 미복원" 은 다른 얘기가 아니라 **증상과 원인**이다.

### 7-0. ★★ 조각 전환의 실제 코드 — 프레임 안 순서 충돌

`tools/build_snatcher_0_4_6_29_native_arm.py` 의 `sched_due` (조각 전환 시점):

```
TAI $1A10 -> selector_cpu, 9     새 selector 9 B 를 CPU 렌더러 이미지에 설치
TAI $1A10 -> stage_cpu, 31       stage 루틴 복원 (앞 rebuild 가 글리프로 덮었다)
STZ ready_cpu                    ready = 0  -> 렌더러 재빌드
INC S_PART                       다음 조각으로
```

그리고 그 위 주석: **"FEC4 는 resident 에서 프레임당 한 번 호출된다."**

한 프레임 안의 순서가 이렇게 된다:

```
①  게임이 우리 list(5 B x N)를 읽어 SATB 로 올린다
②  스케줄러(FEC4)가 selector 를 갈고 ready=0 을 놓는다
③  렌더러가 재빌드 -> 글리프 업로드 + list 재작성
```

**②③ 이 ① 보다 뒤면 그 프레임에 게임이 실어 나른 것은 옛 list 다.**
글리프는 이미 새 것이다.  정확히 측정값("글리프 N / 스프라이트 N+1")이다.

★ 오버클럭이 안 먹히는 것도 이걸로 설명된다 -- 프로그램 순서라 빨라져도 안 뒤집힌다.
★ 소유자가 지목한 "키 전달 시점과 자막 그리는 시점의 충돌" 이 이것이다.

⚠ ①②③ 의 실제 호출 순서는 **아직 안 읽었다.**  resident 에서 FEC4 를 어디서 부르는지,
  게임의 list 소비가 그 앞인지 뒤인지 확인할 것.  위는 구조상 가능한 배치이지 확정이 아니다.

### 7-1. ★ 두 후보를 가르는 판 — 0.5.133 (아직 안 돌림)


둘 다 화면 결과가 같다.  `0.5.133` 이 가른다:


(나)면 렌더러 653 B 를 안 건드리고 **resident 의 호출 순서만** 바꾸는 일일 수 있다.

#### 0.5.133 이 무엇을 고쳤나

`0.5.126` 은 `$15` 가 **19 에서 시작**하는 복원만 잡았다.  렌더러의 글리프 루프는
8·11·14 에서 시작해 전혀 안 걸렸다.  그래서 개선이 0 이었다.
`0.5.133` 은 `$15` 가 **어떤 값에서든** 0 까지 내려오면 MAWR 을 되돌린다.


### 7-2. 그다음 후보 — 이중 버퍼
