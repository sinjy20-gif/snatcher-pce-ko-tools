# 저장 → 타이틀 → 재로드 그래픽 깨짐 — 원인 확정 (2026-08-15 저녁)

> **원인을 잡았고 수정 방침까지 확정했다.** §0 과 §0.5 만 읽으면 된다.
> §9 는 원인 확정 이전의 조사 기록이고, §0 이 그중 일부를 뒤집는다.

## 0. 결론 — 묵은 레코드 캐시가 원인, 96 바이트만 비우면 된다

### 0.1 인과를 직접 건드려 확인했다

Lua 로 실행 중에 캐시를 비우고 로드해서 확인했다 (`lua\PROBE 0.4.4/0.4.5`).
관측이 아니라 **개입**이므로 상관관계가 아니다.

```
타이틀에서 캐시를 비우고 -> 로드 -> 화면 확인
```

| 비운 구간 | 크기 | 결과 |
|---|---|---|
| **$5B80-$5BDF  텍스트/메타데이터** | **96 B** | **깨짐 없음 · 글자 정상 · 게임 정상** |
| $5BE0-$5C3F  상수 슬롯 0-2 | 96 B | 미시험 (지우면 마침표·공백이 깨질 것) |
| $5C40-$5E1F  글리프 슬롯 3-17 | 480 B | 깨짐은 사라지나 메뉴 두 줄이 글자 깨짐 |
| $5E20-$5E3F  슬롯 18 | 32 B | **깨짐 그대로** |
| $5B80-$5E3F  전체 | 704 B | 깨짐은 사라지나 화면이 까맣게 |

**게임이 보는 것은 앞쪽 96 바이트 헤더다.**  그것이 `FF` 면 "레코드 없음" 으로
보고 넘어가므로 타일 전송도 메뉴 재출력도 하지 않는다.  그래서 부작용이 없다.

480 B(글리프)를 비우면 게임은 "레코드는 있는데 글자가 FF" 인 상태로 그려서 메뉴
두 줄이 깨지고, 704 B 전부를 비우면 게임이 아직 쓰는 부분까지 지워 화면이 까맣다.

### 0.1-b 비울 시점은 넓다 — 두 지점 모두 성공

같은 구간의 서로 다른 두 시점에서 지워 봤고 **둘 다 정상**이었다 (2026-08-15 실측).

```
그 문장(미번역 대사) 출력 직후에 삭제   →  정상
타이틀 화면에서 삭제                  →  정상
```

그 문장이 나오면 **반드시 타이틀로 넘어간다.** 즉 두 시점 사이에는 다른 일이
없고, 그 구간 안이면 어디서 지워도 된다는 뜻이다.

그리고 미번역 줄은 조회가 미스라 우리 레코드가 캐시에 새로 들어가지 않는데도
깨졌다. 즉 캐시에 남아 있던 것이 무엇이든, 언제 들어갔든 무관하다 -- **재로드
시점에 헤더가 `FF` 이기만 하면** 게임이 "없음" 으로 보고 넘어간다.

**이것이 §0.5 의 난이도를 크게 낮춘다.** 정확한 한 지점을 찾아야 하는 문제가
아니라, 넓은 구간 중 걸기 쉬운 곳을 고르는 문제다.

### 0.1-c 대사가 떠 있는 중에 지워도 무해하다 — 시점 문제는 없다

그 대사가 **화면에 표시된 상태 그대로** 96 B 를 wipe 하고 진행했다 (2026-08-15 실측).

```
대사 표시 중  →  그 상태에서 $5B80-$5BDF 96 B 를 FF 로
              →  화면의 글자는 그대로 남음
              →  타이틀  →  로드  →  정상
```

캐시는 **글자를 만들 재료**이고 화면은 이미 VRAM 에 찍힌 결과다. 재료를 치워도
찍힌 것은 남는다. 표시 중에 지워도 무해하다는 것이 이것으로 확인됐다.

**따라서 "안전한 순간을 노린다" 는 문제 자체가 없다.** §0.5 의 유일한 미지수였던
"비울 시점" 이 해소된다. 우리 렌더러 훅 `$66E5` 가 이미 그 자리에 있으므로 새 훅도,
타이틀 진입 코드 탐색도 필요 없다. 남은 것은 구현뿐이다.

남은 위험은 하나로 좁혀진다 -- 게임이 캐시를 **다시 읽어 그리는** 경우(저장 메뉴
"계속한다" 복귀). 그 대사 뒤에는 복귀가 없으므로 그 줄에 한정하면 그 위험도 없다.

### 0.2 왜 우리만 깨지나

```
원본    BIOS CD 읽기($EA9E)가 이 버퍼를 계속 갈아준다.  재로드 시점에 FF 였다 (실측)
우리    초기화 때 한 번 채워지고 그 뒤 아무도 안 갈아준다.
        저장 전에 그려둔 레코드가 그대로 남아 재로드 때 읽힌다
```

`$5B80-$5E3F` 는 "안 쓰는 빈 자리" 가 아니라 **게임이 돌려 쓰는 공용 버퍼**였다.
`FF` 는 빈 공간이 아니라 "여기는 없음" 이라는 값이다.

### 0.3 그래서 수정은

```
작별 대사를 그린 시점에 $5B80-$5BDF 96 B 를 $FF 로 채운다
```

**시점 문제는 §0.1-c 로 해소됐다** -- 대사가 떠 있는 중에 지워도 무해하므로 새 훅을
찾을 필요가 없고, 이미 있는 렌더러 훅 `$66E5` 안에서 끝난다. 채우기 자체는 몇
바이트짜리 루프다. 구현 절차는 §0.5.

### 0.4 오후에 쫓던 `$5E22 +165` 전송은 원인이 아니다

세 판 대조(`PROBE 0.3.9`)로 재로드 경로에만 있는 이상 전송을 찾아냈고, 그 길이
165 가 슬롯 18 의 첫 바이트 `$A5` 라는 것까지 확인했다.  기전이 그럴듯했지만
**틀렸다.**

```
PROBE 0.4.3   $5E20 을 $A5 -> $10 으로 직접 덮어써 그 전송을 없앴다
              -> 전송은 사라졌는데 화면은 그대로 깨졌다
PROBE 0.4.5   슬롯 18 을 32 B 통째로 FF 로 비웠다
              -> 역시 깨짐 그대로
```

**같이 나타나던 현상이지 원인이 아니었다.**  직접 건드려 기각한 것이 소득이다 --
관측만 계속했으면 이 선으로 더 팠을 것이다.

## 0.5 남은 것은 훅 지점 하나 — 타이틀 진입에 건다

### 1단계 — 타이틀 진입 지점을 찾는다 (유일한 미지수)

```
타이틀에 들어갈 때 한 번  $5B80-$5BDF 96 B 를 $FF 로
```

**왜 여기인가.** 후보가 둘이었고 둘 다 동작이 확인됐다.

```
매 출력마다 (렌더러 훅 $66E5)   훅은 이미 있다.  깨지지 않는 것도 실측 확인
                                단 대사마다 96 B 전송이 붙는다 -- 593 사이클,
                                약 1.3 스캔라인
타이틀 진입에 한 번              진입 코드를 찾아야 한다
                                대신 재생 중 비용이 0                <- 채택
```

같은 날 폐공장 깜빡임 작업에서 레코드 비용을 5,631 -> 3,829 사이클로 깎았다
(`SNATCHER_KO_0.3.5_RELEASE`). 매 출력 wipe 는 거기에 593 을 도로 얹는다.
타이틀은 세션당 몇 번뿐이라 그 비용이 사실상 없다.

**첫 진입(파워사이클 직후)에도 걸리지만 무해하다.** 그때 캐시는 이미 비어 있고,
원본도 그 시점엔 `FF` 였다는 것이 §0.2 에 실측으로 있다. 그래서 "복귀인지 아닌지"
판정도 필요 없다 -- 타이틀이면 무조건 지우면 된다.

### 찾는 법 — `lua\PROBE 0.5.0.lua`

RAM 스냅샷 차이로 상태 변수 후보를 뽑고, 거기에 쓰기 훅을 걸어 PC 를 잡는다.

```
게임 진행 중        R      기준 스냅샷
저장 -> 타이틀       T      후보 추출 + 훅 자동
로드 -> 저장 -> 타이틀       이때 후보를 바꾼 PC 가 찍힌다
Stop                       census
```

F1-F10 은 세이브 스테이트 키라 쓰지 않는다. 후보가 너무 많으면(64 초과) 훅을 걸지
않고 멈춘다 -- RAM 전체에 훅을 걸면 에뮬이 기어간다.

판정:

```
PC 가 한두 개로 좁혀짐   그 자리가 훅 후보.  JMP 3 B 를 넣을 곳
PC 가 수십 개            상태 변수가 아니라 잡음.  R/T 간격을 좁혀 다시
후보 0 개                R 과 T 사이가 너무 가깝다.  게임을 더 진행하고 R
```

### 1단계 결과 — **철회됨** (2026-08-15 밤). 아래 결론은 틀렸다

> **이 절의 "없다" 는 무효다.** 측정이 답할 수 없는 질문이었고, 전제 하나도 사실이
> 아니었다. 근거는 §0.6 에 있다. 아래는 어떻게 틀렸는지 보려고 남긴다.

찾지 못한 것이 아니라 **그런 코드가 존재하지 않는다.** 대안으로 넘어간다.

**어떻게 확인했나.** `lua\PROBE 0.5.1.lua` 로 타이틀 진입 두 번(A = 파워사이클
직후 최초, B = 저장 후 복귀)의 실행 주소를 교집합했다. `dump\probe_v051_185545.tsv`:

```
A 고유 1007 · B 고유 1200 · 교집합 1007 · A만 0 · B만 193
소수 실행(<=4회) 후보 19 개
```

후보 40개(entry 19 + both 21)의 실행비가 **전부 정확히 1:3 또는 2:6** 이었다.
A=1·B=1 인 주소는 **0 개**. "진입 1회성" 코드가 하나도 없다는 뜻이다.

Mesen 실행 중단점으로 `$7845` 를 잡아 실제 명령을 읽었다 (디스크 이미지로는 못 읽는다
-- `$6000-$7FFF` 는 CD-RAM 이라 Track 02 에 없다. 타이틀 밖에서 디스어셈블러를 열면
뱅크가 달라 `.db` 로만 보인다):

```
7845  INC $08          ; 포인터 하위 증가
7847  BNE $784B
7849  INC $09          ; 상위 자리올림
784B  LDA ($08)        ; 그 포인터가 가리키는 바이트를 읽는다
784D  CMP $2DC0,X
7850  BNE $7853
7852  CLA
7853  DEC
7854  STA $2DC0,X
7857  JMP $7B7C        ; 디스패치 루프로 복귀
```

`$08/$09` 를 한 바이트씩 밀며 읽고 `$7B7C` 로 돌아가는 **게임의 스크립트
인터프리터**다. 후보 4개 덩어리(`$76B8` / `$77B0` / `$7845` / `$7B7C`)가 전부 같은
VM 이며, `$7B7C` 가 그 디스패치 루프다.

**그래서 교집합이 실패한 이유가 설명된다.** 잡힌 것은 "타이틀 진입 코드" 가 아니라
**드물게 쓰이는 스크립트 명령어**다. 1:3 비율도 타이틀을 3번 지나서가 아니라
B 구간에서 스크립트를 3배 더 돌려서다. 게임이 스크립트 VM 으로 돌아가므로 "장면
진입" 이라는 개념이 코드에 없고, **걸 자리 자체가 없다.**

부수 확인: 소유자가 A/B 를 타이틀 화면에서 정확히 눌렀다는 것은 확인됐다
("나 좀 길었을뿐이지 타이틀 화면에서 누른건데 시간이 좀 길뿐"). 측정은 유효했고,
전제가 틀렸다. 재측정할 이유는 없다 -- **PROBE 0.5.0 / 0.5.1 은 여기서 끝난다.**

### 대안 (채택) — 렌더러 훅에서 매 출력마다 지운다

동작은 이미 실측 확인됐다 (소유자: "안깨진다고.... 이미 시험 다 했음").
`$66E5` 훅은 이미 존재하므로 **새 훅도 새 상태도 만들지 않는다.**

비용은 대사마다 96 B, `TII` 로 593 사이클(약 1.3 스캔라인)이다.

**주의 -- 같은 세션의 깜빡임 작업과 충돌할 수 있다.** 폐공장 깜빡임의 원인 A 는
"원자적 블록전송이 IRQ 를 오래 막는 것" 이었고, 608 B `TII/TAI` 를 76 B×8 로 쪼개
해결했다. 여기에 **원자적 96 B 를 도로 얹으면 같은 종류의 부하가 다시 붙는다.**
따라서 구현 시 둘 중 하나로 한다:

```
(a) 96 B TII 를 그대로       593 사이클 · 1.3 스캔라인 IRQ 차단   가장 단순
(b) STA 루프로 채운다        약 860 사이클이지만 IRQ 차단 없음    깜빡임에 안전
```

`LDA #$FF / LDX #95 / .loop STA $5B80,X / DEX / BPL .loop` 는 12 B 안팎이고
헬퍼 여유 17 B 에 들어간다. **총 사이클은 늘지만 차단이 0 이므로 (b) 를 권한다** --
이번 작업에서 확정된 것은 "총량" 이 아니라 "연속 차단 길이" 가 문제라는 것이었다.

미확정: (b) 는 아직 실측하지 않았다. 빌드 후 폐공장에서 깜빡임 회귀를 봐야 한다.

## 0.6 1단계 철회 — 측정이 답할 수 없는 질문이었다 (2026-08-15 밤)

소유자 지적: *"타이틀 화면 켜진 상태에서는 당연히 감지 못하는 거 아닐까"*, *"타이틀
화면 들어가기 전부터 찾아야 되지 않나"*. 맞다. 코드가 그대로 확인해 준다.

### 0.6.1 측정 구간에 전환 순간이 들어 있지 않았다

`lua\PROBE 0.5.1.lua` 사용법 주석 (29·32행):

```
2) 타이틀 화면이 떠 있을 때  **A**        <- 1회차 기록 시작/종료 토글
4) 타이틀이 떴을 때  **B**
```

기록은 **타이틀이 이미 떠 있을 때** 시작한다. 우리가 찾던 전환 순간은 창 밖이다.
진입 코드는 구조상 잡힐 수가 없었다.

판정 기준이 더 결정적이다 (132행):

```lua
if item[2] <= 4 and item[3] <= 4 then   -- "양쪽에서 소수 실행" = 진입 후보
```

정지한 타이틀 루프만 담긴 창에서는 **모든 주소가 루프 몸통**이다. "1회만 실행된
주소 0 개" 는 관측 결과가 아니라 정지 루프를 재면 반드시 나오는 값이다. 없다는
증거가 아니다.

### 0.6.2 "$6000-$7FFF 는 디스크에 없다" 도 틀렸다 — 있다

§0.5 는 `$6000-$7FFF` 가 CD-RAM 이라 Track 02 에서 읽을 수 없다고 적었다. 사실은
그 오버레이가 Track 02 에 그대로 들어 있다.

```
Track 02  sector 251-258  (Mode 1, 섹터당 user data 2048 B)  ->  $4000-$7FFF
CPU 주소 -> user offset   251*2048 + (addr - $4000)
```

세 가지로 교차 확인했다.

```
$7845 의 바이트가 Mesen 이 읽은 명령과 완전히 일치       (§0.5 의 디스어셈블과 동일)
KO 0.3.6 의 $66E5 가 `20 40 5E` = JSR $5E40 = 우리 렌더러 훅
                     원본은 `AD 71 34` = LDA $3471
두 계산이 서로 독립인데 같은 base(sector 251)를 준다
```

**정적으로 읽을 수 있다.** 라이브 프로브에 의존할 이유가 없어졌다. 도구는
`tools\disasm_huc6280.py` 다 (HuC6280 디스어셈블러 + 섹터 매핑).

```
python tools\disasm_huc6280.py --cdram 76B8 77A7     명령표
python tools\disasm_huc6280.py --trace 7668         흐름 추적
```

### 0.6.3 VM 전체를 떴다 — 명령 33 개

`$76B1` 에서 스크립트 바이트를 읽고, `BMI` 로 `$80` 이상이면 명령, 미만이면
`$77A7`(문자 출력)로 간다. `$76B8-$77A7` 이 `CMP #$xx / JMP handler` 사슬이다.

```
$F9 -> $785A   $F8 -> $7886   $F7 -> $78BE   $F6 -> $791B   $F5 -> $780F
$F4 -> (inline $779F)          $F3 -> $77C5   $F2 -> $77CB   $F1 -> $7B32
$F0 -> $77BA   $EF -> $7999   $EE -> $79DB   $ED -> $7A05   $EC -> $7A2F
$EB -> $7A5F   $EA -> $7934   $E9 -> $7A8F   $E8 -> $7AB9   $E7 -> $77DC
$E6 -> $7833   $E5 -> $7983   $E4 -> $79AD   $E3 -> $78E7   $E2 -> $78B2
```

`$FF`(`$7841`) 만 `JSR $75B0 / RTS` 로 **디스패치 루프로 돌아가지 않는다** — 나머지는

VM 은 X 로 인덱스되는 **태스크 슬롯 구조**다 (`$2DC0,X` 프로그램 카운터,
`$2700,X`/`$2740,X` 스크립트 베이스, `$2E00,X` 재시작 플래그).

### 0.6.4 "장면 진입" 코드는 존재한다 — `$53BD`

§0.5 는 "게임이 스크립트 VM 으로 돌아가므로 장면 진입이라는 개념이 코드에 없다" 고
적었다. 스크립트 베이스 `$2700,X`/`$2740,X` 에 쓰는 코드를 디스크 전체에서 찾으니
나온다.

```
$53BD   태스크 스폰 루틴
        $FA/$FB 가 가리키는 표에서 슬롯 번호와 필드들을 읽어
        $27C0,X $2800,X $2880,X $28C0,X $2F00,X $2F40,X
        $2700,X $2740,X  <- 스크립트 베이스
        $2F80,X $2EC0,X $3000,X 를 채우고
        $2DC0,X = $FF · $2E00,X = $FF  (PC 리셋 · 재시작 표시)
        -> $73CD / $74BB 로 복귀
```

같은 루틴이 다른 뱅크(sector 248)에 한 벌 더 있다.

**이것이 "새 스크립트를 건다" 는 단 하나의 원시 동작이다.** 타이틀도 스크립트로
돌아간다면 타이틀 진입은 반드시 여기를 지난다. 대사 중에는 실행되지 않으므로
재생 중 비용도 0 이다 — §0.5 가 원하던 조건 그대로다.

### 0.6.4-b 단 `$53BD` 자체는 훅 자리가 아니다 — 부르는 곳이 없다

`$53BD` 를 호출/점프하는 코드를 디스크 전체에서 (플랫 스트림과 raw 이미지 양쪽으로)
찾았고 **0 건**이다. 유일한 raw 매치 1 건은 Mode 1 섹터의 ECC 영역이라 잡음이다.

```
JSR $53BD   0 건
JMP $53BD   0 건 (ECC 영역 우연 매치 1 제외)
```

`$53BD` 사본은 텍스트 오버레이(sector 251-258) 안에서는 **죽은 코드**다. 살아 있는
쪽은 sector 248 의 다른 사본이고, 그것은 참조가 전부 `$4xxx` 다 (`JSR $4DE9` 로 다음
스크립트 바이트를 하나씩 읽고, `JMP $4A2C` / `JMP $49CF` 로 복귀). 즉 **자기 오버레이
안에서 완결**된다.

그 오버레이의 적재 주소는 아직 못 박았다. "sector 247-250 → `$4000-$5FFF`" 를 걸어
보면 루틴이 `$4A1E` 근처가 되고 참조가 전부 창 안에 들어와 그럴듯하지만, 그 주소를
부르는 코드가 역시 안 나온다. **가정 확인 실패이므로 채택하지 않는다.**

```

```

그 RAM 쓰기에 훅을 걸면 **쓴 PC 가 곧 살아 있는 스폰 루틴의 주소**다. 적재 베이스를
알 필요가 없어진다. 대사 시점은 우리 렌더러 훅 `$66E5` 를 같이 찍어 표시하므로 한
판에 셋이 나온다.

```
1) 살아 있는 사본의 CPU 주소      pc 컬럼
2) 어떤 스폰이 어떤 베이스를 받나  slot / value 컬럼
3) 그것이 대사 전인가 후인가       dialogue 행과의 순서
```

판정:

```
마지막 dialogue 뒤에 spawn    그 spawn 이 타이틀 진입.  훅 자리 확정
마지막 dialogue 앞이 끝       타이틀은 스폰을 거치지 않는다.  이 선은 닫힌다
```

**후자가 나오면 그때는 정말 닫아도 된다** -- 이번에는 전환 순간이 측정 구간 안에
들어 있고, 판정이 "1회 실행" 같은 간접 지표가 아니라 그 동작 자체이기 때문이다.
그 경우 §0.5 의 매 출력 wipe 로 간다.

오버레이 로더(어느 섹터를 어디로 읽는지)를 뜨는 일은 이제 필요 없다 -- PC 가 곧

## 0.6.8 스폰 루틴 확정 — `$73BD`, 장면 VM 의 명령 2번

### 뱅크를 잘못 짚고 있었다

`$4000-$7FFF` 를 sectors 251-258 이 연속으로 채운다는 §0.6.2 의 그림이 틀렸다.
오버레이는 **전부 `$6000-$7FFF` 한 창에 번갈아 올라가는 8 KB 뱅크**다.

```
bank A   sectors 251-254  ->  $6000-$7FFF    장면 VM · 스폰 루틴 $73BD
bank B   sectors 255-258  ->  $6000-$7FFF    텍스트 VM $7845 · 우리 훅 $66E5
```

`$66E5`/`$7845` 가 맞았던 것은 둘 다 bank B 여서다. bank A 를 `$4000` 기준으로 읽은
탓에 스폰 루틴이 "`$53BD` 에 있는데 부르는 데가 없는 죽은 코드" 로 보였다 (§0.6.4-b).
**같은 바이트, 틀린 페이지였다.** 살아 있는 코드이고 주소는 `$73BD` 다.

검산: `$73F8`(STA $2700,X)의 디스크 오프셋 519160 은 bank A 시작(514048)에서
`$13F8`, 런타임 PC `$73FB`(STA 다음 명령)와 정확히 맞물린다. `PROBE 0.6.5` 가
`pceMemory` 로 떠 온 바이트도 같다.

도구는 `--bank A|B` 로 고쳤다.

```
python tools\disasm_huc6280.py --bank A --cdram 73BD 742B
```

### 구조

```
7322  B2 FA        LDA ($FA)          장면 스크립트 바이트
7324  C9 FF        CMP #$FF
7326  D0 02        BNE
7328  18 60        CLC / RTS          끝
732A  20 7F 47     JSR $477F          디스패처
732D  ...          핸들러 표가 JSR 뒤에 인라인
```

`JSR` 복귀주소를 표 베이스로 쓰는 방식이다. 표는 10 개.

```
op 0 $7341   op 1 $7382   op 2 $73BD <- 스폰   op 3 $742D   op 4-6 $744C
op 7 $746F   op 8 $749E   op 9 $74B1
```

`$73BD` 는 `$FA/$FB`+2 의 표를 읽어 슬롯마다 필드를 채우고, `$FF` 를 만날 때까지
`JMP $73CD` 로 돈다 (`$FF` 면 `JMP $74BB`). **한 명령이 여러 태스크를 건다.**

### 그래서 훅 자리

```
$73BD 핸들러 안.  bank A = track 02 sector 251-254 -- 우리가 이미 패치하는 트랙이다
```

베이스 상위 바이트로 타이틀만 고를 수 있다 (`$95`). 무엇보다 **스폰은 드물다**.

```
스폰      세션당 9 회
대사      세션당 572 회
```

§0.5 의 매 출력 wipe 는 593 cycles x 572 = 약 339,000 cycles 다. 스폰 훅은 9 회이고,
타이틀만 고르면 실질 2 회다. **재생 중 비용이 사실상 0** 이라는 §0.5 의 원래 목표가
그대로 달성된다.

남은 구현 문제는 분석이 아니라 자리다 -- bank A 안에 wipe 코드를 넣을 여유 공간을
찾는 것. `$73BD` 핸들러를 우리 헬퍼로 우회시키는 형태가 될 것이다.

## 0.7 구현 — `$73BD` 를 헬퍼로 우회시켰다 (2026-08-15 밤)

### 0.7.1 주소를 세 번째로 짚기 전에 통째로 떴다

§0.6.2 와 §0.6.8 의 섹터 매핑이 둘 다 틀렸었다. 세 번째 추측 대신 타이틀 스폰
순간의 `$4000-$7FFF` 16 KB 를 통째로 뜨고(`lua\PROBE 0.6.6.lua`), 그 8 KB 씩을
빌드된 디스크에서 찾았다. **각각 정확히 한 곳씩** 나온다.

```
$4000-$5FFF  <-  sectors 247-250  (offset 505856)   캐시 $5B80 · 프리로더 $5E40
$6000-$7FFF  <-  sectors 251-254  (offset 514048)   장면 VM · 스폰 핸들러 $73BD
```

원본과는 안 맞고 KO 빌드와만 맞는다 -- 우리가 이미 그 섹터들을 패치한다는 뜻이다.
`$2000` 오차의 정체도 이것으로 설명된다: `$4000-$5FFF` 는 247-250 인데 251-254 로
잡고 있었다.

런타임 실측도 전부 맞았다.

```
$73BD  a5 fa 18 69 02 ...    스폰 핸들러
$732D  41 73 82 73 bd 73     핸들러 표
$7FCF  ff x 17               여유 공간
$5B80  82 ff ff 01 3e ...    캐시 (FF 아님) <- wipe 대상
$66E5  d4 29 7f ...          우리 훅이 아니다 = 타이틀에 렌더러 오버레이는 비상주
```

**마지막 줄이 중요하다.** 타이틀 시점에 `$66E5` 자리에는 다른 오버레이가 들어와
있다. §0.5 의 "매 출력 wipe" 는 렌더러 안에 있으므로 타이틀에서는 돌 수 없다 --
지금 자리가 맞는 자리다.

### 0.7.2 넣은 것

`extraction\patch\static\patch_title_cache_wipe.py`.

깜빡임 작업에서 확정된 것은 "총량" 이 아니라 "연속 차단 길이" 였다 (§0.5 (b)).

EDC/ECC 는 `build_disc_patch.rebuild_mode1_sector` 로 sector 253·254 를 재계산한다
(빌더도 그렇게 한다 -- 실측 확인).

### 0.7.3 무조건 wipe 다 -- 의도한 선택

헬퍼는 타이틀만 고르지 않고 **모든 스폰에서** 돈다. 조건 분기를 넣지 않은 이유:

```
스폰      세션당 9 회      x 약 860 cycles = 약 7,700
대사      세션당 572 회    x 593 cycles   = 약 339,000  (§0.5 안)
```

9 회면 비용이 없는 것이나 마찬가지고, §0.1 에서 96 B wipe 는 **어느 시점에 해도
무해**했다 (대사 표시 중에도, 타이틀에서도). 조건을 넣으면 코드가 길어지고 여유
17 B 를 넘길 위험이 있다.

**회귀가 보이면 여기를 조인다.** 베이스 상위 바이트가 `$95` 일 때만 wipe 하도록
좁히면 실질 2 회가 된다 (타이틀 서명, §0.6.7).

### 0.7.4 검증 -- 다음 세션이 할 일

```
필수   저장 -> 타이틀 -> 로드 를 3 회.  깨짐 0 · 글자 정상 · 진행 정상
필수   파워사이클 -> 로드 (경로 A).  기존에 정상이던 경로가 안 깨지는지
필수   폐공장에서 대사 몇 줄.  깜빡임 회귀가 없는지 · 분수공백이 멀쩡한지
필수   장면 전환을 여러 번.  무조건 wipe 의 부작용이 없는지 (§0.7.3)
권장   본부 등 다른 장소에서 한 번 더
```

채택안 "매 출력 wipe" 는 그대로 살려 둔다 — **동작이 실측된 유일한 안**이고, 위
정적 분석이 막히더라도 배포를 막지 않는다.

### 9.0 왜 이것이 1순위인가

폐공장 깜빡임과 달리 **이것은 배포를 막는다.**

```
깜빡임      특정 장면에서만, 한 프레임, 자동 복귀.  진행·세이브 손상 없음
이 문제     저장 후 재개마다 100%.  화면 타일이 깨진 채로 남는다
```

저장 후 재개는 플레이어가 가장 흔히 하는 행동이다. 배포하면 거의 모두가 만난다.

### 9.1 확정된 것 — 100% 재현이고 완전한 비대칭이다

소유자 실측(2026-08-15):

```
경로 A   파워사이클 → 게임 내 로드            정상.  한 번도 안 깨짐
경로 B   플레이 → 저장 → 타이틀 → 같은 슬롯 로드   100% 깨짐
```

**0.3.5 에서도 재현된다** (2026-08-15 확인). 0.3.4 의 팩 선적재로 재생 중 CD 접근이
사라졌는데도 그대로다 — 이 문제는 CD 접근 패턴과 무관하다는 뜻이고, 깜빡임 쪽
대책이 여기에는 아무 영향이 없다는 §7 의 예상이 맞았다.

**로드 코드는 같다.** 그런데 한쪽만 깨진다. 그리고 파워사이클이 고친다.

#### 9.1.1 깨짐 모양이 단서다 — BAT 쪽일 가능성

0.3.5 재현 화면은 **일정 간격의 세로 줄무늬**다. 화면 전체(그림 바깥 영역 포함)에
같은 간격으로 파랑·빨강 줄이 선다.

```
우리 코드 바이트가 타일 그림으로 읽혔다면   무작위에 가까운 노이즈가 나와야 한다
실제                                      규칙적인 세로 줄무늬
```

규칙적이라는 것은 **BAT(타일맵)가 덮였을 때의 모양**에 가깝다. 몇 칸마다 같은 타일
번호를 가리키게 되면 정확히 이렇게 보인다. 케이브는 코드 끝과 스크래치 사이가 `FF`
패딩이고 스크래치는 대부분 0 이라, 그런 규칙적인 바이트열이 BAT 로 들어가면 이 그림이
된다.

#### 9.1.2 디버거로 확인 — BAT 와 스프라이트가 **동시에** 오염된다

Mesen 의 타일맵 뷰와 스프라이트 뷰를 각각 확인했다(2026-08-15).

```
타일맵    넓은 영역이 균일한 값으로 채워져 일정 간격 세로 줄무늬가 됨
          (그림이 두 번 보이는 것은 BAT 가 화면보다 넓어서 생기는 정상 표시)
스프라이트 여기에도 같은 성격의 세로줄 뭉치가 들어와 있음
한글 메뉴  그 위에 멀쩡히 그려진다 -- 우리 렌더러는 정상 동작 중
```

**두 곳이 동시에 깨진다는 것이 중요하다.** 전송 한 번이 잘못된 것이 아니라, VRAM 의
서로 다른 목적지로 가는 **여러 전송이 연달아** 같은 잘못된 소스를 읽고 있다는 뜻이다.
그리고 이것이 §3 가설과 정확히 맞는다 — 포인터 하나가 낡으면 그 포인터를 쓰는 모든
전송이 함께 빗나간다.

균일하게 채워진다는 것은 **소스가 반복되는 바이트열**이라는 뜻이다. 케이브에는 실제로
그런 구간이 있다.

```
코드 끝    $BCD2 + 765 = $BFCF
FF 패딩    $BFCF ~ $BFDF
스크래치   $BFE0 ~        (대부분 0)
```

`FF FF FF…` 나 `00 00 00…` 이 BAT 로 들어가면 같은 타일이 반복되고, 그 타일에 세로선이
있으면 이 그림이 된다.

#### 9.1.3 그래서 프로브는 목적지도 기록해야 한다

`PROBE 0.3.6` 은 소스 포인터만 본다. 그것으로는 "빗나갔다"까지만 알 수 있고, **되돌릴
범위**는 알 수 없다. VDC 의 MAWR(레지스터 $00)을 따라 전송 목적지를 함께 기록하면
다음이 갈린다.

```
목적지가 BAT · SATB 영역에 한정   되돌릴 대상이 좁다
                                 → §6 의 "그래픽만 재적재" 가 급격히 싸진다
패턴 영역까지 넓게 흩어짐         타일 그림 자체가 깨진 것.  재적재 범위가 커진다
```

다음 프로브(0.3.7)는 **소스 포인터 · 목적지 · 전송 길이**를 한 줄에 담을 것.
한 번 실행으로 "무엇을 어디로 얼마나" 가 전부 나온다.

이 두 사실이 함께 말하는 것은 하나뿐이다.

> 소프트 복귀 경로에서 **초기화되지 않는 값**이 있고, 그 값은 전원을 내려야
> 리셋된다.

어제 문서는 이 비대칭을 "설명되지 않는 모순"으로 남겼는데, 100% 재현이 확인되면서
**모순이 아니라 단서**가 됐다. 확률적 사고가 아니라 결정적 사고로 접근할 수 있다.

| 후보 | 근거 |
|---|---|
| AC 상태 오염 (magic/flags/atlas) | 소프트 복귀 후에도 **불변** (§4 실측) |

외과적"이라고 본 안인데, 그 전송이 우리 전송인지 알 방법이 없어서 성립하지 않는다.

### 9.3 [기각됨] 남은 가설 — 전송원 포인터

깨진 화면을 만드는 루프는 이것이다.

```asm
B1 12    LDA ($12),Y      ← 제로페이지 $12/$13 이 전송원을 가리킨다
20 B0 71 JSR $71B0        ← VDC 전송
C8 / C4 01 / D0           INY / CPY $01 / BNE
```

전송원이 **포인터 하나**로 정해진다. 부팅 때는 세팅되는데 소프트 복귀에서 갱신이
빠지면, 낡은 값이 남아 원래 `FF` 였고 지금은 우리 코드가 있는 자리를 소스로 읽는다.

이 가설은 관측을 전부 설명한다.

| 관측 | 설명 |
|---|---|
| 재시작하면 정상 | 포인터가 새로 세팅됨 |
| 우리 코드가 타일로 그려짐 | 낡은 포인터가 그 자리를 가리킴 |
| 0.2.26 · ac_0.1.14 · 0.3.x 전부 발생 | 모두 예전 `FF` 자리에 코드를 넣음 |
| 순정은 멀쩡 | 같은 자리를 읽어도 `FF` 라 무해 |
| AC 상태는 불변 | 상태 오염이 아니라 **읽기 대상만** 빗나감 |

**아직 검증되지 않았다.** §4 가 이 실험을 지정했으나 미실행이다.

### 제로페이지의 실제 위치 — 틀리기 쉬운 곳

```
MPR1 = $F8 이라 RAM 이 CPU $2000 부터다
따라서 $12/$13 은 $2012/$2013
CPU $0012 는 MPR0=$FF (I/O 페이지) -- 읽으면 항상 $FF
```

통합 인계서 §12-2 의 `$F8` / `$20F8` 함정과 같은 계열이다.

### 9.4 [불필요] 실험 — `lua\PROBE 0.3.6.lua`

100% 재현이므로 **한 번 실행에 두 경로를 다 담는다.**

```
Run  (빌드는 디스크 이름에서 자동 판별)
  경로 A   파워사이클 상태에서 게임 내 로드 → 대사 몇 줄
  Q        A 구간 종료
  경로 B   저장 → 타이틀 → 같은 슬롯 재로드 → 대사 몇 줄 (깨짐 확인)
  Q → Stop (census 는 Stop 에서만 남는다)
```

무엇을 재는가:

```
$70BF 이 실행될 때마다 그 순간의 $2012/$2013 값을 읽는다
```

포인터를 **쓰는 쪽**이 아니라 **쓰이는 순간**을 본다. 어느 코드가 세팅했는지와
무관하게 실제 값이 잡히므로, 세터를 못 찾아도 답이 나온다.

`$5B80-$5E1F` 캐시를 가리키는 것은 세지 않는다 — 거기는 글리프 데이터라 `$70BF` 가
읽는 것이 정상이고, 그것까지 세면 평상시 폰트 전송에 묻힌다.

### 판정

```
A 와 B 의 상위 포인터가 다르다      원인 확정.  초기화 누락 한 곳이고 국소적
                                   → 복귀 경로에서 그 값만 다시 세팅하면 끝날 가능성
같다                               포인터는 무죄 → 원본 디스크 대조(§5)로
B 에서만 패치 구간을 가리킨다        그것이 곧 답
```

**"국소적인가"까지만 증명하고, 고치는 비용이 크면 보류"** 라는 기존 방침에 맞는
실험이다. 화면 깨짐이 더 큰 오염의 첫 증상인지 아닌지가 여기서 갈린다.

### 프로브 작성 시 함정 (이 저장소에서 실제로 밟은 것들)

```
F5 를 마커로 쓰지 말 것    Mesen 의 세이브 스테이트 저장 키와 겹친다.
                          누를 때마다 스테이트가 덮어써진다.  0.3.6 은 Q 를 쓴다
BUILD 를 손으로 맞추지 말 것  08-15 에 틀려서 1,538 프레임을 0 으로 기록했다.
                          0.3.6 은 디스크 이름에서 자동 판별한다
Stop 을 잊지 말 것         census 가 Stop 에서만 기록된다.  08-15 에 두 번 놓쳤다
나눗셈 결과에 %d 금지       Lua 5.4 는 정수 표현 없는 실수를 거부한다.  %.0f 를 쓸 것
```

### 9.5 A/B 가 같게 나올 때 — 원본 디스크 대조

`PROBE 0.3.6` 은 `$BCD2-$BFFF` 를 감시할 뿐이라 **원본 디스크에서도 그대로 돈다**
(트램폴린 훅이 안 걸릴 뿐 무해). 원본으로 같은 A/B 를 돌려 비교한다.

```
A·B 모두 그 자리를 읽음    원본도 읽고, FF 라서 무해했던 것
                          → 원인은 "우리가 그 자리를 썼다" → 재적재 쪽으로
B 에서만 읽음              소프트 복귀만 그 경로를 지난다.  우리 훅과 무관
A·B 모두 안 읽음           우리 훅이 그 경로를 만든 것
                          → $66E5 / $5E40 / $7F50 을 하나씩 끄고 이분탐색
```

### 9.7 이 문제와 폐공장 깜빡임은 다르다

혼동 방지를 위해 적어 둔다. 08-14~15 에 깜빡임 쪽은 원인이 규명됐고 0.3.4/0.3.5 로
크게 줄었지만, **이 문제에는 아무 영향이 없다.**

