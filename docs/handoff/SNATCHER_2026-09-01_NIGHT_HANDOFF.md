## 2. 오늘 실측으로 지운 것들

### 2-1. VRAM 전체 (0.5.91 + `tools/compare_vram_dumps.py`)

원본과 패치본에서 VRAM 64 KB 를 세 시점에 떠서 블록 대조했다.

```
챕터1 시점   $4800-$4FFF · $6C00-$6FFF 만 다름
+4200        $6F00-$6FFF 256 word · SATB $105E/$1076 각 1 word
$7900-$7DBF  완전히 같음
BAT          완전히 같음
```

`$6F00` 은 **자막을 한 글자도 안 그린 #1 시점에 이미 256/256 이 다르고**, 양쪽 다
주행 내내 안 변한다 -> 우리가 만든 차이가 아니다 (번역 디스크가 다른 데이터를 올린다).
SATB 두 칸은 y/x/팔레트가 같고 pattern 만 다르다 -> 게임 스프라이트의 애니메이션 위상.

### 2-2. 팔레트 (0.5.92 + `tools/compare_palette_dumps.py`)

```
512 엔트리 중 다른 것 2 개.  둘 다 스프라이트 팔레트 15
  색 1   원본 000 -> 패치 1FF   우리 글자색
  색 15  원본 0C7 -> 패치 08D   #1 부터 이미 다름
```

### 2-3. 영구 발자국 — 한 주행 안에서 (0.5.93)

원본 대조는 두 주행의 진행이 어긋나 장면이 안 맞는다는 지적을 받았다 (소유자).
그래서 대조를 버리고 한 주행 안에서 쟀다 — 임대 중 우리가 쓴 word 를 값까지
기억했다가 한참 뒤 살아남았는지 센다.

```
우리가 쓴 word 1284
  1216  $7900-$7DBF 가 그대로 남음   <- 복원이 되쓴 값.  원본과 같다고 이미 확인됨
    68  덮였다                       <- SATB.  게임이 매 프레임 다시 쓴다
```

**해로운 영구 발자국이 하나도 없다.**

### 2-4. VDC 레지스터 (0.5.94 / 0.5.96)

```
우리가 건드리는 레지스터 :  $01 MARR · $00 MAWR · $02 VWR   (셋뿐)
스크롤 BXR/BYR · MWR · 창 HDR/VDW · CR · DVSSR   전부 안 건드림

안 되돌리는 것
  $01 MARR   진입 $0000 -> 반환 $7900   (반환 뒤 첫 게임 접근 pc $60AC)
  $00 MAWR   진입 $1000 -> 반환 $7D40   (pc $6506)
```

MARR 이 새로 나왔다 -- **VRAM 읽기 주소**이고, 오늘 한 측정은 전부 쓰기만 봤기
때문에 안 보였다.  게임 `$60Ax` 는 MARR 로 읽고 MAWR 로 쓰는 복사 루틴으로 보인다.

그래서 Lua 로 반환 직전에 되돌려 봤다 (0.5.96 · 게임 코드 무수정).

```
MODE 'marr'  -> 깨짐
MODE 'both'  -> 깨짐
```

**VDC 레지스터 노선도 종료.**

## 3. 남은 후보 — CPU RAM (내일 여기부터)

오늘 본 것은 전부 **화면 쪽 자원**이다.  그런데 우리는 화면 밖에서도 빌린다.

```
$5B80-$5E1E   게임 레코드 캐시.  helper/renderer 를 매 프레임 여기 복사한다
              반납할 때 첫 바이트만 STZ 로 지운다.  **원래 내용은 안 돌려준다**
제로페이지    렌더러/상주부가 $08-$11 · $16 · $17 을 쓴다 ($17 에 $3F 를 박는다)
```

게임이 CD-DA 뒤에 그 캐시를 읽으면 **우리 엔진 바이트를 자기 데이터로 읽는다.**
그러면 "게임이 그리긴 그렸는데 엉뚱한 것을 그렸다" 가 설명되고, 화면 자원이 전부
멀쩡한 것도 같이 설명된다 -- 우리가 화면을 망친 게 아니라 게임이 잘못된 재료로
그린 것이 된다.

### 내일 첫 프로브 (아직 안 만듦)

**읽기 콜백 한 방이면 판정된다.**

```
emu.callbackType.read 를 $5B80-$5E1E 에 건다
임대가 끝난 뒤 게임(PC 가 그 범위 밖)이 거기를 읽는가
읽으면 어느 PC 에서 · 어느 주소를 읽는가
```

읽으면 원인 확정이고, 고치는 방법도 정해져 있다 -- **빌리기 전에 그 512 B 를
어딘가에 저장했다가 반납할 때 되돌린다** (AC 에 자리는 있다).
안 읽으면 CPU RAM 도 지워지고, 그때는 ADPCM/CD-ROM 레지스터와 BIOS 작업 RAM 이 남는다.

## 5. ⚠ 오늘 밟은 함정 (다음에 또 밟지 말 것)

### 5-1. Track 24 를 안 갈면 헬퍼 수정이 디스크에 안 들어간다

`.43/.47` 체인은 Track 24 를 기준판에서 **통째로 복사**하고 끝에 native bundle 만
덧붙인다.  헬퍼 소스를 고치고 빌드해도 디스크에 실리는 것은 옛 헬퍼다.

```
python tools/build_snatcher_0_4_6_XX_....py
python tools/patch_track24_helper.py 0.4.6.XX --write      ★ 이걸 빼먹으면 무효
python tools/restore_track24_cdda_engine.py 0.4.6.XX --write
```

### 5-2. 렌더러의 런타임 y 계산을 상수로 바꾸면 자막이 죽는다

`0.4.6.53/.54` 의 CD-DA 렌더러가 `.48` 과 47 B 달랐다.

```
.48  18 AD 1E 5D 69 40 85 08 A9 00 69 00 85 09   y = record+3 을 읽어 +$40 (16bit)
.5x  64 08 A9 01 85 09                           y = $0100 상수 (-8 B)
     ... 20 63 64 [03 00 13 00 23 10 03 02] 60   그 8 B 로 MAWR 복원을 넣었다
```

671 B 슬롯에 죽은 바이트가 없어서 자리를 그렇게 만들었는데, 그 계산이 곧
**자막 세로 자리(위/중간/아래)** 기능이다.  상수로 바꾸면 기능이 죽는다.
`$5D9A-$5DD9` 의 64 B 도 빈 자리가 아니다 -- `TIA $5D5A,$0002,128` 이 VRAM 에
올리는 글리프의 빈 오른쪽 절반이다.

### 5-3. 프로브 출력 필터가 TSV 까지 막으면 안 된다

`0.5.95/0.5.96` 이 `if hits <= 8 or hits % 200 == 0` 안에서 `say` 와 `rec` 를
같이 했다.  그래서 `$5C3F`(복원 끝) 가 실제로 걸렸는지 **파일로도 확인할 수 없었다.**
자리별 첫 적중은 무조건 기록하게 고쳤다.

### 5-4. 진입 지문은 헬퍼가 슬롯에 있을 때 읽어야 한다

`0.5.91` 이 61 프레임에 `$5B83` 을 읽어 "어느 판인지" 를 찍게 했는데, 그 시점엔
어느 빌드든 슬롯이 비어 있어 판별이 안 된다.  CD-DA 중에 읽어야 한다.

### 5-5. Mesen Firmware 의 BIOS 가 우리 빌드로 덮여 있다

```
Firmware/[BIOS] Super CD-ROM System (Japan) (v3.0).pce         = 0.4.6.58 빌드
Firmware/...pce.JP_ORIGINAL / .ORIGINAL_BAC                    = E11527B3B96CE112 (진짜 원본)
```

소유자는 Mesen 옵션에서 BIOS 를 직접 고르므로 오늘 결과는 유효하다.  다만 원본
대조를 할 때는 `.JP_ORIGINAL` 을 명시적으로 골라야 한다.

### 5-6. `emu.getState()` 를 뜨거운 경로에서 부르면 1 fps 가 된다

`0.5.83` 이 VDC 포트 쓰기마다(한 판에 2,002,915 회) 불러서 그렇게 됐다.
소유자 판정은 **exec 콜백 플래그**로 하고, PC 조회는 보고할 때만 한다.

## 7. ★ 안 풀린 것 — 0.5.77 은 왜 됐나

이것이 내일 가장 먼저 답해야 할 질문이다.  오늘 자료를 다 놓고 보면 **모순**이다.

```
                대역 $7900-$7DBF 내용        화면
원본            원본 내용                    정상
0.4.6.48        원본 내용 (복원이 되돌림)     깨짐     <- 내용이 같은데 결과가 다르다
0.5.77 (Lua)    원본 내용 + 우리 글자        정상
0.4.6.56/.58    우리 글자 / 0                깨짐
```

**대역 내용으로는 어느 쪽도 설명되지 않는다.**  원본과 `.48` 은 그 대역이 같은데
한쪽만 깨진다.  그러므로 `0.5.77` 의 성공도 "백업을 최신으로 갱신해서" 가 아닐
가능성이 크다.  인과를 잘못 짚었을 수 있다.

`0.5.77` 이 실제로 한 일은 두 가지뿐이다.

```
1. helper ENTRY($5B83) 에 exec 훅을 걸었다 (cmd != 0 · base $7900 일 때만 동작)
2. AC $1F0400 에 현재 VRAM 2,432 B 를 emu.write 로 써 넣었다
```

VRAM · 팔레트 · SATB · VDC 는 오늘 전부 지워졌으므로, 남는 것은 **2 번의 AC 기입**
이거나 **그 훅 자체** 이거나, 아니면 애초에 `0.5.77` 의 "정상" 관측이 개입과
무관했던 것이다.

### 내일 첫 실험 -- 무개입 대조군 (5 분)

`0.5.77` 과 **모든 것이 같되 AC 에 한 바이트도 안 쓰는** 판을 만든다.
같은 자리에 훅을 걸고, 같은 조건을 보고, 로그만 찍는다.

```
멀쩡하다   -> 0.5.77 의 성공은 갱신 때문이 아니었다.
              "복원 내용" 노선은 완전히 폐기.  오늘 밤 절반이 재해석된다
깨진다     -> AC 기입이 진짜로 뭔가를 고치고 있다.
              그러면 AC $1F0400 대역을 게임이 읽는지부터 본다
```
