# SNATCHER 9월 11~13일 환경 B 인계서

작성 시각: 2026-09-13 밤  
현재 유지 버전: **0.7.11** (`0.8`은 별도 지시 전까지 보류)

## 0. 내일 가장 먼저 볼 것

1. 이 패키지의 `GAME_BUILD/0.7.11`은 오늘 실기 확인에 사용한 완전 실행판이다.
2. 번역 정본은 `snatcher_tool/translation/snatcher_ko_master.tsv`다. 이 파일은
   실행판을 만든 뒤 57개 미번역 대사와 충돌 1건을 더 반영했으므로, **동봉 실행판에는
   그 마지막 번역분이 아직 구워지지 않았다.** 사용자가 빌드를 보류한 상태가 맞다.
3. 현재 정본을 과거 파일로 통째로 덮거나 되돌리지 않는다. 병합이 필요하면 키 단위로만
   비교하고, 먼저 별도 백업을 만든다.
4. 가우디 키패드는 아직 배포 기능이 아니다. test1~4는 실패 원인을 가른 시험판이며
   패키지에는 용량 절약을 위해 재생성 스크립트·매니페스트·로그만 싣는다.
5. 환경 B에서 이어갈 첫 기술 작업은 `dump/probe_gaudi_search_v011.tsv`의 `$C985`
   후보 문자열 포인터가 어느 디스크 표에서 로드되는지 찾는 것이다.

## 5. 가우디 완성형 한글 키패드

- 자모 조합기는 만들지 않는다.

기 길 깁 나 느  닝 덤 디 라 랜  레 리 린 마 메  미 반 벤 벨 사

### 오늘 마지막 측정에서 새로 확정된 것

`lua/PROBE_GAUDI_SEARCH_0.1.1.lua`를 원본 0.7.11과 전체 `ギブスン` 입력에 사용했다.
`dump/probe_gaudi_search_v011.tsv`에 성공 비교가 기록됐다.

```text
frame 7930
compare PC  $BA00 / $BA19
input       $363E부터 83 4D 83 75 83 58 83 93 FF  (= ギブスン)
D4:D5       $0985
candidate   CPU $C985
candidate   83 4D 83 75 83 58 83 93 FF  (= ギブスン)
MPR         FF F8 68 69 7C 7D 7E 00
```

즉 `$C985`는 성공 시 실제로 비교한 후보 문자열이다. 다음 작업은 이 RAM 표를 만든
디스크 원본/로더를 역추적하여 토큰 문자열과 필요한 길이·메타데이터를 함께 바꾸는 것이다.
기능 검색이 성공하기 전에는 아래 BG 키패드 그래픽을 먼저 완성하지 않는다.

## 6. 환경 B에서 합치는 법

기존 환경 B `C:\snatcher`를 통째로 지우거나 미러 동기화하지 않는다.

1. 기존 환경 B 정본과 패키지 정본의 SHA-256을 비교한다.
2. 환경 B 정본에 패키지보다 새 변경이 있으면 키 단위 병합 후 새 백업을 만든다.
3. 패키지 `project/`를 `C:\snatcher`에 **삭제 없이** 덮어쓴다.
4. 패키지 `snatcher_tool/`을 `C:\snatcher\snatcher_tool`에 **삭제 없이** 덮어쓴다.
5. `GAME_BUILD/0.7.11`은 실행 보관본이다. 빌더가 기대하는 경로가 비어 있으면
   그대로 `C:\snatcher\build\patch\0.7.11`에 복사한다.
6. 가우디 상태를 바로 이어가려면 `TEST_STATE/`의 sav/mss를 원래 Mesen 폴더에
   복사하되 기존 파일은 먼저 별도 이름으로 백업한다.
7. 검사:

```powershell
python C:\snatcher\tools\check_build_invariants.py 0.7.11
```

## 7. 금지선

- 특별한 지시 전까지 버전을 0.8로 올리지 않는다.
- 현행 `snatcher_ko_master.tsv`와 `cdda_subtitles.tsv`를 과거 백업으로 통째로

- RTA의 가우디 입력창/빈 칸을 미번역 대사로 편입하지 않는다.
- 남은 ADPCM 초상화 2건은 위치를 추측해 일괄 수정하지 않는다.

## 8. 9월 13일 심야 추가분 — 검색 훅 성공과 BG 자판 실측

### 검색 기능은 `깁슨` 1건 성공

- `0.7.11-keypad-test5b-gibson-hook`에서 완성형 입력 `깁슨`이 원본 검색어
  `ギブスン`으로 변환되어 실제 검색에 성공했다. Lua 없이 동작하는 영구 훅 시험이다.
- Track 2 sector 346의 호출을 CPU `$B9E0 -> $BE56`으로 연결했고 코드 동굴은 97 B다.
- Track 02 SHA-256:
  `549BFDCA56D648AC8600EC7BAE56428AF94F430B4C4C5CEA4440ED5DA0381C11`
- BIOS SHA-256:
  `12D4823F0648472C6D6EBE761E94913B56CB25ED3AAB57910B3C1BE3B35135B9`
- 현재 훅이 지원하는 검색어는 **깁슨 하나뿐**이다. 다음 단계는 이름·퀴즈 답 전체의
  토큰열을 같은 방식으로 변환하는 일반표를 만드는 것이다.
- 앞선 test5는 명령 중간을 덮은 잘못된 시험이므로
  `INVALID_0.7.11-keypad-test5-gibson-hook_DO_NOT_OPEN`을 절대 실행하지 않는다.
- CUE 이름은 기존 세이브 호환을 위해
  `Snatcher CD-ROMantic (Japan) [KO].cue`로 복구했다.
- 근거: `qa/2026-09-13-0.7.11-keypad-test5b/README.md`,
  `tools/build_gaudi_gibson_hook_test.py`,
  `lua/PROBE_GAUDI_TEST5B_HOOK_0.1.0.lua`.

### 0.7.13 — 인명 검색 18개 표 연결

- 0.7.12의 실기 통과 `깁슨` 비교 진입점 `$B9E0 -> $BE56`은 그대로 유지했다.
- 동굴 `$BE56-$BFFF` 426 B에 공용 비교 코드 109 B와 매핑표 295 B를 넣었다.

### 아래 자판은 BG이며 원본 글자 한 칸이 8x16 두 타일

- `DUMP_GAUDI_KEYPAD_VRAM_0.1.0.lua`로 VRAM 65,536 B와 CRAM 512 B를 확보했다.
- 자판 글자는 BIOS 글꼴이나 스프라이트가 아니라 BG 패턴이다. 선택 커서만 스프라이트다.
- 중요한 정정: BAT를 128칸 폭으로 해석해 논리 행 17/18/19만 보았던 것은 각 글자의
  **윗부분만 본 것**이다. 실제 BAT 폭은 64칸이고 원본 가나 한 글자는 다음처럼 위·아래
  타일 두 장을 사용한다.
  - 첫째 줄: 물리 BAT 행 34/35
  - 둘째 줄: 물리 BAT 행 36/37
  - 셋째 줄: 물리 BAT 행 38/39
- 따라서 현재 `build_gaudi_keypad_bg_tiles.py`와
  `POC_GAUDI_KEYPAD_BG_0.1.0.lua`의 8x8/상단 타일 교체 결과는 **시각 실패 POC**다.
  한글 윗부분과 남아 있는 일본어 아랫부분이 합쳐져 깨져 보인다. 디스크에는 반영하지
  않았으며 런타임 VRAM만 바꿨다.
- 다음 작업은 원본과 동일한 8x16 크기로 상·하 타일을 모두 만드는 것이다.
  45글자에는 90개 타일 슬롯이 필요하며 현재 상·하 슬롯은 74개만 고유하다. 즉 공유
  타일을 분리할 16개가 추가로 필요하다.
- BAT 미참조이면서 내용도 빈 `$200-$3FF` 패턴은 실측상 5개뿐
  (`$200,$280,$34B,$34F,$377`)이다. 나머지 11개를 임의로 잡으면 스프라이트 또는
  프리로드 그래픽을 침범할 수 있으므로, 먼저 SATB/전환 장면의 패턴 사용 범위를
  측정해야 한다.
- 사용자가 요구한 최종 방향은 **패널이나 글자 영역을 늘리지 않고 원본 글자와 동일한
  8x16 크기에 맞추는 것**이다. 위 큰 입력창으로 선택 결과를 확인하므로 아래판의 완벽한
  가독성보다 안전한 원본 레이아웃 유지가 우선이다.
