# SNATCHER 인계서 — AC 선적재 일회성 가드 재설계 (0.4.6.10)

작성일: 2026-08-27
기준판: **`0.4.6.10`**
대체 대상: `0.4.6.9` (리셋 결함), `0.4.6.4`~`0.4.6.8`

---

## 0. 결론

`0.4.6.4`부터 `0.4.6.9`까지 들어 있던 **일회성 가드가 아케이드 카드 포트3 주소
래치(`$1A32`)에 의존**하고 있었다. 그 래치는 자기가 지키는 페이로드와 아무 연결이
없고, 콘솔 리셋으로도 지워지지 않는다. `0.4.6.10`에서 가드를 **AC 메모리 실물
확인**으로 바꿨고, 리셋 후 재적재를 RetroArch Beetle PCE(PC)에서 확인했다.

Mesen 검증에서는 이 결함이 드러나지 않았다. 이유는 에뮬레이터 동작이 아니라
**우리 절차**다 — 검증은 항상 Power Cycle로 시작한다(Lua 스크립트들도 전부
"Power Cycle -> ..."). **소프트 리셋 경로를 한 번도 밟은 적이 없다.** Mesen이
소프트 리셋에서 AC 레지스터를 어떻게 다루는지는 확인한 바 없다.

---

## 1. 래치 결함의 범위

래치가 확실히 설명하는 것은 **소프트 리셋 후 선적재를 건너뛰는 증상**이다.
`0.4.6.4`로 직접 확인한 결정적 관측:

```text
첫 부팅      로딩 길게 함          (선적재 실행됨)
리셋 후      로딩 없이 타이틀 직행  (선적재 건너뜀, 번역 없음)
```

래치가 리셋을 넘어 살아남고 AC 메모리는 소실되므로, 가드가 "이미 적재됨"으로
오판한다. 해당 관측:

```text
PC RetroArch Beetle PCE       리셋 후 로딩 없이 타이틀, 번역 없음
Android Beetle SuperGrafx     리셋 후 LOAD FAIL, 재적재 안 일어남
```

`0.4.6.10`에서 이 증상은 해소됐다(PC Beetle PCE에서 리셋 후 재적재 확인).

### 래치로 설명되지 **않는** 것

Android RetroArch Beetle PCE / PCE Fast의 **부팅 자체가 안 넘어가는** 증상은
별개다. 작업 중에는 이것도 같은 래치로 설명하려 했다 — "read-back 미구현 →
가드가 영영 불일치 → 매 CD_READ마다 1.2 MB 무한 재적재". 그럴듯했지만
**틀렸다.** 래치를 완전히 제거한 `0.4.6.10`에서도 그 코어는 여전히 실패한다.

즉 Android Beetle PCE의 실패 원인은 **미규명**이며, 이 문서의 수정과는 무관한
별개 사안이다. §4 참조.

Geargrafx는 Android에서 처음부터 정상이었다.

## 2. 왜 틀린 설계였나

```text
LDA $1A32          ; AC 포트3 주소 래치를 읽어
CMP #magic         ; 매직과 비교
BNE preload_needed
...적재...
LDA #magic / STA $1A32   ; 끝나면 래치에 매직을 써둔다
```

래치는 **"적재됐다"는 주장**일 뿐 적재의 **증거**가 아니다. 주장과 사실이 따로
노는 순간(리셋으로 AC 메모리만 날아감) 가드가 거짓말을 한다.

버전별 매직은 `0x60 + (마이너 & 0x0F)`였다.

```text
0.4.6.4  AD 32 1A C9 A5   <- 가드가 처음 들어간 지점
0.4.6.5  AD 32 1A C9 65
0.4.6.6  AD 32 1A C9 66
0.4.6.7  AD 32 1A C9 67
0.4.6.8  AD 32 1A C9 68
0.4.6.9  AD 32 1A C9 69
0.4.6.0 ~ 0.4.6.3   가드 없음 (다만 이 빌드들은 다른 이유로 정상 아님)
```

## 3. `0.4.6.10`의 가드

래치를 완전히 제거하고, **게시된 상태 블록을 AC 메모리에서 되읽는다.**

```text
A9 00 20 32 BF   LDA #$00 / JSR $BF32     포트0 -> AC $010000
A2 00            LDX #$00
AD 00 1A         LDA $1A00                AC에서 읽기 (자동증가)
DD CE FF         CMP $FFCE,X              state_table과 대조
D0 08            BNE preload_needed
E8 E0 06 D0 F3   INX / CPX #6 / 반복

$FFCE            AC 15 51 00 01 02        state_table
```

게시 단계도 같은 테이블을 쓴다:

```text
A9 00 20 32 BF   LDA #$00 / JSR $BF32
A2 00            LDX #$00
BD CE FF         LDA $FFCE,X
8D 00 1A         STA $1A00
E8 E0 06 D0 F5   INX / CPX #6 / 반복
```

**가드가 보는 것과 그것을 참으로 만드는 것이 같은 6바이트**라 둘이 어긋날 수 없다.

성립 근거:

- 게시는 **네 페이로드 적재가 전부 성공한 뒤에만** 실행된다.
- 페이로드 이미지의 `$010000`은 `FF FF FF FF FF FF`다. 매직은 게시가 돌았을
  때만 존재하므로 **부분 적재도 걸러진다.**
- 리셋으로 AC가 비면 매직도 사라져 자동 재적재된다.
- read-back은 게시와 **완전 대칭**이다(둘 다 `LDA #$00 / JSR $BF32` 후 `$1A00`
  순회). 레지스터 read-back 같은 별도 가정이 없다.
- AC 메모리를 못 읽는 코어는 번역 렌더러도 AC를 못 읽으므로 애초에 동작이
  불가능하다. 즉 가드가 **어차피 참이어야 하는 것**에만 의존한다.

### `$BF32` (Bank69 헬퍼)

```text
BF32  8D 02 1A   STA $1A02     ; 포트0 베이스 low (진입 시 A)
BF35  9C 03 1A   STZ $1A03     ; mid = 0
BF38  A9 01      LDA #$01
BF3A  8D 04 1A   STA $1A04     ; high = 1   -> 베이스 $01_00_A
BF3D  8D 07 1A   STA $1A07     ; 증가치 = 1
BF40  9C 08 1A   STZ $1A08
BF43  A9 11      LDA #$11
BF45  8D 09 1A   STA $1A09     ; 컨트롤 = 자동증가
BF48  60         RTS
```

포트0 레지스터만 건드리므로 Bank69가 MPR5에 매핑된 상태 외에 다른 창이 필요
없다. 가드 지점에서 MPR5=`$69`는 이미 매핑돼 있다.

### 부수 변경

- 캐이브가 280 B라 언롤 비교를 루프로 압축했다(310 B → 예산 내).
- 코드가 40 B 늘며 범위를 벗어난 원거리 분기 두 개를 절대 `JMP`로 바꿨다:
  `boot_done`(`BNE` → `BEQ cd_read_ok` + `JMP`), `restore_windows`(공용 `bail`
  트램펄린 경유).

## 4. 확인 상태

| 항목 | 확인 | 방법 |
|---|---|---|
| AC 선적재 | O | 첫 부팅 긴 로딩 + 한글 |
| 타이틀 · 게임 진입 | O | 실행 확인 |
| 리셋 후 재적재 | O | RetroArch Beetle PCE (PC) |
| 접수처 액션 UI 복구 | 바이트 동일 | `0.4.6.9` 런타임 합격, 코드 동일 확인 |
| Android Beetle SuperGrafx | O | 실행 확인 — **기준 코어** |
| Android Geargrafx | O | 실행 확인 |
| Android Beetle PCE | X | 실패, 원인 미규명 — 아래 참조 |

### Android Beetle PCE — 배제

`0.4.6.10`으로도 Android RetroArch Beetle PCE는 동작하지 않는다. **원인은
규명하지 않았고, 규명할 계획도 없다.**

작업 중 "여전히 실패하면 그 코어가 AC 메모리 read-back을 못 하는 것으로
확정된다"고 적었으나 그것은 과한 추론이었다. 이 테스트는 그 원인과 다른
원인을 구분하지 못한다. 사실로 남길 것은 하나다 — **`0.4.6.10`에서 Android
Beetle PCE는 실패한다.**

실용적으로는 달라질 게 없다. 우리 쪽 가정은 이번에 전부 정리됐고(래치 제거,
가드가 AC 메모리 실물만 봄), 남은 것은 코어 구현 영역이라 우리가 손댈 대상이
아니다. **Beetle PCE는 배제하고 다른 코어를 쓴다.**

## 5. 남긴 교훈

- **일회성 가드는 자기가 지키는 것의 실물을 봐야 한다.** 별도 래치·플래그에
  기록하는 순간, 그 둘이 따로 날아갈 수 있는 모든 경로가 버그가 된다.
- **Power Cycle만 하는 검증 절차로는 이 부류를 절대 못 잡는다.** 우리 Lua는
  전부 "Power Cycle -> ..."로 시작한다. "이미 했음"을 기억하는 상태는 소프트
  리셋을 눌러야만 검사된다. 검증 항목에 명시적으로 넣을 것.
- **하나의 그럴듯한 원인으로 여러 증상을 묶기 전에, 수정이 그 증상들을 실제로
  다 없애는지 확인할 것.** 이번에 Android 부팅 실패까지 래치로 묶었다가
  `0.4.6.10`에서 반증됐다(§1). 묶음이 맞았다면 같이 사라졌어야 했다.
- 하드웨어 레지스터 read-back과 리셋 시맨틱은 에뮬레이터마다 다르다. 단일 환경
  검증으로 닫지 말 것.
