0.3.5 부터 나던 글자 깨짐의 원인을 찾아 고치고, skip2 를 그 위에 얹은 판이다.

## 0. 번호가 넷인 이유

0.3.6 docstring 이 "0.3.5 를 제자리에서 덮어써 릴리스 노트와 디스크가 어긋났다"
고 경고를 남겼는데, 이번에 그것을 세 번 반복했다. 그래서 변형마다 번호를 새로 땄다.

```
0.3.8         helper 755 B   깨짐 재현 대조군.  덮어쓰지 말 것
0.3.8.1       helper 741 B   상수 재작성 복원 — 깨짐 수정
0.3.8.2       helper 771 B   + 스텁.  핸들러 표는 안 돌림 (스텁 있으나 안 불림)
0.3.8.2-skip2                gate=count    세이브 있을 때 새로 시작하면 깨짐
0.3.8.3-used                 gate=used     복귀 로드마다 깨짐
0.3.8.4-header               gate=header   부팅부터 깨짐
0.3.8.5-magic  helper 776 B  gate=magic    ★ 현행.  A·B·C 전부 통과
```

**변형은 폴더를 새로 판다. 기존 폴더에 다시 쓰지 않는다.**

`-tag` 없는 폴더(0.3.8.2 · 0.3.8.3 · 0.3.8.4 · 0.3.8.5)는 **스텁을 심었으나 핸들러
표를 안 돌린 판**이다. 그 자체로는 wipe 가 안 도는 대조군이고, 플레이할 디스크는
언제나 `-tag` 붙은 쪽이다.

## 1. 글자 깨짐 — 상수 슬롯이었다

### 1.1 증상

안내원 대사 `실례지만… 누구신가요?` 에서 **줄임표 칸이 쓰레기 타일**로 나오고,
그 오염이 뒤따르는 `누구신` 에 겹쳐 보였다. 0.3.5 · 0.3.6 · 0.3.7 전부에서 났다.

### 1.2 원인

0.3.5 §2.1 이 상수 슬롯 96 B($5BE0-$5C3F)를 매 레코드 다시 까는 대신 **센티널
2 바이트만 보고 건너뛰도록** 바꿨다. 그 2 바이트는

```
슬롯 0 의 첫 바이트      검사함
슬롯 1 (빈칸)            검사 안 함
슬롯 2 (줄임표)          마지막 바이트만 검사
```

**가운데가 깨지면 검사를 통과하고 영영 복구되지 않는다.** 그리고 슬롯 2 가 줄임표다.

이 구간이 실제로 손상된다는 것은 0.3.5 자신이 이미 적어두었다 — "검사 없이 한 번만
복사하는 판을 만들었더니 한참 뒤 글자가 깨졌다. 이 헬퍼 밖의 무언가가 그 구간에
닿는다." 0.3.4 는 매 레코드 96 B 를 무조건 다시 깔았기 때문에 손상이 나도 **다음
레코드에서 복구**됐고, 그래서 한 번도 보이지 않았다.

### 1.3 수정

`SNATCHER_CONST_CHECK=0` — 0.3.4 처럼 무조건 복사. 비용은 레코드당 593 사이클로
0.3.4 가 내던 값 그대로다. 기본값은 `1`(검사 유지)이라 0.3.5-0.3.7 재현은 그대로 된다.

### 1.4 0.3.8 이 안 고쳐졌던 이유 — 되돌린 줄 알았는데 아니었다

0.3.8 은 "0.3.4 로 되돌린 판" 이라고 적혀 있었지만, 되돌린 것은 환경변수 셋
(`PRELOAD_PACKS`/`TAI_CHUNK`/`BLANK_SLOTS`)뿐이었다. **0.3.5 가 실제로 바꾼 것은
그 셋이 아니라 공유 stage 3 모듈의 헬퍼 코드**였고, 되돌릴 스위치가 아예 없었다.

```
0.3.4     helper 713 B
0.3.5-7   helper 765 B
0.3.8     helper 755 B   <- 0.3.4 가 아니다.  플래그만 0.3.4
0.3.8.1   helper 741 B
```

**교훈: 진입점의 DEFAULTS 가 같다고 런타임이 같은 것이 아니다.** 헬퍼 바이트 수를
먼저 대조할 것. `manifest.json` 의 `helper_code_bytes` 한 줄이면 된다.

## 2. 검수 규칙 — `예외처리` 는 이제 아무것도 싣지 않는다

소유자 지정(2026-08-16). 마스터를 런타임 수집 기준으로 리빌드하면서 조각 처리가
`{EMPTY}`(머리 행에 흡수) 또는 자기 텍스트로 갈렸고, `예외처리` 는 쓸 자리가 없어졌다.
소유자가 직접 재검토한다.

```python
if mark.upper() == "O":          # 이것만 실린다
```

재현용 스위치는 남겨뒀다. 0.3.3-0.3.7 은 그것이 실리던 시절 빌드다.

```bash
SNATCHER_REVIEW_EXCEPTIONS=1 python extraction/patch/static/build_snatcher_ko_0_3_7.py
```

`manifest.json` 의 `review_exceptions_ship` 로 디스크만 보고 구분된다.

검수 행 897 → 865. 예전에 `예외처리` 로 나가던 꼬리 줄이 일본어로 보이는 것은 정상이다.

## 3. skip2 — 소스에서 사라져 있었다

`build_ac_dynamic_0_1_14.build_helper_compact` 에 있어야 할 `title_cache_wipe`
스텁이 트리에 없었다. 0.3.7 에도 0.3.8 에도 라벨이 없고, 실험 빌드
`EXPERIMENT\0.3.7-titlewipe-skip2` 의 헬퍼 이미지에만 남아 있었다.

디스크에서 30 B 를 떠와 에미터로 다시 심었고, 결과가 원본과 바이트 단위로 같다.

```
a0 0a b1 fa c9 95 d0 13 a9 02 f0 05 ce f8 7c 80 0a
a9 ff a2 3f 9d 80 5b ca 10 fa 4c bd 73
```

### 베끼면 안 되는 곳

`CE F8 7C` 는 **자기 오퍼랜드 주소를 하드코딩한 DEC** 다 (부팅 스폰 2 회를 세는
카운터가 바로 위 `LDA #$02` 의 즉치값이다). 헬퍼 크기가 바뀌면 스텁이 옮겨가므로
이 주소는 `a.pc` 로 계산한다. 그대로 베끼면 엉뚱한 바이트를 깎는다.

### 빌드 플래그로 뺀 것

§0.9 가 손으로 고치라던 `LDX #$3F` 도 플래그다.

```
SNATCHER_TITLE_WIPE         0   스텁을 심을 것인가 (기본 끔)
SNATCHER_TITLE_WIPE_SKIP    2   부팅 스폰 몇 개를 흘릴 것인가
SNATCHER_TITLE_WIPE_BYTES  64   $5B80 부터 몇 바이트를 $FF 로 채울 것인가
```

**N 을 줄이는 작업은 착수하지 말 것.** §0.9 는 액션 메뉴 깨짐을 "wipe 범위가 넓다"
로 보고 N 을 줄이려 했는데, §3.1 이 그것을 기각했다 — **양이 아니라 대상의 문제**였다.
`N=64` 그대로 둔다.

## 3.1 wipe 판정 — 세 번 추측하고 한 번 쟀다

스텁은 타이틀 스폰에서 캐시를 지운다. 단 **부팅 타이틀에서는 지우면 안 된다.**
그 구분을 세 번 시도해 세 번 다 틀렸다.

```
gate=count    스폰 2 개를 흘린다      "부팅 스폰은 2 개" 라고 가정
              -> 세이브가 있으면 3 개다.  세이브 있는 새 게임에서 깨짐

gate=used     스크래치에 깃발          "$7FF1 이 안전하다" 고 가정
              -> PROBE 0.7.0 이 이미 $7FC0-$7FFF 를 BIOS CD 읽기가 덮는다고
                 적어 뒀다.  타이틀로 나가며 깃발이 지워져 복귀에 wipe 가 안 걸림
                 -> 원래 버그(저장->타이틀->로드) 재발

gate=header   $5B80 == $FF 인가        "부팅에는 캐시가 비어 있다" 고 가정
              -> 82 였다.  부팅에 게임 레코드를 지워버려 부팅부터 깨짐
```

**셋 다 가정이 하나씩 들어 있었고 그 가정이 하나씩 틀렸다.** 네 번째 추측을 만드는
대신 `lua\PROBE 1.0.0.lua` 로 타이틀 스폰마다 `$5B80` 을 찍었다.

```
부팅   #1  82 FF FF 01 3E 00 00 82     게임 자신의 레코드
       #2  82 ...                       (안 지우면 그대로 남는다)
       #3  82 ...                       세이브가 있으면 스폰이 하나 더 난다
복귀   #5  53 44 52 34 09 0A DB 54     "SDR4" -- 우리 레코드
       #6  FF ...                       지운 뒤
```

세 상태가 첫 두 바이트로 완전히 갈린다. `build_direct_overlay_layout` 이
`MAGIC = b"SDR4"` 를 **모든 레코드 payload[0:4] 에 무조건** 찍으므로, 캐시에서 그
넉 자로 시작하는 것은 우리 것뿐이다.

```
$5B80 = 53 44 ...   우리 레코드   ->  지운다
$5B80 = 82 ...      게임 레코드   ->  안 건드린다
$5B80 = FF ...      이미 지웠다   ->  안 건드린다
```

가정이 없다. 상태를 안 두므로 CD 읽기에 날아갈 것이 없고(used), 부팅 스폰이 몇
개든 상관없고(count), 캐시가 비어 있다고 보지 않는다(header).

### 프로브가 같이 정정한 것

```
§0.8  "부팅은 스폰을 두 번 낸다"       세이브가 없을 때만.  있으면 세 번
§0.9  "선적재된 캐시가 날아간다"        아니다.  날아간 것은 게임 자신의 레코드다.
                                        메뉴 첫 줄이 빈 칸이 아니라 쓰레기였던 이유
§0.9  "N 을 줄여야 한다"                방향이 아니었다.  양이 아니라 대상이었다
```

### 프로브를 그렇게 만든 이유

`$7CEF` 하나만 빌드별 주소로 쓰고(세 판이 모두 같다), 지우기와 채우기는 **`$5B80`
쓰기 콜백**으로 잡는다. 0.9.3 은 라벨 주소를 손으로 맞추다 틀렸고, 헬퍼 크기가
바뀔 때마다 그 주소가 움직인다.

```
$5B80 <- FF      스텁이 지웠다
$5B80 <- 그 외    copy_record 가 채웠다
```

### 출력 폴더 이름

`patch_title_cache_wipe.py` 의 기본 출력 이름이 `0.3.7-titlewipe-<tag>` 로
하드코딩돼 있어 다른 버전에서 뽑아도 0.3.7 로 적혔다. 소스 폴더 이름을 따르도록
고쳤다 (`<source>-<tag>`).
