# 안드로이드에서만 ADPCM 다음 대사가 일본어로 뜬다 — 2026-09-08 밤

## 증상 (소유자 실측)

```
ADPCM 음성 **바로 다음 대사 하나**만 치환이 안 되고 일본어로 뜬다
그 밖의 대사는 전부 정상 치환
PC (메센 · RetroArch Beetle SuperGrafx · CUE 도 CHD 도)   나온다
안드로이드 RetroArch                                       처음부터 안 나온다
  PCE Fast · SuperGrafx · GearFX 코어 3 종 전부 동일
  반환 로직을 넣기 전 판에서도 안 됐다
```

★ **빌드는 변수가 아니다.** 판을 바꿔도, 반환을 넣거나 빼도, CHD 든 CUE 든 결과가
같다. PC 는 늘 되고 안드로이드는 늘 안 된다.

## 오늘 지운 가설 넷

| 가설 | 왜 틀렸나 |
|---|---|
| 자막 팩 불일치 (rc1 `44B2401A` vs 138 `1C01623E`) | 트랙 02 가 네 판 전부 `6f12fe002bc2c798` 로 동일. 대사 데이터·사전은 판마다 같은 바이트다 |
| CHD 가상 프리갭이 LBA 를 민다 | PC 에서 CHD 로 정상 동작 확인. 가상 프리갭은 INDEX 01 이후 대응을 안 건드린다 |
| 반환(release) 로직이 회귀를 넣었다 | 반환 넣기 전 판도 안드로이드에선 안 됐다 |
| 스프라이트 한도 | PC 의 GearFX 는 `no_sprite_limit = "Disabled"` 인데도 정상 |

## 죽은 코드에 3 시간 쓴 것 — 다음 사람은 피할 것

BIOS `$FEC7-$FEF9` 에 지문 검사 + `STZ $22A7` 이 있고 매니페스트의
`subtitle_trigger_consume` 이 이걸 가리킨다. **그런데 안 돈다.**

```
$FEC4  20 D4 FF   JSR $FFD4
$FEC7  C9 00      CMP #$00
$FEC9  60         RTS          ← direct_return_patch 가 박은 무조건 반환
$FECB  ...        지문 검사     ← 도달 불가
```

`legacy_fec7_fallthrough: false` 가 이 뜻이다. 프로브 `0.5.192` 로 진입 0 을
실측해 확정했다. ★매니페스트가 가리키는 주소가 살아 있다는 보장은 없다.

`0.5.193` 도 헛짚었다 — 뱅크1 `$FC38` 진입 0. 게다가 `$7FDF` 는 `$6000-$7FFF`
라 **뱅크 종속**이라 그냥 읽으면 `$00` 만 나온다.

**교훈: 주소를 먼저 찍고 걸지 말 것. 하드웨어 레지스터에 걸고 PC 로 역추적할 것.**

## ★ 살아 있는 자리 — `0.5.194` 실측

`$1800-$180F` 읽기 전수 감시. 3,632 프레임.

```
$180D 를 읽는 PC       $F6EB  4,017 회   ← 압도적 1 등.  나머지는 두 자리
$180D 가 돌려준 값     $00 3,092 · $60 1,275 · 그 밖 4 회씩
비트5 하강             4 회, 전부 $60 -> $00 at $F6EB
$180C 를 읽는 PC       $F3D4  107,431 회 · $F6DE 4,017 · $F6F2 3,074
$180C 가 돌려준 값     $01 91,837 · $05 21,742 · $08 943
```

`$F6EB` 는 `$F6E8 LDA $180D` 의 다음 주소다. 그 루틴 전체:

```
$F6DB  LDA $180C / AND #$01 / BNE -> $F6E7
$F6E2  LDA $1803 / AND #$04
$F6E7  TAX
$F6E8  LDA $180D / AND #$20      ★ADPCM 재생중 판정
$F6ED  BNE -> $F6F4                비트5 켜짐 = 재생중.  A=$20 으로 반환
$F6EF  LDA $180C / AND #$08       비트5 꺼짐이면 $180C 비트3 으로 판정
$F6F4  RTS
```

**시스템카드 `AD_STAT` 이다** — 점프테이블 `$E045 -> $F6DB` (23 번 항목).
그리고 **원본 일본판 BIOS 와 바이트가 완전히 같다.** 우리가 만든 코드가 아니다.

## 가설 — 쓰기 전용 레지스터의 읽기 되돌림

`$180D` 는 ADPCM **주소 제어 레지스터**로 실기에서 쓰기 전용이다. 읽었을 때
무엇을 돌려줄지는 **구현이 정한다.**

```
Mednafen 계열(PC)   마지막에 쓴 래치를 돌려준다 -> $60 이 나오고 비트5 가 뜻을 갖는다
다른 구현            0 · 오픈버스 · 고정값일 수 있다
```

비트5 가 늘 켜진 것으로 읽히면 `AD_STAT` 이 영영 "재생중" 을 반환한다 →
우리 엔진이 음성 종료를 못 보고 → 슬롯이 반납 안 되고 → **다음 대사가 일본어로
뜬다.** 코어 3 종이 나란히 실패한 것도 설명된다 — 코어 구현이 아니라 그 셋이
공유하는 지점이 어긋나는 것이다.

⚠ **미검증.** 안드로이드에서 `$180D` 가 실제로 뭘 돌려주는지는 못 쟀다.
기기에 디버거가 없다. 그래서 아래를 굽는다.

## 후보 수정 — 1 바이트

`AD_STAT` 은 비트5 가 꺼졌을 때 이미 `$180C` 비트3 으로 판정한다. `$180C` 는
진짜 상태 레지스터라 구현 편차가 훨씬 작다. 이번 주행에서 `$08` 이 943 회
잡혔으니 그 신호는 메센에서도 살아 있다.

```
$F6EE   05 -> 00        BNE +5  ->  BNE +0
```

두 갈래가 다 `$F6EF` 로 떨어져, `AD_STAT` 이 **`$180C` 비트3 만으로** 판정한다.
크기 변화 없음 · 재배치 없음.

빌드: `build/patch/0.6.3-diag-adstat-180c/`
132-ab 와 **BIOS 1 바이트만 다르다.** 디스크는 그대로 쓰면 된다.

⚠ 위험: `AD_STAT` 은 게임도 쓰는 공용 루틴이다. 게임이 비트5 경로에 기대고
있으면 다른 데가 바뀔 수 있다. 그래서 진단판이지 출하 후보가 아니다.

## ★ 결과 — `adstat-180c` 실패 (2026-09-08 밤, 소유자 실기)

안드로이드에서 BIOS 만 `0.6.3-diag-adstat-180c` 로 바꿔 확인. **여전히 안 나온다.**

즉 `$180C` 비트3 도 답이 아니다. 그리고 이건 가설 하나보다 더 큰 것을 지운다:

```
$180D 비트5   진단판으로 무력화   -> 여전히 실패
$180C 비트3   그 대체 경로        -> 여전히 실패
```

**AD_STAT 의 두 갈래를 다 건드렸는데 증상이 안 변한다.**
-> 우리 엔진의 종료 판정이 `AD_STAT` 을 안 탈 가능성이 높다.

⚠ 여기 구멍이 있었다. `0.5.194` 는 `$F6E8` 이 **누군가에게** 4,017 회 불린다는
것만 보였다. **그게 우리 엔진인지 게임 자신인지는 확인한 적이 없다.**
게임의 ADPCM 코드가 부르는 것이었다면 우리는 내내 남의 루틴을 보고 있었다.

## 다음 — 여기서부터

1. ★ **누가 `AD_STAT` 을 부르는가**를 먼저 가른다. BIOS 안 호출자는
   `$F407` · `$F5C6` · `$F61F` 셋, 점프테이블은 `$E045`.
   `$E045` 진입에 걸고 **호출자 PC(스택의 반환주소)** 를 히스토그램으로 뜬다.
   우리 엔진이 목록에 없으면 이 경로 전체가 무관하다.
2. 없으면 반대로 간다 -- 자막이 살아 있는 동안 **우리 엔진이 읽는 것**을 훑는다.
   STATE 를 들고 있는 자리부터 찾을 것 (`$7FDF` 는 뱅크 종속이라 그냥 읽으면 안 된다).
3. 그래도 안 잡히면 안드로이드에서 실제로 재는 수밖에 없다.
   프로젝트 방침대로 **Mednafen 단독판 + 디버거**(`mednafen-1.32.1-win64 (1)`)로
   Beetle 계열 동작을 재현해 보는 쪽이 기기보다 빠르다.
