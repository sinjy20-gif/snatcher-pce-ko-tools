# Snatcher CD-DA 오프닝 중간 스킵 해결 인계서 — 2026-09-01

> **2026-09-01 오후에 대체됨.** 여기 적힌 `$8411` 수정은 틀리지 않았지만
> **세 경로 중 하나만** 가리고 있었다 -- 자막이 뜨기 전에 스킵하면 그대로 깨진다.
> 진범은 `$5B80-$5E1E` 671 B 미반납이다.
> 최신 결론과 기준판은 `SNATCHER_CPU_CACHE_ROOT_CAUSE_2026-09-01.md` 를 먼저 볼 것.

## 0. 결론

**해결 성공.**

기준 조합은 다음과 같다.

```text
BIOS   build/patch/0.4.6.48/Syscard3_galmuri_0.4.6.48.pce
Lua    lua/SUB/0.5.102.lua
결과   오프닝 CD-DA 자막 중간 스킵 정상
       스킵 이후 화면 정상
       자막 출력 정상
```

`0.5.102.lua`는 정상 종료가 검증된 `0.5.77-refresh-cdda-backup.lua`를 불러오고,
게임의 실제 오프닝 스킵 분기 `$8411`에서만 자막 상태를 `2 -> 3`으로 바꾼다.

소유자 최종 확인 로그:

```text
SUB 0.5.102 ★ OPENING MID-SKIP f10415 · track=$11 state $02->$03 · elapsed=2454
SUB 0.5.77 ★ 10417f · base $7900 · 백업을 현재 화면으로 갱신 #1
              (바뀐 바이트 1026/2432)
```

위 로그 뒤 화면과 자막 모두 정상임을 소유자가 확인했다.

## 1. 실제 원인

오프닝 스킵 자체가 문제가 아니라 **CD-DA 자막이 active인 상태에서 스킵했는데도
자막 엔진이 이를 알지 못하고 고정 타이머를 계속 진행한 것**이 원인이었다.

기존 실패 순서:

```text
CD-DA 자막 state=2
-> 사용자가 오프닝 중간 스킵
-> 게임은 새 장면으로 전환
-> 자막 엔진은 스킵을 모르고 다음 조각까지 출력
-> 약 300프레임 뒤 늦게 restore
-> 이미 바뀐 화면 위에 과거 lifecycle이 개입하여 화면 파손
```

따라서 `audioPlayer.currentSector` 정지를 스킵 신호로 사용하는 접근은 틀렸다.
CD 오디오는 정상 재생 중에도 정지/전환처럼 보이는 구간이 있고, 실제 게임 분기보다
몇 프레임 늦게 감지된다.

## 2. 확정한 실제 스킵 분기

`0.5.100` 정상/스킵 비교에서 스킵 주행에만 CPU RAM `$2228-$2236`에 `$08`이
기록되는 것을 찾았다. `0.5.101`로 writer/consumer를 좁힌 결과 실제 코드는 다음과 같다.

```asm
$8011  AD 2D 22   LDA $222D
$8014  29 0C      AND #$0C
$8016  F0 03      BEQ $801B
$8018  4C 11 84   JMP $8411
```

실측 입력값은 `$222D=$08`이었다. 따라서 `$8411`은 추측이 아닌 **게임의 실제
오프닝 스킵 목적지**다.

관련 확정값:

```text
CD_PLAY 호출       $60E4
자막 arm           $F798
입력 trigger       $222D = $08
입력 판정 시작     $8011
스킵 목적지        $8411
CD-DA track        $11
CD-DA signature    $5DDA = $38
자막 active        $7FDF = $02
자막 종료 요청     $7FDF = $03
```

## 3. 성공 구현 `0.5.102.lua`

파일:

```text
lua/SUB/0.5.102.lua
```

동작:

```text
1. 정상 종료 기준선 0.5.77을 dofile로 로드한다.
2. CPU exec $8411을 감시한다.
3. 아래 조건이 전부 맞을 때만 $7FDF에 $03을 쓴다.
   - track == $11
   - state == $02
   - signature == $38
4. 네이티브 엔진이 다음 helper 진입에서 기존 restore/sprite wipe를 수행한다.
5. 0.5.77은 restore 직전에 AC backup을 현재 VRAM으로 갱신한다.
```

이 조건 때문에 다음 경로에는 개입하지 않는다.

```text
자막 시작 전 스킵       state != 2
자막 정상 종료 후 스킵  state != 2
ADPCM                   track/signature 불일치
일반 게임 진행          $8411 미진입
```

성공 실측에서는 `$8411` 감지 후 2프레임 뒤 helper restore가 왔다.

## 4. 실패한 접근과 폐기 이유

### `0.5.97.lua`

읽기 전용 lifecycle 측정. 스킵 뒤에도 state 2가 유지되고 다음 자막 조각 및 늦은
restore가 실행됨을 증명했다. 원인 규명용으로 유효하다.

### `0.5.98.lua`, `0.5.99.lua`

`audioPlayer.currentSector` 정지를 조기 스킵 신호로 사용했다. 정상 CD-DA 종료와
스킵을 안정적으로 구분하지 못했고 실제 분기보다 늦어 실패했다. 다시 사용하지 말 것.

### `0.5.100.lua`

정상 종료와 스킵의 CPU RAM/실행 경로를 광범위하게 비교했다. 정답 후보
`$2228-$2236`을 찾았지만 콜백 범위가 넓어 매우 느리다. 재실행할 필요 없다.

### `0.5.101.lua`

`$2228-$2236`의 writer/reader만 좁혀 `$8011-$8018 -> $8411`을 확정한 읽기 전용
프로브다. 원인 증거로 보존한다.

## 5. Lua가 느린 이유

`0.5.102` 자체의 `$8411` 콜백은 가볍다. 느린 부분은 포함된 `0.5.77`이다.

복원 순간 `0.5.77`은 VRAM 2,432바이트를 바이트 단위로 읽고, AC 백업과 비교하고,
다시 쓰므로 약 7천 회의 Lua API 호출이 집중된다. 또한 `$5B83`은 renderer/helper가
자주 통과하는 뜨거운 주소라 exec 콜백 비용도 붙는다.

이것은 **진단 Lua의 성능 문제**다. 최종 네이티브판에서는 65C02/TIA로 처리해야 하며,
Lua 속도를 최종 런타임 성능으로 오해하지 말 것.
