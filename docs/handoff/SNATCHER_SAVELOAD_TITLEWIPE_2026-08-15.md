# SNATCHER 세이브→타이틀→재로드 그래픽 파손 인계서

작성 시점: 2026-08-15
기준 빌드: KO `0.3.6`
현재 실험: `build\patch\EXPERIMENT\0.3.6-titlewipe`

## 0. 현재 결론

세이브 후 타이틀로 복귀하여 같은 슬롯을 다시 로드할 때 발생하는 그래픽 파손은
`$5B80` 계열 캐시에 남아 있는 한글 패치 레코드가 타이틀 복귀 경로에서 재해석되는
현상과 강하게 연결되어 있다.

Lua에서 캐시를 FF로 초기화했을 때 기존 파손이 사라지는 것이 실측되었으므로,
캐시 초기화 자체의 효과는 확인됐다.

다만 첫 실제 패치인 `0.3.6-titlewipe`는 초기화를 타이틀 진입 때만 하지 않고 모든
스크립트 spawn에서 수행하도록 구현했다. 그 결과 최초 게임 로드에서도 선택지/
그래픽이 파손되는 회귀가 발생했다.

따라서 현재 문제는:

**wipe 자체가 틀린 것이 아니라 wipe 조건이 너무 넓다.**

다음 수정은 타이틀 스크립트 spawn만 식별하여 wipe하도록 제한해야 한다.

## 1. 원래 증상

정상 기준 빌드 `0.3.6`:

```
파워사이클
→ 게임 로드
→ 플레이
→ 저장
→ 타이틀 복귀
→ 같은 슬롯 로드
→ 그래픽 파손
```

특이점:

* 최초 로딩은 정상.
* 플레이 중 일반 대사 출력도 정상.
* 타이틀로 복귀한 뒤 재로드하는 경로에서만 파손.

원본 Vanilla에서는 동일 현상 없음.

## 2. 캐시 관련 인과 실험

문제 영역:

```
$5B80-$5E3F
```

한글 패치가 사용하는 레코드/글리프 관련 작업 영역이다.

문제 상황에서 다음과 같은 비정상 전송이 실측됐다.

```
src=$5E22 +165
```

원본에서는 같은 조건에서 이 전송이 발생하지 않는다.

Lua로 캐시를 FF로 초기화한 뒤 재로드하면 기존 그래픽 파손이 사라졌다. 따라서:

**stale cache가 파손의 핵심 조건이라는 것은 실험적으로 확인됨.**

단, 캐시 전체를 무차별적으로 지우면 정상 렌더링에 필요한 데이터도 사라질 수 있다.

## 3. 타이틀 진입 훅 탐색 — 과거 결론 철회

과거 문서에서 한때 다음과 같이 결론냈다.

> "게임이 스크립트 VM이므로 타이틀 진입 훅은 존재하지 않는다."

**이 결론은 철회됨.** 원인은 잘못된 측정 설계였다.

`PROBE 0.5.1`은 타이틀이 이미 표시된 뒤의 실행 PC를 관측했기 때문에, 타이틀로
전환되는 순간을 측정하지 못했다. 따라서:

```
타이틀 화면에서 고유 PC를 못 찾음
≠
타이틀 전환 경계가 없음
```

이다.

## 4. 스크립트 VM 구조

정적 분석 및 런타임 계측으로 다음이 확인됐다.

스크립트 태스크 베이스:

```
$2700,X
$2740,X
```

스크립트 PC/상태:

```
$2DC0,X
$2E00,X
```

스크립트 spawn 시 위 고정 RAM 영역이 갱신된다. 따라서 코드 위치를 추측하는 대신
`$2700-$277F` WRITE를 감시하여 실제 spawn을 계측했다.

## 5. 타이틀 스크립트 서명

독립된 여러 실행에서 동일하게 재현됨.

부팅 타이틀:

```
slot 5   base $9520
slot 16  base $95C2
```

플레이 후 타이틀 복귀:

```
마지막 대사
↓
slot 5   base $9520
↓
slot 16  base $95C2
↓
타이틀
```

3회 이상 동일하게 재현됨. 따라서 현재 타이틀 spawn 서명은:

```
base high = $95
```

로 볼 수 있다. 플레이 중 일반 spawn은 주로 `$89xx` · `$5Axx` 등으로 관측됐다.

## 6. 마지막 대사와 타이틀 spawn 순서

중요. 실제 계측:

```
마지막 대사
↓
$9520 spawn
↓
$95C2 spawn
↓
타이틀
```

즉 타이틀 spawn은 종료 선택 직후가 아니라 **마지막 대사 이후에도 존재한다.**
따라서 이 지점에서 wipe하면 **wipe 이후 종료 대사가 다시 캐시를 채워버리는 문제**를
피할 수 있다.

종료 대사 내용은 4패턴 존재하지만 타이틀 spawn 서명은 동일하므로 문자열 4종을
직접 비교할 필요가 없다.

## 7. 실제 살아 있는 spawn 핸들러

런타임 계측:

```
MPR:
0=$FF
1=$F8
2=$68
3=$69
4=$6D
5=$6E
6=$6C
7=$00
```

실제 spawn WRITE:

```
bank $69

$73FB  low byte write
$7401  high byte write
```

라이브 RAM에서 읽은 코드:

```
C8
B1 00
9D 40 27
C8
B1 00
9D 80 2F
...
```

정적 분석에서 발견했던 spawn 루틴과 동일하다. 정확한 실제 루틴:

```
$73BD
```

## 8. 디스크 ↔ 런타임 오버레이 매핑 확정

이 부분에서 과거 두 번 주소 계산 오류가 있었으므로 **이 매핑을 다시 추측하지 말 것.**

타이틀 spawn 순간의 16KB RAM을 직접 dump한 뒤 KO `0.3.6` 디스크 전체에서
검색했다. 각각 정확히 한 곳에서 일치했다.

```
$4000-$5FFF
← Track 02 sectors 247-250
← file offset 505856

$6000-$7FFF
← Track 02 sectors 251-254
← file offset 514048
```

역할:

```
sectors 247-250
  $5B80 cache
  $5E40 preloader

sectors 251-254
  scene VM
  spawn handler $73BD
```

Vanilla에는 일치하지 않고 KO `0.3.6`에만 일치하므로 현재 패치가 실제로 사용하는
오버레이임이 확인됨.

## 9. 타이틀 시점에는 `$66E5` 한글 렌더러 훅이 비상주

타이틀 시점 라이브 RAM:

```
$66E5 = D4 29 7F ...
```

평소 한글 렌더러 오버레이의 `$66E5 = JSR $5E40` 가 아니다. 즉 타이틀에서는 텍스트
렌더러 오버레이 자체가 내려가 있다.

따라서 과거 차선책이었던 **`$66E5`에서 매 렌더마다 cache wipe** 는 타이틀 전환
lifecycle 처리로 사용할 수 없다. spawn 쪽에서 처리하는 방향이 구조적으로 맞다.

## 10. spawn dispatcher 구조

bank A의 상위 VM:

```
$7322  LDA ($FA)
$7324  CMP #$FF
$7326  BNE ...
$7328  CLC
$7329  RTS

$732A  JSR $477F
$732D  ; inline handler pointer table
```

핸들러 표에:

```
$7341
$7382
$73BD   ← spawn
$742D
$744C
...
```

가 존재한다.

`$73BD`는 `$FA/$FB+2`의 spawn table을 읽어 여러 태스크를 등록하고 `$FF`까지
반복한다. 타이틀에서 `$9520`과 `$95C2` 두 spawn이 연속해서 관측된 이유도 이
구조와 일치한다.

## 11. bank A 여유 공간

확인된 원본 FF 공간:

```
$7CD2-$7FFF = 814 B
```

기존 한글 패치 사용:

```
$7CD2-$7FCE
$7FE0-$7FF0
```

확인된 잔여:

```
$7FCF-$7FDF = 17 B
$7FF1-$7FFF = 15 B
```

첫 실험 헬퍼는 13B였으므로 `$7FCF-$7FDF`에 들어갔다.

## 12. 첫 실제 패치 `0.3.6-titlewipe`

생성:

```
build\patch\EXPERIMENT\0.3.6-titlewipe
```

패처:

```
patch_title_cache_wipe.py
```

첫 구현:

```
$7331 handler table
$73BD → $7FCF
```

헬퍼:

```
$7FCF  A9 FF       LDA #$FF
$7FD1  A2 5F       LDX #$5F

$7FD3  9D 80 5B    STA $5B80,X
$7FD6  CA          DEX
$7FD7  10 FA       BPL $7FD3

$7FD9  4C BD 73    JMP $73BD
```

즉 `$5B80-$5BDF = 96 B` 를 FF로 초기화하고 원래 spawn 핸들러로 복귀한다.

TII는 사용하지 않았다. STA loop이므로 긴 연속 IRQ 차단을 만들지 않는다.
EDC/ECC도 재계산함.

## 13. 첫 패치의 실패 원인

**중요: wipe 자체 실패로 판단하지 말 것.**

첫 구현에는 `$95xx` 판별이 없다. 즉:

```
모든 spawn
→ 96B wipe
→ 원래 $73BD
```

이다. 실제 세션에서 spawn은 약 9회 발생하며 부팅/게임 시작/장면 진입에도 발생한다.
따라서 최초 로딩에서도 cache header를 지워버린다.

실제 결과:

* cache wipe 자체는 작동.
* 하지만 최초 게임 시작/로드부터 선택지 그래픽 등이 파손.
* Sprite Viewer에서도 관련 타일 데이터 이상 확인.

이는 모든 spawn에서 wipe한 구현의 예상 가능한 부작용이다. 정상 `0.3.6`에는 해당
wipe가 없으며 기존 최초 로딩은 정상이다.

## 14. 다음 수정

현재 `patch_title_cache_wipe.py`를 수정 중.

목표:

```
spawn base high == $95
    → $5B80-$5BDF 96B를 $FF
    → 원래 $73BD

그 외 spawn
    → wipe 없이 원래 $73BD
```

즉 타이틀 서명 `$9520` · `$95C2` 에서만 초기화한다.

부팅 타이틀에서도 `$95xx`가 발생하지만 문제없다고 판단한다. 이유: 부팅 시에는 해당
영역이 원래 빈/FF 상태이므로 `FF → FF` 일 뿐이다.

반면 플레이 후 타이틀 복귀에서는:

```
한글 레코드 잔존
→ $95xx spawn
→ FF 복원
→ 타이틀
```

이 되어 우리가 원하는 lifecycle 복원이 된다.

## 15. 현재 메모리 영역에 대한 해석

아직 원작 설계 의도를 완전히 역공학한 것은 아니므로 **가설로 유지할 것.**

현재 현상과 가장 잘 맞는 설명:

타이틀의 특정 주변부/빈 그래픽 영역은 최초에 한 번 생성된 뒤 다시 갱신할 필요가
없는 정적 영역일 가능성이 높다. 원작에서는 관련 메모리가 FF 상태이므로 문제가 없다.
한글 패치는 그 영역을 런타임 레코드 캐시로 재사용하면서 원작이 기대하지 않은
데이터를 남긴다.

따라서:

```
최초 타이틀
  FF
  → 정상

플레이
  한글 레코드가 해당 영역 사용

타이틀 복귀
  원작은 정적 영역을 다시 만들지 않음
  → stale record가 남음
  → 그래픽 데이터로 오해
  → 파손
```

이라는 설명이 현재 관측과 잘 맞는다. **확정된 사실과 이 해석을 문서에서 혼동하지
말 것.**

## 17. 다시 파지 말아야 할 것

다음은 이미 폐기/정정된 방향이다.

| 폐기된 결론 | 정정 |
|---|---|
| "타이틀 진입 훅은 존재하지 않는다." | 철회. 잘못된 측정 창 때문에 나온 결론 |
| 대사 4패턴 문자열 비교 | 불필요. 마지막 대사 이후 공통 `$95xx` spawn이 존재 |
| 타이틀 화면이 뜬 뒤 PC 빈도 비교 | 전환 순간을 잡지 못하므로 이 문제에는 부적합 |
| 정적 sector 매핑 추측 | 금지. 실제 16KB runtime dump로 sectors 247-254 매핑 확정됨 |
| `$53BD`가 죽은 코드 | 오류. `$2000` 주소 계산 실수. 실제 살아 있는 주소는 `$73BD` |
| 모든 spawn에서 96B wipe | 최초 로딩 회귀 발생. 타이틀 spawn으로 제한 필요 |

## 한 줄 요약

세이브→타이틀→재로드 파손은 stale `$5B80-$5BDF` 데이터와 연결되어 있고, 마지막
대사 이후 공통 타이틀 spawn `$9520/$95C2` 및 실제 spawn 핸들러 `$73BD`까지
확정했다. 첫 패치는 모든 spawn에서 96B를 지워 최초 로딩을 깨뜨렸으며, 현재 해야 할
일은 `$95xx` spawn일 때만 동일한 96B wipe를 수행하도록 좁혀 구현·회귀 테스트하는
것이다.

## 18. `$95xx` 제한판 결과 (2026-08-15 저녁, 실측)

`patch_title_cache_wipe.py` 를 §14 목표대로 좁혀 빌드했다.

```
$7331 표   $73BD -> $7FCF
$7FCF  16 B  PHY / LDY #$0A / LDA ($FA),Y / PLY / CMP #$95 / BNE / JMP
$7FF1  13 B  96 B wipe -> JMP $73BD
```

Y 보존(PHY/PLY)은 문서에 없던 추가다. §12 의 "Y는 untouched" 는 **첫 헬퍼**
기준이고, 판정이 `LDY` 를 쓰는 이 판에는 맞지 않는다.  `$73BD` 가 Y 를 미리
로드한다는 증거가 없어 2 바이트로 막았다.

**결과: 최초 로딩의 선택지 파손이 그대로다.**  `$95xx` 제한만으로는 부족하다.

부팅 타이틀에서도 `$95xx` spawn 이 일어나고, §14 는 그때 해당 영역이 이미 FF 라
`FF -> FF` 라서 무해할 것으로 봤다.  **그 가정이 틀렸다** -- 부팅 타이틀 시점에
그 96 B 가 이미 무언가로 채워져 있고, 지우면 직후 메뉴 두 줄이 깨진다.

다음에 이어갈 때의 후보:

```
부팅 타이틀과 복귀 타이틀을 구분한다   같은 $95xx 라도 다른 상태가 있을 것.
                                    세이브 유무 · 진행 플래그 등
$9520 과 $95C2 중 하나만 골라 본다     둘 다에서 wipe 하는 지금과 다르다
wipe 시점을 spawn 이 아니라 그 뒤로     spawn 직후 메뉴가 캐시를 쓰므로,
                                    메뉴가 다 그려진 뒤여야 할 수 있다
```
