# 헌정 화면 한글화 — route C (원본 데이터 제자리 치환)

작성 2026-09-09 저녁 · 이전 문맥: `docs/handoff/` 의 GFX native r1~r5 계열 문서

---

## 0. 한 줄

**주입(injection) 노선은 죽었다.** IRQ 안에서 VRAM 을 건드리는 설계라 원리적으로
못 고친다. 대신 디스크의 **원본 그래픽 블록을 제자리에서 갈아끼우는** 노선으로
전환한다 — 성공하면 런타임 코드 0 바이트 · 훅 0 개.

---

## 1. 오늘 실기로 확정된 것

### r6 = r5 + 선적재 가드 → **부팅 살아났다**

r5 는 부팅부터 화면 전체가 깨졌다. r6 는 tick 첫머리에서 AC `$1A0006:07 == A0 16`
(선적재 지문)을 확인하고 아니면 즉시 `JMP tick_exit` 한다. 가드 22 B.

    소유자 실기: 코나미·타이틀·시작메뉴 정상 · 음악 정상
                 **헌정 화면에서만** 화면 전체가 타일 쓰레기

→ "선적재 전 phase 쓰레기값" 가설은 **맞았다**. 그건 닫혔다.

빌드: `build/patch/0.6.3-gfx-native-r6/` · 빌더 `tools/build_gfx_native_dedication_r6.py`
`tick $FF27-$FFD1 171/179 B` · r5 대비 diff 는 가드 22 B + 주소 밀림뿐
(`$F006`/`$F040` 의 `vdc_exit` 참조가 `$FF94 -> $FFAA`).

### 왜 헌정 화면만 깨지나 — MAWR 재진입

우리 tick 은 `$FC07`, 즉 **인터럽트 안**에서 돈다. 게임은 자기 루프에서
`$3B00` 버퍼를 채우고 `$725C` 에서 MAWR 을 잡은 뒤 워드를 흘린다. 그 도중에
우리 IRQ 가 끼어들어 **MAWR 을 옮긴다.** 돌아온 게임은 남은 워드를 우리가
옮겨놓은 주소에 쏟는다.

⚠ **못 고친다.** HuC6270 의 MAWR 은 쓰기 전용이라 저장→복구가 불가능하다.
IRQ 안에서 VRAM 을 쓰는 설계 자체가 안전하지 않다. `SETTLE` 을 늘리는 건
증상 회피이지 해결이 아니다.

### 죽은 가설 (다시 꺼내지 말 것)

| 가설 | 판정 |
|---|---|
| BIOS 굴이 실제로는 안 비었다 | ✗ nohook 판이 정상 부팅. 코드가 앉아만 있는 건 무해 |
| 자막 엔진이 AC 채널을 밀었다 | ✗ 엔진은 **채널 0** (`$1A02/03/04/07/08/09`) 만 쓴다. 우리는 2·3 |
| 선적재 전 쓰레기 phase | ★ 맞았다 — r6 가 부팅을 살렸다 |

## 2. 원본 그래픽 포맷 (정적 해독, 오늘 최대 소득)

### 디스크에 타일이 없는 이유

원본 타일 16 B (`80 00 40 00 20 00 10 00 08 00 04 00 03 00 FC 00`) 를
Track 01·02·24 **213 MB 전체**에서 찾으면 16 B 는 물론 **8 B 도 0 건**이다.
압축이 아니라 **저장 형태가 다르기 때문**이다 — 디스크엔 청키(chunky) 픽셀이
들어 있고, 플레이너(planar) 타일은 실행 중에 만들어진다.

### 스크립트 레코드 — `$6E0B`

    $6E0D  A*3 + 2 -> Y           인덱스로 스크립트 스트림($08)에 들어간다
    $6E14  ($08),Y == FF ? 끝
    $6E1A  -> $04   뱅크
    $6E1D  -> $11   종류   $08 -> JMP $6FC8 · $04 -> JMP $7019 · 그 외 폴스루
    $6E30  (그래픽 경로)
    $6E36  -> $0002/$0003   VRAM 주소 2 B (MAWR)
    $6E42  -> $00/$01       소스 포인터 P 2 B
    $6E48  P+1 -> $14/$15
    $6E56  LDA $04 / JSR $43B1     P 의 뱅크를 페이징
    $6E59  LDA (P) -> $16          헤더
    $6E5D  AND #$7F -> $10         표 길이 N
    $6E61  P + N + 1 -> $12/$13    본문 시작
    $6E6C  STZ $CC
    $6E71  JSR $7061               ← 본문을 읽어 그리는 루틴 (아직 안 읽음)

⚠ `$6E30` 은 **분기 목적지가 아니라 폴스루**다. `30 6E` 를 가리키는 점프표는
오버레이에도 트랙 전체에도 없다 — 찾지 말 것.

### 디스크 위 바이트열

    [뱅크][종류][VRAM lo][VRAM hi][P lo][P hi]

### 버퍼 적재기 `$71B0`

    $71B0  BBS7 $16 -> $7201     헤더 bit7 = 비트역순 변형 ($7204 에 LSR/ROL x8)
    $71B3  BBS6 $16 -> $71AD     헤더 bit6 = 또 다른 변형
    $71B8  STA $3B00,X           A 를 버퍼에 쌓는다 ($CC = 인덱스)
    $71BD  BPL $7200             $CC < $80 이면 리턴 (128 B = 4 타일분 모을 때까지)
    $71C1  LDA $10 / BEQ $71ED   N=0 이면 전개 없이 바로 업로드
    $71C5  ... 전개 ...
    $71EE  $3B00-$3B7F -> VDC    64 워드 업로드

### 전개기 `$71C5` — 픽셀 단위 16색 재매핑 (전치가 아니다)

    X = $1F..0 (32 행), 각 행마다 A=0 에서 9 회:
        Y = A & $0F
        A = ($14),Y                 ← 니블 변환표 16칸
        ASL A / ROL $3B60,X / ROL A / ROL $3B40,X / ROL A
                / ROL $3B20,X / ROL A / ROL $3B00,X / ROL A

★ 핵심: `ROL $3Bxx,X` 는 **버퍼 바이트를 회전시키면서 캐리를 A 로 되돌린다.**
그래서 `AND #$0F` 시점의 A 하위 4비트 = 네 플레인의 최상위 비트가 모인 값 =
**그 픽셀의 4비트 색인**이다. 표로 바꿔 다시 밀어 넣는다.

⚠ 오독 이력 둘 (다시 밟지 말 것):
  · "($14),Y 표를 걸어 읽는 루프" -> 아니다. 메모리 회전이 A 를 먹인다
  · "청키 -> 플레이너 전치" -> 아니다. **이미 플레이너**이고 색만 바뀐다

### 정리한 포맷

    P[0]       플래그(bit7·bit6) + 표 길이 N (하위 7비트)
    P[1..N]    니블 변환표 16칸
    P[N+1..]   RLE 압축된 **플레이너** 4bpp 타일 데이터

### 본문 압축 — `$7061` 명령표 (완전 해독)

    cmd $00        [n][b]        b 와 리터럴 n 개를 번갈아 낸다
    cmd $01        [lo][hi][b]   b 를 16비트 횟수만큼
    cmd $02        [n][b1][b2]   b1 b2 짝을 n 번
    cmd $03-$3F    [b]           b 를 cmd 개 (짧은 RLE)
    cmd $40-$7F                  0 을 (cmd & $3F) 개
    cmd $80        [lo][hi]      리터럴, 16비트 길이            ★인코더는 이것만 쓰면 된다
    cmd $81-$BF                  리터럴 (cmd & $7F) 개
    cmd $C0-$FD                  0 과 리터럴을 번갈아 (cmd & $3F) 쌍
    cmd $FE        [n][4바이트]  4바이트 무늬를 n 번
    cmd $FF                      끝

보조 루틴:

    $719F   ($12),Y..1 을 제로페이지 $01.. 로 복사 (인자 읽기)
    $71A8   LDX #$12 / JMP $4798   포인터 $12/$13 을 A 만큼 전진
    $7149   CLC / ADC $12 -> $12 / INC $13 / JMP $7061   다음 명령으로

★ 인코더는 `80 <lo> <hi> <원시 바이트들> FF` 한 줄이면 된다.
원본 압축기를 흉내 낼 필요가 없다. 다만 크기가 커지므로 제자리에 안 들어가면
레코드의 **뱅크·P 를 둘 다 바꿔** 다른 자리로 보낼 수 있다 (레코드가 둘 다 들고 있다).

### 매핑 검증 (다른 출처로)

⚠ `tools/disasm_huc6280.py` 와 `tools/dis6280.py` 가 `$7256` 에서 **완전히 다른 코드**를
보여준다. 오류가 아니다 — 전자는 뱅크 B(텍스트 VM, 섹터 255-258)를 같은 CPU 주소에서
읽는다. 그 도구 주석이 경고하는 "같은 바이트, 틀린 페이지" 함정이 이것이다.

그래픽 코드는 **평평한 매핑** 쪽이 맞다. 독립 근거:

    UPLOAD_HOOK_OLD      = A4 97 9F 11 14 82  @ $7256   ← 바이트 일치
    UPLOAD_ROUTINE_OFFSET= 0x916DC            @ $725C   ← 일치

즉 `파일 = 0x90480 + (CPU - 0x6000)` 이 이 오버레이에서 성립한다.
(섹터 경계를 넘는데도 성립하므로 이 구간은 파일에서 연속이다.)

### ★★ 매핑 함정 — 평평한 파일 오프셋을 쓰지 말 것

Track 02 는 **Mode 1 / 2352 B 섹터**다 (파일 80,779,440 B = 2352 x 34,345, 섹터마다
싱크 `00 FF x10 00` 확인). 섹터당 헤더 16 B + EDC/ECC 288 B = **304 B 가 데이터가 아니다.**
그래서 CPU 주소를 평평한 파일 오프셋으로 옮기면 섹터 하나 넘을 때마다 304 B 씩 어긋난다.

    올바른 매핑:  CPU $6000  =  섹터 251 사용자영역 +0     (경계에 딱 맞는다)
                  파일 = (251 + (A-0x6000)//2048)*2352 + 16 + (A-0x6000)%2048

⚠ 이 함정에 실제로 빠졌다. 평평한 base `0x90480` 으로 뜬 것 중

    $7061 · $71B0 · $71C5 · $7256   섹터 253   평평 == 논리   ✓ 유효했다
    "$6E30" 이라고 적었던 것          섹터 252   240 B 어긋남   ✗ 실제로는 **$6F60**

바이트열 자체는 같았기 때문에 해독 내용(레코드 규약)은 결과적으로 맞았지만,
**주소를 그대로 믿었으면 엉뚱한 자리를 패치할 뻔했다.**

교차검증 방법: `JSR $71B0` 17 곳의 CPU 주소가 논리 이미지와 평평한 디스어셈블에서
일치하는지 본다 ($707A, $707F, $70A8, $70BA, ...).

작업용 이미지는 이렇게 만든다 (스크래치패드에 캐시해 두면 편하다):

    논리 = 모든 섹터의 [16 : 16+2048] 을 이어붙인 것   (70,338,560 B)

### ⚠ 검증 안 된 추측

"상주부($4000-$5FFF)가 오버레이 바로 앞(0x8E480)에 이어 붙어 있다" 고 가정하고
`$43B1` 을 떠봤더니 코드처럼 읽히긴 했다:

    $43B1  LDA $3CF0 / STA $F8 ... LDA #$0E / STA ($F8) ... PLA / STA ($F8)

그런데 이건 **뱅크 페이징 루틴이 아니다** (큐에 밀어 넣는 모양이고 `PLA` 로 복귀주소를
건드린다). 매핑이 틀렸을 공산이 크다. **이 위에 아무것도 쌓지 말 것.**

### ★ 뱅크 매퍼 `$43B1` — 데이터는 `$8000-$DFFF` 에 올라온다

`$4000-$5FFF` 오버레이는 **섹터 247-250** 이다 (`$6000` = 섹터 251 바로 앞 네 개).

    $43B1  PHA / TMA #$10 / STA $3F00      현재 MPR4 저장
    $43B7  PLA / CLC / ADC $3F80           요청 뱅크 + 기준 뱅크($3F80)
    $43C1  TAM #$10                        MPR4 = A      $8000-$9FFF
    $43C3  INC A / TAM #$20                MPR5 = A+1    $A000-$BFFF
    $43C6  INC A / TAM #$40                MPR6 = A+2    $C000-$DFFF

⚠ 따라서 소스 포인터 `P` 는 **`$8000-$DFFF`** 다. 한때 `$4000-$7FFF` 로 걸렀는데
그건 틀렸고, 그때 나온 후보 7~8 건은 **전부 무효**다.

뱅크는 `$3F80` 의 기준 뱅크에 **상대**적이다. 8 KB 뱅크 = 논리 4 섹터.

## 3. 탐색 현황 — 아직 못 찾았다

### 눈먼 블록 스캔 (실패)

`tools/gfx_block_codec.py --scan` 으로 헤더 후보를 훑어 규약대로 풀리는 블록만
남기고 지문을 찾았다.

    평평한 이미지   헤더 후보 1,984,190 · 풀린 블록 3,869 · 지문 0
    논리 이미지     헤더 후보 1,910,553 · 풀린 블록 3,022 · 지문 0

⚠ **"없다" 로 읽지 말 것.** 이 주행이 못 잡는 구멍이 셋이다:

    1. 필터가 (H & $7F) == $10 만 본다.  **N = 0 이면 전개를 아예 안 하는데**
       (`LDA $10 / BEQ $71ED`) 그 블록은 후보에서 빠진다
    2. 지문을 잰 $7256 이 $71EE 와 다른 루틴이라 그 버퍼가 전개를 거쳤는지 미확정.
       전개 전/후 둘 다 보도록 도구는 고쳤지만 이 주행엔 안 들어갔다
    3. 출력 32 KB · 입력 16 KB 상한.  큰 화면이면 잘린다

### 레코드 후보 (P 고친 뒤)

`[뱅크][종류][A0 16][P lo][P hi]` 로 논리 이미지를 훑어 24 건. 그런데 **전부
섹터 11,477 이상**이고 바이트 문맥이 ADPCM 잡음처럼 보인다. 스크립트·그래픽이
있을 저지대에 하나도 없다.

읽는 법 둘:

    (가) 헌정 화면이 이 경로($6F60)가 아니다 -> 종류 $04($7019)·$08($6FC8) 를 읽어야 한다
    (나) 시작 VRAM 주소가 $16A0 이 아니다 (지문 타일이 화면 첫 타일이 아닐 수 있다)

## 3-1. 옛 후보 (무효 · 기록만)

`[뱅크][종류][A0 16][P lo][P hi]` 규약으로 Track 02 (JP 원본) 를 훑었다.
`A0 16` 827 건 → 규약 통과 **8 건**. 종류 $04·$08 제외, P 상위 $40-$7F 로 거른 것.

|---|---|---|---|---|
| `$01F4FDA` | 872 +1114 | $5A | $0E | $5A7B |
| `$1F2CF45` | 13898 | $80 | $09 | $4173 |
| `$35B40AA` | 23942 | $19 | $01 | $4153 |
| `$35F33BD` | 24052 | $D8 | $09 | $4023 |

높은 섹터는 오디오 잡음일 공산이 크다. **저지대 872 가 가장 그럴듯하다.**

판별법: P 를 따라가 헤더가 `(H & $7F) == $10` (니블표 16칸) 인지 본다.

## 3-2. 핸들러 셋 (전부 `JSR $7061` 로 모인다)

    $6F60  기본       $12/$13 = P + N + 1   표가 인라인 · $14/$15 = P+1

## 3-3. 프로브 `lua/GFX/0.6.0-source-block.lua`

정적으로는 여기까지가 끝이다. 세 핸들러가 `$7061` 한 곳으로 모이므로 **거기만**
걸면 `P`·`N`·헤더·표·본문이 다 잡히고, 뱅크도 이미 `$8000-$DFFF` 에 매핑돼 있다.
`$3B00` 이 원본 지문과 맞는 순간(`$71EE`/`$7256`)에 **그때 돌던 블록을 통째로 뜬다.**

뜬 바이트를 논리 이미지에서 그대로 바이트 검색하면 위치가 확정된다 (추측 0).

    산출물  dump/gfxsrc_0_6_0_<시각>_hits.tsv · _block<n>.bin · _buf<n>.bin · _summary.txt

판정:

    지문 일치 + 블록 덤프   -> 디스크에서 찾아 제자리 치환
    히트는 있는데 지문 없음 -> 헌정이 이 경로가 아니다. hits.tsv 로 다시 짠다
    히트 0                  -> 오버레이(섹터 251-254)가 그 장면에 없다

## 3-4. ★ 실기로 확정된 것 (2026-09-09 밤, 프로브 0.6.0/0.6.1)

### 헌정 화면의 VRAM 은 `$16A0` 이 아니라 `$1100` 이다

`build/gfx/dedication.tiles.tsv` 의 타일 번호는 **16진수**다 (`111`…`19B`, 중간에
`11A` 가 있어 10진일 수 없다). 즉 헌정은 **타일 `$111`-`$19B` = 136 장**이고
VRAM 워드 `$1110`-`$19B0` 이다. 화면 업로드의 MAWR 은 그 앞 `$1100`(타일 `$110`).

⚠ `SIG_WORD = $16A0` 은 **지문 타일 하나**의 주소일 뿐이다. 화면 시작이 아니다.
디스크를 `A0 16` 으로 훑던 것은 전부 헛수고였다.

### `$7061` 은 블록 진입점이 아니라 **루프 머리**다

`$7152 JMP $7061` 이 **명령마다** 돌아온다. 그래서 여기 훅을 걸면 히트가
블록 수가 아니라 RLE 명령 수가 된다 (실측 5,981).

게다가 압축 해제기가 **`$00` 을 카운터로 쓴다** (`$70D0 STA $00` 등). 그래서
첫 명령 뒤에는 P 가 파괴된다 -- "P=$8001, $8002, $8003…" 은 포인터가 아니라
덮어써진 카운트였다.

    ★ 올바른 훅 지점은 `JSR $7061` **호출부** 셋:  $6FA1 · $700E · $7056

### 제로페이지는 `$2000-$20FF`

프로브 0.6.0 이 `$0000` 에서 읽어 전부 `$FF` 를 봤다 (`$0000` 대는 VDC 포트).
`emu.read` 는 CPU 버스를 읽으므로 `$2000 + zp` 로 읽어야 한다.

### 레코드 포맷 -- 6 바이트 고정, `FF` 로 끝

CPU `$7635` (논리 섹터 253 +1589) 에 실물이 있다:

    $7635  03 00 00 11 B3 82     뱅크$03 종류$00 VRAM $1100 P=$82B3
    $763B  03 00 00 00 A2 91     뱅크$03 종류$00 VRAM $0000 P=$91A2
    $7641  FF                    끝

둘 다 프로브가 본 블록과 **정확히 일치**한다.

### ★★ 뱅크 -> 디스크 매핑

    논리 오프셋 = (247 + 4 x 뱅크) * 2048 + (P - $8000)

뱅크 하나 = 8 KB = 논리 4 섹터. 기준 섹터 247 은 `$4000-$5FFF` 오버레이 자리와 같다.
프로브가 뜬 512 B 와 **독립 3 점**에서 바이트 일치로 검증했다
(뱅크 $03 의 `$8004` · `$82B3` · `$91A2`).

⚠ 기준 247 은 이 장면 묶음 기준이다. `$3F80` 이 장면마다 바뀌면 기준도 바뀐다.

### 실물 블록 하나 확보 -- 다만 헌정은 아니다

    논리 $0081AB3 (섹터 259 +691)  헤더 $80  N=0
    압축 3,257 B  ->  4,800 B = **150 타일**  MAWR $1100

내용은 진짜 그래픽이다 (0 바이트 42.7%, 앞 64 B 가 빈 타일). 그런데 지문이 없다 --
부팅 직후(프레임 3553) 블록이라 다른 화면이다.

### ⚠ 눈먼 스캔이 실패한 진짜 이유 셋 (전부 내 가정이었다)

    1. 헤더를 (H & $7F) == $10 으로 걸렀다   -> 진짜는 **N = 0** (헤더 $80)
    2. 출력이 128 배수여야 한다고 걸렀다     -> 진짜는 **4,800 B**, 배수가 아니다
    3. 지문을 전개 후에서만 찾았다           -> N=0 이면 전개가 아예 없다

`tools/gfx_block_codec.py` 는 셋 다 고쳤다.

## 3-5. ★★★ 헌정 블록 확정 (2026-09-09 밤)

    디스크 논리 $0224B4B  (섹터 1097 +843)      ← 여기가 그 자리다
    뱅크 $07 · P=$934B · 헤더 $80 · N=0
    압축 1,153 B  ->  4,032 B = **126 타일** (MAWR $1100 = 타일 $110~$18D)
    0 바이트 82 %

확인 방법 (독립):

    풀어낸 타일 $16A 자리(+2880) = 80 00 40 00 20 00 10 00 08 00 04 00 03 00 FC 00
                                    ↑ 몇 달 전 Lua 가 VRAM 에서 잰 BUFFER_SIG 와 바이트 일치

블록은 디스크에 **빈틈없이 붙어 있다** -- 이 블록 끝 `$0224FCC` 가 다음 블록의 시작이다.
그래서 제자리 치환은 **1,153 B 안에** 들어가야 한다.

### 뱅크 -> 디스크 매핑은 **장면마다 기준이 다르다**

    논리 오프셋 = (기준섹터 + 4 x 뱅크) * 2048 + (P - $8000)

    기준 247    부팅/타이틀 묶음      (뱅크 $03 -> 섹터 259)
    기준 1067   헌정이 있는 묶음      (뱅크 $06/$07/$09/$13 -> 1091/1095/1103/1143)
    기준 1167   또 다른 묶음          (뱅크 $05..$09 -> 1187..1203)

⚠ 그래서 기준을 하나로 고정하면 안 된다 (`$3F80` 이 장면마다 바뀐다).
가장 안전한 방법은 **프로브가 뜬 바이트로 디스크를 바이트 검색**하는 것이다 -- 매핑 가정이 0.

### 인코더 -- 원본과 대등하고, 한글은 넉넉히 들어간다

`$40-$7F` 0 채우기 · `$03-$3F` 짧은 RLE · `$01` 16비트 RLE ·
`$C0-$FD` **0 과 리터럴 번갈아** (플레이너 4bpp 가 `XX 00 XX 00` 이라 이게 핵심) ·
`$80`/`$81-$BF` 리터럴 · `$FF` 끝. 탐욕 인코더로 충분하다.

    원본 4,032 B  -> 우리 인코더 1,166 B   (원본 압축기 1,153 B · 13 B 차)  왕복 일치
    한글 4,448 B  -> 우리 인코더   914 B   ★ 1,153 B 자리에 **239 B 여유로 들어간다**

왕복(풀기->다시압축->풀기)이 바이트 단위로 일치한다. 코덱은 양방향 검증 완료.

### ★ BAT 도 찾았다 -- 블록 순서가 열쇠였다

프레임 순서를 보면 **타일 블록 뒤 3 프레임에 항상 BAT 블록**이 온다:

    프레임 6279  def  VRAM $1100  뱅크$07 P=$934B   ← 헌정 타일
    프레임 6282  $08  VRAM $0000  뱅크$09 P=$91C1   ← 헌정 BAT

    헌정 BAT  논리 $02289C1  압축 789 B -> 2,048 B = 32x32
              ⚠ 종류 $08 은 헤더가 2 B 다 -- 본문은 **P+2** (P+N+1 이 아니다)

배치를 풀어보니 타일이 **열마다 아래로** 증가한다 (열1: $111..$11B, 열2: $11C..$126 …).
원본 헌정은 **세로쓰기**다. 쓰는 타일 범위가 `$111-$18C` 로 타일 블록(`$110-$18D`)과
정확히 맞물린다 -- 신원 확정.

⚠ 헷갈리기 쉬운 것: 같은 장면의 다른 BAT 블록(`P=$8DE5`)은 행 3-28 을 꽉 채운
**다른 화면**이다. "우리 타일 범위를 가리키는 워드 수" 만으로 고르면 그걸 집는다.
블록 **순서**로 골라야 한다.

### ★★ 크기 -- 둘 다 들어간다 (인코더는 DP 로)

명령을 우선순위로 고르는 탐욕은 한쪽만 잘한다 (`$02` 를 앞에 두면 BAT 은 좋아지고
타일이 나빠진다). 자리마다 모든 명령을 후보로 놓고 **뒤에서부터 최소 비용**을 구한다.

    헌정 BAT    2,048 B  ->  558 B   (원본 789 B   · 231 B 낫다)
    헌정 타일   4,032 B  ->  999 B   (원본 1,153 B · 154 B 낫다)
    ★ 한글 타일 4,448 B  ->  771 B   (자리 1,153 B · **382 B 여유**)

풀기->다시압축->풀기 왕복이 바이트 단위로 일치한다. 코덱 양방향 검증 완료.
구현은 `tools/gfx_block_codec.py` 의 `encode()`.

⚠ 남은 확인 둘:

    1. 한글은 139 타일이라 원본 126 타일보다 13 장 많다.  타일 $18E-$197 을
       새로 쓰게 되는데 그 자리를 다른 것이 쓰는지 확인해야 한다
    2. **BAT** -- 화면의 타일 배치표도 같이 바꿔야 한다.  헌정 장면의 다른 블록
       (VRAM $0000 계열 · 종류 $08) 중에 있을 것이다.  `build/gfx/dedication.bat.tsv` 참고

### 치환 방법

914 B 를 앞에서 덮고 **나머지는 그대로 둔다**. 압축 해제기는 `$FF` 에서 멈추고
다음 블록은 자기 레코드의 P 로 따로 찾아가므로, 뒤에 남은 옛 바이트는 아무도 안 읽는다.
Mode 1 섹터라 EDC/ECC 재계산이 필요하다 -- `build_disc_subtitle_hook.rebuild_mode1_sector` 를 쓴다.

## 3-6. ★★ BAT 은 **열 우선**이다 (제일 위험했던 함정)

    화면 (행, 열)  <-  자료[열 * 32 + 행]

VDC 쓰기 자동증가를 **32** 로 놓고 열 방향으로 채우기 때문이다 (핸들러 앞의
`JSR $4776`/`$476B` 가 그걸 세운다). 행 우선으로 그리면 화면이 **90 도 눕는다**.

⚠ 무서운 건 누운 화면도 "세로쓰기 일본어" 처럼 그럴듯해 보인다는 것이다.
실제로 한동안 "원본 헌정은 세로쓰기다" 라고 결론 내렸다가, 소유자가 실기
스크린샷을 보여주고 나서야 틀린 걸 알았다.

    검증법: 원본 타일+BAT 을 그려서 **일본어가 읽히는지** 본다.  읽히면 맞다.
