## 1. 결정적 단서 — 소유자가 Event Viewer 에서 찾았다

폐공장에서 UI 를 부르면 `$1A00` **Register (R)** 이 무더기로 찍힌다.
PC 는 `$BCD7 · $BCDE · $BCE5 · $BD86 · $BD8C · $BD92 · $BD98 · $BDAE · $BE2D`.

★ **게임은 `$1A00-$1AFF` 를 단 한 번도 안 쓴다** (실측 3 분/90 회, 접근 0 회 —
`memory: arcade_card_2mb_available`). Snatcher 는 Super CD-ROM² 타이틀이고 게임
코드에 Arcade Card 의 존재가 없다. 따라서 저기 찍히는 것은 **예외 없이 우리 것**
이다. 범인 식별에 추론이 필요 없었다.

## 2. 사슬 — 실측으로 끝까지 이었다

### 2.1 무엇이 얼마나 (`0.5.186` · `0.5.187`)

```
정지 상태     AC 1 read + 5.8 write / frame        ← 상시 부하는 없다
메뉴 갱신     읽기 2,201 = 11 × 200 + 1
단일 이벤트   105(1회) · 209(2회) · 313(3회)       ← 전부 200 배수 + 1
active/blank  48 / 0                               ← 전부 활성 표시 구간
```

`0.5.187` 이 `$1A02/03/04` 쓰기에서 AC 주소를 복원했다. **5 개가 정확히 11 번
반복**된다:

```
STATE $010000 → DIR $0022E0 → STATE $010005 → TPL $010200 → PACK $1F2700
                    $0022E4                                      $08E7E0
                    $0022E8 · EC · F0 · F4 · F8 · FC · $002300 · 04 · 08
                    ★ 디렉터리 주소가 4 씩 연속
ATLAS 접근 0 → BIOS 폰트 경로가 맞다.  아틀라스 잔재 없음
```

레코드 전개 1 회 = **정확히 200 B**:

```
PACK   텍스트+메타   96 B   TEXT_SPAN = 0x60
TPL    상수 3 슬롯   96 B   CONST_SLOTS 3 × GLYPH_BYTES 32   ← 마침표·공백·줄임표
DIR    엔트리         4 B
STATE  2 회           4 B
```

### 2.2 누가 부르나 (`0.5.190` · 정적 디스어셈)

```
정문        $7F88  (bank B, Track 02 섹터 255-258)
              PHP / SEI / TMA #$20 / LDA #$69 / TAM #$20 / JSR $BCD2 / … / PLP
              ★ 전개 내내 인터럽트 차단 · Bank $69 페이지 인/아웃
헬퍼        $BCD2  (Bank 69 cave, 814 B)
루프 몸통   $5F20  slot = ($7FF1,$7FF2) + $84B5 → JSR $7F88 → 매직/식별 비교
바깥 루프   $5F97  INC $7FF1/$7FF2 · INC $7FFB · $5FAD CMP #$5C · JMP $5F20
★ 부른 자리 $5F34  507 회 중 507 회 — 단 한 곳
```

★ 섹터 250 = CPU **$5800-$5FFF** (섹터 251 이 $6000). 원본과 **479 B 다르다**
= 우리 코드다. `LDA $7FFB / CMP #$5C` 는 원본에 0 개, 우리 판에 1 개.

슬롯은 매번 같다 — 메뉴는 `$8D6D … $8D77` 연속 11 개, 국장실이든 폐공장이든
동일(같은 커맨드 메뉴). 다른 블록도 같은 모양: `$B5A0-$B5A6`(7) ·
`$AD1C-$AD1E`(3) · `$9BAE $9BAF`(2) · `$8E52`·`$A11D`·`$9E90`(1).

### 2.3 VDC — 이쪽을 제일 늦게 쟀는데 제일 나쁘다 (`0.5.191`)

```
                VWR       MAWR   폭(VWR 첫~끝 줄)
바닥(매 프레임)   512 B      2     34 줄 (25~59)
우리 버스트     1,408 B     12    196 줄 (48~244)
                1,068 B     14    203 줄 (45~248)
```

활성 표시가 ~240 줄인데 **200 줄에 걸쳐 VDC 를 건드린다.**
바이트가 3 배인 것보다 **덩어리(MAWR)가 2 → 14 로 흩어진 것**이 더 나쁘다.

## 3. 기전 — 지연이 아니라 **점유**다

`extraction/patch/static/build_ac_dynamic_0_1_14.py` 주석의 실측:

> the cost is CPU **occupancy**, not interrupt latency: the game reloads its
> scroll **every 10-12 scanlines by polling** … **there is no threshold to get
> under, it is linear.**

래스터 IRQ 이야기가 아니다. 게임이 **폴링**으로 10~12 줄마다 스크롤을 다시
얹으므로 안전선이 없고 비용이 선형이다.

### 시간 재계산 (추정 — 가정 포함)

```
후보 1 회        0.6.2      notpl
 낱개 셋업       ~270 cyc   ~270 cyc   ← LDA $1A00 / STA 변수 를 하나씩.  손 안 댐
 텍스트 TAI      ~576       ~576       ← 96 B × 6 cyc/B.  손 안 댐
 템플릿 TAI      ~576          0       ← notpl 이 없앤 것
 합계          ~1,420       ~845       -40 %

11 후보          ~34 줄      ~20 줄
글리프 업로드   1,408 B × ~6 cyc/B ≈ 8,450 cyc ≈ 18 줄
합계            ~52 줄      ~38 줄     (폴링 주기 10~12)
```

⚠ 가정 둘: Mesen Event Viewer 의 `Cycle` 열을 master cycle 로 읽었고
(1 스캔라인 ≈ 1,365 master ≈ 455 CPU), 블록 전송을 6 cyc/B 로 잡았다.
자릿수는 맞지만 정밀값이 필요하면 다시 재야 한다.

### ★ vblank 산수가 처음으로 맞는다

```
글리프 업로드 1,408 B ≈ 8,450 cyc   <   vblank 약 10,900 cyc
```

옛 기록의 "vblank 이송은 산술적으로 죽었다" 는 **엔진 671 B 복사(25,800 cyc)**
이야기다. 글리프 업로드는 다른 숫자고, **모아서 vblank 에 밀면 들어간다.**

## 6. 코드 수정 (커밋 안 함 · 굽기 전)

### 6.1 `build_ac_dynamic_0_1_14.py` — sentinel 자리 (★ 잠복 버그 제거)

구운 `0.6.2` 에는 상수 검사 코드가 **아예 없다** (디스크 바이트 확인:
`LDA #$60 / STA tpl_len / … / JSR set_ac / TAI $1A00→$5BE0` 사이에 CMP·분기 없음).
= 검사가 들어가기 전 빌더로 구운 판이다.

그런데 소스의 sentinel 이 이랬다:

```python
const_sentinels = (template[0], template[95]) = ($00, $00)
```

마침표의 윗줄과 줄임표의 아랫줄이라 **둘 다 항상 0**이다. 그대로 다시 구웠으면
검사가 처음 들어가면서 `0==0, 0==0` 으로 **항상 건너뛰는** 반대 방향 고장이
날 뻔했다 (게임이 `$5BE0-$5C3F` 를 `$FF` 로 채우는 것을 `0.5.188` 로 실측했다).

고침: **0 이 아닌 바이트 오프셋 두 곳**을 골라 쓰고, 고를 자리가 없으면 검사를
포기(매번 복사)한다. 빌드 로그에 이 줄이 찍힌다:

```
const sentinels : $5BE4=1F · $5C3A=6B  (0 아닌 바이트 6/96)
```

### 6.2 시험 디스크 도구 둘 — 하드링크로

⚠ **심볼릭 링크를 쓰면 안 된다.** NTFS reparse point 로 제대로 만들어져도
**Mesen 이 크기를 0 으로 읽어** BIOS 선택을 거부한다
("The selected file does not match the required size (262144 bytes)").
`build_scan_budget_test.py` · `build_no_template_test.py` 둘 다 `os.link` 로 바꿨다.

## 8. 다음에 할 것

### 8.1 대조군 (제일 급함)

원본 일본판 BIOS 로 **같은 폐공장에서 `0.5.191`**.
★ `Mesen_2.2.1_Windows/Firmware/[BIOS] Super CD-ROM System (Japan) (v3.0).pce.JP_ORIGINAL`
을 **명시적으로** 고를 것 (우리 빌드로 덮여 있을 수 있다).

소유자 예상은 "원본이 200 줄 폭일 리 없다" 이고 아마 맞다. 다만 이 주행의
목적은 **유죄 입증이 아니라 예산 목표**다 — 게임이 스스로 글자를 그릴 때
몇 B / 몇 덩어리 / 몇 줄인지가 우리가 맞춰야 할 값이다.

### 8.2 "본다" 만 접촉이 많은 이유

소유자 관측. `0.5.191` 로 항목마다 커서를 올려놓고 `R` 표식.
`vwr` 보다 **`mawr`(덩어리 수)** 가 갈릴 것으로 본다.

### 8.3 고칠 후보 — 이제 우선순위가 바뀌었다

```
A  글리프 업로드를 모아서 vblank 로      1,408 B ≈ 8,450 cyc < 10,900   ★ 산술 맞음
   (RAM 버퍼가 필요하다 -- 여유부터 재야 함)
B  덩어리 수 줄이기 (MAWR 14 -> 소수)    목적지를 이어붙여 전송 횟수를 줄인다
C  AC 낱개 셋업을 블록 전송으로          후보당 ~270 cyc.  바이트가 아니라 명령 수
D  탐색 깊이 11 -> 1~2 (호출부 $5F34)    A~C 와 곱해진다
E  템플릿 상수 제거 / sentinel 고침      이미 코드에 있음.  -576 cyc/후보
```

**하나만으로는 안 된다** — 오늘 두 번 확인했다. 문턱(10~12 줄)까지 내리려면
`~38 줄`을 3 분의 1 이하로 깎아야 하므로 **두세 개를 같이** 얹어야 한다.

## 11. 저녁 추가 — 미번역 대사 (RetroArch/기기, Mesen 정상)

증상: ADPCM 직후 자동으로 나오는 **그 대사 하나만** 일본어. 다른 곳은 다 한글.
**항상** 재현. Mesen 에서는 정상 번역. 두 번째 기기에서도 동일.

★ Mesen 이 같은 디스크로 한글을 보여주므로 **디스크 고정값은 전부 무죄**다 --
제어문자 · 미번역 · oversize · 팩 배정 · 인코딩이 한꺼번에 기각된다.
원인은 "런타임에 에뮬마다 달라지는 것" 안에만 있다.
CD Image Cache · CD 배속 · Beetle PCE · 우리 BIOS 는 전부 확인됨 -> CD 적재도 아니다.

### 엔진 점유 범위 — 확정: **$5B80-$5E1F · 672 B (671 B 사용)**

```
tools/build_subtitle_engine_*.py     SAFE_BYTES = 0x5E20 - base.ENGINE_LO
                                     주석 "672 B 슬롯 한도"  -> ENGINE_LO = $5B80
tools/build_subtitle_chain.py        "엔진 자리가 $5B80-$5E1F 672 B 인데 이미
                                      671 B 를 쓴다 -- 남은 자리가 1 바이트"
```

즉 **480 B ($5C40-$5E1F) 는 다른 모듈의 숫자다** -- `build_subtitle_disc_payload.py`
의 디스크 훅 스텁. 컷신 자막 엔진은 그보다 **192 B 아래에서 시작한다.**

```
$5B80-$5BDF   레코드 텍스트+메타 96 B   ← 조회 비교 바이트 $5B85-$5B89 가 여기
$5BE0-$5C3F   상수 3 슬롯 96 B          ← 오늘 낮에 본 "매번 다시 읽는 96 B"
$5C40-$5E1F   480 B                     ← AC 빌더가 알고 있는 예약 범위
              ─────────────────────────
              엔진은 $5B80 부터 671 B 를 쓴다.  위 셋을 전부 덮는다
```

⚠ **`build_ac_dynamic_0_1_14.py` 의 BIOS_FONT 가드 주석이 192 B 낡았다.**
"글리프 루프가 되살아나면 $5C40-$5E1F 480 B 를 덮는다" 고만 적혀 있는데,
실제로는 **레코드 텍스트/메타 자체가 엔진과 겹친다.** 가드가 지키는 범위가
실제보다 좁다.

### 그런데 겹침만으로는 증상이 안 나온다 -- 한 단계가 비었다

```
조회 매직   LDA $5B80 / CMP #$53      엔진 서명이 'S''U''B' 라 $53 로 통과한다
비교        $5B85-$5B89 vs $7FEC/$7FED/$7FF3-5
```

엔진이 앉아 있으면 비교가 틀리는 것은 맞다. **그러나 `copy_record` 가 후보마다
`TAI $1A00 -> $5B80` 으로 텍스트 96 B 를 덮어쓴다.** 그러면 첫 후보에서 엔진이
파괴되고 비교는 정상화된다 -- 자막이 깨져야지 조회가 실패할 이유가 없다.

그러므로 갈래가 둘이고, **어느 쪽인지는 아직 못 정했다**:

```
(가) 조회가 엔진을 덮어쓴다        -> 자막이 깨져야 한다.  관측과 다르다
(나) 무언가가 조회를 막는다        -> 미스 -> 조용히 일본어.  관측과 맞는다
     ★ (나) 라면 "엔진이 살아 있으니 캐시를 건드리지 마라" 는 가드가 어딘가에
       있다는 뜻이다.  아직 못 찾았다.  후보: CACHE_USED_MAGIC($5A) 게이트 ·
       상주/프리로더 쪽 · $7F88 정문 앞단
```

### 다음 한 걸음

**`copy_record` 진입 전에 조회를 막는 가드가 있는지** 소스에서 찾는다.
있으면 (나) 확정이고 고칠 자리도 그것이다. 없으면 (가)/(나) 둘 다 아니고
`return_miss` 로 가는 다른 경로(디렉터리 `PACK_ID == $FF` · `load_blob` 실패)를
런타임에서 봐야 한다 -- 그때는 `return_miss` 표식 진단판이 답이다.

곁가지로 소유자 가설 하나가 살아 있다: **"Beetle 이 음성 끝을 더 오래 잡는다"**
= Mesen 도 같은 취약점을 갖고 있고 여유만 넓다는 뜻. 그러면 "Mesen 에서 되니까
괜찮다" 는 판정 기준 자체가 무효다. 여유(종료 판정 -> 조회 사이 프레임 수)는
Mesen 만으로 잴 수 있다.
