## 1. 왜 밤새 못 찾았나 — 엉뚱한 자원을 뒤졌다

새벽 문서(`SNATCHER_2026-09-01_NIGHT_HANDOFF.md`)는 VRAM · BAT · SATB · 팔레트 ·
VDC 레지스터를 전부 재고 **원본과 같다**는 결론을 냈다.  그 측정은 전부 맞았다.

같은 순간을 두 자원에서 재면 이렇게 나온다.

```
VRAM   $7900-$7DBF     바뀐 바이트    0 / 2432     (0.5.77)
CPU    $5B80-$5E1E     바뀐 바이트  668 /  671     (0.5.105)
```

**파손은 화면 자원이 아니라 게임의 데이터에 있었다.**  우리가 화면을 망친 게
아니라 게임이 **잘못된 재료로** 그린 것이다.  그래서 화면 쪽을 아무리 재도
전부 멀쩡하게 나왔다.

새벽 문서 §3 이 마지막 후보로 지목해 놓고 못 재본 그 자리가 맞았다.

## 2. 증거 (`0.5.104` · 읽기 전용)

`$8411` 진입 뒤 `$5B80-$5E1E` 에 읽기 콜백을 걸었다.  자리별 첫 적중만 기록한다.

```
9401f SKIP@8411 track=$11 state=$00 sig=$38 · cmd=$01 status=$02
9607f READ $5B80  pc=$7064 ★게임  val=$00
9607f READ $5B83  pc=$70BF ★게임  val=$AD
9607f READ $5B84  pc=$70BF ★게임  val=$30
9607f READ $5B85  pc=$70BF ★게임  val=$5D
      ...  $5BA7 까지 순차
```

읽힌 값을 헬퍼 빌더 출력과 맞추면 정확히 일치한다.

```
$5B83  AD 30 5D D0 64   LDA $5D30 / BNE        헬퍼 entry
$5B88  A9 00 8D 02 1A   LDA #$00 / STA $1A02   ┐
$5B8D  A9 04 8D 03 1A   LDA #$04 / STA $1A03   │ set_ac($1F0400)
$5B92  A9 1F 8D 04 1A   LDA #$1F / STA $1A04   │ = AC_VRAM_BACKUP
$5B97  A9 01 8D 07 1A   LDA #$01 / STA $1A07   │ 자동 증가
$5B9C  9C 08 1A         STZ $1A08              │
$5B9F  A9 11 8D 09 1A   LDA #$11 / STA $1A09   ┘
$5BA4  03 01            ST0 #$01 (MARR)
$5BA6  AD 34 ..         LDA $5D34 (vram_lo)
```

`tools/build_subtitle_engine.py:131 set_ac()` 가 뱉는 시퀀스 그대로다.

**한 PC 에서 연속 주소를 읽는다 = 블록 복사.**  게임이 자기 VM 스택을 옮기면서
우리 코드를 실어 나른다.  그걸 스크립트 데이터로 되쓰면 "그리긴 그렸는데
엉뚱한 것" 이 된다.

`state=$00 · status=$02` — 이 주행의 스킵은 자막이 **이미 끝난 뒤**였는데도
읽힌다.  노출은 스킵 창에 국한되지 않는다.

## 4. ⚠ 밟은 함정 (다음에 또 밟지 말 것)

### 4-1. ★ 되돌리기를 그 자리에서 하면 BIOS 로 튕긴다

`$7FDF <- 0` 을 쓰는 것은 **슬롯 안에서 도는 렌더러**다.  그 콜백에서 671 B 를
바로 덮으면 실행 중인 코드가 데이터로 바뀌어 `RTS` 가 쓰레기로 돌아간다.

```
0.5.105 첫 판   state->0 에서 즉시 되쓰기   -> 자막 끝나자마자 BIOS 화면
고친 뒤         프레임 끝에서 PC 확인 후    -> PC=$67FB · 0프레임 대기 · 정상
```

`$8411` 은 게임 코드(슬롯 밖)라 즉시 해도 안전했다 -- **그래서 스킵만 통과하고
노스킵만 튕겼다.**  경로마다 다른 결과가 나오면 PC 위치부터 의심할 것.

### 4-2. ★ `0.5.77` 을 "진단 부하" 로 오해하고 빼지 말 것

가볍게 만들라는 요청에 `0.5.103` 에서 `dofile 0.5.77` 을 뺐다가 **노스킵·중간
스킵까지 전부 깨졌다.**  `0.4.6.48` 맨몸으로 돌아간 것이다.

```
안 그린 케이스   diff 0/2432      무해 -- 여기만 보고 일반화했다
그린 케이스      diff 1026/2432   실제로 일을 한다
```

⚠ **이 경고는 671 B 보존이 없던 때에만 참이다.**  `0.5.105` 가 671 B 를 되돌린
뒤로는 `0.5.77` 없이도 세 케이스가 전부 정상이다 (`0.5.105-no077` 실측).
그전까지는 유일하게 증상을 덮고 있던 물건이라 빼면 전부 깨졌다.  `0.5.103/0.5.104/0.5.105/0.5.106` 헤더에 경고를 박아 두었다.

### 4-3. 진단 계측이 무효였던 자리

`$5D30-$5D35` (control block) 는 **헬퍼가 상주 중일 때만** 유효하다.  슬롯이
게임 것일 때 그 주소는 VM 스택이라 값이 쓰레기다.

```
0.5.103 WIPE seen=255 done=161 done=250   <- done 은 최대 64.  게임이 쓴 값이다
```

### 4-4. 지운 가설 — AC 백업 슬롯 충돌

`AC_VRAM_BACKUP $1F0400` 은 ADPCM(`$2000`)·CD-DA(`$7900`) 가 **같이 쓴다**
(목적지가 상수 · 크기 2,432 B 고정 · `$1F0E00` 전까지 2,560 B 라 한 벌만 들어간다).
구조적으로 겹치는 것은 맞지만 **지금 증상의 원인은 아니다.**

`0.5.86` 덤프에서 짝이 제대로 닫혔다.

```
 6000f entry=1 save=1 restore=0     save #1 열림
12600f entry=2 save=1 restore=1     restore #1 닫힘
30600f entry=3 save=2 restore=1     save #2 열림
31200f entry=4 save=2 restore=2     restore #2 닫힘
```

끼어듦 없음.  설계대로 번갈아 돈다.  다시 재지 말 것.

### ★ `0.5.77` 폐기 (2026-09-01 확정)

`0.5.105-no077.lua` 로 세 케이스 전부 정상.  즉 `0.5.77`(복원 직전 AC 백업을
현재 VRAM 으로 갱신)은 **671 B 파손을 덮고 있던 것**이지 고친 게 아니었다.
오전 문서의 "성공 기준" 도 같은 이유로 재해석된다.

```
케이브에 넣을 것   671 B 저장/복원  하나뿐
버리는 것          VRAM 백업 갱신 (뜨거운 $5B83 훅 + 반납마다 7 천 회 API)
```

### (해결됨) `LOAD_077 = false` 가 왜 중요했나

`0.5.77` 은 뜨거운 `$5B83` 훅에 반납마다 7 천 회 API 라 **네이티브로 옮기기
부담스럽다.**  671 B 미반납이 진짜 원인이라면 오전의 `0.5.77` 성공은 이 파손을
우연히 덮고 있었을 가능성이 크고, 그렇다면 `0.5.105/0.5.106` 하나로 대체된다.

```
셋 다 정상   -> 0.5.77 폐기.  이식이 671 B 저장/복원 하나로 단순해진다   ★ 이쪽
```

## 8. 네이티브 이식 — ★ 이미 구현돼 있다 (0.8 POC)

**새로 짤 것이 거의 없다.**  `tools/build_subtitle_native_trigger_bios_0_8.py` 가
바로 이 동작을 65C02 로 갖고 있다.  지금 `0.4.6.x` 체인에서 **사라졌을 뿐이다.**

```
CPU_CACHE_LO    = 0x5B80
CPU_CACHE_BYTES = 671            <- 오늘 잰 671 B 와 정확히 같다
CPU_CACHE_AC    = 0x1F0E00       <- layout.AC_CPU_CACHE_BACKUP
```

```asm
; 저장 -- "resident가 helper/renderer로 덮기 전에 게임의 텍스트 레코드 캐시를 보존한다"
setac0($1F0E00)
D3 80 5B 00 1A 9F 02        TIN $5B80 -> $1A00 · 671 B      ; 한 방

; 복원 -- "renderer/helper가 남은 $5B80-$5E1E도 원래 게임 캐시로 되돌린다"
setac0($1F0E00)
페이지별 LDA $1A00 루프                                      ; TAI $1A00 은 금지
```

### ★ 자리 결정 -- 케이브 + 뱅크 $01 · 상주부 무수정

상주부 실측 (`0.4.6.48` Track02 · 헬퍼 지문 오프셋 0x92282)

```asm
$7F49  PHP / NOP / LDA #$3F / STA $17
$7F4F  JSR $FEC4        ★ 케이브에 판정을 묻는다 -- **복사보다 먼저**
$7F52  BEQ $7F85
$7F58  JSR $7F87        AC 포인터 = $1F1C00 (헬퍼 이미지)
$7F5B  JSR $7FA2        헬퍼 448 B 복사   (256 -> $5B80 · 192 -> $5C80)
$7F6C  JSR $5B83        헬퍼 ENTRY
$7F6F  JSR $7FBB        ★ 렌더러 671 B 복사 (256+256+159 = $5B80-$5E1E 를 꽉 채운다)
$7F77  STZ $7FDF / INC $5D30 / JSR $5B83      반납 경로
$7F85  PLP / RTS
```

```
상주부 예산   $7F49-$7FDE  150/151 사용.  여유 1 B ($7FDF 는 state)  -> 못 넣는다
```

**넣을 필요가 없다.**  `$7F4F` 의 `JSR $FEC4` 가 곧 "빌리기 직전" 이다.

```
저장   케이브가 자막 시작을 판정할 때 671 B -> AC $1F0E00
복원   케이브가 다음에 불릴 때 (state 0 이 된 뒤) 되돌린다
       ★ 케이브는 슬롯 밖이라 자기 코드를 안 덮는다 -- Lua 의 PC 가드를 구조로 대체
자리   케이브 $FEC4 는 이미 $FFD4 로 뱅크 $01 브리지를 갖고 있다
       뱅크 $01 CPU $FC7A-$FFD9  864 B 비어 있음 (JP 원본도 FF)
결과   상주부 한 바이트도 안 고친다
       -> 0.4.6.47 의 "Track02 는 0.4.6.42 와 바이트 동일" 감사 그대로 통과
```

⚠ `0.4.6.47` 에 **`TAI $1A00,$5B80,#653/671` 금지 가드**가 있다
(`F3 00 1A 80 5B ..` 를 dispatcher 에서 찾아 빌드를 세운다).  "state 발행 전
CPU renderer 선복사 금지" 라는 별개 계약이다.  우리 복원은 dispatcher 가 아니라
케이브에 들어가고 방향도 반대지만, **같은 서명을 쓰지 말 것** -- 페이지별
`LDA $1A00 / STA` 루프를 쓰면 걸리지 않는다 (0.8 POC 도 그렇게 한다).


### ★ 끼워 넣을 자리 (케이브 디스어셈블 · 2026-09-01)

도구: `tools/dis6280.py` (새로 만듦.  HuC6280 확장 포함 -- 블록전송 5 개가 7 B 라
65C02 표로 뜨면 그 뒤가 전부 밀린다.  `CPX/CPY #imm` 을 빠뜨려도 밀린다)

케이브 `$FEC4` 는 껍데기다.  **판정은 이미 뱅크 $01 에서 돈다.**

```asm
$FEC4  JSR $FFD4        ; 브리지
$FEC7  CMP #$00 / RTS   ; 0.4.6.48 DIRECT_TAIL
$FFD4  PHP / SEI / LDA #$01 / TAM #$80    ; MPR7 <- 뱅크 $01
$FFDA  JMP $F0EA        ; (뱅크 $01) -> ... -> JMP $F370
```

그래서 **새 트램폴린이 필요 없다.**  뱅크 $01 안에서 이어 붙이면 된다.

```asm
; 자막 시작 결정 -- 두 곳.  둘 다 5 B 라 JSR(3)+NOP NOP(2) 로 정확히 맞바꾼다
$F760  A9 01 8D DF 7F    LDA #$01 / STA $7FDF     CD-DA 시작
$F863  A9 01 8D DF 7F    LDA #$01 / STA $7FDF     ADPCM 시작

; 판정 진입 -- 3 B 라 JSR(3) 로 정확히 맞바꾼다
$F370  AD DF 7F          LDA $7FDF
```

```asm
; 뱅크 $01 $FC7A-$FFD9 (864 B 여유 · JP 원본도 FF) 에 새로 넣는다
start_sub:                    ; $F760 · $F863 이 부른다
    save 671 B -> AC $1F0E00  ; 상주부는 JSR $FEC4 **뒤에** 복사한다 -> 아직 게임 데이터
    LDA #$01 / STA $7FDF / RTS

entry_hook:                   ; $F370 이 부른다
    LDA $7FDF / BNE done      ; 자막 중이면 통과
    LDA $5B83 / CMP #$AD      ; 슬롯에 헬퍼 서명이 남았나 = 미반납
    BNE done
    restore 671 B <- AC       ; ★ 여기는 슬롯 밖 -> 자기 코드를 안 덮는다
done:
    LDA $7FDF / RTS           ; 원래 명령의 결과를 그대로 돌려준다
```

**플래그가 필요 없다.**  "슬롯에 우리 서명이 남았나" 로 미반납을 판정하고, 되돌리면
게임 데이터가 서명을 덮으므로 다음엔 저절로 안 걸린다.  자기정리된다.

⚠ **남은 설계 항목 -- AC 채널.**  저장/복원이 채널 0(`$1A00`)을 쓰면 판정 코드의
포인터를 망가뜨릴 수 있다.  `$F855` 근처가 채널 1(`$1A12-$1A14`)을 밀고 당기므로
채널 1 도 쓰인다.  진입 때 두 채널 레지스터를 밀어두고 나올 때 되돌리는 것이 안전하다
(864 B 여유라 바이트 부담은 없다).

⚠ **"$FECA-$FF0F 옛 ADPCM 판정이 죽었다" 는 미확인.**  ROM 전체에서 `20`/`4C`
바이트를 찾는 스캔은 그래픽·데이터까지 걸려 무의미했다.  죽었다고 **가정하지 말 것.**

### 옮길 때 확인할 것

```
[ ] $F61A / $F6EF 훅이 0.4.6.x 의 BIOS 패치와 안 부딪히는가
[ ] 되돌리는 시점이 **마지막 반납 뒤**인가 (Lua 는 프레임 끝 PC 로 회피했다)
[ ] 0.8 POC 는 키 하나(E6800_0E)에 고정돼 있다 -- 조건을 일반화해야 한다
[ ] $1F0E00 ~ $1F1100 = 768 B.  671 B 가 들어간다 (SATB 백업과 안 겹침)
```

⚠ Lua 판정은 **시점이 운에 맞은 것일 수 있다.**  되돌린 2 프레임 뒤에 상주부가
헬퍼를 다시 복사해 넣는 것이 관측됐다 (`0.5.77` 이 서명을 확인).  게임이 그 자리를
읽는 결정적 순간이 좁아서 통과하는 것으로 보인다.  네이티브는 `$F6EF` 처럼
**반납이 끝나는 지점**에 걸어 단단히 잡을 것.


### ★ 복사·반납 지점 실측 (`0.5.107` · 2026-09-01)

```
$5B80 <- $53   pc=$7FAA    복사 시작 ('S' 매직)       상주부
$5B83 <- $AD   pc=$7FAA    헬퍼 본체 복사             상주부
$5B80 <- $53   pc=$7FC3    복사 지점 2                상주부
$5B80 <- $53   pc=$BE50    복사 지점 3                RAM $BE50
$5B80 <- $00   pc=$5BEB    반납 STZ   ★ 슬롯 **안**
$5B80 <- $00   pc=$5C3F    반납 STZ   ★ 슬롯 **안**
$5B80 <- $79   pc=$EA9E    게임이 자기 VM 스택에 쓰는 것 (무관)
```

**결론 둘 -- 이식 설계가 여기서 정해진다.**

```
1. 복사하는 것은 BIOS 가 아니라 우리 상주부다
   -> 671 B 저장은 상주부의 복사 **직전**에 넣는다
   -> BIOS 케이브(여유 2 B)·뱅크$00 트램폴린(여유 5 B) 문제가 사라진다

2. 반납($5BEB·$5C3F)은 슬롯 **안**에서 일어난다
   -> 헬퍼가 복원하면 실행 중인 자기 코드를 데이터로 갈아치워 죽는다
   -> 복원은 반드시 슬롯 **밖**에서.  상주부가 다음에 도는 순간이 자연스럽다
   -> Lua 의 "프레임 끝 PC 확인" 우회를 네이티브는 구조로 해결한다
```

⚠ 복사 지점이 **셋**이다 (`$7FAA`·`$7FC3`·`$BE50`).  하나만 막으면 샌다.

### 폐기 -- `0.5.106` (프레임 표본 방식)

프레임 끝마다 `ours()` 로 점유를 판정했다.  **빌리는 구간이 한 프레임보다 짧아서**
프레임 끝에는 이미 VM 스택으로 돌아가 있다.  그림자가 우리 코드까지 같이 삼켜

**게임이 멈춘다.**  다시 쓰지 말 것 -- 아는 지점에서 뜨고 아는 지점에서 되돌리는

### ★ 자리 감사 -- 네 항목 (`tools/audit_bios_free_space.py`)

"이미지가 FF" 는 "아무도 안 쓴다" 의 증명이 아니다.  이 저장소는 그 함정을 다섯 번
밟았다.  그래서 승격 조건을 넷으로 못박고 **CDL(Mesen Code/Data Log)** 로 검증했다.

```
구간  뱅크 $01 $FC7A-$FCFC  131 B (실제 사용분)
[1] 직접 참조   0 건    뱅크 $01 코드 안의 JSR/JMP
[2] 포인터      9 건 -> 전부 뱅크 $00 벡터 (아래)
[3] 실행        0 / 131  (CDL)
[4] 데이터      0 / 131  (CDL)

대조군  케이브 $FEC4  코드 240·데이터 278 / 278 B     찍힘
        뱅크1 $F370  코드 64                          찍힘
        뱅크1 $F760  코드 32                          찍힘
바로 뒤 $FFDA (브리지 착지점)                          찍힘
```

**★ 뱅크를 안 따지면 전부 오탐이다.**  MPR7 이 뱅크 $01 이면 `$E000-$FFFF` 는
**전부** 뱅크 $01 이므로, 그 상태의 코드는 뱅크 $00 BIOS 루틴을 못 부른다.
반대로 뱅크 $00 코드가 도는 동안은 우리 자리가 안 보인다.  그래서 위험한 것은
**같은 뱅크 안의 참조**뿐이다.

결정적 증거: **뱅크 $01 의 `$E000` 이 전부 `00`(BRK)** 이다.  MPR7 에 올라간 채로는
즉시 죽는다.  그런데 CDL 은 그 구간을 실행됨으로 찍었다 -> 뱅크 $01 은 **다른 MPR
슬롯**에 매핑돼 실행된다 -> 거기서 `$FCxx` 를 참조하면 그것은 뱅크 $00 이다.

남았던 두 히트가 그래서 풀린다.

```
$E86B JSR $FE92    호출자가 $18C0 에 $AA/$55 를 쓴다
                   뱅크$00 $FE92 = LDA $18C5/CMP #$AA/LDA $18C6/CMP #$55  -> 짝이 맞는다
워드 $FCC0/$FCC2   뱅크$00 $FCC2 = AND #$20/BEQ/LDA $F3/STA $0002 ...  진짜 루틴
```

⚠ **한계.**  CDL 은 실제로 가 본 장면만 기록한다.  오프닝~접수처 위주 주행이라
후반부는 미지수다.  다만 이 구간은 시스템 카드 ROM 이지 게임 데이터가 아니다.
우리 코드가 접근하는 것은 `$5B80`(MPR2) · `$7FDF`(MPR3) · `$1A00`(AC 하드웨어)뿐이라
MPR7 전환과 무관하다.

### ★ 0.4.6.59 -> .60 : 스킵 감지를 같이 넣어야 했다

`.59` 는 671 B 반납만 넣었더니 **자막 전 스킵만** 깨졌다.  `0.5.108` 로 재보니
원인이 예상과 달랐다 -- 낡은 것을 덮어쓰는 게 아니라 **아예 안 돌려준다.**

```
4697f  state <- 1        저장
4697f  state <- 2        활성
4852f  SKIP@8411         state=$02 · 시작 뒤 155 프레임
       (그 뒤로 state 0 도, 복원(pc=$FCDB)도 오지 않는다)
```

자막 엔진이 스킵된 것을 몰라 `state=2` 에 갇히고, 복원 조건(`state==0`)이 영영
안 맞는다.  오전 Lua `0.5.102` 가 `$8411` 에서 `2->3` 을 강제하던 그 일이
네이티브에 없었던 것이다.

`$8411` 은 RAM 오버레이라 BIOS 에서 훅을 못 건다.  그래서 **게임이 보는 것과 같은
입력 조건**을 케이브가 직접 본다 (매 프레임 도니까).

```asm
$8011  LDA $222D / AND #$0C / BEQ / JMP $8411    게임의 스킵 판정
; -> entry_hook 에 34 B 추가.  가드는 0.5.102 와 동일
   state==2 · track $11 · sig $38 · $222D & $0C  -> state <- 3
```
