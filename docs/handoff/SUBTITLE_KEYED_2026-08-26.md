## 1. 갈래 A — 열쇠 파이프라인 (거의 끝)

### 1-1. 무엇이 바뀌었나

자막이 `event_id` 에 물려 있었다.  event_id 는 **재생 한 번**을 가리키므로 같은
음성이 다시 나오면 자막이 안 붙는다.  실측: 재생 1,650 회 = 고유 음성 389 개.
4 배가 헛돌고 있었다.

이제 **열쇠**로 문다.  열쇠는 음성 자체를 가리킨다.

```
수집 로그   key_text 열
클립 파일   k003078_6800_0E.bin
팩 색인     항목 앞 6 B
렌더러      6 B 가 그대로 박힌다
```

네 곳이 **같은 모양**이라 번역만 채우면 얹힌다.  재매핑 단계가 없어졌다.

### 1-2. 만든 것

```
tools/build_voice_keys.py          수집 로그 -> voice_keys.tsv + 자막 (--studio 로 스튜디오용도)
tools/build_subtitle_chain.py      팩 -> 엔진 -> 상주 -> 디스크 를 한 명령으로
tools/build_subtitle_keyed_experiment.py   실험 디스크
tools/ram_adpcm_to_wav.py          --in/--out 인자 추가 (판마다 폴더가 는다)
```

지금 상태:

```
voice_keys.tsv              389 열쇠 · 클립 1:1 · 전사 214 승계
voice_subtitles_keyed.tsv   118 행 (56 음성) · 손실 0
subtitle_pack.bin           89,598 B · ADPCM 색인 118 조각 · 충돌 0
디스크                      build/patch/0.4.5.9-subtitle-keyed/
BIOS                        build/bios_font/Syscard3_galmuri_0.4.5.9-subtitle-keyed.pce
```

**디스크와 BIOS 는 반드시 짝으로 쓴다.**  BIOS 케이브에 적재표(팩 상대섹터·섹터
수)가 박히므로 팩 크기가 바뀌면 BIOS 도 바뀐다.

### 1-3. ★ 팩을 구우면 엔진부터 다시 구워야 한다

`build_subtitle_engine_ac_timed_safe_poc.py` 가 **팩 오프셋을 상수로 굽는다.**

```python
count, index_off = struct.unpack_from("<HI", blob, 14)
record_off,      = struct.unpack_from("<I",  blob, 26)
args = dict(index_base=AC_PACK+index_off, record_base=AC_PACK+record_off, ...)
```

오늘 팩이 61,605 -> 89,598 B 로 커지면서 기록 시작이 **4699 -> 8058 로 3359 B
밀렸는데** 엔진은 4699 를 봤다.  디스크를 다시 구웠는데도 자막이 안 떠서 한참
헤맸다.

엔진 자리가 `$5B80-$5E1F` 672 B 인데 이미 671 B 를 쓴다 -- **남은 자리 1 바이트**라
머리를 런타임에 읽는 코드가 안 들어간다.  그래서 순서를 강제하는 것이 지금의 답이다.

```bash
python tools/build_subtitle_chain.py            # 팩부터 전부
python tools/build_subtitle_chain.py --check    # 어긋났는지만
```

엔진 옆에 그때 쓴 팩 해시를 적어 둔다(`engine_pack_stamp.json`).  어긋나면 알려준다.

### 1-4. 열쇠에서 sector 를 뺀 이유 (측정으로 확정)

```
(sector, end, rate)                 389/389   지금 열쇠
(end, rate)                          31/389   못 씀
(end, rate, length)                 282/389   못 씀
(end, rate) + 소리 3 B              384/389   ★ 이걸로 간다
(end, rate, length) + 소리 6 B      388/389
```

**sector 는 콘솔이 못 본다.**  BIOS 진입점 32 개(`$E000-$E05F`)를 전부 걸고 호출
이력을 통째로 뒤져도 없었다 (`PROBE_CD_SECTOR_0_1_0~0_1_2`).  애초에 그것은
적재가 끝난 뒤 드라이브가 멈춘 자리일 뿐 음성의 신원이 아니다.

**length 도 못 본다.**  워크램 `$2000-$3FFF` 를 훑어도 없다.  수집기조차
`cdrom.adpcm.adpcmLength` -- **칩 내부 레지스터**에서 읽는다.

**콘솔이 보는 것:**

```
end   $22A6/$22A7   상주부가 이미 읽고 있다
rate  $22AA         상주부가 이미 읽고 있다
소리  ADPCM RAM     end/4 · end/2 · 3·end/4 절대주소에서 1 B 씩
```

`read`/`length` 는 재생마다 흔들리지만(6794↔6795) **합인 `end` 는 안 변한다.**
그래서 `$22A6` 하나로 표본 자리까지 계산된다.

**재생 직전에 ADPCM RAM 이 이미 차 있다** (5/5 확인, `PROBE_ADPCM_ID_0_1_0`).
그러므로 재생 전에 표본을 뜨면 되고, "재생 중 포트 읽기가 소리를 깨뜨리나" 라는
위험한 질문은 안 해도 된다.

남은 5 충돌 중 1 건은 51,095 B 가 한 바이트도 안 다른 **같은 음성**이다
(디스크 두 곳에 실려 sector 만 달랐다).  합치는 것이 맞다.

### 1-5. ★ 다음에 할 것 — 케이브가 selector 를 채운다

렌더러는 **이미 표를 훑는다.**  하나만 뜨는 건 `selector` 내용이 빌드 때
박혀서다.

```lua
-- BIOS 케이브 $FEC4 (여유 103 B · 지금 177/280)
a.abs(0xAD, 0x22A6); a.branch(0xD0, "idle")        -- $22A6 == 00 ?
a.abs(0xAD, 0x22A7); a.emit(0xC9, 0x68); ...       -- $22A7 == 68 ?   ★ 상수
a.abs(0xAD, 0x22AA); a.emit(0xC9, 0x0E); ...       -- rate == 0E ?    ★ 상수
```

이 상수 두 개가 **한 음성만 통과시키는 문지기**다.  이걸 "값을 읽어 selector 에
쓴다" 로 바꾸면 된다.

```
케이브가 할 일        $22A6/$22A7 -> end · $22AA -> rate
                      ADPCM 포트로 3 B 표본
                      6 B 를 $5CEE 에 쓴다
엔진                  안 건드린다 (671 B 그대로)
```

selector 자리는 확정됐다 (`engine_ac_timed_safe_poc.json`):

```
selector        $5CEE   (엔진 +366)   <- 여기 6 B
next_selector   $5D3E   (엔진 +446)   <- 2 번째 조각용
```

`r3` 빌더가 열쇠를 박던 오프셋 366 이 정확히 이 `selector` 다.

**왜 케이브인가**: 이미 그 레지스터들을 읽고, 매 프레임 **제일 먼저** 돌고
(`JSR $FEC4` 가 상주부의 첫 호출), 여유가 103 B 다.  헬퍼는 VRAM 담당이라 역할이
다르고 도는 시점도 늦다.  엔진은 1 B 남아 불가능하다.

## 2. 갈래 B — VRAM 자리 (미완)

### 2-1. 증상

자막이 뜨면 **게임 그림이 깨진다.**  자리를 옮기면 그 장면은 낫고 다음 장면이
깨진다.  초상화가 조각나서 엉뚱한 데 뜨기도 한다.

### 2-2. SAT 겹침이 아니라 VRAM 충돌이다 (실측)

`PROBE_SUB_SATB_0_1_2` 프레임 2130:

```
슬롯  0-15  y186 · x99~211 · w7900~7CC0 · 팔레트 F   <- 우리 자막 (정상)
슬롯 20-23  y208~240 · x200~232 · w7900~7C00 · 팔레트 D   ★ 게임 아이콘
```

**게임 아이콘 4 개가 우리 글리프 자리를 가리키고 있었다.**  팔레트가 D 라 빨간
글자로 보였고, 안 겹친 하나가 원래 그림(파란 책)이라 섞여 보였다.

즉 SAT 배분 문제가 아니라 **패턴 데이터 자리** 문제다.  되돌리기를 강화해도
안 된다 -- 자막이 떠 있는 **동안** 게임이 그 자리를 읽어 그리기 때문이다.

> ⚠ Mesen 의 `pceVideoRam` 은 **바이트 주소**다.  SATB 는 바이트 `$2000` ·
> 한 항목 8 B · 패턴은 +4.  패턴 -> 워드는 `pattern << 5`.
> 워드 주소로 읽으면 엉뚱한 값이 나온다 (오늘 한 번 당했다).

### 2-3. 어제 만든 allocator 가 옳은 방향이다

고정 자리는 존재하지 않는다.  장면마다 게임이 쓰는 자리가 다르다.
`POC_SUBTITLE_DYNAMIC_FRAGMENT_ALLOCATOR` 가 **자막 띄울 때 그 순간 빈 자리를
고르는** 방식이고, 그게 맞다.

### 2-4. 오늘 찾은 원인 셋

**① allocator 가 음성 하나에만 반응했다** — 0.3.0 에서 고쳤다

```lua
local FIRST_TARGET = 0x6800
if endAddr ~= FIRST_TARGET ... then return end     -- 여기서 빠져나갔다
```

다른 음성이 오면 `reset()`·`choose()`·`patchRenderer()` 를 다 건너뛴다.
그래서 2 장면에서 **1 장면 자리를 그대로 쓰고** 반대편 그림이 깨졌다.
allocator 가 엔진이 열쇠 하나짜리이던 때에 맞춰 만들어졌고, 엔진만 표를 훑게
바뀌고 allocator 는 안 따라온 상태였다.

**② 후보가 VRAM 32K 중 8K 뿐이다** — 아직 안 고침

```lua
emu.write(ENGINE + 167, base >> 8, MEM)          -- MAWR 상위
emu.write(ENGINE + 276, (base >> 5) & 0xFF, MEM) -- 패턴 **하위 바이트만**
```

패턴 상위 비트를 안 고치니 `base>>13` 이 고정이어야 하고, 그래서 `$6000-$7FFF`
안에서만 고를 수 있다.  `0x100` 간격이라 **딱 28 자리**만 본다.

**③ `blank()` 조건이 틀렸다** — ✓ **0.3.1 에서 고쳐졌다** (아래 08-27 추가분 참조)

```lua
if blank(base) and not satbUses(base) then return base end
```

`blank()` 는 그 구간이 **전부 0** 이어야 통과시킨다.  그런데 VRAM 에는 예전에
쓰다 만 스프라이트 데이터가 남아 있다 -- 0 이 아니지만 **아무도 안 가리키는**
자리다.  그걸 전부 거절하고 있었다.

소유자가 스프라이트 뷰어로 확인: **실제로 쓰는 슬롯은 10 개 남짓 = 640 워드뿐**
인데 VRAM 은 그 몇 배가 "0 이 아니라서" 후보에서 빠진다.

써야 할 기준은 "0 이다" 가 아니라 **"아무도 안 가리킨다"** 다.
스프라이트(SATB)와 배경 타일(BAT) 둘 다 봐야 한다.

```lua
-- 이렇게 바꾼다 (오늘 만들려다 멈춘 것)
local function batUsed()
  local used = {}
  for i = 0, 0x0FFF do                      -- BAT 자리를 확실히 모르므로 워드 0..0xFFF
    local at = i * 2                        -- 틀리면 더 많이 막는 쪽이라 안전하다
    local entry = (rb(at) | (rb(at+1) << 8)) & 0x07FF
    for k = 0, 15 do used[entry * 16 + k] = true end   -- 8x8 4플레인 = 16 워드
  end
  return used
end

local function freeBlock(base, bat)
  if satbUses(base) then return false end
  for word = base, base + N - 1 do
    if bat[word] then return false end
  end
  return true
end
-- choose(): blank(base) 대신 freeBlock(base, bat) · 간격 0x100 -> 0x40
```

**④ 백업 장치가 둘이다** — 아직 안 고침

```
Lua          snapshot(base) / restore(base)
네이티브 헬퍼  prepareFirst 가 헬퍼 오프셋 42·134 를 base 로 바꾼다
```

둘 다 같은 자리를 백업·복원하는데 **뜨는 시점이 다르다.**  헬퍼가 우리 글리프가
이미 쓰인 뒤에 백업을 떴다면, 복원할 때 원본이 아니라 **글리프를 써 넣는다.**
초상화가 조각나서 남는 것이 이 증상으로 보인다 (가설 -- 확인 안 했다).

### 2-5. 0.3.0 을 돌린 결과 (참고)

```
DYNAMIC FRAGMENT armed: end=$7800 · first $7000     <- 음성마다 뜬다 (①은 고쳐졌다)
DYNAMIC FRAGMENT #1..#197: $7000 selected            <- 매번 같은 자리
DYNAMIC FRAGMENT restore $7000 (voice end)
DYNAMIC FRAGMENT armed: end=$3800 · first $7000
DYNAMIC FRAGMENT SKIP #3: safe 19-glyph block 없음   <- ②③ 때문에 못 찾는다
```

`SKIP` 이 나면 패치를 안 하므로 렌더러가 옛 자리를 가리킨 채 남고 **자막이 통째로
사라진다.**  0.4.0 에서는 "못 찾으면 앞 자리 유지" 로 바꿀 것.

## 0. 확정

`lua/SUB/0.3.5.lua` 로 자리 문제가 해결됐다.  확인된 것:

```text
자막 정상 표시
조각별 안전 VRAM 재선정
메탈기어 초상화 및 반대편 장면 정상
음성 종료 후 복원 정상
올바른 개입 시점 = $5C0B count_ok 이후
```

성공 로그:

```text
armed: end=$6800 · first $6800 · BAT 64x64/371패턴 · SATB 24
#1: $6800 selected at count_ok
#2: $6C00 selected at count_ok
restore $6C00 (voice end)
armed: end=$6800 · first $6000 · BAT 64x64/298패턴 · SATB 9
#1: $6000 selected at count_ok
```

조각마다 다른 자리를 고르고(`$6800` → `$6C00`), 음성이 끝나면 되돌리고, 다음
음성에서 다시 고른다.  이것이 의도한 동작이다.

## 1. 폐기 — 다시 만들지 말 것

```text
blank() 방식        VRAM 내용이 전부 0 인 블록만 고름.  0.3.1 의 freeBlock()
                    (BAT+SATB 참조 검사)이 대체했다
$5BA6 선개입 방식    키 조회 중에 렌더러를 고쳤다.  매 프레임 REBUILD 폭주가 나고
                    화면이 깨진다.  개입은 $5C0B count_ok 이후여야 한다
AC 이미지 전체 교체   헬퍼/렌더러를 통째로 다시 쓰는 방식.  INPLACE_IMAGES=true 로
                    VRAM 주소 피연산자 4 B 만 고치는 것이 맞다
```

이 문서 앞부분(§2-4 ①②③④, §3 다음 순서)은 그 시점의 기록이며 위 결론이 우선한다.

## 2. `SUB 0.3.5` 의 구성

`POC_SUBTITLE_DYNAMIC_FRAGMENT_ALLOCATOR_0_3_1.lua` 를 전역 변수로 설정해 부른다.

```lua
SUB_ALLOCATOR_VERSION = '0.3.5'
SUB_ALLOCATOR_INPLACE_IMAGES = true       -- AC 헬퍼/렌더러 교체 0 B, 주소 4 B 만

dofile('C:/snatcher/lua/POC_SUBTITLE_DYNAMIC_FRAGMENT_ALLOCATOR_0_3_1.lua')
```

**이 네 줄이 핵심이다.** 같은 `0_3_1` 파일이라도 전역을 안 켜면 폐기된 동작
($5BA6 선개입 + AC 이미지 교체)이 되고 화면이 깨진다.  기본값으로 그냥 부르지 말 것.

## 4. 참고 — 렌더러의 고정 base

디스크 빌드에는 allocator 가 없다.  헬퍼·렌더러에 `$7900` 이 상수로 구워져 있다.

```text
resident_renderer_slot_native_poll_0_8_3.bin  offset 167 = $79 · offset 276 = $C8
helper (303 B 내용 / AC 슬롯 320 B)            offset 41 · 133 에 같은 base
-> 글리프는 VRAM $7900-$7DBF (19 x $40 = 1216 word)
```

역할 구분:

```text
helper    AC 글리프 -> VRAM 복사.  주소는 상수
renderer  화면에 그림.             주소는 상수
allocator 그 주소를 고르는 로직.   ★ Lua 에만 있다.  헬퍼 안에 있지 않다
```

native 병합은 기존 헬퍼를 가져다 쓰는 것으로 되지 않는다.  "어디에 쓸지 고르는
로직"을 새로 만들어야 한다.

## 4-1. 아직 열려 있는 별개 문제 — 메탈기어 이후 배경(BAT) 침범

`0.3.5` 가 닫은 것은 **스프라이트/초상화** 쪽 자리 충돌이다.  그와 별개로
**자막 글리프가 BAT 배경 패턴을 덮는 문제**가 남아 있다.

```text
발생 시점   접수처가 아니다.  메탈기어가 나온 뒤 한참 진행해야 나온다
증상        문서 화면(예: 깁슨 환경 A 컴퓨터) 하단에 글리프 조각이 배경으로 뿌려진다
            본문 텍스트와 자막 자체는 정상
```

**접수처 검증과 섞지 말 것.** 접수처 쪽은 오프닝 선적재 지연 패치를 보는 별도
트랙이고(`subtitle-deferred` 빌드 + `lua/SUB/0.3.7.lua`), 거기서 `PASS` 가 나와도
이 배경 침범은 그대로 남는다.  반대로 이 침범이 보인다고 선적재 패치가 실패한
것도 아니다.

관련 빌드:

```text
build/patch/TEST/0.4.5.9-subtitle-deferred/
build/bios_font/Syscard3_galmuri_0_4_5_9_subtitle_deferred.pce
tools/build_snatcher_0_4_5_9_subtitle_deferred.py
```

다음 작업은 그 장면 세이브로 돌아가 **VRAM 실주소를 측정**하는 것이다.

## 4-2. 패턴 상위 비트 추적 (2026-08-27) — 창 확장의 벽

`0.3.36`~`0.3.39` 로 메탈기어 이후 문서 화면을 재고 강제 시험까지 한 결과다.

### 측정 (0.3.36, BAT/SATB 본체 제외 후)

```text
필요                    1,216 word (19 글자 x 0x40)
창 $6000-$7FFF          최대연속   768 word @ $6500 · 총여유  1,392
VRAM 전체               최대연속 3,824 word @ $1110 · 총여유 11,648
```

**자리는 창 밖에 있다.**  창을 넓히는 것이 맞는 방향이다.

### 강제 시험 (0.3.37~0.3.39) — 패턴 상위 2 비트는 실재한다

`base` 를 `$1110` 으로 강제하고 아는 세 바이트만 패치했다.

```text
패치 결과   렌더러 off165/167/276 = $10/$11/$88   (전부 기대값, 패치는 먹었다)
            AC 헬퍼 off39/41/131/133 = $10/$11/$10/$11
글리프 쓰기  base $1110 = 19/64 word 채워짐  ·  $7900 = 0/64
SATB 실제   $7100 $7140 $7180 ... $74C0   (16 개, 0x40 간격 = 우리 글리프)
```

`$7100 >> 5 = 0x388`.  하위 바이트는 우리가 쓴 `$88` 인데 상위가 `0x03` 으로
남았다 — 원래 base `$7900 -> 0x3C8` 의 그 `3` 이다.

**쓴 곳($1110)과 읽는 곳($7100)이 갈라졌다.**  화면에는 글리프 대신 `$7100` 의
게임 데이터가 그려진다.  창이 `$6000-$7FFF` 로 묶여 있던 이유가 이것이다 —
그 범위에서는 `base>>13` 이 항상 3 이라 상위 비트를 안 고쳐도 맞아떨어진다.

### 상위 비트는 우리 바이너리 밖에 있다

```text
renderer  off 162-169  ST0/ST1/ST2 로 MAWR = base        <- 글리프 쓰기 주소
          off 268-284  SATB 스테이징 3 바이트만 채움
                       [X+0] Y  ·  [X+1] 패턴 하위  ·  [X+2] $BF (속성)
          off 344-363  $10/$11 = $5CEE (스테이징) 세팅 후  JSR $6463 · RTS
helper                 VRAM 백업/복원 전용.  $7900 구간을 AC $1F0400 에 떠뒀다
                       되돌린다.  SATB 도 글리프도 안 건드린다
                       (off 39/41 = MARR 하위/상위, off 131/133 = MAWR 하위/상위)
```

즉 스테이징을 SATB 로 펼치는 것은 **게임 루틴 `$6463`** 이고, 패턴 상위 비트는
거기서 붙는다.  렌더러/헬퍼에 `A9 03` 이 없던 이유다.

`$6463` 은 bank 6A 라 디스크에 있고 원리상 패치 가능하다.  **다만 디스크의 정적
내용을 그대로 믿으면 안 된다** — `$66xx` 영역은 장면마다 다른 오버레이로 덮인다
(같은 문서 §4 의 `$66E5` 사례).  정적 디스어셈블은 루틴 중간처럼 보였다.

### 다음 측정

`$6463` 을 **런타임에** 읽어야 한다.  자막이 뜨는 순간 `pceMemory` 의
`$6463` 부터 한 덩어리를 덤프하는 읽기 전용 Lua 면 된다.  거기서 패턴 상위
바이트를 만드는 자리를 찾으면 창 확장이 열린다.

### 선택지 정리

```text
A  창 확장        $6463 의 상위 비트 자리를 찾아 패치.  자리는 확실히 있다(3,824 word)
B  조각 쪼개기     19 글자 -> 10 글자면 640 word.  창 안 최대연속이 768 이라 들어간다
                  --max-glyphs 가 빌드 파라미터라 상위 비트 추적이 필요 없다
C  자막 건너뛰기   문서 화면처럼 배경 타일이 빽빽한 장면은 자막 대신 타일 번역으로
                  대체한다.  키 단위로 "자막 없음" 을 표현하면 된다
```

**B 가 지금 가장 싸다.**  창 안 최대연속 768 word > 640 word 이므로 상위 비트를
건드리지 않고도 이 장면이 해결된다.  A 는 근본적이지만 게임 루틴 추적이 남아 있고,
C 는 어느 쪽이든 정책으로 가져갈 값어치가 있다.

## 4-3. ★ 2026-08-28 — 「글리프 쓰기가 배경을 덮는다」는 가설은 반증됐다

§4-2 까지의 추적으로 주소 지정에 필요한 것을 전부 찾았다.

```text
renderer off 165 MAWR 하위 · off 167 MAWR 상위 · off 276 패턴 하위
renderer off 281 = 0x80 | (패턴상위 << 4) | 팔레트     ★ 창을 묶던 비트
helper   off 39/41 MARR 하위/상위 · off 131/133 MAWR 하위/상위
base 는 반드시 32 word 배수 (& 0xFFE0)
```

`off 281` 의 정체는 `build_subtitle_engine.py` 주석에 있었다 -- 레코드 5 번째
바이트가 `0x80 | ((word>>8)<<4) | palette`, `word = base>>5`.  `$6463` 이
`AND #$70` 으로 패턴 상위를, `AND #$8F` 로 속성을 뽑는다.  base `$7900` 이면
`0xBF` 가 된다.  **바이너리에서 `A9 03` 을 찾으면 안 나온다** -- `<<4` 되어
`0xBF` 안에 섞여 있다.

### 그리고 전부 맞춘 결과

`SUB 0.3.41` 로 base 를 `$1140` 강제:

```text
렌더러 off165/167/276 = $40/$11/$8A · off281 = $8F
SATB 실제 = $1140 $1180 $11C0 $1200 ... $1500      <- 예상과 완전 일치
$7900 = 0/64        (더 이상 아무도 안 쓴다)
$7100 = 사용 안 함   (0.3.40 에서 상위 비트가 3으로 남아 가리키던 자리)
```

**주소 사슬이 완전히 일치했는데도 하단 깨짐이 그대로였다.**

### 결론

하단 글리프 침범은 **우리 글리프 쓰기가 만드는 것이 아니다.**  allocator 를
완성하거나 창을 넓혀도 이 증상은 사라지지 않는다.  §4-1 과 §4-2 가 전제한
"글리프가 배경 타일을 덮어쓴다" 는 폐기한다.

다만 §4-2 에서 찾은 오프셋들은 유효하다.  allocator 네이티브 이식에 그대로 쓴다.

### 다음에 볼 곳

```text
1  ★ 자막을 완전히 끈 상태에서 그 장면이 깨지는지 먼저 확인할 것
   렌더러 offset 366 의 열쇠 6 바이트를 0 으로 만들면 자막이 아예 안 그려진다.
   거기서도 깨지면 자막과 무관한 문제다.
   이 확인을 안 하고 자막 쪽만 계속 팠다 -- 오늘의 가장 큰 낭비였다

2  깨진 칸의 BAT 엔트리를 읽어 패턴 번호를 구하고,
   그 패턴이 가리키는 VRAM 구간에 누가 쓰는지 추적

3  의심 후보 (미검증)
   - 자막이 쓰는 팔레트/속성이 배경에 영향
   - 렌더러가 SATB 스테이징($5CEE~)을 넘기는 JSR $6463 쪽 부작용
```

## 4-3b. ★ 원인 확정 (2026-08-28 환경 B) — allocator 는 미래를 모른다

§4-3 에서 "글리프 쓰기가 배경을 덮는 것이 아니다" 까지 좁혔다.  환경 B에서 부하
시험(`allvoice` BIOS + `0.3.5-allvoice-guard.lua` + `watch_allocator.py`)으로
**원인을 확정했다.**

```
음성 16 · 조각 36 · SKIP 0        자리를 못 찾은 적이 없다
그런데도 초상화 장면에서 깨진다    = 찾은 자리가 안전하지 않았다는 뜻

INTRUDER 슬롯 16 패턴 $6400~$647F   우리 블록 $6000~$64BF
INTRUDER 슬롯 18 패턴 $6300~$63FF
INTRUDER 슬롯 19 패턴 $6200~$62FF
INTRUDER 슬롯 20 패턴 $6100~$61FF
INTRUDER 슬롯 21 패턴 $6000~$60FF
```

**초상화 스프라이트 5 개가 우리 블록을 통째로 덮었다.**  allocator 가 고를 때는
비어 있었고 그 뒤에 게임이 가져갔다.  "그 순간 비어 있는 자리를 고른다" 는 전략
자체가 부족하다 -- 미래에 게임이 무엇을 쓸지 모르기 때문이다.

상세: `SNATCHER_ALLOCATOR_CDDA_2026-08-28.md` §3

## 4-4. ★ 결정 (2026-08-28) — 그림이 많은 화면은 자막을 넣지 않는다

메탈기어 이후 문서 화면(깁슨 환경 A 컴퓨터)은 **타일맵 절반이 그림**이다.
실측 892 패턴 = 약 14,272 word 가 배경에 묶여 있고, 창 여유는 1,392 word 뿐이다.

이 화면은 **자막을 넣지 않는다.**  화면의 글자는 어차피 그림/타일 한글화 경로로
번역되므로, 없는 VRAM 을 쥐어짜서 같은 정보를 두 번 그릴 이유가 없다.

```text
음성 자막   소리에 대한 것.  화면에 글자가 없을 때 쓴다
타일 번역   화면에 이미 글자가 있으면 그쪽으로 처리한다
```

### 이 결정이 요구하는 것

```text
1  키 단위로 "자막 없음" 을 표현할 방법
   자막 표에서 그 키를 빼거나, 명시적 건너뛰기 표시.
   voice_subtitles_keyed.tsv 에서 해당 열쇠 행을 비우면 된다

2  allocator 의 SKIP 이 안전해야 한다
   자리가 없는 장면이 정책적으로 존재하게 되므로,
   못 찾았을 때 옛 base 에 쓰는 경로는 반드시 막아야 한다
```

### 이것으로 닫히지 않는 것

이 결정은 **그 화면 하나**를 처리한다.  자막이 실제로 뜨는 다른 장면에서
스크롤·타일 스트리밍이 일어나면 §4-3 의 문제가 그대로 남는다.  특히
헬퍼의 백업/복원이 의심스럽다.

```text
자막 시작   base 구간 1,216 word 를 AC $1F0400 에 백업
자막 종료   그 백업을 base 구간에 되쓴다
   -> 그 사이 게임이 그 구간에 새 타일을 올렸다면 복원이 그것을 덮는다
```

base 를 $7900 -> $6100 -> $1140 으로 옮겨도 깨짐이 그대로였던 것과 정합한다.
쓰기 경로만 옮겼고 복원 경로는 그대로였기 때문이다.  **미검증 가설이다.**
확인법: `restore()` 를 건너뛰고 같은 장면을 지나 하단 깨짐이 사라지는지 본다.

## 5. 다음 단계

**이 allocator 를 범용 음성 키와 결합해 모든 자막에 적용한다.**

지금 `0.3.5` 는 `TARGET_END = 0x6800` 한 음성에만 반응한다.  native BIOS 도 그
음성 하나만 자막 엔진을 시작시킨다.  키 파이프라인(§1)이 이미 열쇠 표를 갖고
있으므로, 엔진이 표를 훑게 되면 allocator 도 같이 따라가야 한다.
(0.3.0 에서 한 번 겪은 문제다 -- 엔진만 바뀌고 allocator 가 안 따라와 2 장면에서
1 장면 자리를 그대로 썼다.)

## 6. 오늘 이 문서에서 정정된 것

작업 중 다음을 잘못 기록했다가 고쳤다.  같은 실수 반복 방지용으로 남긴다.

```text
"헬퍼 303 B 가 320 B 슬롯에 덮여 잡종이 된다"
   틀림.  303 B 는 320 B 슬롯의 앞부분과 동일하고 뒤 17 B 는 00 패딩이다.
   SUBTITLE_HANDOFF_2026-08-24.md 에 "helper 303 B / AC 슬롯 320 B" 로 이미 적혀 있었다.
   파일 크기 차이만 보고 단정하기 전에 기존 문서를 볼 것.

"화면 깨짐은 전부 관측 도구 아티팩트다"
   틀림.  디스크 빌드의 $7900 고정도 별개로 존재한다.

"깨짐의 원인은 base 재배치 경로다"
   틀림.  폐기된 $5BA6 선개입으로 돌렸기 때문이다.
   0_3_1 을 기본값으로 부르면 폐기 동작이 된다는 것을 몰랐다.
```

공통점: **설정으로 동작이 갈리는 스크립트를 기본값으로 돌려 놓고, 그 결과를
스크립트 자체의 성질로 단정했다.**  전역 스위치가 있는 Lua 는 어느 조합으로
돌렸는지부터 확인할 것.
