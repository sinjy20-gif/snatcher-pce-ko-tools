## 1. 지금까지 확정된 사실 (실측 완료)

### 1.1 RAM 대여 — PASS

| 항목 | 결과 | 근거 |
|---|---|---|
| `$5B80-$5FFF` 대여·복원 | PASS | lifecycle v0.1.5, 실제 Mesen |
| IRQ1 벡터 설치·복원 | PASS | 흐름 `$40A4 → $5B80 → $40A4` |
| ADPCM 재생 중 해당 RAM 무결 | PASS | 등록된 재생 구간에서 미변경 확인 |

### 1.2 BIOS 패치 배치 — 안전 확인됨

정본(`JP_ORIGINAL`)과 현재 BIOS를 바이트 단위로 비교한 결과, 자막 패치는 정확히 3곳이다.

| 위치(파일) | CPU | 크기 | 원본 | 현재 |
|---|---|---|---|---|
| `0x00161A` | `$F61A` | 3 B | `STA $180D` | `JSR $FEC4` |
| `0x0016EF` | `$F6EF` | 3 B | `LDA $180C` | `JSR $FF74` |
| `0x001EC4` | `$FEC4` | 269 B | **전부 `FF`** | 케이브 |

- 케이브 자리는 원본이 전부 `FF`인 **진짜 죽은 영역**이다. 뒤로 11 B 더 여유가 있고
  `0x1FDC`부터 실제 점프 테이블(`JMP $E900` …)이 시작된다. → **케이브 한도 280 B, 현재 269 B 사용.**
- 훅 2개는 실제 명령을 덮었지만, 케이브가 그 명령을 대행한다
  (`$FEC4`가 `STA $180D`로 시작, `$FFCD`가 `LDA $180C`로 끝남). 구조는 맞다.

### 1.3 화면 자원 — 실측했으나 **결론은 부정적**

`dump/probe_vram_free_0_1_0_20260822_134338.tsv` (샘플 323회, 엔딩까지)

| VRAM 블록 | nonzero | changed | 해석 |
|---|---|---|---|
| `0000-06FF` | 323 | 0 | 항상 데이터 있음 = **점유** |
| `1000-13FF` | 323 | 68 | SATB. 가장 많이 바뀜 |
| `1400-1FFF` | 323 | 0 | 점유 |
| `7000-73FF` | 261 | 64 | 혼용 |
| `7400-77FF` | 197 | 82 | 혼용 |
| **`7800-7BFF`** | **34** | **46** | 대체로 빔, 그러나 **쓰기 발생** |
| **`7C00-7FFF`** | **46** | **38** | 대체로 빔, 그러나 **쓰기 발생** |

`nonzero=323`은 "샘플 전부에서 데이터가 있었다" = 점유라는 뜻이다.
비어 보이는 건 `7800-7FFF` 뿐인데 **여기도 게임이 쓴다.**

> **`$7B00`은 자유 영역이 아니다.** TARGET 로그에서 `7B00`은 323샘플 중 22회 쓰기·19회 비영(非零).
> `0.2.4`가 `$7B00`에 패턴을 올렸다가 실패한 건 이 사실과 일치한다.

### 1.4 IRQ와 게임 VDC 접근의 충돌 — **실측 완료, 위험 존재**

`dump/probe_irq_vs_satb_0_1_0_20260822_133515.tsv` (IRQ 19,421회)

| 구간 | 횟수 | 비율 |
|---|---|---|
| `IN_PUSH` (SATB 밀어넣는 루프 한가운데) | **0** | 0% |
| `IN_HOLD` (`$600C-$6527`, MAWR 들고 있는 구간) | **14** | 0.07% |
| `ELSEWHERE` (안전) | 19,407 | 99.93% |

- SATB 푸시 루프 한가운데로 IRQ가 들어온 적은 **한 번도 없다.** SAT 갱신은 걱정 안 해도 된다.
- 그러나 게임이 **MAWR을 들고 있는 동안** IRQ가 들어온 경우가 14회 있다.
  MAWR은 **쓰기 전용이라 저장·복구가 불가능하다.** 내 핸들러가 MAWR을 만지면 그 14회는 게임의
  VRAM 전송을 망가뜨린다.
- 대응은 하나뿐이다: **IRQ 진입 시 PC가 `$600C-$6527`이면 이번 프레임은 건너뛴다.**
  0.07%라 자막 1프레임 늦는 건 눈에 안 띈다.

## 2. 지금 막혀 있는 지점 — `0.2.5` 부팅 멈춤

### 2.1 어제 세운 가설은 틀렸다

"Mesen 펌웨어 파일명이 문제"라고 했는데, **아니다.**

```
42d360487d34e9bf72067e8705b70479  SUBTITEL_0.2.5.pce
42d360487d34e9bf72067e8705b70479  [BIOS] Super CD-ROM System (Japan) (v3.0).pce
```

Mesen이 읽는 정규 이름 파일이 **이미 0.2.5와 동일**하다. 파일명은 원인이 아니고
**0.2.5 자체가 멈춘다.**

### 2.2 케이브 디스어셈블 결과 — 유력 원인

설치 경로와 복원 경로가 **비대칭**이다.

```asm
; 설치 (FF59) -- 8/21에 고친 수동 루프.  152 B.
FF59: LDX #$00
FF5B: LDA $1A00
FF5E: STA $5B80,X
FF61: INX
FF62: CPX #$98        ; $98 = 152
FF64: BNE $FF5B

; 복원 (FFC6) -- ★ 안 고쳐졌다.  1152 B.
FFC6: TAI $1A00,$5B80,#$0480
```

8/21 인계서에 이렇게 적혀 있다:

> `TAI $1A00, $5B80, #length`는 AC data port `$1A00`만 연속 읽는 동작이 아니다.
> `$1A00/$1A01`을 번갈아 읽어 `$5B80`에 쓰레기 바이트가 들어갔다.

**그 명령이 복원 경로에 그대로 남아 있다.** 설치만 고치고 복원은 놓쳤다.

추가로 비대칭이 하나 더 있다:
- 백업 `TIN $5B80,$1A00,#$0480` → 1152 B 저장
- 설치 수동 루프 → **152 B만** 덮어씀
- 복원 `TAI` → **1152 B** 되돌림 (그것도 쓰레기로)

### 2.3 부팅 시 게이트

`$FECA`부터 다섯 조건이 모두 맞아야 설치로 넘어간다.

```asm
$22A6 == $00
$22A7 == $68
$22AA == $0E
$2202 == $A4      ; IRQ1 벡터 하위 = 게임 핸들러 $40A4
$2203 == $40
```

하나라도 틀리면 `PLX PLA PLP RTS`로 빠진다. 푸시 3 / 팝 3으로 **균형은 맞다.**
`stat`(`$FF74`)도 푸시가 없고 `$FFCD: LDA $180C / RTS`로 원래 명령을 대행하므로 균형이 맞다.

즉 **스택 균형은 이제 문제가 아니다.** 남은 의심은 위 2.2다.

### 2.4 그리고 구조적 전제 하나

설치 루프는 AC 오프셋 `$0500`에서 엔진 152 B를 읽어온다.
**그 152 B를 AC에 넣는 건 Lua 로더(`LOAD_SUBTITEL_0_2_5.lua`)다.**
Lua를 안 돌린 상태에서 게이트가 통과하면 쓰레기를 `$5B80`에 복사한 뒤
`$2202/$2203 = $5B80`으로 IRQ 벡터를 걸어버린다 → 다음 IRQ에서 쓰레기로 점프 = 멈춤.

## 3. 단계별 계획

### [A] 부팅 안정 — 지금 할 일

**A-1. 어느 훅에서 멈추는지 가른다 (실측)**

정본 BIOS를 놓고 훅을 **하나씩만** 넣은 BIOS를 각각 만든다.

| 빌드 | 훅1 `$F61A` | 훅2 `$F6EF` | 케이브 | 기대 |
|---|---|---|---|---|
| `0.2.6a` | 원본 유지 | 원본 유지 | 넣되 호출 안 함 | 반드시 PASS (케이브는 죽은 자리) |
| `0.2.6b` | `JSR $FEC4` | 원본 유지 | 있음 | ? |
| `0.2.6c` | 원본 유지 | `JSR $FF74` | 있음 | ? |

- `0.2.6a`가 FAIL이면 → 케이브 자리 전제가 깨진 것. 즉시 중단하고 재조사.
- `b`/`c` 중 FAIL 나는 쪽이 범인이다.

**측정 항목**: 각 빌드에서 부팅 도달 여부, 멈춘 시점의 PC.

**A-2. 게이트가 부팅 중에 통과하는지 센다 (실측)**

Lua 프로브로 `$FEC4` 진입 횟수와, 게이트 5조건 각각의 통과 횟수를 **부팅~타이틀 구간에서** 센다.

- 부팅 중 통과가 **0회**여야 정상이다.
- 1회라도 통과하면 → Lua가 AC를 채우기 전에 설치가 일어난 것 = 2.4가 원인 확정.
- 대응: 게이트에 **AC 매직값 검사**를 추가한다. Lua가 AC `$0500`에 매직(예: `4B 4F`)을
  써두고, 케이브는 그 매직을 확인한 뒤에만 설치한다. 비용 약 10 B.

**A-3. 복원 경로의 `TAI`를 수동 루프로 교체**

`FFC6: TAI $1A00,$5B80,#$0480` 를 설치 경로와 같은 형태로 바꾼다.
길이도 설치와 맞춰 **152 B**로 통일할지, 백업과 맞춰 1152 B로 할지 먼저 정한다.

> 판단 기준: 엔진이 152 B만 쓰는데 1152 B를 백업/복원하는 이유가 있는가?
> 없다면 **백업·설치·복원 전부 152 B로 통일**하는 게 맞다. AC 트래픽도 1/7로 준다.

**측정 항목**: 복원 직후 `$5B80`의 첫 5바이트. 게임 UI 엔진의 원래 값과 일치해야 한다.

**A-4. 케이브 예산 재확인**

현재 269/280 B. `TAI` → 수동 루프 교체는 +약 8 B, AC 매직 검사는 +약 10 B.
**269 + 18 = 287 > 280 → 넘친다.**

대응 후보:
- 백업/복원을 152 B로 통일하면 AC 주소 설정 블록 하나가 통째로 준다 (약 -20 B)
- 반복되는 AC 주소 설정 5블록(각 약 20 B)을 서브루틴 1개로 접는다 (약 -60 B)

**둘 중 하나만 해도 예산이 넉넉해진다. A-3과 같이 진행할 것.**

---

### [B] VDC 주소만 건드리기

케이브가 아니라 **`$5B80` 엔진** 쪽 작업이다. 여기부터는 케이브 예산과 무관하다.

- IRQ 핸들러에서 MAWR(`$0000`/`$0002`)만 설정하고 **데이터는 쓰지 않는다.**
- 반드시 **1.4의 스킵 조건**을 먼저 넣는다: 진입 시 PC가 `$600C-$6527`이면 즉시 복귀.

**측정 항목**: `IN_HOLD` 구간 진입 시 스킵이 실제로 걸리는 횟수. 프로브의 14회와 맞아야 한다.

---

### [C] 아주 작은 VRAM 전송

- `$7800-7FFF` 중 **한 워드**만 쓴다.
- 어디에 쓸지는 1.3 때문에 아직 못 정한다. → **선행 실측 필요**

**선행 실측 (C-0)**: `7800-7FFF`를 워드 단위로 쪼개, 323샘플에서 **한 번도 nonzero가 아니고
한 번도 changed가 아닌** 워드만 추린다. 현재 프로브는 블록 단위라 이 해상도가 없다.
`PROBE_VRAM_FREE`를 0.2.0으로 올려 워드 단위로 다시 돌린다.

> 기억해둘 원칙: **감시하지 않은 주소에 쓰지 않는다.** 여러 장면에서 죽어 있음을 증명한 뒤에 쓴다.

---

### [D] SAT 엔트리 1개

- 게임 SAT는 초반 샘플에서 0–16번을 썼다. **17–63은 후보일 뿐 확정이 아니다.**
- **선행 실측 (D-0)**: 엔딩까지의 로그로 SAT 슬롯별 최대 사용 번호를 집계한다.
  프로브는 이미 돌렸으므로 기존 덤프 재집계로 가능할 수 있다.

---

### [E]~[F] 글리프 표시

- 한글 글리프는 12×12를 8×8 타일 4개에 나눠 넣는다.
  사분면 오프셋은 이미 확인됨: `T`, `T+$10`, `T+$200`, `T+$210`.
- 1개 → 2 → 4 → 9개로 늘리며 매번 PASS 조건을 확인한다.

---

### [G] 실제 대사 연동

- ADPCM 클립 지문 `ADPCM_<read>_<len>_<rate>`로 재생 중인 클립을 식별하고 자막을 건다.
- 전사 결과 `snatcher_tool/logs/voice_transcript.tsv` (237/248) 활용.

---

### [H] CD-DA 자막

- 재생 위치는 `CD_SUBQ($E01E)`로 읽는다.
- 큐 시각은 `snatcher_tool/logs/cdda_transcript_tagged.tsv`의 `start`/`end`.
- `kind == 대사`인 222 세그먼트만 쓴다. 음악 트랙에 섞인 21구간은 **직접 청취로 확정 예정.**

## 5. 하지 말 것

- `$7B00`에 쓰지 말 것. 죽은 자리가 아니다 (1.3).
- 감시하지 않은 VRAM/RAM 주소에 쓰지 말 것.
- 케이브를 `0x1FDC` 이상으로 넘기지 말 것. 점프 테이블이 시작된다.
- AC 경로에 `TAI`/`TII` 계열 블록 전송을 쓰지 말 것. `$1A00`만 반복 읽는 수동 루프를 쓸 것.
- 정본 BIOS 백업(`*.JP_ORIGINAL`, `*.ORIGINAL_BACKUP`)을 덮지 말 것.

## 6. 추가 발견 (같은 날 밤)

### 6.1 SAT 슬롯 -- "0–16만 쓴다"는 전제가 깨졌다

`dump/vram_20260822_*.bin` 3개(각 64 KB 전체 VRAM)에서 SATB(`워드 $1000-$10FF`
= `바이트 $2000-$21FF`)를 직접 읽었다.

| 덤프 | 살아있는 슬롯 | 최대 번호 | 사용 슬롯 |
|---|---|---|---|
| `134756` | 7 | 6 | 0–6 |
| `135546` | 5 | 4 | 0–4 |
| `135610` | 26 | **27** | 0–5, **8–27** |

- **27번까지 쓴다.** `17–63이 후보`라는 기존 메모는 폐기한다.
- 6·7번이 비었는데 8–27이 차 있다 → 슬롯 배정이 **장면마다 유동적**이다.
  "N번 이상은 항상 빈다" 식의 가정은 성립하지 않는다.
- 이 덤프 3개는 **13:47~13:56, 약 9분짜리 한 구간**이다. 엔딩까지의 표본이 아니다.

> **D-0은 기존 덤프 재집계로 끝나지 않는다.** SAT 슬롯 점유를 장면 누적으로 기록하는
> 프로브를 새로 돌려야 한다. 기록할 것: 프레임마다 살아있는 슬롯 비트맵을 OR 누적,
> 그리고 "한 번도 살아난 적 없는 슬롯" 집합.

### 6.2 신규 버그 -- 엔딩 크레딧 후 타이틀 복귀 실패

증상: 엔딩 크레딧이 올라간 뒤 초기 타이틀로 돌아오지 않는다.

**우리 패치가 용의선상에 있다.** 근거:

- 훅 2개가 걸린 `$180C`/`$180D`는 CD-ROM 레지스터다.
- 엔딩 후 타이틀 복귀는 CD 재초기화를 탄다 → 훅이 그 경로에서 반드시 밟힌다.
- `$FF74`(`stat`) 게이트가 그 순간 우연히 맞으면 **2.2의 `TAI` 복원 경로**가 실행되어
  `$5B80-$5FFF`를 쓰레기로 덮는다.

**가르는 실험 (비용 낮음):**

정본 BIOS로 되돌리고 엔딩만 다시 본다.

```bash
cp "Mesen_2.2.1_Windows/Firmware/[BIOS] Super CD-ROM System (Japan) (v3.0).pce.JP_ORIGINAL" \
   "Mesen_2.2.1_Windows/Firmware/[BIOS] Super CD-ROM System (Japan) (v3.0).pce"
```

| 정본에서 | 해석 |
|---|---|
| 복귀 **안 됨** | 게임/에뮬 문제. 우리 책임 아님. 별건으로 분리 |
| 복귀 **됨** | 우리 훅이 범인. A-3(`TAI` 교체)로 같이 잡힐 가능성 높음 |

이 실험은 A-1보다 먼저 해도 된다. 결과가 `우리 책임 아님`이면 A 단계에서 고려할
변수가 하나 줄고, `범인`이면 A-3의 우선순위가 올라간다.
