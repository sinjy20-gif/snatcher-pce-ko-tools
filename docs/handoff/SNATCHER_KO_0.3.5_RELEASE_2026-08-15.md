# SNATCHER KO 0.3.5 — 릴리스 노트 및 롤백 절차 (2026-08-15)

```
디스크    build\patch\0.3.5\Snatcher CD-ROMantic (Japan) [KO 0.3.5].cue
진입점    extraction\patch\static\build_snatcher_ko_0_3_5.py
근거      docs\handoff\SNATCHER_FLICKER_ELIMINATION_2026-08-15.md  (§0 원인)
          docs\handoff\SNATCHER_UI_FLICKER_HANDOFF_2026-08-14.md   (원인 A/B)
```

0.3.4 와 마찬가지로 **번역 데이터가 아니라 런타임 코드**가 바뀐 릴리스다. 레코드
하나를 재구성하는 동안의 CPU 점유를 줄였다.

---

## 1. 왜 점유를 줄이나

08-15 §0 이 밝힌 기전이다.

```
게임    하늘을 10~12 스캔라인마다 스크롤을 갈아끼우며 그린다 (폴링)
우리    레코드 하나를 재구성하는 동안 CPU 를 붙잡는다
충돌    점유가 갱신 지점을 걸치면 갱신이 한 줄 늦고 경계가 밀린다
```

**임계값이 아니라 확률이다.** 점유가 짧을수록 걸칠 확률이 낮아진다. 인터럽트
차단이 아니므로 TAI 를 더 쪼개는 것으로는 안 되고(§2 에서 0.27 줄까지 줄여도
그대로였다), 실제로 붙잡는 시간을 줄여야 한다.

---

## 2. 무엇이 바뀌었나

레코드당 하던 일 중 **바이트를 옮길 필요가 없는 것 둘**을 걷어냈다.

### 2.1 상수 슬롯 — 매번 다시 깔지 않는다

상수 슬롯 96 B($5BE0-$5C3F)를 레코드마다 다시 복사하고 있었다. 그런데 이 구간을
쓰는 것은 그 전송 자신뿐이다(텍스트는 $5BDF 에서 끝나고 글리프는 $5C40 에서
시작한다). 이제 센티널 2 바이트를 먼저 본다.

```
정상일 때   약 14 사이클
깨졌을 때   593 사이클로 복사하고 그 레코드 안에서 복구
```

무조건 건너뛰면 안 된다. 08-14 에 검사 없이 한 번만 복사하는 판을 만들었더니
한참 뒤 글자가 깨졌다 — **이 헬퍼 밖의 무언가가 그 구간에 닿는다.**

### 2.2 낡은 글리프 슬롯 — 다시 채울 칸은 지우지 않는다

지우기는 "직전 레코드가 쓴 칸 전부"였고, 그 직후 글리프 루프가 대부분을 다시
채웠다. 6 글자 다음 6 글자면 6 칸을 지웠다가 같은 6 칸을 덮어썼다 — 1,152 사이클,
2.5 스캔라인이 헛일이었다.

이제 글리프 루프가 **이번 레코드가 안 쓰고 직전 레코드는 썼던 칸만** 칸 단위로
지운다. 상태는 스크래치 1 바이트(직전 글자 수 × 2)면 된다. 루프가 슬롯 17 에서
내려오고 글리프 배치가 조밀(빌더가 구멍을 거부)하므로, 처음 채운 칸이 곧 최대
칸이고 그 값 하나로 범위가 정확히 정해진다.

### 2.3 선적재 기본값 = `resident`

0.3.4 는 25 팩 전부(52 청크)를 올려 부팅이 13.75 초였다. 멈춤을 유발한 것은 122 KB
`ui` 팩이 수요적재로 오는 경우였고, 장면 팩은 평균 5.8 KB 라 처음 필요할 때 가져와도
싸다. 이제 상주 4 팩(35 청크)만 올린다.

## 3. 측정 (같은 경로, 두 판)

`lua\PROBE 0.3.5.lua` — 디스크 이름에서 빌드를 자동 판별하므로 주소를 손으로
맞출 일이 없다(08-15 에 그것을 틀려 1,538 프레임을 날린 기록이 있다).

```
0.3.4   진입 188 · copy 178 · AC 포트 읽기 101,936   레코드당 573 회
0.3.5   진입 138 · copy 129 · AC 포트 읽기  45,989   레코드당 357 회   -38%

전송 시간   7.6 -> 4.7 스캔라인  (+ 고정 오버헤드 약 0.9)
부팅        52 -> 35 청크
```

AC 포트 읽기 하나가 Mesen Event Viewer 의 초록 점 하나다. **세 축이 독립적으로
일치했다** — 포트 읽기 수, 초록 띠 폭, 그리고 눈으로 본 밀림 빈도.

미측정으로 남은 것: **헬퍼 진입~반환의 실제 사이클**(PROBE 0.3.5 census). 두 번
모두 Stop 전에 넘어갔다. 08-15 §4 가 남긴 항목이 그대로 남아 있다.

---

## 4. 안 고쳐진 것

**여전히 밀린다.** 점유는 이미 갱신 간격(10~12 줄)의 절반인데도 그렇다. 남은 것은
길이가 아니라 **위치** — 하필 갱신 지점을 걸치느냐다. 그 위치는 게임이 우리를
언제 부르느냐로 정해지므로 우리가 못 고른다.

옮길 것도 거의 다 걷어냈다. 남은 357 회의 대부분이 글리프 데이터이고, 한 글자는
32 바이트이며 한 번은 와야 한다.

```
글리프   n x 32 B   192~480 회   줄일 수 없음
텍스트   96 회      레코드마다 다른 실제 내용
인덱스   30 회
조회     약 8 회
```

다음에 다시 판다면 §6 순서를 볼 것.

## 5. 롤백

되돌리기는 revert 가 아니라 선택지다. 모든 단계를 0.3.4/0.3.3 과 공유한다.

```bash
python extraction/patch/static/build_snatcher_ko_0_3_4.py
```

```bash
python extraction/patch/static/build_snatcher_ko_0_3_3.py
```

`build\patch\0.3.4\` 와 `0.3.3\` 은 PROTECTED 라 페이로드가 그대로 있다. **다시
빌드하지 않고 그 디스크를 바로 실행해도 된다.**

수정을 하나씩만 끄는 것도 된다. 셋 다 0.3.5 진입점의 기본값이다.

```bash
SNATCHER_BLANK_SLOTS=0 python extraction/patch/static/build_snatcher_ko_0_3_5.py
```
**진단용으로만.** 끄면 지우기가 없어져 잔상이 난다 — 0.3.4 릴리스 노트 §4 참조.

```bash
SNATCHER_PRELOAD_PACKS=all  python .../build_snatcher_ko_0_3_5.py   # 52 청크
SNATCHER_PRELOAD_PACKS=none python .../build_snatcher_ko_0_3_5.py   # 13 청크
SNATCHER_TAI_CHUNK=608      python .../build_snatcher_ko_0_3_5.py
```

비기본값은 빌드 로그 첫 줄과 `manifest.json` 에 남는다. **디스크만 보고도 어떤
설정인지 알 수 있다.**

## 6. 확인은 됐지만 넣지 않은 것 — `SNATCHER_AC_FAST=1`

글리프마다 AC 포트의 제어 레지스터 3 개($1A07/$1A08/$1A09)를 다시 쓰고 있다. 값은
매번 같고 기저만 바뀐다. 그래서 글리프 루프만 기저 3 바이트만 쓰는 짧은 진입점
(`set_ac_base`)을 타게 하는 실험판을 만들었다.

```
결과        한글 정상 출력 -> 제어 재기록은 불필요했다.  기술적으로 가능
이득        글리프당 약 33 사이클.  12 글자면 0.87 스캔라인
비용        헬퍼 +4 B (여유 17 -> 13)
```

**그래도 0.3.5 에는 넣지 않았다.** 검증 범위가 좁다.

```
전제   "포트 모드가 직전 set_ac 이후로 안 바뀌었다"
그런데 load_blob 은 BIOS CD_READ 를 MPR4 목적지 모드로 부른다.
       BIOS 가 포트를 건드리면 팩 적재 직후 첫 레코드만 깨진다.
       preload=resident 라 장면 팩은 재생 중에도 적재된다.
```

대사 한 줄로는 그 조합이 안 나온다. 08-14 에 `both` 가 정확히 이런 식으로 짧은
시험을 통과했다가 나중에 잡혔다. **채택하려면 "팩 적재 직후 첫 한글 출력"을
의도적으로 만들어 보는 시험이 먼저다.**

지금은 "필요해지면 0.9 스캔라인을 회수할 수 있다"는 것을 아는 것으로 충분하다.
헬퍼 여유가 17 B 뿐이라, 앞으로 무엇을 넣을 수 있는지 판단할 때 이 값이 쓰인다.
