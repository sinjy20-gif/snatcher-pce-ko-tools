# SNATCHER KO 0.3.4 — 릴리스 노트 및 롤백 절차 (2026-08-14)

```
디스크    build\patch\0.3.4\Snatcher CD-ROMantic (Japan) [KO 0.3.4].cue
진입점    extraction\patch\static\build_snatcher_ko_0_3_4.py
근거      docs\handoff\SNATCHER_UI_FLICKER_HANDOFF_2026-08-14.md
```

0.3.3 대비 **번역 데이터가 아니라 런타임 코드**가 바뀐 릴리스다. 폐공장에서 한글
출력이 시작될 때 상단 그림의 아래 경계가 한 프레임 밀리던 현상을 다뤘다.

---

## 1. 무엇이 바뀌었나

원인 세 가지를 각각 측정해서 각각 고쳤다. 하나의 수정이 아니다.

| | 0.3.3 | 0.3.4 |
|---|---|---|
| 인터럽트 차단 (출력마다) | 3,665 사이클 = **8.05 스캔라인** | 473 = **1.04 스캔라인** |
| 레코드 재구성 | 5,631 사이클 | **3,829** |
| 재생 중 CD 접근 | 팩마다 1회 + 탐색 2회 | **없음** |
| 미번역 줄 | 최대 **약 4초 멈춤** | 없음 |
| 초기 적재 | 13 청크 (104 KB) | 52 청크 + 3 섹터 (422 KB) |

### 1-1. `TAI` 분할

608 B 템플릿을 블록전송 **한 명령**으로 옮기고 있었다. HuC6280 블록전송은 원자적이라
실행 내내 인터럽트를 받지 않는다. 76 B × 8 로 쪼갰다. AC 포트 `$1A00`/`$1A01` 은 같은
데이터 레지스터의 두 미러라 어디서 잘라도 바이트 순서가 같다 — 무해한 분할이다.

### 1-2. 팩 선적재

`resident` 는 "미리 적재"가 아니었다. 초기화는 디렉터리·아틀라스만 올리고 **모든 팩
플래그를 `$FF`(미적재)로** 지웠고, `ui` 팩조차 첫 접근 때 CD 에서 왔다. 게다가 빗나간
프로브가 남의 팩을 통째로 끌어올 수 있어, 미번역 줄 하나가 팩을 5~6개까지 불렀다.

폐공장에서 **게임 자신이 13~14 프레임 주기로 CD 를 읽는다.** 우리 적재가 그 사이에
끼면 게임의 다음 읽기가 22~30 프레임으로 밀렸다(관측 5건 중 5건). 이제 25개 팩을
초기화 때 한 번에 올린다.

### 1-3. 경계 지우기

템플릿 608 B 는 상수 슬롯 복원과 글리프 슬롯 비우기를 겸하고 있었고, 그 비용이
레코드당 4,377 사이클 중 3,784(86%)였다. 이제 `96 + (직전 레코드 글리프 수) × 32`
바이트만 옮겨 두 일을 정확히 한다.

### 1-4. 빌더 — 런타임 조각 장면 상속

두 줄짜리 런타임 캡처의 둘째 줄(`{EMPTY}`)이 검토 표시되면 빌드가 중단됐다. 카탈로그에
캡처가 한 항목으로만 있어 `KEY:2` 가 매칭되지 않았기 때문이다. 같은 캡처의 두 줄이
다른 장면일 수 없으므로 형제 줄에서 물려받게 했다
(`build_ac_dynamic_0_1_11.py`, method `sibling-line-of-same-capture`).
이번 빌드에서 3건 적용됐다. 실제 배정과 수동 복구가 항상 우선한다.

## 2. 아직 안 고쳐진 것

깜빡임이 **산발적으로 남아 있고, 음성 재생이 방아쇠다.**

```
음성 전   10회 중 약 3
음성 후   10회 중 약 9    그리고 되돌아오지 않는다
```

게임이 음성 재생 이후 프레임 예산을 잃는 것으로 보인다(ADPCM 서비스 지속). 패치가
게임 동작을 바꿀 수는 없고 우리 비용을 줄이는 것만 가능한데, **안전하게 줄일 여지는
이번에 대부분 썼다.**

**이것은 버그가 아니라 예산 문제다.** 화면 손상·세이브 손상·진행 불가 없음. 폐공장처럼
번개와 스프라이트가 많아 게임 쪽 여유가 적은 장면에서만 드러난다.

다음 시도는 `SNATCHER_UI_FLICKER_HANDOFF_2026-08-14.md` §4.6 의 전역 글리프 슬롯.

## 3. 롤백

**되돌리기는 되돌림(revert)이 아니라 선택지다.** 모든 단계를 0.3.3 과 공유한다.

### 3-1. 통째로 0.3.3 으로

```bash
python extraction/patch/static/build_snatcher_ko_0_3_3.py
```

`build\patch\0.3.3\` 은 PROTECTED 라 페이로드가 그대로 있다. **다시 빌드할 필요 없이
그 디스크를 바로 실행해도 된다.**

### 3-2. 수정 하나씩만 끄기

문제가 어느 수정에서 왔는지 가릴 때 쓴다. 셋 다 0.3.4 진입점의 기본값이다.

```bash
SNATCHER_PRELOAD_PACKS=0 python extraction/patch/static/build_snatcher_ko_0_3_4.py
```
초기 로딩이 길다 / 부팅이 이상하다 → 선적재를 끈다. 미번역 줄의 멈춤이 돌아온다.

```bash
SNATCHER_TAI_CHUNK=608 python extraction/patch/static/build_snatcher_ko_0_3_4.py
```
글자가 깨진다 → 분할을 되돌린다. (분할은 바이트 무해가 논증돼 있어 가능성은 낮다.)

```bash
SNATCHER_BLANK_SLOTS=0 python extraction/patch/static/build_snatcher_ko_0_3_4.py
```
**끄지 말 것.** 아래 §4 참조. 진단용으로만.

비기본값으로 돌리면 빌드 로그 첫 줄에 그 사실이 찍히고, `manifest.json` 의
`compact_records` 에도 `preload_packs` / `template_chunk_bytes` 로 남는다. **디스크만
보고도 어떤 설정으로 나왔는지 알 수 있다.**

## 4. 다시 시도하지 말 것 — 빈칸 처리 제거

2026-08-14 에 만든 `noblank` · `both` · `lean` · `lean2` 는 글리프 슬롯 지우기를 없애
레코드당 2,044~2,637 사이클까지 내려갔다. **잔상이 난다.** 실측으로 확인됐다 —
폐공장에서 "…공장? 내부로 들어왔습니다" 의 첫 글자가 이전 줄 글자로 남았다.

기전:

```python
while used and used[-1] == blank: used.pop()   # 끝쪽 빈 글리프를 버린다
```

원본 레코드가 **끝쪽 슬롯을 빈 글리프로 참조**하는 경우가 있다. 그 슬롯은 압축
레코드에 `FFFF` 로 남아 글리프 루프가 건너뛴다. 템플릿 복사가 있을 때는 0 이라 빈칸으로
정확히 그려졌지만, 지우지 않으면 직전 레코드의 글자가 남는다.

`lean2` 의 상수 센티널 자가 복구는 **상수 슬롯만** 보므로 이 잔상을 못 잡는다.

**빈도가 낮아 짧은 시험은 통과한다.** `both` 로 "잔상 없음" 판정이 한 번 났다가 뒤에
`lean` 에서 잡혔다. 짧게 보고 무해하다고 결론내지 말 것.
