# §8-B 저장 후 재로드 화면 깨짐 — 조사 인계서 (2026-08-14 오전)

통합 인계서 §4 의 후속이다. **§4 의 결론 하나를 반증했고, 다음에 할 실험을 특정했다.**
§4 를 먼저 읽고 이 문서를 읽을 것.

```
현재 버전   0.3.3
진입점      extraction\patch\static\build_snatcher_ko_0_3_3.py
디스크      build\patch\0.3.3\Snatcher CD-ROMantic (Japan) [KO 0.3.3].cue
```

---

## 1. 증상 (변동 없음)

```
게임 중 저장 → 타이틀 복귀 → 같은 세션에서 재로드 → 그래픽/문자 타일 깨짐
재실행 후 로드는 정상.  세이브 파일 손상 없음.  게임 진행은 가능
```

---

## 2. §4 의 논리에 빈틈이 있다 — 이것이 이번의 핵심

§4 는 이렇게 결론지었다.

> AC 헬퍼를 케이브에 두지 않는 0.2.26 에서도 같은 깨짐이 난다
> → 따라서 장소 문제가 아니다. 헬퍼를 옮겨도 안 고쳐진다

**앞 절반은 맞고 뒤 절반은 증명되지 않았다.**

0.2.26 이 케이브를 안 쓴다는 사실은 **케이브가 유일 원인이 아님**만 보인다. 그런데
0.2.26 도 `$66E5` · `$5E40` · `$7F50` 훅은 **똑같이 쓴다.** 즉 모든 빌드가 공유하는
그 훅들은 후보에서 배제된 적이 없다.

사용자의 관찰이 이 빈틈을 정확히 찔렀다.

> 딱 저 지점에서 난 걸 보니 타이틀 나가서 복귀할 때의 복귀 지점을 우리가 건드렸나
> 싶은데, **그냥 로드는 문제가 없다**

**정상 로드와 소프트 복귀가 서로 다른 경로를 지나는지**가 아직 확인되지 않았다.

## 3. 실측으로 확인된 것

### 3.1 두 곳에서 각각 관측됐다 (같은 현상, 다른 장소)

`dump\saveload_v4_214553.tsv` — 뱅크 $69 케이브

```
f1613~f4119   inHelper=true    우리 헬퍼가 자기 코드를 실행 (정상)
f5771  342 reads  $BCD2-$BE27  inHelper=false   ← 외부가 읽음
f5772  472 reads  $BE28-$BFFF  inHelper=false
               342+472 = 814 = 케이브 크기와 정확히 일치
```

**블록 전송이다.** 특정 바이트 탐색이 아니라 처음부터 끝까지 순차로 훑는다.

`dump\SAVE_0.1.3_234053.tsv` — 프리로더 계열. 외부 caller 만 집계하면

```
preloader           $5E40-$5FF1   8,984 reads   caller $70BF(8,673) · $7064(311)
record_tail_helper  $5E20-$5E3F   2,618 reads   caller $70BF
font_loader_state   $7F50-$7FFD   2,168 reads   caller $5E86(2,122) · $7FEB(46)

자기 실행만 있는 구간 (정상)
fractional($64B6-$64E3) · renderer_hook($66E5) · space_hook($674A)
```

`font_loader_state` 의 caller `$5E86` 은 프리로더 내부이므로, **우리 코드가 우리 상태를
읽는 정상 동작일 가능성이 높다.** 외부 침입으로 단정하지 말 것.

### 3.2 읽는 쪽은 범용 복사 루프다

```asm
B1 12    LDA ($12),Y      ← $12 가 가리키는 곳을 그냥 읽는다
JSR $71B0
INY / CPY $01 / BNE
```

우리 코드를 노리는 전용 루틴이 아니라, 게임이 포인터를 그쪽으로 맞춰 두고 도는
**일반 전송**이다. 그래서 "우리 구간일 때만 FF 로 보이게" 하려면 **이 전송이 그
전송인지 판별**해야 하는데, 범용 루프라 판별 근거가 없다.

**"마스킹이 가장 외과적"이라는 §4 의 평가는 이 점에서 낙관적이다.**

### 3.3 크래시 가능성

지금까지 관측된 것은 **읽기와 VDC 쓰기뿐**이다. 코드가 파괴되는 게 아니라 읽혀서
화면에 그려진다. §4 가 훅·캐시의 byte-exact 무결성을 확인했고(`CHANGE 0건`),
AC 의 magic/flags/atlas 도 소프트 복귀 후 불변이다.

**크래시로 번지는 경로는 관측된 바 없다.** 다만 "관측 안 됐다"이지 "없다"는 아니다.

## 4. 비대칭이 설명되지 않는다 — 가장 유력한 가설

§4 의 기전만으로는 **왜 재시작하면 낫는지**가 설명되지 않는다. 이것이 이번 조사에서
가장 값어치 있는 지적이다.

```
§4 기전:  "재로드 경로가 우리 코드를 그래픽 소스로 읽는다"

그렇다면 파워사이클 후 로드에서도 똑같이 읽어야 한다. 재로드 경로는 같으니까.
그런데 그때는 멀쩡하다.
```

즉 **읽는 행위 자체가 소프트 복귀에서만 일어나거나, 읽는 대상 주소가 달라진다.**
어느 쪽이든 결론은 하나다 — **소프트 복귀에서 초기화되지 않는 값이 있다.**

### 후보는 이미 로그 안에 있다

§3.2 의 루프를 다시 보라.

```asm
B1 12    LDA ($12),Y      ← 제로페이지 $12/$13 이 소스 주소를 가리킨다
```

**전송원 포인터가 제로페이지 `$12/$13` 이다.** 부팅 때는 제대로 세팅되는데 소프트
복귀에서 갱신이 빠지면, 낡은 값이 남아 **엉뚱한 곳** — 원래 `FF` 였고 지금은 우리
코드가 있는 자리 — 을 소스로 읽는다.

이 가설은 관측된 것을 전부 설명한다.

| 관측 | 설명 |
|---|---|
| 재시작하면 정상 | 포인터가 새로 세팅됨 |
| 우리 코드가 타일로 그려짐 | 낡은 포인터가 그 자리를 가리킴 |
| 0.2.26 · ac_0.1.14 · 0.3.2 전부 발생 | 모두 예전 `FF` 자리에 코드를 넣음 |
| 순정은 멀쩡 | 같은 자리를 읽어도 `FF` 라 무해 |
| AC magic/flags/atlas 불변 | 상태 오염이 아니라 **읽기 대상만** 빗나감 |

### 상태 오염 우려에 대한 답

§4 가 이미 확인한 것들이 이 가설과 맞물린다.

```
AC magic/flags/atlas   소프트 복귀 후에도 불변
훅 / 캐시              byte-exact, CHANGE 0건
CD 섹터 시퀀스          순정 실행과 바이트 단위 동일
```

**상태가 오염된 흔적이 아니라, 읽기 대상 하나가 빗나간 흔적이다.** 포인터 하나가
낡은 것이면 국소적이며, 아틀라스 슬롯·AC 플래그·뱅크 매핑·캐시 포인터로 번질 이유가
없다. 다만 이는 **가설이 맞을 때의 이야기**이고, 4.1 로 먼저 확인해야 한다.

### 4.1 제로페이지 포인터를 본다 — 이것을 먼저 할 것

패치 디스크 하나로 끝나고, 순정 비교보다 직접적이다.

```
감시 대상   제로페이지 $2012 / $2013
            (MPR1=$F8 이라 제로페이지는 CPU $2000 부터다. $00F8 이 아니라 $20F8
             이었던 것과 같은 이유 — 통합 인계서 §12-2 계열의 함정)

경로 A  부팅 → 세이브 로드              전송 직전 $12/$13 값
경로 B  플레이 → 저장 → 타이틀 → 재로드   전송 직전 $12/$13 값
```

판정

```
두 값이 다르다   → 원인 확정. 초기화 누락 한 곳.  국소적임이 증명된다
                  → 그 값을 복귀 경로에서 다시 세팅하면 끝날 가능성이 크다
같다             → 포인터는 무죄. 4.2 순정 비교로 넘어간다
```

**"원인이 국소적이라는 것까지만 증명하고, 고치는 비용이 크면 보류"** 라는 방침에
정확히 맞는 실험이다. 화면 깨짐이 더 큰 오염의 첫 증상인지 아닌지가 여기서 갈린다.

---

### 4.2 순정 디스크로 같은 프로브를 돌린다 (4.1 이 "같다"로 나올 때)

`lua\PROBE_SAVELOAD_STATE_v4.lua` 는 `$BCD2-$BFFF` 읽기를 감시할 뿐이라
**원본에서도 그대로 돈다**(트램폴린 훅 두 개는 안 걸릴 뿐 무해).

원본 디스크로 다음 두 경로를 각각 돌려 비교한다.

```
경로 A  부팅 → 세이브 슬롯 로드           (정상 로드)
경로 B  부팅 → 플레이 → 저장 → 타이틀 → 재로드  (소프트 복귀)
```

#### 4.2 판정

```
A·B 모두 $BCD2-$BFFF 읽음
   → 원본도 그 자리를 읽고, FF 라서 무해했던 것
   → 원인은 "우리가 그 자리를 썼다"  →  마스킹 또는 재적재로 감
   → 이때 비로소 §4 의 마스킹 안이 성립한다

B 에서만 읽음
   → 소프트 복귀만 그 경로를 지난다
   → 원본에도 있는 성질이므로 우리 훅과 무관.  재적재 쪽으로 감

A·B 모두 안 읽음
   → 우리 훅이 그 경로를 만든 것  ←  사용자 가설이 맞음
   → $66E5 / $5E40 / $7F50 을 하나씩 끄고 이분탐색
```

**세 갈래 중 어느 쪽이냐에 따라 수정안이 완전히 달라진다.** 이 실험 없이 수정안을
고르면 §5 처럼 없는 땅을 파게 된다.

### 4.3 보조 실험

`$70BF` 가 우리 구간만 읽는지, 넓은 영역을 훑다가 지나가는지 확인한다. 훑는
것이라면 조건 판정이 필요하고, 그것이 **헬퍼 여유 118 B** 안에 들어가는지가 관건이다.

```
0.3.2 에서 헬퍼가 709 → 664 B 로 줄어 여유가 73 → 118 B 로 늘었다
```

## 5. 수정안 재평가

| 안 | §4 평가 | 이번 조사 후 |
|---|---|---|
| 소스에서 패치 구간 마스킹 | 가장 외과적 | **범용 루프라 판별 근거 없음.** 4.2 가 "A·B 모두 읽음"으로 나와야 성립 |
| 그래픽만 정상 재적재 | — | **가장 현실적.** 원인 제거가 아니라 덮어쓰인 VRAM 되돌리기. 범용 루프를 안 건드림 |
| 코드를 cold region 이동 | §5 가 닫음 | 동일. FF 구간 셋이 전부 우리 것 |
| 특수 경로에서 전체 재초기화 | 둔하지만 확실 | 동일 |
| 현행 유지 | 진행 불가는 아님 | 동일. **배포 전까지는 유효한 선택** |

재적재를 고를 경우 추가로 확인할 것 두 가지.

```
재로드 완료 시점을 잡을 훅이 있는가
되돌릴 원본 타일 데이터를 어디서 가져올 것인가
```

## 6. 우선순위에 대한 의견

**급하지 않다.** 게임 진행이 막히지 않고, 파워사이클 후에는 정상이다. 다만 저장 후
재개는 플레이어가 가장 흔히 하는 행동이라 **배포하면 거의 모두가 만난다.**

번역 작업을 진행하면서 **4.1 실험만 먼저** 해두는 것을 권한다. 패치 디스크 하나로
30분이면 "국소적인가"가 갈리고, 그때 수정안을 고르면 헛수고가 없다.
