# 갈무리 글꼴을 BIOS 경로에 얹기 — 인계서

기준일: 2026-08-18
직전 문서: `SNATCHER_BIOS_FONT_2026-08-18.md` (0.3.11-bios-opt)
상태: 설계 확정 · 글리프 팩 완성 · 런타임 래퍼 미착수

---

## 0. 한 줄 요약

0.3.11-bios-opt 의 구조(96B 레코드 · 아틀라스 0 · 밀림 해결 · 593 cycle)를 **그대로 두고**,
글리프의 출처만 시스템 카드에서 우리 갈무리 폰트로 바꾼다.
시스템 카드는 패치하지 않는다. 해태 한글 카드는 **선택 사항**이 된다.

---

## 1. 왜 이 방향인가

0.3.11-bios 전환으로 15자 제한·밀림·코드 공간이 한꺼번에 풀렸지만, 대신 글자 모양이
해태 카드의 굵은 기울임체가 되었다. 원래 쓰던 갈무리로 돌아오고 싶다는 것이 이번 요구다.

두 가지 방법을 검토했다.

| | A. AC 상주 폰트 후킹 | B. 시스템 카드 IPS |
|---|---|---|
| 방식 | 갈무리 2,350자를 AC 에 상주, 폰트 래퍼가 공급 | Syscard3k 의 한글 글리프 테이블을 갈무리로 덮어씀 |
| 런타임 비용 | `$69C2` 캐시 미스 때 32B 복사 | 0 |
| 헬퍼 코드 | 50~70B 예상 (151B 여유 안) | 0B |
| AC | +106,496B | 없음 |
| 이용자 부담 | 없음 | 각자 BIOS 에 IPS 적용 |
| 일본 시스템 카드 | **동작함** | 안 됨 |

**A 로 확정** (소유자 승인, 2026-08-18). 해태 카드 의존이 끊기는 것이 결정적이다.

> 해태 카드를 못 쓰게 되는 것이 아니라 **필수가 아니게 되는 것**이다.
> 그 카드로 돌리면 한글 부팅 로고는 그대로 나오고, 글리프만 갈무리로 나간다.

### B 를 버린 이유가 아닌 것

B 도 기술적으로는 성립한다. `PECSYSTEMK\Syscard3k.pce` 를 직접 디코드해서 확인했다.

- 한글 글리프가 **16x16 1bpp, 32B, 행마다 2바이트 MSB-first** 로 들어 있다.
- 우리 `glyph_1bpp_left_shifted` 산출물과 **바이트 형식이 완전히 같다**.
- 굵은 기울임체이며 0x14000 대역에서 육안 확인된다.

즉 나중에 IPS 판이 필요해지면 글리프 생성은 이미 끝나 있다. 다만 **테이블 기점(base)은
아직 확정하지 않았다** — 상관 스윕으로 0x137A0 부근까지 좁혔으나 KS 순서 가정이
안 맞는 듯 렌더가 어긋난다. B 를 되살릴 때 여기부터 다시 봐야 한다.

## 2. 설계

### 2.1 바꾸지 않는 것

인코더·레코드·렌더러를 **한 줄도 안 고친다**.

```
snatcher_ko_master.tsv
   -> game_text_codec._bios_hangul_bytes()   ← 그대로
   -> 96B compact record                     ← 그대로
   -> CD -> AC                               ← 그대로
   -> 렌더러 -> $648C -> 폰트 래퍼            ← 여기만 바뀜
```

### 2.2 되는 이유 — 코드가 곧 주소다

`_bios_hangul_bytes` 가 내보내는 SJIS 코드는 EUC-KR 완성형과 1:1 이다.
한글 lead 는 **0x88 .. 0x94, 13 개뿐이고 전부 0xA0 미만**이라 SJIS 의 0xE0 대역
접기를 런타임에서 처리할 일이 없다.

**AC 배치는 KS 조밀 배열이 아니라 SJIS 바이트를 그대로 키로 쓰는 성긴 배열이다.**

```
L      = lead - 0x88                       0 .. 12
offset = (L << 13) | (trail << 5)

  lo  = (trail << 5) & 0xFF
  mid = (trail >> 3) | ((L << 5) & 0xFF)
  hi  = L >> 3
```

`trail >> 3` 은 최대 0x1F 이고 `(L << 5)` 는 하위 5 비트가 0 이라 겹치지 않는다.
**곱셈도 표도 없다.  순수 시프트/OR 20 바이트 남짓.**

대가는 AC 공간뿐이다.

```
성긴 배열   13 x 8,192 = 106,496 B
조밀 KS     2,350 x 32 =  75,200 B   (+31 KB 차이)
```

2 MB 중에서 쓰는 것이므로 POC 단계에서 따질 값이 아니다.
**공간을 코드가 아니라 AC 로 내는 쪽이 지금 프로젝트 상황에 맞다** (소유자 판단,
2026-08-18): BIOS 전환으로 겨우 5 B 지옥에서 151 B 를 되찾았는데 폰트 하나
넣겠다고 다시 11 B 까지 태우면 같은 싸움을 반복하게 된다.

> 조밀 KS 배열은 `index = (ku-16)*94 + (ten-1)` 이 필요해서 25 항 50 B 표나
> `*94 = *64 + *32 - *2` 시프트 누산을 쓰게 된다.  **둘 다 채택하지 않았다.**
> 나중에 AC 를 줄여야 할 때 다시 꺼낼 선택지로만 남긴다.

`build_ks_hangul_pack.py` 는 조밀 KS 순서로 낸다.  성긴 배열은 그 팩을
`(lead, trail)` 자리로 다시 뿌리기만 하면 되므로 팩 자체는 그대로 쓴다.

### 2.3 폰트 래퍼

자리: `extraction\patch\static\build_full_overlay_patch.py:159` `build_font_wrapper()`
설치: `build_direct_overlay_patch_ui.py:482`, `FONT_WRAPPER = $7F50`

현재 동작:

```
$F9 (lead) == F0 ?  --- 아니오 ---> JMP $69C2  ->  캐시 미스  ->  BIOS $E060
       | 예
       +-> WRAM 폰트팩 32B -> $00/$01 -> JSR $69FC -> CLA/RTS
```

바꿀 동작: lead 가 0x88~0x94 면 BIOS 로 안 보내고 우리가 AC 에서 32B 를 가져온다.

**중요: 일이 늘어나는 게 아니다.** 지금도 캐시 미스마다 BIOS 가 32B 를 긁어온다.
같은 지점에서 출처만 바뀌므로 593 cycle 레코드 비용과 밀림 해결은 그대로 유지된다.

### 2.4 자리 예산 (실측)

```
폰트 래퍼   54 B 사용 / 56 B 한도    ($7F50 - $7F88 = SECTOR_LOADER)
헬퍼        631 B 사용 / 782 B 한도  -> 151 B 여유
```

헬퍼 범위는 `$BCD2 - $C000` = 814 B 이지만 `build_helper_compact` 가 맨 위
`scratch = HELPER_LIMIT - 0x20` 로 32 B 를 떼어 쓴다.  따라서 실제 코드 한도는
782 B 이고 여유는 **151 B** 다 (0.3.11-bios-opt 빌드 출력과 일치).

**래퍼 자리에는 2 B 밖에 안 남았다.** lead 범위 분기와 AC 페치 본체는 헬퍼 여유
쪽에 두고 래퍼에서는 `JMP` 만 건다.

### 2.5 비용

```
AC 팩   237,568 -> 344,064 B   (+106,496)
```

opt 이전(299,008 B)보다 45 KB 많다. CPU·밀림 이득은 그대로다.
**POC 가 통과한 뒤에** 줄일지 정한다 -- 조밀 KS 로 -31 KB, 실사용 1,115자만
실으면 -70 KB.

로딩시간이 문제가 되면 **실제로 쓰는 글자만** 싣는 압축 배치가 가능하다
(0.3.11 아틀라스 실측 1,115자 = 35,680 B). 다만 코드->색인이 산술에서 표 조회로
바뀌므로, **단순한 판으로 동작을 먼저 확인하고 그 다음에 줄인다.**

## 4. 남은 작업

### 4.0 지금은 POC 다 ★

**최적화판을 만들 때가 아니다** (소유자 명시, 2026-08-18).  우선 목표는 이것 하나다.

```
일본 System Card -> 한글 코드 가로챔 -> AC 의 갈무리 글리프 하나 -> 정상 출력
                 -> AC 상태 복원
```

여기까지 성공한 **다음에** 결정한다.

- 2,350자 성긴 배열을 유지할지, 조밀 산술로 줄일지
- 실제로 쓰는 1,115자만 실을지
- 코드를 다른 케이브로 옮길지

글자 한 자가 제대로 나오는 것이 먼저다.  전체 배치를 완성해놓고 안 나오면
어디가 틀렸는지 알 수 없다.

### 4.1 AC 페치 루틴

헬퍼 여유(151 B)에 넣는다.  §2.2 배치를 쓰면 표가 없다.

```
lead 0x88..0x94 인가?           아니면 JMP $69C2
L = lead - 0x88
lo/mid/hi 를 시프트로 조립       ~20 B
AC 포트 저장 -> 세팅 -> 32B -> 포트 복원
$00/$01 = 스크래치 -> CLX -> JSR $69FC -> CLA -> RTS
```

거칠게 잡아 50~70 B.  **80 B 안팎이 남는다.**  151 B 를 11 B 로 태우지 않는다.

새 WRAM 표를 만들지 않는다 — 표를 만들면 초기화·상태·충돌이 따라온다.

### 4.2 미확인 — AC 포트 상태 공유 ★

**이번 작업의 유일한 진짜 위험이다.**

래퍼는 `$69C2` 훅 시점, 즉 **렌더링 도중**에 돈다.  거기서 AC 포트
`$1A07/$1A08/$1A09` 를 건드려야 하는데, 그 값은 `copy_record` 가 세워둔 상태를
공유한다 (`build_snatcher_ko_0_3_11_bios.py` 0.3.8.7 항 참조 — 그 항은 재기록이
**불필요**하다는 근거로 쓰였고, 우리는 그 전제를 깨는 쪽이다).

따라서:

- 페치 전후로 포트 3바이트를 **반드시 저장/복원**한다.
- 그것으로 충분한지는 에뮬에서 확인해야 한다.  특히 `copy_record` 진행 중에
  래퍼가 끼어들 수 있는지를 본다.
- 래퍼 실행 시점의 MPR 배치에서 `$1A00` 접근이 유효한지도 같이 본다.
  (헬퍼는 `TIA $1A00` 을 이미 쓰고 있으므로 경로 자체는 증명되어 있다.)

Lua 프로브를 붙여 미스 때 실제로 우리 글리프가 나가는지 기록하는 것이 가장 확실하다.
`lua\` 에만 만든다.

### 4.3 시험 빌드

```
python build_snatcher_ko_0_3_11_bios.py --tag galmuri
```

`--tag` 는 폴더명 suffix 중복 버그가 있다 (`-opt-opt-unpatched`).  무해하다.

### 4.4 탈출구 — B 가 있다

**A 를 억지로 성공시킬 이유가 없다** (소유자 명시).  대공사 냄새가 나면
"됐어, 갈무리 BIOS IPS 쓰자" 로 빠지면 된다.  §1 에 적었듯 글리프 형식은 이미
같은 것이 확인됐고, 그때 필요한 것은 `Syscard3k.pce` 의 테이블 기점 확정뿐이다.

판단 기준: **§4.2 의 포트 공유가 저장/복원으로 안 닫히면 B 로 간다.**

## 5. 우선순위

이 작업과 **독립적으로** §15 1순위인 UI lookup 문제가 아직 열려 있다.
`ui:UI0002 조사하다` / `slot 1C68` / `reception-action-v1` 이 조사 대상이고,
UI 데이터는 두 BIOS 빌드에서 byte-identical 임이 확인되어 있다.

소유자 판단 대기: **갈무리 래퍼 먼저** 인지 **UI 복구 먼저** 인지.

## 6. 건드리지 말 것

`SNATCHER_BIOS_FONT_2026-08-18.md` §16 이 그대로 유효하다. 추가로:

- **시스템 카드를 패치하지 않는다.** A 안의 요지가 그것이다.

## 부록 — 2026-08-18 저녁 세션 (환경 A)

### A 안 -> B 안 (소유자 판단)

```
A  갈무리를 AC 상주 + 폰트 래퍼   헬퍼 50~70B · AC +106KB · 런타임 경로 추가
B  BIOS 에 직접 써넣고 xdelta      코드 0B · AC 0B · 런타임 표면 0
```

근거: 여유가 151B 뿐인데 **자막이 남아 있고 버그 수정에도 공간이 든다.**  0 원짜리
대안이 있는 문제에 활주로를 태울 이유가 없다.  BIOS 는 xdelta 로 뿌리면 되고
안드로이드에서도 파일 하나 지정이라 부담이 없다.  A 로 돌아갈 길은 열려 있다.

### 실측 확정

```
행 오프셋 표   ROM $0127E · 16비트 LE · 유효 0x21~0x47 (39행) · 전체 3,461 글리프
               **일본 카드와 한글 카드가 완전히 동일**
인덱스 공식    index = 행표[row-0x21] + (cell-0x21)     ROM $F264 로 확인
12x12 base     $030000 · stride 18                      PROBE_FONT_ADDR 두 표본 일치
               idx1665 뱅크$1B src$B512 -> $37512 - 1665x18 = $030000
               idx2855 뱅크$1E src$A8BE -> $3C8BE - 2855x18 = $030000
               '가'·'한'·'글' 렌더 육안 확인
```

### 12x12 는 해태 카드의 제약이었다

프로브 표본 24건이 전부 12x12($F2CC, 18B).  한글만이 아니라 기호·가나·영문·한자까지
전부.  인계서 §2 의 갈래에서 **"원본 한자도 $F2CC"** 로 확정 -- 우리 빌드 버그가 아니다.

그런데 소유자 실측: **일본 원본 BIOS 는 16x16 으로 나온다.**  12x12 는 해태가 한글
2,350자를 ROM 에 넣으려고 코드까지 바꿔 만든 제약이다.

목적지 24 B = 12행 x 16비트 -> **가로 16칸 중 12칸, 세로 16행 중 12행만 찬다.**
영문·한글이 헐거워 보이는 이유 (소유자 지적).

### 결정 — 일본 원본에 얹는다

```
16x16 그대로 · 글리프가 꽉 찬다
글리프 팩이 이미 32B 16x16 이라 변환 불필요 (galmuri_ks_2350.bin)
해태 카드 의존 없음
한자가 안 죽는다 (아래)
```

### 한자를 안 죽이는 배정

코덱이 한글을 JIS 행 0x30~0x48(상용한자 자리)로 보낸다.  덮으면 미번역 일본어가
깨진다 -- 해태 카드가 정확히 그 상태다.

그런데 **게임은 한자 행마다 94칸 중 30~50칸만 쓴다.**

```
게임이 쓰는 (행,셀)   1,643      원문 4개 파일 전수
번역이 쓰는 한글        713
안 쓰는 칸            1,833      -> 배정 후 1,120 여유
```

`tools\build_bios_hangul_map.py` 가 **게임이 한 번도 안 쓴 칸에만** 배정한다.

```
우선순위   한자 행(0x30~0x47) 빈 칸 먼저 -- 정상 JIS 코드점이라 변환이 확실
           0x29~0x2F(JIS 미할당)는 넘칠 때만 -- 변환기가 거부하는지 미확인
안정성     이미 배정된 글자는 안 옮긴다.  새 글자만 뒤에 붙인다
산출물     build\bios_font\hangul_slot_map.tsv  (713행)
```

### 남은 작업

```
1. 16x16 base 확정     일본 BIOS 로 PROBE_FONT_ADDR_0.1.3 한 판이면 역산된다
                       ('一' 스윕으로 $006784 부근이 유력하나 미확정)

  $00297D-$002A81(261B) · $02C020 대역이 후보
```

## 부록 2 — 2026-08-18 밤 세션.  산술 버그 두 개

BIOS 로 한글을 내보내는 경로를 실제로 만들었다.  중간에 **내가 손으로 쓴 산술에서
버그가 두 개** 나왔고, 둘 다 증상이 크게 달랐다.

### 버그 1 — 인덱스 공식 (한자를 죽였다)

```
틀린 것   index = 행표[row-0x21] + (cell-0x21)
맞는 것   한자 행은 행표[row-8] 을 쓴다
```

`$F222` 부근이 **행 0x28~0x2F 를 거부한다** (`C9 28 / 90 36`, `C9 30 / 90 E1`).
그 8행은 JIS 미할당이라 글리프가 없고, BIOS 는 표를 압축해 쓴다.  그래서 한자
인덱스가 **752(= 8 x 94)** 씩 어긋났다.

증상: 게임이 쓰는 글리프 위에 갈무리가 얹혀 `東 -> 헤`, `人 -> 스` 로 나왔다.

**검증이 순환 논리였다.**  배정 제외도 "안 바뀌었다" 확인도 같은 틀린 공식을 썼다.
프로브의 실제 관측(SJIS -> 인덱스)과 대조해서야 드러났다.

```
SJIS  글자  관측    내 예측   차이
8EF3   受   1665    2417     -752
8FEC   嬢   1846    2598     -752
8A5A   鎧    761    1513     -752
835B   ー     27      27        0   (가나는 맞았다)
```

행 0x23(영문)은 또 달라서(Ｊ 관측 127, 어느 행표 값으로도 안 나옴) **0x23/0x26/0x27
은 배정에서 통째로 뺐다.**

### 버그 2 — SJIS 역함수 (한 글자도 안 나왔다)

`sjis_of(row, cell)` 를 손으로 썼는데 **저바이트의 0x7F 건너뛰기**가 빠졌다.
정방향에는 `if s2 >= 0x80: s2 -= 1` 이 있었고 역방향에 대응이 없었다.

```
한자행 1,128 조합이 어긋남
'각' SJIS 889F -> 배정표 idx 454 인데 재계산하면 453     한 칸 밀림
'가' SJIS 889E -> 유효한 SJIS 가 아님                    디코드 실패
```

**글리프는 인덱스 N 에 썼는데 코덱은 N-1 을 가리키는 코드를 내보냈다.**  그래서
한 글자도 안 나왔다.

고친 방법: **역함수를 쓰지 않는다.**  정방향 산술을 모든 유효 SJIS 조합(11,280)에
돌려 표를 만들고 왕복 검증했다 (불일치 0).

```python
_SJIS_TABLE = _build_sjis_table()      # build_bios_hangul_map.py
def sjis_of(row, cell): return _SJIS_TABLE.get((row, cell))
```

### 교훈

두 버그 다 **손으로 쓴 산술**에서 났다.  BIOS 의 코드/관측을 기준으로 검증하지
않으면 자기 공식으로 자기를 통과시킨다.  앞으로 이 계열은:

```
정방향은 ROM 코드를 읽어서 맞춘다
역방향은 정방향을 전수 열거해서 얻는다.  손으로 쓰지 않는다
검증은 프로브 관측값으로 한다.  같은 공식으로 확인하지 않는다
```

### 또 하나 -- 빌드는 2 단계다

`-unpatched` 폴더는 **중간 산출물**이다.  스텁만 심은 상태이고 핸들러 표를 돌리는

## 부록 3 — 한글 출력 성공, 그리고 한자 희생의 실체

### 성공

BIOS 폰트 경로로 **한글이 화면에 나온다** (2026-08-18 밤 확인).  화자 이름·본문 모두
갈무리 글리프로 렌더링된다.  사슬 전체가 붙었다:

```
마스터 ko_text -> 코덱(배정표 조회) -> 디스크 팩 레코드 -> 런타임 치환
               -> BIOS(코드 -> 인덱스 -> 갈무리 글리프)
```

### 그런데 "안 쓰는 칸" 은 없었다

**한자 행(0x30~0x47)의 유효 2,256 칸 전부에 글리프가 들어 있다.  빈 칸 0.**

원본 BIOS 를 직접 훑어 확인했다.  즉 배정표가 말하던 "게임이 안 쓰는 칸" 은
**"우리가 아는 텍스트에 안 나오는 칸"** 이었을 뿐이다.  NOTES 대로 정적 추출은 게임
전체의 30~40% 이므로, 못 본 대사에만 나오는 한자가 자유 칸으로 오분류된다.

커버리지를 최대로 넓혀도 (마스터·참조대장·UI·화자 + `extraction\out\` 의 복원본
전부, 합집합 3,417 조합) **남는 칸은 45 개**다.  필요한 713 에 한참 못 미친다.

증상: 미번역 일본어 줄에서 한자 하나가 한글로 튄다 (`残念だわ` -> `残의だわ`).

### 그래도 최종적으로는 문제가 아니다 (소유자 판단)

```
목표 상태   게임 전체가 한글 -> 일본어 원문이 화면에 안 남는다
그러므로    한자 글리프 파괴는 **미번역 구간에서만** 보인다
```

**수집에도 영향이 없다.**  수집기는 `$5E40` 에서 렌더링 **전**의 버퍼 바이트를 뜨므로
`source_hex` 는 원본 SJIS 그대로 들어온다.  화면이 깨져도 로그는 멀쩡하다.

실제 비용은 하나뿐이다 -- 수집·검수하면서 일본어를 읽을 때 불편하다.

### 줄이는 방법 (미적용)

빈 칸이 45 개뿐이라 약 670 자는 **쓰는 한자를 덮어야** 한다.  다만 어느 것을 덮을지는
고를 수 있다.

```
지금      행·셀 순서대로 앞에서부터   -> 자주 나오는 한자가 먼저 죽는다
개선안    전체 원문에서 출현 빈도를 세어 **희귀한 한자부터** 내준다
```

빌드 타임 계산이라 런타임 비용 0.  1~2 회만 나오는 한자가 많으므로 체감이 크게 준다.

근본 해법은 글리프 테이블 자체를 늘리는 것인데(ROM 끝 $03F35A ~ 256KB 사이 여유),
행 오프셋 표와 용량을 건드려야 해서 별건이다.

### 문서 화면 — 앞선 §8-N / §8-R 정정

```
가우디 사전       **정상 텍스트 경로.  별도 렌더러가 아니다.**  한글패치 가능
깁슨 환경 A 컴퓨터    **비트맵.**  텍스트 렌더러를 안 탄다 -> 수집기·프로브에 안 잡힌다
                  단서가 걸려 있어 번역이 필요하지만 그래픽 작업이다
```

둘을 한 덩어리로 보고 "같은 렌더러인가" 를 물은 것이 오류였다.  PROBE 0.6.8 에서
본문이 0 건이었던 것은 깁슨 환경 A 컴퓨터(비트맵)를 봤기 때문으로 보인다.

**그 결과 "문서 때문에 코드 공간이 필요하다" 는 전제가 사라졌다.**  §8-R 을 "다음 판의
분기점" 으로 크게 잡았는데 그 분기 자체가 해소됐다.

```
디스크    build\patch\0.4.1-bios\...[KO 0.3.12-bios] (0818-2000).cue
```

## 부록 4 — 자막 · yunatools (2026-08-19 새벽)

### 자막 로직은 검증됐다.  출력만 못 했다

`SUBTITLE_OVERLAY_0.1.2` 로그가 전 구간 통과를 보여준다:

```
SUB  적재 E6800_0E -> 금일부로 JUNKER로 임명된 길리언 시드다.
SUB  클립 key=E6800_0E -- 자막 1줄
SUB  >  금일부로 JUNKER로 임명된 길리언 시드다.
```

`SUB  >` 는 `emu.drawString` 을 **부른 뒤에** 찍는 줄이다.  즉 아래가 전부 맞았다:

```
클립 신원   ADPCM read+length(끝 주소) 키.  E6800_0E · E5800_0E 로 정확히 매칭
타이밍      재생 시작 프레임 기준 경과 초
자막 선택   start_sec / duration_sec 구간 판정
```

**화면에만 안 나왔다.**  0.1.3 으로 endFrame·지속프레임·색형식(작동 스크립트와 동일)
까지 맞췄으나 여전히 안 보였고, **`DELAY_SWEEP_0.2.1`(과거에 화면 보며 쓰던 것)도
지금은 안 보인다.**  따라서 스크립트가 아니라 Mesen 환경 문제다.

### 그래서 Lua 자막은 폐기한다 (소유자 지정)

Lua 로 얻은 세 가지(신원·타이밍·구간)는 CD 방식에서도 그대로 필요하므로 **버려지지

### 스프라이트 방식을 우리가 쓸 수 있나 — 나중에 잴 것 하나

```
음성 재생 중 스내처가 스프라이트를 몇 개 쓰나     SATB 는 64개
VRAM 에 패턴 자리가 있나                        자막 16개 = 2KB / 32개 = 4KB
```

게임이 40개를 쓰면 여유 24개 -> **한 줄(16개)은 된다.**  목표가 "최소 한 줄"이므로
그것으로 충분하다.  대사 아무거나 하나 재생시키고 SATB 를 읽으면 끝이라 프로브가
길게 돌 필요 없다.
