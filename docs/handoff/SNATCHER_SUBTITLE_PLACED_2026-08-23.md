앞 문서: `SNATCHER_SUBTITLE_EXTEND_2026-08-23.md` (빼앗지 않고 늘리기 — §3 후킹 지점이 이 문서로 대체됨)

## 1. 후킹 지점이 `$601E` 로 옮겨졌다 — 앞에 그리려면

앞 문서는 `$606F`(0 채우기 직전)에서 밀었다.  동작은 했지만 **게임 다음**이라
슬롯 번호가 항상 높았고, PCE 는 슬롯이 낮을수록 앞에 그리므로 자막이 초상화에
가렸다.  실제로 화면에서 초상화가 자막을 잘라먹었다.

지금은 조립 **시작**을 가로챈다.

```asm
601E  A9 3F 85 17   ->   20 20 5C EA          (JSR $5C20 + NOP)

스텁 $5C20 (54 B)
  PHP / SEI
  LDA #$3F / STA $17        ★ 밀려난 원본을 먼저 한다
  LDA $6500 / CMP #$82      스텁 자신도 오버레이를 확인
  BNE exit
  zp $08-$0F 원점 · $10/$11 리스트 · $16 글자수
  JSR $6463                 게임 푸시 루프를 빌린다 -> 슬롯 0.. 을 차지
exit
  PLP / RTS                 게임 객체 루프가 그 뒤 슬롯부터 이어간다
```

왜 맞는가:

```
MAWR   $6008 에서 슬롯 0 에 서 있다.  우리가 밀면 그만큼 전진하고
       게임 객체 루프가 그 자리에서 이어 쓴다
$17    우리가 $3F 로 세우고 우리 푸시가 깎는다.  $60A6 의 0 채우기가
       남은 칸을 정확히 채운다
VDC    한 글자도 안 쓴다.  MAWR 도 레지스터 래치도 안 건드린다
```

무장 `$6000` / 회수 `$6072` 는 앞 문서 §3.2 그대로다.  패치가 프레임 경계를
넘지 않으므로 오버레이가 갈려도 남의 코드에 우리 `JSR` 이 남지 않는다.

## 2. 잔류의 진짜 원인

앞 문서는 오버레이 교체만 의심했다.  실제로는 하나가 더 있었다.

```
지문은 맞는데 $601E 를 안 지나는 프레임이 있다 (메뉴가 떠 있을 때 등).
그러면 게임이 SATB 를 다시 안 쓰고, 지난 프레임의 우리 엔트리가 그대로 남는다.
```

지문으로 판단하면 이 상태를 못 잡는다.  **판단 기준을 "이번 프레임에 실제로
밀었는가" 로 바꿨다.**  안 밀었으면 SATB 64 칸을 훑어 우리 것만 지운다.

우리 것 판별:

```
attr == $0080  그리고  패턴 워드가 우리 대역 ($3C8 .. )
```

> 규칙: **"조건 A 일 때만 청소" 는 A 가 청소가 필요한 모든 경우를 덮는지
> 먼저 확인해야 한다.**  지문은 "오버레이가 갈렸다" 만 알려주지
> "이번에 안 그렸다" 는 못 알려준다.

## 3. 표시 폭은 256 px 다 — 재서 알았다

18 자(288 px)가 들어갈 거라고 넘겨짚었다가 좌표가 계속 어긋났다.
`emu.getState()` 경로를 추측해 두 번 실패한 뒤, **게임이 VDC 레지스터에
쓰는 값을 직접 잡아** 확정했다.

```
CPU $0000 = 레지스터 선택 · $0002/$0003 = 데이터
reg $0A HSR = $0202   HSW=2  HDS=2
reg $0B HDR = $041F   HDW=31 HDE=4
표시 폭 = (HDW + 1) * 8 = 256 px
```

프로브: `lua/PROBE_SCREEN_WIDTH_0_1_1.lua`

`emu.getState()` 의 전체 키 구조도 그 판이 찍어준다 — `vdc.hvReg.horizDisplayWidth`,
`vdc.spriteOverflow`, `vdc.satbTransferRunning` 등이 다 있다.  경로는
`st.vdc.hvReg.*` 가 아니라 재귀로 훑어야 나온다.

```
그림        게임 x 36..228   (192 px)   건드릴 수 없다
아래 검은 띠                              메뉴·초상화가 앉는다
자막        그림 아래쪽 띠에 얹는다
```

직접 움직여 잡은 자리가 `y 122 · 가운데 128` 이다.
`lua/PROBE_SUB_PLACE_0_1_0.lua` 로 I/K·J/L 로 옮기고 P 로 찍는다.

여기서 실수 하나를 고쳤다 — **원점이 글자의 왼쪽 끝**이라 "가운데=128" 인데
여백이 16/0 으로 어긋났다.  줄 폭의 절반을 빼야 진짜 가운데가 된다.

## 5. 폰트 — 재고 골랐다

구운 `poc_patterns.bin` 은 16x16 등폭이었다.  한 줄 11 자가 한계였고
글자 사이도 벌어 보였다.  `extraction/font_research/*.bdf` 를 실측:

```
              한글 DWIDTH   BBX      ASCII 'A'      4305 행 중 176 px 에
                                                    한 번에 들어가는 행
Galmuri9         10 px      9x9        6 px             98.4%     ★ 채택
Galmuri11        12 px     11x11       8 px             90.8%
Galmuri14        15 px     14x14      11 px             61.0%
구운 16x16       16 px     16x16      16 px          한 줄 11 자
```

**Galmuri 는 비례폭이다.**  영문·숫자가 한글의 2/3 폭이라 실제 문장은 등폭
계산보다 훨씬 짧게 들어간다.  우리 SAT 레코드가 글자마다 부호 8 비트 X
오프셋을 갖고 있어(앞 문서 §2) 비례폭이 **공짜**다.

렌더러: `tools/render_subtitle_line.py`

```
플레인 0 = 글자 본체   -> 색 1 (펌웨어가 흰색)
플레인 1 = 외곽선      -> 색 2 (펌웨어가 검정)
```

외곽선은 자막이 그림 위에 얹히기 때문에 넣는다.  1 px 팽창에서 본체를 뺀 것이다.
글자는 16 px 셀의 **세로 가운데**에 놓는다 — 위쪽에 붙이면 작은 폰트일수록
보이는 글자가 좌표보다 위로 떠 보인다.

```
Galmuri9   셀 행 3..11   외곽선 2..12
Galmuri11  셀 행 2..12   외곽선 1..13
Galmuri14  셀 행 1..14   외곽선 0..15
```

## 6. 오늘 걷어낸 잘못된 결론들

기록으로 남긴다.  같은 함정에 다시 안 빠지려면 왜 틀렸는지가 필요하다.

### 6.1 "16 글자는 스캔라인 한계에 걸린다" — 아니다

`0.1.5` 가 "한 스캔라인에 21 스프라이트 / 23 칸, 한계 16" 을 냈다.
그런데 **그 23 은 우리 16 + 게임 7 이었다.**  게임 단독은 최대 9 칸이다
(`PROBE_SPRITE_BUDGET 0.1.0`, 4200 프레임).

그리고 사용자 환경은 **스프라이트 라인 제한을 꺼둔다.**  실기를 고려하지
않으므로 이 한계 자체가 이 프로젝트에선 없는 문제다.
(다른 에뮬레이터는 기본이 제한 켜짐이라, 배포하면 거기선 깜빡일 수 있다.)

### 6.2 "초상화가 사라졌으니 드롭아웃이다" — 아니다

그 장면에서 초상화가 **원래 안 나올 시간**이었다.
화면에서 무엇이 없는 것을 근거로 삼기 전에 그것이 원래 있어야 했는지를 확인해야 한다.

### 6.3 "글자가 잘리는 건 스프라이트가 화면을 넘어서다" — 절반만 맞다

스프라이트 뷰어에는 16 개가 온전히 다 있었다.  화면에서만 잘렸다.
표시 폭이 256 이고 16 px x 16 자 = 256 px 라 **여백이 0** 이었던 것이다.
넘친 게 아니라 가장자리에 딱 붙어 있었다.

### 6.4 "번역이 18 셀에 맞춰져 있으니 18 자로" — 아니다

`snatcher_ko_master.tsv` 의 `max_cells = 18` 은 **게임 자체 텍스트 박스**의
제약이다.  음성 대사 자막은 아직 없고 새로 쓴다.  그러니 글자 수는 우리가
정하고 거기 맞춰 쓰는 것이 맞다.
