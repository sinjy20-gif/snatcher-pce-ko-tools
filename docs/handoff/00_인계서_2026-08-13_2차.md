## 1. 오늘 해결한 것 — UI 대량 적재 시 글자 깨짐

### 원인

`COMMON_DATA_BASE = $16000` 이 **atlas 크기를 참조하지 않는 하드코딩 상수**였다.
초기 CD→AC 적재는 AC `$00000` 부터 한 덩어리로 흐르고 8 KiB 청크로 올림 패딩되는데,
그 끝과 resident 팩 시작을 비교하는 코드가 없었다.

```python
init_total = align(DIRECTORY_BYTES + STATE_SPAN + TEMPLATE_BYTES + len(atlas), CHUNK_BYTES)
cursor     = align(dynamic.COMMON_DATA_BASE, USER_BYTES)   # $16000, atlas 무관
```

팩은 초기 적재 **다음에** 전송되므로 팩이 atlas 꼬리를 덮는다. 그리고 init 은
MAGIC 가드라 세션 중 재실행되지 않아 **파워사이클 전까지 복구되지 않는다.**

절벽은 청크 정렬 때문에 칼같다.

```
glyphs  atlas_end  init_total  speaker $16000
   741     $16000      $16000  OK          ← 마지막 안전
   742     $16020      $18000  8,192 B 파괴 ← 32B가 아니라 청크 통째로
  1089     $18B80      $1A000  16,384 B 파괴
```

실패본의 파괴 대상을 이름까지 특정했다. `direct_records.tsv` 로 atlas 순서를
재현하면 **정확히 1,089개**로 manifest 와 일치한다.

```
index 740  루   ← 마지막 생존
index 741  썩   ← 여기부터 348개 파괴  "썩 좋은 취향은 아니군."
출처: dialogue 190 / ui 150 / speaker 8      ← UI만의 문제가 아니었다
```

### 수정

```python
common_base = max(dynamic.COMMON_DATA_BASE, init_total)
dynamic.COMMON_DATA_BASE = common_base   # manifest 가 실효값을 보고하도록
```

`max()` 인 이유: atlas 가 `$16000` 아래면 기존 베이스를 유지하므로 **ac_0.1.14 가
바이트 단위로 재현된다.** 커지면 resident 가 따라 밀린다. 더해서 초기 적재·resident
팩·scene 바닥의 extent 를 정렬해 겹치면 빌드를 죽이는 감사를 넣었고, 에러 메시지에
**몇 번 인덱스부터 깨지는지** 찍는다.

### 검증

```

실물    UI 981 상태로 빌드 → atlas 1,089 glyph (0.3.0 을 죽인 그 수치)
```

## 2. 오늘 규명한 것 — §8-B 세이브 후 타이틀 복귀 시 화면 깨짐

> ⚠ **3차가 반증했다.** 아래 관측(케이브 814 B 를 게임이 통째로 읽어 VRAM 에 올린다)은
> 사실이지만, 그것이 §8-B 의 **유일한** 원인이라는 결론은 틀렸다. 같은 깨짐이
> `0.2.26`·`ac_0.1.14` 에서도 나오고, 3차가 `$5E20-$5FF1` 프리로더 영역에서도 동일한
> read-as-graphics 를 확인했다. 문서 상단 반증 블록을 볼 것.

**우리 버그가 맞고, 원인은 뱅크 `$69` 헬퍼 케이브다.**

### 대조 실험

원본 무패치 디스크에서 같은 조작(세이브 → 타이틀 → 로드)은 **정상**이다.
재플레이 없이 대조하는 방법: Mesen 은 BRAM 을 큐 파일명으로 저장하므로
`Saves\...[KO 0.3.1].sav` 를 `Saves\Snatcher CD-ROMantic (Japan).sav` 로 복사하면
원본 디스크가 같은 세이브를 바로 읽는다.

### 확정된 기전

케이브 `$BCD2-$BFFF` 에 읽기 콜백을 걸어 잡았다.

```
f5771   342 reads  $BCD2-$BE27   inHelper=false
f5772   472 reads  $BE28-$BFFF   inHelper=false
        342 + 472 = 814 = 케이브 크기 정확히,  구간도 빈틈 없이 연속
        같은 프레임 VDC 포트 쓰기 1,170 / 1,298
```

게임이 케이브 **전체를 순차로 긁어 VRAM 에 올린다.** 두 프레임에 나뉘므로
블록전송 명령이 아니라 루프다(정적 검색에서 `src=$BCD2` 또는 `len=814` 인
TIA/TII 0건). 원본 `track02.iso` 의 그 자리(ISO `$07F4D2-$07F7FF`)는 **814바이트
전부 `FF`** 다. 원본은 `FF` 를 퍼가고, 우리는 그 자리에 코드를 넣었으니 **우리 코드가
타일로 그려진다.** 텍스트가 멀쩡한 것도 이 구조와 맞는다.

### 교훈

케이브 검증은 "게임이 실행하지 않는다"를 증명했다. 사실이었다. 증명되지 않은 것은
**"읽지도 않는다"** 였다. `FF` 는 미사용의 증거가 아니라 **의도적으로 `FF` 로 채워둔
소스**였다. 이 프로젝트는 이미 같은 원칙을 다른 구간에 적어뒀다 — "not allocated is
not proven free". 뱅크 `$69` 케이브에는 적용되지 않았다.

## 4. 공간 조사 — 결론은 "없다"

> ⚠ **조사 결과는 유효하지만 목적이 무의미하다.** 헬퍼를 옮겨도 §8-B 는 안 고쳐진다
> (상단 반증 블록). 이 절은 이제 "§8-B 해법"이 아니라 **"패치가 쓸 수 있는 공간은
> 없다"는 독립된 사실**로만 읽을 것. 앞으로 코드를 어디에 놓을지 고민할 때의 기준이다.

헬퍼 814 B 를 옮겨야 하는데 **갈 곳이 없다.** 이건 부정적 결과지만 확정된
지식이고, 다시 파헤치지 않기 위해 남긴다.

### 4.1 이미 폐기된 땅 (2026-08-10)

`docs\prefetch_ram_audit.md` 의 RETRACTED 절이 두 가지를 이미 닫았다.

```
WRAM $2000-$3FFF   게임 상태·렌더러 포인터·$3619 버퍼·글리프 작업영역.
                   기존 덤프에도 비어있는 8 KiB 구간이 없다
뱅크 $6C           UI 0.1.42.lua 로 확인. 프레임 ~834 부터 BIOS PC $EA9E 가
                   32페이지 전부에 기록한다
```

그리고 방법론 자체에 대한 경고가 붙어 있다. **이걸 놓쳐서 오늘 같은 삽질을 반복했다.**

> 실수는 "뱅크 번호"를 고정된 디스크 오프셋처럼 다룬 것이다.
> `bank $68 == user $07B800` 은 부트 로더가 마침 거기 적재하기 때문일 뿐이고,
> **적재 영역 밖에서는 그 대응이 성립하지 않는다.** "이 8 KiB 디스크 이미지가 전부
> 0"이라는 사실은 어떤 뱅크에 대해서도 아무것도 말해주지 않는다.

`track02.iso` 를 뱅크 오프셋으로 환산해 스캔하는 방식은 **적재 영역(대략 뱅크
`$68-$6F`) 밖에서는 무효다.** 오늘 뱅크 `$70-$87` 을 그렇게 훑은 결과는 버린다.

### 4.3 게임이 우리 캐시를 덮어쓴다 (기존 문서, 오늘 재확인)

`03_OVERLAY_CONFLICT_MAP.md` §4 의 실측이 결정적이다.

BODY 는 줄마다 캐시를 재적재하므로 **데이터로는** 버틴다. 그러나 **코드를 거기 놓으면

### 4.5 검토했으나 수지가 안 맞는 안 — 글리프 온디맨드

704 B 캐시의 구성:

```
$5B80-$5BDF   96 B   메타데이터 + 텍스트      (레코드마다 갱신)
$5BE0-$5C3F   96 B   상수 3슬롯               (모든 레코드 동일)
$5C40-$5E1F  480 B   한글 글리프 15슬롯       ← 회수 후보
$5E20-$5E3F   32 B   분수 공백 헬퍼 코드      (정적)
```

480 B 는 매번 AC 에서 퍼오는 사본이고, 폰트 래퍼는 글리프를 하나씩 꺼내 쓴다.
AC→WRAM 32바이트 경로(`TII $1A00,dest,$20`)는 이미 있으므로 미리 펼치지 않고
필요할 때 가져오면 된다(동적 폰트 연구 문서 §12.4 와 같은 구조).

그런데 §4.3 때문에 **회수분 중 코드로 쓸 수 있는 것은 `$5CBA` 위쪽뿐**이다.

```
회수 가능 (코드용)  $5CBA-$5E1F  358 B  +  NOP 80  +  꼬리 14   =  452 B
필요               헬퍼 축소분 약 603  +  래퍼 AC 페치 약 +50   =  653 B
                                                        적자      약 150 B
```

**여유 0 이 아니라 적자다.** 착수하면 안 된다.

### 4.5 헬퍼 분할 가능성 (착수 시 쓸 자료)

call graph 를 뽑아 재배치 단위를 확정해뒀다. 709 B 는 연속 한 덩어리일 필요가 없다.

```
CORE   진입 + 디스패치           324 B   (BR 로 얽혀 있어 분리 불가)
CD 적재   load_blob 그룹         174 B   JSR 진입 → 이동 가능
레코드 복원 copy_record 그룹     141 B   JMP 진입 → 이동 가능
반환      return_miss/status      15 B   JMP 진입 → 이동 가능
set_ac                            32 B   JSR 진입 → 이동 가능
set_state_address                 23 B   JSR 진입 → 이동 가능
```

즉 요구조건은 "709 연속"이 아니라 "324 연속 + 나머지 조각들"이다. 다만 §4.4 대로
총량 자체가 모자라므로 이 분할만으로는 풀리지 않는다.

프리로더 433 B 도 뜯었으나 **349 B 가 살아있는 SRT4 조회 기계**(해시·개방주소 탐색·
서명검증)라 잘라낼 중복이 없다. 유일한 후보는 와일드카드 경로 32 B.

## 6. 남은 알려진 항목

### A. 화자명과 병합된 UI 라벨 22건이 1px 낮게 그려진다

`hangul_y_shift` 는 kind 가 100% 결정한다 — dialogue·speaker = `0`, ui = `-1`.
UI 라벨의 일본어 원문이 화자명과 같으면 화자명 레코드로 병합되고, 그 항목만
1픽셀 내려간다.

```
국장   kind=speaker  ref=speaker:3,ui:UI0109   y_shift=0    ← 1px 아래
모니터  kind=ui       ref=ui:UI0073             y_shift=-1
```

접수처의 **안내원**(`speaker:1,ui:UI0116`)도 같다. 총 22건 — 길리언·해리·미카·
리사·이사벨라 등. 순수 미관이라 이번엔 넘어가기로 했다.

### B. speaker/UI 원문 충돌 5건 — 검토 해제 상태

같은 일본어에 다른 한국어가 붙어 런타임 trie 가 구분할 수 없다. 빌더가
`speaker/UI source conflict` 로 죽인다.

```
UI0241 呼び込み  호객 vs 호객꾼        UI0350 <원문 5자>  오카네상 vs 오카네씨
UI0351 <원문 6자> 가면라이더 vs 가면 라이더   UI0370 イワン  어반 vs 이반
UI0419 <원문 8자>  코우네리상 vs 코우네리 아저씨
```

다섯 건 모두 **같은 인물**이라, 한국어를 화자명 쪽으로 통일하면 전부 출하 가능하다.

### C. 레코드당 15자 제한에 4행이 걸려 있다

704 B 레코드의 글리프 슬롯은 19개 = 상수 3 + 가용 15 + 분수공백 헬퍼 1.
한 줄에 서로 다른 한글이 16자를 넘으면 담을 곳이 없다.

```
19자  '데이터를 천성의 목소리 뱅크에 복사하는 것을'
16자  '…해리의 젊은 시절이라고는 생각 안 되는군.'  (2행)
16자  '을 모토로 서비스를 제공하고 있습니다.'
```

빌드가 예외로 죽으므로 조용히 깨진 디스크는 안 나온다. 해결은 번역 쪽이다.

### D. ★ 항목 8건 출하 제외

`UI0162 ★フレ★<원문 5자>` 는 개발자 디버깅 메뉴. 나머지 7건(`★`, `★★`, `０★`)은
category=candidate 파편. 전부 검토 해제했다.

## 8. 빌드와 용량

> ⚠ **자동 프루닝은 3차에서 제거됐다.** 일반 빌드는 이제 아무것도 지우지 않고,
> `--no-prune` 도 사라졌다. 삭제는 `--prune` 을 직접 줄 때만 일어난다.
> 보호 목록에 `0.2.26` 이 추가됐다. 아래는 갱신된 목록이다.

```
python build_snatcher_ko_0_3_2.py                 빌드만. 아무것도 지우지 않음
python build_snatcher_ko_0_3_2.py --check         무엇이 실릴지만 보고
python build_snatcher_ko_0_3_2.py --stage3        3단계만
python build_snatcher_ko_0_3_2.py --prune         정리 (명시할 때만)
python build_snatcher_ko_0_3_2.py --prune --deep  중간물까지 (--stage3 포기)
python build_snatcher_ko_0_3_2.py --space F041|20 띄어쓰기 실험. 별도 폴더로 산출
python build_snatcher_ko_0_3_2.py --tag NAME      데이터 실험. 별도 폴더로 산출
```

빌드당 실비용은 **200 MB**(패치된 Track 02 + Track 24)다. 나머지 22트랙은
`rom(japan)` 과 같은 inode 라 0 이다. 누적 1.67 GB 였던 것을 795 MB 정리했다.

보호 목록은 현재 버전 · `ac_0.1.11-source` · `ac_0.1.14`. manifest·TSV·검증 로그는
전 빌드 합쳐 5 MB 미만이라 **어느 경우에도 지우지 않는다.**

⚠ `ac_0.1.14` 는 현재 **재현 불가**다. 오늘 전체 빌드가 `ac_0.1.11-source` 중간물을
현재 마스터 기준으로 재생성했기 때문이다. 그 200 MB 가 출하 검증본의 유일한 사본이다.

## 9. 함정 (기존 인계서에 더해)

1. **`FF` 나 `00` 으로 채워져 있다는 것은 빈 공간의 증거가 아니다.** 실행·읽기·쓰기
   셋 다 조용해야 하고, 그것도 **실제로 지나간 경로에 한해서만** 유효하다.
2. **디스크 이미지의 뱅크 오프셋 환산은 적재 영역 밖에서 무효다.** `bank $68 ==
   user $07B800` 은 부트 로더의 우연이다.
3. **계측 Lua 를 제자리에서 고치지 말 것.** 버전을 올리고 **출력 파일 경로도 같이**
   올린다. 로그는 그것을 만든 코드 없이는 판독할 수 없고, 프로브에 결함이 있었다면
   더더욱 남겨야 한다. `lua\README.md` 에 규칙으로 적어뒀다.
4. **빌드 전 Studio 를 닫을 것.** 열어둔 채 외부에서 TSV 를 고치면 저장 시 되살아난다.
5. 파이썬으로 TSV 를 쓸 때 `encoding=` 명시.
