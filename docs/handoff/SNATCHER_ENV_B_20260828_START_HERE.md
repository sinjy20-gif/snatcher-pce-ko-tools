## 1. 버전별 변경점 (0.4.5.9 → 0.4.6.10)

전부 `build_snatcher_0_4_6_0.py`를 기반으로 하고, `SNATCHER_BUILD_VERSION`
환경변수로 출력 폴더가 갈린다. `0.4.6.7` 이후는 전용 빌더가 따로 있다.

| 버전 | 일회성 가드 | `$66E5` 훅 | 상태 |
|---|---|---|---|
| 0.4.6.0 | 없음 | `20 40 5E` (원본) | AC 선적재 첫 판 |
| 0.4.6.1 | 없음 | 원본 | |
| 0.4.6.2 | 없음 | 원본 | |
| 0.4.6.3 | 없음 | 원본 | **스프라이트 깨짐. 대조군으로 못 씀** |
| 0.4.6.4 | latch `$1A32` (`C9 A5`) | 원본 | **타이틀 안 뜸.** 가드가 처음 들어간 지점 |
| 0.4.6.5 | latch (`C9 65`) | 원본 | |
| 0.4.6.6 | latch (`C9 66`) | 원본 | 코나미 빌딩 한글 확인된 판 |
| 0.4.6.7 | latch (`C9 67`) | `20 D4 FF` | 접수처 복구 1차 — **접수처 크래시** |

### 1-1. 접수처 복구 (0.4.6.7 → 0.4.6.9)

세 번 만에 닫았다. 실패 원인이 각각 달랐다.

```
0.4.6.7 크래시   TAM #$80으로 BIOS bank1을 $E000-$FFFF에 매핑하면 IRQ 벡터가
                 전부 $FF가 된다. SEI가 없어 인터럽트가 $FFFF로 점프했다
0.4.6.8 무동작   가드를 JSR $5E40 뒤에서 평가했다. $5E40은 게임 자신의 접수처
                 판정을 내장하고($5E5E~$5E76) 빠져나오며 포인터를 $5B90으로
                 덮어쓴다($5F8A). 그래서 $3499를 절대 볼 수 없었다
0.4.6.9 합격     가드를 JSR $5E40 앞으로 옮김 + PHP/SEI로 bank1 구간을 감쌈
```

최종 구조:

```
Track02 $66E5   20 D4 FF   JSR $FFD4     (원본 20 40 5E)
Track02 $66F8   4C 3F 68   원본 유지. armed일 때만 런타임 변경

BIOS bank0 $FFD4  08 78 A9 01 53 80   PHP / SEI / LDA #$01 / TAM #$80
BIOS bank1 $FFDA  4C 54 F0            dispatch로 착지
BIOS bank1 $F054  150 B               dispatch $F054 / repair $F08A
BIOS bank1 $F04E  53 80               TAM #$80 -> bank 0
BIOS bank0 $F050  68 28 60            PLA / PLP / RTS (기존 BIOS 바이트 재활용)
```

상세: `docs/SNATCHER_RECEPTION_FIX_2026-08-27.md`

### 1-2. 일회성 가드 재설계 (0.4.6.10)

`0.4.6.4`~`0.4.6.9`는 아케이드 카드 포트3 주소 래치(`$1A32`)에 매직을 써두고
되읽어 "이미 적재됨"을 판정했다. **그 래치는 페이로드와 아무 연결이 없고,
여러 코어에서 소프트 리셋으로 지워지지 않는다.**

```
리셋 -> 래치는 생존, AC 메모리는 소실 -> 가드가 "적재됨"이라 거짓말 -> 번역 없음
```

`0.4.6.10`은 래치를 없애고 **AC 메모리를 실제로 되읽는다**.

```
A9 00 20 32 BF   LDA #$00 / JSR $BF32     포트0 -> AC $010000
A2 00            LDX #$00
AD 00 1A         LDA $1A00
DD CE FF         CMP $FFCE,X              state_table
D0 08            BNE preload_needed
E8 E0 06 D0 F3   INX / CPX #6 / 반복

$FFCE   AC 15 51 00 01 02
```

게시 단계도 같은 테이블을 쓴다. 가드가 보는 것과 그것을 참으로 만드는 것이
같은 6바이트라 어긋날 수 없다. 페이로드 이미지의 `$010000`은 `FF`이므로
부분 적재도 걸러진다.

상세: `docs/SNATCHER_AC_GUARD_FIX_2026-08-27.md`

## 5. 종결 — 화면 잔상은 우리 것이 아니다

**2026-08-28 소유자 확인: 우리 패치 문제가 아니다.  코어 정확도 문제다.**

증상이 코어·장면마다 다르게 나타난다:

```
깁슨 환경 A 문서 화면   하단에 글리프 조각      (SuperGrafx)
폐공장             위쪽에 그림 잔상        (Beetle PCE, 제일 깨끗한 축인데도)
```

아래 기록은 **다시 파지 않기 위해** 남긴다.  특히 §5-2 의 반증은 그대로 유효하다
-- 우리 글리프 쓰기와 무관하다는 것이 이미 실측으로 나와 있었다.

### (아래는 08-28 이전의 조사 기록)

### 옛 제목: 자막 배경(BAT) 침범

메탈기어 등장 이후 문서 화면(깁슨 환경 A 컴퓨터) **하단에 글리프 조각이 배경으로
깔린다.** 접수처 건과는 완전히 별개다.

### 5-1. 08-28에 확정한 것

디스크 빌드에는 allocator가 없고 `$7900`이 상수로 구워져 있다.

```
renderer off 165  MAWR 하위        off 167  MAWR 상위
renderer off 276  패턴 하위         off 281  0x80 | (패턴상위<<4) | 팔레트
helper   off 39/41   MARR 하위/상위 (VRAM 백업)
helper   off 131/133 MAWR 하위/상위 (VRAM 복원)
base는 반드시 32워드 배수 (& 0xFFE0)
```

`off 281`의 정체는 `build_subtitle_engine.py` 주석에 있다 — 레코드 5번째 바이트가
`0x80 | ((word>>8)<<4) | palette`, `word = base>>5`. `$6463`이 `AND #$70`으로
패턴 상위를, `AND #$8F`로 속성을 뽑는다. base `$7900`이면 `0xBF`가 된다.
**바이너리에서 `A9 03`을 찾으면 안 나온다** — `<<4` 되어 `0xBF` 안에 섞여 있다.

그 장면 VRAM 실측 (BAT 본체 4096 + SATB 본체 256 제외):

```
필요                1,216 word (19글자 x 0x40)
창 $6000-$7FFF      최대연속   768 word · 총여유  1,392
VRAM 전체           최대연속 3,824 word @ $1110 · 총여유 11,648
```

### 5-2. ★ 반증된 가설 — 다시 세우지 말 것

"글리프가 배경 타일을 덮어써서 깨진다"고 보고 base를 옮겨 시험했다.

```
0.3.41에서 base = $1140 강제
  렌더러 off165/167/276 = $40/$11/$8A · off281 = $8F
  SATB 실제 = $1140 $1180 $11C0 ... $1500   <- 예상과 완전 일치
  $7900 = 0/64,  $7100 = 사용 안 함
```

**주소 사슬이 완전히 일치했는데도 하단 깨짐이 그대로였다.**

즉 하단 깨짐은 **우리 글리프 쓰기가 만드는 것이 아니다.** allocator를 완성해도
이 증상은 안 사라진다. 원인을 다른 데서 찾아야 한다.

### 5-3. 다음에 볼 곳

```
깨진 타일이 실제로 어느 VRAM 주소에서 오는지부터 특정할 것
  - 하단 깨진 칸의 BAT 엔트리를 읽어 패턴 번호를 구하고
  - 그 패턴이 가리키는 VRAM 구간에 누가 쓰는지 추적

의심 후보 (미검증)
  - 자막 스프라이트가 아니라 자막이 쓰는 팔레트/속성이 배경에 영향
  - 렌더러가 SATB 스테이징($5CEE~)을 넘기는 JSR $6463 쪽 부작용
  - 자막과 무관한 별개 버그 (자막 없이도 재현되는지 먼저 확인할 것)
```

**가장 먼저 할 것: 자막을 완전히 끈 상태에서 그 장면이 깨지는지 확인.**
렌더러 offset 366의 열쇠 6바이트를 0으로 만들면 자막이 아예 안 그려진다.
거기서도 깨지면 자막과 무관한 문제다. 이 확인을 안 하고 계속 자막 쪽을 팠다.
