## 2026-08-31 20:20 환경 A에서 확정 — 노스킵 화면 깨짐의 원인

**낡은 백업으로 복원하는 것**이 원인이다.  개입 시험 두 판으로 갈랐다.

```
0.5.76  CD-DA 의 VRAM 복원을 건너뜀        -> 여전히 깨짐
0.5.77  복원은 그대로 · 백업 내용만 최신화  -> ★ 정상
```

두 판의 차이는 **복원하는 내용** 하나뿐이다.  그래서
"복원한다/안 한다" 가 아니라 "무엇을 복원하느냐" 가 원인으로 확정된다.

`0.5.76` 이 실패한 이유도 설명된다 -- 복원을 막으면 우리가 그린 글자가
`$7900-$7DBF` 에 남아 그 자리를 쓰는 화면이 어차피 깨진다.  두 원인이 같은
결과를 내므로 그 판으로는 가려지지 않았다.

### 기구 (0.5.75 · 0.5.77 실측)

```text

재생 중             writesGame 320 (PC $650C-$60BA)  게임이 같은 자리에 쓴다
7788f  CD-DA 종료   시작 시점 백업으로 덮는다
                    start->after = 0   복원 후가 시작 스냅샷과 완전 동일
```

`0.5.77` 이 복원 직전에 백업을 현재 화면으로 갈아치우며 잰 값:

CD-DA 는 트랙 하나를 몇 분씩 재생하는데 백업은 **시작 때 한 장**뿐이다.

### 무엇이 잘못됐나

CD-DA POC 가 **"트랙 재생 중"과 "VRAM 을 빌린 중"을 한 상태로 묶었다.**
ADPCM 의 "음성 시작 ≈ 자막 임대 시작" 계약을 긴 CD 트랙에 그대로 적용한 결과다.
ADPCM 은 음성 하나가 몇 초라 그 등식이 성립했고, CD-DA 는 몇 분이라 깨진다.

### 임대 단위는 "자막 표시 구간"

"자막 한 줄"도 아니고 "CD 트랙 전체"도 아니다.
**같은 VRAM base 를 연속해서 쓰는 표시 구간 하나**가 임대 단위다.

```text
0.00초   CD-DA 시작    시계만 시작.  VRAM 은 아직 안 빌린다
36.46초  c17_001 시작  그 순간의 VRAM 백업 · STATE=1 · 첫 줄
40.59초  둘째 줄       selector 만 교체.  같은 자리이므로 저장/복원 없음
44.72초  c17_001 종료  STATE=3 · 36.46초에 저장한 것을 정확히 복원
```

base 가 달라지는 경계(다음 clip)에서는 `기존 base 복원 -> STATE=0 완료 ->
다음 프레임 새 base 백업` 순서로 넘어간다.

### ⚠ 앞 절의 `sched_due` 지적은 철회한다

`sched_due` 는 **ADPCM scheduler** 다.  통합부는 CD-DA 엔진 시그니처
(`$5B80+timer == $38`)를 확인해 CD-DA 에 ADPCM scheduler 를 적용하지 않는다.
CD-DA 의 시간 진행과 줄 전환은 렌더러 자체 타이머가 한다.
따라서 `sched_due` 를 고쳐도 Track 17 에는 적용되지 않는다.

### 고칠 곳 — 시간축과 임대축 분리

`build_snatcher_0_4_6_29_native_arm.py` 의 `cdda_start` 가 지금 둘을 같이 한다.

```text
line 331-332   base $7900 설치        (00 79 03 C8)
line 343       STATE=1                 -> resident 가 즉시 백업
```

이 둘을 떼어낸다.  필요한 상태는 두 개다.

```text
CDDA_ACTIVE   트랙 시간이 흐르고 있는가
STATE         VRAM 을 실제로 빌리고 있는가  (0/1/2/3)
```

`STATE` 의 의미를 바꾸는 것이 아니라 **더 엄격히 지키는** 수정이다.

```text
STATE 0 = 빌리지 않음
STATE 1 = 지금 백업하고 빌림 시작
STATE 2 = 빌린 상태
STATE 3 = 지금 정확히 복원하고 반납
```

### ★ 구현상 걸림돌 — 시계가 임대 안에 있다

```text
elapsed   engine offset 669 -> $5E1D      엔진 슬롯 안
timer     offset 602        -> $5DDA
```

렌더러는 `STATE != 0` 일 때만 `$5B80` 에 실려 불린다.  그러므로 지금 구조로는
**"시계만 돌리고 STATE 는 0" 이 성립하지 않는다** -- 시계가 아예 안 돈다.

시계를 임대 밖으로 빼야 한다.  선례가 있다 -- ADPCM scheduler 가
`AC_SCHED = $1F2710` 에 `elapsed u16 · part · count · next ptr` 7 B 를
persistent 로 둔다.  CD-DA 도 같은 방식이면 된다.

그러면 통합부가 매 프레임 하는 일이 이렇게 된다.

```text
CDDA_ACTIVE 면    elapsed++ (AC persistent)
elapsed == 2188   base 설치 · STATE=1      ← 여기서 처음 빌린다
elapsed == 2683   STATE=3                  ← 반납
```

렌더러의 `threshold_low` 표(2188/2435/2683)를 그대로 쓰고, 줄 전환(2435)만
렌더러에 남긴다.

### ⚠ 그래도 남는 노출

임대가 45 초 -> 8 초로 줄지만 **0 이 되지는 않는다.**  그 8 초 안에도 게임이
그 자리를 쓰면 복원이 덮는다.  `0.5.75` 는 `writesGame 320` 을 시간대별로 가르지
않았으므로 표시 구간 안의 쓰기 유무는 아직 모른다.

그 답은 안전 위치표가 해야 하는데 지금은 `$7900` 이 하드코딩이라 연결이 끊겨 있다.
현재 표가 `c17_001` 에 고른 값은 `$2000` 이다.  다만 후보가 71 개라 `$7900` 이
표시 구간 중에 위험하다고 **단정할 수는 없다** -- 출력표는 최종 선택 하나만 남긴다.
확실한 문제는 하드코딩 값이 authoritative 표와 분리돼 있다는 점이다.

최종판은 이렇게 되어야 한다.

```text
CD-DA 창 시작 -> 그 창의 검증된 base 를 읽는다
                 없으면 fail-closed (자막 미출력)
                 있으면 그 base 로 백업하고 표시
```

### 그대로 쓰는 것

```text
helper 의 저장·복원      그대로
resident 의 STATE 계약   그대로
SATB wipe                그대로
CD-DA 렌더러의 줄 전환    그대로
```

고칠 것은 **CD-DA 의 시간축과 임대축 분리** 하나다.

## §239  0.4.6.53 — CD-DA renderer 반환 VDC 상태 복원 (정적 검증 통과 · 실기 대기)

`.49` 이후의 늦은 lease 자체와 별개로, `0.5.84/.85` 전수 관측이 화면 깨짐의 두 번째
독립 원인을 확정했다. renderer가 반환할 때 HuC6270의 MAWR만 `$7D40` 등으로 남기고,
게임은 다음 VDC 스트림을 진입값 `$1000`에서 이어 쓴다. 실제 관측은 다음과 같다.

```text
엔진 진입 2,685 / 2,685   sel=$02 · MAWR=$1000 · increment=+1
선택/증가량 파손          0 회
CD-DA renderer 반환        MAWR=$7D40/$3A00 등 (renderer push 경로)
```

`.52`의 helper 반환 복원만으로는 renderer의 `push -> RTS` 뒤에 남는 MAWR을 고치지
못한다. 또한 `.52` 래퍼는 `.51`의 `CDDA_LEASE_AT=2188` 설정을 넘기지 않아, 그
산출물을 쓰면 늦은 lease도 꺼진다. **`.52`는 시험하지 말고 `.53`을 사용한다.**

`.53`은 Track 17 POC의 두 record가 모두 SATB y=`$0100`인 불변 계약을 사용해 push의
동적 y 계산 14 B를 6 B 상수로 줄였다. 확보한 8 B에 아래 9-byte 꼬리(기존 RTS 1 B
대체)를 넣어, 반환 직전에 MAWR 및 VWR 선택을 복원한다. ST0/ST1/ST2는 A/X/Y/flags를
변경하지 않는다.

```text
03 00  13 00  23 10  03 02  60
 ST0     ST1     ST2     ST0    RTS
 MAWR    lo=00   hi=10   VWR
```

`.51`의 늦은 lease도 함께 유지했다: 트랙 시작부터 AC 시계만 돌리고, `2188f`에서만
백업/STATE=1을 발행하며 AC 원본 renderer에 동일 elapsed를 심는다.

```text
build/patch/0.4.6.53/
tools/build_snatcher_0_4_6_53_cdda_vdc_restore.py

정적 감사
  CD-DA renderer           671 B · 반환 복원 꼬리 정확히 1개
  lease                    2188f
  Track02 resident         0.4.6.42와 SHA-256 동일
  BIOS SHA-256             4043665A425EF40876F7099203B231F859908CCED5A5FDF473958977EB8A3913
```

실기에서는 `.53` BIOS/CUE만 올린 뒤 Lua 없이 노스킵으로 다음을 모두 확인한다.

```text
1  CD-DA 두 줄: 36.46 / 40.59 / 44.72초
2  종료 뒤 ACT1 · 챕터1 · 접수처 화면 정상
3  D000 ADPCM 1/2/3 및 UI 복귀 정상
```
