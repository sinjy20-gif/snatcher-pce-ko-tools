### ✔ SEI 제거의 잔여 위험 -- **실측으로 기각** (0.5.26 · 2026-08-30)

아래 §"감사 대상" 의 가설을 `0.5.26-backup-roundtrip-recheck` 로 직접 쟀다.
현행 기준판(0.4.6.22 + 0.4.93-hq-key-vram, `$7F4A` = NOP), 국장실.

```
SAVE    18 회   VRAM->AC 불일치 0/2432      외부 $0000 쓰기 0   (#10 만 4)
RESTORE 18 회   왕복     불일치 0/2432      외부 $0000 쓰기 7   (PC $4775)
base    $6600 $4600 $4B00 $4300 $6D00 $5200   전부 깨끗
```

**외부 코드가 실제로 래치를 건드리는데도 데이터는 멀쩡하다.**

`$4775` 는 `$4000-$5FFF` = MPR2 구간이고 baseline §3 의 IRQ1/VSync 핸들러
`$2202 -> $40A4` 안이다.  즉 IRQ 는 우리 helper 한복판에 **실제로 떨어진다.**

왜 안 깨지는가 -- 0.5.20 덤프가 답을 준다.

```
$E42F  set_MARR  ... A9 02 / 85 F7 / 8D 00 00 / RTS    끝에 $02 선택
$E446  set_MAWR  ... A9 02 / 85 F7 / 8D 00 00 / RTS    끝에 $02 선택
```

**게임의 관례상 선택 래치의 평상시 값이 `$02`(VWR) 다.**  핸들러가 `$F7` 로
복원하면 그것이 곧 우리가 필요한 `$02` 다.  우연히 맞아떨어진다.

#### ⚠ 그래도 남는 것 두 가지

1. **우연한 안전이다.**  우리는 게임의 `$F7` 이 마침 `$02` 인 것에 기대고 있다.
   어떤 경로가 `$F7` 을 다른 값으로 둔 채 helper 가 돌면 깨진다.
   지금 결함은 아니지만 설계상 보장이 아니다.

2. ~~이 측정이 못 답하는 것~~ -- **0.5.27 로 닫았다.**

   0.5.26 은 `save 진입 VRAM` vs `restore 완료 VRAM` 만 비교했으므로, 그 사이에
   렌더러가 그 영역을 안 건드렸다면 "불일치 0" 이 자동으로 나올 수 있었다.
   0.5.27 은 **복원 직전에도** 원본과 비교하도록 했다.

   ```
   RESTORE #1  복원전 더럽힘 1410/2432 · 왕복 불일치 0/2432
   RESTORE #2  복원전 더럽힘 1433/2432 · 왕복 불일치 0/2432
   RESTORE #3  복원전 더럽힘 1440/2432 · 왕복 불일치 0/2432
   ```

   렌더러가 실제로 **58~59 %** 를 덮어쓰고, 복원이 원본과 정확히 일치하게 되돌린다.
   -> "불일치 0" 은 실질적인 값이다.  **이 감사 항목은 완전히 닫혔다.**

#### ⚠ 0.5.27 이 만든 오경보 -- `$7F4A` 진동은 프로브 결함이다

0.5.27 로그에 `$7F4A` 가 `$EA`(NOP) 와 `$E2` 사이를 격프레임으로 오가는 줄이
수백 개 찍힌다.  **빌드 불안정이 아니다.**

`$7F4A` 는 CPU `$6000-$7FFF` = **MPR3 뱅킹 구간**이다.  0.5.20 덤프의 MPR 은
`FF F8 68 6A 7C 7D 7F 00` 으로 MPR3 = `$6A` 이고 상주부는 그 CD 작업 RAM 뱅크에 있다.
게임이 MPR3 에 다른 뱅크를 걸면 같은 주소를 읽어도 **남의 데이터**가 나온다.

```
NOP ($EA)   상주부 뱅크가 걸려 있는 프레임
$E2         다른 뱅크가 걸려 있는 프레임.  상주부와 무관한 바이트
```

같은 로그에서 SAVE/RESTORE 가 전부 정상이므로 코드가 실제로 덮어써진 것이 아님은
자명하다.  원인은 **뱅킹을 확인하지 않고 매 프레임 읽은 것**이다.

★ 교훈 -- `$4000-$BFFF` 의 CPU 주소를 프레임 단위로 감시할 때는 **먼저 지문으로
그 뱅크가 걸려 있는지 확인**하고, 아니면 그 프레임을 건너뛴다.
`$7F49` 의 상주부 지문은 `08 ?? A9 3F` (PHP · SEI/NOP · LDA #$3F) 다.
같은 함정이 `$5B80-$5D3F`(MPR2, 뱅크 `$68`) 감시에도 그대로 적용된다.

## 1. ★ 두 증상은 다른 원인이다

| 증상 | 한 글자 엔진(0.4.87) | 결론 |

### 1-1. ⚠ 이 절은 2026-08-30 에 뒤집혔다 — 둘은 **같은 뿌리**다

> 아래는 당시 관측에 근거한 판단이었고, **관측 자체는 지금도 맞다.**
> 그러나 §7-E 에서 원인이 하나로 밝혀졌다:
> `SEI -> NOP` 한 바이트로 **떨림과 번쩍임이 동시에 사라졌다.**
>
> 둘은 원인이 다른 게 아니라 **같은 원인의 다른 발현**이었다:
>
> ```
> 떨림      차단 시간이 프레임마다 글자 수에 따라 흔들린다 -> 분할선이 떨린다
> 번쩍임    자막 시작 프레임엔 고정 비용(복사)만으로도 분할을 통째로 놓친다
>           -> 띠가 번지고 타일맵 위쪽이 나온다
> ```
>
> 한 글자 엔진이 떨림만 줄이고 번쩍임은 못 줄인 것도 이것으로 설명된다 --
> 루프는 줄었지만 고정 비용은 그대로였으므로 시작 프레임의 놓침은 남았다.
>
> **처방도 하나다: IRQ 차단 창을 쪼개거나 옮긴다.**

당시 기록(참고):

```
떨림          글자 수에 비례한다.  전송량 문제다
뒷화면 소환   글자 수와 무관하다.  조각마다 한 번, 짧게
```

이 "다르게 반응한다" 는 관측이 원인 분리로 이어지지 않는다는 것이 교훈이다.
같은 원인이라도 지속 시간과 타이밍에 따라 다르게 보일 수 있다.

> 게임이 우리를 부르는 경로를 타는 것 자체가 원인이다.**

그 경로에 들어 있는 것은 네이티브 헬퍼의 일이다 -- AC `$1F1F00` 의 653 B 를
`$5B80` 으로 복사하고 `JSR $5B83`.  653 B 블록 전송이면 중단 불가로 대략
8~9 스캔라인을 먹는다.

### 2-2. 이걸로 그동안의 모순이 전부 풀린다

| 관측 | 설명 |
|---|---|
| 한 글자로 안 줄었다 | 복사량은 글자 수와 무관하다.  항상 653 B |
| VDC 재무장이 못 고쳤다 | 우리 전송이 아니라 헬퍼의 복사다 |
| 와이프 · 팔레트 무죄 | 둘 다 분기 안쪽의 세부사항일 뿐이다 |
| 음성마다 한 번, 짧게 | 게이트가 음성마다 한 번 열린다 |
| 떨림만 글자 수에 비례 | 떨림은 우리 글리프 루프.  애초에 다른 원인이다 |

### 2-3. ★ 그 구간을 실제로 재봤다 — 653 B 가 아니었다

[0.5.2](../../lua/SUB/0.5.2-copy-timing.lua) 로 `$5B80-$5E1F` 쓰기를 프레임마다
셌다.  entry=RTS 엔진이므로 **우리 엔진은 아무것도 쓰지 않는** 조건이다.

```
평소 프레임      144~221 회   ·  프레임 전체(line 56 -> 248)에 흩어짐
자막 첫 조각     3,425 회     ·  line 23 -> 52   span 29~30 줄
자막 이후 조각   2,755 회     ·  line 22 -> 68   span 44 줄
```

**두 가지가 한꺼번에 나왔다.**

#### (1) "653 B 복사" 라는 추정은 자릿수가 틀렸다

3,425 회는 653 의 5 배다.  밀도를 보면 더 분명하다 -- 30 줄 ≈ 13,650 사이클인데
그 안에 3,425 회면 **4 사이클당 1 회**다.  블록 전송(6 사이클/바이트)과 같은
급이고, 즉 그 29~44 줄 동안 **CPU 가 이 영역에 쓰는 것 말고는 거의 아무것도
안 한다.**  그것도 표시 구간 한복판(line 22~68)에서.  래스터 분할이 밀릴
수밖에 없다.

그리고 이 폭주는 **조각마다** 난다 (첫 조각 3,425 · 이후 2,755).
번쩍임 주기와 정확히 같다.

#### (2) `144~221 회/프레임` 은 **음성 사이의 UI 상태** 값이다 — 기준선이 아니다

`144~221 회` 가 나온 구간(121~155f)과 마지막 구간(3384~3400f)은 **둘 다 UI(메뉴
창)가 떠 있는 상태**였다.  그리고 이 게임은 **음성 중에는 UI 를 안 띄운다.**
사용자 확인.

```
UI 떠 있음  =  음성 없음  =  우리 엔진 없음
음성 중     =  우리 엔진 있음  =  UI 없음
```

**둘은 겹치는 시점이 아예 없다.**  그러므로

- "게임이 평소에도 $5B80 을 매 프레임 쓴다" 고 말하면 안 된다.
  그 표본은 음성이 끝나고 UI 로 복귀한 시점이다.
- "UI 스크립트 VM 이 쓰는 동안 우리가 덮는다" 는 그림도 성립하지 않는다.

`subtitle_layout.py` 의 전제는 이렇다:

```
$5B80  엔진 704 B      스크립트 VM 데이터 스택.  **음성 중에만** 빌린다
```

이 전제가 성립하려면 **음성 중에 게임이 그 자리를 안 써야 한다.**  그런데
지금까지 잰 것은 전부 (a) UI 상태이거나 (b) 우리 엔진이 이미 올라간 음성 중이다.
**"음성 중 · 우리 엔진 없음" 의 $5B80 트래픽은 한 번도 잰 적이 없다.**
그것이 이 전제를 확인하거나 무너뜨리는 유일한 측정이다 (§7-0).

#### (3) ★ 그 폭주는 **전부 우리 것**이다 (0.5.3)

[0.5.3](../../lua/SUB/0.5.3-vm-stack-during-voice.lua) 은 `SUB_VOICE_NO_GATE` 로
게이트를 안 열어 **엔진이 $5B80 에 올라가지 않는다.**  음성은 그대로 재생되고
UI 도 안 뜬다.  그 상태에서 같은 구간을 셌다.

```
voice   2,724 프레임 · 평균 0.0 · 최대 0 · 무쓰기 100%
idle      876 프레임 · 평균 11.0 · 최대 2112
```

**음성 중에 게임은 `$5B80-$5E1F` 에 한 번도 쓰지 않는다.**  2,724 프레임 동안
최댓값이 0 이다.  `subtitle_layout.py` 의 "음성 중에만 빌린다" 전제는 **맞다.**

그래서 뺄셈이 끝난다:

```
0.5.2  음성 프레임 (복사 있음)   2,755 ~ 3,425 회
0.5.3  음성 프레임 (복사 없음)           0 회
──────────────────────────────────────────────
차이                             2,755 ~ 3,425  =  전부 우리 것
```

게임 복구가 아니다.  **100 % 우리 분기가 만든 것**이다.

#### (4) ★ 분해 (0.5.4) — 672 B x4~5 가 아니었다

[0.5.4](../../lua/SUB/0.5.4-copy-decompose.lua) 가 버스트를 **연속 구간(run)** 으로
쪼갰다.  블록 전송은 주소가 연속이므로 run 목록이 곧 패스 목록이다.

```
run1      +$000..+$13F    320 B   x1     line 22~24 -> 34~36
run2~21   +$0AF..+$12E    128 B   x19    각 4~8 줄, line 35 -> 177
run23     +$000..+$29E    671 B   x1     첫 조각에만
──────────────────────────────────────────────────────────────
          320 + 19x128 = 2,752   이후 조각  (실측 2,755)
          + 671        = 3,423   첫 조각    (실측 3,425)
```

숫자가 `bios_preload.json` 과 정확히 맞는다 -- `subtitle_helper 320 B` ·
`subtitle_renderer 671 B`.  그리고 `19 x 128 B` 는 글리프 19 개 x 글리프 크기다.

#### (5) ★ 누가 쓰는가 (0.5.5) — PC 로 특정

[0.5.5](../../lua/SUB/0.5.5-writer-pc.lua) 가 run 시작 시점의 PC 를 찍었다.

```
x1    320 B  +$000..+$13F  PC $7FAA      ← 상주 스텁 ($7FA0 대)
x19   128 B  +$0AF..+$12E  PC $5BB5/$5C14 ← $5B80 에 올라온 320 B 헬퍼
x1    671 B  +$000..+$29E  PC $7FC3      ← 상주부.  단 STUB_BYTES(32 B) 밖이다
```

순서: 스텁이 헬퍼 320 B 복사 -> 헬퍼가 19x128 -> 스텁이 엔진 671 B 복사 -> entry.

> ⚠ 이 판의 `$5BED` 지문 판정은 **내 기준값이 틀려서** "우리 것이 아니다" 로
> 오경보를 냈다.  `A9 01 EA` 는 **한 글자 엔진**의 서명(+$6D)이고, `entry=RTS`
> 엔진은 **offset 3** 만 다르다.  재무장 엔진의 +$6D 는 `AD 4E 5D`
> (`LDA $5D4E` = LDA record, record=462) 로 **정확히 우리 것**이다.
> 0.5.1 · 0.5.4 의 전제는 유효하다.

#### (6) ★ 그 19x128 의 정체 — 죽은 VRAM 백업/복원 (디스어셈)

`resident_helper_slot_native_poll_0_8_3.bin` (320 B) 를 `$5B80` 기준으로 뜯었다.

```
$5B83  LDA $5C2D                       "이미 백업했나" 플래그
$5B86  BNE $5BE4                       했으면 복원 경로로
       AC 포트0 = $1F0400 (= AC_VRAM_BACKUP)
$5BA4  ST0 #$01 / ST1 #$00 / ST2 #$79  MARR = $7900     ← 읽기 주소
$5BAA  ST0 #$02
$5BAC  LDX #$13                        19 회
$5BAE  TAI $0002 -> $5C2F, $0080       VDC -> RAM 버퍼 128 B
$5BB5  TIN $5C2F -> $1A00, $0080       RAM 버퍼 -> AC 128 B
$5BBC  DEX / BNE $5BAE

$5C00  ST0 #$00 / ST1 #$00 / ST2 #$79  MAWR = $7900     ← 쓰기 주소
$5C08  LDA #$13 / STA $15              19 회
$5C0C  LDX #$00
$5C0E  LDA $1A00 / STA $5C2F,X / INX / CPX #$80 / BNE $5C0E
                                       ★ 128 B 를 한 바이트씩
$5C19  TIA $5C2F -> $0002, $0080       버퍼 -> VDC
$5C20  DEC $15 / BNE $5C0C
$5C24  LDA #$02 / STA $5C2E            상태 플래그
$5C29  STZ $5B80 / RTS
```

**★ 여기서 내린 진단 셋 중 둘은 다음 날 소스를 보고 틀린 것으로 밝혀졌다.
아래는 정정본이다.**

① **`$7900` 은 하드코딩이 아니다 — 나흘 묵은 빌드다.**
소스([build_subtitle_vram_helper.py](../../tools/build_subtitle_vram_helper.py))는
처음부터 `layout.PAT_VRAM` 을 따라간다.

```python
a.emit(0x03, 0x01, 0x13, layout.PAT_VRAM & 0xFF,
       0x23, layout.PAT_VRAM >> 8, 0x03, base.VDC_VWR)
```

```
build/cutscene_subs/subtitle_vram_helper.bin   2026-08-24 22:47   ← $7900 이 박힌 시점
tools/subtitle_layout.py                       2026-08-28 19:57   ← PAT_VRAM = $1600
```

**헬퍼만 다시 안 구웠다.**  그래서 실행 중인 바이너리가 `ST2 #$79` 를 들고 있다.
"설계가 죽었다" 가 아니라 "빌드가 낡았다" 다.  고치는 법은 제거가 아니라 재빌드다.

② **복원의 바이트 루프는 하드웨어 제약이다 — 게으름이 아니다.**
소스에 이유가 적혀 있다: `# TAI $1A00은 금지. 고정 포트 LDA로 128 B를 stage에 읽는다.`

HuC6280 블록 전송은 다섯뿐이다 --
`TII(증가,증가) · TDD(감소,감소) · TIN(증가,고정) · TIA(증가,교대) · TAI(교대,증가)`.
**"고정 소스 -> 증가 목적지" 가 없다.**  AC 데이터 포트는 고정 주소이므로
`AC -> RAM` 방향은 블록 전송이 **원리적으로 불가능**하다.
(저장 방향은 `TAI VDC -> stage` + `TIN stage -> AC` 로 둘 다 블록 전송이 된다.
비대칭인 것은 맞지만 그것이 정답이다.)

> 그러므로 "복원을 블록 전송으로 바꿔 134 -> 32 줄" 은 **불가능하다.**
> 복원 비용을 줄이는 길은 **백업/복원을 안 하는 것**뿐이고,
> 그러려면 아무도 안 쓰는 자리를 골라야 한다 -> §6 allocator.

③ **조각마다 도는 것**은 그대로 사실이다.  `command`/`status` 플래그가 헬퍼
이미지 안에 있고 스텁이 조각마다 320 B 를 AC 에서 다시 복사한다.
(다만 0.5.7 관측에 따르면 디스크 선적재는 헬퍼 이미지를 되돌리지 않는다.)

### 2-4. ★ 그런데 그 루프는 번쩍임의 원인이 **아니었다** (0.5.7)

죽은 백업/복원을 끄고 A/B 를 봤다.  두 번 시도했다.

**0.5.6 (실패) — 건너뛰기는 게임을 멈춘다.**
진입부를 꼬리 `$5C29` 로 점프시켜 두 루프를 통째로 건너뛰었더니 **화면이 멈췄다.**
`$5C29` 는 `STZ $5B80 / RTS` 라서 그 앞의 `LDA #$02 / STA $5C2E`(상태 플래그)를
건너뛴다.  스텁이 그 플래그를 기다리면 영영 안 온다.
**교훈: 이 상주부는 상태 기계다.  경로를 건너뛰면 안 되고 양만 줄여야 한다.**

**0.5.7 (성립) — 횟수만 19 -> 1.**
흐름과 플래그를 하나도 안 건드리고 반복 횟수만 줄였다.

```
$5BAC  +$02C  A2 13  LDX #$13  ->  A2 01     백업 19 -> 1
$5C08  +$088  A9 13  LDA #$13  ->  A9 01     복원 19 -> 1
```

AC 이미지(`$1F1C2D` · `$1F1C89`) 2 바이트다.  결과:

```
멈춤 없음 · 음성 18 개 · 자막 정상 (WIPE 칸 수가 글자 수대로)
번쩍임 = 그대로
```

전송량이 1/19 이 됐는데 증상이 안 변했다.  **이 루프는 번쩍임의 원인이 아니다.**

> ⚠ **`19 -> 1` 은 처방이 아니다.  성능 A/B 용 도구다.**
> 자막 VRAM 은 19 글리프분(`$4C0` word)이고, 그 영역 **전체**를 보존하려면
> 19 블록을 다 돌아야 한다.  1 로 줄이면 128 B 만 지켜지고 나머지 18 글리프
> 영역은 보호가 안 된다.  `0.5.7` 을 그대로 두고 쓰면 안 된다.
>
> **정석은 블록 수 19 를 유지하고 실행 빈도를 바꾸는 것이다** (§6-5).

**부수 관측:** 패치가 `#1`/`#2` 이후 다시 안 찍혔다 -> 디스크 선적재는
**헬퍼 이미지($1F1C00)는 안 되돌린다.**  렌더러 슬롯($1F1F00)은 음성마다 되돌려
`AC install #2~#19` 가 계속 찍히는 것과 대조된다.  실제 수정 때 쓸 수 있는 비대칭이다.

### 2-5. ⚠ 여기까지의 측정은 전부 열쇠구멍이었다

`0.5.2`~`0.5.7` 은 **`$5B80-$5E1F` 쓰기만** 봤다.  분기가 그 밖에서 하는 일은
한 번도 안 쟀다 -- VDC 쓰기, AC 셋업, SATB 조작, 그리고 `$7FC3` 처럼
`STUB_BYTES(32 B · $7FA0-$7FBF)` **밖**에서 도는 상주 코드.

그러므로 "분기 안에 무엇이 남았나" 를 쓰기 주소로 더 좁히는 것은 한계에 왔다.
다음은 **"CPU 가 얼마나 오래, 어느 코드에 있는가"** 를 재야 한다.
[0.5.8](../../lua/SUB/0.5.8-branch-duration.lua) 을 그렇게 만들어 뒀다 (미실행).

## 3. 측정으로 죽인 가설들 — 근거

### 3-1. BAT 본체 침범 (기각)

[0.4.90](../../lua/SUB/0.4.90-bat-overlap.lua) 실측.  국장실에서:

```
BAT 64x64 = 4096 word -> 0..$0FFF      SATB $1000-$10FF
글리프 $1600-$1ABF                      -> bat-clear
```

프로브가 장면마다 32x32 · 128x32 · 64x64 를 정확히 따라갔고 `portHits` 가
수십만이었다.  **못 재서 clear 가 아니라 진짜 clear 다.**

### 3-2. BG 패턴 침범 (기각)

[0.4.91](../../lua/SUB/0.4.91-bg-pattern-overlap.lua) 은 BAT 엔트리가
**가리키는 타일의 그림 데이터**(`tile * 16 word`)가 글리프 블록과 겹치는지 센다.

```
다른 장면들   겹침 165 / 78 / 45 엔트리   <- 검출 능력 증명
국장실 단독   겹침 0/4096 · 3360 프레임    <- 음성 결과
```

배경 그림 데이터는 `$1100` 에서 시작해 그림 크기만큼 위로 자란다.  그래서
`$1600` 은 **일부 장면에서 실제로 남의 자리다** -- 다만 국장실은 아니다.
이건 별도로 남은 문제다 (§6).

> `tile_hi = $7FFF / $7FDF` 는 초기화 안 된 BAT 엔트리(`$FFFF & 0x7FF`)다.
> 무시해야 한다.  실제 배경이 뻗은 최대는 `$4ACF` 였다.

### 3-3. 래스터 분할 손실 — 신호는 있으나 판정 불가

[0.4.94](../../lua/SUB/0.4.94-raster-split-skip.lua) /
[0.4.95](../../lua/SUB/0.4.95-split-skip-control.lua) 실측:

```
idle  3278 프레임   BYR 최빈 4
first    9          BYR 최빈 3     <- 음성 첫 조각 프레임
later   13          BYR 최빈 4
miss     0          ★ 통제군 표본 없음
```

첫 조각 프레임에서 BYR·BXR·RCR·CR 이 **나란히 하나씩** 줄었다.  분할 하나가
어긋난 게 아니라 래스터 IRQ 한 회차가 통째로 안 돈 모습이다.  다만 그 프레임은
게임이 ADPCM 을 시작하는 프레임이기도 하다.  **MISS 표본이 0 이라 그 교란을
못 걷었다.**  이 신호는 살아 있고, §2-3 의 남은 질문과 이어진다.

## 4. ★ 0.4.87 이 두 번 실패한 진짜 이유 (고침)

## 6. ★ 별도 트랙 — `$1600` 고정은 전역 안전하지 않다.  allocator 를 되살린다

번쩍임과는 **별개 문제**다.  섞지 말 것.

### 6-1. 지금 말할 수 있는 것과 없는 것

```
정커 본부 · 국장실에서 잘 됨   =  그 장면들에서는 충돌이 없었다
게임 전체에서 안전            =  아직 미확인
```

`0.4.91` 이 **다른 장면에서 165 / 78 / 45 엔트리 겹침**을 실제로 찍었다.  배경
그림 데이터는 `$1100` 에서 시작해 그림 크기만큼 위로 자라고, 큰 그림에서는
`$1A00` 대까지 온다.  즉 `$1600-$1ABF` 는 전역적으로 비어 있는 자리가 아니다.

19:03 에 정한 "고정 `$1600`" 은 **정커 본부까지만 검증된 값**이었다.
`--pat-vram` 옵션과 `0.4.92`(=$7900 판)를 만들어 뒀으나 안 돌렸고, `$7900` 도
안전하다는 증거가 없다 (스프라이트 패턴을 아직 안 봤다).

**중요:** 백업/복원을 `$1600` 에 맞춰 완벽하게 고쳐도 이 문제는 안 풀린다.
원래 게임이 그 영역을 쓰는 장면에서는 정상 데이터를 백업했다가 자막 동안
덮어버리는 것이 그대로 남는다.  자리를 옮겨야 풀린다.

### 6-2. 채택한 설계 — "음성당 1회" allocator

예전 allocator 를 그대로 부활시키지 않는다.  조각마다 고르기 · ping-pong 은
타이밍 비용과 복잡성만 키운다 (ping-pong 은 이미 실측으로 배제됐다).

```
음성 시작
  └ 1회  안전 슬롯 결정   현재 화면의 BG 패턴(BAT) + 스프라이트 패턴(SATB) 을 보고
  │                      19 글자분 $4C0 word 가 연속으로 비는 곳을 고른다
  └ 1회  그 자리 백업
  ├ 조각 1 렌더          모든 조각이 같은 주소를 쓴다
  ├ 조각 2 렌더
  ├ 조각 N 렌더
음성 종료
  └ 1회  복원
```

> "조각" = 한 음성 안에서 시간에 따라 바뀌는 여러 자막 파트.
> (예: 6 초 음성 = 0~2 초 1파트 · 2~4 초 2파트 · 4~6 초 3파트)
> allocator · 백업 · 복원은 **파트마다가 아니라 음성 전체 기준 1 회**다.

### 6-3. BAT 만 보면 부족하다

`0.4.91` 은 BAT 가 가리키는 BG 타일만 봤다.  **게임 스프라이트 패턴도 같은
VRAM 에 있다.**  SATB 가 참조하는 패턴 영역까지 피해야 진짜 안전 슬롯이다.
(`VRAM-key-map-0.2` 는 이미 BAT 본체 · BG 패턴 · SATB 본체 · 스프라이트 패턴을
모두 점유로 치는 모델을 갖고 있다.  그 모델을 런타임 1 회용으로 줄이면 된다.)

### 6-4. 왜 allocator 가 **유일한** 비용 절감 길인가

§2-3(6)② 에서 확인했듯 `AC -> RAM` 복원은 블록 전송이 **원리적으로 불가능**하다
(고정 소스 -> 증가 목적지 opcode 가 없다).  그러므로:

```
백업/복원을 유지하는 한   2,432 B 바이트 루프 ≈ 107~134 줄은 못 줄인다
                          (조각마다 -> 음성당 1 회로 줄이는 것이 최선)
백업/복원을 없애면        0 줄
                          단 아무도 안 쓰는 자리를 골라야만 없앨 수 있다
```

즉 allocator 는 "안전성" 만이 아니라 **비용 문제의 유일한 해법**이기도 하다.
안전 슬롯을 고르면 백업/복원 자체가 필요 없어지고, 헬퍼의 그 경로를 통째로
들어낼 수 있다.

그 전까지의 중간 상태는 **재빌드**다 (§2-3(6)①).  재빌드하면 백업/복원이
비로소 `$1600` 을 대상으로 하여 **실제로 동작한다** -- 지금은 엉뚱한 자리를
지키느라 `$1600` 을 쓰는 장면에서 배경이 안 돌아온다.

### 6-5. ★ 블록 수 19 는 유지한다.  바꿀 것은 **실행 빈도**다

```
지금        조각 시작 -> 19 회 백업 -> 표시 -> 19 회 복원
            다음 조각 -> 또 19 회 백업 -> 또 19 회 복원

정석        음성 시작 -> 19 회 백업  딱 1 번
            자막 1 / 2 / 3 조각이 같은 자리를 계속 쓴다
            음성 끝   -> 19 회 복원  딱 1 번
```

19 는 자막 VRAM 전체(`$4C0` word = 19 글리프분)를 덮는 **필요한 수**다.
줄이면 나머지가 보호되지 않는다.  `0.5.7` 의 `19 -> 1` 은 성능 A/B 도구였지
처방이 아니다 (§2-4).

**실측된 현재 동작** (0.5.4 / 0.5.5):

```
첫 조각    320 B 복사 + 19x128 (save 루프 · PC $5BB5) + 671 B 복사
이후 조각  320 B 복사 + 19x128 (restore 루프 · PC $5C14)
```

즉 조각 전환마다 **복원**이 돌고 있다.  조각당 한 번씩 원래 화면을 되돌린 뒤
다음 조각 글리프를 다시 올리는 셈이다.  음성당 1 회 구조로 바꾸면 이 왕복이
조각 수만큼 사라진다 (관측된 음성은 1~4 조각).

> 확인해야 할 것: 조각 사이 복원에 **기능적으로 의존하는 것이 있는지**.
> 이전 조각 글리프를 지우는 용도라면 이미 `0.4.48` 와이프가 SATB 슬롯을
> 지우고 있어 VRAM 내용 자체를 되돌릴 필요는 없어 보인다.  다만 확인 전에는
> 단정하지 말 것.

restore  $5C00  ST0 #$00 / ST1 #$00 / ST2 #$16   MAWR = $1600
         $5BAC  LDX #$13      $5C08  LDA #$13     (19 회 유지)
```

### ★ 재빌드가 드러낸 것 — 잠복 버그와 그 원인 (2026-08-30)

주소를 고치자 **복원이 처음으로 실제 동작**했고, 그 즉시 새 증상이 보였다:
대사 종료/조각 전환에 **1 프레임짜리 깨진 화면**이 대사 자리에 떴다.
`$7900` 을 되돌리던 동안에는 아무도 안 보는 자리라 이 결함이 숨어 있었다.

#### (1) 왕복은 무손실이다 — 복원 자체는 정상 (0.5.9)

[0.5.9](../../lua/SUB/0.5.9-backup-roundtrip.lua) 가 백업 직전과 복원 완료 후의
`$1600-$1ABF` 2,432 B 를 통째로 비교했다.

```
6/6 음성   다른 워드 0/1216      -> 왕복 무손실
           백업 비영 899/1216    -> 6 회 내내 **동일**
```

즉 "복원이 틀렸다" 는 기각이다.  그리고 **비영 899 가 매번 같다**는 것은
`$1600-$1ABF` 가 실제로 쓰이는 자리라는 직접 증거다.
`$7900` 때처럼 "아무도 안 쓰는 자리" 가 아니다 --
**백업/복원은 이제 진짜 필요한 기능이다.**

#### (2) 원인은 순서였다 (0.5.10)

우리 자막 스프라이트 19 개는 패턴 소스로 `$1600` 을 가리킨다.  그런데 헬퍼의
복원은 **표시 구간 한복판(line 34~168)** 에서 그 자리에 원본을 덮어쓴다.
그 사이 SATB 의 옛 스프라이트는 여전히 `$1600` 을 가리키므로,
그 프레임에 스프라이트가 **복원 중인(글리프가 아닌) 데이터를 글자로 그린다.**

[0.5.10](../../lua/SUB/0.5.10-wipe-before-restore.lua) 이 복원 진입점 `$5BE4` 에서
그 슬롯들을 **먼저** 지우자 증상이 사라졌다.  로그가 객관적으로 뒷받침한다:

```
이전   END WIPE #2: VRAM SATB 9칸 · Sprite RAM 9칸
지금   END WIPE #2: VRAM SATB 0칸 · Sprite RAM 0칸     6/6 음성 전부 0
```

우리가 더 일찍 지웠으므로 뒤따르는 END WIPE 에 지울 것이 남지 않았다.
**같은 슬롯 · 더 이른 시점 = 증상 소멸.**  순서 문제 확정이다.

#### (3) 그래서 출하 설계에 조건이 둘 붙는다

```
① 복원은 조각마다가 아니라 음성 끝에 1 회      (§6-5)
   -> 2~4 조각 음성에서 중간 노출 자체가 사라진다
② 그 복원 직전에 우리 SATB/Sprite 슬롯을 먼저 비운다
   -> 마지막 1 회에서도 스프라이트가 복원 중인 데이터를 그리지 않는다
```

①만으로는 부족하다.  마지막 복원 한 번이 남기 때문이다.

#### (4) 정식 코드에서 손댈 자리 — 상주 컨트롤러

구조를 확인했다.  순서를 정하는 것은 헬퍼가 아니라 **상주 컨트롤러**다.

```
위치    RAM $7F49-$7FDF (151 B).  디스크 페이로드가 아니라 BIOS 케이브 체인에서 만들어진다
        (payloads() 는 translation / pack / helper / renderer 넷뿐이다)
소스    tools/build_subtitle_resident_controller_poc.py  (ORIGIN $7F49)
        + build_subtitle_resident_native_poll_0_8_3.py 의 build()
실측    0.5.5 의 PC $7FAA · $7FC3 이 이 안이다
```

상태 기계:

```
JSR $FEC4                            BIOS 판정
BEQ done / CMP #$02 / BEQ run
JSR select_helper / JSR copy_helper  ← 헬퍼를 매번 새로 복사 (command 가 0 으로 초기화된다)
LDA state / CMP #$01 / BNE restore
    JSR ENTRY (command 0 -> 저장) / JSR copy_renderer / INC state
restore:
    STZ state / INC $5C2D (command -> 1 = 복원) / JSR ENTRY
run:
    JSR ENTRY                        ← 렌더러 실행
```

**넣을 자리는 `restore:` 의 `INC $5C2D` 앞이다.**  거기서 우리 SATB/Sprite 슬롯을
비우면 0.5.10 이 한 일이 정식 코드가 된다.  빈도(§6-5)를 바꾸는 것도 같은
상태 기계의 문제다 -- `state` 전이를 조각 단위에서 음성 단위로 옮기면 된다.

> `copy_fixed` 도 바이트 루프다.  AC 포트가 고정 소스라 여기서도 블록 전송이
> 불가능하기 때문이다 (§2-3(6)② 와 같은 이유).  320 B · 671 B 복사 비용의 근거다.

> ⚠ 구현 제약: 헬퍼는 **303 B / 슬롯 320 B** 라 여유가 **17 B** 뿐이다.
> SATB 64 슬롯을 조건부로 훑어 지우는 코드는 그보다 크다.  선택지는
> (a) `HELPER_SLOT_BYTES` 를 늘린다 (상주부 `copy_fixed` 크기도 따라간다)
> (b) 컨트롤러/렌더러 쪽에서 순서를 만든다 (빈 자막을 한 번 그려 슬롯을 비우는
>     방식 -- 0.4.6.15 의 "empty-render separator" 가 이 계열로 보인다)
> 어느 쪽인지는 아직 안 정했다.

### (5) SATB 주소를 어디서 얻나 — DVSSR 조사 (2026-08-30)

복원 직전에 우리 슬롯을 비우려면 헬퍼가 SATB 주소를 알아야 한다.  그런데
**VDC 레지스터는 되읽기가 안 되고**, 헬퍼는 매번 AC 에서 새로 복사되므로
스스로 기억할 수도 없다.  `$1000` 하드코딩은 `0.4.90` 이 `$0700` 도 본 적이
있어 위험하다.

[0.5.12](../../lua/SUB/0.5.12-dvssr-writer.lua) 로 DVSSR($13) 을 쓰는 코드의
PC 를 잡았다.  **write site 는 둘뿐이다.**

```
PC $E418 / $E41E   DVSSR = $0700    x1        BIOS.  부팅 때 한 번
PC $42EF / $42F1   DVSSR = $1000    x6527     게임 코드.  매 프레임
```

#### BIOS 경로 — RAM 변수를 거친다

파일 오프셋 = `cpu - $E000` 으로 BIOS 를 뜯었다.

```
$E40C  A9 13        LDA #$13
$E40E  85 F7        STA $F7
$E410  8D 00 00     STA $0000        ; 레지스터 $13 = DVSSR 선택
$E413  AD 14 22     LDA $2214        ; ★ RAM 에서 읽는다
$E416  8D 02 00     STA $0002
$E419  AD 15 22     LDA $2215        ; ★ RAM
$E41C  8D 03 00     STA $0003
$E41F  60           RTS
```

**`$2214`/`$2215` 가 SATB 주소를 담은 BIOS 워크 RAM 변수다.**

#### 게임 경로 — 즉치다.  RAM 을 안 거친다

PC 보정(+2)을 적용하면 보고 `$42EF`/`$42F1` -> 시작 `$42ED`/`$42EF` 로
**2 바이트 간격**이다.  3 바이트 `STA abs` 두 개는 들어갈 수 없다.
`ST1 #$00` / `ST2 #$10` (각 2 바이트) 다.

그러므로 **매 프레임 도는 게임 경로는 `$2214/$2215` 를 갱신하지 않는다.**
그 변수가 부팅 값 `$0700` 에 머물러 있으면 실제 DVSSR(`$1000`)과 어긋난다.

#### 다음 판정

[0.5.13](../../lua/SUB/0.5.13-satb-shadow-check.lua) 이 매 프레임 `$2214/$2215`
와 실제 DVSSR 을 비교한다.

```
불일치 0      $2214/$2215 가 진짜 shadow 다.  헬퍼가 LDA 두 번(6 B)이면 끝.
              디스크 패치도 필요 없다
불일치 발생   게임 즉치 경로가 BIOS shadow 를 우회하는 것이 확정.
              -> 게임 write site($42ED/$42EF)를 패치해 즉치를 RAM 에도 남긴다
              -> 그때는 $42ED 가 어느 뱅크인지 먼저 잡아야 한다 (MPR2 캡처)
```

> 채택 순위 (사용자 결정):
> **1** 헬퍼가 읽을 shadow 확보 · **2** `$1000` 일 때만 wipe (임시 진단판 한정) ·
> **비추천** `$1000` 하드코딩.

### 이제 확인할 것 (베이스라인)

```

```

$7F5B  JSR $7FA2              copy_helper    448 B 바이트 복사
$7F5E  LDA $5B80 / CMP #$53   매직 검사
$7F65  LDA $7FDF / CMP #$01   state
$7F6C  JSR $5B83              helper (저장)
$7F6F  JSR $7FBB              copy_renderer  671 B 바이트 복사
$7F72  INC $7FDF / BRA done
$7F77  STZ $7FDF / INC $5D30  ← control block command (오늘 넣은 것이 보인다)
$7F7D  JSR $5B83              helper (복원)
$7F82  JSR $5B83              renderer 실행
$7F85  PLP                    ★ 여기서야 푼다
$7F86  RTS
```

0.5.8 이 잰 그 안의 무게:

```
자막 시작 프레임   복사 ≈ 43 스캔라인
조각 렌더 프레임   복원 + 렌더 ≈ 121 스캔라인
```

즉 래스터 분할 IRQ 가 수십~백 줄 동안 못 뜬다.  그림 창의 스크롤 전환이
통째로 밀리면 타일맵 위쪽이 화면으로 끌려나온다 -- 증상과 같은 모습이다.

### 검증 (0.5.16)

`$7F4A` 의 `SEI`($78) 한 바이트를 `NOP`($EA) 으로 덮었다.  PHP/PLP 는 그대로라
플래그 균형은 유지된다.

**결과: 뒷화면 소환과 떨림이 **둘 다** 사라졌다.**

> ✅ **2026-08-30 재확인.**  깨끗한 Power Cycle 뒤 이 판만 올려 다시 확인했다.
> 교차 오염 가드에도 걸리지 않았다.  **"완벽히 정상."**
> (첫 관측이 오염이었을 가능성을 배제하기 위한 재실험이다 -- §2-4 참조.)

즉 두 증상은 원인이 다른 게 아니라 **같은 원인의 다른 발현**이었다 (§1-1 정정).

```
떨림      차단 시간이 프레임마다 글자 수에 따라 흔들린다 -> 분할선이 떨린다
번쩍임    자막 시작 프레임엔 고정 비용(복사)만으로도 분할을 통째로 놓친다
```

한 글자 엔진(0.4.87)이 떨림만 줄이고 번쩍임은 못 줄였던 것도 이것으로 풀린다 --
루프는 1/19 이 됐지만 고정 비용(복사 43 줄)은 그대로였으므로 시작 프레임의
놓침이 남았다.

### 이것이 지금까지의 모든 실패를 한 번에 설명한다

```
0.5.1  entry=RTS      복사가 SEI 안에서 그대로 돎        -> 남음  ✓
0.5.7  복원 19->1     마찬가지                            -> 남음  ✓
0.4.89 VDC 재무장     SEI 창 **안쪽** 세부사항일 뿐        -> 남음  ✓
0.5.0  팔레트         같은 창 안                          -> 남음  ✓
0.4.97 와이프         같은 창 안                          -> 남음  ✓
0.4.90/0.4.91  BAT/BG  애초에 자리 문제가 아니었다         -> 무관  ✓
```

**범인은 특정 작업이 아니라 창 자체였다.**  그래서 창 안쪽을 아무리 바꿔도
증상이 안 변했던 것이다.

> ⚠ `SEI -> NOP` 은 **진단이지 수정이 아니다.**  SEI 는 이유가 있어 있다
> (상태 기계 · AC 포트 접근의 원자성).  출하 수정은 창을 **쪼개거나 옮기는** 것이지
> 그냥 푸는 것이 아니다.

### 다음 — 창을 얼마나 줄여야 하는가

[0.5.17](../../lua/SUB/0.5.17-offload-copies.lua) 이 그것을 잰다.  상주부의
바이트 복사를 Lua 로 옮겨 **비용만** 없앤다 (Lua 쓰기는 에뮬레이션 사이클을
안 먹으므로 상태는 동일하고 시간만 0 이 된다).

```
SUB_OFFLOAD = 'both'(기본) · 'helper' · 'renderer'

복사만 빼도 사라지면   43 줄만 줄이면 된다 -> 수정이 쉬워진다
그대로면               복원+렌더 121 줄까지 손대야 한다
```

### 0.5.17 결과 (2026-08-30) — ★ 철회.  오염된 관측이었다

처음 관측: "번쩍임 사라짐 · 떨림은 시작에 한 번만".  **이 결과는 철회한다.**

**Mesen 은 스크립트를 다시 로드해도 RAM 을 초기화하지 않는다.**
`0.5.16`(SEI -> NOP)을 돌린 뒤 파워사이클 없이 `0.5.17` 을 올리면
`$7F4A` 는 **여전히 NOP 인 채로 남는다.**  그 상태에서 본 "사라짐" 은
`0.5.17` 이 아니라 남아 있던 `0.5.16` 패치의 효과다.

깨끗한 Power Cycle 뒤 `0.5.17` 만 올리자 **번쩍임이 돌아왔다.**

```
0.5.17 (복사만 이관, SEI 정상)   번쩍임 남음
```

**즉 복사 43 줄을 빼는 것만으로는 부족하다.**  창 안에 남은 일
(helper save/restore · 렌더)이 여전히 분할을 놓치게 만든다.

### 세 판을 나란히 놓으면 (전부 깨끗한 Power Cycle)

```
0.5.16  SEI 전체 off                    -> 둘 다 소멸.  "완벽히 정상"
0.5.17  복사만 Lua 로 이관               -> 남음
0.5.18  복사 이관 + save/restore 건너뜀   -> 남음   (창에 **렌더만** 남음)
```

`0.5.18` 은 §6 allocator 이후의 세계를 미리 만든 것이다 -- 백업/복원이 사라지고
복사도 없는 상태.  그래도 증상이 남았다.

### ★★ 그러므로 문제는 "길이" 가 아니라 "위치" 다

렌더만 남으면 창은 0.5.8 산술로 **~15 스캔라인**뿐이다 (engine 13,859 중
복원 루프 12,160 을 뺀 나머지).  그런데도 증상이 난다.

```
15 줄짜리 차단으로도 분할을 놓친다
-> 총 시간이 문제가 아니라 **차단 구간이 분할선을 덮느냐**가 문제다
-> 짧게 만드는 것만으로는 못 고친다.  IRQ 를 막지 않거나, 막아도 되는 때에 해야 한다
```

이것이 `0.5.16`(SEI 전체 off)만 유일하게 깨끗했던 이유다.  IRQ 가 살아 있으면
무슨 일을 하든 분할이 제때 뜬다.

### 로드맵 수정

**§6 allocator + 복사 수정으로는 부족하다.**  그 둘을 다 해도 렌더가 남는다.

```
필요한 것
  · 렌더를 IRQ 차단 밖으로 빼거나 (CLI 구간을 두거나)
  · 분할이 없는 때 -- VBlank -- 에 하거나
  · 차단 구간이 분할선을 안 덮게 배치한다

그러려면 먼저 알아야 할 것
  · **분할선이 몇 번째 스캔라인인가** (RCR 값).  아직 안 쟀다
  · 게이트는 line 21~25 에 불린다 (0.5.8).  렌더 ~15 줄이면 차단은 대략 21~40
  · 그 구간이 분할선을 덮는지 숫자로 확인되면 "얼마나 옮겨야 하는지" 가 나온다
```

> ★ 교훈: **RAM 패치 실험은 반드시 Power Cycle 로 시작한다.**
> 스크립트 교체만으로는 이전 판의 RAM 패치가 남는다.
> 이 프로젝트에서 세이브스테이트/리로드가 실험을 깬 것은 이번이 두 번째다
> (`0.4.93` 의 MWR 미관측이 첫 번째).
>
> ⚠ 같은 이유로 **§7-E 의 0.5.16 결과도 깨끗한 Power Cycle 에서 재확인해야 한다.**
> 그 판정이 지금 모든 결론의 토대다.

### ⚠ 수정의 제약 — 상주부에 넣을 공간이 없다

복사 구간만 IRQ 를 풀려면 `CLI` / `SEI` 를 넣어야 하는데 **상주부는 151/151 로
여유 0** 이다 (§2-3(4)).  `SEI` 를 뒤로 옮기는 것도 그 자리에 여유가 없다.

```
$7F49 PHP / $7F4A SEI / $7F4F JSR $FEC4 / ... / $7F5B JSR copy_helper / $7F5E LDA $5B80
```

선택지:
- 상주부를 줄인다 (copy_fixed 를 더 짧게 쓸 방법이 있는가)
- 복사 자체를 없앤다 -- 헬퍼/렌더러를 매번 옮기지 않고 상주시킨다
  (음성 중 게임이 `$5B80` 을 안 쓰는 것은 0.5.3 으로 확인됐다)
- 창을 옮긴다 -- 게이트 처리를 VBlank 로

**두 번째가 가장 근본적이다.**  조각마다 991 B 를 다시 옮기는 구조 자체가
없어지면 복사 43 줄이 통째로 사라진다.

이 답에 따라 출하 수정이 갈린다:

```
① 복사 구간만 IRQ 를 푼다 (PHP/CLI ... PLP 를 구간별로 쪼갠다)
② 무거운 이동을 VBlank 로 옮긴다
③ 복원 빈도를 음성당 1 회로 (§6-5) -- 121 줄이 조각마다에서 음성당으로
```

## 7-F. ★ 분할선 실측과 지표 발견 (0.5.19 · 2026-08-30)

### 국장실의 래스터 분할 구조

```
화면줄 7     (RCR 예약 시점: 줄 250 -- 전 프레임 VBlank)
화면줄 135   (예약 시점: 줄 32~39 이 정상)
화면줄 148   (예약 시점: 줄 160)
게이트 진입  줄 21~26
```

`화면줄 = RCR - 64`.

### ★★ 지표 -- `RCR=135` 의 **예약 시점**

값은 늘 135 로 같은데 **언제 예약되는지가 크게 흔들린다.**

```
정상   135(줄32) · 135(줄39)
밀림   135(줄72) · 135(줄91) · 135(줄143) · 135(줄145)
심함   135(줄185) · 135(줄195) · 135(줄197) · 135(줄199)   <- 이미 135 를 지난 뒤
```

그리고 심하게 밀린 프레임은 예약이 **3 개가 아니라 2 개**다 -- `148` 이 통째로 빠진다.

```
135(줄32)  148(줄160)  7(줄250)      정상 3 개
135(줄197)             7(줄250)      밀림 2 개.  148 소실
```

밀린 프레임들이 `MATCH` / `PATCHED` 근처에 몰린다.

### 메커니즘이 숫자로 닫혔다

```
IRQ 차단 -> RCR=135 를 프로그램하는 핸들러가 늦게 돈다
        -> 줄 135 를 이미 지난 뒤 예약하면 그 분할이 그 프레임에 안 뜬다
        -> 그림 창 스크롤 전환이 빠진다        = 뒷화면 소환
        -> 밀리는 정도가 프레임마다 다르다      = 떨림
```

**두 증상이 하나의 지표로 설명된다.**  그리고 이 지표는 **눈이 아니라 숫자로**
판정할 수 있다 -- 앞으로의 수정은 "`RCR=135` 예약이 줄 135 이전에 끝나는가" 로
검증하면 된다.

### ⚠ 아직 안 맞는 것 (미확인)

게이트가 줄 21~26 에 끝나면 줄 135 까지 **109 줄 여유**가 있다.
렌더 15 줄로는 143 까지 밀릴 수 없다.  즉 `RCR=135` 를 쓰는 핸들러가
게이트 직후에 도는 것이 아니라 **다른 무언가에 연쇄로 물려 있다**
(예: 줄 7 분할 핸들러가 그것을 예약하는데 그 핸들러 자체가 밀리는 구조).

**이것은 추측이다.**  다음 측정으로 `RCR` 을 쓰는 코드의 PC 를 잡으면 연쇄가
드러난다 (`0.5.12` 가 DVSSR 쓰기 PC 를 잡은 것과 같은 방법).
PC 보정(+2)을 잊지 말 것 -- §8.

## 7-G. ★★ 법칙 확정 -- 창이 닫히는 줄 + 1 (0.5.20 · 2026-08-30)

### 측정

`RCR` 쓰기의 PC 와 SEI 창(`$7F49` PHP ~ `$7F85` PLP)의 진입/이탈 스캔라인을
같은 프레임에서 붙였다.  국장실, 파워사이클, 0.5.20 단독.

```
창[13..184]  ->  135 을 줄185 에      184 + 1
창[14..134]  ->  135 을 줄135 에      134 + 1
창[17..95]   ->  135 을 줄95  에      (95)
창[22..85]   ->  135 을 줄86  에       85 + 1
창[24..198]  ->  135 을 줄199 에      198 + 1
창[23..196]  ->  135 을 줄197 에      196 + 1
창[22..142]  ->  135 을 줄143 에      142 + 1
```

**표본 18, 예외 0.**

```
    RCR=135 이 쓰이는 줄  =  창이 닫히는 줄 + 1
```

래스터 IRQ 가 창 동안 **계류**했다가 `PLP` 로 I 가 풀리는 순간 터진다.
그리고 `RCR` 은 비교 레지스터가 **하나뿐**이라 분할이 반드시 연쇄다
(7 -> 135 -> 148 -> 7).  하나가 밀리면 뒤가 전부 밀린다.
그래서 "미리 예약해 두기" 같은 우회는 **불가능**하다.

### writer 는 공용 리프 루틴이었다

`$E3EC-$E4AC` 는 VDC 레지스터 접근 라이브러리다.  전부 `$F7` 을 선택 섀도우로 쓴다.

```
$E40B  set_DVSSR   LDA #$13 -> $2214/$2215      <- 0.5.12 가 찾은 것과 동일
$E41F  set_RCR     PHA/LDA #$06/STA $F7/STA $0000/PLA/STA $0002/STX $0003/RTS
                   ★ A = RCR 하위 · X = RCR 상위
$E42F  set_MARR    + 끝에 VWR($02) 선택
$E446  set_MAWR    + 끝에 VWR($02) 선택
$E45D  set_DMA     $10 SOUR / $11 DESR / $12 LENR  ($F7 저장·복원 있음)
```

`$E42B` 의 `STX $0003` 이 우리가 잡은 지점이다 (PC 보정 2 -> 실제 3, 1 빗나감).
**리프 루틴이라 호출자는 안 나온다.**  그러나 위 법칙으로 인과가 이미 닫혔으므로
호출자 추적은 불필요하다.

★ `$E41F` 는 **선택 레지스터를 복원하지 않는다.**  IRQ 가 지나가면 VDC 선택 래치가
`$06`(RCR) 로 남는다.  이것이 렌더 중 IRQ 를 막아야 했던 이유다 -- 7-H 참조.

### 창 폭을 국면별로 (실측)

```
idle             0~1 줄     -> 끝 22       안전
조각 렌더        63~95 줄   -> 끝 85~95    안전
음성 시작       120 줄      -> 끝 142      ★ 135 놓침
음성 끝/복원    171~174 줄  -> 끝 196      ★ 135 · 148 둘 다 놓침
```

증상이 **대사 시작과 끝**에 나온다는 관찰과 정확히 맞는다.
그리고 조각 렌더 프레임(63~95)은 3 개 예약이 온전하다 -- 안 놓친다.

### ⚠ 이전 추정 정정

§7-F 의 "렌더 ~15 줄" 은 **틀렸다** (0.5.8 산술을 잘못 옮긴 것).
실측은 63~174 줄이다.  0.5.18(렌더만 남김)이 실패한 이유가 이것으로 설명된다 --
렌더만으로도 113 줄을 넘는다.

### 남은 여유 (산술)

```
줄 7 -> 135      128 줄    (창 시작이 22 이므로 실제 가용 113)
줄 135 -> 148     13 줄
줄 148 -> 7      121 줄
```

**120 줄 창은 어느 틈에도 간신히다.  171 줄은 아예 안 들어간다.**
따라서 "창을 통째로 옮기기" 로는 못 고친다.  창을 **쪼개거나 줄여야** 한다.

  POC 엔진으로 돈다.  로그의 `engine ___ B` 가 653(또는 631)이 아니면 잘못 로드다.
- `0.5.1`(entry=RTS)에서 **`STAGE REARM` 이 안 찍히는 것은 정상이다.**
  재무장은 stage 가 글리프 데이터로 덮였을 때만 다시 쓴다.  전송이 없으면
  덮이지 않으므로 조용히 넘어간다.  성립 조건은 **`PATCHED` 가 안 찍히는 것** 하나다.
- `0.4.93` 에서 `BAT 0x0 · unknown` 이 나오면 판정 불가다.  MWR($09)은 화면 모드가
  바뀔 때만 쓰이므로 세이브스테이트로 장면에 바로 들어가면 못 본다.
  (`emu.getState()` 폴백을 넣어 고쳤다.  출처를 `(mwr)/(state)` 로 같이 찍는다.)
- `0.4.95` 는 `miss:0` 이면 판정하지 말 것.
- `0.4.48` 의 `forceRenderer` 는 631 B 기준 오프셋(+144/+146/+255/+260)을
  하드코딩한다.  재무장 엔진에서 켜면 `glyph_loop` 코드를 부순다.
  `0.4.89` · `0.4.92` · `0.5.x` 진입점에 assert 로 막아 두었다.
- **상주 헬퍼는 상태 기계다.  경로를 건너뛰면 안 된다.**  `0.5.6` 이 진입부를
  꼬리로 점프시켰다가 `LDA #$02 / STA $5C2E`(상태 플래그)를 빠뜨려 게임이 멈췄다.
  손대야 한다면 **양만 줄여라** (`0.5.7` 처럼 반복 횟수 변경).
- **지문 판정의 기준값을 엔진 판별에 재사용하지 말 것.**  `A9 01 EA` 는
  **한 글자 엔진**의 +$6D 서명이다.  `entry=RTS` 엔진은 **offset 3** 만 다르다.
  `0.5.5` 가 이 때문에 "우리 것이 아니다" 오경보를 냈다.
  재무장 엔진의 +$6D 는 `AD 4E 5D` 이고 그것이 정상이다.
- ★ **Mesen 이 보고하는 PC 는 명령 시작 + 2 다.**  trace 로 잡은 PC 를 그대로
  디스어셈 주소로 쓰면 2 바이트씩 밀린다.  BIOS 로 보정을 확인했다:

```
$E416  8D 02 00  STA $0002   ->  보고된 PC $E418   (시작 + 2)
$E41C  8D 03 00  STA $0003   ->  보고된 PC $E41E   (시작 + 2)
```

  이 보정을 쓰면 명령 길이도 역산된다.  보고 PC 두 개가 **2 바이트 간격**이면
  3 바이트 `STA abs` 가 아니라 2 바이트 `ST1/ST2 #imm` 이다 (게임의 $42ED/$42EF).
- 실험 Lua 는 Power Cycle 뒤 한 파일만 로드한다.

## 9. 확정: CD-DA 자막 직접 경로와 HQ 체인 통합 (2026-08-30)

### 판정

트랙 17 오프닝(`c17_001.wav`)에서 아래 항목을 실제 화면으로 모두 통과했다.

```
CD-DA 현재 sector 감지        PASS
섹터 -> 트랙/시간 변환       PASS
Galmuri 글리프 -> VRAM        PASS
SATB 슬롯 0 삽입              PASS
팔레트 15 흰 글자/검은 외곽   PASS
하단 중앙 위치(y=192)         PASS
기존 한국어 UI 보존            PASS
```

직접 렌더의 SATB 경로는 CD-DA 전용이다.

```
$600C  CD-DA SATB pass 시작: 한 프레임만 $601E를 스텁으로 교체
$601E  $7F49 상주 JSR/NOP 대신 CD-DA 스텁 실행
$5C40  팔레트 15 설정 + 게임의 $6463 push loop 호출
$5D00  최대 28 글자의 5 B SATB 레코드
$6072  원래 $601E bytes(JSR $7F49/NOP) 복원
```

`$600C -> $601E -> $6072`는 반드시 같은 프레임에서만 유효하다. 다음 프레임에
미리 회수하면 한 번도 push되지 않는다. 팔레트는 Lua endFrame 포트 쓰기가 아니라
스텁의 실제 6280 `STA $0402-$0405`로 설정해야 CD-DA 장면에서도 보인다.

### ★ AC 충돌 금지

옛 POC가 AC `$1C04F0/$1C0500`에 매직/엔진을 썼고, 현재 출하 빌드의
`translation_all`이 AC `$1C0000`부터 차지한 lookup 테이블 중간을 덮었다.
그 결과 원래 한국어였던 일반 UI가 일본어 원문으로 fallback했다.

따라서 CD-DA 런타임은 **AC를 읽거나 쓰지 않는다.** 글꼴은 Lua가 VRAM으로 직접
올리고, AC는 기존 ADPCM/일반 UI 번역 체인 소유로 남긴다. 이 사고 뒤에는 반드시
Power Cycle로 preload 테이블을 복원한다.

### ADPCM과 공존하는 방식

CD-DA 스텁/레코드 영역 `$5C40-$5D8B`는 일반 ADPCM 엔진 영역과 겹친다. CD-DA가
처음 그리기 직전에 이 범위를 백업하고, CD-DA 트랙이 끝나거나 verified 위치가
아닌 트랙으로 넘어가면 SATB를 지운 뒤 원본 바이트를 복원한다. 그러므로 CD-DA가
끝난 다음 ADPCM 자막 엔진을 깨뜨리지 않는다.

통합 진입점은 다음 하나다.

```
lua/SUB/0.4.94-hq-key-vram-cdda.lua
```

이 파일은 기존 `0.4.93-hq-key-vram.lua`를 먼저 올린 뒤 CD-DA 런타임을 붙인다.
둘을 따로 병용하지 않는다.

### 트랙 단위 번역과 안전 위치

Studio의 CD-DA 원고는 의도적으로 **트랙 1개 = 음성 1개 = TSV 1행**이다.
세부 클립/조각 분할은 더 이상 번역 단위가 아니다.

```
원고:  snatcher_tool/translation/cdda_subtitles.tsv
위치:  build/cutscene_subs/cdda_safe_positions.tsv
```

위치 표의 `status=verified` 트랙만 실제 렌더한다. pending 트랙은 번역문이 있어도
의도적으로 skip한다. 수집 전 미검증 VRAM을 덮어 그림/SATB 충돌을 만드는 것을
막기 위함이다.

초기 상태:

```
track 17  VRAM $7900 · y=192 · center_x=128 · verified
나머지 18개 트랙                              pending
```

트랙을 수집해 안전한 VRAM/화면 위치가 정해지면 해당 행의 `vram_base`, `text_y`,
`center_x`를 기록하고 `status`만 `verified`로 바꾸면 된다. 통합판의 첫 실제
재생 검증은 번역 원고가 들어간 verified 트랙에서 수행한다. 현재 확정된 것은
트랙 17 POC 경로이며, 다른 트랙은 이 안전 게이트를 통과하기 전에는 그리지 않는다.
