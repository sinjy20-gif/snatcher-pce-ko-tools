# SNATCHER 자막 런타임 인계서 — 2026-08-21

## 현재 결론

자막 데이터·번역과 별개로, 런타임의 마지막 과제는 음성 재생 중 화면에 스프라이트 자막을 안전하게 공존시키는 일이다.

- 안정 기반은 **lifecycle v0.1.5**다. 대사 시작 시 `$5B80-$5FFF`를 AC에 백업하고 IRQ1을 빌린 뒤, ADPCM 종료에서 벡터와 RAM을 원상복구한다.
- 이 lifecycle은 실제 Mesen에서 부팅, 대사 종료, UI 복귀까지 PASS했다.
- 기본 Mesen 펌웨어는 수정하지 않는다. 아래 실험 BIOS만 설정에서 직접 선택한다.

## 오늘 확정한 사실

| 항목 | 결과 |
| --- | --- |
| `$5B80-$5FFF` 대여/복원 | PASS (v0.1.5) |
| IRQ 벡터 설치/복원 | PASS. 실제 흐름 `$40A4 → $5B80 → $40A4` |
| 팔레트(VCE) 쓰기만 수행 | PASS (`0.2.3`) |
| AC payload의 `TAI $1A00,...` 복사 | FAIL. `$1A00/$1A01`을 교대 읽어 엔진이 깨짐 |
| 수동 `$1A00` 반복 읽기 | 복사 바이트 문제 해결 확인 |
| `$7B00`에 패턴 1개 업로드 | FAIL. 대사 진행이 멈추고 눈만 움직임 (`0.2.4`) |

### 중요: 디버거로 확정한 AC 복사 버그

`TAI $1A00, $5B80, #length`는 AC data port `$1A00`만 연속 읽는 동작이 아니다. `$1A00/$1A01`을 번갈아 읽어 `$5B80`에 쓰레기 바이트가 들어갔다.

정상 payload의 시작은 `48 68 4C A4 40` 또는 UI 엔진의 `48 DA 5A ...`여야 한다. 실패본은 `$5B80`에 `08 00 08 6C ...`처럼 보였고, 이후 엉뚱한 주소로 점프했다.

현재 AC 경로는 `$1A00`만 `LDA` 반복하여 대상 RAM에 `STA abs,X` 하는 수동 복사 방식으로 바꿨다. 복사 루프가 쓰는 X는 반드시 저장·복구한다.

## 화면 자원 조사 결과

- 초반 대사 10회 샘플에서 게임 SAT는 0–16번까지 사용했다.
- 17–63은 **초반 구간 후보**일 뿐이다. 게임 전체의 안전공간으로 확정하지 않는다.
- `$1038`부터의 0 VRAM run은 SATB `$1000-$10FF` 내부였다. 글리프 패턴 저장소가 아니다.
- 최종판은 여러 장면의 SAT/VRAM 점유를 누적 조사한 뒤 결정한다.

## 재개 순서

1. `0.2.5`: VDC 주소(MAWR)만 설정하고 데이터는 쓰지 않는다.
2. `0.2.5`가 PASS하면, VDC data port에 아주 작은 전송을 별도 단계로 시험한다.
3. 패턴 업로드가 PASS한 뒤 SAT 엔트리 하나만 기존 SATB의 빈 후보에 쓴다.
4. 글리프 1개를 보인다.
5. 2개 → 4개 → 9개로 한 줄을 확장한다.

공통 PASS 조건은 **부팅 → E6800_0E 대사 종료 → UI 복귀**다. 화면이 검어지거나 눈만 움직이며 대사가 끝나지 않으면 FAIL로 기록하고 직전 PASS 단계로 돌아간다.

## 디버거 절차

AC 복사 확인이 필요하면:

1. CPU Memory / Write breakpoint: `$2202-$2203`.
2. `$FF60: STA $2202`에서 멈춘다. 이 시점은 엔진 복사 후, IRQ1 설치 직전이다.
3. `Go to $5B80`에서 엔진 첫 바이트를 확인한다.
4. 바이트가 payload와 다르면 VDC/SAT는 보지 않고 AC loader부터 수정한다.

## 번역 데이터 메모

일반 대사는 `text_key + line_no`가 키다. 같은 일본어 원문이라도 서로 다른 레코드면 다른 번역을 허용한다.

- `R03693`: 제이미 — `<원문 5자>。` → `알겠어.`
- `R00737`: 미카 — `<원문 5자>。` → `알겠어요.`

단, 사전 항목은 원문 바이트 자체가 키라 같은 원문에 번역을 하나로 통일해야 한다.
