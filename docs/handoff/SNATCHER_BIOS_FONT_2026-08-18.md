# BIOS 폰트 경로 — 우리 번역이 시스템 카드 폰트로 출력된다 (2026-08-18)

> **결론이 나왔다.** §0 을 먼저 읽을 것.  실험 빌드가 실제로 돌아간다.
> 이 문서는 인계서(SNATCHER_RUNTIME_BOUNDARY_2026-08-15.md) 의 §8-Y 에서 갈라져 나온
> 것이고, 그쪽보다 이쪽이 크다.

---

## 0. 결론

우리 파이프라인이 낸 한국어를 **시스템 카드 BIOS 폰트 코드**로 내보내면 그대로 화면에
나온다.  아틀라스도, 레코드 전용 폰트도, AC 도 쓰지 않는다.

실험 빌드 `0.3.11-bios` 로 확인:

```
안내원
 여기는 ＪＵＮＫＥＲ본부입니다.
 무슨 용무이신가요?
```

이것이 닫는 문제들:

```
15자 예산 (§5)          없어짐 — 레코드마다 19칸 폰트를 채우던 구조 자체가 불필요
화면 밀림 (§FLICKER)     거의 없어짐 — 소유자 실측.  원인이던 608B 재구성이 사라진다
코드 공간 5바이트 (§8-M)  아틀라스·프리로더·폰트 래퍼가 통째로 불필요
AC 의존                 없어짐 — 원본 스내처는 AC 게임이 아니다.  우리가 끌어다 썼던 것
인명 검색 한글화 (§8-Y)   19칸 벽이 사라지므로 길이 열린다
```

대가:

```
이용자가 한글 시스템 카드를 써야 한다
빌더 체인 재작성 (스테이지 3 개가 없어지는 방향이라 단순해지기는 한다)
폰트를 BIOS 격자(16x16 / 12x12)에 맞춰야 한다
```

**번역 데이터는 그대로 산다.**  마스터는 원문↔번역 쌍이라 렌더링 방식과 무관하다.

## 1. 어떻게 여기까지 왔나

인명 검색 자판을 한글로 바꾸려다 나왔다.  순서대로:

```
1  인명 검색은 목록 선택이 아니라 가나 자판 입력이다 (§8-Y)
2  자판은 배경 타일이다 — 텍스트 렌더러를 안 탄다
     그래서 §8-N 의 "반각 가타카나 0건" 이 나왔던 것이다.  글자가 없어서가 아니라
     렌더러를 안 지나가서 수집기가 못 봤다
3  그러면 글리프는 어디서 오나 -> $69C2 -> **EX_GETFNT ($E060)** -> 시스템 카드 ROM
     PROBE_KANA_FONT_0.1.3 의 bios 행 20 건으로 확정
4  시스템 카드 ROM 은 디스크로 못 고친다.  가나 그림 갈아끼우기 불가
5  그런데 **한글 시스템 카드가 이미 존재한다** (소유자가 찾아옴)
6  원본과 바이트 비교 -> 폰트 데이터만 바뀌고 코드는 그대로
7  스내처 본문의 한자가 한글로 깨져 보인다 -> **본문이 BIOS 폰트를 쓴다**
8  그러면 우리 번역을 BIOS 코드로 내보내면 되지 않나 -> 된다 (§4)
```

7 번이 결정적이었다.  한글 카드를 물리고 미번역 일본어를 보니 **한자만 한글로 바뀌고
가나는 멀쩡**했다.  즉 대사 렌더러가 한자를 BIOS 폰트로 그린다는 뜻이다.

## 2. EX_GETFNT 구조 (실측)

```
$E060   4C 24 F1        JMP $F124          <- EX_GETFNT 는 점프 테이블 항목이다
$F124~                  본체
$F1E3~                  SJIS -> JIS 코드 변환
$F264~                  JIS -> 글리프 인덱스
$F27E                   행 오프셋 표.  16 비트 리틀엔디언 x 48 행
```

행 오프셋 표는 JIS 행마다 그 행 첫 글자의 글리프 인덱스를 담는다:

```
행 0x21 ->     0   (94 자, 기호)
행 0x22 ->    94   (14 자, 숫자)
행 0x23 ->   108   (62 자, 영문)      <- 한글 카드는 이 행도 바꿔 놓았다
행 0x24 ->   170   (83 자, 히라가나)
행 0x25 ->   253   (86 자, 가타카나)
행 0x30 ->  1205   (한자 시작)        <- 한글 카드가 여기부터 한글로 채웠다
```

글리프를 복사하는 자리:

```
$F12C   A9 A0 85 FC     LDA #$A0 / STA $FC     16x16 모드 베이스
$F143   A9 60 85 FC     LDA #$60 / STA $FC     12x12 모드 베이스
$F1A7   FF FC 07        BBS7 $FC,+07           $FC 비트 7 로 격자가 갈린다
$F1AA~  53 08/10/20/40  TAM                    폰트 뱅크를 페이징
$F1B6   8F FF 0C        BBS0 $FF,+0C
$F1B9   C2              CLY                    <- 글리프당 한 번.  훅은 여기에
$F1BA   B1 EC           LDA ($EC),Y            <- ★ 글리프 읽기
$F1BC   91 FA           STA ($FA),Y
$F1BE   C8              INY
$F1BF   C0 20           CPY #$20               <- 한 글자 32 바이트
$F1C1   D0 F7           BNE $F1BA
$F1C5   20 CC F2        JSR $F2CC              <- BBS0 이 걸린 대체 경로
```

> **주소 정정 (2026-08-18).**  이 표는 처음에 복사 루프를 `$F1B8 / $F1BA / $F1BD` 로
> 적었는데 **2 바이트 어긋난 값**이었다.  `$F1B8` 은 바로 위 `8F FF 0C` 의 **분기
> 오퍼랜드 바이트**라 명령 시작이 아니고, 거기 exec 훅을 걸면 영원히 안 걸린다 --
> `PROBE_FONT_ADDR_0.1.1` 이 실제로 0 표본을 뱉었다.  위 값은 ROM 실물을 주소별로
> 찍어 고친 것이다.  `$F12C` / `$F143` 은 원래 적힌 대로 맞다.

### 정정 — 우리는 이미 12x12 를 쓰고 있다 (실측 2026-08-18, PROBE_FONT_ADDR_0.1.2)

위 표는 `$F1BA` 복사 루프가 본줄인 것처럼 읽히지만 **한 번도 안 돈다.**  진입 8 건이
전부 `$F1B6` 의 `BBS0 $FF` 에 걸려 대체 경로로 샜다:

```
$F1B6   8F FF 0C   BBS0 $FF,+0C   -> 걸리면 $F1C5
$F1C5   20 CC F2   JSR $F2CC

$F2CC   C2         CLY
$F2CD   B1 EC      LDA ($EC),Y    <- ★ 진짜 글리프 읽기
  ...              니블 시프트 언팩 (3 바이트 읽어 4 바이트 쓴다)
$F2F3   C0 12      CPY #$12       <- 한 글자 **18 바이트** = 12x12 팩 (24 B 로 풀린다)
$F2F5   90 D6      BCC $F2CD
```

그러므로 **0.3.11-bios 에서 우리 한국어는 12x12 로 그려진다.**  "12x12 모드가 따로
있다. 아직 안 써봤다" 고 적었던 것은 거꾸로였다 -- 뒤집는다.

> **다만 여기까지다.**  표본 8 건은 전부 **우리 텍스트를 우리 빌드에서** 뜬 것이고
> **원본 일본어 한자는 한 번도 안 떴다.**  소유자가 "애초에 스내처는 전부 16x16
> 이었다" 고 지적했고 그것과 충돌한다.  갈래가 둘이다:
>
> ```
> 원본 한자도 $F2CC   스내처 한자가 원래 12x12.  기억 속 16x16 은 게임 자체 폰트로
>                     그리는 가나다 -- EX_GETFNT 를 안 탄다 (§1-2 와 일치)
> 원본 한자는 $F1BA   우리 빌드가 $FF 를 뒤집었다.  버그이고 고치면 한글이 전부
>                     커진다.  공짜로
> ```
>
> `PROBE_FONT_ADDR_0.1.4` 가 $20FF 쓰기를 PC 별로 세어 범인을 가린다.
> **원본 디스크와 0.3.11-bios 두 번 돌려야 결론이 난다.  아직 안 났다.**

**`$FC` 도 격자 플래그가 아니다.**  `$F19E` 에서 포인터 상위 바이트에 더해지므로
**창 베이스**다 ($A0 -> $A000).  격자를 가르는 것은 `$FF` 비트 0 이다:

```
$FF 비트 0 = 1  ->  $F2CC   12x12   18 B 팩       <- 우리가 타는 쪽
$FF 비트 0 = 0  ->  $F1BA   16x16   32 B 그대로
$FC = $A0 / $60 ->  창을 $A000 / $6000 에 건다.  $F1A7 BBS7 $FC 가 가른다
```

### 글리프 베이스 확정

```
81 40 (전각 공백)  JIS 2121  인덱스   0   src $A000    <- 베이스
82 69 (Ｊ)         JIS 234A  인덱스 127   src $A8EE    127 x 18 = $8EE  ✓
```

인덱스 127 은 §2 의 행 표와 맞아떨어진다 -- 행 0x23 베이스 108 + (숫자 10 + Ａ~Ｉ 9).
**행 표는 실제 글리프만 세고 JIS 의 빈 칸은 건너뛴다.**

남은 것은 뱅크뿐이다.  `ROM 오프셋 = 뱅크 * 0x2000 + (src - $A000)` 이고 뱅크는 `$EE`
가 정해 `$F1B1~$F1B4` 의 TAM 이 창에 건다.  `PROBE_FONT_ADDR_0.1.3` 이 `$F1B6` 에서
그것까지 잡는다.

### 영문이 작은 이유 — 해태 폰트가 아니라 격자로 보인다

12x12 를 타기 때문이다 (위 유보가 풀린 뒤에 확정된다).  카드에는 16x16 한 벌이 통째로 들어 있다(§3).  선택지 둘:

```
가  $FF 비트 0 을 꺼서 16x16 으로   영문만이 아니라 한글까지 다 커진다.
                                    다만 목적지가 24 B -> 32 B 라 타일 배치가 틀어진다.
                                    공짜가 아니고 별도 검증이 필요하다
나  행 0x23 의 62 자만 교체         12x12 유지.  62 x 18 = 1,116 B 짜리 IPS.
                                    어차피 만들 폰트 IPS 에 행 하나 더 얹는 것뿐이다
```

§3 의 바이트 검산도 다시 봐야 한다.  12x12 를 24 B 로 잡고 맞춘 값인데 실제 저장은
18 B 다.  2,350 x (32 + 18) = 117,500 이라 실측 129,984 와 12 KB 벌어진다.  차이는
기호·가나·영문 행(0x21~0x25)까지 바뀐 몫으로 보이지만 **확정된 값이 아니다.**

## 3. 한글 시스템 카드 실물 분석

`PECSYSTEMK\Syscard3k.pce` 를 원본과 바이트 비교했다.

```
원본   Mesen_2.2.1_Windows\Firmware\[BIOS] Super CD-ROM System (Japan) (v3.0).pce
       262,144 B = 256 KB          <- ROM 파일 실측.  작업 RAM 256KB 와 헷갈리지 말 것
한글   PECSYSTEMK\Syscard3k.pce
       262,144 B

다른 바이트   129,984 B (49.6%)
```

뱅크별:

```
뱅크  0  (BIOS 코드 $E000-$FFFF)     변경 0 B     <- ★ 코드는 안 건드렸다
뱅크  1, 3                          114 B, 152 B
뱅크  8~18 (0x10000~0x25FFF)        대량          <- 폰트
뱅크 24~30 (0x30000~0x3DFFF)        대량          <- 폰트
```

양이 맞는지 검산:

```
완성형 2,350 자 x 16x16 (32 B)  =  75,200
                x 12x12 (24 B)  =  56,400
                          합계  = 131,600 B
실측 변경량                      = 129,984 B      (차이 1.2%)
```

**한글 완성형 2,350 자가 16x16 과 12x12 두 벌로 들어가 있다.**  "수천 자 한글을 넣은
사례가 없다" 는 추정이 돌아다니는데, 실물이 여기 있고 열어 봤다.

## 4. 코드 매핑 — 한글 한 글자를 어떤 바이트로 쓰나

한글 카드는 **JIS 한자 자리에 KS X 1001 한글을 같은 행/열로** 넣었다.
그러므로:

```
EUC-KR 코드 - 0x8080 = JIS 코드 -> SJIS 로 다시 인코딩
```

검산:

```
가  EUC-KR B0A1  ->  JIS 3021  ->  SJIS 889F     (원본에서 `亜` 자리)
각  EUC-KR B0A2  ->  JIS 3022  ->  SJIS 88A0     (`唖`)
간  EUC-KR B0A3  ->  JIS 3023  ->  SJIS 88A1     (`娃`)
```

구현은 `extraction\translation\game_text_codec.py` 의 `_bios_hangul_bytes()` 에 있다.

### 실험 스위치

```
SNATCHER_KO_BIOS=1      한글을 F0 xx 대신 BIOS 코드로 내보낸다
기본값 0                현행 0.3.x 는 아무 영향 없다
```

실제 출력 비교 (`여기는 JUNKER본부입니다.`):

```
기본   F0 49 F0 43 F0 44 81 40 82 69 ... F0 40 FF        아틀라스
BIOS   90 48 89 82 8A C0 81 40 82 69 ... F0 40 FF        BIOS 폰트
       여    기    는
```

마침표(`F0 40`)만 우리 글리프로 남는다.  나머지는 전부 BIOS 다.

### 낭비 제거 — 끝났다 (2026-08-18, `0.3.11-bios-opt`)

스위치가 인코더에만 걸려 있었다.  스테이지 1 은 인코딩 결과와 무관하게 **줄마다 한글을
래스터로 굽고 있었고**, 그래서 아틀라스도 글리프 루프도 그대로 돌았다.  뿌리는 두 곳:

```
build_full_overlay_layout.build_assets      glyphs = ordered_hangul([text])
build_direct_overlay_layout.build_menu_session_payloads   같은 패턴
```

둘 다 `SNATCHER_KO_BIOS` 에서 `glyphs = ()` 로 두고, 스테이지 3 에는 같은 스위치로
`COMPACT_BYTES = TEXT_SPAN` 과 헬퍼의 3~4 단계(아틀라스 오프셋 전송 · 글리프 루프)
생략을 넣었다.  상수 3 칸(F040/F041/F042)과 반칸 도우미는 남으므로 608 B 템플릿과
그 상수 검사는 그대로 둔다 -- 마침표는 여전히 우리 글리프다 (§4).

결과:

```
                    0.3.11-bios              0.3.11-bios-opt
압축 레코드          2,308 x 128 B            2,439 x 96 B
아틀라스            1,115 글리프 / 35,680 B    0 / 0 B
AC 팩 전송          299,008 B                237,568 B      -61,440
초기 CD 적재        49 청크                   38 청크
헬퍼 코드           777 B (여유 5 B)          631 B (여유 151 B)
```

**레코드당 전송 사이클 593 + 209 x 15 = 3,728 -> 593.  8.2 스캔라인이 1.3 으로.**
템플릿 전체 복사가 걸리는 최악의 경우도 16.5 -> 9.6 이다.

`helper_free_bytes` 가 5 -> 151 로 벌어진 것이 특히 크다.  §8-M 의 "코드 공간
5 바이트" 제약이 실제로 풀렸다.

**15 자 예산도 같은 줄에서 죽었다.**  `FONT_GLYPH_CAPACITY - 4` 검사는 `glyphs` 가
비어 있으므로 이제 아무것도 막지 않는다.

### 걸린 것 하나 — 완성형 밖 한글

`오늘부로 JUNKER로 임명됬다.` 의 **됬**(U+B42C)이 KS X 1001 완성형 2,350 자 밖이라
BIOS 로 그릴 수 없다.  아틀라스 시절에는 우리가 글리프를 구워서 통했다.
`snatcher_ko_master.tsv` 68 행을 **됐** 으로 고쳤다 (오타였다).

전수조사 결과 **실제 출력되는 칸(`ko_text` / `ko_name`)에서 이것 하나뿐**이다.
`legacy_static_master.tsv` 에 5 곳 더 있으나 그 파일은 배포에 안 들어간다.

> **코덱 함정.**  파이썬 `euc-kr` 코덱은 완성형 밖 글자를 **8 바이트 조합형 이스케이프**로
> 인코딩해 성공한다 (`됬` -> `a4d4 a4a7 a4ca a4b6`).  그래서 `try: ch.encode("euc-kr")`
> 만으로 거르면 못 잡는다.  `len(raw) != 2` 를 봐야 한다 -- `_bios_hangul_bytes()` 는
> 원래부터 그렇게 되어 있다.

### 빌드 방법

```

python extraction\patch\static\patch_title_cache_wipe.py ^

`--tag` 를 쓰면 중간 폴더 이름에 접미사가 **두 번** 붙는다 (`-opt-opt-unpatched`).
빌더의 접미사 처리 흠이고 무해하지만, 경로를 그대로 옮겨 적어야 한다.

## 8. 폰트와 배포 — 결정됨 (소유자 지정 2026-08-18)

받아 쓴 한글 카드는 **해태 정식 발매판**이다.  부트 화면까지 한글이다:

```
슈퍼컴 K CD / 해태 바이스타 CD
VER. 3.0K
NEC Home Electronics, Ltd. 1993 / HAITAI SOFT 1993
```

폰트만 바꾼 것이 아니라 **로고 그래픽까지** 바꿔 놓았다.  §3 의 diff 에서 뱅크 1·3 의
소량 변경(114 B / 152 B)이 그것으로 보인다.

### 배포 방식

```
기본      이용자가 해태 한글 카드를 받아서 쓴다.  그대로 플레이 가능
선택      우리가 만든 **폰트 IPS 패치**를 얹으면 갈무리 글꼴이 된다
```

강제하는 것이 없고, 해태 폰트가 마음에 드는 사람은 그냥 쓰면 된다.

**IPS 로 배포하는 이유**: 수정된 ROM 통째는 남의 저작물이라 재배포할 수 없다.
IPS 는 차이분만 담으므로 관행상 통용된다.  `dshadoff/SYSCARD_Translatefont`
(BSL-1.0) 가 같은 방식이고, 그쪽은 EX_GETFNT 를 확장해 번역용 ASCII 폰트를 넣는다.
호출 규약을 거의 안 깨는 구조라 참고 가치가 크다.

**로고는 건드리지 않는다.**  폰트 영역(뱅크 8~18, 24~30)만 덮는다.

### 아직 못 한 것 — 폰트 데이터의 ROM 시작 오프셋

행 오프셋 표($F27E)까지는 정적으로 뽑았는데 베이스를 못 맞췄다.  휴리스틱으로 찾으려다
빈 영역이나 엉뚱한 자리를 짚었다.

확실한 방법을 프로브로 준비해 뒀다:

```
lua\PROBE_FONT_ADDR_0.1.0.lua

  $F1B8 (LDA ($EC),Y -- 글리프를 실제로 읽는 명령) 에 훅
  그때 $EC/$ED = CPU 주소, MPR = 어느 뱅크가 걸렸나
  둘을 합쳐 ROM 오프셋을 계산해 찍는다
  문자마다 한 번씩, 24 개 모으면 스스로 멈춘다.  3~5 초면 된다
```

`note` 열의 `ROM 오프셋` 이 답이다.  글자마다 32 씩 벌어지면 연속 배열이고, 그러면
갈무리 2,350 자를 어디에 쓸지 계산이 끝난다.

그 뒤는 스크립트다:

```
1  Galmuri11.bdf -> 16x16 비트맵    parse_bdf() 는 이미 아틀라스에 쓰고 있다
2  해태 카드에 써넣기
3  원본과 diff -> IPS 생성
4  12x12 도 같이 (BIOS 에 두 벌 다 있다)
```

## 8-U. 열린 문제 — BIOS 판에서 UI 가 원문으로 샌다

행동 메뉴 등 일부 UI 가 번역 대신 **원문 일본어**로 나온다.  해태 카드에서는 한자가
