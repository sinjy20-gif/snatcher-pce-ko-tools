## 1. 메뉴를 다시 열 때마다 CD를 읽던 문제

### 증상

같은 메뉴를 열고 닫고 다시 열면 약 5초 로딩. 데이터는 한 번 읽으면 AC에 남아야
하는데 계속 CD를 탔다.

### 실측

`lua\PROBE_PACK_RELOAD_0.1.1.lua` 로 CD 읽기마다 `PACK_ID`·목적지를 찍었다.

```
scene_111800  $50000  ×7    f3822 · 6513 · 7071 · 7473 · 13817 · 14700 · 14923
scene_10F800  $50000  ×5    f6868 · 7001 · 7383 · 14483 · 14777
scene_121800  $50000  ×2
scene_111000  $50000  ×1
─────────────────────────
서로 다른 팩 4개인데 로드 15회
```

resident 팩(`ui`→`$1C000`, `shared`→`$3B800`, `small_scenes`→`$3A000`)은 각각
한 번씩만, 목적지도 manifest와 일치했다. **`shared` 는 무죄다.**

### 원인

```python
destination = cursor if resident else scene_base    # scene 팩 전부 $50000
capacity    = ... if resident else (AC_BYTES - scene_base)
```

scene 팩을 **한 슬롯 오버레이**로 설계했다. 런타임도 "현재 장면팩 ID" 한 칸
(`3 + resident_count`)만 두고 있었다. 전제는 "한 번에 한 장면"인데, 실제로는
**같은 장소 안에서 메뉴와 대사가 서로 다른 팩에 있어** 핑퐁했다.

그리고 아끼려던 자원이 남아돈다.

```
scene 팩 전체 102 KB  /  scene 영역 1.7 MB  →  전부 동시 상주해도 6%
```

### 수정

```python
scene_cursor = scene_base            # scene 팩도 순차 할당
destination  = cursor if resident else scene_cursor
```

런타임은 팩 종류 구분을 없애고 **모두 `3 + pack_id` 플래그**를 쓴다. 초기화도
팩 수만큼 돌도록 루프로 바꿨다(25개를 펼쳐 쓰면 125 B, 루프는 10 B).

부수 효과로 헬퍼가 줄었다.

```
헬퍼 코드   709 B → 664 B      여유 73 B → 118 B
제거        scene_flag 5 B · mark_scene 11 B · 판정 분기
```

### 결과

```
scene 팩 21개   목적지 고유 21개   겹침 0건
AC 사용 309,248 B = 2 MB의 14.7%
$50000 부터 $70800 까지 차례로 배치
```

### 검증 완료

`lua\PROBE_PACK_RELOAD_0.1.2.lua` 로 0.3.2 를 실측했다.

```
f10800 이후   speaker×1  ui×1  small_scenes×1  shared×1
              scene_10F800×1  119800×1  121800×1  111800×1  110800×1
              179800×1  160800×1
              읽기 49회에서 정지 — 이후 5,400프레임(90초) CD 접근 0
loaded again  0줄
```

0.3.1 에서 `scene_111800` ×7, `scene_10F800` ×5 였던 것이 **전부 ×1** 이 됐다.
팩은 한 번 읽으면 AC 에 남는다.

프로브 0.1.1 의 결함 두 개도 0.1.2 에서 고쳤다 — 게임 자신의 CD 읽기를
트램폴린(`$7F88`/`$7F92`)으로 걸러내고, 팩 표를 25개 기준으로 재생성했다.
0.1.1 로그의 `pack_id 225 dest $B852D6` 같은 행은 전부 그 노이즈였다.

## 2. 팩 개수 상한에 걸렸다

번역이 늘어 BODY 검토가 1,857 → 1,974행이 되자 팩이 15 → **25개**가 되면서
빌드가 죽었다.

```
메타데이터  AC $10080-$100FF  128 B,  팩당 8 B  →  16개가 상한
```

08-12 인계서가 "14,000줄 도달하면 손볼 두 가지"로 예고한 그 천장이다.

### 수정 — 상수 하나

```python
METADATA_AC_OFFSET = 0x20        # 기존 0x80
```

메타데이터를 상태페이지 아래쪽(매직 3 B + 팩별 플래그 바로 위)으로 내렸다.
헬퍼가 `CLC; ADC #offset` 으로 **한 바이트** 오프셋을 쓰므로 표 전체가 256 B
상태페이지 안에 있어야 하고, 상한은 `(256 - offset) / 8` 이다.

```
$80 → 16개      $20 → 28개      현재 25개 (여유 3)
```

플래그와 메타데이터가 서로를 향해 자라므로 만나면 죽는 검사도 넣었다.

⚠ **28개를 넘으면 상수로는 안 된다.** 헬퍼에 16비트 주소 지정을 넣거나 08-12
인계서가 말한 별도 메타데이터 구역으로 옮겨야 한다. 에러 메시지에 그 내용을
적어뒀다.

## 3. `ui_text.tsv` 를 못 읽어 빌드가 죽던 문제

### 진짜 원인

파이썬 `csv` 의 기본 필드 한도가 128 KB인데 `UI0001` 의 `note` 가 136 KB였다.
**파일은 처음부터 유효한 CSV였다.**

```python
# extraction/translation/tsv_io.py
csv.field_size_limit(min(sys.maxsize, 2**31 - 1))
```

### 조사 중 저지른 실수 — 반드시 읽을 것

`note` 열은 스튜디오가 런타임 캡처 신원을 **한 줄에 하나씩 쌓는** 열이고,
여러 줄을 담으므로 정상적으로 따옴표로 인용된다. 이걸 줄 단위로 쪼개서 보면
"안 닫힌 따옴표"처럼 **보인다.** 그 착시로 파일을 "복구"하다가:

```
note 80,957줄 삭제      (스튜디오가 읽는 캡처 연결고리)
검토 O 976 → 756        (인용 필드가 깨지며 뒤 열이 밀림)
```

게다가 대조 검증까지 같은 잘못된 방식으로 해서 **"차이 0건"으로 통과**했다.
백업에서 원복했다.

**교훈: TSV를 줄 단위로 다루지 말 것.** 인용 필드는 설계상 개행을 포함한다.
반드시 `csv` 로 읽고 쓰고, 손대기 전에 **무변경 왕복이 바이트 동일한지** 먼저
확인할 것. (이번엔 그 확인을 하고 나서야 안전하게 중복을 걷어낼 수 있었다.)

## 4. 스튜디오 — 캡처 신원 중복

```
[RUNTIME_UI] 총 80,957 줄  /  고유 803 줄 (1.0%)
UI0131 한 행만 1,701줄 → 고유 16줄
```

`MainForm.cs` 의 중복 판정이 **note 전체를 한 문자열로** 집합에 넣고 있었다.

```csharp
.Select(row => ui.Get(row, "note"))                    // 여러 신원이 통째로
.Where(note => note.StartsWith("[RUNTIME_UI]", ...))   // 첫 줄만 보고 판단
```

그래서 개별 신원과 절대 안 맞고, note가 다른 문장으로 시작하면 그 행은 통째로
제외됐다. 임포트마다 전부 다시 붙은 이유다.

```csharp
.SelectMany(row => ui.Get(row, "note").Split('\n'))    // 줄 단위로 펼침
.Select(line => line.Trim())
.Where(line => line.StartsWith("[RUNTIME_UI]", ...))
```

기존 중복도 `csv` 로 정리했다.

```
8,204,004 B → 202,962 B      고유 신원 683 → 683 (손실 0)
note 이외 열 차이 0건        번역 989 · 검토 O 976 유지
```

⚠ Lua는 무죄다. `COLLECT_RUNTIME_UI_STRINGS.lua:13` 은 `dump\` 로 올바르게 쓴다.

## 6. 실험 — 대사 3줄 (부분 성공, 규칙 도출)

접수처 첫 대사는 게임이 레코드를 2개만 요청한다. 레코드는 늘릴 수 없지만
한국어 안에 `{BR}`(= `FD`)을 넣어 표시상 쪼갤 수 있다.

```
레코드 1 에 {BR}   →  '여기는' 은 제 줄에 나왔으나
                      'JUNKER본부입니다.' 와 다음 레코드가 같은 줄에 겹침
레코드 2 에 {BR}   →  3줄 정상 출력.  단 세 번째 줄이 왼쪽 끝에 붙음
```

**도출된 규칙**

```
FD 는 동작한다
FD 는 커서를 x=0 으로 되돌린다 (게임의 BR 은 대사창 여백까지 맞춘다)
FD 뒤에 레코드가 오면 겹친다   게임의 줄 카운터가 FD 를 모른다
→ 인라인 줄바꿈은 마지막 레코드(after_control=END)에서만 안전하다
```

여백 보정으로 `무슨{BR} 용무이신가요?`(줄바꿈 뒤 공백 1개)를 빌드해뒀다.
**미검증** — `build\patch\0.3.1-3line3\` 에 디스크가 살아 있다.

실익은 크다. `END` 레코드가 4,229개라 **모든 대사 뭉치의 마지막 줄을 두 줄로
쪼갤 수 있다.** 18칸 제한 때문에 줄여 쓴 문장을 되돌릴 수 있다.

마스터는 실험 후 전부 원복했다(`backup\master_before_3line*.tsv`).

## 7. 새로 드러난 문제 — 마스터에 없는 줄이 원문 그대로 나온다

국장실 대사에서 3번째 줄만 일본어(`だぞ。`)로 남는 것이 확인됐다.

```
text_key 112000:51C7
  line 1  ac=BR    <원문 8자>。                 → 정말 가만있질 못하는군.
  line 2  ac=CONT  <원문 18자>  → 신기한 건 알겠지만 집중하게.
  line 3  ── 마스터에 없음 ──                        だぞ。
```

원문이 「…大切**だぞ。**」로 이어지는데 꼬리가 별도 레코드다. 런타임 치환은 일본어
원문 바이트로 조회하므로, 없는 행은 원문 그대로 그려진다.

### 조사 경로에서 저지른 오진 두 개 (기록용)

1. **"런타임이 못 잡았다"** — 틀렸다. 카탈로그가 UTF-16 인데 UTF-8 로 읽어 파일이
   조용히 건너뛰어졌다. `だぞ。` 는 정상 수집돼 있다.
2. **"마스터에 그 행이 없다"** — 틀렸다. `text_key` 로만 찾아서 못 봤다. 같은
   일본어를 쓰는 참조들은 **한 행을 공유**하고 `references` 열로 묶인다.
   `112000:51C7:3` 은 `161800:3D8B` 행이 들고 있다.

수집기 게이트(`$3471 == $3619`)도 이 건과 무관하다.

### 진짜 원인 — 카탈로그가 이미 진단해뒀다

`snatcher_tool\logs\audit_archive\runtime_text_catalog_20260814_001611.tsv`
(UTF-16, 780행)에 `classification`·`state`·`action` 열이 있다.

```
だぞ。   classification=MASTER_ONLY   state=01A2
         references  161800:3D8B:3, 112000:51C7:3, 162000:758E:3
         master_ko   '부족해지면... 바로 신청하게.'
         action      "MASTER에는 있으나 현재 빌드에서 제외됨: O/상태/예외처리 확인"

か？     state=006D  HIT         "정상 치환"          ← 111800:2890:2 는 잘 된다
         state=017C  ROUTE_FAIL  "다른 상태에만 등록됨: 상태 라우팅 확인"
         state=0000  ROUTE_FAIL  동일
```

사용자가 본 **"루트 페일"이 이 `ROUTE_FAIL`** 이다.

### 원인 — 마스터와 런타임의 키 단위가 다르다

```
마스터    일본어 1행 = 한국어 1개.  여러 참조가 한 행을 공유한다
런타임    (일본어, state) 마다 다른 한국어를 요구한다
```

같은 `か？` 가 장면마다 다른 `state` 로 오는데 마스터는 하나만 담을 수 있다. 그래서
한 상태에서는 치환되고 나머지 상태에서는 `ROUTE_FAIL` 이 된다. `だぞ。` 는 마스터의
한국어가 다른 장면(`161800`) 것이라 검토 O 를 못 받아 아예 빠졌다.

`snatcher_tool\translation\master_conflict_exclusions.tsv` 가 이 충돌을 "검토 해제"로
처리해온 집행 기록이다. 짧은 꼬리 580행 중 225행(39%)만 출하되는 이유다.

**문맥 구분 장치 자체는 이미 있다.** 조회 키는 원문 바이트만이 아니라 `state` 를
포함하고, 프리로더는 실패 시 루트로 한 번 재시도한다.

```asm
scan_record        레코드 못 찾음 → PASS_NO 가 0이면 retry_root_state
retry_root_state   부모 상태가 있으면 have_parent_state
have_parent_state  MATCH_LO/HI = 0 (루트로) · PASS_NO = 1 · restart_scan
                   → 여기서도 못 찾으면 no_match
```

사용자가 본 **"루트 페일"이 바로 그 2차 실패**다.

실제 예 — 이 레코드는 출하까지 됐는데 화면에서 치환되지 않는다.

```
build\patch\0.3.2\direct_records.tsv
  111800:2890:1   state=0000  next_state=006D   'JUNKER에 관심 있으세요?'
  111800:2890:2   state=006D  next_state=0000   '{EMPTY}'   src=82 A9 81 48 (か？)
```

1번 줄이 루트에서 찾히며 **006D 를 넘겨주고**, 2번 줄은 부모 상태 006D 로만 찾을 수
있게 저장돼 있다. 루트 페일은 그 006D 가 조회 시점에 없었다는 뜻이다.

꼬리 전반이 이 구조다. 그래서 같은 `。`·`か？` 가 장면마다 달라도 **원문 충돌 없이
구분된다** — 설계는 이미 옳다.

```
state != 0000 인 레코드   385 / 2194
  0BB800:2816:2  state=0020  src=81 42 (。)
  111800:2BE8:2  state=0082  src=82 AA 81 42
  111800:2890:2  state=006D  src=82 A9 81 48
```

### 해법 — 마스터를 (jp, state) 단위로 쪼갠다

엔진은 이미 상태로 라우팅한다. 부족한 것은 **데이터**다. 같은 일본어라도 상태가
다르면 별도 행이어야 한다.

카탈로그가 상태를 이미 기록하므로 재료는 다 있다.

```
classification=ROUTE_FAIL 인 행     그 (jp, state) 조합에 레코드가 없다는 뜻
classification=MASTER_ONLY 인 행    행은 있는데 검토/상태 때문에 빠졌다는 뜻
action 열                          무엇을 해야 하는지 한국어로 적혀 있다
```

작업 순서는 카탈로그를 `classification` 으로 분류해 `ROUTE_FAIL` 을 세고, 각
`(jp, state)` 에 필요한 한국어를 채워 넣는 것이다. 스튜디오가 이 카탈로그를 이미
읽으므로 UI 쪽 지원이 있는지부터 확인할 것.

## 8. 빌더 옵션

```
python build_snatcher_ko_0_3_2.py                 빌드만. 아무것도 지우지 않음
python build_snatcher_ko_0_3_2.py --check         무엇이 실릴지만 보고
python build_snatcher_ko_0_3_2.py --stage3        3단계만
python build_snatcher_ko_0_3_2.py --prune         정리 (명시할 때만)
python build_snatcher_ko_0_3_2.py --prune --deep  중간물까지
python build_snatcher_ko_0_3_2.py --space F041|20 띄어쓰기 실험
python build_snatcher_ko_0_3_2.py --tag NAME      데이터 실험
```

`--space`/`--tag` 는 **산출 폴더와 1·2단계 중간물을 함께 분기**한다. 중간물을
분기하지 않으면 이후 평범한 `--stage3` 이 실험 바이트를 정식 이름으로 뱉는다.

## 9. 함정 (누적)

1. **`FF`·`00` 은 빈 공간의 증거가 아니다.** 실행·읽기·쓰기 셋 다 조용해야 하고,
   실제로 지나간 경로에 한해서만 유효하다.
2. **디스크 이미지의 뱅크 오프셋 환산은 적재 영역 밖에서 무효다.**
3. **계측 Lua 는 버전을 올린다. 출력 경로도 같이.** 로그는 그것을 만든 코드
   없이는 판독할 수 없다.
4. **TSV 를 줄 단위로 다루지 말 것.** 인용 필드는 개행을 포함한다. `csv` 로 읽고
   쓰고, 손대기 전에 무변경 왕복이 바이트 동일한지 확인할 것. (§3)
5. **자기 검증을 자기와 같은 방식으로 하지 말 것.** 잘못된 파서로 읽고 같은
   파서로 대조하면 "차이 0건"이 나온다. (§3)
6. 빌드 전 Studio 를 닫을 것.
7. 파이썬으로 TSV 를 쓸 때 `encoding=` 명시.
