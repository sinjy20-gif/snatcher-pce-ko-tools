## 1. 음성 추출 — 무엇이 틀렸고 무엇이 맞았나

### 1.1 틀렸던 것: `sector` 는 대사의 위치가 아니다

`voice_events.tsv` 의 `sector` 를 디스크 좌표로 보고 잘랐다. 그것으로 만든 클립이
대사 중간에서 끊겼다 (소유자 확인: 「노도노 이타…」 하고 끊김).

수집기가 그 칸에 넣는 값은 `cdrom.scsi.sector`, 즉 **드라이브가 마지막에 서비스한
자리**다. 그 대사의 위치가 아니다. 실측이 증명했다 — 한 세션 12 개 이벤트가 전부
`sector=002F0A` 였다. 서로 다른 대사인데 같은 자리를 가리켰다.

수집기가 적는 값 다섯 개 전부가 하드웨어 상태이지 디스크 좌표가 아니다:

```lua
readAddress  = cdrom.adpcm.readAddress      -- ADPCM 전용 RAM 안의 포인터
writeAddress = cdrom.adpcm.writeAddress     -- 〃
length       = cdrom.adpcm.adpcmLength
rate         = cdrom.adpcm.playbackRate
sector       = cdrom.scsi.sector            -- 헤드 위치
```

### 1.2 맞는 길: ADPCM RAM 을 직접 뜬다

게임은 CD 에서 ADPCM RAM 으로 적재를 끝낸 다음 거기서 재생한다. **재생이 시작되는
순간의 RAM 이 곧 그 대사다.** 디스크를 파싱할 이유가 없다.

Mesen 에 그 메모리가 열려 있다:

```
pceAdpcmRam = 63        (memType 107 개 중 확인)
```

### 1.3 어디서부터 어디까지인가

**시작은 `readAddress`, 길이는 `adpcmLength`.** 근거:

```
length == (writeAddress - readAddress) % 0x10000
```

프로브 표본 17 건 중 16 건이 이 등식을 만족했다. readAddress 는 전부 `005D~0077`
로 RAM 맨 앞이었다.

검증 세 가지가 서로 맞물린다:

| 검증 | 결과 |
|---|---|
| 파일 크기 | `length` 와 바이트 단위로 정확히 일치 |
| 재생 시간 | `len 9F90` → 계산 5.11 초, 실제 `duration=5.100s` |
| 귀 | 소유자 확인 — **하나도 안 잘리고 그대로 나옴** |

⚠ **`0.1.0` 은 `writeAddress` 에서 떴는데 그것은 끝점이다.** 시작점은 `readAddress`.

### 1.4 `buffer_delta` — 참/거짓 표식은 틀렸다

처음에는 `write - read == length` 를 "정상" 으로 보고 어긋나면 `★` 를 찍었다.
누적 3,692 건으로 재보니 **61% 만 일치**했다. 그런데 어긋난 값이 전부 2048 의
배수였다:

```
(write-read) - length = +10240 (0x800×5)  285건
                        +34816 (0x800×17) 140건
                         +6144 (0x800×3)  120건
                            +1             174건   <- 포인터 1 B 전진
```

**2048 은 CD 섹터 크기다.** 로더가 섹터 단위로 미리 읽어 둔 것이지 클립이 깨진
것이 아니다. 그래서 참/거짓이 아니라 **차이 그 자체**를 적는다:

```
buffer_delta   0             딱 맞음
               2048 의 배수  선반입.  정상
               그 밖         들여다볼 것
```

최종 분포 (3,702 행): `0` 2,252 · 섹터 배수 1,276 · `+1` 174 · CDDA 122.
**설명 안 되는 것이 하나도 없다.**

### 1.5 파일 이름은 내용 지문 — 끝에서 8 KB

`sequence` 는 세션 안에서만 유효하다. 세션마다 1 부터 다시 세고, 실제로 서로 다른
대사가 같은 번호를 받았다 (173 개 중 23 개 겹침). 그래서 이름을 **내용**에서 짓는다.

**지문은 끝에서 8,192 B 를 뽑아 만든다.** 앞에서 잡으면 안 된다 — 같은 대사를 두
세션에서 잡으면 시작이 몇 바이트 흔들리고 끝은 고정이기 때문이다:

```
15:01  read=006B  len=6795  write=6800
15:09  read=006D  len=6793  write=6800     같은 대사, 시작만 2 B 차이
```

앞 기준이면 이 둘이 다른 파일로 갈린다 (실제로 3 쌍이 갈렸다). 뒤 기준이면 겹친다.
실물 3 개로 시작 0/1/2/3/5 B 밀림 전부 같은 지문이 나오는 것을 확인했고, 이것은
우연이 아니라 **고정 절대 위치를 읽으므로 구조적으로 보장**된다.

길이는 이름에서 뺐다 (`6795` vs `6793` 로 흔들려 지문이 겹쳐도 파일이 갈렸다).

## 3. 마스터 — 오늘 잡은 구멍 둘

### 3.1 잘린 대사 28 개 — 재수집으로도 안 채워지던 이유

마스터에 **마지막 줄이 `CONT` 인데 문장이 안 끝난 레코드가 28 개** 있다
(3,328 중 0.8%). 예: `R02999` 「<원문 10자>、<원문 7자>」.

원인은 수집 실패가 아니었다. **게임이 상자를 넘길 때 텍스트 포인터를 다시
설치해서($6FFD) 한 문장이 레코드 둘로 갈린다.** 실측:

```
레코드 1010  [메탈기어] <원문 10자>、<원문 7자>
                       <원문 17자>、    <- 미완
레코드 1011  [메탈기어] <원문 7자>、<원문 10자>
                       <원문 7자>。                        <- 이어짐
```

뒷조각은 「い・・・」「る。」처럼 짧고 흔하다. 그런데 빌더의 접기 키가 **텍스트
전체**였다. 그래서 게임 다른 곳의 같은 조각과 하나로 접혔고, 앞조각 뒤에 이어질
줄이 영영 안 생겼다. **표본 6/6 이 전부 이 원인이었다** — 뒷조각이 마스터의 다른
레코드에 이미 있었다 (「い・・・」 → R00181L2, 「ます。」 → R01184L3 외 3 곳).

다시 플레이해도 또 접히므로 **재수집으로도 안 채워졌다.**

**고침** — 접기 키에 스크립트 위치를 넣는다:

```python
key = (pack, ptr) + tuple(visible_normalize(l) for l in lines)
```

재방문은 같은 자리라 여전히 접히고, 다른 자리의 같은 글자만 살아난다.
실측 효과: 고유 레코드 1,989 → 2,093 (+104).

### 3.2 `--install` 이 마스터를 줄인다

빌더는 로그에서 마스터를 **다시 만든다.** 그런데:

```
현역 마스터   3,328 레코드 / 4,679 행   (여러 날 누적)
지금 로그      2,175 레코드            (0.2.0 형식 로그 4 개뿐)
```

옛 로그는 돌려쓰거나 옮겨져 없고, 08-14 이전 것은 0.1.x 형식이라 기본으로 읽지
않는다. 그대로 `--install` 하면 **1,919 행이 그릇째 사라진다.** 지금까지 무사했던
것은 `--install` 을 쓰지 않고 스튜디오에서 직접 편집해 마스터가 누적돼 왔기
때문이다.

**고침** — 로그에 없는 현역 레코드는 손대지 않고 그대로 옮긴다. 기본으로 켜져 있고
`--no-keep-master-only` 로만 끌 수 있다.

**대조 결과 (설치 안 함, 후보 파일만):**

```
현역  4,679행 / 3,328레코드
새것  5,062행 / 3,367레코드
번역된 원문 4,041종 중 없어진 것  0
검토 표식  4,063 -> 4,421
로그 밖 현역 레코드 보존  1,919 행
```

후보 파일: `dump/runtime_master_20260820_155902.tsv`

### 3.3 알아둘 것 — 번역 승계의 정규화 충돌

빌더가 번역을 물려줄 때 원문을 정규화해서 찾는데 `{FE:n}` 과 공백을 뗀다. 그래서
이런 것이 뭉친다:

```
「下さい。」        R00403 (세이브해 두세요)
「下さい。{FE:1}」  R00502 (높여 보세요)        같은 키 -> 나중 것이 이김
```

4,041 종 중 2 종. **오늘 만든 변경과 무관한 원래 성질**이다. 소유자가 전수 검토하므로
거기서 걸린다.

## 4. `신규 누락` 이 무슨 뜻인가 (헷갈리기 쉬움)

스튜디오 하단의 `신규 누락 1,299` 는 **로그 부족과 아무 상관이 없다.**

```csharp
IsUneditedRuntimeMiss(row) => note 에 [RUNTIME_MISS_UNEDITED] 가 있는가
```

게임에서 **일본어로 남아 있던 것을 런타임이 자동 등록한 행**이다. 손으로 고치면
표식이 지워진다. 숫자가 §3.2 의 1,919 와 비슷한 것은 우연이다.

## 5. 자막 — 오늘은 안 건드렸다 (상태만)

- Lua 렌더러로 **화면에 한글 자막이 실제로 그려지는 것을 확인함** (`SUBTITLE_DRAW_0.2.0`)
- 확정된 사양: `SUB_BOTTOM=140` · `LINE_GAP=18` · 글리프 실폭 11 px · 자간 12 px
  → 한 줄 21 자. 외곽선은 8 이웃 검정 후 흰 본체
- ⚠ **막힌 것은 적재 시점이 아니라 RAM 자리다.** `$5C40-$5E1F` 를 자막 엔진 자리로
  잡았는데 그것이 스크립트 VM 데이터 스택 한복판이었다. 빌드에 `SUBS_POC` 가드가
  걸려 있는 이유다
- 다음 할 일: `PROBE_ARENA_0.1.3` 으로 최대 스택 깊이 측정. 이것이 자막 자리를
  정하고 본편 빌드의 위험도 같이 걷어낸다

### 참고 — 타이틀 메뉴를 AC 적재 트리거로 쓰자는 안

검토했고 **채택하지 않는다.**

1. 타이틀 시점 트리거는 이미 있다 — `title_cache_wipe` (`$BCEF`, 실측 확인됨)
2. 막힌 것은 적재 시점이 아니라 RAM 자리다. 일찍 채워도 안 풀린다
3. 「<원문 5자>」는 고정 그림 두 장이다. AC 는 디스크에 안 들어가는 큰 데이터를
   흘리려는 것이지 고정 이미지용이 아니다. 디스크 타일을 직접 갈면 된다.
   타이틀 화면은 POC 가 이미 두 번 죽인 자리이기도 하다

다만 **"한글 처음부터 가 뜨면 로더가 돌았다"** 는 눈으로 보는 검증은 값어치가 있다.
AC 없이 타일만 갈고 성공했을 때만 그리게 해도 같은 신호가 나온다.
