## 1. ★ 막힘 — 빌드가 안 나간다

### 1-A. 트라이 충돌 (빌드 중단 지점)

```
RuntimeError: same runtime trie state/source has conflicting Korean text:
              R00289:2 and R03668:2
```

두 레코드의 L1·L2 원문이 **완전히 동일**한데 번역이 다르다.  트라이는
`(state, source)` 로 키를 잡으므로 같은 원문에는 같은 한국어여야 한다.

```
R00289 [미카]      L1 左の{FE:3}<원문 5자>{FE:1}<원문 6자>、
                   L2 右の{FE:2}<원문 6자>{FE:1}<원문 10자>
                   L3 すわ。          <- 여기만 원문이 다르다
R03668 [메탈기어]  L3 します。
```

**L1·L2 에는 말투가 안 실려 있다.**  통일하고 말투는 L3 가 받으면 된다.
아래 안은 칸수 검증까지 통과했다 (미적용 — 소유자 판단 대기).

```
R00289 1  왼쪽 {FE:3}빨간 게이지{FE:1}는 적의 출현 수      18칸
R00289 2  오른쪽 {FE:2}노란 게이지{FE:1}는                11칸
R00289 3  명중 횟수를 나타내요.
R03668 1  (위와 동일)
R03668 2  (위와 동일)
R03668 3  적을 맞힌 수를 나타냅니다.
```

R00289 는 검토 O 인 기존 번역이라 손대지 않았다.

```

**한자 행 밖은 선택지가 아니다.**

```

0x29~0x2F   BIOS 가 거부       $F22F  CMP #$30 / BCC  (08-18 확정)
0x30~0x47   한자 행            지금 쓰는 유일한 풀

**풀 문제가 아니라 판정 문제다.**  "게임이 쓴다" 1,906 개 중 **런타임 관측은 1 개**
뿐이고 나머지 1,905 는 코퍼스 추정이다.  도구 주석도 관측만이 확실한 출처라고
적고 있다.  추정분에 실제로는 화면에 안 그려지는 한자가 섞여 있을 것이다.

-> **오늘 밤 수집에 글리프 사용 로깅을 얹으면 그대로 풀린다.**  `EX_GETFNT` 에
   실제로 들어간 글리프 인덱스만 기록하면 되고, 어차피 도는 플레이라 추가 비용이
   없다.  관측이 쌓이는 만큼 추정을 걷어낼 수 있다.

배정표를 억지로 다시 돌리면 기존 배정 **10 자가 재배정**되며 (곽님릴뽑줬첩청총항혼)
이미 나간 판과 어긋난다.  **관측 없이는 돌리지 말 것.**

## 3. 자막 — 결정이 하나 남아 있다

구조(런타임 오버레이)는 확정.  규모상 다른 선택지가 없다.  **다만 구현이 두 가지고
아직 안 골랐다.**

```
A  매 프레임 IRQ 합성   게임이 덮어도 살아남음.  매 프레임 VDC 를 놓고 싸움
                        0.2.4 가 막힌 지점
B  클립당 1 회 렌더     AD_PLAY 훅에서 그리고 AD_STAT 에서 지움
                        IRQ 에서 VDC 를 안 건드림 -> 그 문제를 아예 안 만남
```

화자별로 클립이 쪼개지므로 **자막이 바뀔 순간 = 훅이 뜨는 순간**이다.  프레임 단위
타이밍이 필요 없고, lifecycle v0.1.5 의 백업/복원 주기가 이미 그 주기다.

**A/B 를 가르는 측정이 아직 0 행이다** (`dump/probe_subtitle_marker_vdc_0_1_0.tsv`).

```
E6800_0E 음성 구간 동안
  게임이 $0000-$0003(VDC) 에 쓰는가?  몇 번, 어느 MAWR 대역인가?
  SATB($1000-$10FF) 를 다시 쓰는가?
  SAT 17-63 이 그대로인가?
```

Lua 만으로 되고 ROM 을 안 구워도 된다.  **0.2.5 를 굽기 전에 이것부터.**

살아 있는 사실: 0.2.3(팔레트) PASS / 0.2.4(패턴 업로드) FAIL 은 RAM 대여·IRQ 대여·
AC 로더가 전부 동일하고 VDC 접근만 다른 통제비교다.  **범인은 VDC 로 격리됐다.**

용량: AC 자막 예약이 `$1C0000-$1FFFFF` 256 KB 인데, 클립 2,600 개 × 100 B ≈ 260 KB
로 이미 넘는다.  AC 2 MB 가 비어 있으니 **512 KB~1 MB 로 올려둘 것.**  자리 옮기는
게 제일 비싸다.

## 4. 판 크기 — 처음 나온 숫자

스크립트 페이지의 명령 개수는 텍스트 디코드가 깨져도 셀 수 있다.

```
채택 27 페이지            3,548 레코드
검증 195 페이지          14,651     (페이지당 평균 75)
미스캔 94 페이지 추정      7,062
검증 289 페이지 전체     21,713 레코드
채택 밀도(131/페이지)로 환산하면  약 37,900

현재 마스터               3,763 레코드  ->  10~17%
```

**이것도 바닥값이다.**  289 페이지는 런타임이 챕터 1 에서 밟아본 곳뿐이고, 2·3 막은
아직 하나도 안 세어졌다.  ±30% 는 감안할 것 (깨진 페이지의 명령 검출에 허수 가능).

### 정적 추출이 어디서 멈췄나

```
런타임 검증 텍스트 페이지   289
보수적 코퍼스 채택           27      <- 9%
  스캔은 됐으나 미채택      168
  스캔조차 안 됨             94
```

작업목록: `extraction/verified_text_pages.tsv` — 페이지마다 script/text 오프셋과
**oracle 문자열 3 개**(그 페이지에서 반드시 나와야 하는 런타임 관측 문자열).
해결책이 아니라 **채점표**다.  무슨 가설을 시도하든 사람 눈 안 거치고 판정된다.

원인은 미해결.  정렬(phase)은 이미 4 종 다 쓸어봤으므로 정렬 문제가 아니다.
후보: 디코더가 장면별 CPU/뱅크 상태를 탄다 · 그 장면은 `script = text - 0x2000`
쌍이 아니다 · 초기 논리 포인터가 다르다.

**구조 자체는 확정됐다.**  게임은 텍스트를 통문장으로, 나오는 순서 그대로 저장한다.

```
장면 27 개 중  text_pointer 단조증가 27/27 · command_offset 단조증가 27/27
역행 0 건 · 포인터 간격 중앙값 32 B

명령 1 개 = 포인터 1 개 = 완결된 문장 1 개
1C 63 12 <arg0> <arg1> <textPtrLo> <textPtrHi>
         ^^^^^ 화자 ID (51 종)
```

조각을 조립하는 구조가 **아니다.**  플래그는 문장을 조립하는 게 아니라 **통문장
중에 고른다.**  같은 문자열이 디스크 2~6 곳에 중복 저장된 게 1,731 건인 것도 같은
얘기다.  raw 추출에서 조각처럼 보인 것은 토큰 압축을 잘못된 지점부터 푼 결과다.

## 5. 수집 계기판

음성은 표지재포획으로 진행률이 나온다.

```
관측 고유 클립 404 · 총 관측 2,515 · f1=136 · f2=58
Chao1 추정 563  ->  탐색 범위 커버리지 72% · 미발견 약 159
Good-Turing 95%  (다음에 만나는 클립이 새것일 확률 5%)
```

-> **지금 도는 구역은 거의 다 긁었다.**  남은 159 는 잘 안 나오는 조건부라 여기서
   더 갈아도 효율이 안 난다.  진도를 빼는 게 낫다.

**텍스트는 계기판이 없다.**  마스터의 `seen` 열이 전부 0 이다.  수집기가 레코드마다
목격 횟수만 세주면 같은 계산이 된다.  플래그 조합 때문에 표집으로는 못 채우는
구조라, 어느 구역을 다 긁었는지 아는 게 특히 중요하다.
