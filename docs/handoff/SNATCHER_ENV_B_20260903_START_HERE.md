### 0-1-1. ★★ 정적 분석으로 이미 나온 것 — Lua 판은 이식할 수 없다

`0.4.48-fragment-wipe.lua` 를 읽었다.  머리말이 우리가 어젯밤 측정한 증상을
**그대로** 적어놨다:

> 0.4.47은 음성 전체 종료 때만 지웠다.  여러 조각짜리 음성은 다음 조각의 PATCHED가
> 발생한 뒤에도 **이전 조각 SATB가 한 프레임 남을 수 있다.**  그 사이 이전 VRAM
> 블록의 게임 패턴이 UI 조각처럼 비친다.

즉 **한 프레임 지연은 2026-08 에 이미 알려져 있었다.**  그리고 그 판이 그것을
어떻게 덮었는지가 문제다:

```lua
local SPR = emu.memType.pceSpriteRam
...
wipeSelected = function(reason)
  local v = wipeTable(VRAM, SATB)     -- VRAM 의 SATB
  local s = wipeTable(SPR, 0)         -- ★ VDC **내부** Sprite RAM
```

**VDC 내부 스프라이트 RAM 을 직접 지웠다.**  그곳은 SATB DMA 로만 채워지고
**HuC6280 코드로는 주소가 없어 쓸 수 없다.**  에뮬레이터에서만 되는 반칙이다.

```
-> FRAGMENT_TEAR §5 의 "남은 길은 B 의 네이티브 이식" 은 **무효다.**
   B 는 이식할 수 있는 방법이 아니었다.
-> Lua 가 "됐다" 는 기록도 그대로 믿으면 안 된다.  하드웨어가 못 하는 일을 하고 있었다
```

★ 그러면 네이티브에서 가능한 길은 하나로 좁혀진다:
  **스프라이트 표 갱신이 글리프 업로드와 같은 프레임에, 그 프레임의 SATB DMA 이전에
  VRAM 에 도달하게 만드는 것.**  지우는 문제가 아니라 **도달 시점** 문제다.

  그리고 §3 이 그 도달을 막는 것을 이미 지목한다 -- 우리가 MAWR 을 안 돌려줘서
  게임의 SATB 갱신 256 word 가 우리 VRAM 으로 새고 있다.
  **`0.5.133` 이 그 연결을 시험하는 판이고, 아직 안 돌렸다.**

### 0-1-2. ★ Lua 판이 정확히 어느 판인지 (확인 완료)

### 0-3-1. 렌더러 코드는 완전히 동일하다

## 3. 확정된 사슬 하나 — MAWR 을 빌리고 안 돌려준다

증상 2(음성 종료)의 원인은 **아니지만**(0.5.126 으로 기각), 실재하는 버그다.
그리고 증상 1(조각 전환)에는 아직 살아 있는 후보다.

```
게임이 line 20~42 에 MAWR = $1000 을 잡는다 (SATB 갱신 준비)
우리가 line 29~62 에 MAWR 을 가져간다 (글리프 업로드 또는 복원)
게임이 line 197~231 에 SATB 256 word 를 흘린다.  MAWR 을 다시 안 잡는다
  -> 우리 VRAM 뒤쪽으로 떨어진다
  -> 그 프레임 스프라이트 갱신이 사라진다
```

증거:

```
PC     A(우리) $5C33          B(게임) $60BA x25 · $650C x10   MPR 도 다르다   0.5.125
       $60BA/$650C 는 09-01 이 적어둔 $60AC/$6506 과 같은 루틴이다
크기   글리프 프레임 word = 칸수x64 + 256                                    0.5.132
       960=11x64+256 · 768=8x64+256 · 832=9x64+256 · 1152=14x64+256
개입   복원 뒤 MAWR=$1000 을 되돌리면 B 가 $1000-$10FF 로 간다               0.5.126
```

⚠ `0.5.126` 은 `$15` 가 **19 에서 시작**하는 복원만 잡았다.  렌더러의 글리프 루프는
8·11·14 에서 시작해 전혀 안 걸렸다.  그래서 개선이 0 이었다.
`0.5.133` 이 양쪽을 같은 훅으로 덮게 고친 판이다 — **아직 안 돌려봤다.**

⚠ MAWR 은 HuC6270 에서 **write-only** 라 "빌리기 전 값을 떠뒀다 되돌린다" 가 안 된다.
  상수 `$1000` 이 이 장면에서는 맞지만 다른 장면은 안 쟀다.

⚠ `0.4.6.52` 의 실패를 MAWR 탓으로 돌리지 말 것.  그 8 B 는 렌더러의 y 계산
  (자막 세로 자리 기능)을 죽여서 마련한 것이라, **MAWR 복원만 단독 시험된 적이 없다.**

## 7. 별건 — CD-DA 예약 자리 $79xx (소스 수정 완료 · 디스크 미반영)

헬퍼 복원이 목적지 상위바이트로 지우기/되쓰기를 가른다 (`CMP #$79`).
자리를 키별로 나눠주면서 ADPCM 키도 `$79xx` 를 받게 됐고, 그러면 백업이 있는데도
blank 로 가서 **그 자리가 까맣게 남는다** (1 프레임이 아니라 지속 손상).

```
고친 곳  tools/build_vram_key_bases.py
         CDDA_RESERVED_HI / is_cdda_reserved() · A/B 맞바꿈 · 빌드 관문
결과     키 1157 -> 1157 · base_a 바뀐 키 15 (전부 순수 맞바꿈) · 남은 $79xx 0
백업     _backup_vram_bases_20260902/
```

### 7-1. ★ 표를 다시 구울 때의 정본 인자

```
python tools/build_vram_key_bases.py --pairs --align 0x100
```

`--align` 을 빼면 기본 `0x20` 이 되어 base 가 전부 밀리고 **2,290 행이 바뀐다.**
어젯밤 한 번 밟았다.  `BUILD_CHAIN_2026-09-02.md` §1 에 이 인자가 없다.

⚠ 아직 디스크에 안 실렸다.  base 즉치값은 네이티브 디렉터리(route 당 9 B 의 뒤 3 B)에
들어가므로 표만 고쳐서는 반영되지 않는다.  팩은 안 바뀌므로 팩 자리 왕복은 없을 것이다.
