## 2. 몫이 어떻게 나뉘어 있나

**"Lua 는 데이터만 나른다" 는 말은 정확하지 않다.** 판단도 아직 Lua 가 한다.

### 디스크 (6280) — 다 됐다

```
$601E   20 A0 7F EA        JSR $7FA0 / NOP   (원래 LDA #$3F / STA $17 을 밀어냄)
$7FA0   상주부 32 B         매직 3 B 를 보고 맞으면 JSR $5B83
```

훅과 상주부가 **같은 오버레이에 같이 실린다.** 오버레이가 갈리면 둘 다 사라지고
같이 돌아온다 — 한쪽만 남아 남의 코드가 우리 자리로 뛰어드는 일이 구조적으로 없다.
아침의 UI 복구 실패가 정확히 그 잔류 때문이었다.

상주부는 **일을 안 한다.** 판단 하나만 하고 넘긴다:

```
7FA0  08 78              PHP / SEI
7FA2  A9 3F 85 17        LDA #$3F / STA $17      밀려난 원래 명령 -- 항상
7FA6  AD 80 5B C9 53 D0  LDA $5B80 / CMP #'S' / BNE   ┐
7FAD  AD 81 5B C9 55 D0  LDA $5B81 / CMP #'U' / BNE   │ 매직 3 B
7FB4  AD 82 5B C9 42 D0  LDA $5B82 / CMP #'B' / BNE   ┘
7FBB  20 83 5B           JSR $5B83               엔진 진입점
7FBE  28 60              PLP / RTS
```

매직을 3 바이트 보는 이유: `$5B80` 은 VM 스택 바닥이라 음성이 아닐 때는 게임 값이
들어 있다. 그냥 `JSR` 하면 쓰레기를 실행한다 — `SUBTITEL 0.2.5` 가 정확히 그렇게
부팅에서 멈췄다. 2 바이트면 60 fps 로 18 분마다 우연히 맞고, 3 바이트면 3 일이다.

**엔진이 없으면 이 디스크는 아무 일도 안 한다** (매직 불일치 -> 즉시 RTS).
"안 켜면 깨끗" 으로 확인됨.

### 엔진 (6280 · `$5B80` 704 B 중 362 B)

```
글리프를 AC -> 창 -> VRAM $7900 에 올린다 (ready 플래그로 조각당 한 번)
스프라이트 팔레트 15 의 색 1(흰) · 2(검) 을 세운다
레코드를 zp 에 걸고 게임 푸시 루프 $6463 을 부른다
```

**우리가 VDC 를 직접 안 건드린다.** 게임이 SATB 를 조립하기 직전에 우리 것을 먼저
밀어 넣으므로 슬롯 0 부터 차지하고, 그래서 그림·초상화보다 앞에 그려진다.
MAWR 은 `$6008` 에서 이미 슬롯 0 에 서 있고 우리 푸시가 `$17` 을 깎으므로
`$60A6` 의 0 채우기도 저절로 맞는다.

레코드는 글자당 5 B — `$6463` 이 먹는 형태다:

```
00 00 <x오프셋> <패턴워드 lo> <0x80 | (패턴워드 hi << 4) | 팔레트>
                              ^^^^   ^^^^^^^^^^^^^^^^^^   ^^^^^^^
                              앞쪽    $64D6 이 AND #$70    $64F8 이 AND #$8F
```

### Lua — 판단과 나르기 둘 다

**판단**

```
음성 시작/끝    emu.getState()['cdrom.adpcm.playing']
지문            읽기주소 + 길이 = 끝 주소      ★ 합만 안 변한다 (§5)
팩에 있나       ADPCM 색인 선형 탐색           = 효과음 필터
몇 번째 조각    흐른 프레임 vs start_frame
```

**나르기** (음성 하나당)

```
엔진 362 B          -> $5B80 (매직 포함)
글리프 n x 64 B     -> AC $1F1400   16 자면 1,024 B
레코드 n x 5 B      -> 엔진 안 list
글자수 2 곳 · y     -> 엔진 안 즉치값
VRAM 1,216 워드     떠 뒀다가 음성이 끝나면 되돌린다
```

팩과 `engine.bin` 을 **호스트 파일에서** 읽는다. 게임 안에는 아직 없다.

## 3. 자리표 — ★ 적재 작업의 전제

`tools/subtitle_layout.py`. 자리는 **한 곳에만** 적는다.

빌더마다 상수를 따로 들고 있었더니 실제로 겹쳤다:

```
팩            $1C0000 에 두려고 했다
글리프 스테이징  엔진과 Lua 가 $1C0000 에 썼다      <- 같은 자리
```

팩을 아직 AC 에 안 올려서 안 터졌을 뿐이다. 올리는 순간 **첫 글자가 팩 머리를 덮는다.**
적재 타이밍을 손대기 직전에 터졌을 문제다.

```
AC 예약  $1C0000-$1FFFFF  256 KB
  $1C0000  192 KB 까지   팩              지금 8.8 KB · 613 조각이 다 차도 ~110 KB
  $1F0000    1 KB        엔진 이미지      상주부가 $5B80 으로 복사할 원본
  $1F0400    4 KB        VRAM 백업        음성 중 빌린 VRAM 을 떠 두는 자리
  $1F1400    2 KB        글리프 스테이징   ★ 임시 -- 엔진이 팩을 직접 읽으면 없어진다
  $1F1C00   57 KB        남는 자리

RAM   $7FA0 상주부 32 B (헬퍼 여유 151 B 안) · $5B80 엔진 704 B (음성 중에만)
VRAM  $7900 부터 19 x $40 워드 (음성 중에만 · 되돌린다)
```

`$1F0000` 과 `$1F0400` 은 **아직 아무도 안 쓴다** — 3·4 단계에서 쓸 자리를 미리
잡아 둔 것이다. `subtitle_layout.check()` 가 겹침과 예약 초과를 잡는다.

### 왜 이것이 다음 작업의 전제인가

적재 경로를 설계하려면 **적재물 목록과 목적지**가 있어야 한다. 전에는 "자막 데이터"
가 뭉뚱그려져 있어 로더 쪽에 요구사항을 못 넘겼다.

```
최초 적재 타이밍   "접수처 전에 팩 8.8 KB 를 $1C0000 에"   -> 문장이 완성됐다
엔딩 크레디트      AC 를 언제 비우고 채우나                -> 어느 구간이 자막 것인지 명확
```

## 4. Lua 를 걷어내는 순서 — ★ AC 부팅 로더가 마지막이다

한때 "AC 적재가 관문이니 거기부터" 라고 적었는데 **순서가 거꾸로였다.**
AC 는 런타임에 쓸 수 있다. Lua 가 시작할 때 팩을 한 번 부어 놓으면, 부팅 로더 없이도
엔진이 팩을 직접 읽을 수 있다.

```
1  Lua 가 팩 8.8 KB 를 AC $1C0000 에 한 번 붓는다        몇 줄
2  엔진이 AC 에서 조회한다 (끝 주소 선형 탐색)
     -> Lua 의 레코드 만들기 · 글리프 1 KB 나르기가 통째로 사라진다
3  엔진이 VRAM 을 저장/복원한다 (버퍼는 AC $1F0400)
     -> Lua 의 제일 큰 나르기가 사라진다
4  상주부가 음성을 감지하고 엔진을 AC $1F0000 에서 복사한다
     -> Lua 가 $5B80 을 안 건드린다
5  AC 적재를 게임 부팅 경로로 옮긴다
     -> Lua 없음
```

각 단계가 무엇을 남기나:

```
2 번 뒤   Lua: 엔진 올리기 + 매직 지우기 + VRAM
3 번 뒤   Lua: 엔진 올리기
4 번 뒤   Lua: 부팅 때 팩 붓기 한 번   <- 사실상 다 된 상태
5 번 뒤   없음
```

### 예산

```
헬퍼 여유 151 B    상주부 32  ->  남은 119 B      (4 번이 여기 들어간다)
엔진 704 B         지금  362  ->  남은 342 B      (2·3 번이 여기 들어간다)
AC 예약 256 KB     팩 8.8 KB  ->  넉넉
```

조회는 곱셈이 없는 선형 탐색이고 VRAM 복사는 TIA/TAI 블록전송이라 342 B 안에
들어갈 크기로 보인다. **다만 재 보고 정할 것.**

### 5 번을 손대기 전에

`_archive/build_records/DELETED_BUILDS_2026-08-13.md` 를 읽을 것.
CD 읽기가 느려 AC 로 옮긴 경위와 **철회된 비용 계산**이 들어 있다.
관련: `build/patch/0.4.5.6/manifest.json` 의 `ac_dynamic_packs`.

## 5. 오늘 밤 뒤집힌 것 셋

### 지문은 끝 주소로 정규화해야 한다

팩 버전 2 는 `(읽기주소, 길이, 재생률)` 세 값을 정확히 맞추려 했다. **하나도 안 맞았다.**

```
팩 0063+CF9D = D000     런타임 0068+CF98 = D000
팩 0066+579A = 5800     런타임 0064+579C = 5800
팩 006B+6795 = 6800     런타임 0070+6790 = 6800
```

재생 시작 지점이 매번 달라 읽기주소와 길이가 서로 상쇄되고, **합만 안 변한다.**
기존 연구의 "끝 주소로 정규화" 가 이 뜻이었는데, 팩을 만들 때 "정확한 세 값이 더
정밀하다" 며 일부러 뺐다. 정밀한 것이 아니라 **안 맞는 값**이었다.

> 대가는 알고 간다: 449 이벤트 -> 71 열쇠로 뭉갠다. 빌더가 충돌을 세어 보고한다.

### 팔레트 0 은 메뉴가 쓴다

레코드 5 번째 바이트의 **하위 니블이 팔레트 번호**다 (`$6463` 이 `AND #$8F` 로 속성을
뽑는다). 0 으로 두고 팔레트 0 의 색 1·2 를 흰/검으로 덮었더니 **메뉴 선택
하이라이트가 깨졌다.** 팔레트 15 로 옮겼다 (VCE `$1F1`).

### VRAM 은 빌리되 되돌려야 한다

```
항상 빈 VRAM 은 없다       32768 워드 중 31620 이 쓰인다   PROBE_VRAM_FREE 0.2.0
음성 중에는 거의 안 쓴다    $2078-$7FFF 24456 워드 무변화   PROBE_VRAM_VOICE 0.1.0
```

`$5B80` 과 같은 모양이다. 다만 **RAM 과 달리 게임이 안 지운다** — 하이라이트가 음성이
끝난 뒤에도 계속 깨져 있었다. 그래서 음성 시작에 떠 두고 끝나면 되돌린다.

### 규칙이 세 겹 늘었다

```
Write 를 못 봤다 != 안전                     (ARENA §7 · 기존)
안 돌더라도 코드가 있으면 산 자리다            오버레이 구멍 여섯 중 다섯이 휴면 코드였다
패치 실험은 실제로 돌리는 디스크로 할 것       원본에 구운 표식이 안 나온 것은 당연했다
                                            (헬퍼는 KO 패치에만 있다)
```

## 6. 자리 (위 · 중간 · 아래)

기록 머리의 남는 바이트를 y 로 쓴다 (팩 버전 4 · **크기가 안 늘었다**).

```
+00 cells u8 · +01 width u8 · +02 flags u8 · +03 ★y u8 · +04 frames u16
```

```
위 32 · 중간 122 · 아래 192        기본  ADPCM 중간 · CD-DA 아래
```

**중간 122 가 눈으로 맞춘 값**이라 게임 중 대사는 그대로고, 컷신은 화면을 다 쓰므로
아래로 간다. 자막 **한 줄 단위**라 특정 줄만 올릴 수도 있다.

값은 `tools/subtitle_layout.py` 가 아니라 `tools/build_subtitle_pack.py` 의
`POSITIONS` 에 있다. 화면 자리라 AC/RAM 자리표와 성격이 다르다.

TSV 의 `pos` 열에 `위`/`중간`/`아래` 를 적으면 그 줄만 바뀐다. 비면 기본값.
**스튜디오에 버튼은 아직 없다.**
