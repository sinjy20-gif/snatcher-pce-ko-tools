## 0. 원인 — CPU 점유가 게임의 래스터 갱신과 겹친다

Mesen Event Viewer 에서 **Arcade 이벤트만 켜니 그림 한가운데를 가로지르는 초록
일자**가 보였고, 그것이 깨지는 순간의 그 자리였다.

```
게임    하늘을 10~12 줄마다 스크롤을 갈아끼우며 그린다.
        Event Viewer 실측: 스캔라인 32 · 42 · 54 · 64 ... 마다 같은 여섯 쓰기가 반복
        ($43F7 · $43FD · $4408 · $440E · $E428 · $E42B)
우리    레코드 하나를 재구성하는 데 12.3 스캔라인을 CPU 로 점유한다 (TAI 연속)
충돌    점유가 갱신 시점과 겹치면 갱신이 한 줄 늦게 들어가고 경계가 밀린다
```

경계는 화면 Y≈139 이고, 그 자리에 우리 AC 접근이 가로줄로 찍힌다.

### 용량-반응이 확인됐다

이것이 상관을 넘어 인과로 볼 근거다.  소유자 관측:

> 깨지는 순간에 초록색으로 사진 중간을 일자로 좀 넓게 채운다.
> **이게 넓으면 많이 깨지고 작으면 작게 깨진다.**

초록 띠의 폭 = 그 프레임에서 우리가 CPU 를 점유한 양이고, 그것이 깨짐의 정도와
같이 움직인다.  원인이라면 양이 늘 때 결과도 늘어야 하는데 정확히 그렇다.
이분탐색(0.2.26 정상 / ac_0.1.14 최악 / 0.3.3+ 개선)이 판 단위로 보여주던 것을
**한 화면 안에서 프레임 단위로** 다시 확인한 셈이다.

### 이 기전이 그동안의 모순을 전부 설명한다

| 관측 | 설명 |
|---|---|
| 프레임이 안 넘친다 (0/1782) | 둘 다 결국 끝낸다.  총량 문제가 아니다 |
| 레지스터 값이 두 판 동일 | 늦게 썼을 뿐 값은 같다 |
| VRAM 이 두 판 동일 | 그려질 내용도 같다 |
| 인터럽트 차단을 0.27 줄로 줄여도 그대로 | IRQ 지연이 아니라 **CPU 점유**다 |
| 비용을 줄이면 실제로 나아진다 | 점유 줄 수가 줄어 겹칠 확률이 준다 |
| ac_0.1.14 가 제일 심하다 | 템플릿 608 B 통짜라 점유가 가장 길다 |
| 0.2.26 은 정상이다 | CPU 재구성이 없다.  CD 가 캐시로 직접 넣는다 |
| 호출이 드문데(세션 425 회) 증상은 잦다 | 겹칠 때만 나므로 호출 수와 증상 수가 다르다 |

### 그래서 남은 선택지

```
점유 줄이기      12.3 -> ?  §4.5 에서 32% 줄여 실제로 개선됐다.  여지는 작다
언제 하느냐      갱신이 없는 구간에 작업을 배치.  런타임 상태가 늘어나는 구조 변경
현행 유지        진행 불가·손상 없음.  특정 장면에서만 드러난다
```

**"더 빠르게" 보다 "언제" 가 본질이다.** 12 스캔라인을 0 으로 만들 수는 없지만,
갱신이 없는 자리로 옮기는 것은 원리적으로 가능하다.  다만 헬퍼 여유가 56~70 B 라
그 판단 로직이 들어갈지는 별도 검토가 필요하다.

## 1. 증상이 무엇인지 (측정됨)

지금까지 "폐공장에서 그림이 밀린다"는 눈으로만 있었다. 이제 숫자다.

```
화면 경계가 59줄 -> 64줄로 내려가 11~18프레임(0.2~0.3초) 머물다 돌아온다
대사에서 메인 UI 로 복귀하는 순간에 난다
지속구간이 세션마다 6~7개, 전부 64줄에 11~18프레임으로 균일
E 마커 여러 개가 구간 종료 8~16프레임 뒤에 찍혔다 (사람 반응시간과 일치)
```

**한 프레임 튐이 아니라 0.3초짜리 느려짐**이고, 그동안 경계가 밀려 있다.
소유자 표현으로 "게임이 느려져서 밀리는 게 아주 잘 보인다".

균일성이 중요하다. 단발 사고면 길이와 값이 저렇게 고르지 않다. 소유자 판단대로
**폐공장 고유 현상이 아니라 거기서 드러났을 뿐**일 가능성이 높다.

## 2. 기각된 가설 — 다시 파지 말 것

| 가설 | 근거 |
|---|---|
| UI 렌더링 | `0.3.4-noui`(UI 통째 제외)도 똑같이 밀린다 |
| ADPCM 이 CPU 를 훔친다 | 재생 중/아닌 중 `copy_record` 중앙값이 **15,132 로 사이클까지 동일** |
| CD 경합 | `packloads=0 / cdreads=0` 인데 밀린다 (0.3.3-preload, 08-14) |
| 스프라이트 / VDC 대역 | `DisableSprites` 로도 밀린다 |
| 인터럽트 차단 (TAI) | 76 → 38 → 16 B (1.04 → 0.54 → 0.27 스캔라인) 인데 그대로 |
| RCR 이동 | RCR 은 **71 로 고정**, 세션 내내 한 번도 안 바뀐다 |
| `copy_record` 비용 | 지속구간 안 0~1건, 앞뒤 60프레임에도 2~4건뿐 |

마지막 둘이 오늘의 핵심이다.

### 2.1 RCR 은 안 움직인다

경계가 밀리니 래스터 분할이 이동하는 줄 알았다. `vdc.rasterCompareRegister` 를
직접 보니 **71 고정**이다. 분할선 자체는 제자리고, 움직이는 것은 그 뒤의 무엇이다.

### 2.2 헬퍼는 너무 드물게 돈다

`PROBE 0.2.7` 로 헬퍼 진입점부터 반환까지 잡았다.

```
헬퍼 진입 92 · copy_record 87 · miss 5      (한 세션)
어긋난 프레임 1,658
```

미번역 줄의 조회가 숨은 비용일 것이라 봤는데 **miss 가 5건뿐**이다. 진입과 copy
가 거의 같아 숨은 호출량이 없다. 그리고 호출이 92번인데 증상은 1,658 프레임이다.
**우리 코드가 도는 것보다 증상이 훨씬 많다.**

## 3. 그래도 우리와 무관하지 않다 — 이것이 모순이다

이분탐색은 뒤집히지 않는다.

```
0.2.26 (AC 이전)     정상
ac_0.1.14 (AC 도입)  제일 심함
0.3.3+ (최적화 후)   덜함
```

AC 로 옮기면서 생겼고, 레코드당 비용을 줄이면(TAI 분할 + 경계 지우기, 5,631 →
3,829 사이클) **실제로 덜해진다**. 소유자가 세 판을 눈으로 확인했다.

그런데 셋이 동시에 성립한다.

```
1. 호출은 드물다 (세션당 92회)
2. 비용을 줄이면 나아진다
3. 호출 시점에는 증상이 없다
```

**이 셋을 함께 설명하는 가설이 아직 없다.** 여기가 막힌 지점이고, 다음 사람이
풀어야 할 것이다.

## 4. 아직 안 잰 것 하나

`PROBE 0.2.7` 의 census 를 못 받았다 — Stop 전에 디스크를 바꿨다.
**헬퍼 진입~반환 한 번의 실제 사이클**이 거기 있다.

지금 있는 값은 `copy_record` 구간만의 것이다.

```
copy_record   15,132 masterClock = 5,044 CPU = 11.1 스캔라인
진입~반환 전체  ?                                <- lookup(AC 포트 접근) 포함
```

이 값이 40~50 스캔라인이면 3장의 모순 1과 3이 풀린다. 호출이 드물어도 한 번에
프레임의 20% 를 먹으면 그 순간 드러나니까. 11 근처면 헬퍼는 통째로 무죄고,
**AC 하드웨어 접근 자체**를 봐야 한다 — 0.2.26 이 안 건드린 유일한 것이다.

```
python  ->  lua\PROBE 0.2.7.lua  ·  BUILD="0.3.4"  ·  폐공장  ·  반드시 Stop
```
