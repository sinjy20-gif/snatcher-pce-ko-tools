# SNATCHER GFX native 재검토 인계 — 2026-09-09

## 한 줄 결론

현재 GFX native POC는 **완성 또는 채택 상태가 아니다.** r4는 r3에서 확인된
타이틀 화면 오탐을 줄이려던 임시 후보일 뿐이며, 공용 타일 업로더에서 장면을
추측하는 설계 자체를 다시 검토해야 한다. 실제 Mesen 판정 전에는 후속 화면을
추가하지 않는다.

## 현재 상태

- 기준판: `0.6.2`
- 마지막 실험 후보: `build/patch/_FAILED_EXPERIMENTS_2026-09-09/0.6.3-gfx-native-poc-r4`
- 목적: Lua `GFX/0.3.0`에서 검증한 dedication 한 화면을 BIOS 상주 코드로 이전
- 런타임 판정: **미완료**
- 배포 판정: **사용 금지 / POC 보존만**
- 자동 정적 검사: 통과
- 실제 결과: 앞 장면부터 게임 그래픽 파손. 뒤의 날짜 화면은 다시 올린 타일/BAT로
  일시 정상처럼 보였으나 게임 전체가 이미 깨진 상태였음.

후보 해시:

- BIOS `7A238DFF427628003C1C35A3B7EC21DA9C0671F554D54A9A04B04B6122B90978`
- Track02 `E550E6FFE8091D2863AAC23E28E063356D40AFB044D10E5C0A62B4E10CE41DC0`
- Track24 `4C3EAEED7AAC09D2BC5DE43AA5C62C52F90127944E0F1A3BB8B805737A2FF174`
- GFX payload `AE1168EB037279E04BE3E3D76A8E0DE2A47835A5F77DB444AB9BE36080A022CE`

## 무엇이 잘못됐는가

구현의 직접적인 문제보다 **장면 식별 전략**이 약하다.

현재 진입점은 Track 02의 공용 `$725C` 타일 업로더 직전 `$7256`이다. 이 업로더는
dedication 전용이 아니므로, 여기에 들어왔다는 사실만으로 대상 화면을 확정할 수
없다. r3는 `$3B00`에 들어오는 원본 타일 `$16A`의 첫 16 B를 지문으로 썼지만,
타이틀 / 시작 선택 화면에서 같은 지문이 재사용되어 화면 전체를
헌정 타일/BAT로 오염시켰다.

r4는 아래 두 조건을 함께 쓴다.

1. 게임 드라이버 현재 CD-DA track `$263B == $17`(BCD)
2. `$3B00`의 16 B 타일 지문 일치

이 조합은 **이미 발견한 타이틀 오탐을 차단하려던 방어책**이지, dedication을
유일하게 식별한다는 증명은 아니다. 같은 Track 17 안에서 동일 타일이 다시 쓰일
수 있고, 음악 재생 상태와 화면 로딩 상태가 항상 일대일이라는 보장도 없다.
고정 12프레임 대기 역시 현재 장면의 관측값일 뿐 모든 실행 환경에서 안정적인
장면 경계라는 증거가 없다.

따라서 r4가 Mesen에서 한 번 성공하더라도 곧바로 150개 화면에 일반화하면 안 된다.

## 실험판별 결과

  추정 복원하면서 진행 중인 영상 전송을 파손.
- 판정: 실패, 사용 금지.

  프레임에 덮여 목표 타일을 놓침.

### r4 `0.6.3-gfx-native-poc-r4`

- 변경: `$263B == $17`을 먼저 확인한 뒤에만 16 B 지문 검사.

- 판정: **실패. 사용 금지.** 격리 폴더로 이동함.

## 다음에 다시 시작할 때

우선 dedication과 오탐 장면의 **장면 전용 신호**를 찾아야 한다. 다음 순서를 권장한다.

1. dedication 진입 직전부터 `$7256/$725C`까지 호출 경로와 관련 RAM 값을 기록한다.
2. 같은 기록을 타이틀 / 시작 선택 화면에서 뜬다.
3. 두 경로를 비교해 스크립트 명령, 이벤트/장면 번호, 원본 데이터 포인터 또는
   전용 callsite처럼 화면과 일대일인 값을 찾는다.
4. 전용 신호가 없다면 공용 업로더 후킹을 포기하고, 더 위쪽의 화면 로드 명령이나
   해당 화면 전용 데이터 참조 지점을 후킹한다.
5. 한 화면에서 `헌정 성공 → 이탈 정상 → 재진입 정상 → 타이틀 정상`을 모두 통과한
   뒤에만 두 번째 화면을 추가한다.

하지 말아야 할 것:

- 타일 지문 길이만 늘려서 장면 ID처럼 취급
- CD-DA/ADPCM 재생 상태만으로 화면을 확정
- r4 성공 1회를 근거로 전체 GFX dump를 일괄 등록
- r3에서 만든 Mesen 상태 저장으로 r4를 판정

## ⚠ 정정 — 2026-09-09

**r3 오탐 장면은 "첸슈호 대화 종료 부근" 이 아니라 타이틀 / 시작 선택 화면이다.**

소유자 확인 + 캡처 실물 확인으로 바로잡았다. `037-...-remix-corruption-important.png`
에 「初めから」「<원문 8자>」가 그대로 보이고, `036-...-false-positive-suspect.png`
는 타이틀 화면이다. 첸슈호는 같은 시기 **CD-DA 작업** 이야기가 섞여 들어간 것이며
그 장면에서 GFX 오염은 일어난 적이 없다.

이 정정이 중요한 이유 — **r4 의 설계 근거가 무너진다.**

r4 는 "오탐이 게임 후반이므로 CD-DA track 문(`$263B == $17`)으로 막는다" 는
전제였다. 그런데 실제 오탐 자리는 **부팅 직후**다. 그 시점의 `$263B` 는 게임
드라이버가 아직 채우지 않은 **쓰레기값**이라 문이 열려 있을 수 있다.

### r4 실기 결과 (2026-09-09, 소유자)

```
시작부터 배경 스프라이트가 전부 깨진다.  r3 보다 나쁘다.
```

판정: 실패, 사용 금지. 두 조건(타일 지문 · CD-DA 트랙)이 다 약한데 AND 로
묶어서 강해 보였을 뿐이다. 지문 `80 00 40 00 20 00 10 00 08 00 04 00 03 00 FC 00`
은 대각선 한 줄이라 부팅 그래픽에도 얼마든지 나온다. 어젯밤 지문 오탐 감사는
`gfx_*.vram.bin` 29 개로 했는데 **타이틀·부팅 화면이 그 29 개에 없었다.**

### 디스크 바꿔치기 길은 닫혀 있다 (2026-09-09 실측)

원본 타일을 디스크에서 직접 교체하면 런타임 코드가 0 이라 오탐이 원리적으로
불가능하다. 그래서 다시 찾아봤다 -- 헌정 화면 VRAM 덤프의 타일 `$16A` 부터
**연속 8 장(256 B)** 을 네 형태로 트랙 01·02·24 전수 검색:

```
raw · swap16 · planes · half01   ->  세 트랙 모두 0 곳
```

압축이거나 다른 인코딩이다. 그러므로 런타임 주입이 유일한 길이고, 문제는
**장면 식별** 하나로 좁혀진다.
