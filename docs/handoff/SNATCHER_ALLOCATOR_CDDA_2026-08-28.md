## 3. ★ 초상화 아래 깨짐 — 원인 확정

### 3-1. 시험 장치를 먼저 만들었다

자막이 음성 하나(`E6800_0E`)에서만 떠서 allocator 에 부하가 안 걸렸다.
**selector 를 만들지 않고** 문지기만 열어 부하를 만들었다.

```

  케이브 문지기 세 줄 중 신원 검사 두 줄만 NOP
    AD A6 22 D0 xx              끝주소 하위   ★ 지운다
    AD A7 22 C9 68 D0 xx        끝주소 상위   ★ 지운다
    AD AA 22 C9 0E D0 xx        재생 속도     남긴다
                                ⚠ 이것으로 효과음이 걸러진다고 적었으나 **틀렸다** (§9)
  -> build/patch/0.4.6.10/Syscard3_galmuri_0.4.6.10_allvoice.pce

selector($5CEE)는 그대로라 어떤 음성에서든 같은 자막 한 줄이 뜬다.
내용은 상관없다 -- 뜨기만 하면 allocator 가 돈다.
디스크는 0.4.6.10 그대로.  BIOS 만 바꿔 끼운다.
```

짝이 되는 Lua 와 도구:

```

## 4. CD-DA — 위치 추정이 풀렸다

### 4-1. 무엇이 막혀 있었나

CD-DA 자막은 **재생 중인 섹터가 어느 구간에 드는가**로 고른다.

```
lba_from <= 현재섹터 <= lba_to
색인 646 항목 · 10 B (lba_from u24 · lba_to u24 · rec_off u24 · flags u8)
lba_from 정렬 -> 이분 탐색 10 회
```

Lua 는 `cdrom.audioPlayer.currentSector` 를 읽으면 됐지만 **실기에는 그런 게 없다.**
그래서 "위치를 계속 따라갈 수 있나" 가 미지수였고, 그게 풀리기 전에는 훅을 찾아도
소용이 없었다.

### 4-2. 실측 — 프레임만 세면 된다

`lua/SUB/CDDA_DRIFT_0_1_0.lua` 로 쟀다.

```
실측   1,429 섹터 / 1,140 프레임 = 1.2535 섹터/프레임
가정   75 / 60      = 1.25      <- 어긋난다
정답   75 / 59.826  = 1.25364   <- 실측과 소수점 넷째 자리까지 일치
                                   PC엔진은 60 Hz 가 아니다
오차   8,581 프레임(143 초)에 4 섹터 (0.05 초)
```

**자막에는 차고 넘친다.**  케이브가 프레임 카운터 하나만 들면 된다.

### 4-3. 남은 미지수 하나

```
실기에서 시작 LBA 를 어디서 얻나
  후보 1  BIOS 의 CD-DA 재생 상태 변수
  후보 2  게임이 CD-DA 재생을 요청할 때 넘기는 인자를 훅에서 가로챈다   <- 유력
  후보 3  SUBQ 직접 읽기 (정확하지만 비싸다)
```

Lua 로 먼저 찾을 수 있다 — CD-DA 가 시작되는 순간의 BIOS 호출과 인자를 잡으면 된다.
**그것만 찾으면 나머지는 기계적이다.**

### 4-4. 재료는 다 있다

```
한국어    cdda_subtitles.tsv  648 행 · 408 클립 (c01~c19 컷신 전체.  오프닝만이 아니다)
팩 색인   CD-DA 646 항목 (팩 89,598 B · 버전 5 · 글리프 620 · ADPCM 118)

## 8. ★ 0.3.42-wide 실측 — 위험하다.  그대로 쓰지 말 것

§3-4 를 실행했다.  **창 확장은 동작했지만 게임이 멈췄다.**

```
고른 자리   $6000 37 · $6400 27 · $6700 4 · $6600 4 · $6A00 2
            $1A00 1 · $1600 1        <- 앞쪽으로 내려간 것은 두 번뿐
침범        5 건 전부 §3-2 의 $6000 건.  $1xxx 에서는 안 잡혔다
증상        퀸 병원 **입장하는 순간** 화면 전체 초록 · FPS 0
```

### 8-1. 유력한 원인 — 복원(restore)이 장면 전환을 덮는다

allocator 는 자막 시작에 base 자리를 백업하고, 음성이 끝나면 되돌린다.

```
자막 시작    base 의 VRAM 을 백업
자막 끝      백업본을 다시 쓴다
그 사이에 장면이 바뀌면  ->  새 장면 데이터 위에 **옛 데이터**를 덮어쓴다
```

좁은 창($6000 대)에서는 게임이 그 자리를 곧 다시 채우므로 티가 덜 났다.
$1600 처럼 장면 전환 때 새로 채워지는 자리는 옛것으로 덮으면 치명적이다.

**이 위험은 창 크기와 무관하게 원래 있던 것이고, 창을 넓히면서 드러났다.**

### 8-2. 곁가지 — Lua 부하

0.3.41 계열은 프레임마다 SATB 주소를 통째로 로그에 찍고 flush 한다.
거기에 침범 감시(64 슬롯 스캔)까지 얹혔다.  FPS 0 에는 이것도 섞여 있을 수 있다.
**원인을 가르기 전에 진단 로그부터 줄일 것.**

### 8-3. 다음 시도 — B 안이 안전하다

```
A  창을 넓히되 게임이 쓴 적 있는 구간을 제외
   정주행하며 "한 번이라도 참조된 word" 지도를 만들어야 한다.  비싸고 느리다

B  창은 그대로 두고, 침범이 감지되면 그때 자리를 옮긴다        ★ 권장
   allocator 는 이미 조각마다 다시 고른다.  그 주기를 프레임 단위로 당기는 것
   구조를 크게 안 바꾸고 침범을 실시간으로 피한다

### 9-2. ★ 결론 — 효과음이 자막 경로를 깨운다

```
기준판(원본 BIOS)은 퀸 병원을 정상으로 지난다.
문지기 두 줄을 NOP 한 allvoice BIOS 에서만 멈춘다.  Lua 는 무관하다.
그 자리는 **음성이 나오는 데가 아니다 -- 효과음이다** (소유자 확인)
```

⚠ **`rate == $0E` 가 효과음을 걸러준다고 적었던 것은 틀렸다.**
효과음도 같은 속도로 난다.  실제로 효과음을 막고 있던 것은 **끝주소 신원 검사**
(`$22A6`/`$22A7`)였고, allvoice 는 바로 그것을 지웠다.

그래서 효과음마다 자막 경로가 깨어나고, 장면 전환·CD 읽기 도중에 상주부가
AC/VRAM 을 만지면서 게임과 부딪힌다.

(과거 기록과도 맞는다: "효과음이 대사 자막을 띄우던 것"은 열쇠를 끝주소만으로
잡던 시절의 같은 뿌리다.  지금 열쇠가 `sector + 끝주소` 인 이유이기도 하다.)

★ **selector 를 만들 때 그대로 재발한다.**  selector 는 신원 검사를 "값 읽기"로
   바꾸는 것이라, 효과음도 그 경로를 지나가게 된다.  그러므로 selector 에는
   **효과음을 걸러내는 수단**이 반드시 함께 들어가야 한다.

```
막는 법 후보
  1  팩 조회 결과로 거른다      열쇠가 표에 없으면 아무것도 안 한다   ★ 제일 자연스럽다
     -> 효과음은 팩에 없으므로 저절로 걸러진다.  추가 조건이 필요 없다
     -> 다만 "조회 미스일 때 아무것도 건드리지 않는다"가 보장돼야 한다
        지금 상주부가 조회 전에 VRAM/AC 를 만지면 그 보장이 깨진다.  확인할 것
  2  안전한 때인가를 따로 본다   장면 전환 / CD 읽는 중이 아닌가
     CD_READ 래퍼는 이미 우리 것이다 (boot_hook · §1-1 $FFD4)
     읽기 시작에 잠그고 끝에 푸는 것이 싸다
```

1 번이 옳은 설계로 보인다 -- 효과음을 이름으로 구분할 방법이 없으니
**"팩에 있는 것만 뜬다"** 가 곧 필터다.  2 번은 그 위에 얹는 안전장치다.

### 9-3. 왜 지금까지 안 걸렸나

자막이 음성 하나에서만 떴기 때문이다.  문지기가 나머지를 다 막고 있었으니
전환 중에 깨어날 일이 없었다.  **allvoice 시험판이 아니었다면 selector 를

### 10-2. 그래서 무엇인가

Lua 가 아니고 디스크(0.4.6.10)도 아니다.  남는 것은 **allvoice BIOS 로 열어 둔
자막 경로**다.  게다가 그 장면이 **자막이 처음 뜨는 자리**라는 것이 결정적이다.

```

그런데 이 장면은 초상화가 올라오는 컷신이다 -> 게임도 같은 것을 만진다
=> 부딪힌다
```

§9 의 "문지기가 원인" 과 같은 뿌리이고, **§9 와 별개 사건이 아니다.**
퀸 병원 건과 이 건은 같은 원인의 두 발현으로 보는 것이 맞다.

### 10-2b. 그 음성은 특별하지 않다 (실측)

"이 음성이 문제인가" 를 먼저 의심했으나 **아니다.**

```
ADPCM_008FA4  rate=0E  len=FFB4
바로 앞 10 개  rate=0E  len=FFCB FFE5 FFAC FFAC 1F9F FFC4 FFC3 6793 FF92 FFB3
              -> 길이도 속도도 같은 부류.  전부 무사히 지나갔다
len 0xF000 이상인 클립이 317 개나 된다 -- FFB4 는 흔한 값이다
```

**그리고 END 이벤트가 찍혔다.**

```
START seq=251 frame=25075
END   seq=251 frame=25596      <- 음성은 끝까지 재생됐다
```

재생 중에 죽은 것이 아니라 **끝난 뒤**에 죽는다.  그러므로 범인은 음성이 아니라
그 다음에 오는 것이다 -- 자막을 지우고(복원) 다음 장면으로 넘어가는 구간.

⚠ 소유자 확인: **장면 진입마다 자막이 계속 나왔다.**  즉 "여기서 자막이 처음
떴다" 는 것이 원인이 아니다.  앞에서도 자막은 계속 떴고 멈추지 않았다.
남는 차이는 **이 장면 자체**다 (국장 초상화 컷신).

```

현재 테스트 기준:

```
게임 빌드    C:\snatcher\build\patch\0.4.6.10
바이오스     정상 바이오스
대상 음성    ADPCM_008FA4_FFFF_0E
증상         자막이 끊긴 뒤 다음 대사로 넘어가지 않고 게임 정지
```

allvoice가 아닌 정상 바이오스에서도 재현됐다. Lua를 끈 상태에서도 통과하지 못했으므로,
현재까지는 Lua 자막 훅 단독 원인으로 볼 수 없다.

### 14-2. 0.4.10 진단 결과

진단 스크립트:

```
C:\snatcher\lua\SUB\0.4.10.lua
덤프        C:\snatcher\dump\probe_voice_freeze_008FA4_irq_writer_0410.tsv
```

덤프는 정상 생성됐다. 핵심 헤더 상태:

```
reason=auto IRQ loop: E736 x256 in one frame
frame=493 active=true ended=false
adpcm_playing=1
lock20F4=$00 lock20F5=$06 lock20F6=$20
irq_mask=$FF irq_status=$FF
```

확인된 실행 반복:

```
$E736 -> $E739 -> $E742 -> $E74C -> RTI
```

`$E74C`에서 `$20F2`에 `$00`을 쓰는 주체는 BIOS IRQ 루틴 자체다.
한 프레임에 256회 반복되고, 스택 포인터가 `$B2`에서 `$9E` 방향으로 계속 감소했다.
따라서 IRQ가 정상적으로 복귀하지 못하고 중첩되는 상태가 직접적인 진행불가 원인으로 보인다.

중요하게도 이 덤프 시점에는 `VOICE_END`가 발생하지 않았고 `adpcm_playing=1`이었다.
즉 음성 종료 후 자막 정리 단계가 아니라, 대상 음성 재생 중 CD/ADPCM IRQ 처리가 먼저 꼬인다.

### 14-3. 아직 모르는 것

`$E74C`는 반복되는 BIOS 증상 지점이지 최초 원인 지점이 아니다.
대상 음성 시작 직후 `$E6B6`에서 `$20F5`를 반복해서 읽는 것은 확인했지만,
그 전에 `$20F5` 또는 CD/ADPCM 상태를 바꾼 최초 writer는 아직 잡지 못했다.

## 14. ★★★ 정정 — 기준판 0.4.6.10 도 `008FA4` 에서 멈춘다 (출하 막는 건)

§9·§10 은 "원본 BIOS 는 정상" 을 전제로 썼다.  **그 전제가 틀렸다.**
소유자가 정상 BIOS + 0.4.6.10 디스크 + Lua 없음으로 재현했고, 같은 자리에서 멈춘다.

### 14-1. 프로브가 잡은 것 (`lua/SUB/0.4.11.lua`)

```
reason=auto IRQ loop: E736 x256 in one frame  frame=493  active=true ended=false
current_key=ADPCM_008FA4_FFFF_0E

pc=$E736  sp=$A1  a=$85  x=$A6  y=$05  p=$00
irq_mask=$FF  irq_status=$FF
lock20F4=$00  lock20F5=$06  lock20F6=$20
adpcm_playing=1  read=$017D  length=$FE82  rate=$0E
selector = 78 30 00 00 68 0E        <- 정상 BIOS 맞다 (E6800_0E 하드코딩 그대로)
eng165=$00 eng167=$79 eng276=$C8 eng281=$BF   <- base $7900.  allocator 안 돎
```

반복되는 것:

```
IRQ_LOCK_WAIT   $E736
IRQ_STATE_READ  $20F5   (한 프레임에 256 회 이상)
IRQ_READ        $1803   CD-ROM 인터럽트 상태
```

**BIOS 의 잠금 변수 `$20F5` 가 `$06` 인 채로 안 풀린다.**  `$E736` 의 대기 루프가
그것을 기다리며 IRQ 를 끝내지 못한다.  ADPCM 은 계속 재생 중이다.

### 14-2. 무엇이 아닌가 (프로브가 배제한 것)

```
자막      selector 가 하드코딩 그대로다.  이 음성에는 자막이 안 뜬다
allocator base 가 $7900 (기본값).  Lua 는 돌지 않았다
디스크    Track02/24 는 해시 일치본이다
```

즉 §10 에서 "장면 자체가 원인" 이라 한 것도 부정확하다.  **BIOS 잠금 문제**다.

### 14-2b. 자막 팩은 이미 배제돼 있다 (소유자 확인)

지금 멈추는 판(0.4.6.10)은 **자막 내용이 없는 판**이다.  팩에 들어 있는 것은
글리프와 색인뿐이고, `selector` 는 `E6800_0E` 하나로 하드코딩돼 있다.
프로브가 찍은 것도 그것과 맞는다.

```
selector = 78 30 00 00 68 0E      008FA4 와 안 맞는다 -> 이 음성엔 자막이 안 뜬다
eng167=$79  eng276=$C8            base $7900 기본값
```

그러므로 "자막을 그려서 멈춘다" 는 설명은 **성립하지 않는다.**
남는 것은 BIOS 에 넣은 셋뿐이다 (§14-3).

### 14-2c. 소유자 관찰 — 자막이 사라질 무렵이다

⚠ **이 절은 관찰이지 규명이 아니다.**  아래 두 줄만 실제로 본 것이고,
그 뒤는 전부 아직 확인 안 된 추측이다.

```
관찰 (소유자, 2026-08-28)
  앞 음성에서 자막이 떠 있었다      E6800_0E (하드코딩된 그 하나)
  그 자막이 사라질 무렵 멈춘다
```

프로브가 찍은 값과 나란히 두면 이렇다:

```
프로브 (기계가 잰 것)
  selector = 78 30 00 00 68 0E     008FA4 와 안 맞는다
  eng167=$79 eng276=$C8            base $7900 기본값
  adpcm_playing=1                  008FA4 재생 중
  lock20F5=$06                     안 풀린다
  pc=$E736                         IRQ 대기 루프
```

**아직 모르는 것**: 자막 뒷정리(헬퍼의 VRAM 복원)가 이 잠금과 실제로 부딪히는지.
그럴싸하지만 **재본 적이 없다.**  아래 시험이 그것을 가른다.

### 14-2d. 그래서 이것부터 재면 된다 (제일 싼 시험)

```
앞 자막 없이 008FA4 만 재생시킨다
  통과   -> 앞 자막이 있어야 멈춘다.  뒷정리 쪽을 파면 된다
  멈춤   -> 자막과 무관.  §14-3 이분 탐색으로 간다
```

세이브스테이트가 있으므로 그 자리만 반복하면 된다.
**어느 쪽이 나오든 그때 결론을 적는다 -- 지금은 비워 둔다.**

### 14-3. 다음에 할 것 — 이분 탐색

우리가 BIOS 에 넣은 것이 셋이다.  어느 것이 `$20F5` 잠금과 부딪히는지 가른다.

```
1  CD_READ 훅          $E009 -> $FF0D 래퍼            (0.4.6.0 부터)
2  상주 케이브          $FEC4.  매 프레임 돌고 AC 를 만진다 (JSR $BF32)
3  접수처 복구          $FFD4 스텁 + bank1 $F054.  PHP/SEI + TAM #$80
```

가르는 법:

```
0.4.6.6  (접수처 복구 **없음**) 로 그 장면      멈추면 -> 1 또는 2
0.4.6.9  (복구 있음 · 래치 가드) 로 그 장면      0.4.6.6 이 정상이면 -> 3
```

⚠ 3 번이 유력해 보인다.  `TAM #$80` 으로 bank1 을 `$E000-$FFFF` 에 매핑하는 동안
**IRQ 벡터가 전부 `$FF`** 가 된다 (0.4.6.7 크래시의 원인, §1-1).  `PHP/SEI` 로
막았지만, 그 구간에서 **CD/ADPCM 인터럽트가 지연되면** BIOS 가 기대하는 순서가
깨질 수 있다.  `$20F5` 는 그 순서를 지키는 잠금으로 보인다.

### 14-4. 왜 이제야 나왔나

**0.4.6.x 로 이 지점까지 간 사람이 아무도 없었다** (집·환경 B 모두).
"0.4.6.10 은 검증됐다" 는 말은 **접수처 근처까지**에 한해 참이었다.
