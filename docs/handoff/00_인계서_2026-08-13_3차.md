# Snatcher PCE-CD 한글화 조사 인계서 — 2026-08-13 3차

## 0. 이번 인계서의 범위

이 문서는 동적 글리프 연구를 잠시 보류한 뒤 조사한 **저장 후 특수 재로드 화면 깨짐**과,
그 과정에서 확인된 빌드 보존 문제를 인계한다.

현재 우선순위는 다음과 같다.

1. 기존 정적 완성형 glyph/AC 구조는 당장 변경하지 않는다.
2. ROM·빌더·훅에 버그 수정은 아직 구현하지 않는다.
3. 저장/재로드 버그는 읽기 전용 Lua로 원인만 특정한다.
4. 에뮬레이터 조작은 사용자가 직접 한다. 조사자는 빌드·로그·덤프 분석을 담당한다.

## 1. 사용자 확인 기준의 정확한 재현 조건

### 재현 경로

```text
게임 중 저장
  → 타이틀로 복귀
  → 게임/에뮬레이터를 재시작하지 않음
  → 같은 실행 세션에서 방금 저장한 슬롯을 다시 로드
  → 자동차 장면과 메뉴가 다시 그려질 때 그래픽/문자 타일 깨짐
```

### 재현되지 않는 경로

- 게임 또는 에뮬레이터를 완전히 종료한 뒤 다시 실행해 세이브를 로드하면 정상이다.
- 현재까지 세이브 파일 자체가 영구 손상됐다는 증거는 없다.
- 일반적인 대사/UI 표시만으로는 쉽게 발생하지 않는다.

### 증상

- 화면 가장자리와 메뉴 주변에 파랑/빨강 세로 줄 및 잡음 타일이 나타난다.
- 메뉴 글자 일부가 깨지거나 한 글자가 사라진다.
- 0.2.26에서도 발생하지만 AC 계열/0.3.1보다 상대적으로 손상이 적어 보였다.
- 재실행 후 로드하면 정상으로 돌아온다.

따라서 현 시점 심각도는 **세이브 손상이나 진행 불가가 아닌 특수 세션 전환 표시 버그**로
평가한다. 기능 심각도는 낮지만 완성도 관점에서는 수정 가치가 있다.

> 주의: 조사 중 자동 입력으로 저장 직후 화면을 보고 너무 일찍 정상/실패를 판정한 적이
> 있다. 최종 재현 조건은 위의 사용자 직접 확인 경로를 기준으로 한다.

## 3. 이미 반증되거나 약해진 가설

### 3.1 “대형 UI atlas가 저장 버그의 직접 원인”

반증 근거:

- 대형 UI가 없는 0.2.26에서도 같은 특수 경로로 깨진다.
- UI가 훨씬 작은 AC_0.1.14에서도 발생한다.

단, 별도의 평상시 글자 누락/989개 UI 문제에는 atlas 크기·index·전송량이 여전히 관련될 수
있다. **저장 재로드 버그와 전체 atlas 문제를 하나로 합치지 말 것.**

### 3.2 “저장 overlay가 한글 런타임 고정 코드를 덮어쓴다”

`SAVE 0.1.2` 결과로 현재 반증됐다.

검사한 0.2.26 고정 영역:

| 구분 | CPU 범위 |
|---|---:|
| renderer preloader | `$5E40-$5FF1` |
| fractional glyph shift | `$64B3-$64E3` |
| font hook | `$648C-$648E` |
| renderer hook | `$66E5-$66E7` |
| fractional-space hook | `$674A-$674C` |
| font wrapper + sector loader | `$7F50-$7FEB` |

확인 결과:

- baseline 6개 영역이 재빌드된 0.2.26 Track 02의 패치 바이트와 모두 byte-exact 일치했다.
- 저장 → 타이틀 → 재로드 동안 `CHANGE_*` 기록은 0건이었다.
- `changed_*.bin`, `at_change_*.bin`도 생성되지 않았다.
- 따라서 고정 코드/훅 바이트 파괴는 관측되지 않았다.

`SAVE 0.1.2` 로그:

```text
C:\snatcher\dump\SAVE_0.1.2_233113.tsv
```

주요 행:

```text
frame 630  baseline captured with MPR2=$68 MPR3=$6A and hooks intact
이후 MPR3가 $69와 $6A 사이를 반복 전환
고정 영역 CHANGE 행 없음
```

프레임 179~183의 `first_write_* pc=$EA9E`는 baseline 이전 초기 CD/프로그램 적재 때
발생했으므로 저장 후 손상 증거로 해석하지 않는다.

### 3.3 Bank `$69` helper cave 단독 원인

AC 빌드의 엄격한 cave POC는 저장 관련 초기 구간에서 `$7171` 경로 적중이 없었다.
또한 0.2.26은 AC helper를 그 cave에 두지 않는데도 동일 계열 버그가 발생한다.

따라서 `$BCD2-$BFFF` AC helper만으로 모든 저장 재로드 깨짐을 설명할 수 없다.
다만 과거 로그의 게임 측 814-byte cave read는 별도의 후기 재로드 단계 문제에 영향을 줄 수 있으므로
완전히 폐기하지 않는다.

## 4. 현재 가장 유력한 가설

### “코드가 파괴되는 것이 아니라 코드 바이트가 그래픽 데이터로 읽힌다”

0.2.26은 원본의 FF/cave 영역에 다음 런타임을 설치한다.

- `$5E20-$5FFF` 부근: record tail helper + renderer preloader
- `$648C`, `$64B3-$64E3`, `$66E5`, `$674A`: 훅/shift 코드
- `$7F50-$7FFF`: font wrapper, sector loader, private state

원본 게임이 타이틀 → 게임 재로드 시 이 bank 영역을 그래픽 원본으로 읽어 VRAM에 다시 올린다면,
원래 `$FF`였어야 할 부분 대신 한글 런타임의 기계어가 타일 데이터로 전송된다. 이 경우:

- RAM의 코드 바이트는 그대로다.
- 재실행하면 정상화된다.
- 잡음 타일/세로 줄이 생긴다.
- 패치 규모가 큰 빌드일수록 증상이 더 심해질 수 있다.

현재 증상과 `SAVE 0.1.2` 결과에 잘 맞으며, 아래 `SAVE 0.1.3` 중간 결과로
**0.2.26에 대해서는 직접 확인됐다.**

## 5. 현재 진행 중인 SAVE 0.1.3

파일:

```text
C:\snatcher\lua\SAVE 0.1.3.lua
```

목적:

- 0.2.26 패치 영역이 CPU에서 **data read** 되는지 기록한다.
- 같은 프레임의 VDC `$0000-$0003` write 횟수를 함께 기록한다.
- 패치 영역 read와 VDC write가 같은 프레임에 집중되면 그래픽 업로드 문맥이라는 직접 증거가 된다.

감시 범위:

```text
$5E20-$5E3F  record tail / fractional helper
$5E40-$5FF1  preloader
$648C-$648E  font hook
$64B3-$64E3  fractional shift
$66E5-$66E7  renderer hook
$674A-$674C  space hook
$7F50-$7FFF  font loader/state
```

출력:

```text
C:\snatcher\dump\SAVE_0.1.3_<시각>.tsv
```

현재 테스트가 시작되어 다음 파일이 열려 있다.

```text
C:\snatcher\dump\SAVE_0.1.3_234053.tsv
```

### 2026-08-13 23:42 최종 분석 — 직접 적중

실행 코드가 자기 명령어를 fetch하는 행을 제외하고, 감시 범위 바깥 caller PC가 읽은 행만
분리했다. 그 결과 저장 후 재로드 구간에서 다음 접근이 확인됐다.

| 감시 범위 | 외부 caller PC | 프레임 | read 수 | 같은 행들의 VDC write 합계 |
|---|---:|---:|---:|---:|
| `$5E20-$5E3F` helper/record tail | `$70BF` | 7582-7609 | 2,618 | 44,634 |
| `$5E40-$5FF1` preloader | `$70BF` | 7585-7609 | 8,673 | 39,869 |
| `$5EBB-$5FF1` preloader tail | `$7064` | 7610 | 311 | 1,464 |

해석:

- `$70BF/$7064`는 한글 preloader 내부 PC가 아니다.
- 외부 게임 루틴이 한글 런타임이 설치된 `$5E20-$5FF1`을 data source로 읽었다.
- 같은 프레임에 대량의 VDC port write가 발생했다.
- 따라서 **원래 그래픽용 데이터 범위에 설치된 한글 런타임 기계어가 재로드 시 VRAM으로
  업로드되는 것이 0.2.26 화면 깨짐의 직접 원인**이다.
- 고정 코드가 덮여 파괴되는 것이 아니라, 정상적으로 남아 있는 코드 바이트가 타일 데이터로
  오인되어 화면에 나타난다.

사용자가 화면 깨짐 재현 완료를 확인한 뒤 로그가 종료됐으며 위 숫자는 최종 로그 기준이다.

추가로 Track 02의 `$70BF` 주변 실제 명령열은 다음 반복 구조다.

```text
B1 12       LDA ($12),Y
20 B0 71    JSR $71B0
C8          INY
C4 01       CPY $01
D0 F1       BNE (loop)
```

`$7064` 경로에도 `B1 12` source read가 존재한다. 즉 단순히 같은 프레임에 우연히 VDC write가
있었던 것이 아니라, `$12/$13` 간접 source에서 순차로 읽은 바이트를 `$71B0` 전송 루틴에
넘기는 실제 게임 루프가 패치 영역을 통과했다.

최종 로그:

```text
C:\snatcher\dump\SAVE_0.1.3_234053.tsv
```

테스트 중에는 열린 파일의 크기가 일시적으로 0으로 보일 수 있다. 테스트 종료/flush 후 다시 읽을 것.

판정법:

- 패치 범위 read + 높은 `vdc_writes` 동시 발생: read-as-graphics 가설 강하게 지지
- 패치 범위 read는 있으나 VDC write 없음: 일반 데이터/검증 read 가능성
- 패치 범위 data read 0건: 다음 단계로 VRAM/BAT/palette 상태 자체를 저장 전후 비교

## 7. 0.2.26 재빌드와 자동 삭제 사고

### 문제

0.2.26을 재빌드한 뒤 잠시 지나면 CUE만 남고 `.bin` 24개가 모두 사라져 실행되지 않았다.
두 번 재현됐다.

원인은 공식 0.3.1 빌더의 일반 빌드 종료 경로가 자동으로 `prune()`을 호출해,
보호 목록에 없는 과거 빌드의 모든 `.bin`을 삭제하는 정책이었다.

문제 코드:

```text
C:\snatcher\extraction\patch\static\build_snatcher_ko_0_3_1.py
```

### 수정

- 일반 빌드 종료 후 자동 `prune()` 호출을 제거했다.
- `--no-prune` 옵션도 제거했다. 이제 보존이 무조건 기본이다.
- 삭제는 사용자가 명시적으로 `--prune`을 실행할 때만 가능하다.
- `PROTECTED`에는 추가로 `0.2.26`을 넣었다.

사용자 정책:

> 빌드 산출물은 자동 삭제하지 않는다. 사용자가 필요할 때 직접 삭제를 명령한다.

### 근거가 확인된 사실

- 저장 파일은 재실행 후 정상 로드된다.
- 버그는 같은 실행 세션의 저장 → 타이틀 → 재로드라는 특수 경로에서 발생한다.
- 0.3.1, AC_0.1.14, 0.2.26에서 같은 계열 증상이 관측됐다.
- 0.2.26의 고정 한글 런타임 코드와 훅은 저장 후에도 변경되지 않았다.
- 0.2.26 baseline은 Track 02 패치 바이트와 정확히 일치한다.
- 대형 UI atlas만으로는 이 저장 재로드 버그를 설명할 수 없다.
- 일반 빌드의 자동 payload 삭제는 제거됐다.

### 근거가 확인된 추가 사실

- 0.2.26에서 외부 게임 루틴 `$70BF/$7064`가 `$5E20-$5FF1`을 data로 읽는다.
- 그 접근과 같은 프레임에 대량의 VDC write가 발생한다.
- 따라서 해당 한글 runtime bytes가 재로드 그래픽 전송에 섞이는 것이 확인됐다.

### 현재 추론

- AC_0.1.14/0.3.1의 더 심한 증상도 같은 공통 원인에 추가 helper/resident 영역이 더해진 결과일
  가능성이 높다. AC 빌드에서는 별도 범위 실측이 필요하다.
- AC 빌드에서는 추가 helper/resident 패치 때문에 오염되는 타일 양이 더 커 보일 수 있다.
- 영구 데이터 손상이 아니라 같은 세션에 남은 그래픽 상태/재구성 경로 문제다.

### 아직 모르는 것

- 실제로 어느 patched range가 data source로 읽히는가.
- 읽는 caller PC와 정확한 destination VRAM 주소.
- BAT, pattern data, palette 중 최초로 잘못되는 것이 무엇인가.
- 원본 일본어판도 같은 특수 경로에서 완전히 정상인지에 대한 동일 조건의 최종 계측 대조.
- 가장 안전한 수정이 reload, read masking, 코드 재배치 중 무엇인지.
