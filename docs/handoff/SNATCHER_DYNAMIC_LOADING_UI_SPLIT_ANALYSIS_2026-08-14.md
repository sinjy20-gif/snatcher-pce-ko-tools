## 3. MPR6 팩 — 실측 결과

### 3.1 라인 키로는 안정적이다

오늘 수집분에서 **같은 원문이 두 팩에 걸친 사례가 거의 없다.**

```
UI    고유 116건   팩 1개 116  팩 2개 0
대사  고유 936건   팩 1개 933  팩 2개 2   팩 5개 1
```

즉 **원문 → 팩 배정은 결정적**이다. 빌드 시점에 배정할 수 있다.

### 3.2 장면 키로도 성립한다 — 단 공용 뱅크를 분리해야 보인다

⚠ 이 절의 초판은 "장면 키 불성립"이라고 썼다. **틀렸다.** 공용 뱅크를 섞어 놓고
전이를 센 결과였다. 순차 로그로 다시 세면 결론이 뒤집힌다.

```
제외 없음     캡처 2770   전이 856   평균 런 3.2
6D 제외       캡처 1799   전이 368   평균 런 4.9
```

`6D` 는 장소가 아니라 **공용/시스템 뱅크**다. 세이브 메뉴·소지품·`見る`·차량·
화자명이 전부 여기 있고 전 구간에 고르게 깔린다(2,770 중 971 = 35%).

`6D` 를 빼면 장소 팩이 **수천 프레임짜리 국면**으로 갈린다.

```
f404   - f6550    72   141캡처 연속
f12883 - f19332   75   국면 6개, 합 143캡처
f19988 - f28748   74   국면 4개, 합 132캡처
f28748 - f36408   77 + 74 교대
f40801 - f45826   76    69캡처       ← 컴퓨터실(가우디)
f53668 - f55015   76    48캡처
```

사용자 동선(본부 → 폐공장 → 본부 → 깁슨집)과 국면 경계가 대응한다.

**정리하면 이렇다.**

```
6D          공용.  항상 상주해야 한다
72 74 75 76 77   장소.  한 장소가 1~2개를 쓴다
71 6E 70    소량.  공용 프롬프트 / 소지품 계열
```

원문 → 팩 배정이 결정적(§3.1)이고 장소가 국면을 이루므로, **팩 기반 동적 로딩의
데이터 전제는 충족된다.**

### 3.2-b 다만 "장소 = 팩 1개" 는 아니다 (원래 지적의 유효한 부분)

`SNATCHER_KO_HANDOFF_2026-08-13.md` §4 는 "MPR6 = 장면(팩) 키"라고 확정했다.
**이 결론은 오늘 수집분에서 반증된다.**

프레임 순으로 팩 전이를 세면 한 세션에서 **394회** 바뀐다. 같은 장소 안에서
`6D` 와 `72` 가 계속 핑퐁한다.

```
f404   72  UI   <원문 5자>
f593   6D  대사  <원문 14자>
f647   72  대사  ます。
f807   72  UI   外へ出る
f809   6D  UI   見る
f810   72  UI   聞く
f813   6D  UI   持物
```

`見る` 와 `聞く` 가 **같은 메뉴 한 화면**인데 팩이 다르다.

해석: `6D` 는 장소가 아니라 **공용/시스템 뱅크**다. 세이브 메뉴·소지품·`見る`·
차량·화자명이 전부 여기 있고, 3개소 플레이 내내 최다(대사 288 · UI 45)로 나온다.
08-13 표에 `6D` 가 없었던 것은 그때 세이브·차량 경로를 지나지 않았기 때문이다.

**따라서 한 장소는 팩을 하나 쓰지 않는다. 2~4개를 동시에 쓴다.**
3개소 플레이가 8개 팩(`6D 72 74 75 76 77 6E 70 71`)을 건드렸다.

이건 동적 로딩을 막지 않는다. 다만 **"장소 = 팩 1개" 전제로 설계하면 안 된다.**
장소 진입 시 그 장소가 쓰는 팩 **집합**을 통째로 올려야 하고, 공용 팩(`6D`)은
상주여야 한다. 줄 단위 스와핑은 불가능하다 — 한 메뉴 안에서 팩이 갈리기 때문이다.

### 3.3 규모

마스터에서 팩이 기록된 행은 1,793건이다(전체 7,395 중).

```
6D  503    75  498    74  372    76  226
77   91    72   79    6E  15     71   7    70   2
```

레코드 128 B 로 환산하면 팩 태그된 분량은 약 **229 KB**. 현재 출하 레코드
2,334건 = 299 KB 와 비교하면 77%가 이미 팩 귀속을 갖고 있다.

## 4. 동적 로딩 — 해결하는 문제가 무엇인가

사용자 제안 구조는 이렇다.

```
게임 시작 → 첫 대사 훅 → MPR 확인 → 시작 장면 팩 적재
자동차 이동 → "차에서 내린다" 훅 → 목적지 판별 → 다음 팩 선적재 → 진입
```

**훅 지점 선택은 정확하다.** 차량 이동은 게임 자신이 이미 CD 를 크게 읽는
구간이라 우리 적재를 숨길 수 있는 유일한 자연스러운 지점이다.

문제는 **이 설계가 없애는 비용이 지금 어디에도 없다는 것**이다.

### 4.1 공간은 남지만, 시간은 안 남는다 ★ 정정

```
AC 사용   309,248 B / 2,097,152 B = 14.7%
scene 영역 capacity  1,638,400 B   현재 사용 약 130 KB
```

공간 압박은 0 이다. 번역이 3배가 되어도 안 찬다.

**그러나 부팅 로딩 시간이 실사용상 문제로 제기됐다.** 이 문서 초판은 그 비용을
"전원 사이클당 1회"라며 넘겼는데, 실측 환산하면 넘길 크기가 아니다.

```
초기 적재 50 청크 x 188 ms/호출  =  약 9.4 초
```

**따라서 오버레이의 존재 이유는 공간이 아니라 시간이다.** 아래 §5.5 로 이어진다.

### 4.2 재생 중 CD 접근은 이미 0 이다

0.3.4 가 25개 팩을 초기화 때 전부 올린다(422 KB, 52 청크 + 3 섹터).

```
0.3.3-preload 실측  packloads = 0  cdreads = 0  전 구간
```

동적 로딩은 이걸 **되돌리는** 방향이다. 얻는 것은 부팅 로딩 422 KB → 약 150 KB,
잃는 것은 장소 전환마다 60~100 KB 적재와 그 타이밍을 게임 읽기와 겹치지 않게
맞추는 책임이다.

`ui_load_v11_180102.tsv` 에서 우리 적재가 게임 읽기 구간에 떨어진 5건이 5건 모두
게임의 다음 읽기를 13 → 22~30 프레임으로 밀어냈다. **그 위험을 다시 들여온다.**

### 4.3 병목은 CD 가 아니다 — 이미 기각됐다

```
0.3.3-preload   packloads=0 · cdreads=0 인데 버벅임 9회 그대로
독립 방증        CD 배속을 올려도 동일하게 끊김
```

## 5. UI 976행 분할 — 효용 검토

### 5.1 UI 도 장면 매칭이 가능하다 (신규 확인)

`runtime_text_audit.lua` 는 UI 캡처에도 `pack` 을 찍는다. 오늘 수집분에서
**UI 117행 전부 팩이 기록돼 있다.**

```
UI pack   6D 45 · 72 23 · 74 17 · 75 11 · 77 11 · 76 7 · 70 2 · 71 1
```

다만 `ui_text.tsv` 에는 `pack` 열이 **없다.** 마스터는 스튜디오가 캡처 매칭 시
MPR6 를 찍어주는데 UI 표에는 그 경로가 없다. 즉 데이터는 이미 나오고 있고
**옮겨 담는 일만 안 돼 있다.**

정적 경로는 못 쓴다 — `all_disc_offsets` 가 채워진 UI 는 976행 중 58행뿐이고
918행은 비어 있다(런타임 수집분이라 디스크 오프셋이 없다).

### 5.2 그런데 분할해도 병목은 안 줄어든다

병목의 정체는 측정돼 있다. **레코드 재구성 비용 × 화면의 항목 수**다.

```
메뉴 한 화면 = 레코드 13건 재구성, 연속 10프레임
프레임당      1건 10~17 스캔라인 · 3건 29~50 (0.3.3-glyphopt 후 20~33)
```

이 비용은 팩이 AC 어디에 있든, 언제 올라왔든 **동일하다.** `copy_record` 는
이미 AC 에 있는 레코드를 WRAM 으로 재구성하는 비용이고, 분할은 "AC 에 언제
올리느냐"만 바꾼다.

즉 **UI 를 나눠 담아도 메뉴를 열 때 13건을 재구성하는 것은 그대로다.**

### 5.3 그런데 부팅 로딩에는 UI 가 지배적이다 ★ 이것이 결론을 뒤집는다

```
팩 총량 298,752 B 중
  ui            122,112   41%    ← 단일 최대
  scene 21개    121,216   41%
  shared         42,368   14%
  speaker         7,040
  small_scenes    6,016
```

**UI 팩 하나가 전체 팩 데이터의 41% 다.** 부팅 로딩의 최대 지렛대가 여기 있다.

| 선적재 집합 | 초기 적재 | 청크 | 188 ms 환산 |
|---|---:|---:|---:|
| 전부 (현재 0.3.4) | 405,248 | 50 | **9.4 초** |
| 공용 4팩만 | 284,032 | 35 | 6.6 초 |
| 공용 4팩 − UI | 161,920 | 20 | 3.8 초 |
| 공용 + 구역분할 UI (6 KB) | 167,920 | 21 | **3.9 초** |
| 선적재 없음 (0.3.3) | 106,496 | 13 | 2.4 초 |

**UI 를 구역 단위로 쪼개 현재 구역 것만 상주시키면 부팅이 9.4 → 3.9 초다.**

### 5.4 UI 를 통째로 수요적재하면 안 되는 이유가 곧 분할의 이유다

`見る`·`調べる`·`聞く` 는 모든 장소에 있다(occurrences 50·48·37). 단발 라벨은
194개뿐이므로 "장소 전용으로 뺄 수 있는 건 25 KB 뿐"이라는 계산은 맞다.

그러나 그건 **공용/전용을 나눠 담는** 문제이지 분할이 무의미하다는 뜻이 아니다.

```
UI 를 선적재에서 빼기만 함     첫 메뉴에서 122 KB 를 한 번에 끌어온다 = 거대한 스톨
UI 를 구역 단위로 쪼갠 뒤 뺌   구역당 2~6 KB.  스톨이 스톨이 아니게 된다
```

0.3.4 가 전부 선적재로 간 이유가 이거다 — 미번역 줄 하나가 팩 5~6개를 부르며
최대 4초 멈췄다. **팩이 크면 수요적재가 못 쓸 물건이 된다.** 분할은 수요적재를
다시 쓸 수 있게 만드는 전제조건이다.

### 5.5 팩 분할은 이미 돼 있다 — 지금 그걸 무력화하는 것은 "전부 선적재"다

25개 팩 구조와 수요적재 경로(`load_package` → `load_blob`)는 **헬퍼에 그대로
살아 있다.** 0.3.4 는 그걸 지운 게 아니라, 전부 미리 올려서 한 번도 안 타게 했다.

빌더 코드가 그 사실을 명시한다.

```python
# Without PRELOAD_PACKS it stops at the atlas and every pack arrives later,
# on first touch, from CD.  With it, the run continues straight through the
# pack blob -- the blob begins at init_total on disc and the packs' AC
# addresses begin at common_base, which resolves to the same number, so one
# contiguous read lands them correctly.
```

즉 선적재는 **"읽기를 더 길게 한다"** 일 뿐이고, 팩 경계와 무관하다. 따라서
**앞쪽 N개만 읽고 플래그를 N 기준으로 나눠 세우면 선택적 선적재가 된다.**

```
현재   PRELOAD_PACKS=1  → 전 팩 flag[i]=i (적재됨)     루프 1개
       PRELOAD_PACKS=0  → 전 팩 flag=$FF (미적재)      루프 1개
필요   앞 N개 = i, 나머지 = $FF                        루프 2개, 약 +12 B
```

**헬퍼 여유 69 B 안에 들어간다.** 팩 순서는 빌더가 정하므로 상주 대상만 블롭
앞쪽에 모으면 된다. 새 훅도, 장소 판별도, 목적지 매핑도 필요 없다.

---

## 6. 구현 난이도 대비 효용

| 안 | 난이도 | 효과 | 판정 |
|---|---|---|---|
| 오염행 정리 | 낮음 (데이터) | 오조회 제거 | **완료** |
| `ui_text.tsv` 에 `pack` 열 | 낮음 (스튜디오 1곳) | UI 분할의 전제 데이터 | **1순위** |
| 선택적 선적재 | 낮 · 중 (빌더 + 헬퍼 12 B) | 부팅 9.4 → 3.8 초 | **2순위** |
| UI 팩 구역 분할 | 중 (빌더) | 위와 결합해 스톨 제거 | **3순위** |
| 장소 전환 훅 프리페치 | **높음** (신규 훅 · 목적지 판별) | 첫 접근 스톨 제거 | 보류 |
| 음성 후 예산 실측 | 낮음 (Lua) | 남은 깜빡임 원인 확정 | 병행 |

### 왜 훅이 필요 없는가

수요적재는 **레코드가 자기 `pack_id` 를 들고 있어서** 첫 접근에 스스로 발동한다.
장소를 판별할 필요가 없다. 훅은 "첫 줄에서 멈추지 않게" 하는 최적화일 뿐이다.

그 최적화가 비싼 이유는 헬퍼 여유다.

```
helper_code_bytes 713 / 여유 69 B
```

장소 판별 + 목적지 매핑 + 적재 스케줄링이 69 B 에 들어가지 않는다. 반면 선택적
선적재는 플래그 루프를 둘로 나누는 **약 12 B** 다. **같은 문제의 90% 를 1/5 비용에
해결한다.**

## 7. 권고 순서

```
1. ui_text.tsv 에 pack 열          스튜디오가 이미 UI 캡처에 MPR6 를 찍고 있다.
                                   옮겨 담기만 하면 된다
2. UI 를 pack 기준으로 분할         구역당 2~6 KB.  공용 라벨(見る·調べる)은 공용 팩
3. 선택적 선적재                    공용 팩 + 시작 구역만.  나머지는 기존 수요적재
   → 부팅 9.4 → 3.9 초 목표
4. 실측                            첫 메뉴 스톨이 실제로 얼마인지.
                                   견딜 만하면 여기서 끝. 아니면 5
5. 장소 전환 훅 프리페치            "차에서 내린다" 지점.  여기서만 훅이 값을 한다
```

**깜빡임과 로딩은 다른 문제다.** 위 전부는 로딩 대책이고 깜빡임에는 영향이 없다.
깜빡임은 `PROBE_ADPCM_STATUS_0.1.1` 로 음성 전후 프레임 예산을 재는 것이 다음 수순이다.
